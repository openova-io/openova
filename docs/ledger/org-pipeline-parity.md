# Organization pipeline parity

Three code paths set up an Organization today. The console pipeline of catalyst-api (`runOrganizationPipeline`), the legacy overlay that this pipeline commits to Git, and the provisioning service under `core/services/provisioning`. The organization-controller (`core/controllers/organization`) is the one place where this work is meant to live.

This file names, for each entry point, the pipeline that serves it today. Then it lists every step of the console pipeline, every resource of the legacy overlay and every cluster write of the provisioning service. For each one it gives the place in the organization-controller that already does the same work, or the word `missing`, and the work package that closes the row.

Every file and line in this file was read at commit `435fea9078d666e9b0d68cb218a12b9ff205bf8b` (2026-11-13). Code merged later can move a line.

## How a row changes

- A package that moves a step into the organization-controller writes the file and line of the new step in the column "Organization-controller".
- A package that deletes a step that nothing replaces deletes the step's row.
- A row whose column "Organization-controller" names a file and line is done: the controller already does that work. The package in "Closed by" deletes the legacy site.
- `python3 scripts/check-org-pipeline-parity.py` checks the form of this file and prints `missing=<n>`, the number of rows whose column "Organization-controller" is `missing`. Its rules are written at the top of the script.

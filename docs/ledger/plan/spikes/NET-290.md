# NET-290: Platform-owned Cilium on the National Cloud's managed Kubernetes (lab test result)

Date: 2026-11-13. Type: lab test on the reference cloud, in two sessions. Result line: **outcome: POSSIBLE-WITH-LIMITS**.

Mechanism M1 holds `policy.cilium`, `node.daemonSets`, `lb.noNodePort` and `cilium.platformOwned`. It survived a scale-out and a minor cluster upgrade with zero failed dials. `gateway.hostPort` is true. `mesh.cilium` was not measured, so the class file must declare it false. That is the limit. M2 was not needed and was not run.

## Question

Can the platform install, own and upgrade its own Cilium on the cloud's managed Kubernetes service (CCE)?

Mechanism M1 is tested first. It uses a standard cluster on the VPC network model. Cilium replaces the service's network plug-in and routes natively over the cloud route table.

## What was run

- **Where.** The reference cloud (Huawei Cloud Stack): the project, the region, one zone.
- **Session 1.** 06:44 to 07:44 UTC.
  - Cluster v1.31, VPC model, kube-proxy mode `iptables`.
  - Cilium 1.19.3 applied with `kubectl`.
  - Kubernetes calls went through the cloud API gateway's per-cluster path.
- **Session 2.** 08:10 to 09:23 UTC.
  - **Network.** One new VPC and subnet with public DNS resolvers. One NAT gateway with an EIP (100 Mbit/s, billed by traffic).
  - **Cluster.** `cce.s1.small`, v1.31.14-r20, VPC model, kube-proxy mode `iptables`. It was created in 4 minutes.
  - **Nodes.** One node pool of `s7n.large.2` nodes (2 vCPU, 4 GiB) on Huawei Cloud EulerOS 2.0. Root volume 40 GB, data volume 100 GB. The pool started with 1 node and was scaled to 2. There was no other VM.
  - **Direct API endpoint.** A second EIP was bound to the API server. `kubectl`, `exec`, `logs` and `/version` then worked directly.
  - **Flux v2.4.0.** Only the source and helm controllers ran. A HelmRelease installed the upstream Cilium chart 1.19.3 into `kube-system`. Every later Cilium change went through this HelmRelease (Helm revisions 1 to 8).
  - **Starting Cilium values.** `cni.exclusive: true`, `routingMode: native`, `autoDirectNodeRoutes: false`, `ipv4NativeRoutingCIDR` = the cluster pod range, `ipam.mode: kubernetes`, `kubeProxyReplacement: false`, Envoy on, Hubble on (relay off), one operator replica.
  - **Changes made later through Flux.**
    - `endpointRoutes.enabled: true` and `rollOutCiliumPods: true`.
    - `kubeProxyReplacement: true` with the API server's internal endpoint.
    - `gatewayAPI.enabled: true` with `gatewayAPI.hostNetwork.enabled: true`, limited to nodes labelled as edge.
    - `envoy.securityContext.capabilities.keepCapNetBindService: true`, with `NET_BIND_SERVICE` added to the Envoy capabilities.
  - **Platform podCIDR copier.** A small host-network Deployment. It copies each node's /24 from the service's `NodeNetworkConfig` annotation `yangtse.io/vpc-router-node-allocated-subnets` into `Node.spec.podCIDR`.
  - **Probes.**
    - A client pod dials every 5 s: a Service by DNS name, a Service, a host-network listener on port 443 of an edge-labelled node, and an external HTTPS site.
    - A watcher records every 20 s: node versions, Cilium readiness, the CNI directory of every node and `podCIDR`.
    - A privileged host pod reads host services, routes and logs.

## Results

### 1. Facts about the service (session 1 unless marked)

- **Add-on catalogue.** 23 templates, none of them a Cilium-based data plane. The word "cilium" appears once: a toleration in volcano 1.16.17.
- **Quota and data volume.** The cluster quota is 50. A data volume must be at least 100 GB (`Data volume size must between 100 and 32768`).
- **Upgrade paths.** Each cluster gets the newest patch of its minor version, so a patch upgrade is not available. The upgrade-paths call lists minor steps up to v1.34.3-r10. From v1.31 (platform `cce.14.20`) the only target is `v1.32.9-r20` (session 2).
- **The service's network plug-in, "yangtse".**
  - It installs a NetworkAttachmentDefinition of type `vpc-router`, eight resource types and two validating webhooks, one of them on every Service.
  - On the host it runs as systemd services: `yangtse` and `yangtse-monit`, next to `kube-proxy`, `kube-proxy-monit`, `kubelet`, `cce-agent` and `docker` (session 2).
  - It creates an ipvlan gateway interface that holds the first address of the pod range as a /16.
- **Node pool sync.** The node pool status reports `TaintSynchronizing` and `LabelSynchronizing` conditions (session 2). A label added by hand to one node stayed for 50 minutes.
- **Node security group.** The group the service creates opens TCP and UDP 30000-32767 and TCP 22 to any source (session 1).
- **Nodes.** Container runtime docker 18.9.0. The upgrade pre-check warns that docker is deprecated and that containerd should replace it.
- **Admission.** Three LoadBalancer Services with `allocateLoadBalancerNodePorts: false` were accepted in a dry run, all with no node port (session 1).

### 2. Joining nodes in a new VPC

- **The cloud's internal resolvers did not answer from a new VPC.** With them, nodes never joined (session 1, error 28 to the cluster manager).
- **With public resolvers and NAT egress, nodes joined.**
  - First node: its VM was created at 08:18:10 and its Node object appeared at 08:21:20.
  - Scale-out node: it registered 1.6 minutes after the pool count was raised.
- **NTP.** The node's NTP server is an internal name that public resolvers do not resolve. Two things depend on it:
  - The upgrade pre-check's node test runs `chronyd -Q` against that server. It hung, and the check failed after about 9 minutes with `wait node condition timeout`.
  - After a public NTP server was added to `chrony.conf` on the nodes, the node test passed.

### 3. Mechanism M1

- **CNI file.** The Cilium agent writes `05-cilium.conflist` and renames the service's `cni.conflist` to `cni.conflist.cilium_bak`. Kubelet then calls Cilium. Every pod started after that was a Cilium endpoint, on both nodes.
- **podCIDR.** The service leaves `Node.spec.podCIDR` empty.
  - The platform copier set it in 34 s on the first node and in 4 s on the scale-out node.
  - The API server accepted the patch.
  - The Cilium agent was Ready right after.
- **Scale-out: passed with no hand step.**
  - The pool count was raised from 1 to 2 at 08:23:56.
  - The node registered, the copier set its range, the Cilium agent was placed and Ready by 08:26:42, and pods scheduled there were Cilium endpoints.
- **Pods started before Cilium.** Three pods kept the service's interfaces: two Flux controllers and one storage controller. They broke once the host route changed and had to be restarted.
  - Cilium's operator restarts only pods labelled `k8s-app=kube-dns`.
  - The service's CoreDNS is labelled `k8s-app=coredns`, so it was also restarted by hand once.
- **The service's agent rewrites the pod-range route (new finding).**
  - About every 90 s, `yangtse-agent` re-adds the node's /24 route on its own ipvlan gateway device. This replaces Cilium's `/24 via cilium_host` route.
  - Route monitor lines: Cilium's route at 08:29:09, the agent's route at 08:30:17 on node 1; the agent's at 08:30:02 and Cilium's at 08:30:15 on node 2.
  - While the agent's route was in place, the host could not reach pods (`connect: no route to host` on kubelet probes). CoreDNS went NotReady, so DNS, Service and host-port dials failed.
  - This explains the unexplained collateral failures of session 1. With a stable route, a cluster-wide deny dropped only the targeted dial; the DNS and host-port dials stayed up.
- **Stopping the agent.**
  - `systemctl stop yangtse-monit yangtse` stopped it. It stayed stopped for 14 minutes and Cilium's routes stayed.
  - The cluster upgrade then refused: `NodeCheck/Exception/Fatal/CheckNodeComponent: CNI Agent is not active`. The agent cannot be stopped in a supported way.
- **The fix that holds: Cilium endpoint routes.**
  - With `endpointRoutes.enabled: true`, every pod has its own /32 route to its own device. The agent's /24 route then carries no traffic.
  - The agent was started again at 08:45:51. Its route came back at once.
  - The client then logged 0 failed dials in 144 lines from 08:45:16 to 08:58:27, through the whole upgrade.
- **Minor upgrade: passed.**
  - From v1.31.14-r20 to v1.32.9-r20, started at 08:46:13 and done at 08:58:27 (12 min). Pre-check took 1 min, the control plane about 6.5 min and the nodes about 5 min (in-place).
  - The API server did not answer for about 2 minutes during the control-plane step. Pod traffic was not affected.
  - The node upgrade rewrote the service's `cni.conflist` on each node (08:55:42 node 2, 08:57:40 node 1). The running Cilium agent renamed it again in the same second: `Renaming non-Cilium CNI configuration file source=cni.conflist destination=cni.conflist.cilium_bak`.
  - The Cilium agents did not restart. `podCIDR` was kept on both nodes. The agent `yangtse` and `kube-proxy` were active again. Cilium reported 30/30 controllers healthy and 2/2 nodes reachable.
  - The upgrade also reset `chrony.conf` to the internal NTP server only.
- **Node reboot: failed in the lab.**
  - One node was rebooted through the compute API at 08:59:05. The VM booted (cloud-init finished at 09:00:54) and the console showed `Failed to start NTP client/server`. Kubelet never listened again, and the node was still NotReady at 09:18 when cleanup started.
  - The kubelet start script runs `ensure_ntp`, which runs `chronyd -q` against the internal NTP name. That name does not resolve in the lab subnet, and the upgrade had removed the public NTP server. This is the likely cause. It was not proven, because there was no host access to the node.
  - What a repair does to the CNI directory was therefore not measured.
- **kube-proxy removal (one node, by hand).**
  - Cilium was switched to `kubeProxyReplacement: true` through Flux. `cilium status` showed `KubeProxyReplacement: True`. Cilium also picked up the service's gateway interface as a device.
  - `kube-proxy` and `kube-proxy-monit` were stopped and their `KUBE-SVC` rules removed. Services and DNS kept working: 0 failed dials in 10 minutes.
  - `cce-agent` ran its "adapt kube-proxy configuration" step every 30 s but did not start kube-proxy again within 10 minutes.
  - The create API offers only `iptables` or `ipvs`. Whether an upgrade or a repair brings kube-proxy back was not measured.
- **Host port and load balancer.**
  - A host-network listener on port 443 answered on the edge-labelled node and was refused on the other node.
  - A private dedicated ELB was created through the ELB API, not through the service's controller. It had a TCP 443 listener with one member: the edge node on port 443, its host port. From the other node's host, the ELB address returned the edge node's answer twice.
  - From a pod on the member node, the same dial failed 3 times. This is the expected hairpin case.
  - No Service had a node port. All 14 Services were ClusterIP.
- **Cilium Gateway in host-network mode.**
  - GatewayClass `cilium` was Accepted. A Gateway on port 80 and an HTTPRoute to the test Service answered `HTTP/1.1 200 OK` on the edge node.
  - First attempts failed with `cannot bind '0.0.0.0:80': Permission denied`. The fix is `keepCapNetBindService: true` plus `NET_BIND_SERVICE` in the Envoy capabilities.
  - The Gateway status stayed `Programmed=False`, reason `AddressNotAssigned`, while it served traffic.

### 5. Outcome

- The four required flags hold on M1, and the mechanism survived a scale-out and a minor upgrade.
- `gateway.hostPort` is true. `mesh.cilium` was not measured, so it must be declared false.
- The service does rewrite two things: its CNI file during an upgrade, and the pod-range route every 90 s. Cilium puts the file back within a second, and with endpoint routes no traffic uses the route. Neither rewrite broke the mechanism.
- The agent process cannot be stopped in a supported way, but it no longer configures pod interfaces.
- The outcome is therefore **POSSIBLE-WITH-LIMITS**, not NOT-POSSIBLE.

### 6. What the vendor must allow (the hypothesis, checked)

- **Pod interfaces.** Confirmed, with a correction. The service's agent cannot be stopped: the upgrade pre-check treats it as Fatal. What is needed is a supported statement that the agent may run while Cilium's CNI file replaces the service's file and the service's file is renamed. A switch that stops the agent's route and CNI-file sync would also do.
- **CNI directory.** Left alone across scale-out. Rewritten by an upgrade and immediately displaced again. Across a node repair it is not measured.
- **podCIDR.** The service must set `Node.spec.podCIDR`, or allow a platform controller to copy it. The copy worked.
- **kube-proxy.** It can be stopped by hand and was not restarted in 10 minutes. A supported "no kube-proxy" mode is needed.
- **DaemonSets.** Privileged host-network DaemonSets with BPF were allowed.
- **Pod-range routes.** The routes in the cloud route table are kept, and cross-node pod traffic used them.
- **Load balancer.** It can target host ports without the service's controller.
- **No revert by an upgrade.** Upgrades rewrite host files: the CNI file and `chrony.conf`. Only what Cilium re-asserts survives.
- **Added.**
  - The internal resolvers and the internal NTP name must be reachable from node subnets. Without them, nodes do not join, the upgrade check hangs, and a rebooted node likely does not come back.
  - Remove the security group rules that open 30000-32767 and SSH to any source.
  - Use containerd nodes.

## What later tasks must take into account

Later tasks must take these into account.

1. **Outcome and scope.** The outcome is POSSIBLE-WITH-LIMITS for mechanism M1. Epic NET-320 may start for single-region Organization workloads only. The class file declares mesh.cilium and encryption.wireguard false until a ClusterMesh test with a reference-class cluster and a WireGuard test pass. Founder decision F6 is still needed.

2. **Required Cilium settings.**
   - The service's node agent (yangtse) re-adds the node's pod-range /24 route on its own gateway device about every 90 s, replacing Cilium's route. Without `endpointRoutes.enabled: true`, host-to-pod traffic fails ("no route to host"), CoreDNS goes NotReady and add-on checks fail. `endpointRoutes.enabled: true` is mandatory on this class.
   - This flap was also the cause of session 1's unexplained collateral dial failures.

3. **The agent must stay running.** It cannot be stopped in a supported way. With it stopped, the cluster upgrade pre-check fails Fatal ("CNI Agent is not active").
   - A minor upgrade (v1.31.14-r20 to v1.32.9-r20) with the agent running and endpoint routes on passed with zero failed dials.
   - The upgrade rewrote the service's CNI file, and the running Cilium agent displaced it in the same second. Certification must cover this displaced state.

4. **podCIDR.** The service leaves `Node.spec.podCIDR` empty. A platform controller that copies the /24 from the NodeNetworkConfig annotation (`yangtse.io/vpc-router-node-allocated-subnets`) worked: scale-out joined with no hand step.
   - Pods that start before Cilium (CCE CoreDNS is labelled `k8s-app=coredns`, not `kube-dns`) keep the service's interfaces. Widen Cilium's operator restart selector, or restart them once at install.

5. **Internal DNS and NTP from node subnets.** Node subnets need the cloud's internal resolvers and internal NTP name to be reachable.
   - With public resolvers only, the upgrade pre-check hangs on `chronyd -Q` ("wait node condition timeout").
   - A rebooted node did not come back (kubelet start runs `chronyd -q` against the internal NTP name). This cause is likely but not proven.
   - Host workarounds such as `chrony.conf` edits are reset by an upgrade.
   - The provider pack must fix this at the network level. Node repair stays unmeasured until then.

6. **Direct API endpoint.** Use an EIP on the API server or a runner inside the VPC. With it, exec, logs, Hubble and `/version` worked.
   - The first kubeconfig fetch right after binding the EIP failed ("Generate role and rolebinding failed ... EOF"). A retry 20 s later worked.

7. **kube-proxy.** The create API offers only iptables or ipvs. kube-proxy was stopped by a host action under Cilium kube-proxy replacement. Services kept working, and cce-agent did not restart it in 10 min.
   - A supported none mode must be requested.
   - Whether an upgrade restores kube-proxy is not measured.

8. **Host-network Gateway.**
   - It needs `envoy.securityContext.capabilities.keepCapNetBindService: true` plus `NET_BIND_SERVICE` to bind ports below 1024.
   - It answers 200 but stays Programmed=False (AddressNotAssigned). Gate checks must not wait on that status.
   - A raw ELB TCP listener to a node host port works without any node port. A pod on the member node cannot reach the ELB address (hairpin).

9. **Nodes and the node pool.**
   - Nodes run docker 18.9, which the pre-check flags as deprecated. A class needs containerd node pools.
   - The service-made node security group opens 30000-32767 and SSH to any source. Whether the service re-adds these rules after removal is still unmeasured.
   - Node pools sync taints and labels (TaintSynchronizing and LabelSynchronizing conditions).

10. **Lab hygiene.** Keep the node pool count as the VM cap; never delete node VMs directly. Session 2 stayed at two VMs, took 73 minutes, and all resources were deleted and checked.

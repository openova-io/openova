# SVC-210 result: the ring switch on the pinned Flux

Date: 2026-11-13
Outcome: works
Flux version tested: v2.4.0 (kustomize-controller v1.4.0, helm-controller v1.1.0, source-controller v1.4.1)
Evidence branch: `spike/SVC-210` in openova-io/openova. It is never merged.

## Question

A ring is switched off by one entry in `spec.patches` of the kit's Flux Kustomization. The entry is a strategic-merge `$patch: delete` for kind `HelmRelease`, targeted by the label selector `catalyst.openova.io/ring=<ring>`. On the pinned Flux, does that entry remove exactly the labelled HelmReleases? Does Flux then uninstall them? Does removing the entry install them again?

## What was run

The workflow is `.github/workflows/spike-svc-210.yaml`. The scripts and fixture are under `tests/spikes/SVC-210/`. There are two jobs, both on `ubuntu-24.04` (runner image 20261111.370.1, docker 28.0.4, helm 3.22.1, yq 4.54.3, jq 1.7).

**Job `cluster`**

1. The job started a k3d v5.7.4 cluster with one server on `rancher/k3s:v1.31.4-k3s1`. This is the k3s version that Sovereigns pin. Traefik, servicelb and the k3d load balancer were turned off. At start, the only Service was `default/kubernetes` (ClusterIP). No NodePort was used at any point.
2. It installed Flux with `kubectl apply` of the v2.4.0 `install.yaml`, the same file that cloud-init applies (sha256 `3aca0de604932df9632c6cc8e7522873d16cdd621d1debcf91293589a6d41afe`). At tag v1.4.0, the go.mod of kustomize-controller pins `sigs.k8s.io/kustomize/api` v0.17.3, `kyaml` v0.17.2 and `fluxcd/pkg/kustomize` v1.13.0. The flux CLI v2.4.0 uses the same modules.
3. The source was a GitRepository on this branch, filtered to the fixture directory. It used the same `ignore` idiom as the Sovereign source.
4. The fixture is a `kustomization.yaml` that lists six "slot" files with one HelmRelease each, plus a Namespace and a ConfigMap. Every HelmRelease installs a chart that renders one ConfigMap. The labels are:
   - three HelmReleases with `operations` (`svc210-ops-a`, `-b`, `-c`; `-b` depends on `-a`)
   - one with `foundation` (`svc210-found`)
   - one with `observability` (`svc210-obs`, which depends on `svc210-found`)
   - one with no ring label (`svc210-plain`)
   - the ConfigMap `svc210-ops-configmap`, which is not a HelmRelease but carries `operations`
5. One Flux Kustomization, `svc210-kit`, used the same settings as the Sovereign kit object: `prune: true`, `wait: true`, `timeout: 5m`, `postBuild.substitute`. Each phase is a `kubectl apply` of that object, which is how cloud-init writes it today. Nothing asked for a reconcile by hand. The generation change alone started each reconcile.
   - p0: no patch
   - p1: the delete patch for `operations`
   - p2: no patch
   - p3: three entries (`operations`, `observability`, and `commerce`, which has no member)
   - p4: no patch
   - p5: a parent Kustomization with `postBuild.substitute` applies, from Git, a suspended kit Kustomization object that carries the delete patch. The stored object is then read back from the API.
6. After each phase the job recorded:
   - each HelmRelease object's name and uid
   - each Helm release's name, revision and status
   - the ConfigMaps
   - the Kustomization's inventory and Ready condition
   - the seconds since the apply, polled every 2 s

**Job `kit-render`**

The flux CLI v2.4.0 ran `flux build kustomization --dry-run` on the real kit path `clusters/_template/bootstrap-kit`. This runs the kustomize-controller build code without a cluster.

- The job worked on a scratch copy of the kit. In that copy:
  - The HelmReleases of slots 11a, 29, 56 and 57 got `catalyst.openova.io/ring: operations`.
  - Every other HelmRelease got a different ring value.
  - No file was added, moved or removed, and `kustomization.yaml` was not changed.
- It made three renders: the original kit, the labelled copy with no patch, and the labelled copy with the `operations` patch.
- It also rendered the substituting parent from p5.
- Run B added three checks:
  - whether a remaining release has a `dependsOn` on a removed release
  - whether any HelmRelease exists in the other `clusters/_template` paths
  - whether any kit object carries `kustomize.toolkit.fluxcd.io/prune: disabled`

## Outcome

works. On Flux v2.4.0, the delete patch targeted by ring label, set in `spec.patches` of a Flux Kustomization, removes exactly the labelled HelmReleases. Flux prunes them and helm-controller uninstalls them. Removing the entry installs them again. Other releases are not touched, and objects of other kinds that carry the label are not touched.

## What follows for the plan

- SVC-220 goes ahead as written, with the delete-patch form. Its switch test can render with `flux build kustomization --dry-run` (flux CLI 2.4.0) or with a scratch `kustomization.yaml`. On today's tree the `operations` numbers are 68 to 64. The test must compute them from the tree.
- This record pins Flux v2.4.0, with kustomize-controller v1.4.0 and kustomize api v0.17.3. A package that depends on this record stops if the pinned Flux differs.
- SOV-765 may render one entry per disabled ring, even for a ring with no member on that Sovereign, because an empty match is not an error. The kit object may sit in Git under a parent that substitutes variables, because `$patch` without braces is not substituted.
- The switch removes HelmReleases only. The slot's Namespace and HelmRepository stay applied, so an empty namespace remains. If a ring that is off must leave no namespace, the label and the patch must also cover those kinds. Today the label is on the HelmRelease only.
- Switching a ring back on is a fresh install (revision 1, new object), not a rollback. Anything a chart deletes on uninstall is lost. Each chart in a switchable ring must be judged for this before the switch is offered.
- Not answered in CI:
  1. How the real charts of each switchable ring behave on uninstall and reinstall: hooks, CRDs, PVCs, webhooks left behind, callers that expect the service. This needs the real kit with real images, on a Sovereign or a large lab cluster.
  2. The end-to-end delay when the switch is a Git commit (Git poll interval plus the parent Kustomization). This needs SOV-765 on a Sovereign.
  3. Whether the cloud-init template renders the entry unchanged. In a Terraform template, `$patch` is not an interpolation sequence, but SOV-765 should render and compare it in its own test.
  4. `dependsOn` edges for rings other than `operations`. Only `operations` was checked here. The rule that a ring depends only on foundation, provider or itself must stay enforced by a check. Not measured: with `wait: true`, a remaining release that depends on a removed one would probably keep the kit Kustomization from becoming Ready.

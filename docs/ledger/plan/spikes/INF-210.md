# INF-210 result: composite resource in an Organization's release, changed placement, moved Primary

Date: 2026-11-19, one session, on origin/main 15d45f42ec. Type: spike, measured in CI on the `local` pack with two regions (three runs of `conformance-local` on lab branches), and with the application-controller's own reconcile code in a lab test. Outcome:

- A yes. The release of an Organization's Application put its composite resource on the host cluster of each region the Application is placed in, in the Organization's namespace. The HelmRelease has no `spec.kubeConfig`.
- B no. The edit route answered 200 to a change of a singleton from region A to region B, in both body shapes. Within 52 seconds the resource in region A was deleted (its release uninstalled) and a new one existed in region B.
- C yes. After an uninstall through the delete route, the composite resource annotated `helm.sh/resource-policy: keep` stayed; the one without it was deleted. Measured twice.
- D no. The first Primary move of an Application made by the install route deleted every composite resource of the two moved Applications, in both regions, and created new ones (new UIDs within 52 seconds): the move renames the release of each region. A second move upgraded the releases in place and every resource stayed. The Primary value itself never moved on the pack: Continuum made no commit in 12 minutes.
- An `active-hot-standby` placement renders the resource in every region: one per region.

## Question

Does a release of an Organization render a composite resource on the host cluster, and what do a placement change, a moved Primary and an uninstall do to it? Four yes/no answers:

- A: the resource is created on the host cluster of the Application's region.
- B: a placement change is refused.
- C: `helm.sh/resource-policy: keep` leaves the resource after an uninstall.
- D: a move of the Primary leaves the resource where it is.

## Measured values

### A: where the resource is created

- Run c, P2: 6 seconds after region A's Kustomization applied the folder, every `LabMachine` existed in region A's cluster, namespace `inf210lab`, the Organization's namespace. Each was owned by the HelmRelease `inf210lab/<app>`, with `targetNamespace: inf210lab` and no `spec.kubeConfig`. Run b gave the same.
- h1 had a second `LabMachine` in region B's cluster (`self` B, `primary` A). h2 had one in region A only.
- Lab test, a target with the tier `mgmt`: the HelmRelease of the region file names `spec.kubeConfig.secretRef: vc-mgmt` and lives in namespace `mgmt`, so the chart would be applied into that vCluster. The install route accepts only `host` unless `CATALYST_PLACEMENT_VCLUSTER_TIERS` is set (`products/catalyst/bootstrap/api/internal/instances/create.go` line 68), and neither the chart nor the kit sets it.

### B: a placement change

Seconds from 14:40:22 UTC, when the last of the four PUTs of run c answered:

| Application | Edit | Route | Region B | Region A |
|---|---|---|---|---|
| s1 | mode and regions | 200 | HelmRelease `inf210-s1` and a new `LabMachine` (UID 3e70cff2) at 21 | HelmRelease pruned at 14:41:08, release uninstalled at 14:41:10, `LabMachine` 42db13e9 gone at 52 |
| s2 | targets with cluster `rtz-B` | 200 | HelmRelease `inf210-s2-rtz-b` and a new `LabMachine` (88f805fc) at 36 | pruned and uninstalled at the same times, gone at 52 |

- Run b: an edit whose target had no `cluster` answered 200. The controller then set `Ready=False`, reason `Invalid`, `spec.placement.targets[0].cluster is required`, and left the resource in region A for 20 minutes.
- By source: the only placement refusals of the edit route are a drop in the number of regions and a change to `singleton` from a multi-region mode, both 409 `placement-transition-blocked` without `?force=true` (`topologyTransitionAllowed`, `products/catalyst/bootstrap/api/internal/handler/applications_update.go` line 1189). No code returns `placement-immutable`.

### C: uninstall with and without keep

| Run | DELETE | HelmRelease pruned | Release uninstalled | k0 | k1 (keep) |
|---|---|---|---|---|---|
| b | 13:51:50 | k1 13:51:57, k0 13:52:59 | k1 13:51:57, k0 13:53:01 | gone at 13:53:15 | there at the end, no `deletionTimestamp` |
| c | 15:05:20 | both 15:06:06 | k1 15:06:06, k0 15:06:08 | gone at 15:06:12 | there at the end |

Helm v3.16.1 keeps a manifest annotated `helm.sh/resource-policy: keep` on uninstall (`pkg/action/uninstall.go` line 210, `filterManifestsToKeep`), and an upgrade that drops such a manifest does not delete it (`pkg/kube/client.go` line 452).

### D: a move of the Primary

First move, to region B (run c, PUT at 14:40:22, 200):

- The install route writes the Application without targets, and the controller renders the release `<app>` in each region. The edit's targets switch it to the per-cluster fan-out, which names the release `<app>-rtz-a` and `<app>-rtz-b`. Region A's Kustomization pruned `inf210-h1` and `inf210-h2` at 14:41:08. helm-controller started the install of `inf210-h1-rtz-a` at 14:41:10.678 and uninstalled `inf210-h1` at 14:41:10.770.
- `LabMachine` h1 in region A: UID 10f5384f, then 7e8da2ca. h1 in region B: a2ba2cb7, then 082b0e2e. h2 in region A: e784e620, then c5acc45b. All were new 52 seconds after 14:40:22.
- `openova.topology.primary` stayed region A in both regions for the 12 minutes. The Continuum document (`dr.openova.io`) with `desiredPrimaryRegion` B was applied in both regions. The continuum controller made no commit to the Org repo (every commit after the PUT is the application-controller's) and logged nothing after its leader election. h2 stayed in region A.

Second move, back to region A (PUT at 14:52:52, 200):

- The HelmReleases were upgraded in place at 14:53:03 (`release config values changed`: the value `_openova_standby: true` of region A's leg was removed). Every `LabMachine` kept its UID.

Lab test, on Applications with targets:

- A Primary move adds and removes no region file. The controller changes the Continuum document only. The commit the continuum controller makes (`regionfile.SetTransitionFields`, applied by the test) changes `openova.topology.primary` in each existing leg, and a re-render keeps it.
- So a chart that renders in every leg keeps its resources through a completed move, as P3b measured for an upgrade. A chart that renders only in the Primary leg drops the resource from the old region's release, and Helm deletes it there unless it carries the keep annotation.

### Two more findings

- `GET …/applications/{name}/placement` answered `"targets": []` with `"derivedFromRuntime": false` for every lab Application. The placement read derives targets from where Pods run, and a chart that renders only a composite resource runs none. The journeys' move builds its body from that list. With an empty list it sent `targets: []`, and the route answered 400 `placement.mode is required when placement is set` (run b).
- The edit route accepts a target without `cluster` (200), and the controller refuses it afterwards (`Ready=False`).

## Answer

A yes. B no. C yes. D no.

## What later stories must take into account

1. INF-240: A is yes, so no fix is needed for where the composite resource is created. `bp-virtual-machine` must declare no vCluster tier: with a tier, the chart is applied into that vCluster (lab test).
2. INF-240 and SVC-185: B is no and D is no, so SVC-185 (the Blueprint declaration that pins an Application to its region, refused with 422 `placement-immutable` by the install route, the edit route and the Primary move) becomes a blocking dependency of INF-240. Without it, a region change deletes the virtual machine in the old region within a minute and creates a new one in the new region.
3. INF-240: `bp-virtual-machine` offers `singleton` only. An `active-hot-standby` or `active-active` placement renders the composite resource in every region: one virtual machine per region.
4. INF-240: C is yes, so `deletionProtection` can be the keep annotation and section 4.4 stays as it is. A kept composite resource belongs to no release after the uninstall; in both runs it stayed to the end.
5. SVC area, for the install and edit routes: the first edit of an Application made by the install route renames its release in every region, which deletes and re-creates every resource of the chart. That holds for every Blueprint, not only virtual machines, and for a Primary move too. The install route must write the targets that the edit route writes, or the controller must keep the release name when targets appear.
6. INF-240 and INF-260: the placement read gives no targets for an Application whose chart runs no Pod, so the journeys' move (and a console move built the same way) cannot be made for a virtual machine. A walk of INF-G03 builds its edit from the Application's own placement.
7. The local pack, for every later lab and for INF-G03 in mode `application` on it: the Organization funnel stops there without `CATALYST_GITOPS_TOKEN`. The organization controller makes no Environment while the Organization's vCluster is not Ready. Region B has no Gitea and no Keycloak, so region B's folder is not delivered. The local kit has no slot 62, and with slot 62 added Continuum made no commit.

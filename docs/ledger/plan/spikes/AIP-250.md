# Lab test AIP-250: the agent workspace on the Organization's own sign-in with a short-lived tool identity

Outcome: **fail as shipped, on T2, T3 and the `create_application` half of T4.** T1 passes. T2 and T3 pass in the lab with one change each, and both changes were measured. T4's `create_application` needs a token that nothing issues today. Date of the runs: 2026-11-19. The machine-readable values are in `docs/ledger/plan/spikes/AIP-250.yaml`.

## Question

Can the agent workspace (`bp-agenity`: a workspace daemon built outside this repository, with Claude Code inside it) run on the Organization's own sign-in and a short-lived tool identity? That means no credential seeded from the Sovereign and no one-year bearer. The binary tests:

- **T1.** A person signs in with the Organization's own plan, and the credential is never a Secret object.
- **T2.** The sign-in survives a restart, with one refresher.
- **T3.** The tool path works on a bearer of at most one hour that is renewed without a restart.
- **T4.** `list_applications` answers, and `create_application` answers for a person of tier admin.

The lab also had to settle two choices:

- **Where the sign-in lives.** (a) A person signs in inside the workspace and the credential stays on the workspace's volume. (b) A route of each Organization writes it to OpenBao, and the workspace reads it by mount.
- **Whose identity the tool path carries.** (a) The workspace forwards the signed-in person's own short-lived session. (b) An agent token with an acting-person claim and one entry in the mutation table.

## Read in the source, at the pins

Claude Code 2.1.185, read from the strings of the native binary of the npm package above:

- **Where the credential lives.** It is a plain file, `<config directory>/.credentials.json` (storage `plaintext`). The config directory is `CLAUDE_CONFIG_DIR`, or else `~/.claude`.
- **Where it signs in and refreshes.** The token endpoint is `https://platform.claude.com/v1/oauth/token`, with the client identifier of Claude Code.
- **Refresh across processes.** A refresh takes the lock file `<config directory>/.oauth_refresh.lock`, which goes stale after 10 s. A process re-reads the file when its modification time has changed.
- **When a headers helper runs.** For an HTTP or SSE tool server, the `headersHelper` runs when the transport is created. Its headers are then fixed in the transport's `requestInit`.
- **Tool search.** It is on for the provider's own host unless `ENABLE_TOOL_SEARCH` turns it off. With it on, the model is first offered a search tool, not the tools of each tool server.

The workspace daemon at `bcd38b15816694e82bddbbc9d6385ff3de00e3cf`:

- **An agent's home.** With the in-pod spawner, an agent's home is the daemon's own home (`internal/runtime/container.go` lines 643 to 646).
- **The credential check before each spawn.** The daemon looks in its vault, then in `~/.claude/.credentials.json`, or at `CHEPHERD_CLAUDE_CREDS_PATH` when that is set (`container.go` lines 763 to 781). It refuses to spawn without a credential.
  - When the credential expires within 60 s, the daemon refreshes it itself, at `https://console.anthropic.com/v1/oauth/token` (`internal/runtime/runtime.go` line 4291).
  - It writes the new pair back only to a vault entry that the spawn names (line 3497).
  - A pair read from the home file is not written back (lines 3489 to 3516).
- **Its sign-in screen** (`internal/runtimehttp/server.go`).
  - It starts a Claude Code process with no credential, shows the address that process prints, and types the person's code into it (lines 3475 to 3500).
  - It then waits 40 s for the credential under `<state>/agents/<name>/home/.claude/` or inside a container (lines 3735 to 3815).
- **Its vault.** The vault is `<state>/vault.json`, encrypted with the key `<state>/vault.key` beside it (`internal/vault/vault.go` lines 140 to 145).
- **No forwarded identity.** It reads neither `X-Forwarded-Access-Token` nor `X-Forwarded-Email` (no match in its source).

This repository at `385718c3d36729388a94fe9959158d187f6b1db1`:

- **How the chart supplies credentials today.** An init container copies the credential from a Secret into an `emptyDir` home, and a sidecar keeps it current from that Secret. The tool server gets `OPENOVA_MCP_BEARER` from a Secret. See `products/agenity/chart/templates/statefulset.yaml` lines 68 to 241, 377 to 382 and 463 to 552, and the files `externalsecret-anthropic.yaml` and `externalsecret-mcp-bearer.yaml`.
- **The sign-in gate passes no token upstream.** `products/agenity/chart/templates/oidc-gate.yaml` has 0 lines with `pass-access-token`. It sets only `--set-xauthrequest=true` (line 212).
- **How the tool server gets its bearer.**
  - The stdio tool server reads `OPENOVA_MCP_BEARER` once, at start (`products/openova-mcp/cmd/openova-mcp/main.go` line 141).
  - Its HTTP transport takes the bearer from each request's `Authorization` header (`http.go`, `bearerFromRequest`). It answers a refused bearer with a JSON-RPC error in a `200` response, never with `401`.
- **Who may call `create_application`.**
  - In the tool server it needs tier admin (`products/openova-mcp/internal/tools/catalogue.go` line 140). `tools/list` offers only the tools that the caller's tier reaches (`internal/tools/registry.go` line 120).
  - An agent token lives at most 3,600 s, carries tier viewer or developer only, and may change nothing at catalyst-api (`products/catalyst/bootstrap/api/internal/agenttoken/agenttoken.go`, `restrict.go`).
  - Run on this host at that commit, the unit tests `TestIssueRefusals/tier_admin`, `TestRestrict` and `TestAgentTokenThroughTheSessionChain` pass. They prove three things: a token of tier admin is refused, an agent token gets `GET /api/v1/org/applications` with `200`, and its `POST` gets `403 agent-token-forbidden`.
- **After the runs, AIP-150 merged** (main `52ae301c793e0ed499d655db514b83a01b38cf9d`). The tool server now caps an agent token's tier at developer, so an agent never sees `create_application`, and its HTTP transport has no fallback bearer. The stdio transport still reads `OPENOVA_MCP_BEARER` once, at start (`main.go` line 146 there). None of the findings below changes.

## Answer

- **Where the sign-in lives: (a), on the workspace's volume.** A person signs in to unmodified Claude Code inside the workspace. Claude Code is the party that spends the refresh token, and it writes the successor back to its own file, under its own lock (E1, E2B, E3). A copy read by mount, as in (b), cannot take the successor back. The mount would go stale after the first refresh, and keeping it current needs a second writer. That second writer is the failure E4 shows.
- **Whose identity the tool path carries: (b), an agent token.** Option (a) cannot be built with the pinned daemon:
  - the gate passes no token upstream;
  - the daemon reads none;
  - the agent acts between a person's requests, after a request-time token has gone.

  An agent token of at most one hour works for reading, once the tool server reads it from a file at every call (arm C). `create_application` needs the acting person's tier admin on that token (arm D), and nothing issues such a token today.
- **The outcome as shipped is fail:** T2, T3 and the create half of T4.

## What follows for the plan

1. **The home on the volume.** The workspace's home (`/home/chepherd/.claude` and `/home/chepherd/.claude.json`) lives on the workspace's persistent volume, not on an `emptyDir`. The credential's only copy is the file Claude Code writes there, so no Secret, no ExternalSecret, no seeding init container and no copy sidecar remain.
2. **No refresh by the daemon.** The daemon must not refresh. Until the daemon stops refreshing credentials that it does not write back, the chart sets `CHEPHERD_CLAUDE_CREDS_PATH` to a file with no refresh token and a far `expiresAt`. That is the measured setting of E4B.
3. **A bearer file for the tool server.** The tool server reads its bearer from a file at every call (`OPENOVA_MCP_BEARER_FILE`, the lab change of 11 lines). A sidecar of the workspace renews that file before half the token's life has passed. It calls `POST /api/v1/internal/agent-tokens` with its projected ServiceAccount token, and replaces the file by rename.
4. **An acting person for `create_application`.** The acting-person claim is added with its reader:
   - catalyst-api issues it only for a person who holds tier admin in that Organization at the time of issue;
   - `MutationsAllowed` gains the one entry `POST /api/v1/org/applications` for it;
   - the tool server takes its tier from it.
5. **The sign-in screen's false error.** In in-pod mode, the daemon's sign-in screen reports a failure after a sign-in that succeeded (E5). The fix belongs to the daemon, outside this repository. Until then, the workspace's own documentation says that the sign-in counts when the agent answers.

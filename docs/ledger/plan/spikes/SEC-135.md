# SEC-135: Key-service seal on the reference cloud (lab test result)

Date: 2026-11-13. Type: lab test. Outcome: **NO**.

## Question

Can OpenBao seal itself with the key service of the reference cloud? Three things have to hold:
- a credential can call encrypt and decrypt on one key;
- that credential can be limited to that one key;
- an OpenBao external seal plug-in from the OpenBao project works against the cloud's key-service endpoint.

The test also asks for the device name that a guest sees for a data disk attached at creation, and whether that name holds after a reboot.

## What was run

- **Where.** The reference cloud, in the platform's own project, in the region of the provider module. All calls were signed with the project's provisioning access key (SDK-HMAC-SHA256). They ran from the platform's jump host, which is an instance in the same project. The credential stayed in process memory only.
- **Software.** OpenBao 2.7.2 (official linux_amd64 tarball, checksum matches the release's checksums.txt). Go 1.26.11. go-kms-wrapping core v2.9.0 and plugin v2.4.0, the versions OpenBao 2.7.2 and openbao-plugins use.
- **Storage.** A single OpenBao process with raft storage on 127.0.0.1. The `file` storage type is gone in 2.7.2 ("unknown storage type file").
- **Throwaway instance.** It was never created. From 06:59 to 07:40 UTC the project had no free VPC (5 of 5) and no free elastic IP (10 of 10). The existing environment, the jump host and three other lab tests running at the same time held them all. The OpenTofu config for the instance was written and initialised, and it created nothing.

### Step 1 details

- Key-service quota: 100 keys, 1 in use before the test. Grants: 100 per key.
- Latency over 20 round trips from the jump host: encrypt median 31 ms, max 37 ms. Decrypt median 32 ms, max 38 ms. All 40 calls returned 200.
- Without a signature, the key-service endpoint answers 401 APIGW.0301, so the route is published.
- The endpoint's TLS certificate passed verification with the system trust store. It comes from a public CA (Sectigo) and expires on 2026-11-26.

### Step 2 details

- **Identity API.** Every identity management call returns 404 APIGW.0101 ("The API does not exist or has not been published in the environment"). The signature is valid. That covers listing users, creating a user, creating a custom policy, creating an agency, listing and creating access keys, temporary security tokens, listing projects and the service catalog. No other identity host resolves. So there is no API path to a second credential, and no API path to a policy that limits a credential to one key.
- **Instance identity.** The metadata service has the security-key path. On the jump host it answers 401 "Please configure Cloud Service Agency first". None of the 14 instances in the project has an agency.
- **Key-service grants.** The grant API exists: list-grants returns 200 and the quota is 100 grants per key. A grant needs a grantee user, and no such user can be created through the API.
- **Result.** The only credential available is the project's static access key. Through the API it cannot be limited to one key.

### Step 3 details

- **Published plug-ins.** openbao/openbao-plugins publishes KMS plug-ins for alicloud, aws, azure, gcp, oci, ovhcloud, pkcs11, securosys and tcloudpublic. There is none for Huawei Cloud.
- **Built-in seals.** OpenBao 2.7.2 builds in only the transit, kmip and static wrappers. Its seal documentation has no Huawei page.
- **Upstream library.** A Huawei wrapper still exists in openbao/go-kms-wrapping. Its last tag, `wrappers/huaweicloudkms/v2.2.0` (2025-02-13), does not compile against core v2.9.0: `undefined: wrapping.WrapperTypeHuaweiCloudKms`. The main branch (pseudo-version v2.2.1-0.20261111111310-9e83ca3366f3) compiles.
- **Plug-in A (upstream).** The 17-line `main.go` of the alicloud plug-in, with the main-branch Huawei wrapper swapped in. OpenBao refused to start: `Error configuring seal "huaweicloudkms": Resource not found: [GET <identity endpoint>/v3/projects?name=<region>] ... APIGW.0101`.
  - Cause: the wrapper's SDK (huaweicloud/golangsdk, 2021-08-31) always looks the project up by name. It then always lists the service catalog. Both calls go to the identity service, and both return 404 APIGW.0101 here. The wrapper takes no project ID and no key-service endpoint.
- **Plug-in B (patched).** The same wrapper with 14 added lines. When a project ID and a key-service endpoint are given, it skips both identity lookups and signs key-service calls directly. Results:
  - Status before init: `type huaweicloudkms`, `recovery_seal true`, `recovery_seal_type shamir`, version 2.7.2.
  - `bao operator init -recovery-shares=1 -recovery-threshold=1` returned 1 recovery key and 0 unseal keys. OpenBao unsealed itself.
  - A kv-v2 value was written and read back.
  - After a process restart the log says "unsealed with stored key", and the value read back equal.
  - Restart with the key disabled: "failed to unseal core ... KMS.0209 The key has been disabled and cannot be used."
  - Key enabled again, then restarted: "unsealed with stored key".
- **Stanzas used (plug-in B).** The credentials were passed through a pipe, not a file.

```hcl
plugin "kms" "huaweicloudkms" {
  command   = "openbao-plugin-kms-huaweicloud-patched"
  version   = "v0.0.2"
  sha256sum = "<sha256 of the binary>"
  env = ["HUAWEICLOUD_ACCESS_KEY=…", "HUAWEICLOUD_SECRET_KEY=…",
         "HUAWEICLOUD_PROJECT_ID=…", "HUAWEICLOUD_KMS_ENDPOINT=https://<key-service endpoint>",
         "TMPDIR=<work dir>"]
}
seal "huaweicloudkms" {
  region            = "<region>"
  project           = "<region>"
  kms_key_id        = "<key id>"
  identity_endpoint = "https://<identity endpoint>/v3"
}
```

- **Plug-in socket.** The plug-in puts its unix socket in TMPDIR (it used /tmp until TMPDIR was set in `env`).

### Step 4 details

- No throwaway instance could be made, so there is no first-boot or after-reboot measurement.
- **Substitute evidence.** It is read-only and comes from the jump host, an existing instance on the same cloud with one data disk:
  - the guest sees the data disk as `/dev/vdb` and the system disk as `/dev/vda`;
  - the compute API's attachment list gives the same names;
  - the guest also has `/dev/disk/by-id/virtio-<first 20 characters of the volume ID>` for each disk.
- Smallest instance flavor offered in the zone: s7n.small.1 (1 vCPU, 1 GiB). Volume types: SSD and SAS.

### Step 5 details

- The key service refuses a deletion period under 7 days: KMS.1401 "Set the pending deletion period between 7 to 1,096 days."
- The test key was scheduled for 7 days. Its state is now 4 (pending deletion), and the cloud deletes it on 2026-11-20. An encrypt call on it is refused with KMS.0210.
- Read calls show 0 VPCs, security groups, elastic IPs, instances and volumes with the test prefix.
- The project's other key was not touched.

## What follows for the plan

- **Decision NO.** The reference pack stays on rank 2 (`static-node-file`). SEC-155 stays dropped.
- **What the vendor would have to allow.** This list goes to the founder.
  1. A credential limited to encrypt and decrypt on one key. That means publishing the identity management API to the tenant (user, custom policy scoped to one key, access key), or creating such a user per region on request. Whether the stack's identity service can scope key-service actions to one key was not measurable here.
  2. Or instance identity: allow a cloud service agency on instances. The metadata service already asks for one. The wrapper would then also have to read temporary credentials from the metadata service, which it does not do today.
  3. For an unpatched upstream wrapper: publish identity `GET /v3/projects` and `GET /v3/auth/catalog` to access-key callers. Without that, the platform must carry the 14-line patch.
- **The mechanism itself works.** With the patch, OpenBao 2.7.2 seals and auto-unseals on this key service, and a disabled key stops the unseal. If the vendor grants item 1 or 2, SEC-155 must build and ship its own plug-in: the alicloud-style `main.go` plus the patched main-branch wrapper. The tagged wrapper does not build. Contributing it upstream would also work.
- **Step 4 is open.** It needs one free VPC and one free elastic IP in the project, and about 15 minutes. Until then `/dev/vdb` is the best evidence for SEC-150, from an existing instance only. `/dev/disk/by-id/virtio-<volume-ID prefix>` is a name that does not depend on attach order.

## What later tasks must take into account

Decision NO; the reference pack stays on rank 2 and SEC-155 stays dropped. Steps 2 and 3 fail on their own, so step 4 cannot change the outcome.

Later tasks must take into account:
- The identity management API is not published here (404 APIGW.0101 on users, policies, agencies, access keys, security tokens, projects and catalog). There is no API path to a credential limited to one key.
- Instance identity needs a cloud service agency. The metadata service answers 401 "Please configure Cloud Service Agency first", no instance in the project has one, and none can be created through the API.
- OpenBao publishes no Huawei KMS plug-in. The tagged upstream wrapper v2.2.0 does not compile against core v2.9.0. The main-branch wrapper compiles but always calls identity /v3/projects and /v3/auth/catalog, so OpenBao fails at seal set-up.
- A 14-line patch (project ID plus key-service endpoint, no identity lookups) makes OpenBao 2.7.2 init, auto-unseal after a restart and read back. Disabling the key blocks the unseal (KMS.0209). If the vendor ever grants a limited credential, SEC-155 must ship that self-built plug-in.
- Credentials reach the plug-in through the plugin stanza `env`. Set TMPDIR there too, or the plug-in socket goes to /tmp.
- Key-service deletion takes at least 7 days. A wipe can only schedule it, and the project has 100 keys at most.
- The key-service TLS certificate is publicly trusted and expires on 2026-11-26.

What is left:
- Step 4 (data-disk device name at first boot and after a reboot) and step 1 from a throwaway instance. They need one free VPC and one free elastic IP in the project, and about 15 minutes.
- Both quotas stayed full for 40 minutes because other lab tests were running at the same time. Run instance-based lab tests one after another, or ask for a quota raise.
- Until then SEC-150's /dev/vdb rests only on an existing instance, where the guest and the API agree. The stable name /dev/disk/by-id/virtio-<volume-ID prefix> is a better choice.

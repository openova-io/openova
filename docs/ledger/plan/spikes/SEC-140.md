## The question

Can a value that is born in OpenBao reach a pod as a mounted file, with no Secret object anywhere? The test asked this for a pod on the host and for a pod inside an Organization's virtual cluster. It answers five things:
- Step 2. Can an External Secrets PushSecret with `updatePolicy: IfNotExists` create the value when its policy gives only `create` on values and `read` and `delete` on metadata?
- Step 3. Does the CSI mount work in a host pod that uses role `workload` and audience `openbao`? What are the exact parameter names of the SecretProviderClass?
- Step 4. Does a pod inside the virtual cluster start with the same volume while its SecretProviderClass sits in the host namespace? Which identity reaches OpenBao?
- Step 5. Does `postgres:16-alpine` start with `POSTGRES_PASSWORD_FILE`? Does the entrypoint shim let an image that reads only plain variables connect?
- Added steps. Does the mount work in a pod with `automountServiceAccountToken: false`? Does a Job created at run time inside the virtual cluster get one mounted object?

## Measured results (run 43358876601 unless another run is named)

### Step 1: install and policies

PASS. The driver's service account cannot create Secrets (`kubectl auth can-i create secrets` printed `no`). The provider ran 1/1.

One difference from the plan: on OpenBao 2.7.2 you cannot generate a root token from the unseal key without a token. `bao operator generate-root -init` uses `sys/generate-root-token/attempt` and got 403 without a token. Since OpenBao 2.5.3 the old token-free endpoints under `sys/generate-root/*` are off by default (`disable_unauthed_generate_root_endpoints = true`). With the init root token, generating a new root token from the unseal key worked. The init token was then revoked (exit code 0), and the rest of the test ran on the generated token.

### Step 2: birth by PushSecret

FAIL for the planned policy, on all three External Secrets versions. The OpenBao audit log shows why. External Secrets always does these things, in this order:
1. It reads the value for the `IfNotExists` check.
2. It writes custom metadata.
3. It writes the value. The key now exists because of step 2, so OpenBao treats this write as an update, not a create.

| Policy variant (same result on 0.10.7, 0.16.2 and 2.14.0) | First refused call | PushSecret | Value in OpenBao |
|---|---|---|---|
| P0 as planned: data `create`; metadata `read`, `delete` | read of `mounted/data/...`: 403 | Errored: "could not verify if secret exists in store" | absent |
| P1: P0 plus data `read` | write of `mounted/metadata/...`: 403 | Errored | absent |
| P2: P1 plus metadata `create`, `update` | update of `mounted/data/...`: 403 | Errored | an empty key with `current_version` 0 is left behind |
| P3: P2 plus data `update` | none | Synced | version 1. After two more refreshes it is still version 1, so `IfNotExists` holds |

So External Secrets can only create a mounted value if its identity can also read and overwrite that value.

The fallback was measured as well: a one-shot Job (image `quay.io/openbao/openbao:2.7.2`). It logs in with its own projected token (audience `openbao`, `automountServiceAccountToken: false`). Its policy is `create` on `mounted/data/NS/*` and `read` on `mounted/metadata/NS/*`.
- **First run.** It created the value at version 1 with `cas=0`, exit 0.
- **Second run.** It found the metadata and exited 0 without reading the value.
- **Probes with the same token.**
  - Refused with 403: reading the value, overwriting it, overwriting with `cas=0`, deleting the metadata, and creating a value in another namespace.
  - Allowed: reading the metadata, and creating a new key in its own namespace.
- **Afterwards.** The value was still version 1 and was not the probe string.
- **Note on `cas=0`.** Under a create-only policy, OpenBao itself refuses the overwrite (403) before check-and-set matters. `cas=0` does no harm, but it is not what protects the value.

### Step 3: host-namespace pod

PASS. A pod with service account `wordpress` in namespace `acme` mounted `mounted/data/acme/sa/wordpress/db-password/e1`. The file's hash matched the OpenBao value. The file is mode 0644, owned by root, 32 bytes, with no trailing newline. No Secret object in the cluster holds the value (0 found).

Parameter names, measured with provider 2.0.3:
- `provider: openbao`
- `roleName`
- `audience`
- `objects`, each entry with `objectName`, `secretPath` (the full API path including `data/`) and `secretKey`

For the address:
- `vaultAddress`, `openbaoAddress` and `baoAddress` all worked (PASS).
- With no address at all, the provider fell back to the chart's agent socket and still worked.
- Provider 1.5.0 is the version that the platform's present OpenBao chart 0.16.0 ships. Its source reads only `openbaoAddress`. That version was not run.

Negative checks:
- Without `audience: openbao` the mount fails. OpenBao refuses the login: "invalid audience (aud) claim". There were 11 such failed logins in the run.
- A pod with another service account (`other`) gets a 403 on the read (17 refused reads).

### Added step: `automountServiceAccountToken: false`

PASS on the host, in both token paths below, and in the virtual cluster. Every pod that the virtual cluster syncs to the host has `automountServiceAccountToken: false` anyway, and they all mounted.

Two token paths were measured:
- **Path A (chart default).** The driver has no `tokenRequests`. The provider mints each pod's token itself through the TokenRequest API. For that it needs a cluster-wide `serviceaccounts/token create` grant from the OpenBao chart. The provider log shows 51 "using self-generated service account JWT" lines.
- **Path B.** The driver has `tokenRequests: [{audience: openbao}]`. The kubelet hands the token to the driver, and the provider logs "using token from mount request" (4 new pods). The provider's binding `openbao-openbao-csi-provider-clusterrolebinding` was then deleted (`can-i create serviceaccounts/token` printed `no`). After that, a host pod and a virtual-cluster pod still mounted (PASS). In path B, a SecretProviderClass without `audience` also works, because the provider picks the `openbao` token by default.

The provider creates one Secret of its own: `openbao/openbao-csi-provider-hmac-key`.

### Step 4: pod inside the Organization's virtual cluster

PASS. The pod starts.
- The SecretProviderClass must live in the host namespace. The virtual cluster has no SecretProviderClass API (0 resources found).
- The synced pod points at the host object by name. This is the one object the host side must provide.

Identity that reaches OpenBao, from the audit log and the provider log:
- **`org1`, the platform's setting (service-account sync off).** Every pod of the Organization runs on the host as `org1/vc-workload-vcluster`, whatever its virtual service account (`app` or `other`). A value at `mounted/data/org1/sa/vc-workload-vcluster/...` was read by pods of both virtual accounts (both PASS). So the host cannot tell two Applications apart. The virtual cluster's CoreDNS pod runs under the same host account.
- **`org2` (service-account sync on).** The host identity is `org2/<sa>-x-<namespace>-x-vcluster`, for example `org2/app-x-apps-x-vcluster`.
  - The same name came back after the pod was deleted and recreated.
  - A pod of the other account (`other-x-apps-x-vcluster`) got a 403 on that path. So isolation works in this setting.
  - When the joined name would pass 63 characters, vcluster cuts it to 52 characters and adds `-` and a 10-character hash. Measured: `wordpress-application-database-client-service-accoun-f3bef471a0` (53-character virtual name). That name was stable across recreation, and a mount at `sa/<that name>` passed.
  - Sync on also creates a host service account for every virtual account, including the virtual cluster's own controllers.

### Added step: Job created at run time inside the virtual cluster

PASS. A Job with one CSI object, created through the virtual cluster's API, completed with exit 0 and logged `mounted-bytes=32`. Its host pod ran as `vc-workload-vcluster`.

### Step 5: images inside the virtual cluster (`org1`)

PASS for both routes.
- **File variable.** `postgres:16-alpine` with `POSTGRES_PASSWORD_FILE=/var/run/secrets/openova/db-password` became Ready.
- **Entrypoint shim.** The client was `postgres:16-alpine` running `psql`, which reads only `PGPASSWORD`. The shim maps the mounted file to that variable and then execs `psql`. It exited 0 and printed "connected as postgres".
- **Shim with a missing file.** It exited 78 with "entrypoint shim: /var/run/secrets/openova/not-mounted is not mounted".
- **Control without a password.** It exited 2 with "fe_sendauth: no password supplied". This shows the server really needs the password that the shim supplied.

### Step 6: clean-up

The kind cluster is deleted when the CI job ends.

## What follows for the plan

- **Step 2 FAIL, so the Job variant applies.** Tier B values are born by a one-shot Job per chart, and `eso-ns` gets no rights on `mounted/`. Three changes follow from what was measured:
  - The Job's policy needs `read` on `mounted/metadata/NS/*` as well as `create` on `mounted/data/NS/*`. Without it, a second run cannot see that the value exists.
  - The Job must treat a key as existing only when `current_version` is 1 or more. A failed writer can leave a metadata-only key at version 0, as P2 showed.
  - The same External Secrets limit hits every other PushSecret into `mounted/`: the peer push of tier B values (the create-only lines planned for `openbao-peer-push`) and the `mountedCopies` PushSecret. Neither can work with create-only rights. They need the Job, or a policy with `read` and `update` on the value.
- **Step 3 PASS. Settings for SEC-211:**
  - Write `openbaoAddress` in every SecretProviderClass. It works in provider 1.5 and 2.0; `vaultAddress` works only in 2.0.
  - Keep `audience: openbao` in every SecretProviderClass.
  - Set the driver's `tokenRequests` to audience `openbao`, and drop the provider's cluster-wide token-mint binding. Both were measured to work.
  - Add `openbao-csi-provider-hmac-key` to the Secret census.
  - Workload pods never call OpenBao; the provider pods and the birth Jobs do. The ingress to port 8200 is needed only from those.
- **Step 4 PASS. The outcome word is `shared`, for the platform as it is configured today.** SEC-214 uses remote key `<slug>/shared/db-password/e1`. Isolation between Applications inside one Organization is not provided, and the record must say so. If the lead architect wants `scope: sa`, there is one change: the Organization controller's vcluster values set `sync.toHost.serviceAccounts.enabled: true` (control-plane area). The producer then has to compute vcluster's name translation, including the cut-and-hash rule for names over 63 characters.
- **Step 5 PASS.** Route 2 (file variable) and route 3 (entrypoint shim) both stand. Exit code 78 for a missing file works as designed.
- **Root token generation.** Any runbook that generates a root token from the unseal key on OpenBao 2.7 must start from a token with the right capability. Today's token-free path stops working when SEC-162 lands 2.7.2.
- **Not measured here.** These need the single-region spike Sovereign from `main` after SEC-162, about half a day:
  - k3s and Cilium (ingress to port 8200 from the provider pods).
  - Kyverno enforcement: resource requests on the driver and provider DaemonSets and the agent sidecar; images through the Harbor proxy. The chart defaults have empty resources and pull from `registry.k8s.io` and `quay.io`.
  - TLS on the OpenBao listener.
  - A second region.
  - OpenBao 2.1.0, the version live today.
  - Rotation by the hourly poll.

## What later tasks must take into account

The test ran fully in CI. Run 43358876601 is the evidence run; the two earlier runs agree on every measurement they share. The branch spike/SEC-140 is left in place at 3de77ee52cb152ab1e36769b49e60e9d5553347f.

What later packages must take into account:
- SEC-200, SEC-213 and SEC-215. An External Secrets PushSecret cannot write into mounted/ with create-only rights. This holds for 0.10.7, 0.16.2 and 2.14.0. It reads the value first, writes metadata second, then updates the value. So the birth Job variant applies, and it also breaks the planned tier B peer push through openbao-peer-push and the mountedCopies PushSecret. Those need a Job, or a policy that can read and overwrite the value. The birth Job also needs read on mounted/metadata/NS/*, and it must count a key as existing only when current_version is 1 or more.
- SEC-211. Write openbaoAddress in every SecretProviderClass, because provider 1.5 reads nothing else. Keep audience openbao. Set the driver's tokenRequests to audience openbao and drop the provider's cluster-wide serviceaccounts/token grant; both were measured to work. Add Secret openbao/openbao-csi-provider-hmac-key to the Secret census. Only the provider pods and the birth Jobs reach OpenBao on port 8200, not workload pods.
- SEC-214. With the platform's present vcluster values (service-account sync off), every Organization pod presents <org ns>/vc-workload-vcluster. So the scope is shared, and isolation between Applications inside one Organization is not provided. Switching sync.toHost.serviceAccounts.enabled to true gives stable translated names and real per-account isolation (measured). That is a control-plane change and the lead architect's choice. The producer would then have to compute vcluster's name translation, including the cut-to-52-characters-plus-hash rule for names over 63 characters.
- SEC-162 and runbooks. On OpenBao 2.7.2, a root token cannot be generated from the unseal key without a token: it returns 403, because the token-free endpoints are off by default since 2.5.3. It works with a token.

What could not be measured in CI, and what it needs: k3s with Cilium policy, Kyverno enforcement (resource requests and Harbor-proxied images for the CSI DaemonSets), the TLS listener, a second region, OpenBao 2.1.0 as live today, and rotation by the hourly poll. These need the single-region spike Sovereign from main after SEC-162, about half a day.

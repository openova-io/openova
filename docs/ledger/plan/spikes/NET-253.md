# NET-253 result: the reference cloud's native firewall with a load balancer

- Measured: 2026-11-24, 05:30 to 06:08 UTC, by hand from the agents' host in the cloud's network, on the reference cloud (ADR-0024): the project, the region, one zone.
- Outcome: **NATIVE**. The cloud's web application firewall was created, read, changed and deleted through the cloud's API, behind a load balancer of the Sovereign's shape, and the pass rule of NET-270 held through it: a clean request 200, a cross-site-scripting request 403 and an SQL injection request 403, three times each.
- The 403 needs one setting: by default the firewall answers a blocked request with HTTP 418. A custom block page on the protected host name, with status code 403, gives 403.

## Question

Decision record 0038 (WF5, WF8) gives the firewall contract a second implementation, `waf-native`: the native firewall of the cloud, with the edge nodes reachable only through the load balancer. The reference pack may ship `waf-native` only if its cloud passes this test.

- Can the firewall be created, read and deleted through the cloud's API, together with a load balancer?
- Does the pass rule of NET-270 hold through it: `GET /` 200, `GET /?q=<script>alert(1)</script>` 403 and `GET /?id=1' OR '1'='1` 403, in block mode?
- **Outcomes.** `NATIVE`: both hold. `NONE`: either fails; then a new decision record names the second implementation before NET-257 starts.

## What was run

**Where.** The reference cloud, from the agents' host. Every object was created for this test with the name prefix `nslab-net-253-`, in a network of its own, and deleted at the end. No resource of a test environment, of the jump host or of the parent was changed. A load balancer of its own was used, because a lab test never changes a resource it did not create.

**Tools.** OpenTofu 1.12.0 with the provider `huaweicloud/huaweicloud` 1.91.0, the version that `infra/providers/huawei/.terraform.lock.hcl` pins, with the endpoint pattern of `infra/providers/huawei/versions.tf` and one more endpoint, for the firewall service (`waf`). Read calls were signed requests to the cloud's API gateway with the signing method that the provider uses.

**Read-only probes first.**
- The firewall API is published: the list calls for dedicated instances (`/v1/<project>/premium-waf/instance`), protected host names (`premium-waf/host`), policies (`waf/policy`) and the subscription (`waf/subscription`) answer 200. A made-up path answers `404 APIGW.0101`. A call without a `Content-Type` header answers `400 APIGW.0106`, even a GET.
- The service's console configuration (`waf/config/console`) offers one mode only: `premium_waf: true` (a dedicated instance in the project's own network), `cloud_waf: false`, `elb_mode: false`, `premium_waf_bind_eip: false`, `load_balance_enable: false`. It lists one instance flavor, `s7n.2xlarge.2` (8 vCPU, 16 GiB), for x86 and for Arm, and the one zone.
- Before the test: no instance, no protected host, no policy (`purchased: false`). Quotas: 3 of 5 networks, 7 of 10 public addresses and 2 of 50 load balancers in use.

**The objects.**
- A network and a subnet. Two security groups: the firewall instance admits TCP 80 from anywhere; the backend admits TCP 80 from the lab subnet only.
- The backend: one small VM (`s7n.medium.2`) with no public address, from the image the provider module uses. A socket-activated shell script answers every request with `200` and the body `ok`.
- The firewall: one dedicated instance (specification `waf.instance.professional`, flavor `s7n.2xlarge.2`, x86), one policy (block mode, level 1, the lowest of the three the provider takes; basic web protection on), and one protected host name with the backend as its server, HTTP to HTTP on port 80.
- The load balancer: the shape of the Sovereign's gateway load balancer in `infra/providers/huawei/main.tf` (`huaweicloud_elb_loadbalancer.primary`): dedicated, no flavor pinned, one public address, a TCP listener on port 80, a TCP pool with a TCP health check, and one member: the firewall instance's address, port 80.

The firewall objects as applied (lab values, the rest as above):

    resource "huaweicloud_waf_dedicated_instance" "w" {
      name               = "nslab-net-253-waf"
      available_zone     = "<the zone>"
      specification_code = "waf.instance.professional"
      ecs_flavor         = "s7n.2xlarge.2"
      cpu_architecture   = "x86"
      vpc_id             = huaweicloud_vpc.v.id
      subnet_id          = huaweicloud_vpc_subnet.s.id
      security_group     = [huaweicloud_networking_secgroup.waf.id]
    }
    resource "huaweicloud_waf_policy" "pol" {
      name            = "nslab-net-253-policy"
      protection_mode = "block"        # "log" for detect mode
      level           = 1
      options {
        basic_web_protection = true
        general_check        = true
      }
    }
    resource "huaweicloud_waf_dedicated_domain" "dom" {
      domain         = "<a test host name>"
      policy_id      = huaweicloud_waf_policy.pol.id
      proxy          = true
      protect_status = 1
      custom_page {
        http_return_code = "403"
        block_page_type  = "application/json"
        page_content     = "{\"blocked\":true}"
      }
      server {
        client_protocol = "HTTP"
        server_protocol = "HTTP"
        address         = huaweicloud_compute_instance.be.access_ip_v4
        port            = 80
        type            = "ipv4"
        vpc_id          = huaweicloud_vpc.v.id
      }
    }
    resource "huaweicloud_elb_member" "waf" {
      pool_id       = huaweicloud_elb_pool.http.id
      address       = huaweicloud_waf_dedicated_instance.w.service_ip
      protocol_port = 80
      subnet_id     = huaweicloud_vpc_subnet.s.ipv4_subnet_id
    }

**Probe.** Every probe is a curl from the agents' host to the load balancer's public address with the Host header of the protected name, the requests of NET-270:

    code(){ curl -s -o /dev/null -w '%{http_code}' -m 10 -H "Host: $1" "http://$LB$2"; }
    code "$HOST" '/'                                  # clean
    code "$HOST" '/?q=<script>alert(1)</script>'      # cross-site scripting
    code "$HOST" '/?id=1%27%20OR%20%271%27%3D%271'    # SQL injection
    code other.example '/'                            # a host name the firewall does not protect

Each round sends the three requests of the pass rule three times, then the other host name. After each change the round waited until the answer had changed, and read the instance, the host name, the policy and the attack events back through the API.

## Measured values

### Create, read, change, delete

| Object | Create | Delete |
|---|---|---|
| Dedicated firewall instance | 7 min 11 s. Read at 5 min 13 s, its VM was ACTIVE and the instance still creating (`run_status` 0); at 7 min 11 s it was running (`run_status` 1) | 51 s |
| Policy | 1 s | 0 s |
| Protected host name | 0 s | 0 s |
| Load balancer, pool, health check, member | 0 to 2 s each | 0 to 1 s each |
| TCP listener | 10 s | refused `409 ELB.8907` ("pool ... is using this listener") until the pool was detached from it; then 0 s |
| Network, subnet, security groups and rules, public address | 0 to 7 s each | 8 to 15 s each |

- Read: the instance (name, `run_status`, `access_status`, specification `8vCPUs | 16GB`, flavor, zone), the protected host name (protocol, server, `protect_status`, `access_status`, the custom block page as stored) and the policy (`action.category`, `level`, options) all came back through the API as set.
- Changed in place through the API: the policy's options, its mode (`block` to `log`), and the host name's protection status and block page. Each change took 0 to 1 s at the API. The block page changed the answers within 20 s of the call, the mode within 26 s.
- After the delete, read calls found no instance, no protected host name, no policy, no VM, no load balancer, no network, no subnet, no security group and no public address with the prefix. The subscription stays `purchased: true` with 0 instances.

### The pass rule (block mode, level 1)

| Round, UTC | Setting | Clean | Cross-site scripting | SQL injection | Other host name |
|---|---|---|---|---|---|
| 05:52:10 | as the provider creates them: basic web protection off, protection status 0 | 404 | 404 | 404 | 404 |
| 05:55:54 | basic web protection on, protection status 1 | 200, 200, 200 | 418, 418, 418 | 418, 418, 418 | 404 |
| 05:56:51 | and a custom block page with status 403 | 200, 200, 200 | 403, 403, 403 | 403, 403, 403 | 404 |

- 404 is the firewall's own "Not Found" page (`Server: CloudWAF`, 1033 bytes). The first round came 11 s after the host name was created, so it does not separate the unready instance from the two settings.
- 418 is the firewall's default block page, an HTML page of 1696 bytes with an event identifier. With the custom page the answer is 403 with the configured body.
- A host name that the firewall does not protect, and a request with no Host header, got the firewall's 404 page, not the backend's answer.
- Time: clean 7 to 33 ms; a blocked cross-site-scripting request 51 to 61 ms, a blocked SQL injection 101 to 110 ms, the same in every round.
- The attack events API (`waf/event?recent=today`) listed the blocked requests: type `xss` with rule `010000` and type `sqli` with rule `225323`, action `block`, host name and path.

### Detect mode

The policy's mode was changed to `log`. 26 s later the cross-site-scripting request answered 200. In the round after it all nine requests answered 200 (6 to 13 ms), and the events API listed the attacks with action `log`.

### Other measured facts

- Subnet create. Provider 1.100.0 and 1.91.0 both look up the region's DNS service at the public cloud's host name after they create a subnet without `primary_dns`. That name does not resolve from the cloud's network. The subnet was created, and the provider retried the lookup for as long as it ran (stopped by hand after 1 to 2 minutes, twice). With `primary_dns` and `secondary_dns` set to the cloud's internal resolvers, as on the jump host's subnet, the create took 7 s. `infra/providers/huawei/main.tf` sets neither for its subnets.
- The host's resolver answered "no such host" for the firewall and load-balancer API names once during an apply; the next apply passed. A retry covers it.
- The instance resource has no field for a public address, and the console configuration says `premium_waf_bind_eip: false`. The lab instance had no public address; the load balancer was its only public entry.
- At 05:52:55 the lab's first backend (a netcat loop) answered one request and then 502 through the firewall; it was replaced by the socket-activated script, and every later round used that. This was a defect of the lab backend, not of the firewall.

## Answer

- The native firewall of the reference cloud is a dedicated instance in the project's own network. The load balancer sends traffic to the instance, and the instance forwards it to the servers listed for each protected host name. The console configuration offers no other mode on this cloud.
- Every object was created, read, changed and deleted through the API with the provider version the reference pack pins. The instance takes about 7 minutes to create and 1 minute to delete.
- Through the Sovereign's load balancer shape, in block mode at level 1 with basic web protection on, a clean request returned 200 and the cross-site-scripting and SQL injection requests of NET-270 were blocked and logged. They returned 403 once the host name carried a custom block page with status 403; the default is 418.
- In log mode the same requests passed with 200 and were logged.

## What follows for the plan

- **NET-256** may start (its dependencies NET-184 and CLD-174 aside): the outcome is NATIVE, so WF5 stands and no decision record names another second implementation. The reference pack may ship `waf-native` in its overlay (NET-257).
- **NET-256** writes the unit module with the three firewall resources above and the provider of `infra/providers/huawei/.terraform.lock.hcl`, and adds the `waf` endpoint to the module's provider block (`infra/providers/huawei/versions.tf` has none today). It sets explicitly what the provider leaves off: the policy's `basic_web_protection` and `general_check`, the host name's `protect_status = 1`, and a custom block page with status 403. It sets `primary_dns` and `secondary_dns` on any subnet it creates.
- **NET-256**: in `waf-native` the firewall instance takes the place of the edge nodes as the member of the gateway load balancer's pools, and the edge nodes become the servers of each protected host name. "Reachable only through the load balancer" then means that the edge nodes' security group admits the public ports from the firewall's subnet only.
- **NET-256**: a delete of a TCP listener whose default pool still exists is refused with `ELB.8907`. The module detaches the pool, or deletes it, before it deletes the listener.
- **NET-257**: the composition maps `spec.mode` to the policy's `protection_mode` (`block` or `log`), and `spec.level` must map paranoia levels 1 to 4 onto the firewall's three levels. Only level 1 was measured.
- **NET-257** and **NET-258**: through `waf-native`, a blocked request answers 403 only with the custom block page. The attack events API is where a run can read that a request was blocked or logged.

There is no CI run. The lab configuration, its state and the logs lived in a scratch folder and were deleted after the run; the firewall objects as applied are quoted above.

## What later tasks must take into account

1. Only HTTP on port 80 was measured. HTTPS needs the certificate in the firewall (its certificate API) and a TCP or HTTPS listener on 443. Not measured.
2. The firewall instance is one VM of 8 vCPU and 16 GiB per instance, the only size offered. It counts against the project's compute quota. One instance is a single point of failure; two instances behind the same pool were not measured.
3. Whether the client's address reaches the instance through the TCP listener, and whether the instance passes it on to the servers and in which header, was not measured.
4. Request bodies, the upstream Core Rule Set corpus of WF7, levels 2 and 3, rule exclusions, and the time a policy change takes under load were not measured.
5. Not measured: two regions, more than one protected host name, a host name with many servers, the firewall's health check of its servers, and the cost.

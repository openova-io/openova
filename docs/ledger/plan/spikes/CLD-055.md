# CLD-055 result: machine kind and reduced kit for the `local` pack

**machine kind: A**

## The question

On the hosted CI runner the repository uses, with no cloud account:

- **L1.** Does machine kind A boot the unmodified shared template to a `Ready` node? Kind A is a privileged container running systemd and cloud-init, started with the `kreuzwerker/docker` OpenTofu provider.
- **L2.** Does machine kind B do so? Kind B is a KVM virtual machine from the Ubuntu cloud image, started with `dmacvicar/libvirt`.
- **L3.** Does the reduced kit converge inside the runner's memory and inside 40 minutes, with the in-kit object store as the bucket? Is the distribution's built-in storage class present under the template's flags?
- **L4.** Can a unit Workspace inside the local cluster start one more machine on the runner?
- **L5.** Does moving a HelmRelease between two Flux Kustomizations, with the prune annotation set, avoid an uninstall?
- **L6.** Do two clusters of the chosen kind plus the console's closure converge on the runner inside the time limit? Which slots does that kit hold?
- **L7.** Does a machine answer on TCP 22 from a pod, and restart after an in-guest reboot?

## What was run

**Where.** GitHub Actions in `openova-io/openova`, on branch `spike/CLD-055` (never merged, head `85e11d8c5`). The workflow is `.github/workflows/spike-cld-055.yaml`; the scripts are under `tests/spikes/CLD-055/`. There were five pushes and five runs. Jobs ran in parallel, and a job already measured was switched off in later runs.

- 4 vCPU, 15983 MiB memory, 3 GiB swap.
- 145 GB disk, 109 GB free after removing unused toolchains.

**Versions.**
- OpenTofu 1.11.6, `kreuzwerker/docker` 3.9.0, `dmacvicar/libvirt` 0.8.3.
- QEMU 10.2.1 and libvirt 12.0.0.
- Machine image: Ubuntu 22.04.5 with systemd and cloud-init 26.1.
- k3s v1.31.4+k3s1 and Cilium 1.19.3, as the fixture and template set them.

- L5 only: kind v0.25.0, `kindest/node:v1.30.6`, the `podinfo` 6.7.1 chart.

**Render.** The shared template `infra/providers/_shared/cloudinit-control-plane.tftpl` is used unmodified, with the Huawei fixture of `infra/providers/_shared/tests/render.tf`. The fixture is copied exactly: rendered with render.tf's own host values, its SHA-256 is `8e2bbec5…c095c7`, equal to `golden_huawei`. This was checked in every run. Only values that name a host were changed:
- `cp_private_ip`, `node_ip_cmd` and `load_balancer_ipv4`: the machine's own address.
- `node_external_ip_cmd` and `node_external_ip_value`: from run 3 on, an address that is not on the machine, as an EIP is not.
- `object_storage_endpoint`: the in-kit seaweedfs.
- `catalyst_api_url`: a log sink on the runner. The template's own log helper sent its cloud-init log there.
- `registry_mirror_yaml`.

L6 also uses the per-region values that the Huawei module derives for two regions.

**Kind A.** systemd is PID 1. The module writes the user-data into the NoCloud seed directory. k3s and kubelet state live on volumes, `/lib/modules` is mounted read-only, and the restart policy is `unless-stopped`. The image adds only what a cloud image has. It masks units that need hardware or a network manager, and it marks `/` as a shared mount: systemd does this on a VM but not in a container.

**Kit.** This stands in for the `bootstrap_kit_path` input that CLD-086 adds. Right after the template applied its Flux objects, the job:
- held every Flux Kustomization;
- pointed the GitRepository at the spike commit;
- pointed `bootstrap-kit` at a kit that lists the shared slot files by relative path, with the local values `SOVEREIGN_CNPG_STORAGE_CLASS=local-path`, `EVS_CSI_ENABLED=false` and `HUAWEI_VPC_ROUTES_ENABLED=false`.

The kit also holds a HelmRelease of the upstream local-path chart. The `bp-*` charts and catalyst images on ghcr refuse anonymous pulls, so the job's own read-only token (`packages: read`) went into `flux-system/ghcr-pull`. No repository secret was used. For the object store, the job wrote seaweedfs's generated admin keys into `flux-system/object-storage` and created the bucket through the S3 API (HTTP 200 in runs 4 and 5).

## Findings that change the plan

1. **LB-IPAM must not use the machine's own address.** The Huawei branch builds the single LB-IPAM pool from `node_external_ip_value/32`, and every LoadBalancer Service takes it. In runs 2 and 3 that value was the machine's own address; once `bp-cilium` applied the pool, the machine lost its own TCP egress and the runner lost its apiserver. The diagnosis in run 43369604232 measured:
   - before the pool: egress HTTP 401 from quay, and the runner reached the apiserver;
   - at 130 s: the pool assigned `172.30.0.10`;
   - from 165 s: both failed;
   - after deleting the pool: both recovered.

   With an address off the machine (198.51.100.x), egress never failed. The local module must give LB-IPAM an address that is not the machine's.
2. **The kit pulls through the mothership's Harbor.** Its charts pin images to `harbor.openova.io/proxy-*` (155 references). On 13 November 2026 that proxy returned the index but not the content for `fluxcd/flux-cli:v2.4.0` (the `bp-flux` pre-install hook) and `kubernetes-reflector:7.1.288`. Everything after slot 03 stopped (run 43369604232). The spike sent these paths to the upstream registries through the registries file. A hermetic pack's registries file or image cache must cover them.
3. **The binding limit is CPU requests, not memory or time.** Every machine sees the runner's 4 vCPU. Memory requests (11.7–12.4 GiB per cluster) are accepted because each machine sees the full 16 GB, while real use is 5.1 GB for one cluster and 9.5 GB for two.
4. **The built-in storage class is absent.** CLD-086 adds the local-path release; the spike's HelmRelease of the upstream chart from Git works.
5. **The local values must turn both CSI slots off.** 55a and 55b are in the closure through `bp-cnpg`. With both enabled flags false they render empty and are Ready.
6. **CI needs a pull credential.** The `bp-*` charts and catalyst images are private on ghcr; CI needs a credential or the cache.
7. **Relative paths work.** Flux builds a kit that lists slot files by relative path outside its own directory.
8. **Kind B needed four adjustments on this runner.** A VNC display (QEMU has no SPICE), a pty console, unconfined QEMU, and FORWARD set to ACCEPT (Docker's DROP policy).

## What follows for the plan

- **Machine kind A.** CLD-086 may start on machine kind A, and kind B is a measured fallback. The module needs: a restart policy, volumes for k3s and kubelet state, a shared root mount, and an external address that is not the machine's own.
- **Storage.** CLD-086 adds the local-path release.
- **L3 and L6.** The lead architect decides which releases leave the closure, or whether the local values lower CPU requests, to fit 4000m per machine. The kit also needs Kyverno for `14-crossplane-claims`.
- **L4.** `day2/nodepool` for `local` works as designed, but needs CPU room for the provider's rollout.
- **L5.** CLD-141 and CLD-144 proceed.
- **L7.** Holds as specified.

## What later tasks must take into account

Not measured in CI: (1) a reduced closure that fits the runner. Pushes ran out, so no closure inside 4000m CPU was tried. With the per-release table, the lead architect can pick one, and CLD-086's first run measures it. (2) The console slot's own cost: `bp-catalyst-platform` never installed because its dependencies (gitea, keycloak, crossplane-claims) were not Ready. (3) ClusterMesh between the two L6 clusters; it was not asked.

For later packages:
- **CLD-086, external address.** The local module must not let LB-IPAM take the machine's own address. Use an address off the machine, as the spike did, or do not render the pool. The Huawei branch of the template couples the pool to `node_external_ip_value`.
- **CLD-086, local values.** They must set `HCLOUD_CSI_ENABLED` and `EVS_CSI_ENABLED` to false, use `local-path` as the storage class, add the local-path release, and add Kyverno (or gate the `ClusterPolicy` in `bp-crossplane-claims`).
- **CLD-087, CI job.** It needs a ghcr pull credential (the job token with `packages: read` works) or the image cache. It must cover the mothership proxy paths `harbor.openova.io/proxy-*`, which served broken content on 13 November 2026.
- **Registries rewrite.** It relies on name parity between proxy paths and upstream: it tries ghcr, then quay, registry.k8s.io and Docker Hub, and falls back to the original host.
- **CPU, not memory, is the runner's limit.** The pass rules of L-G1 and L-G3 depend on the closure decision.
- **Evidence.** Branch `spike/CLD-055` at `85e11d8c5` is left in place. Run artifacts hold the per-machine evidence: cloud-init logs, k3s journal, HelmRelease state, warnings and request tables.

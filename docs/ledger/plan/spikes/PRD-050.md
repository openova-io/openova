Outcome: B

# PRD-050 result: client certificates on the Organization listener

## Summary

- On the pinned versions the Organization listener cannot verify a client certificate. The kit installs the Gateway API v1.3.0 experimental CRDs, which carry `listeners[].tls.frontendValidation`. Cilium 1.19.3 is built against gateway-api v1.4.0-rc.2, where the field is no longer on the listener, so the Cilium operator drops it when it decodes the Gateway. Cilium reads the newer Gateway-level field nowhere either.
- The Envoy listener Cilium generates asks for no client certificate. A client with no certificate, with a good one and with one from a wrong authority all get through (run).
- No verified certificate reaches the back end in a header. The gateway strips an `x-forwarded-client-cert` header sent by the client and sets none (run: the lab back ends keep and echo any such header that reaches them).
- Validation per listener would not hold on the shared port anyway. Every TLS-terminating listener of the console Gateway uses one route table, so a TLS session opened for one listener's host is served by another listener's routes (run). Upstream GEP-91 moved client validation from the listener to the port for this reason, and Cilium's main branch follows it. On the shared console port, per port means every Organization and the console at once.
- A TLS passthrough listener for one host of an Organization works beside the Organization's HTTPS listener on the same port. The back end receives the client's own handshake: a good certificate passes; a wrong-authority certificate and no certificate are refused by the back end (run).
- Outcome B: the chart uses a TLS passthrough route and `fingate-api` terminates mutual TLS itself.

## The question

The plan's question (plan entry PRD-050; ADR-0034 decision P17): can the Organization's gateway listener verify a client certificate against a per-listener authority bundle, and hand the verified certificate to the back end in a header only the gateway can set? The experiment: a listener with client validation, and a test client with a good certificate, one from a wrong authority, and none.

The fixed rule. A: yes, on both counts, so `fingate-api` runs in mode `gateway` and the firewall is in the path. B: no, so the chart uses a TLS passthrough route and `fingate-api` terminates mutual TLS itself; the positive model (strict document validation) stands in for the firewall on these hosts, and the result file states "no web application firewall in the path" for them.

Precondition, checked on main at 0c8fed2fd0 before the work: `docs/ledger/plan/spikes/PRD-050.md` did not exist (`test -e` exited 1), and NET-191 was merged (pull request 8946, merge commit 5f3b7cba63).

## Evidence

Outcome: **B**. Both conditions of A fail on the pinned versions: the listener does not validate a client certificate (answers 1 to 4), and no header carries a verified certificate to the back end (answer 5). The passthrough path of B works (answer 8).

- Rendered: `PRD050_BOOTSTRAP=<lab>/cfg/gateway.json go test -count=1 -run 'TestPRD050(Probe|Bootstrap)$' -v ./operator/pkg/model/translation/gateway-api/` in a clone of cilium at tag v1.19.3 (commit f5eb641b18502ebeca412b40c1bec7ff3d8bf9eb), Go 1.25.0, 27 November 2026: PASS.
- Run: the bootstrap written by `TestPRD050Bootstrap`, loaded into the pinned cilium-envoy in a rootless podman pod (podman 3.4.4) published on 127.0.0.1 only, called with curl 7.81.0 and OpenSSL 3.0.2, 27 November 2026. Neither Envoy logged an error line: `down.sh` read Envoy's stderr, 1 log line of the back end and 88 of the gateway; the pod was removed after the run.
- Source, scripts and output: [PRD-050-lab.md](PRD-050-lab.md).

Where the run differs from a cluster:

- The route table is inlined into each connection manager instead of fetched by its RDS name. The content is the rendered table, and every terminating chain gets the same one, as the shared RDS name gives on a cluster.
- Clusters are static on 127.0.0.1 instead of EDS; server certificates are static secrets under the same SDS names.
- The Cilium agent's changes when it loads a CiliumEnvoyConfig are absent: the L7 policy filter (`pkg/ciliumenvoyconfig/cec_resource_parser.go` line 230), the BPF metadata listener filter (line 497) and the qualification of resource names. Read: none of them adds client validation or certificate forwarding; the agent changes a TLS context only to qualify its SDS secret names (lines 909-961).
- HTTP/1.1 with an explicit Host header stands in for the HTTP/2 connection reuse of browsers. Both are routed by the same route table.

## What was not measured

- The Kubernetes path end to end: the API server storing the field, the operator's decode in its cache, the agent loading the configuration, and whether the Gateway's status says anything about the dropped field.
- HTTP/2 connection reuse by a browser.
- A hand-written CiliumEnvoyConfig with a client validation context. Envoy supports it, and the agent would carry it (it qualifies a validation-context SDS name, `cec_resource_parser.go` lines 916-922). It is a second configuration path beside the Gateway API, outside the listeners NET-191 writes, and answer 6 applies to it too. Not pursued.

## What later tasks must take into account

- **NET-195 builds outcome B.** For a host an Organization owns, both writers of the Organization's listeners (`tenant_console_tls.go` and `org_console_tls.go`) add one listener: `protocol: TLS`, `tls.mode: Passthrough`, `hostname` the exact host, on the same port as the Organization's HTTPS listener, `allowedRoutes.kinds` `[{kind: TLSRoute}]` and the namespaces of `orglistener.AllowedRoutes`. TLSRoute is `v1alpha2` in the kit's bundle (`platform/gateway-api/chart/templates/tlsroutes.yaml` line 40), the version Cilium 1.19.3 watches (`operator/pkg/gateway-api/gateway.go` line 159). Admission by namespace is checked by Cilium's route checks, not by ingestion; the probe did not exercise it.
- **PRD-507** writes a TLSRoute for that host to the TLS port of `fingate-api`, and `fingate-api` terminates mutual TLS itself, as ticket PRD-513 builds it. There is no gateway mode. No web application firewall is in the path for these hosts: the gateway sees only the TLS ClientHello. The positive model (strict document validation) stands in for it.
- **No HTTPRoute may name the passthrough host.** The Organization's wildcard certificate also covers the passthrough host, so a client may reuse a session opened for another host of the Organization. The shared route table answers it (answer 9): today with HTTP 404. An HTTPRoute naming the host, or a wildcard HTTPRoute, would send such requests to another back end. None of them reaches `fingate-api` without mutual TLS, but the client gets a misdirected answer.
- **Never read identity from a gateway header.** On these versions the gateway sets none, and it strips one a client sends (answer 5).
- **The listener comment in NET-191 is right about certificates only.** `tenant_console_tls.go` lines 136-147 says the server name differentiates the Organizations' listeners on the shared port. It selects the certificate; the routes come from one table (answer 6). Route admission, which NET-191 changed, is not affected: each route still attaches only to its own Organization's listener.
- **What would reopen the question:** a Cilium and Gateway API upgrade that implements GEP-91's per-port validation, together with a dedicated gateway port for hosts with mutual TLS. Per port on the shared console port is not an opt-in per host (answer 7).

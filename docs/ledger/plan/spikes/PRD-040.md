Outcome: A

# PRD-040 result: authorisation server fitness, consent carrier and conformance run

## Summary

- The consent identifier can travel as an essential ID-token claim, `openbanking_intent_id`, inside the signed request object that the client pushes to Keycloak. Keycloak keeps the claims request for the session. A small extension reads it, makes a consent call, and writes the claim into the access token and the ID token. This works on Keycloak 26.3.3, the version the platform chart pins. It also works on 26.8.2, the newest release.
- With the extension, the OpenID Foundation suite's FAPI1 Advanced Final plan with PAR passes on 26.3.3 for both client authentications. No module fails.
- The extension needs a second part. When client authentication fails, Keycloak's PAR endpoint answers HTTP 401 with `error=invalid_request`. The suite expects `invalid_client`. Four modules of the `private_key_jwt` plan fail because of this on 26.3.3 and on 26.8.2. Keycloak's main branch has the same code. A two-class override of the PAR endpoint changes that one error code, and all four modules then pass on both versions.
- The carrier through PAR was tested with the suite's own UK Open Banking modules. The suite does not offer that combination, so one line of the suite was changed to allow it. One module then fails. The cause is the suite, not Keycloak (details below).
- Carrier B (rich authorisation requests) was not tried, because carrier A passed. Neither Keycloak version advertises `authorization_details_types_supported`.

## The question

Can the pinned Keycloak, with a small extension, pass the authorisation conformance plan for the first profile? The first profile is FAPI 1.0 Advanced Final with pushed authorisation requests, PS256-signed request objects, `private_key_jwt` or mutual-TLS client authentication, and certificate-bound tokens. Which carrier brings the consent identifier: (A) a claim in the signed request object pushed to the authorisation server, or (B) rich authorisation requests? The plan says to try A first and to record the exact plan and variant names.

- **Stub extension.** One jar of 245 lines of Java. The job compiles it against the jars of the Keycloak image under test.
  - `ConsentClaimMapper` is a protocol mapper. It reads the claims request that Keycloak keeps as a client-session note. If that request holds an essential ID-token claim `openbanking_intent_id` with a value, the mapper calls the resource server once with `POST /internal/consent-step` (consent, client, user). On HTTP 2xx it writes the claim into the access token and the ID token. On any other answer it writes nothing. On these clients it replaces Keycloak's built-in claims-parameter value mapper, so the claim reaches the tokens only through the stub.
  - `FapiParRootEndpoint` and `FapiParEndpoint` replace Keycloak's built-in PAR provider (same id `par`, order 100). The subclass changes one thing: a failed client authentication gets `invalid_client` (HTTP 401) instead of `invalid_request`. These two classes were present only in run 43392298025.
- **Built-in Keycloak parts used.** The global client profile `fapi-1-advanced`; a realm profile with `pkce-enforcer` for PAR; and the executor `intent-client-bind-checker`. Before the authorisation step, that executor asks the resource server whether the consent belongs to the client.
- **Stub resource server.** It sits behind the gateway.
  - It creates a consent with `POST /open-banking/v4.0/aisp/account-access-consents`. The consent gets status AWAU and is bound to the token's client.
  - It answers the bind check.
  - It marks the consent AUTH on the consent step.
  - It serves `GET /open-banking/v4.0/aisp/accounts` only when the access token carries the claim of an AUTH consent of the same client.
  - It logs each decision as one line.
- **Client groups and exact plans.** Every plan is `fapi1-advanced-final-test-plan`.

Every module ran to completion except the one failed module in each P3 plan. The six plans took 238 s on 26.3.3 and 327 s on 26.8.2.

- **Warnings.**
  - `EnsureIdTokenDoesNotContainNonRequestedClaims`: Keycloak puts `typ` into the ID token. The SIG lists this as an expected warning.
  - `CheckJwksUriIsHostedOnOpenBankingDirectory` (UK profile only): the key set is not hosted on the UK directory.
- **Review.** These modules end with a screenshot of an error page. For certification, a person must look at each screenshot.
  - In P1: the 7 negative modules for request objects and redirect URIs.
  - In P2 and P3: missing request object, expired `request_uri`, the `request_uri` of another client, and a second use of a `request_uri`. On 26.3.3 the reuse-before-completion module is also in review.
- **The one difference between the versions.** It is the module `fapi1-advanced-final-par-ensure-reused-request-uri-prior-to-auth-completion-succeeds`. On 26.8.2 it PASSED. On 26.3.3 the second visit to the same `request_uri` shows an error page, so the module ends in review. Keycloak 26.3.3 uses up the `request_uri` on the first visit, not at the end of the login. The module calls this behaviour a recommendation, and treats a failure as a warning.
- **The one failed module.** It is `fapi1-advanced-final-ensure-server-handles-non-matching-intent-id` in P3, on both versions and with both client authentications.
  - The module wants the second client to use the first client's consent. It switches to the second client only while it builds the request object.
  - With PAR, it then authenticates the push as the first client (client assertion `kid` `client1-PS256`) and sends the second client's request object (`kid` `client2-PS256`).
  - Keycloak refuses this with HTTP 400 `invalid_request_object`. The module requires HTTP 201, so it stops.
  - The fault is in the suite, not in Keycloak: the module was written for by-value requests. By value (P1), the same module PASSED: the bind check answered "not bound" twice, and Keycloak returned the error.

### The baseline without the PAR fix (run 43386987778)

The consent stub was present. The PAR fix and the reuse scripts were not. The results are the same on 26.3.3 and 26.8.2.
- P1 is the same as above.
- P2 `private_key_jwt`: 5 failed, 55 passed, 3 review, 1 warning, 1 without a result. Two of these modules did not finish.
- P2 `mtls`: 1 failed, 43 passed, 3 review, 1 warning, 1 without a result.
- P3 is the same as P2, plus the suite module described above.
- Four failures appear on both versions, only with `private_key_jwt`:
  - The modules are `fapi1-advanced-final-par-ensure-client-assertion-with-invalid-signature-fails`, `fapi1-advanced-final-par-ensure-client-assertion-with-wrong-aud-fails`, `fapi1-advanced-final-par-ensure-client-assertion-with-wrong-iss-fails` and `fapi1-advanced-final-par-ensure-client-assertion-with-wrong-sub-fails`.
  - The failing condition is `CheckParEndpointHttpStatusIs400Allowing401ForInvalidClientError`. Keycloak answered HTTP 401 with `{"error":"invalid_request","error_description":"Authentication failed."}`. RFC 6749 section 5.2, which PAR section 2.3 follows, allows 401 only together with `invalid_client`.
  - The cause is in Keycloak's source: `AbstractParEndpoint.authorizeClient()` turns every exception into `INVALID_REQUEST` with status 401. The same code is in 26.3.3, 26.8.2 and the main branch (read on 2026-11-13).
  - The SIG's own CI list for this variant leaves out 10 of the plan's 65 modules, including these four. That is why the failure does not show in the SIG's CI.
  - In run 43392298025 the stub override rewrote this error 8 times per job, and all four modules PASSED on both versions.
- The two `request_uri` reuse modules did not finish, because their browser scripts were empty. Change 6 fixed this.

### The carrier at work (run 43392298025)

The counts come from the suite's exported logs, the stub resource server's log and Keycloak's log. Each figure is for 26.3.3; the 26.8.2 figure is given in brackets where it differs.
- P3 sent the consent claim in the pushed request object in 66 of 67 modules (`private_key_jwt`) and in 50 of 51 modules (`mtls`). The suite found the matching `openbanking_intent_id` in 49 and 33 ID tokens (51 and 35). No ID token had a wrong value.
- Bind checks on the PAR flows: 58 (60) answered "bound", none answered "not bound". So the executor runs on the authorisation step that follows a push.
- Consent steps from the extension: 52 (54), all answered with HTTP 200. The claim was written into 90 (94) access tokens and 90 (94) ID tokens.
- Account calls served because the claim matched: 37 (39). Refused: 0.
- P1 by value, the same on both versions: 44 consent steps, 78 access tokens and 78 ID tokens with the claim, 33 account calls served, 2 bind checks that answered "not bound", 0 refusals.

## What follows for the plan

- **Outcome A.** The profile value is `intent-claim`, and PRD-503 builds it.
- **The PAR correction.** PRD-503's extension must also carry the PAR error-code correction, as done here: a subclass that replaces the built-in `par` provider. There are two alternatives: the profile drops `private_key_jwt`, or Keycloak changes upstream. A Keycloak upgrade does not help, because 26.8.2 and the main branch have the same code. The change is a single error code, so offering it upstream would make the override unnecessary.
- **Internal SPIs.** Both parts of the extension use internal SPIs. PRD-503's tests must run against every Keycloak version the chart moves to in the routine upgrade stream.
- **Where the claim is read.** The stub reads the claim and makes the consent call when the token is built. The product runs the consent step inside the login flow. This run measured the claim only at token time.
- **Test C2 (PRD-505).** These are the exact plan names. Run them one at a time with suite `release-v5.3.4`.
  - `fapi1-advanced-final-test-plan[client_auth_type=private_key_jwt][fapi_profile=plain_fapi][fapi_response_mode=plain_response][fapi_auth_request_method=pushed]`
  - `fapi1-advanced-final-test-plan[client_auth_type=mtls][fapi_profile=plain_fapi][fapi_response_mode=plain_response][fapi_auth_request_method=pushed]`
  - `fapi1-advanced-final-test-plan[client_auth_type=private_key_jwt][fapi_profile=openbanking_uk][fapi_response_mode=plain_response][fapi_auth_request_method=pushed]`
  - `fapi1-advanced-final-test-plan[client_auth_type=mtls][fapi_profile=openbanking_uk][fapi_response_mode=plain_response][fapi_auth_request_method=pushed]`
- **About these plans.**
  - The first two are certification profiles.
  - The last two need the one-line suite change. They also need `fapi1-advanced-final-ensure-server-handles-non-matching-intent-id` listed as an expected failure.
  - Expected warnings: `EnsureIdTokenDoesNotContainNonRequestedClaims` (the `typ` claim) and, for the UK profile, `CheckJwksUriIsHostedOnOpenBankingDirectory`.

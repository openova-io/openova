## The question

Does the pinned chat interface (LibreChat) forward the signed-in user's access token to a custom OpenAI-compatible endpoint? The test signs a user in through a test realm, sends a chat message, and lets a stub endpoint print the `Authorization` header it receives.

## Measured results

### Pinned image, v0.7.5 (runs 43382815254, 43383683026, 43385026758, 43386471757)

- **Sign-in.** Sign-in through the test realm worked for both users. The LibreChat log shows "login success" for each. Every message reached the stub and the stub's reply was shown.
- **What reached the stub.** The `Authorization` header arrived as credential `{{LIBRECHAT_OPENID_ACCESS_TOKEN}}` with scheme `Bearer`, as literal text. This held on all 3 messages in each of the four runs, so 12 of 12 requests. The four other headers also arrived as their literal placeholder text.
- **Code search** (runs 43385026758 and 43386471757):

  | Name searched | Files that mention it |
  |---|---|
  | `resolveHeaders` (positive control) | 14 |
  | `LIBRECHAT_OPENID` | 0 |
  | `LIBRECHAT_USER_` | 0 |
  | `OPENID_REUSE_TOKENS` | 0 |
  | `federatedTokens` | 0 |

- **Upstream source at tag v0.7.5 (read, not run).** It agrees with the measurement: `resolveHeaders` substitutes only environment variables.
- **Conclusion.** v0.7.5 cannot forward the user's token, whatever its configuration.

### Newest release v0.8.8, flag on, lifespan 90 s (runs 43385026758 and 43386471757)

- **First message of each user.** The stub received a JWT: 1,153 characters for Alice and 1,142 for Bob. The checks gave:
  - signature valid against the realm's key;
  - `iss` = the test realm;
  - `typ` = `Bearer`, so an access token;
  - `azp` = `librechat`;
  - `aud` = `cortex`;
  - `sub` = the signed-in user's realm id;
  - 86 to 88 s left at receipt.
  - The two users gave two different subjects.
- **Other headers.**
  - `{{LIBRECHAT_OPENID_TOKEN}}` gave the same access token.
  - `{{LIBRECHAT_OPENID_ID_TOKEN}}` gave the user's ID token.
  - `{{LIBRECHAT_USER_EMAIL}}` gave the e-mail.
  - `{{LIBRECHAT_USER_OPENIDID}}` gave the realm subject.
- **Static key.** The fixed `apiKey` value did not appear in any header of any captured request (0 occurrences in run 43385026758). The configured `Authorization` header replaces it.
- **Request body.** It carries `user` = LibreChat's internal user id.
- **Across token expiry, the UI drops the session.**
  - The browser's first 401 came 62.9 s after sign-in (run 43386471757). In run 43385026758 it came at the same point: sign-in at 07:23:55, first 401 at 07:24:58. That is about 27 s before the 90 s token expired.
  - At that second the browser made four `/api/auth/refresh` calls. Each returned 200 with a token.
  - The API calls that followed were rejected. The LibreChat log records `jwt_auth_rejected` with reason `malformed_jwt`.
  - The UI then showed its login page: "Unable to login with the information provided". So Alice's second message was never sent.
- **A reload recovers.**
  - A reload restored the session without a new sign-in at the realm: there was a `/api/auth/refresh` call and no `/oauth/openid`.
  - The third message forwarded a fresh access token. It was issued 197 s after the first one, had 88.8 s left at receipt, and belonged to the same user (run 43385026758). Run 43386471757 gave the same result.

### Newest release v0.8.8, flag on, Keycloak's default lifespan of 300 s (run 43386471757)

- Alice's and Bob's first messages forwarded verified access tokens, with 296.8 s and 297.3 s left.
- Alice's second message was sent 310 s after her first, after that token had expired. It forwarded a different, refreshed access token of the same user, with 299.0 s left.
- The browser saw its first 401 313.6 s after sign-in. The UI refreshed on its own and showed the reply. There was no drop to the login page.
- The platform's per-Organization realms set `accessTokenLifespan` to 900 (`platform/keycloak/chart/templates/configmap-per-org-realms.yaml:135`). A 900 s lifespan was not run.

### Newest release v0.8.8, flag off (runs 43383683026, 43385026758, 43386471757)

- No request reached the stub for any message: 0 requests in each run.
- Every reply read: "SpikeGW could not complete this request. An error occurred while processing the request: OpenID token is expired or unavailable; re-authentication is required to resolve".
- The LibreChat log reads: "OpenID token is expired or unavailable; cannot resolve {{LIBRECHAT_OPENID_ACCESS_TOKEN}} for the current request".
- So it fails closed. It never sends the placeholder text or an empty credential.

## What follows for the plan

- **Outcome A.** PRD-303 reworks `bp-librechat`. The version change is part of that rework, and these settings follow from what was measured:
  1. **Image.** Use `ghcr.io/librechat-ai/librechat:v0.8.8`, pinned by digest `sha256:5b706bcee1ca154a1e2987303aaeca0eb27f97919cccee4bb604226c2f8abf61`. The repository path changes, because the old owner's path stops at v0.8.7.
  2. **Token reuse.** Set `OPENID_REUSE_TOKENS=true`. Without it, every chat to the endpoint fails closed.
  3. **Endpoint headers.** In the custom endpoint for cortex, set `headers.Authorization: "Bearer {{LIBRECHAT_OPENID_ACCESS_TOKEN}}"`. The schema still requires `apiKey`. Give it a fixed value that is not a secret; it is never sent. The chat front end then holds no cortex credential.
  4. **Audience.** The chat front end's client in the Organization's realm needs an audience mapper that adds `cortex` to the access token. Measured: `aud` = `cortex` and `azp` = the chat client. A cortex check of "aud contains cortex" passes. If cortex also checks `azp`, it must accept the chat client.
  5. **Identity comes from the token only.** Cortex must take identity only from the verified access token, never from any other header. LibreChat can also fill headers with the ID token, the e-mail and the subject.
  6. **Token lifespan.** Keep the realm's access-token lifespan at 300 s or more; the platform uses 900 s. At 90 s, v0.8.8 drops the user to its login page about 27 s before each expiry.
  7. **Acceptance test.** PRD-303's acceptance (PRD-G10) should cross one token lifetime: send a message, wait past expiry, send again, and check that the second request carries a fresh token.
  8. **The `user` field.** The chart's present `dropParams: [stop, user]` keeps LibreChat's internal user id out of the request body. Keep it.
- **Outcome B is not needed.** The cortex screens do not need their own chat page, and `platform/librechat/` is not deleted.

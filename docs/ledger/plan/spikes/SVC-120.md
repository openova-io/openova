# SVC-120 result: Flux test hooks and Ready under ignoreFailures

- Date: 2026-11-13
- **Flux version tested: v2.4.0** (helm-controller v1.1.0, source-controller v1.4.1)
- **Outcome: as expected**
- Evidence run: https://github.com/openova-io/openova/actions/runs/43350179743 (commit 4902d30de on branch `spike/SVC-120`, never merged). Evidence artifact `spike-svc-120-evidence` (id 14004235655) is kept until 2027-02-11.

## Question

Take a HelmRelease with `spec.test.enable: true` and `spec.test.ignoreFailures: true` on the pinned Flux. Two things were tested:

1. Does helm-controller record the phase of each test hook in `status.history[].testHooks`?
2. When a hook fails, does it leave the release's `Ready` condition alone and start no remediation?

## What was run

Everything ran in one GitHub Actions job, on a throw-away kind cluster.

- **Workflow:** `.github/workflows/spike-svc-120.yaml`. It starts only on a push to `spike/SVC-120`.
- **Scripts:** `tests/spikes/SVC-120/` holds `run.sh`, `measure.py`, the lab chart and the manifests.

**Steps:**

1. `actions/checkout@v4`.
2. `helm/kind-action@v1` with kind v0.25.0 and node image `kindest/node:v1.30.6` (Kubernetes v1.30.6).
3. `azure/setup-helm@v4` with helm v3.16.3. The CLI only packages the chart and reads Helm's records. helm-controller has its own Helm library.
4. Print the tool versions. The kubectl client is v1.35.0.
5. Run `run.sh`.
6. Run `measure.py evaluate`.
7. Print the evidence into the job log.
8. `actions/upload-artifact@v4`.

**Flux.** The job applied `install.yaml` of Flux release v2.4.0. This is the same download URL form the control-plane cloud-init uses. The file's sha256 is `3aca0de604932df9632c6cc8e7522873d16cdd621d1debcf91293589a6d41afe`.

The file has no version marker of its own. So the job compared the running controller image tags with the tags the bp-flux chart pins in `platform/flux/chart/values.yaml`. All six were equal:

- source v1.4.1
- kustomize v1.4.0
- helm v1.1.0
- notification v1.4.0
- image-automation v0.39.0
- image-reflector v0.33.0

The HelmRelease API served for storage was `helm.toolkit.fluxcd.io/v2`.

**Lab chart.** `spike-fn` 0.1.0 was pushed to an in-cluster OCI registry. The registry sits behind a ClusterIP Service; there is no NodePort. The chart installs one ConfigMap and one test hook Pod in the shape of the function-test contract:

- name `<release>-function-test`
- hook `test`
- delete policy `before-hook-creation,hook-succeeded`
- label `catalyst.openova.io/function-test: "true"`
- `restartPolicy: Never`
- `activeDeadlineSeconds: 300`

The Pod reads the ConfigMap back. It exits 0 when the value matches and 1 when it does not. It prints a last line `FUNCTION-TEST pass|fail ...`.

**HelmReleases.** There were four, shaped like a bootstrap-kit slot:

- object in `flux-system`, with `releaseName` and `targetNamespace`
- an OCI HelmRepository
- install and upgrade timeout 15m, with `disableWait`
- install remediation retries -1, upgrade remediation retries 3

| Release | Test settings | Hook |
|---|---|---|
| spike-pass | enable, ignoreFailures | passes |
| spike-fail | enable, ignoreFailures | fails |
| spike-none | enable, ignoreFailures | chart renders no hook |
| spike-fail-strict (control) | enable only | fails |

A `kubectl get -w` watch recorded every status write on the four objects. The run had four phases:

- **A:** install and test.
- **B:** a no-change reconcile request (`reconcile.fluxcd.io/requestedAt`).
- **C:** upgrade spike-pass and spike-fail to Helm revision 2 by changing one value.
- **D:** 120 seconds with no change.

## Measured values (run 43350179743)

### Question 1: hook phases are recorded

**After install (A):**

- spike-pass: `history[0]` is version 1. Its `testHooks` is `{spike-pass-function-test: phase Succeeded, lastStarted 02:12:52Z, lastCompleted 02:12:59Z}`.
- spike-fail: `history[0]` is version 1. Its `testHooks` is `{spike-fail-function-test: phase Failed}`, with the same times.

**After the upgrade (C):**

- `history[0]` is version 2 and `history[1]` is version 1. Each revision keeps its own hook entry.
- Version 2 is Succeeded for spike-pass and Failed for spike-fail. Both started 02:13:02Z and completed 02:13:04Z.
- So `history[0]` is the newest revision.

**spike-none:**

- `history[0].testHooks` is `{}`.
- `TestSuccess` is True, reason TestSucceeded, message "no test hooks".
- `helm status` shows "TEST SUITE: None".

**Helm's own record agrees.** `helm status` at revision 2 shows `spike-pass-function-test` with phase Succeeded and `spike-fail-function-test` with phase Failed.

**Failing test Pod log:** `FUNCTION-TEST fail spike-fn expected=not-the-value got=hello`.

### Question 2: Ready is untouched

- **spike-fail Ready, from the first Helm action on:** True/InstallSucceeded → Unknown/Progressing (start of the upgrade) → True/UpgradeSucceeded. This is identical to spike-pass. It was never False.
- **Phase snapshots:** Ready was True at A, B, C and D. The final message is "Helm upgrade succeeded for release spikes/spike-fail.v2".
- **TestSuccess** on spike-fail was False, reason TestFailed, message "pod spike-fail-function-test failed".
- **No remediation:** there was no Remediated condition, and no installFailures or upgradeFailures, in any phase.
- **Helm history:** revision 1 superseded, revision 2 deployed. There was no rollback and no uninstall.
- **Phase B:** the request was handled, and `history` and `testHooks` did not change. A no-change reconcile does not re-run the tests.
- **Phase D:** spike-fail had no status write for 120 seconds. Its resourceVersion was 1047 at C and at D, and there was no new Helm revision.
- **Control:** spike-fail-strict went Unknown/AwaitingTests → False/TestFailed. Then Remediated became True/UninstallSucceeded. The cycle repeated: installFailures was 1 at C and 7 at D. So the failing hook really fails a release, and `ignoreFailures` is what keeps Ready.

### Other measured behaviour that later packages need

1. **Ready does not wait for the tests when `ignoreFailures` is true.** Ready became True/InstallSucceeded while `TestSuccess` was Unknown/AwaitingTests and `history[0].testHooks` was `{}`.
   - Install: 02:12:52Z to 02:12:59Z.
   - Upgrade: 02:13:02Z to 02:13:04Z.
2. **An empty `history[0].testHooks` has two meanings.**
   - No hook in the chart. This is final, and `TestSuccess` is True with "no test hooks".
   - The test has not finished yet. `TestSuccess` is Unknown/AwaitingTests.
   - Also, for one status write `TestSuccess` was already False while `testHooks` was still empty.
3. **`status.failures` became 1 on spike-fail after its failed test, even with `ignoreFailures`.** It started no remediation.
4. **Tests run only on install and upgrade.** A test result is as old as the release's last Helm revision.
5. **Leftover Pods.** A failed test Pod stays until the next test run, which deletes it first. A passing Pod is deleted at once. The phase stays in the history either way.

## Outcome

**as expected.** The hook phases are recorded in `status.history[].testHooks`, and `Ready` stays untouched when a hook fails under `ignoreFailures: true`.

## What follows for the plan

- **SVC-130 proceeds as written.** This record names Flux v2.4.0 / helm-controller v1.1.0. SVC-130 and SVC-125 stop if the pinned Flux version differs. To test a new version, change `FLUX_VERSION` in the workflow and push the branch again.
- **SVC-125 (proof check) must handle three things:**
  - Read a release only when it is settled: `observedGeneration == generation` and no Reconciling condition.
  - Treat empty `testHooks` as `none` only when `TestSuccess` is True with "no test hooks". While `TestSuccess` is Unknown/AwaitingTests, the result is pending, not `none`.
  - Never use `Ready` or `status.failures` as the test signal.
- **The proof is per Helm revision.** A gate run reads the test of the last install or upgrade. A no-change reconcile does not refresh it.
- **Substrate:** kind was used instead of k3d. The behaviour under test lives in helm-controller, not in the cluster distribution. On a Sovereign, bp-flux pulls the same tags through the Harbor proxy.

## What later tasks must take into account

Done in 3 of the 5 allowed pushes. Run 43350179743 (commit 4902d30de) is the evidence and returns "as expected". Branch spike/SVC-120 is left in place. Nothing of the question went unmeasured in CI. It was all inside kind: Flux v2.4.0 from the release install.yaml, controller tags checked against the bp-flux pins in the job, and kit-shaped HelmReleases.

What later packages must take into account:

(1) SVC-125 has a real trap. With ignoreFailures, Ready turns True before the test runs. For a few seconds history[0].testHooks is {} while TestSuccess is Unknown/AwaitingTests. A check that maps empty testHooks to "none" without looking at TestSuccess would record "none" for a test that is still running. Read only settled releases (observedGeneration == generation, no Reconciling condition). Treat AwaitingTests as pending, and treat "none" as TestSuccess True with "no test hooks". Do not read Ready or status.failures (failures becomes 1 even with ignoreFailures).

(2) Tests run only on install and upgrade. A proof result is as old as the last Helm revision; a no-change reconcile does not refresh it.

(3) SVC-130 and SVC-125 must stop if Flux is no longer v2.4.0 / helm-controller v1.1.0. To re-test, change FLUX_VERSION in the workflow and push the branch.

(4) Not measured, outside the question: a hook that hangs until activeDeadlineSeconds. 300 s is equal to the default HelmRelease timeout of 5m, which also bounds the test step when spec.timeout is unset, as in the kit. SVC-130 may want an explicit test timeout above 300 s.

(5) kind was used instead of k3d. The behaviour is in helm-controller, so this does not change the result.

Run 43348759353 printed a wrong outcome because of a defect in my evaluator, which counted pre-install SourceNotReady. Its raw data matches the final run. Run 43349817089 stopped on a version header that install.yaml does not carry.

## The inputs judged

On main (`platform/secrets-lib/chart/templates/`):
- **L1 mounted**: a value at `mounted/<ns>/sa/<sa>/<name>/e<epoch>` or `mounted/<ns>/shared/<name>/e<epoch>`. It renders no Secret. The birth Job writes it create-only. Its source is `-` (random) or `empty` (a placeholder) (`_generated-secrets.tpl` 36-45, 98-125; `_birth.tpl` 19-25).
- **L2 synced**: always a Password generator, a PushSecret `IfNotExists` into `openova/apps/<ns>/<name>/e<epoch>`, and an ExternalSecret `<name>`. The ExternalSecret's target has only a name and `creationPolicy: Owner`, and one key, `password` (130-199). It has no type, no labels of the chart and no other key.
- **L3 mountedCopies**: a synced value copied by the birth Job into a mounted path of a service account, in this region (33-34, 200-206).
- **L4 namespace**: the namespace of all objects of a call (SEC-217; 12-16, 351-358).
- **L5 envFromFiles**: an entrypoint shim that turns mounted files into variables (`_env-from-files.tpl` 1-20).
- **The store**: SecretStore `openbao`, role `eso-ns` (`_secret-stores.tpl` 38-57). Policy `eso-ns` reads `openova/apps/<ns>/*` of its own namespace only (`platform/openbao/chart/templates/_config.tpl` 158-171).

Planned:
- **SEC-219** (wp/SEC-219 at eb70ed6773, `platform/secrets-lib/README.md` lines 96-160 of that commit):
  - `template`: the target's type, labels, annotations and data. Text around `{{ .password }}` is kept.
  - `copies`: more ExternalSecrets of the same value, in the value's namespace only.
  - `join`: other synced values, each under its own key. A joined value is still born by a Password and a PushSecret.
- **SEC-225** (plan): the producer's birth Job writes the value, create-only, under `openova/apps/<reader ns>/...` for each reader the chart names.
- **SEC-226** (plan): `seedFrom`, a Secret and a key in the value's namespace. The birth writes that value when the store's path is absent, and never overwrites a value the store holds.

Three facts cut across the charts:
- **X1, peer regions.** A mounted value has `sharedAcrossRegions` true by default (`_generated-secrets.tpl` 91-95). On the primary of a two-region Sovereign, the birth Job then logs in at each peer as `secrets-birth-<ns>`, a role that exists only for the namespaces in `peerTrust.birthNamespaces` (`_config.tpl` 192-199, 428). No file in the tree sets that list, and slot 08 sets only `selfRegion` and `regions` (`clusters/_template/bootstrap-kit/08-openbao.yaml` 334-336). The login fails before anything is written (`_birth.tpl` 36-39).
- **X2, Secrets without `helm.sh/resource-policy: keep`.** Three of the Secrets a roll-out would seed from have no keep annotation: `powerdns-api-credentials` (`platform/powerdns/chart/templates/api-credentials-secret.yaml` 60-102), the stalwart TLS fallback (`certificate-fallback-secret.yaml` 37-48) and the WordPress media Secret (`media-s3-secret.yaml` 21-45). The postgres, valkey, stalwart admin and OIDC, WordPress SSO and chargeback DSN Secrets carry it (`role-secrets.yaml` 121, 198, 256; `context-secrets.yaml` 64; `admin-secret.yaml` 91; `oidc-client-secret.yaml` 75; `sso-secret.yaml` 44; `db-dsn-secret.yaml` 26). The Helm behaviour itself (it deletes an object that leaves the manifest unless the old object carries keep) is read from Helm's documentation, not run.
- **X3, the same name.** P1, D1, S1 and S2 keep their Secret's name, so the ExternalSecret's target names an object that exists and that Helm created. Whether External Secrets with `creationPolicy: Owner` takes such an object over is not measured here. SEC-219 and SEC-226 should each test it.

## (2) Values given from outside: who writes them into the store, and when

- **What exists.** At first boot the provisioner writes `flux-system/cloud-credentials` (`cloudinit-control-plane.tftpl` 205-213, applied and shredded at 1357; bodies at `hetzner/main.tf` 774-797, 1561-1571 and `huawei/main.tf` 995-1010) and `bootstrap-seed`, from which the kit renders `object-storage` (tftpl 168-179, 198-202; `bootstrap-secrets/object-storage.yaml` 12-28). "No secret store exists before Flux" (tftpl 177-178). The hand-over identity `sovereign-ops` (SEC-196, merged) may create, update and read `catalyst/tofu/*` and `catalyst/cloud/*` (`_config.tpl` 231-244), as service account `sovereign-ops` in `catalyst` (`platform/openbao/chart/values.yaml` 279-281; role at `_config.tpl` 497-505). SEC-197 (the hand-over inputs Secret) is not merged.
- **Who.** The hand-over Job, as `sovereign-ops`, writes each cloud value once, from the hand-over inputs of SEC-197, under `catalyst/cloud/<name>`, and under `openova/apps/<reader ns>/<name>/e1` for each reader: `velero`, `cluster-autoscaler`, `hcloud-csi`, `kube-system`, `huawei-evs-csi`. This is the pattern of SEC-225, a producer writing into each reader's prefix, applied to an outside producer. It needs five policy lines in `sovereign-ops`. No namespace reads another's prefix.
- **When.** At hand-over, never at first boot: OpenBao is installed at slot 08 and itself waits for slots (08 lines 80-84). Before hand-over the drivers keep reading the provisioner's Secret.
- **Bring-up drivers.** K4, K5 and K6 run before or beside OpenBao: the cloud controller comes first (slot 55 lines 52-55), and OpenBao's volume may land on K6's default class. Their Secrets should stay written from `flux-system/cloud-credentials` (class U, writer: the provisioner) and leave the ExternalSecret path of SEC-247. K1, K2 and K3 can move after hand-over.

# INF-710 result: the host security service on the operator-hosted stack

- Date: 2026-11-19, 06:12 to 06:50 UTC
- Cloud: the operator-hosted Huawei Cloud Stack that the provider module `infra/providers/huawei` is written for, region `me-east-215`. The project of the standing test environment, signed with that environment's own cloud credential.
- **Outcome: no.** The stack's console hosts an app of the host security service (HSS), but none of the service's API is published to the cloud's customers. A Sovereign cannot call it with its credential, cannot list protected servers or findings, and cannot install the service's agent by API.

## Question

Can the cloud's host security service be the `native` scan engine of the machine plane on this stack? Four points:

1. Is the service deployed there, and can the Sovereign call it with its own cloud credential?
2. Which operating-system families does it protect there?
3. Can its findings be listed per server by API?
4. Does protection need an agent inside the server, and how is it installed?

## What was run

Read-only probes only, from the agents' host in the cloud's network. No cloud resource was created. Nothing was changed on any cluster. The method is the one of BSS-S2 on the same stack.

1. **The routes to call.**

It calls the service through `huaweicloud-sdk-go-v3` `services/hss/v5`, at `https://hss.<region>.<cloud domain>/` (`huaweicloudstack/config/endpoints.go`: entry `hss`, version `v5`, format `https://%s.%s.%s/`).
   - The SDK release v0.1.223 defines 582 operations of the service in `services/hss/v5/hss_meta.go`. 359 distinct paths are `GET`. All 359 were called.
   - The vendor's API reference of the service for Huawei Cloud Stack, HSS 1.6.1 (issue 01, 2026-04-30, 3,175 pages), documents 550 operations, all under `/v5`, with 341 distinct `GET` paths. Each of the 341 is among the 359. The six routes a scan engine needs (section 1 below) are all documented there.
   - That reference gives the endpoint form `service_name-tenant.region0_id.external_global_domain_name`. So both host names were called: `hss.me-east-215.kom4dc.nationalcloud.om` and `hss-tenant.me-east-215.kom4dc.nationalcloud.om`.

### 2. Operating-system families protected there

- **Measured: none.** No route lists protected servers or their status. `/v5/{project_id}/host-management/hosts`, `/v5/{project_id}/host-management/agent/status` and `/v5/{project_id}/asset/overview/status/os` answer `404 APIGW.0101`.
- The test environment has 12 nodes, 6 per region, all `Ubuntu 22.04.2 LTS`. The project's 13 servers all report `os_type` `Linux` and the image `Ubuntu 22.04 server 64bit`. Neither region has a namespace or DaemonSet whose name contains `hss` or `hostguard`. So the service protects none of them.
- **By the vendor's documentation for this stack, not measured** (Service Overview, tables 7-2 to 7-4). Agent and system vulnerability scan both supported on:
  - Windows Server 2012 R2, 2016, 2019 and 2022 (x86 only). Windows Server 2025 is not listed. Windows 10 and 11: agent only, and only on the cloud's desktop service.
  - Ubuntu 16.04 to 24.04 (x86), 18.04 to 24.04 (Arm).
  - Debian 9 to 11 (x86), 11 (Arm). Debian 12: agent only.
  - CentOS 7.4 to 7.9. CentOS 8.x and CentOS Stream 9: agent only.
  - Red Hat Enterprise Linux 7 to 9, Oracle Enterprise Linux 7 to 9, AlmaLinux 8.4 to 9.4, Rocky Linux 8.4 to 9.5 (9.3 agent only).
  - SUSE Linux Enterprise Server 12 SP5, 15 SP1, 15 SP2 and 15 SP6 (15, 15 SP3 and 15.5 agent only).
  - EulerOS 2.2 to 2.12 (2.7 agent only), Huawei Cloud EulerOS 1.1 and 2.0, openEuler 20.03, 22.03 and 24.03, Kylin V10, UnionTech OS V20.
  - Fedora: agent only.
- The node image of the platform, Ubuntu 22.04, is in that list.

### 3. Findings per server by API

- **On this stack: no.** The per-server route `/v5/{project_id}/vulnerability/host/{host_id}`, called with the id of a real server of the project, answers `404 APIGW.0101`. So do the list routes `/v5/{project_id}/vulnerability/vulnerabilities`, `/v5/{project_id}/vulnerability/hosts`, `/v5/{project_id}/vulnerability/host/hosts`, `/v5/{project_id}/baseline/risk-configs` and `/v5/{project_id}/baseline/host/check-rules`.
- By design the API has them: the vendor's API reference for this stack documents each of them.

### 4. An agent inside the server

- **Yes, by design.** The Service Overview, chapter 7, "Protection Quota Limit": "A server or container node can be protected by HSS only after a quota is allocated to it", and "After a protection quota is applied for, your server or container is not protected yet. You need to go to the HSS console and install an agent for the server or container and enable protection as prompted."
- **How it is installed, by design** (User Guide, section 3.3.1, table 3-3). Two modes, both started from the service's console after sign-in:
  - **Commands or script.** The console shows an install command for Linux or Windows, for one server or a batch. Someone logs in to each Linux server as root and runs it. The agent shows as `Online` on the console after 5 to 10 minutes.
  - **From the console.** The console installs the agent on a server through another server in the same VPC whose agent is already online, with the target's password or key.
  - Both need a protection quota per server, and the permissions `VPCOperatePolicy` and `VPCEPOperatePolicy` granted to the service.
- **On this stack the agent cannot be installed or checked by API.** The install-script route `/v5/{project_id}/setting/agent-install-script` (documented with the mandatory query `os_type` Windows or Linux and `os_arch` x86_64 or aarch64) and `/v5/{project_id}/setting/agent-version` answer `404 APIGW.0101`. Quotas cannot be read either (`/v5/{project_id}/billing/quotas`). So an agent could only come from the console after sign-in, server by server, or be baked into an image. No agent runs on the test environment today.

## Answer

- **Deployed:** an app of the service is in the stack's console.
- **Callable with the Sovereign's credential:** no. None of its 359 `GET` routes is published on the gateway, under either host name.
- **Families protected there:** none measured. The vendor documents Windows Server 2012 R2 to 2022 and the common Linux families for this stack, Ubuntu 22.04 among them.
- **Findings per server by API:** no on this stack. The API has the routes, but the gateway does not publish them.
- **Agent needed:** yes, inside each server, and on this stack it cannot be installed or checked by API.

## What later tasks must take into account

- **INF-720** (the capability `HostSecurity` and the engine `native`) needs the answer yes from INF-710. For the reference pack the answer is no. On this stack there is no endpoint for `ListHostFindings` or `EnsureHostProtection`. The self-hosted runner engine (INF-430) is the only scan engine there.
- **INF-730**: the profile of the reference pack lists no family under `native.vulnerabilityScan`. The console shows the engine choice `native` disabled, with its reason. A `ScanPolicy` with `engine: native` on this pack is `Refused` with the reason `engine-not-available`.
- **INF-G09** cannot turn green on this stack. It stays open until the cloud of a pack publishes such an API.
- **Repeat the probe** when the cloud operator announces the service's API. It takes under a minute. One unsigned call shows the change: `curl -sk https://hss.me-east-215.kom4dc.nationalcloud.om/v5/00000000000000000000000000000000/host-management/hosts` prints `APIGW.0101` today. A published route prints `APIGW.0301` instead. Then run the signed calls again.
- Whether the service is licensed for the account, and whether its API can be published to the cloud's customers, is a question for the cloud operator. It was not asked in this task.
- **Not measured:**
  - The console after sign-in: whether the app shows a quota or any server of the project.
  - Any API that the console app uses behind its own session. A Sovereign holds no console session, so such an API would not serve it anyway.
  - The agent's behaviour on a server. Nothing was installed.

# PRD-080: CPU images for embeddings with rerank, document conversion and transcription

Outcome embeddings: A
Outcome conversion: A
Outcome transcription: A

What this lab test pins. Each image ran as a non-root user, with a read-only root file system, all capabilities dropped and no route out of its network, and was faster than the floor stated below.

- **Embeddings and rerank:** Infinity `michaelf34/infinity:0.0.78-cpu@sha256:5401a057f16f82a7a1202369f674dc15695fe37d8517f3c0263fdfb88b2e2717` (MIT). One release serves two models, both on the ONNX engine (`--engine optimum`):
  - embeddings: `hf://ibm-granite/granite-embedding-107m-multilingual`, revision `d6cffd338414d6a1c1f5decfad5fec62eebc90d5` (Apache-2.0, 384 dimensions);
  - rerank: `hf://cross-encoder/mmarco-mMiniLMv2-L12-H384-v1`, revision `1427fd652930e4ba29e8149678df786c240d8825` (Apache-2.0).
- **Document conversion:** docling-serve `quay.io/docling-project/docling-serve-cpu:v1.38.2@sha256:7a480a1604fa3b42efeddc7db9527690d9f9bc903226136013e2bfe6b1a4dfb0` (MIT). OCR engine `rapidocr` for Latin script. OCR engine `tesseract` with the Arabic traineddata for Arabic.
- **Transcription:** speaches `ghcr.io/speaches-ai/speaches:0.8.3-cpu@sha256:21e3df06d842fb7802ab470dd77c25f0e8c0d22950e8d8c6ae886e851af53ef8` (MIT), with `hf://deepdml/faster-whisper-large-v3-turbo-ct2`, revision `4df90f75321148c3a29a9e2351b7ddf8f5b115a8` (MIT), int8. There are two conditions. The caller sends segments of at most 30 seconds. The CPU has AVX-512: on the one runner without it, this model ran below the floor.

## Question

Which upstream images serve embeddings with rerank, document conversion and transcription on CPU within the serving rules? For each task we tried at most three candidate images and recorded:

- the licence of the image and of the model;
- the image digest, and the model pinned to a 40-character commit;
- whether the image starts non-root and with a read-only root file system;
- throughput on four cores: texts per second, pages per minute on a twenty-page scanned file, and seconds of audio per second;
- one right-to-left (Arabic) sample, for multilingual use.

## Floors applied

The design says a candidate passes when it is "at least as fast as the floor written in the ticket". No ticket carries a floor, so this lab test applied the floors below. Every raw value is in the evidence, so the architect can apply other floors without a new run.

| Task | Floor applied | Why this number |
|---|---|---|
| Embeddings | 2 texts per second; texts of about 500 tokens (the default chunk size); batches of 16; one replica | 7,200 chunks an hour. A library of 10,000 documents of 20 chunks each is indexed in about 28 hours. |
| Embedding one query | under 500 ms at the 95th percentile | It sits inside the search request. |
| Rerank | one query against 8 chunks of about 500 tokens (the default `topK`) in under 2 s at the median | An answer waits for it. |
| Conversion | 2 pages per minute on the twenty-page scanned file | A scanned upload of 20 pages is parsed within 10 minutes. |
| Transcription | 1 second of audio per second | One replica keeps pace with the audio it is given. |

The Arabic sample is recorded, not part of the outcome rule. These bars were used to read it:

- embeddings: recall at 1 of at least 0.8;
- rerank: top-1 of at least 0.8;
- conversion: character error rate of at most 0.15;
- transcription: word error rate of at most 0.40 for Arabic and 0.15 for English.

## What was run

- **Where:** GitHub Actions in openova-io/openova, on branch `spike/PRD-080`. The branch was made from main at 313dd165f and is never merged.
- **Files:** the workflow `.github/workflows/spike-prd-080.yaml`, the orchestrator `tests/spikes/PRD-080/spike.py` and the HTTP client `tests/spikes/PRD-080/client.py`.
- **Runner:** hosted `ubuntu-24.04` with 4 vCPUs (2 cores, 2 threads each), 16 GB of memory and Docker 28.0.4. Four CPU models turned up across the jobs: AMD EPYC 7763 (Zen 3, no AVX-512), AMD EPYC 9V74 (Zen 4), AMD EPYC 9V45 (Zen 5) and Intel Xeon 6975P-C. Each job records its own CPU.
- **How each server ran:**
  - Docker on an internal network, with no route out of it. A small client container on the same network sent every request.
  - The models came from a read-only mount, with `HF_HUB_OFFLINE=1`.
  - The first start used the hardened profile: the image's own user if it is non-root, otherwise uid 10001; `--read-only` with a `/tmp` tmpfs (an emptyDir); `--cap-drop ALL`; `no-new-privileges`; `--cpus 4`.
  - Only if that start failed were weaker profiles tried, one at a time: writable root, then the image's default user, then a route out. The record says which profile served each value.
  - The Kubernetes-only parts of the rules (no service-account token, the network policy, CSI files) are pod fields. Docker has no equivalent, so they were not tested here.
- **Data:** FLEURS (`google/fleurs`, CC-BY-4.0), test splits, parquet revision `168de341b3db6859a9bac1c50a2ef5e3b47647e0`. It has 350 English and 283 Arabic sentences. English and Arabic sentences with the same id are translations of each other.
  - **Embeddings:** 160 passages built from these sentences, 80 English and 80 Arabic. Each is 455 to 507 tokens, 488.8 on average, counted with the bge-m3 tokenizer. There are also 40 short queries. The Arabic sample is 100 Arabic–English translation pairs.
  - **Conversion:** a twenty-page English document and a three-page Arabic document, built from the sentences. Every page has two headings, paragraphs, a three-item list and a 5-row table. Chrome 156 printed each to PDF. The pages were then turned into a scan: 200 dpi grey, a skew of 0.4 to 0.6 degrees, noise, blur, JPEG, and no text layer (text layer measured: 0 characters). The truth for each page is known, so the character error rate (CER) and word error rate (WER) are measured. The English file holds 5,428 words, 40 headings, 20 tables and 60 list items.
  - **Transcription:** 20 English clips (203.9 s with 0.4 s gaps) and 20 Arabic clips (221.7 s). Each language was sent two ways: as one long file, and clip by clip as 20 requests. The reference is the FLEURS raw transcription. The WER is computed after lower-casing and removing punctuation, and for Arabic also after removing diacritics and normalising alef, ya and ta marbuta.
- **Runner tools:** Python 3.12, huggingface_hub 0.26.2, pyarrow 18.1.0, numpy 2.1.3, tokenizers 0.20.3, rapidfuzz 3.10.1, pillow 11.0.0, img2pdf 0.5.1, poppler-utils, fonts-noto-core and ffmpeg (Ubuntu 24.04 packages). The client image was `python:3.12.7-slim-bookworm`.
- **Runs.** All are green. Each run is listed with its commit and the CPU of each job:
  - run 1, `43388368504` (0f1e629fa): all three tasks, all on EPYC 9V74;
  - run 2, `43392577902` (0c08ee527): conversion on 9V74, transcription on 9V45;
  - run 3, `43398373239` (d9807eb13): conversion on 9V45, transcription on 7763;
  - run 4, `43399528791` (f6f2e80d3): embeddings on 9V74;
  - run 5, `43410826633` (149a0b2cf): the pinned candidates again. Embeddings ran on 9V74, conversion on 9V45, and transcription twice, on 9V74 and on Xeon 6975P-C.
- **Changes between runs:** each one was made because the run before showed it was needed.
  - Run 2 mounted the Arabic traineddata where docling's tesseract looks, set `NUMBA_CACHE_DIR` for unstructured, scored against the raw transcriptions and used the turbo repository that speaches accepts.
  - Run 3 gave docling's tesseract engines their own language codes and added clip-by-clip transcription.
  - Run 4 moved Infinity's cache to `/tmp` and gave TEI the safetensors weights of granite.
  - Run 5 put docling's models on one read-only volume, turned on token-counted lengths in Infinity and repeated speaches on two more CPUs.

Other transcription findings:

- speaches does not accept the `mobiuslabsgmbh` turbo repository ("is not supported", run 1). It accepts the `deepdml` one, which holds the same 1.62 GB of weights (run 2).
- speaches loads a model on its first request. The server was ready in 2.4 to 2.6 s. The first five-second request then took 6.5 to 13.9 s with turbo and 1.4 to 3.9 s with small. Memory peaked at 2.9 to 3.0 GB with both models loaded.
- The route shape of the design (`POST /v1/audio/transcriptions`, multipart `file`, `model`, `language`, `response_format`) is native in speaches. In whisper.cpp it works through `--inference-path`. whisper-asr-webservice has only `POST /asr` with an `audio_file` field and query parameters.

### What the runner CPU does to speed

The same image and model gave very different speeds on the CPUs that GitHub handed out:

- whisper-asr-webservice with turbo on one long English file: 3.27 on EPYC 9V45, 2.27 on 9V74 and 1.15 on 7763.
- speaches with turbo clip by clip: 1.75 on Xeon 6975P-C, 1.28 on 9V74 and 0.82 on 7763.

The 7763 is the only one without AVX-512.

Embeddings and conversion stayed far above their floors on every CPU they ran on. Transcription with turbo is the only value close to its floor.

## Outcome per task

- **Embeddings: A.** Infinity with granite-embedding-107m-multilingual and mmarco-mMiniLMv2-L12, both on ONNX in one release, meets the rules. Under the hardened profile it gave 12.99 to 13.52 texts per second against a floor of 2. The query p95 was 16 to 18 ms. 8 chunks were reranked in 1.16 to 1.19 s against a floor of 2 s. The Arabic sample scored 1.00 and 0.95.
  - TEI with the same two models also passes, at 4.20 texts per second and 1.26 to 1.27 s. It is the fallback. It needs two containers, safetensors weights for granite, and a translation of the rerank request shape.
  - The 1024-dimension bge-m3 fails the floor on every image, at 0.41 to 0.58 texts per second.
  - The bge-reranker-v2-m3 reranker fails it on every image, at 17.7 to 27.1 s for 8 chunks.
- **Conversion: A.** docling-serve meets the rules. It converted the twenty-page scan at 13.0 to 20.0 pages per minute with a CER of 0.002, and found every heading, table and list. For Arabic, its tesseract engine with the Arabic traineddata reached 15.0 pages per minute, a CER of 0.084 and the full structure.
  - Tika reads text as accurately and faster, but returns no structure. The parsed-document format needs headings, lists and tables.
  - unstructured is a 20.8 GB image with an Arabic CER of 0.215.
- **Transcription: A.** speaches with large-v3-turbo meets the rules. Sent clip by clip, it ran at 1.28 to 1.76 seconds of audio per second on the two AVX-512 CPUs it met. Its English WER was 0.045 to 0.050 and its Arabic WER 0.115 to 0.131.
  - On EPYC 7763, without AVX-512, it ran at 0.82 to 0.86, below the floor. The small model stays above the floor there (2.5 to 3.0), with Arabic WER 0.26 to 0.27.
  - One long file is not reliable in English with any candidate's defaults. VAD drops words, and without VAD the decoder repeats itself. So the caller must cut audio into segments of at most 30 s.
  - whisper-asr-webservice with turbo also stays above the floor on one long file on all three CPUs it met (1.15 to 3.75). But its route has another request shape, and its image is 5.2 GB.
  - whisper.cpp with turbo is below the floor on two of three CPUs.

  - The package is not dropped.
- **PRD-304 (`bp-speech`):**
  - Image: the pinned speaches digest. Model: the `deepdml` turbo revision in Hugging Face cache layout under `HF_HUB_CACHE`. Set `WHISPER__COMPUTE_TYPE=int8` and `ENABLE_UI=false`.
  - Pod: a numeric `runAsUser`, because the image's user is the name `ubuntu`.
  - The server is ready in about 3 s. The model loads on the first request, which took 6.5 to 13.9 s with turbo. The function test should allow for that, or warm the model first.
  - The bundled five-second sample worked as that first request on every run.

- **Floors:** the floors used here should be written into the tickets of PRD-201, PRD-211 and PRD-304, or replaced there. All raw values are above.
- **What CI could not measure:**

  - real scanned customer documents and real call audio, since all inputs here were FLEURS sentences and synthetic scans;

## What later tasks must take into account

All three outcomes are A, measured in 5 green runs. All five pushes are used. The branch spike/PRD-080 (head 149a0b2cf) is left in place as the evidence.

1. No ticket writes a floor. I applied my own floors and stated them in the record: 2 texts per second; under 2 s to rerank 8 chunks; 2 pages per minute; 1 second of audio per second. Write them into the tickets of PRD-201, PRD-211 and PRD-304, or replace them. Every raw value is in the record.

2. Acceptance check: the record has three Outcome lines, one per task, as the plan entry asks, plus a '## Evidence' heading for check A1. The general spike check in the design's spike section, grep -c '^Outcome: [A-D]$' = 1, can never match this record. Do not wire that check to PRD-080.

3. Changes later packages must take on:
   - (a) Embeddings use a 384-dimension model, granite-107m-multilingual, not the 1024-dimension bge-m3 in the example. bge-m3 ran at 0.41 to 0.58 texts per second on every image. Change the example dimensions in PRD-208 and PRD-209 and any guard that assumes 1024.
   - (b) Infinity counts characters as usage.prompt_tokens unless it runs with --lengths-via-tokenize. Turn the flag on, or the meter's input tokens (N3) are wrong.
   - (c) Infinity's image runs as root and needs INFINITY_HOME and HF_HOME on the /tmp emptyDir before it starts under a read-only root. The speaches image's user is a name. Both charts need a numeric runAsUser.
   - (d) Transcription must be sent in segments of at most 30 s. With any candidate's defaults, one long English file loses about 60 % of its words (VAD on) or falls into repetition loops (VAD off). This is a requirement on the callers in PRD-300 and PRD-306, or a segmenting step to add.
   - (e) The speed of turbo transcription depends on the CPU. Clip by clip it ran at 0.82 on an EPYC 7763 without AVX-512, and at 1.28 to 1.76 on AVX-512 CPUs. Measure on the gate environment's CPU before the catalogue promises a speed.
   - (f) docling-serve 1.38.2 needs the tesseract engine codes eng and ara; it rejects the BCP-47 tags. RapidOCR returns Arabic in visual order, so do not use it for Arabic. PRD-211 is not dropped.
   - (g) If Tika is ever chosen, its full image installs Microsoft's core fonts under their own EULA.

4. What CI could not measure: the pod-level rules (no service-account token, network policy, CSI files) have no Docker equivalent; the gate environment's CPU; real scanned documents and real call audio; quality beyond the Arabic sample built from FLEURS sentences.

5. Maintenance risk: Infinity versions itself 0.0.x, and a v3 alpha line runs in the same repository. TEI is the measured fallback for embeddings. It needs two containers and a translation of the rerank request shape.

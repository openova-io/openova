## The question

For each class U register entry with a removal package in SEC-340, at the pinned chart and image:
1. Do the chart's values expose extra volumes and extra volume mounts for the pod?
2. Do they expose a command and arguments override?
3. Does the image have `/bin/sh`?
4. What are the image's entrypoint and command?
5. Does the program accept a file path or a file variable for this secret?

Then render the chart with the route that the answers allow, and start the pod with a mounted test value.

## Measured results

### Keycloak: entry `keycloak-admin`, package SEC-341

The upstream chart names the Secret under every value:
- The StatefulSet mounts it through a projected volume when `usePasswordFiles` is true, the default that bp-keycloak keeps (`statefulset.yaml` lines 280 to 285).
- Otherwise the StatefulSet takes it by `secretKeyRef` (lines 127 to 132).
- The config-cli Job always takes `KEYCLOAK_PASSWORD` by `secretKeyRef`, with no condition (`keycloak-config-cli-job.yaml` lines 82 to 86).
- With `auth.existingSecret` empty, the chart creates a Secret of its own (`secrets.yaml` line 6).

This is the missing upstream feature: no value drops the reference.

| Render | StatefulSet `keycloak` | Job `keycloak-keycloak-config-cli` |
|---|---|---|
| main | 1 | 1 |
| Route values: `extraEnvVars` sets `KC_BOOTSTRAP_ADMIN_PASSWORD_FILE=/var/run/secrets/openova/admin-password`, `extraVolumes` adds a CSI volume, `keycloakConfigCli.enabled: false` | 1 | not rendered |
| The same values plus a post-render patch (JSON 6902: `test` that `volumes/1/projected/sources/0/secret/name` is `keycloak-admin`, then `remove` it) | 0 | not rendered |

After the patch, the projected volume keeps only `keycloak-postgresql` (the database binding, class T, not this entry).

**Post-render does not reach hooks.** Measured with `helm template --post-renderer` on Helm v3.16.3, using a renderer that renames two strings. It changed the env ConfigMap (not a hook) and left the hook Job's `KEYCLOAK_PASSWORD` unchanged. The kit pins helm-controller v1.1.0, which builds on Helm v3.16.1 (its `go.mod`, line 39). So a `postRenderers` patch on the HelmRelease cannot remove the hook's `secretKeyRef`.

Started, in one pod with a PostgreSQL 16 container:
- **Server.** The rendered env ConfigMap and the rendered `cache-ispn.xml` were used, with the admin password file moved to the mounted path. Two test-only changes: the database host is 127.0.0.1, and `KC_HOSTNAME_STRICT=false` (the frontend env ConfigMap renders empty here). Admin login to the master realm returned 200 with the mounted value and 401 with another value. **PASS.**
- **config-cli.** The rendered hook container (command `/bin/bash -ec` and bp-keycloak's script) ran without its `KEYCLOAK_PASSWORD` entry. It got `SPRING_CONFIG_IMPORT=configtree:/var/run/secrets/openova/` and the object `keycloak.password`. It exited 0, and realm `sec335` was then present (GET 200). Test-only change: the availability wait was set to 60 s. **PASS.**
- **Control.** The same container without the import exited 1 with "Could not connect to keycloak in 60 seconds: password required", and the realm stayed absent (GET 404).

### Gitea: entry `gitea-oauth-source`, package SEC-342

The pod that reads the Secret is bp-gitea's own reconciler. The upstream chart's `gitea.oauth` list is empty (`values.yaml` line 197). The secret value leaves the pod only as an argument of `gitea admin auth add-oauth`, through `kubectl exec`, into Gitea's database.

Started: the rendered script, with its two paths moved to `/var/run/secrets/openova/`, ran as user 1001 on a read-only root filesystem. A stand-in `kubectl` answered like one Ready gitea pod with no sources. It recorded `gitea admin auth add-oauth --name openova-sso … --key gitea-test-client --secret <the mounted value> …`. **PASS.** Control: no `kubectl` call at all; the log says "key/secret not yet present".

### Harbor: entry `harbor-sso-oidc`, package SEC-343

The pod that reads the Secret is bp-harbor's own reconciler. It also reads the administrator password from Secret `harbor-admin` at `/etc/harbor-admin/HARBOR_ADMIN_PASSWORD` (lines 141 to 145). `harbor-admin` is in no register entry, and this test gave it a plain bind mount.

Started: the rendered script, with its two paths moved, ran with `HARBOR_CORE_URL` pointed at the local listener. The listener recorded `PUT /api/v2.0/configurations` with `"oidc_client_secret": "<the mounted value>"`. **PASS.** Control: no PUT; the log says "not yet present".

### Grafana: entry `grafana-sso-oidc`, package SEC-344

| Render | Deployment `grafana` |
|---|---|
| main (`envFromSecret: grafana-sso-oidc-credentials`) | 1 |

Started: Grafana 12.3.1 ran with the rendered `grafana.ini` and that one line changed. ### PowerDNS-Admin: entry `pda-sso-oidc`, package SEC-345

The Deployment is bp-powerdns-admin's own template, and the program is the upstream image. The Secret reaches it in three places:
- `envFrom` (`deployment.yaml` lines 295 to 298);
- the init gate `wait-for-oidc`, which mounts it at `/oidc` and waits for `/oidc/OIDC_OAUTH_AUTHORIZE_URL` (lines 119 to 140, volume line 340);
- the reloader annotation (line 36).

Started: the rendered env of the container ran without `envFrom`. It got `OIDC_OAUTH_SECRET_FILE=/var/run/secrets/openova/client-secret`, a client id, and the three endpoints pointed at the listener. Test-only changes: SQLite in `/tmp` instead of the database binding, port 9191 instead of 80, one worker, and test values for the Flask key and the PowerDNS API key (other Secrets, not this entry). `/oidc/login` gave a 302 with a state. On `/oidc/authorized` with a code, the token request carried `Authorization: Basic`, which decodes to `pda-test-client:<the mounted value>`. **PASS.** Control: the container exited 1 with `FileNotFoundError: … '/var/run/secrets/openova/client-secret'`.

## What follows for the plan

- **Decision rule, outcome "a route works", for all five entries.** No entry becomes `none-upstream`. Each package of SEC-340 uses the route of its row in the summary.
- **SEC-341 needs one path outside its touches:** `clusters/_template/bootstrap-kit/09-keycloak.yaml`, for the `postRenderers` patch. The kit already meets missing upstream knobs this way: `01-cilium.yaml` line 201, `03-flux.yaml` line 145 and `19-harbor.yaml` line 292. The patch carries the `test` operation, so a reordered volume list fails the release instead of removing the wrong source.
- **SEC-341 replaces the upstream config-cli hook with a Job of its own** (`keycloakConfigCli.enabled: false`). It uses the same image and the existing `/bin/bash -ec` script, with route 1. A post-render cannot do this part, as measured above. bp-gitea's configurer is the precedent: it replaced the upstream `gitea.oauth` path for the same kind of reason.
- **openbao-snapshot-bucket.** One more register entry names `removal: SEC-340`: `openbao-snapshot-bucket`, class T, consumed by bp-openbao's own CronJobs. It is outside this spike (class T, no upstream chart), and SEC-340 lists no package for bp-openbao.

## Not measured, and what it needs

- A pod on a cluster with the CSI driver and OpenBao. Here the value came from a bind mount with the measured file shape. The CSI mount is SEC-140's measurement. A pod start on kind needs a runner or a host where kind's node boots, which this host is not.
- Kyverno admission of the changed pod templates, the vcluster placement of Grafana and Harbor (see the readers below), and TLS on the OpenBao listener.
- Rotation. Keycloak reads the bootstrap password only on an empty database. A new value in OpenBao therefore reaches config-cli but not the existing admin user, and config-cli then gets 401. Rotating this value must also change the admin user's password in Keycloak.

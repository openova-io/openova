# INF-030 result: kured beside the upgrade controller on k3s

Outcome: confirms

Date: 2026-11-13. Evidence: branch `spike/INF-030` of openova-io/openova. The branch is never merged. It holds the workflow `.github/workflows/spike-inf-030.yaml` and the scripts under `tests/spikes/INF-030/`.

## The question

Does kured work beside the system-upgrade-controller on the k3s the platform pins? Does a Plan's `spec.window` hold an upgrade until the window opens? Six yes/no answers were asked for:

1. Reboots are serial: **yes**.
2. The lock annotation is set: **yes**.
3. The label `upgrade.cattle.io/controller=system-upgrade-controller` is on the upgrade Pod: **yes**. The controller's own Pod carries the same label (finding F1).
4. kured waits on the node that runs the upgrade Pod: **yes**. As the documentation says, it does not wait on another node.
5. A closed `spec.window` holds a Plan: **yes**. It holds only the start of a rollout, not its end (findings F2 and F3).
6. A server node (embedded etcd member) reboots cleanly with `--drain-timeout=15m`: **yes**.

All six answers held in two full runs (run 2 and run 3). Question 5 also held in run 1.

## What was run

Each CI job builds its own throwaway cluster on one GitHub-hosted runner. Nothing leaves the runner.

- Runner: `ubuntu-24.04` (Ubuntu 24.04.5, kernel 7.0.0-1017-azure), 4 vCPU, KVM enabled.
- Virtual machines: QEMU 8.2.2 and libvirt 10.0.0. Three Ubuntu 22.04 cloud-image VMs (serial 20261106), each with 2 vCPU and 3 GiB, on a NAT network. Real VMs were needed because a container node keeps its sentinel file over a restart and never changes its boot ID. The apt timers were masked, so no sentinel appeared on its own.
- k3s `v1.31.4+k3s1`, the version the Huawei provider pins, with etcd 3.5.16. All three nodes are servers with embedded etcd. The first server uses `--cluster-init` and the other two join it. Flags: `--disable=traefik`, `--disable=servicelb`, `--disable=local-storage`. flannel is the CNI, because the CNI is not under test.
- kured: chart `kubereboot/kured` 6.1.0, the newest in `https://kubereboot.github.io/charts`. Application 1.23.0, image `ghcr.io/kubereboot/kured:1.23.0`. The rendered arguments were `--period=15m --concurrency=1 --start-time=00:30 --end-time=22:00 --time-zone=UTC --reboot-days=su..sa --drain-timeout=15m --lock-ttl=1h --lock-release-delay=5m --blocking-pod-selector=upgrade.cattle.io/controller=system-upgrade-controller --annotate-nodes=true --reboot-sentinel=/sentinel/reboot-required`. Reboots go through `nsenter -m/proc/1/ns/mnt -- /bin/systemctl reboot`.
- system-upgrade-controller `v0.21.0`, the latest GitHub release, from its release manifests.
- Tools on the runner: kubectl v1.31.4, helm v3.16.4, etcdctl 3.5.16.
- A monitor on the runner. Every 5 s it read all Node objects and the kured DaemonSet from whichever API server answered. Every 15 s it read etcd member health. It recorded boot ID, Ready, cordon, kubelet version and the lock holder.

The workflow has four jobs:

- **reboots** (Q1, Q2, Q6, and the drain time-out path).
- **window** (Q3, Q5, and what happens at the end of a window).
- **blocking** (Q4, and the controller's own node).
- **overlap** (disjoint windows with a rollout that outlives its window). This job was added in run 3.

Runs:

- Run 1: https://github.com/openova-io/openova/actions/runs/43350024728 (commit 41f0eb21a). The window job completed. The other two jobs stopped at the kured install, because helm read 127.0.0.1 from the k3s kubeconfig. That was fixed for run 2.
- Run 2: https://github.com/openova-io/openova/actions/runs/43353173444 (commit 61acc4aa9). All jobs passed. Jobs: reboots 131648845352, window 131648845412, blocking 131648845104.
- Run 3: https://github.com/openova-io/openova/actions/runs/43362245259 (commit 821009665). This is a repeat. Each etcd member is now asked for its health on its own, and the overlap job was added. Jobs: reboots 131678235396, window 131678235137, blocking 131678235526, overlap 131678235479.

## Measured values

### Q1 serial reboots and Q2 lock (job reboots)

The sentinel was created on n1 and n2 in the same second.

- **Run 2.** Sentinels at 02:40:17.
  - n1 was cordoned at 02:57:11, showed a new boot ID at 02:57:53 and was schedulable at 02:58:28. The lock was released at 03:03:28.
  - At 03:02:26, n2 logged "Lock already held" while n1 held the lock.
  - n2 was cordoned at 03:17:28, showed a new boot ID at 03:18:03 and was schedulable at 03:18:38.
  - The two unavailable intervals did not overlap. The most nodes unavailable in 520 polls was 1.
- **Run 3.** Sentinels at 04:08:03.
  - n2 was unavailable from 04:26:37 to 04:27:47.
  - n1 was unavailable from 04:38:28 to 04:40:04.
  - The intervals did not overlap. The most nodes unavailable in 445 polls was 1.
- **Lock annotation.** The lock is the annotation `weave.works/kured-node-lock` on DaemonSet `kube-system/kured`. Run 2 recorded the value `{"nodeID":"n1","metadata":{"unschedulable":false},"created":"2026-11-13T02:57:10.984917051Z","TTL":3600000000000}`. It is set back to an empty string 5 minutes after the node is uncordoned, which is the release delay.
- **Node annotations.** kured also wrote `weave.works/kured-reboot-in-progress` and `weave.works/kured-most-recent-reboot-needed`.
- **Time from sentinel to Ready on a new boot.** Run 2: n1 1056 s and n2 2266 s. Run 3: n2 1144 s and n1 1856 s. kured's check timing dominates these times. The first check comes 7.5 to 22.5 minutes after kured starts, the next checks come every 15 minutes, and the lock is held for 5 more minutes after each reboot.
- **The reboot itself.** Over the nine reboots in runs 2 and 3, cordon to new boot ID took 30 to 51 s. Cordon to schedulable again took 70 to 105 s.

- Each node's Job lasted 42 to 50 s. On every node the first Pod failed when k3s restarted, and the Job's second Pod completed a few seconds later.

### Q4 kured waits on the node of the upgrade Pod (job blocking)

Setup:

- A is a node that runs an upgrade Pod.
- B is a node that runs nothing.
- C is the node that runs the system-upgrade-controller Pod.
- The upgrade Pod comes from a Plan `hold`. Its container waits for a release file, so the Pod lasts as long as the test needs. The Pod carries the controller's labels (`upgrade.cattle.io/controller=system-upgrade-controller`, `upgrade.cattle.io/plan=hold`, and so on).
- The sentinel was created on A, B and C in the same second.

Results:

- **Run 2** (A=n1, B=n2, C=n3; sentinels at 02:40:46).
  - B was drained at 02:51:47 and rebooted while the Pod on A was Running. B does not wait.
  - The lock was free from 02:58:04.
  - A logged `Reboot blocked: matching pods: [apply-hold-on-n1-...]` at 02:50:59 and again at 03:05:59. The second message came after the lock was free. A was not rebooted in 33 minutes with the sentinel present.
  - The release file was created at 03:14:13. A's next check at 03:20:59 drained it, and A rebooted at 03:21:01. A waits, then reboots once the Pod is gone.
- **Run 3** (A=n1, B=n3, C=n2; sentinels at 04:11:04).
  - B rebooted at 04:21:13 while the Pod on A was Running.
  - A logged "Reboot blocked" at 04:30:11, after the lock was free at 04:28:14.
  - A rebooted at 04:45:13, after the Pod ended at 04:44:30.
- In both runs the unavailable intervals did not overlap. The most nodes unavailable was 1. etcd stayed at 2 or more healthy members, and the API answered every poll.

### Q5 a closed window holds a Plan (job window)

The Plan was created while its window was closed. The window opened 5 to 6 minutes later and stayed open for 60 minutes.

- Before the window opened, no Job existed in 98, 95 and 109 polls (runs 1, 2 and 3, every 3 s).
- While the window was closed, the Plan condition was `Complete=False reason=Waiting message=current time is not within configured window`. The event read "Waiting for start of Spec.Window to sync Jobs for version v1.31.5-k3s1".
- The first Job appeared 57 s, 59 s and 31 s after the window opened (runs 1, 2 and 3). The controller checks the window about once a minute.

### Q6 a server node reboots cleanly with --drain-timeout=15m (jobs reboots and blocking)

There were nine server reboots in runs 2 and 3. All nine were clean.

- Each drain finished in 0 to 3 s. It evicted coredns, metrics-server and one replica of a 3-replica Deployment with `maxUnavailable: 1`.
- No node ever reported NotReady (`max_not_ready` 0 in every job). The reboot is shorter than the 40 s grace period of the node monitor.
- etcd had 3 members before and after each reboot. At least 2 were healthy at every 15 s sample. Run 3 asked each member on its own.
- The API answered every 5 s poll: 0 unreachable in 520, 797, 445 and 686 polls.
- After the reboots every Pod was Running, and the Deployment was at 3/3.

## Findings beyond the six questions

### F1. The controller's own Pod blocks its node for ever

The selector `upgrade.cattle.io/controller=system-upgrade-controller` matches the upgrade Pods. It also matches the system-upgrade-controller Pod, which runs all the time on a control-plane node.

- On node C, kured logged `Reboot blocked: matching pods: [system-upgrade-controller-8557f596d6-...]`. In run 2 this was at 02:58:41 and 03:13:41. In run 3 it was at 04:24:41 and 04:39:41.
- C was never rebooted while that selector was in force: 47 minutes with the sentinel in run 2, and 40 minutes in run 3.
- The selector was then changed to `upgrade.cattle.io/controller=system-upgrade-controller,upgrade.cattle.io/plan`. Inside one selector the comma means AND. With this selector kured logged `Blocking Pod Selectors: [upgrade.cattle.io/controller=system-upgrade-controller,upgrade.cattle.io/plan]`, and C rebooted at 03:45:17 (run 2) and 05:06:12 (run 3). The controller Pod moved to another node.
- Before the change, the narrower selector matched only the upgrade Pod, and the old selector matched the upgrade Pod and the controller Pod.

On a Sovereign with one control-plane node, the old selector means that node is never rebooted by kured.

### F2. The window holds the start of a rollout, not its end

A Plan with a 2-minute window, three nodes and Jobs of 150 s each was run in runs 1, 2 and 3.

- The second and third Jobs were created after the window had ended. In run 1 this was 73 s and 226 s after the end. In run 2 it was 76 s and 230 s, and in run 3 it was 41 s and 196 s.
- The controller checks the window only while no node is in progress. Its own Plan schema says Jobs "will not be generated outside this time window", but the measurement shows otherwise once a rollout has started.

### F3. Disjoint windows still let two nodes be unavailable at once (job overlap, run 3)

Setup: the Plan window ran from 04:11 to 04:13. kured's span started at 04:13. The two windows were disjoint with no gap. Each upgrade Job cordoned its node and lasted 600 s. All three nodes had a sentinel. kured used the narrower selector from F1.

- The Jobs were created at 04:11:08, 04:21:14 and 04:31:21. The last two came 494 s and 1101 s after the Plan window ended.
- From 04:30:02 to 04:31:08 (71 s), n1 was cordoned for its upgrade while kured drained and rebooted n2.
- From 04:36:53 to 04:38:27 (99 s), n2 was cordoned for its upgrade while kured rebooted n1.
- The most nodes unavailable was 2, in 34 of 423 polls.
- The node-local selector worked as designed. It held n3 at 04:16:57 and n1 at 04:21:51 while their own upgrade Pods ran. It cannot see another node.
- These upgrade Jobs only cordoned their nodes. A real k3s upgrade also restarts that node's etcd member for a few seconds. On a three-server control plane, that coinciding with a server reboot would leave one of three members.

### F4. A node that cannot drain keeps the lock and stays cordoned

One Pod was pinned to n3 with a budget that forbids its eviction (runs 2 and 3).

- kured started the drain at 03:28:23 (run 2) and 04:56:39 (run 3).
- It gave up after exactly 15 minutes with `global timeout reached: 15m0s`.
- It waited the 5-minute release delay, uncordoned the node, and started the next drain in the same second (03:48:23 and 05:16:39). Ticks are not lost while a check runs: the drain and the delay together take longer than the period.
- The node was not rebooted, and its boot ID was unchanged. It stayed unschedulable, and it held the lock almost all the time. No other node could reboot while this lasted.

### F5. Other observations

- A real k3s upgrade Pod exists for about 45 s per node, and kured checks every 15 minutes. The node-local selector therefore rarely meets a real upgrade. It is the second guard only.
- The Ready condition did not change during any reboot. A health check must use the boot ID and the cordon, not Ready.
- In run 3, the kured Pod on n1 restarted once when n2 rebooted, and its check schedule started again. The cause was not captured, because only one previous container log is kept. No harm followed.

## What could not be measured in CI

- **The platform's own network and cloud.** The cluster used flannel, not Cilium, and KVM VMs, not Huawei instances. No cloud account was allowed. Reboot durations on Huawei instances will differ.
- **The production topology.** The Huawei provider defaults to one k3s server per region (`huawei_control_plane_count` 1) plus agent nodes. The spike used three servers, as the plan entry asks. On a one-server control plane, every reboot of the server stops that region's API and etcd for the reboot. Here a reboot took 30 to 51 s from cordon to new boot. That outage was not measured here. Agent Plans and agent reboots were not tested.
- **The real upgrade Plans.** The Plans of the Sovereign lifecycle area do not exist yet. How long a rollout runs past its window (F2, F3) depends on their node count, cordon and drain settings, and on agent Plans.
- **A collision with a real k3s upgrade.** A k3s restart during a server reboot was not forced. F3 used cordon-only Jobs.
- **Other kured paths.** kured's closed span from 22:00 to 00:30 was not exercised, because all runs were between 02:00 and 05:30 UTC. The lock TTL expiry after a crashed holder was not tested. Each of these needs a longer or differently timed job, or a Huawei test Sovereign.

## What follows for the plan

None of the stop conditions fired. Question 5 is yes, and Question 6 is yes. The plan goes ahead with these changes:

1. **INF-040** pins chart `kubereboot/kured` 6.1.0 (kured 1.23.0).
2. **INF-050** sets the blocking selector to the one value `upgrade.cattle.io/controller=system-upgrade-controller,upgrade.cattle.io/plan`, as one list item. This is the "different label" case. The single-label selector blocks the system-upgrade-controller's node for ever (F1).
3. **The two-window rule holds only with a gap.** A Plan window bounds when a rollout may start. Each upgrade window must end before kured's span begins by at least the longest rollout: nodes × time per node, plus any drain. INF-G01 should check that gap, not only that the spans do not intersect. The Sovereign lifecycle area should be told the gap when it writes its Plans. The claim that disjoint windows keep unavailability to one node at most was measured false without the gap: two nodes in F3.
4. **drainTimeout stays at 15m.** INF-G01 should also fail when any node stays cordoned by kured for longer than drainTimeout plus lockReleaseDelay (20 minutes). That state means a drain that cannot finish, and it holds the cluster's reboot lock (F4).
5. **Reboot checks use the boot ID and the cordon, not the Ready condition** (F5).

# CTL-050: push trigger, batch commit and lock on the pinned versions

Outcome: differs

- S1, Receiver and instance-wide webhook: differs
- S2, atomic batch commit: as designed
- S3, the lock policy: differs
- S4, adoption without change: as designed
- S6, what creates Environment objects: two writers found, and neither is an HTTP route

## Question

We wanted to know four things on the versions the platform pins:

1. Does the planned Receiver get triggered by a Gitea instance-wide webhook?
2. Is Gitea's batch contents call all-or-nothing?
3. Does the planned lock policy behave as intended?
4. Does Flux adopt an existing object without changing it?

We also wanted to know what creates Environment objects.

## S1: Receiver and instance-wide webhook. Word: differs

**The planned call creates the wrong kind of hook (runs 1, 2 and 3):**
- We called `POST /api/v1/admin/hooks` with the planned fields: type gitea, content type json, events push, and a secret. It returned HTTP 201.
- Gitea stored the hook as a default webhook, not a system webhook. The row has is_system_webhook=0, repo 0, owner 0.
- The hook never fired for an existing repository. There was no delivery, and no source got a new revision within 60 s.
- Gitea copied the hook into a repository created afterwards: 1 hook there, 0 hooks on the existing repository.
- `GET /api/v1/admin/hooks` returned `[]` straight after the create, so the list does not show this hook.

**The same call with `config.is_system_webhook: "true"` works (runs 1, 2 and 3):**
- It returned HTTP 201. The row has is_system_webhook=1, the list shows the hook, and it fires for every repository.

**What Gitea sent and how the Receiver answered:**
- Gitea 1.22.3 sent these headers:
  - Content-Type application/json
  - X-GitHub-Event and X-GitHub-Event-Type, both push
  - X-GitHub-Delivery
  - X-Hub-Signature and X-Hub-Signature-256
  - X-Gitea-* and X-Gogs-* headers for Event, Event-Type, Delivery and Signature
- The Receiver of type github answered 200 to every delivery. Gitea delivered to the cluster-local host, so the allow-list works with that one host name.

**Time from push to a new `status.artifact.revision`.** Three sources were selected: one by name and one by each of the two labels. All three moved together:
- run 1: 2.20 to 2.21 s
- run 2: 3.01 to 3.02 s
- run 3: 3.02 to 3.03 s

**The unselected source was left alone in every run.** It pointed at the same repository, had another label and a one-hour interval. Its revision did not change for 75 s (a 60 s window plus 15 s). It got no reconcile annotation.

**Updating and the fall-back (runs 2 and 3):**
- `PATCH /api/v1/admin/hooks/{id}` with `{"active": false}` returned HTTP 200.
- We then measured the organisation-webhook fall-back: `POST /api/v1/orgs/openova/hooks` with the system hook inactive. It returned 201.
- With the organisation webhook, push to revision took 2.09 to 2.10 s (run 2) and 4.10 s (run 3). The unselected source was again left alone.

**Fall-back that applies:** neither of the design's fall-backs is needed. The Receiver of type github works, and a system webhook can be created. The one amendment is that EnsureSystemHook must send `config.is_system_webhook: "true"`. Without it, every start-up adds one more default hook, because the list never shows the hook it made. The organisation webhook was also measured to work, if the architect prefers it.

## S2: batch contents call. Word: as designed

All values below were seen in runs 1, 2 and 3 unless a run is named.

- **Two creates, then an update with a wrong sha.** HTTP 422 with "sha does not match [given: <sent>, expected: <current blob>]". Neither create was applied (each path returned 404), and the branch head did not change.
- **The wrong-sha update first, then two creates.** The same 422. Nothing was applied and the head did not change.
- **A create, plus a create on a path that already exists.** HTTP 422 with "repository file already exists [path: ...]". Nothing was applied.
- **A create, plus two wrong-sha updates (runs 2 and 3).** HTTP 422. Only the first mismatch was reported, and nothing was applied.
- **Control with the correct sha.** HTTP 201. It made one new commit whose parent is the old head, and the commit holds all three files. The seed call with five creates also made one commit with five files.

**Fall-back:** none. CTL-110 holds as written.

**Note for the library:** the error names the two shas but not the path, and it reports only the first mismatch. The library can tell which file failed from the sha it sent.

## S3: the lock policy. Word: differs

**Compiling the policy:**
- The API server refuses the planned policy (runs 1, 2 and 3). The audit-annotation expression `cond ? <string> : null` fails with "found no matching overload for '_?_:_' applied to '(bool, string, null)'".
- Wrapping either branch in `dyn()` is refused with "must evaluate to one of [string null_type]".
- The policy compiles if the null branch becomes `''` (run 3) or if the annotation is removed (run 2).
- With `''`, only break-glass requests get the annotation. In run 3, one audit event carried `catalyst-intent-lock/break-glass = "alice: restore service after incident 42"`. The event user is the impersonator, and the value names the impersonated user. No other event carried the annotation.
- Every other expression compiled unchanged. `status.typeChecking` showed no warnings.

**With the binding at Audit and Warn (runs 2 and 3):**
- A cluster-admin create succeeded, with the warning "Validation failed for ValidatingAdmissionPolicy 'catalyst-intent-lock' with binding 'catalyst-intent-lock-applications': desired state of Application is owned by Git; ...".
- The metric `apiserver_validating_admission_policy_check_total` exists and carries the labels `policy` and `policy_binding`.
- One violating request added +1 with `enforcement_action="audit"` and +1 with `enforcement_action="warn"`. Both carry `error_type="invalid_error"`, which is the label Kubernetes gives a failed check.
- Requests that pass are not counted.
- The planned report adds audit and warn together, so it rises by two per request, not by one.

**With the binding at Deny (runs 2 and 3; the figures are from run 3):**
- A cluster-admin create was refused by the lock, and the deny count rose by 1.
- The controller account wrote status through the status subresource. Allowed.
- The controller account added a finalizer, and later removed it. Both allowed.
- The controller account changed `spec.blueprintRef.version`. Refused.
- Cluster-admin added the reconcile annotation and a label. Both allowed.
- A cluster-admin delete was refused. The audit log shows code 403.
- A Kustomization impersonating `org-intent-acme`, with the planned Role in namespace `acme`, created the Application in 6.8 s. It then applied a spec update from Git.
- A control account `tenant-beta` had the same Role. Its Kustomization failed with "dry-run failed (Forbidden) ... denied request", and no Application was created.
- kustomize-controller, using its own account, created an Application. It pruned the Application after the file was deleted from Git. The delete was by `system:serviceaccount:flux-system:kustomize-controller` and returned 200.
- A garbage-collection delete through an owner reference was allowed. The user was `system:serviceaccount:kube-system:generic-garbage-collector`.
- A namespace delete removed the Application in 5.5 s. The user was `system:serviceaccount:kube-system:namespace-controller`, with verb `deletecollection`.
- Break-glass with the group `catalyst:break-glass` and a 33-character reason was allowed.
- Break-glass was refused in each of three other cases:
  - the reason was "short"
  - the reason was given without the group
  - the group was given without a reason
- Run 1's audit log, taken with no lock in force, shows the same collector and Flux identities.

**Fall-back that applies:** the architect amends the expressions. Spec comparison works, so the stronger fall-back (listing controller accounts) is not needed. Two amendments were measured:
1. The audit annotation's null branch becomes `''`.
2. The report counts only `enforcement_action="audit"`. Otherwise every violating request is counted twice.

## S4: adoption. Word: as designed

**The default case:**
- We created an Application with field manager `catalyst-api` (operation Update). The live object equalled the intent file in its serialised form.
- A Kustomization then applied that byte-equal file. It was Ready in about 1 s, with the event "Application/adopt/adopted-site configured".
- `metadata.generation` stayed at 1 (runs 2 and 3).
- `resourceVersion` moved once, from 1083 to 1091 in run 3. The cause is Flux adding its two labels, `kustomize.toolkit.fluxcd.io/name` and `kustomize.toolkit.fluxcd.io/namespace`.
- A second reconcile changed nothing. The resourceVersion stayed at 1091.

**Managed fields:**
- Before adoption: catalyst-api (Update) owns spec.
- After adoption: kustomize-controller (Apply) owns spec, and catalyst-api (Update) still owns spec too.
- The report's `nonFluxSpecManagers` for this object stays `["catalyst-api"]`.

**With the override flag:** we restarted kustomize-controller with `--override-manager=catalyst-api`. Generation stayed at 1. Afterwards only kustomize-controller owned spec, and `nonFluxSpecManagers` was `[]` (runs 2 and 3).

**Fall-back:** none. CTL-162 step 5 holds.

## S6: what creates Environment objects

The planned search finds 0 matches. A wider read of the repository at be5860136 finds two creators, and neither is an HTTP route:

- **The organization-controller.** It does a plain Create of `<slug>-<envType>` at `core/controllers/organization/internal/controller/environment_ensure.go:218`. It is called from `organization_controller.go:925` once the Organization's vCluster is Ready.
- **catalyst-api, in the background.** It does a server-side apply of the control-plane Environment at `products/catalyst/bootstrap/api/internal/handler/post_handover_spine_apps.go:891`, with field manager `catalyst-api/spine-application-producer`. It runs at start-up (`deployments.go:714`) and when Phase 1 finishes (`phase1_converged_late.go:236` and `phase1_watch.go:1637`).
- **Charts and the bootstrap kit.** The only manifest is the QA fixture `products/catalyst/chart/templates/qa-fixtures/environment-qa-omantel.yaml`. It is off by default (`qaFixtures.enabled: false`). The bootstrap kit has none.

**Measured in run 3:** we bound the environments stage at Deny and acted as each writer:
- The organization-controller's account tried a create.
- catalyst-api's account tried a server-side apply.
- Both were refused with "denied request: desired state of Environment is owned by Git".

Neither branch of the plan's S6 rule holds. No route enters C9. And stage `environments` cannot move to deny with CTL-212 while these two writers create Environments directly.

  - Use `''` in place of `null` in the audit annotation.

  - Adoption removes the old manager's managedFields entry.
  - The report ignores managers that share spec with Flux.

## What later tasks must take into account

All of S1, S2, S3, S4 and S6 were measured in CI on the pinned versions: k3s v1.31.4+k3s1, Flux v2.4.0 and the Gitea chart 10.5.0 (app 1.22.3). Three green runs, three pushes. The evidence is branch spike/CTL-050, head 72c0ad9d4, and the artifact ctl-050-evidence of run 3.

Points the lead architect must act on:
(1) The planned lock policy is REFUSED by the Kubernetes 1.31 API server. The audit-annotation ternary of string and null does not compile, and dyn() on either branch is also refused. Using '' as the null branch compiles and keeps the break-glass audit trail (measured). CTL-150 must carry this amendment. Its chart test must apply the policy to a real API server, because a render-only test would pass the broken policy.
(2) The planned EnsureSystemHook body creates a Gitea DEFAULT webhook, not a system webhook. That hook never fires for existing repositories, is copied into every new repository, and is not returned by GET /admin/hooks, so the ensure loop would add a duplicate on every start-up. It needs config.is_system_webhook: "true" (measured to work and to be listed). CTL-130 must take this.
(3) One violating request adds +1 to the audit series and +1 to the warn series of apiserver_validating_admission_policy_check_total. The planned report sums both, so it double-counts. Count audit only.
(4) After adoption, catalyst-api stays a co-owner of spec in managedFields, so nonFluxSpecManagers never reaches zero for adopted objects. This blocks the "at zero" rule CTL-178 depends on. kustomize-controller with --override-manager=catalyst-api clears it with no generation change (measured), but that flag applies to every object Flux applies. The architect chooses the remedy.
(5) Environments are created by the organization-controller (a plain Create) and by catalyst-api in the background (a server-side apply), not by a route or a chart. With stage environments at Deny, both writers are refused (measured). CTL-212 must not switch that stage until both writes move to Git or both accounts are listed as writers.

Not measurable in one CI job: two regional Giteas on one shared database (the one system-hook row serving both regions; CTL-055 / S10 needs two Gitea instances); the full eight-binding set under the real controllers; latencies on the platform's own clusters.

The workflow triggers only on pushes to spike/CTL-050. No PR was opened, no other branch was touched, and nothing was built locally.

# INF-020 result: hardware virtualisation on worker nodes

- Date: 2026-11-19, 09:16 to 10:00 UTC.
- Where: the standing two-region test Sovereign `hw307`, on the operator-hosted Huawei Cloud Stack that the provider pack `infra/providers/huawei` is written for. Both regions, all 12 nodes.
- **Outcome: no.** No node exposes hardware virtualisation to its guest. `/dev/kvm` is absent on all 12 nodes, no CPU carries the `vmx` or `svm` flag, and every CPU carries the `hypervisor` flag. A workload that needs `/dev/kvm` cannot run on these nodes as they are.

## Question

Does a worker node of the pack in use expose hardware virtualisation, so that a workload that needs `/dev/kvm` can run on it? Such workloads are KubeVirt virtual machines (epic INF-800), micro-VM sandbox runtimes (Kata Containers, Firecracker, gVisor on its KVM platform) and nested hypervisors. For each pack: the flavour, the image, and `kvm: yes` or `kvm: no`.

## Result per pack

- `pack: huawei`, `flavor: m7n.2xlarge.8` (workers, 8 vCPU, 64 GiB) and `m7n.xlarge.8` (control plane, 4 vCPU, 32 GiB), image Ubuntu 22.04.2 LTS, `kvm: no`. Measured on 12 of 12 nodes. The only pack with an installed environment (FND-070 baseline).
- `pack: local`: not measured by this spike. Its nodes are privileged containers on the hosted CI runner (CLD-055), and that runner exposes `/dev/kvm` (CLD-055, MIG-050).
- `pack: hetzner`: not measured. No Sovereign of this pack was looked at.

## What was run

All of it read-only. Nothing was created or changed on any cluster or in the cloud. Each command names its kubeconfig file.

1. **The measurement.** The architect ran it at 09:16 UTC. One `kubectl exec` per node into the pod of the storage driver's node DaemonSet: namespace `huawei-evs-csi`, container `evs-csi-plugin`. That container mounts the host's `/dev` at `/dev` (`platform/huawei-evs-csi/chart/templates/node-daemonset.yaml`, volume `device-dir`, lines 136, 137 and 163 to 166). So `test -c /dev/kvm` reads the host's device list. `/proc/cpuinfo` in any container shows the host kernel's CPU flags. The two pod lists the script keeps between steps were written to `/dev/shm` on the agents' host, not on a node.
2. **The facts beside it**, at 10:00 UTC: `kubectl get nodes` in each region, grouped by role (vCPU, memory, operating system, kernel, the instance-type label, a KVM device resource), and the region list the Sovereign records, from the ConfigMap `catalyst-system/sovereign-fqdn` in region a, key `regionsJson`. The nodes do not name their flavour: their label `node.kubernetes.io/instance-type` is `k3s`.

The measurement script, as run:
```sh
#!/usr/bin/env bash
# INF-020 measurement, read-only: does a node expose hardware virtualisation? One exec per node into the storage
# driver's node pod (namespace huawei-evs-csi, container evs-csi-plugin, which mounts the host's /dev). Nothing is created or changed.
export KUBECONFIG=/dev/null
for r in a b; do
  K=/home/openova/.kube/sovereigns/hw307-$r.yaml
  echo "== region $r  $(date -u +%FT%TZ)"
  kubectl --kubeconfig "$K" -n huawei-evs-csi get pods -l app=csi-evs-node -o jsonpath='{range .items[*]}{.metadata.name}{" "}{.spec.nodeName}{"\n"}{end}' 2>/dev/null > /dev/shm/inf020.$r
  [ -s /dev/shm/inf020.$r ] || kubectl --kubeconfig "$K" -n huawei-evs-csi get pods -o jsonpath='{range .items[*]}{.metadata.name}{" "}{.spec.nodeName}{"\n"}{end}' 2>/dev/null | grep csi-evs-node > /dev/shm/inf020.$r
  while read p n; do
    out=$(kubectl --kubeconfig "$K" -n huawei-evs-csi exec "$p" -c evs-csi-plugin -- sh -c 'if test -c /dev/kvm; then echo kvm-device=present; else echo kvm-device=absent; fi; echo vmx-or-svm-lines=$(grep -cwE "vmx|svm" /proc/cpuinfo); echo cpus=$(grep -c ^processor /proc/cpuinfo); echo hypervisor-flag-lines=$(grep -cw hypervisor /proc/cpuinfo); echo model=$(grep -m1 "model name" /proc/cpuinfo | cut -d: -f2)' </dev/null 2>&1 | tr '\n' ';')
    echo "node ...${n: -14}: $out"
  done < /dev/shm/inf020.$r
done
```

## Measured values

- `/dev/kvm`: absent on 12 of 12 nodes, workers and control plane, in both regions.
- `vmx` or `svm` flag: 0 CPU lines on every node.
- `hypervisor` flag: on every CPU of every node (8 of 8 on a worker, 4 of 4 on a control-plane node). Each node is itself a virtual machine, and its hypervisor does not pass the virtualisation extensions through.
- CPU: Intel Xeon Gold 6348 at 2.60 GHz on every node.
- Workers: 10, five per region. 8 vCPU, about 62.6 GiB reported by the kubelet. Recorded flavour `m7n.2xlarge.8`.
- Control plane: 2, one per region. 4 vCPU, about 31.2 GiB. Recorded flavour `m7n.xlarge.8`.
- Image: Ubuntu 22.04.2 LTS on every node. Kernel `5.15.0-203-generic` on 11 nodes, `5.15.0-76-generic` on the control-plane node of region b. k3s `v1.31.8+k3s1`.
- No node offers the resource `devices.kubevirt.io/kvm`.

## Answer

- **Hardware virtualisation on the worker nodes of the `huawei` pack: no.** The worker flavour `m7n.2xlarge.8` does not expose it to the guest, and neither does the control-plane flavour `m7n.xlarge.8`.
- What cannot run on these nodes as they are: KubeVirt virtual machines; Kata Containers, Firecracker and other micro-VM runtime classes; gVisor on its KVM platform; QEMU with KVM acceleration; a nested hypervisor such as a nested ESXi host.
- What still runs: gVisor on its default `systrap` platform, which the upstream documentation names the better choice "when running inside a VM, or on a machine without virtualization support" (https://gvisor.dev/docs/architecture_guide/platforms/); and QEMU with software emulation (TCG), which is slower.

## What the cloud's documentation says (not measured)

- The FAQ for bare-metal servers says: "Secondary virtualization is not supported by BMS. That is, virtualization software cannot be installed on a BMS." (https://support.huaweicloud.com/intl/en-us/bms_faq/bms_faq_0001.html, read on 2026-11-19).
- These pages are for the vendor's public cloud, not for the operator-hosted stack. The resource guides of Huawei Cloud Stack are on `support.huawei.com` and answered `403` to an unauthenticated read. They were not read.

## What later tasks must take into account

- **Epic INF-800: INF-810, INF-820, INF-830** (KubeVirt). The epic is scheduled only where this spike says yes for a pack, or where a bare-metal pack exists. For the `huawei` pack the answer is no. INF-810 does not start for this pack. INF-820's profile flag for hardware virtualisation is false for this pack. INF-830 (gate check INF-G10) cannot be walked on this pack's gate environment. The epic waits for a bare-metal pack, or for a flavour that passes the extensions through. Run the measurement script above again on a node of that flavour first.
- **NET-330** (bridged secondary network for virtual machines). It waits with INF-810, as its plan entry says. This answer does not schedule it.
- **AIP-201** (node preparation for the sandbox class). The node preparation stays as AIP-030 recorded it: the Kubernetes version and gates, no runtime binary, no containerd handler, no RuntimeClass. It adds no KVM device plugin and no `/dev/kvm` mount. On this pack the sandbox class runs on a platform that needs no `/dev/kvm`: gVisor `systrap`. Never gVisor's KVM platform, Kata Containers, Firecracker or another micro-VM runtime class. AIP-201 must read the platform the worker image starts gVisor with, record it, and prove the worker becomes Ready on a reference-class node, where `/dev/kvm` is absent.
- **AIP-203** (the kagent chart, which depends on AIP-201). Its WorkerPool and worker values must not ask for `/dev/kvm` or set gVisor's KVM platform.
- **MIG-112** (worker image and conversion) and test 11 of MIG-030 (conversion time on a worker node, not run). A conversion Pod on this pack's workers runs `virt-v2v` and libguestfs with software emulation (`LIBGUESTFS_BACKEND=direct`, QEMU TCG). It must not request `/dev/kvm`. Plan its time with the numbers MIG-050 measured without KVM: about 220 s for the Debian conversion, against about 40 s with KVM. The hermetic test on hosted CI runners is not affected: those runners expose `/dev/kvm`. Test 11 of MIG-030 reads `/dev/kvm` from this result file and does not probe again.
- **MIG-020 and MIG-133** (the lab vSphere). A lab vSphere cannot run as a nested ESXi host on servers of this pack: ESXi needs the extensions these guests lack. The lab runs on physical hosts, or on a cloud whose flavour exposes them.
- **Repeat** the measurement script when a new flavour or a new pack is offered. It is read-only and takes a few seconds per node.

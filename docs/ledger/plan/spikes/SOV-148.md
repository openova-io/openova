# SOV-148 Lab test: first-boot steps from a fetched, checksum-pinned bundle (result)

Date: 2026-11-18, one session, on origin/main 613b4d2388. Type: lab test. Outcome:

- A control-plane machine of the `local` pack booted from one fetched, checksum-pinned bundle that holds its whole `runcmd`, in both regions, with the upstream hosts of the fetch blocked. The kit core came up Ready and the console answered.
- On the worst-case renders of the two cloud modules, the bundle takes 10,498 to 12,993 bytes out of the control-plane user data. What stays inline is a stub of 526 bytes, the values of the installation (1,453 to 1,488 bytes) and, on the reference cloud, the two items that report to the parent (1,344 bytes).
- Neither image pre-pull item shortens an installation that the pack can measure. SOV-149 can delete both.
- The two ServiceAccount items fit one function, and the lab found a defect in them on main: the second item can reuse the first item's token.
- Five follow-up tasks, listed at the end.

## Question

How much of the `runcmd` block of the shared control-plane template (`infra/providers/_shared/cloudinit-control-plane.tftpl`) can become one script bundle that the node fetches before k3s with the helper `oci_fetch` of SOV-142, checks against a SHA-256 carried in the user data, and falls back to the catalogue Git at a pinned commit for? Six points:

1. the bytes that stay inline;
2. what the parent sees when the fetch fails or the checksum differs;
3. the seconds each item of today's `runcmd` takes, from a cloud-init log;
4. whether the host files and the fixed parts of `registries.yaml` and `cilium-values.yaml` can travel in the bundle;
5. whether the two image pre-pull items shorten the installation, and by how much;
6. the two ServiceAccount items as one function.

## What was run

Three lab branches, never merged, each origin/main plus one lab commit:

- `lab/SOV-148-a` (81a330b3c7): nothing else. Today's `runcmd`, timed.
- `lab/SOV-148-c` (4b141838d7): the background image pre-pull item deleted.
- `lab/SOV-148-b` (ae701a4e9f): the local module boots each control plane from a bundle. A lab file `infra/providers/local/lab_sov148.tf` and a 30-line Python origin do this:
  1. take the `runcmd` list of each rendered control-plane user data and make of it the script cloud-init itself makes (`#!/bin/sh`, then each item and a newline);
  2. replace each value of the installation in that script by a shell reference `${V_<NAME>}`. There are 15 values: the two k3s tokens, the node address and external address commands, the k3s extra arguments, the region label, the pod and service ranges, the Sovereign FQDN, the k3s version and its tag form, the Git URL and branch, the pull user and the pull token;
  3. serve the result from an origin container on the machine network (port 5000, the OCI manifest and blob endpoints) as `node-artifacts/cp-boot:<first 12 hex of its SHA-256>`;
  4. replace `runcmd` in the user data by one item, the stub: write the values to `/var/lib/catalyst/boot.env`; block `raw.githubusercontent.com`, `github.com`, `codeload.github.com`, `objects.githubusercontent.com` and `get.k3s.io` in `/etc/hosts`; call `oci_fetch cp-boot <tag>` with the catalogue Git raw address at a pinned commit as fallback; check the file with `sha256sum -c` against the SHA-256 the stub carries; five tries, then the marker `cp-boot-FAILED` and exit 80; restore `/etc/hosts`; read `boot.env` with `set -a`; source the bundle.
  Two lab-only lines point `oci_fetch` at the lab origin through a copy of `variables.env`, because the pack's variables name an origin host that does not resolve. The kit's own variables stay as on main.

Each branch ran `conformance-local` by `workflow_dispatch` on a GitHub runner at the same time, two regions each: run 44315920008 (a), 44315925635 (b), 44315932504 (c). All three passed Up.

On the host, with no cloud and no cluster:

## Measured values

### 1. What stays inline

On the pack (run b, region a), the user data fell from 18,521 to 11,307 bytes and cloud-init's runcmd script from 8,569 to 1,871. Both counts include the lab's timing lines. The bundle is 8,400 bytes. Its SHA-256 `3a7597a8…` was the same in both regions: a region code, address or range is a value, not part of the bundle.

On the worst-case renders of origin/main (no lab lines):

| Surface | User data | runcmd | Inline after | User data after | Saving |
|---|---|---|---|---|---|
| Reference cloud, primary | 28,198 | 15,854 | 3,358 | 15,710 | 12,488 |
| Reference cloud, secondary | 28,664 | 16,324 | 3,323 | 15,671 | 12,993 |
| Second cloud, primary | 27,841 | 12,492 | 1,986 | 17,343 | 10,498 |
| Second cloud, secondary | 29,551 | 14,282 | 2,014 | 17,291 | 12,260 |

"Inline after" is the sum of three parts:

- The stub: 526 bytes. That is the fetch, the check against the pinned SHA-256, five tries, the marker through the module's own mark command, and the two source lines. It was measured with a 12-character tag, a catalogue Git raw address with a 40-character commit and a 64-character SHA-256.
- The values of the installation as a `write_files` entry `/var/lib/catalyst/boot.env`: 1,453 to 1,488 bytes for 16 to 19 values. The largest are the k3s extra arguments (304 on the reference cloud, 450 on the second cloud), the pull token (93), the parent API address (71), the Git URL (68), and the two k3s tokens and the bearer token (64 each).
- On the reference cloud only, the two items of the module that report to the parent and so must run before the fetch: the log sender (807) and the mark helper (537). The second cloud has no such item.

Every other item goes into the bundle, the provider items included: the private NIC setup, the kubeconfig hand-back, the provider id patch.

### 2. What the parent sees when the fetch fails or the checksum differs

| Case | Exit | Marker | Lines in the log (each once per try) |
|---|---|---|---|
| 1 published at the origin, SHA-256 equal | 0 | none | `cp-boot.sh: OK` |
| 2 origin serves another bundle (its layer matches its own digest) | 80 | `cp-boot-FAILED` | 5 x `cp-boot.sh: FAILED`, `sha256sum: WARNING: 1 computed checksum did NOT match` |
| 3 origin layer does not match its manifest digest | 80 | `cp-boot-FAILED` | 5 x `oci_fetch: cp-boot:<tag>: bad layer sha256:<digest>` |
| 4 tag not published (404), catalogue Git serves it | 0 | none | `oci_fetch: cp-boot:<tag> not at the origin (404), fallback true: <address>`, then OK |
| 5 origin unreachable, catalogue Git serves it | 0 | none | `curl: (7) ... Connection refused`, `not at the origin (000)`, then OK |
| 6 origin and catalogue Git unreachable | 80 | `cp-boot-FAILED` | 5 x the two `curl: (7)` lines and `not at the origin (000)` |
| 7 no origin host; catalogue Git answers 404, or serves a changed file | 80 | `cp-boot-FAILED` | 5 x `not at the origin ()` and `curl: (22) ... 404`, or 5 x `FAILED` and the `sha256sum` warning |

What reaches the parent:

- On the reference cloud the module's mark command writes the marker, prints `CLOUDINIT-SENTINEL: cp-boot-FAILED`, and sends `/var/log/cloud-init-output.log` to the parent's `cloudinit-log` endpoint (`infra/providers/huawei/main.tf`, the `mark` helper). The log sender item keeps sending the log every 30 s.
- On the second cloud the mark command is `touch`: the marker is written and nothing is sent.
- On the pack, `scripts/local-pack.sh` (lines 616 and 617) lists the `*-FAILED` markers and the last 60 lines of the log.

Two gaps in what the parent learns:

- No line names the expected or the received SHA-256.
- No line says which source served the file. Only the `not at the origin` line shows that the fallback was used.

`oci_fetch` treats every answer but 200 as a reason to fall back, a 404 for an unpublished tag included. A layer that fails its digest is a failure, never a fallback (case 3).

No workflow or job of the repository publishes anything under the `node-artifacts` path yet. The Harbor project exists (`platform/harbor/chart/values.yaml`, `nodeArtifacts: node-artifacts`), but nothing writes into it. So on every installation today `oci_fetch` falls back. All three runs log `not at the origin (000)` for `k3s-install`, `gateway-api-experimental-install` and `flux-install`.

### 4. Host files, registries.yaml and cilium-values.yaml in the bundle

The template on origin/main writes four host files. Who reads each file:

| File | Rendered bytes, reference / second cloud | Read by | In the bundle |
|---|---|---|---|
| `/etc/sysctl.d/99-catalyst-inotify.conf` | 219 / 219 | `sysctl --system` in runcmd | yes |
| `/etc/sysctl.d/99-catalyst-disable-ipv6.conf` | 220 / none | `sysctl -w` and `sysctl --system` in runcmd | yes |
| `/etc/fail2ban/jail.d/catalyst-sshd.local` | 245 / 245 | `systemctl enable --now fail2ban` in runcmd | yes |
| `/etc/ssh/sshd_config.d/99-catalyst-hardening.conf` | 483 / 483 | sshd, which starts before the final stage that runs runcmd | no |
| `/etc/rancher/k3s/registries.yaml` (packed) | 663 / 471 | k3s at its first start, inside the bundle | the fixed part |

- The SSH hardening file stays inline. In the bundle, sshd would run with the image's defaults from boot until the bundle reloads it.
- `registries.yaml`: the mirror and rewrite rules are fixed per cloud and can travel. The mirror endpoint addresses of the reference cloud and the registry credential of the second cloud are values and stay inline.
- `cilium-values.yaml` is 837 bytes plain. Three of its lines are values (cluster name, cluster id, native routing range). The rest is fixed per cloud and can travel.
- Not proven by a boot: run b moved `runcmd` only. The move of these files is follow-up task 5, which must boot on the pack like run b did.

### 5. The two image pre-pull items

- **Platform image pre-pull.** It is 1,976 or 1,977 rendered bytes and carries the pull token inside `runcmd`. On the pack it pulled 0 of 19 images: every pull got 401, because the pack renders no pull token (`V_GHCR_TOKEN=''` in run b's `boot.env`). It ran 27 to 44 s in the background.
- **Run a against run c.** Run a has the pre-pull, which pulled nothing; run c has none. Their kit core was Ready after 874 and 986 s. Two runs doing the same work differ by 112 s, so one run each cannot measure a smaller effect.
- **What the pre-pull could buy when its pulls work.** The 13 pods with platform images were scheduled about 15 minutes after the machines started. They took 8 s median and 44 s at most from scheduling to start in run a (18 s and 88 s in run c). That includes the start itself and waits for other services, so the pull is shorter. The kit pulls these images at that moment anyway.
- **Flux pre-pull** (610 bytes, reference cloud). The pack does not render it, because it stands in the IPv4-only branch. It starts in the item right before the Flux install, which pulls the same Flux images seconds later, so it can save at most those seconds. The database image it adds is pulled by the kit more than ten minutes later.
- **Answer for SOV-149.** Neither pre-pull shortens an installation by a measurable amount. Delete both; no kit object is needed. Only a cloud can still show the pull time of the platform images over that cloud's own network.

### 6. The two ServiceAccount items as one function

- Bytes, reference cloud: today 1,086 (primary), and 1,086 + 1,080 = 2,166 (secondary). As a function `sa <name> <exit code>`: 1,102 (primary, +16), and 1,102 + a call of 24 = 1,126 (secondary, -1,040).
- Behaviour: both forms ran against a fake `kubectl` in three cases: all succeed, the handover-peer apply fails, the parent-bootstrap apply fails. They gave the same files, the same tokens and the same exit codes (0, 0, 98).
- **Defect, on main today.** The variable `T` is not reset between the two items, which run in one shell. When the handover-peer item never gets its token in its 60 tries, `[ "$T" ]` still holds the parent-bootstrap token. The item then writes `handover-peer.kubeconfig` with the parent-bootstrap token and exits 0. In the fake run, `handover-peer.kubeconfig` was byte for byte `parent-bootstrap.kubeconfig`.
- The function form fixes the defect with `T=` at its start (3 bytes).

## Answer

- **How much can move.** All of `runcmd` can become the bundle except the stub (526 bytes), the values (about 1,500 bytes) and, on the reference cloud, the two reporting items (1,344 bytes). That is 10,498 to 12,993 bytes per worst-case surface. The four control-plane surfaces then measure 15,671 to 17,343 bytes. The host files but SSH, and the fixed parts of `registries.yaml` and `cilium-values.yaml`, can follow later (task 5).
- **Booting from a fetched bundle works on the pack.** Both regions booted and the kit came up. The fetch and check took 0.1 s.
- **The bundle must be built from references.** The bundle is the same for every installation of a cloud only if every value is a reference, an empty value too. In run b the pull token was empty, so the text replacement left the empty value in place. The SHA-256 became `3a7597a8…`; offline with a non-empty token it was `26999a35…`. With another deployment id and another non-empty token it stayed `26999a35…`. The follow-up must build the bundle from the template with references, never by searching the rendered text.
- **One bundle per cloud and role.** The primary and secondary renders differ in items (the handover-peer item, the kubeconfig hand-back). So there is one bundle per cloud and role, or the role becomes a value.

## What later tasks must take into account

- SOV-153 writes the packed entries plain again and needs room for that. With task 4, every control-plane surface falls to at most 17,343 bytes.
- With every upstream host blocked for the whole boot, a node still stops inside the bundle. The k3s installer downloads its binary from `github.com`, the Helm installer comes from `raw.githubusercontent.com`, and the Cilium chart from `helm.cilium.io`. Those are further node artifacts, not part of this bundle.
- The bundle runs in the shell of cloud-init's runcmd script. An `exit` in an item ends the whole boot, as it does today; the lab kept that.
- The pack renders no pull token, so nothing on the pack can measure a pull that needs it.

## Question

- Can OpenBao 2.7.2 on the upstream chart 0.30.7 do three things with chart values alone?
  - Read a static seal key from a node directory mounted read-only.
  - Initialise itself.
  - Write a declared audit device.
- Which user and group does the server run as?
- How long does it take to unseal after a restart?
- Do the existing reconciler and a templated policy still work?
- Is there an upgrade path from the release today's bp-openbao runs (Shamir, 1 key of 1) to 2.7.2 and the static seal?
- After migration, can the old key still produce a root token without a token? What is the authenticated call that rotates the recovery keys?
- Does the External Secrets peer push still work?

## Final values (for SEC-162)

The upstream chart is wired with its own values. No `postRenderers` patch is needed.

These keys are added to the `openbao:` block that bp-openbao passes today:

```yaml
server:
  podManagementPolicy: Parallel        # required: see step 4
  extraArgs: -config=/openbao/userconfig/openbao-seal-config/
  extraVolumes:
    - type: configMap
      name: openbao-seal-config        # mounted read-only at /openbao/userconfig/openbao-seal-config
  volumes:
    - name: seal
      hostPath: {path: /var/lib/catalyst/seal, type: Directory}
  volumeMounts:
    - {name: seal, mountPath: /openbao/seal, readOnly: true}
  nodeSelector:
    catalyst.openova.io/role: control-plane
  tolerations:
    - {operator: Exists, effect: NoSchedule}
```

- **Image:** the test set `server.image` to `quay.io/openbao/openbao:2.7.2` because there is no Harbor in CI. With chart 0.30.7, today's registry and repository override needs no tag. The tag defaults to the app version, 2.7.2.
- **Rendered command:** `bao server -config=/tmp/storageconfig.hcl -config=/openbao/userconfig/openbao-seal-config/`. The server loads every `.hcl` file in that directory.

ConfigMap `openbao-seal-config` holds three files:

- **`seal.hcl`**
  - `seal "static" { current_key_id = "<id>", current_key = "file:///openbao/seal/openbao-seal-<id>.key" }`
- **`initialize.hcl`**
  - `initialize "platform"` with four `update` requests, in this order:
    1. `sys/auth/kubernetes` `{type = "kubernetes"}`.
    2. `auth/kubernetes/config` `{kubernetes_host = "https://kubernetes.default.svc"}`.
    3. `sys/policies/acl/openbao-config-admin` `{policy = "<policy text as one JSON-escaped HCL string>"}`.
    4. `auth/kubernetes/role/openbao-config-admin`, bound to service account `openbao-config` in the release namespace. Policy `openbao-config-admin`, `token_ttl 15m`, `token_max_ttl 1h`.
  - The policy text is today's text with three changes:
    - The two read-only lines on its own policy are removed.
    - `sys/mounts/secret` is added with create and update.
    - `sys/mounts/mounted` is added with create and update.
  - The text is in `tests/spikes/SEC-130/config-admin-policy.hcl`.
- **`audit.hcl`**
  - `audit "file" "stdout" { description = "...", options { file_path = "stdout" } }`

The complete rendered ConfigMap and values are printed in the Results step of runs 2 and 3.

### Step 4: upgrade path and seal migration (runs 1, 2 and 3)

- **The server today runs 2.3.1, not 2.1.0.** Chart 0.16.0 defaults to 2.3.1, and bp-openbao sets no tag. Only the init Job's CLI image is 2.1.0. Both starting points were tested.

- **Second attempt works:** with `server.podManagementPolicy: Parallel`, the upgrade succeeds (rc 0).
- **The pod must be deleted:** `updateStrategy` stays `OnDelete`, so the pod rolls only when it is deleted.

  - `POST sys/generate-root-token/attempt`: 403.
  - `GET sys/generate-recovery-token/attempt`: 403.
  - `POST sys/rekey-recovery-key/init`: 404.
  - `POST sys/rekey/init`: 405.
  - `POST sys/rotate/recovery/init`: 403.
  - `POST sys/rotate/root/init`: 403.
  - Result: none of these is a token-free path.
- **One configuration change opens a path (run 3):**
  - The change: a second listener on `127.0.0.1:8210` with `disable_unauthed_generate_root_endpoints = false`, added to the configuration directory, then a pod restart.
  - With it, the old key produced a valid token with policies `["root"]`.
  - This needs write access to the server's configuration.
- **Authenticated rotation:**
  - Token policy: `path "sys/rotate/recovery/*" { capabilities = ["create", "read", "update", "delete"] }`. No `sudo` is needed.
  - Call 1: `POST /v1/sys/rotate/recovery/init` with body `{"secret_shares":1,"secret_threshold":1,"pgp_keys":["<base64 of the binary public key>"]}`. It answers 200 with `data.nonce` and the PGP fingerprint.
  - Call 2: `POST /v1/sys/rotate/recovery/update` with `{"key":"<old key>","nonce":"<nonce>"}`. It answers 200, `complete=true`, with one key in `data.keys_base64`.
  - The returned key decrypts with the PGP private key to a 64-character key.
  - These endpoints answer under `data`.
- **After rotation:**
  - The old key is refused: `recovery key verification failed`.
  - It is also refused on the re-enabled legacy listener: `root generation aborted`.
  - The new key is accepted.

## What follows for the plan

- **SEC-162 uses the recorded values verbatim.** This follows from steps 1 to 3 passing, and it adds three points:
  - `server.podManagementPolicy: Parallel` is mandatory.
  - The pod must be deleted to roll, because of `OnDelete`.
  - The chart's auth-bootstrap generate-root hook must go in the same change. On 2.7.2 its endpoint answers 405.
- **SEC-150:** user and group `100:1000` are confirmed. The 32 raw bytes are read without trimming. Directory mode 0700 and file mode 0400 work.
- **SEC-170 uses the direct jump.** No stepwise path is needed. The sequence:
  1. Upgrade the chart with `podManagementPolicy: Parallel`.
  2. Delete the pod.
  3. Unseal with the old key.
  4. Apply the final values.
  5. Delete the pod.
  6. Run `bao operator unseal -migrate <old key>`.
  - OpenBao stays sealed between steps 5 and 6, so the step 6 command must follow at once.
- **SEC-170 must also handle three gaps on existing clusters:**
  - The self-initialisation block does not run on an initialised store. On existing clusters, `openbao-config-admin` keeps its two read-only lines on its own policy, so a root token must rewrite it once.
  - Existing clusters have no root token. One must be generated before the image jump, while 2.3.1 still accepts the legacy endpoint. The other way is the measured temporary pod-local listener.
  - The rotation call needs a token with the `sys/rotate/recovery/*` grant above.
- **Recovery-key rotation in SEC-170:** the rule's trigger, a token-free root path, is not met in the default configuration. It is met after one listener-option change by someone who can write the server configuration. The rotation closes that path, so SEC-170 should rotate the recovery keys before it deletes the unseal Secret. The call is recorded above.
- **SEC-262 stays where it is,** because step 6 passed.

## Not measured, and what it needs

- **Three raft members per region,** including seal migration and self-initialisation on a three-member cluster. Only one replica was run; today's slot runs one. This needs a kind cluster with three nodes, or a Sovereign.
- **The seal volume:** the real dedicated volume (`/dev/vdb`) and the cloud-init that writes it. Here the seal directory was a path inside the kind node container. This needs SEC-135 and a real node.
- **k3s:** kind (kubeadm) Kubernetes 1.33.1 was used, not k3s.
- **Cilium ClusterMesh:** the peer address was an ExternalName Service inside one cluster.
- **Flux:** the upgrade was run with the helm CLI, not by a Flux HelmRelease. The same StatefulSet error is expected there but was not measured.
- **The bp-openbao umbrella:** the upstream chart was installed directly with the umbrella's `openbao:` values. Today's init Job, auth-bootstrap hook and unseal reconciler were not run.
- **The full policy:** only two of the planned additions to the `openbao-config-admin` policy were exercised: `sys/mounts/secret` and `sys/mounts/mounted`.

## What later tasks must take into account

All six steps passed (outcome PASS) in two consecutive CI runs, 43355209045 and 43356456144. Run 43353940850 was the first attempt. I used 3 of the 5 allowed pushes. Branch spike/SEC-130 is left in place as the evidence.

Later packages must take four things into account:

1. Chart 0.30.7 changes the default podManagementPolicy, and that field cannot be changed on an existing StatefulSet. A helm upgrade from 0.16.0 with today's values fails until server.podManagementPolicy: Parallel is set. The update strategy is OnDelete, so the pod rolls only when deleted.

2. The server image running today is 2.3.1, not 2.1.0. Only the init Job's CLI image is 2.1.0. The direct jump to 2.7.2 works from both, and no stepwise path is needed.

3. On 2.7.2 the unauthenticated generate-root endpoints answer 405. Today's auth-bootstrap hook uses them, so it stops working after the image jump. SEC-162 must remove that hook in the same change. On an initialised store the self-initialisation block is skipped (measured), so existing clusters keep the self-locked openbao-config-admin policy. SEC-170 therefore needs a root token, and the clusters have none: get one before the image jump, or through a temporary pod-local listener with disable_unauthed_generate_root_endpoints = false (measured to work). SEC-170 needs that token to rewrite the policy once and to rotate the recovery keys. The rotation needs no sudo.

4. In the default configuration the old key, now a recovery key, gives no token-free root path. After one listener-option change it does give a root token. The recorded PGP rotation closes that path, so rotating before deleting the unseal Secret is recommended.

Not measurable in this CI job:
- Three raft members per region.
- The real seal volume and its cloud-init.
- k3s instead of kind.
- Cilium ClusterMesh: an ExternalName Service stood in for it.
- Upgrade through a Flux HelmRelease.
- The whole bp-openbao umbrella with its hooks.

Also observed: the declared audit device is the only way to add audit in 2.7.2; creating one through the API is refused even with root. Every first start logs one harmless ERROR line: "failed to unlock initialization lock: cannot find peer".

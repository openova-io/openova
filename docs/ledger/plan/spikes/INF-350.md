# INF-350 result: change events from the reference cloud

- Dates: 2026-11-19, 06:37 to 07:41 UTC (session 1, read-only); 2026-11-24, 05:32 to 06:09 UTC (session 2, the delivery experiment)
- Cloud: the operator-hosted cloud that the reference provider module is written for. Both regions for the gateway probes of session 1; the first region, in the project the test environments are installed in, for everything else.
- **Outcome: yes.** The audit-trail service is deployed and pushes server create, delete, start and stop events to an HTTPS endpoint on a public address, through a key-event notification, a topic of the notification service and an HTTPS subscription. Every event of the experiment arrived, 0.7 to 2.8 s after the trace's own time. Counted from the API call, a create was announced after 3.6 to 5.2 s and a delete after 2.0 to 3.0 s; both well under 60 s.

| Question | Answer |
|---|---|
| Is the audit-trail service deployed? | **yes** |
| Can events be delivered to an endpoint in the Sovereign? | **yes**, to an HTTPS endpoint on a public address or public name (measured on a lab server with a public address; a private address is refused) |
| Delay for one server create | **3.6 to 5.2 s** from the API call to the first event; 14.3 to 15.6 s to the event of the completed create |
| Delay for one server delete | **2.0 to 3.0 s** from the API call to the first event; 22.0 to 23.5 s to the event of the completed delete |

## Question

Can the cloud's audit-trail service push server create, delete, start and stop events to an HTTPS endpoint inside a Sovereign? How long does delivery take for one create and one delete? If delivery takes under 60 seconds, an `InventoryWatcher` package is planned for the reference adapter. Otherwise the six-hour safety interval of the account source stays and is recorded as a known limit.

## What was run

### Session 1, 2026-11-19, 06:37 to 07:41 UTC: read-only

No cloud resource was created and nothing was changed.

1. **Gateway probes with a made-up access key**, in both regions. The gateway resolves the route before it checks the key: `401 APIGW.0301` means the route is published and the key is unknown, `404 APIGW.0101` means the route is not published. 40 requests.
2. **Portal probes.** Unauthenticated `GET /<app>/` on the console host for 6 app names. A hosted app answers `200`; an unknown name answers `302` to the console home.
3. **Signed reads with the account's access key**, first region, with the signing method the provider module uses (`SDK-HMAC-SHA256`, as `products/catalyst/bootstrap/api/internal/providers/huawei/sigv3.go` signs). Only `GET`: trackers, key-event notifications, traced operations, quotas, topics and subscriptions of the notification service, and 7 days of compute traces.
4. **Two read-only polls of the trace list**, 60 minutes in all, one signed `GET` every 4 or 6 seconds.
5. **Reading.** The request models of the cloud's public Go SDK, release `v0.1.223` (`github.com/huaweicloud/huaweicloud-sdk-go-v3`): `services/cts/v3/model/model_create_notification_request_body.go`, `services/cts/v3/model/model_operations.go`, `services/cts/v3/model/model_traces.go` and `services/smn/v2/model/model_add_subscription_request_body.go`.

Controls: the made-up key on the compute list route answered `401 APIGW.0301` in both regions; a made-up path, the compute path on the trace host and a made-up host answered `404 APIGW.0101`; the real key on the compute list route answered `200`. Every host name under a region resolves to that region's gateway through a wildcard record, so DNS alone proves nothing.

### Session 2, 2026-11-24: the delivery experiment

Run in a lab of its own in the project, every resource named `nslab-inf-350-*`. Nothing was created in the network of the standing test environment. No cluster object was written; the only cluster reads were two on the parent: the list of variables documents, and the account's document (below).

- **The account.** The access key, project and region came from the standing test environment's variables document, read once from the parent's provisioning service into memory on the agents' host and removed at the end. Every cloud call was signed with `SDK-HMAC-SHA256`. The canonical path escapes `:` (`%3A`), which matters for paths that carry a topic URN.
- **Lab network.** One VPC, one subnet, one security group: TCP 80 and 443 open to any address (the sender's address is not known in advance), TCP 22 from the agents' host only. One key pair.
- **Receiver.** One server of the smallest flavour (1 vCPU, 1 GiB, Ubuntu 22.04) with a public address billed by traffic. A small Go HTTP server on it, written for this test, logged the arrival time, headers and body of every request; served HTTP on port 80 and HTTPS on port 443 with a self-signed certificate made at start for no name; and answered a subscription-confirmation message by fetching its `subscribe_url`.
- **Clocks.** The agents' host is NTP-synchronised. The receiver server was not (`NTPSynchronized=no`). Its offset was measured 8 times by a time request over its public address: −934 to −936 ms at round trips of 5 to 47 ms, and once −433 ms at a round trip of 1,010 ms, which was discarded. Arrival times are corrected by the mean of the 7 others, −935 ms.
- **In the cloud.**
  1. One topic.
  2. Two subscriptions to the receiver's public address: protocol `https` and protocol `http`.
  3. Three control messages published to the topic.
  4. One key-event notification, `operation_type` `customized`, no `agency_name`, to the topic. It first asked for service `ECS`, resource type `ecs`, trace names `createServer`, `deleteServer`, `startServer` and `stopServer`. Before the cycles, the resource type `server` with `createServer` and `deleteServer` was added: the receiver's own create had shown that the trace written at the API call carries the resource type `server` (traced operations of the compute service: `server` lists `createServer` and `deleteServer`; `ecs` lists all four).
  5. Three cycles on one test server each (smallest flavour, the lab subnet, no public address): create, soft stop, start, delete with its volume. After each operation the run waited until every expected push had arrived and every expected trace was in the trace list.
- **Trace list.** A watcher on the agents' host read the compute traces of the project every 5 s (signed `GET /v3/{project}/traces`), 350 reads from 05:40:15 to 06:09:22 UTC, all `200`.
- **Times.** t0: the API call returns, on the agents' host. t1: the trace's own `time`, on the cloud's clock. t2: the push arrives at the receiver, corrected to the agents' clock. t3: the first read of the trace list that returns the trace, on the agents' host. The end of each job was read every 3 s.
- **Four short tests after the cycles.** A: the receiver's resolvers set to public ones, a third subscription, confirmed by the receiver alone. B: a subscription to a private address of the lab subnet. C: the receiver stopped, one message published, the receiver started again 61 s later, then watched for 5 minutes. C2: a fourth subscription whose endpoint confirms normally and answers `500` to every event, one message published, every attempt logged until its subscription was deleted, 592 s later.

### Push delivery works

- **No agency and no topic policy were needed.** The notification was created without `agency_name`. The topic's access policy stayed empty (`GET .../attributes?name=access_policy` answered `""`), and every event arrived.
- **Subscription.** The confirmation message reached both endpoints within 1 s of each subscribe call. A subscription stays at status `0` and delivers nothing until its `subscribe_url` is opened once. The URL is on the cloud's console host, valid 48 hours, and a plain `GET` without sign-in answers `200` and sets status `1`.
  - In the cycles the receiver could not open it itself: the lab subnet had been given the cloud's internal resolver addresses, which answered no lookup at all, and the link was opened from the agents' host, one `GET` per subscription.
  - Test A: with public resolvers on the receiver (the resolvers the standing test environment's subnets use), the receiver confirmed a new subscription by itself; status `1` 2 s after the subscribe call.
- **Certificate.** Over HTTPS the sender accepted a self-signed certificate made for no name, on a bare address. It does not check the endpoint's certificate, so a Sovereign's valid wildcard certificate is accepted as well.
- **Private address.** Test B: a subscription to `https://` on a private address of the lab subnet was refused: `400`, `SMN.0069`, "Not authorized to subscribe internal endpoints."
- **Completeness.** Each cycle wrote 6 traces of its test server (create 2, stop 1, start 1, delete 2). All 18 were pushed once to each of the two subscriptions. Servers that another lab test created and deleted in the same project during the run were pushed as well: the notification covers the whole project, whoever makes the call.
- **Sender.** Every message, 85 in all, came from one public address of the cloud, with `User-Agent: SMN` and the headers `X-Smn-Message-Id`, `X-Smn-Message-Type` and `X-Smn-Topic-Urn`.
- **Format.** The body is JSON with `type` (`SubscriptionConfirmation` or `Notification`), `message`, `message_id`, `signature`, `signature_version` (`v1`), `signing_cert_url` (on the notification service's own host), `subject`, `subscribe_url` (confirmation only), `timestamp` and `topic_urn`. An event's `subject` is "CTS - A Trace Generated for a Performed Operation". Its `message` is the whole trace as JSON: `trace_id`, `trace_name`, `trace_type`, `trace_rating`, `service_type`, `resource_type`, `resource_id`, `resource_name`, `time`, `record_time`, `code`, `user` (domain, id, name), `source_ip`, `request`, `response` and a few more. Secrets in the request are masked (`********` or `<SANITIZED>`).

### Delays

Three cycles, min to max, in seconds. "After the call" counts from t0, "after the trace" from t1.

| Operation | Trace (resource type) | Job end after the call | Trace time after the call | Push after the call | Push after the trace | In the list after the call | In the list after the trace |
|---|---|---|---|---|---|---|---|
| create | `server`, at the call | 20.8 to 22.6 | 2.2 to 2.4 | **3.6 to 5.2** | 1.4 to 2.8 | 3.2 to 6.7 | 0.7 to 4.6 |
| create | `ecs`, at completion | 20.8 to 22.6 | 13.1 to 13.5 | 14.3 to 15.6 | 0.9 to 2.5 | 16.3 to 18.2 | 2.9 to 4.6 |
| delete | `server`, at the call | 32.3 to 33.5 | 0.6 to 0.7 | **2.0 to 3.0** | 1.4 to 2.3 | 2.1 to 5.5 | 1.4 to 4.9 |
| delete | `ecs`, at completion | 32.3 to 33.5 | 21.1 to 21.3 | 22.0 to 23.5 | 0.8 to 2.3 | 22.1 to 25.5 | 0.8 to 4.4 |
| stop (soft) | `ecs`, at completion | 51.1 to 52.4 | 46.9 to 47.0 | 47.6 to 49.3 | 0.7 to 2.4 | 50.3 to 50.7 | 3.3 to 3.8 |
| start | `ecs`, at completion | 20.6 to 22.2 | 6.0 to 16.5 | 7.9 to 18.9 | 1.7 to 2.4 | 10.1 to 19.0 | 1.7 to 4.1 |

- The push follows the trace by 0.7 to 2.8 s in all 18 cases. What the delay after the call adds is the operation's own run time: a stop is announced when the server has stopped, about 47 s after the call.
- The `http` subscription received each event within 1 s of the `https` one.
- Control messages published straight to the topic arrived 0.9 to 2.1 s after the publish call returned.
- Job end is the first 3-second read of the job that showed `SUCCESS`, so it is up to 3 s late.
- A trace was in the trace list 0.7 to 4.9 s after its own time, read every 5 s. So the list works as a pull feed as well, with a visibility delay of a few seconds.
- `record_time` equals `time` in every trace and every message, as in session 1. A trace's lateness can only be measured against a clock of our own.
- The trace time and the agents' clock are different clocks. The create trace at the call is 2.2 to 2.4 s after the call returned on the agents' clock, the delete trace 0.6 to 0.7 s. Whether that is skew or the moment the cloud records the call was not separated.

### Delivery rules

- **Endpoint down.** Test C: the receiver stopped (both ports closed), one message published at 05:49:05 UTC, the receiver started again 61 s later. Nothing arrived in the 5 minutes watched after that. The final copy of the log shows the message did arrive later, on both subscriptions, at 06:00:01 UTC: 655 s after the publish, about 10 minutes after the receiver was back.
- **Endpoint answers an error.** Test C2: a fourth subscription, `https` `/smn-fail`, whose endpoint confirms normally and answers `500` to every event. One message published at 05:55:32 UTC. Attempts, counted from the publish call returning: 1.7 s, 28.6 s, then 268.6 s, 269.6 s and 270.6 s (06:00:00 to 06:00:03 UTC). No further attempt until the subscription was deleted at 06:09:24 UTC, 592 s after the publish. Two events that the other lab's server deletes caused during C2 (traces at 06:05:00 and 06:05:09 UTC) were each tried three times on the failing endpoint, about 1 s apart, 1.8 to 4.6 s after the trace, and not again in the 4 minutes until the subscription was deleted; the two working subscriptions got them once each.
- **So the sender retries**, though not in the same pattern for every message. The published message of C2 was retried 27 s after its first attempt and then in a retry pass; each of the two events was tried three times within 3 s and not again in the next 4 minutes. The one pass observed ran at 06:00:00 UTC and carried both pending published messages: the one of test C was delivered on its first try there, the one of test C2 was tried three times in 3 s. Not measured: how often the passes run and after how many attempts or how long the sender gives up. Test C's message was pending with its receiver up from 05:50:07 and arrived only at 06:00:01, so no pass reached it in those 10 minutes.
- **Duplicates.** The http and https subscriptions each received every event once. A message tried three times in one pass shows that an endpoint which answers late or with an error may receive the same message more than once; the receiver must be idempotent by `message_id`.

- Not published on this cloud: the event router (`eg`: sources, channels, subscriptions, all `404 APIGW.0101` in both regions, no console app) and the function service (`functiongraph`: `404`, no console app). The only push path is key-event notification, then topic, then a subscription.

## What follows

1. The decision rule is met: delivery is under 60 s for both create and delete. So the architect plans one package that implements `InventoryWatcher` in the reference adapter: it subscribes a public route of the Sovereign to the account's compute lifecycle traces and re-reads the resource each message names. No package of the plan builds it yet.
2. Until that package has merged, the six-hour safety interval of the account source stays. After it, the interval stays as the backstop for a message that never arrives: the sender retries, but when it gives up was not measured (see "Delivery rules").

## What later tasks must take into account

- **INF-320** keeps the six-hour enumeration of the account source, and its entry in the allow-list of `scripts/check-no-new-polling.py`, until the `InventoryWatcher` package has merged. After that the enumeration stays as the backstop for a message that never arrives (a message the endpoint could not take came again up to 11 minutes later, and when the sender gives up was not measured, see "Delivery rules"), at an interval that package states.
- **Late and repeated messages.** A message may arrive minutes after the change, and more than once. The receiver must be idempotent by `message_id` and must not order changes by arrival: re-reading the resource the message names gives the current state.
- **The endpoint.** It must be on a public address or a public name: the notification service refused a private address. In a Sovereign it is one route on the existing public gateway with the existing certificate; no new load balancer and no NodePort.
- **Authenticity is the receiver's job.** The sender does not check the endpoint's certificate, and anyone can post to a public route. Every message carries `signature`, `signature_version` `v1` and `signing_cert_url`; the receiver must verify the signature and drop a message that fails. The verification itself was not measured here.
- **Confirmation.** A subscription delivers nothing until its `subscribe_url` is opened once. The receiver can do that itself when it can resolve and reach the cloud's console host: give it that egress, once per subscription.
- **Setting it up writes to the cloud.** The topic, the subscription and the key-event notification are created with the account's credential: `POST` and `PUT` calls on the notification service and the trace service. An inventory reader that sends only `GET` cannot set them up. The watcher package must name who creates them, with which rights, and who deletes them when the account goes.
- **Filter.** Ask for both resource types of the compute service: `server` (create and delete, at the call) and `ecs` (create, delete, start and stop, at completion). Treat a message as a hint to re-read the resource: a create is announced before the server exists in full.
- **Scope.** A notification covers the whole project, whoever makes the call: a server created by another lab during the run was pushed too. The quota is 100 notifications per project.
- **What a message carries.** The full trace: the caller's name and ids, the source address, and the request and response bodies with secrets masked. The inventory should keep only what it needs.
- **Signing paths with a topic URN.** The gateway escapes `:` in the canonical path (`%3A`). `canonicalURI` in `products/catalyst/bootstrap/api/internal/providers/huawei/sigv3.go` (lines 184 to 193) uses Go's escaped path, which keeps `:`. A call whose path holds a topic URN (subscriptions, publish, topic attributes) is then refused with `401 APIGW.0301` ("verify aksk signature fail"); the lab's signer failed exactly so until it escaped each path segment to the unreserved characters. The watcher package must fix this before it manages subscriptions.
- **A reader of the trace list instead of a push** is a polling loop. It needs its own entry in the allow-list of `scripts/check-no-new-polling.py`, and it must stay under the gateway's rate limit (the sixth back-to-back read answered `429`).
- **Do not plan on the event router or the function service** of the public cloud: neither is published on this cloud.

## Question

Can the cloud's audit-trail service push server create, delete, start and stop events to an HTTPS endpoint inside a Sovereign? How long does delivery take for one create and one delete? If delivery takes under 60 seconds, an `InventoryWatcher` package is planned for the reference adapter. Otherwise the six-hour safety interval of the account source stays and is recorded as a known limit.

## What was run

Read-only requests only. No cloud resource was created and nothing was changed. No cluster object was written. The only cluster read was the account's access key, from its Secret on the parent cluster.

1. **Gateway probes with a made-up access key**, in both regions. The gateway resolves the route before it checks the key. `401 APIGW.0301` means the route is published and the key is unknown. `404 APIGW.0101` means the route is not published. A made-up key cannot create or change anything. 40 requests (18 signed with the made-up key and 2 unsigned, per region).
2. **Portal probes.** Unauthenticated GET of `/<app>/` on the console host for 6 app names. A hosted app answers `200`; an unknown name answers `302` to the console home.
3. **Signed reads with the account's access key**, first region only, with the signing method the provider module uses. Only GET: the tracker list, the key-event notification lists, the list of traced operations, the quotas, the notification service's topic and subscription lists, and the trace list for the compute service over the last 7 days.
4. **Two read-only polls of the trace list, 60 minutes in all.** One signed GET every 4 seconds (poll 1) or 6 seconds (poll 2), alternating between the compute service and all services. For each trace that appeared after the first poll, its visibility delay lies between the previous poll of that query and the poll that first returned it, measured against the trace's own `time` field.
5. **Reading.** The request models of the cloud's public Go SDK, release `v0.1.223` (`github.com/huaweicloud/huaweicloud-sdk-go-v3`): `services/cts/v3/model/model_create_notification_request_body.go`, `services/cts/v3/model/model_traces.go` and `services/smn/v2/model/model_add_subscription_request_body.go`.

Controls, in the same runs:

- Made-up key on the compute list route: `401 APIGW.0301` in both regions. Unsigned: the same.
- A made-up path on the trace host, the compute path on the trace host, and a made-up host: `404 APIGW.0101` in both regions. So the gateway routes by host and path together, and a `401` on a trace route is that route's own answer.
- The real key on the compute list route: `200`. So the key and the signature work.
- Every host name under a region resolves to that region's gateway through a wildcard record. DNS alone proves nothing.

### The push path exists by design; it was not exercised

- A key-event notification (`POST /v3/{project}/notifications`) sends to a topic of the notification service (`topic_id`). Its `operation_type` is `complete` or `customized`; a customized one lists service, resource type and trace names. Its optional `agency_name` takes the single value `cts_admin_trust`. (SDK model, release `v0.1.223`.)
- The notification service's topic and subscription routes are published in both regions (`401` with the made-up key) and answer `200` with the real key: 0 topics and 0 subscriptions in the project.
- A subscription with protocol `https` needs an endpoint on a public IPv4 or IPv6 address or a public domain name. Private addresses are refused. (SDK model, release `v0.1.223`.) So an endpoint "inside the Sovereign" must be published through the Sovereign's public gateway.
- Not published on this cloud: the event router (`eg`: sources, channels, subscriptions, all `404 APIGW.0101` in both regions, no console app) and the function service (`functiongraph`: `404`, no console app). The notification type `fun` therefore has no target here. The only push path is key-event notification, then topic, then an HTTPS subscription.
- Open by design: on the public cloud the notification may need the agency `cts_admin_trust`. On this cloud the tenant's identity routes, agencies included, are not published (SOV-070). Whether the trace service creates its agency itself is seen only by trying.

### Record times carry no delay

`record_time` equals `time` in every trace read: 1,000 compute traces, and all 187 lifecycle traces above. The cloud's record time therefore says nothing about how late a trace is recorded. A delay can only be measured from outside, against a clock of our own.

Only an operation of our own, at a known time, measures the delay.

### Gateway rate limit

Six signed trace-list reads sent back to back gave `429` on the sixth. A reader of the trace list must pace itself.

## What follows

1. The service is deployed and records server creates and deletes. Push delivery to a Sovereign is possible by design, through a key-event notification, a topic and an HTTPS subscription to a public name of the Sovereign. Whether it works on this cloud, and how fast, is still not measured.
2. The decision of this spike is therefore still open: no `InventoryWatcher` package is planned yet, and the six-hour safety interval stays until the experiment below has run.
3. The trace list works as a change feed for a reader that pulls: it lists server lifecycle traces by service, resource type and trace name. How late a trace appears in it is not measured either. The experiment below measures that as well.

## Still to run

The delivery experiment needs cloud resources and a change to a Sovereign, so it runs in the nightly maintenance window, by the architect's schedule.

- **Where.** The project and first region of the standing test environment; the endpoint in that environment's first region.
- **Created, in order.**
  1. In the Sovereign: one namespace with one receiver Deployment (one replica, a small HTTP server that logs each request's arrival time, headers and body, and answers a subscription-confirmation message by fetching its subscribe URL), its Service and one HTTPRoute on the existing gateway at a public name under the Sovereign's domain, with the existing wildcard certificate. No NodePort, no new load balancer.
  2. In the cloud: one topic of the notification service; one subscription with protocol `https` to the receiver's public URL, confirmed by the receiver.
  3. One key-event notification, `operation_type` `customized`, service `ECS`, resource type `ecs`, trace names `createServer`, `deleteServer`, `startServer`, `stopServer`, to that topic.
  4. One test server of the smallest flavour, in the environment's existing network, with no public address: create, stop, start, delete. Repeat three times.
- **Measured.** For each operation: t0, when the API call returns, on the runner's clock; t1, the trace's `time`; t2, when the receiver logs the message, on the cluster's clock. Both clocks are checked against the same NTP source first. t3, when the trace first appears in the trace list, read every 5 seconds. Delay of a push = t2 − t0; delay of a pull = t3 − t0. Also: the subscription's confirmation status, the message format, and whether the notification needed `agency_name`.
- **Duration.** About 45 minutes, of which the server runs about 30.
- **Removed at the end, checked by listing:** the notification, the subscription, the topic, the test server with its volume and port, and the namespace with the route. Nothing stays behind.
- **Decides.** Delivery under 60 seconds for both create and delete: an `InventoryWatcher` package for the reference adapter. No delivery, or slower: the six-hour interval stays and is recorded as a known limit of the account source.

## What later tasks must take into account

- INF-320 keeps the six-hour enumeration of the account source in the allow-list of the polling guard until this experiment has run.
- A design that reads the trace list instead of receiving a push is a polling loop: it needs its own entry in the allow-list of `scripts/check-no-new-polling.py`, and it must stay under the gateway's rate limit.
- Do not plan on the event router or the function service of the public cloud: neither is published here.

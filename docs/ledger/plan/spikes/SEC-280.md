Chosen variant: **unmanaged management role**. It is defined in "What follows". Step 1 also has a three-minute window for new connections. One setting removes it.

## The question

Can OpenBao issue dynamic database users and rotate static roles on a two-region CloudNativePG pair while the operator manages roles itself? Does that still work across a region switch and an OpenBao outage? The plan asked five questions:

1. Do issued users still work after a switch, and which region can issue?
2. Does the operator revert or interfere with roles OpenBao creates?
3. Does the operator leave a static role's password alone when the role has no `passwordSecret`? Does a pod reading `db/static-creds` through CSI see the new value?
4. What does the server do when a lease expires while connections are open?
5. What does a 30-minute OpenBao outage do to a connection pool?

## What was run

Everything ran in GitHub Actions in openova-io/openova, on branch `spike/SEC-280`. The branch is never merged.

- **Files.** Workflow `.github/workflows/spike-sec-280.yaml`. Driver `tests/spikes/SEC-280/lab.py`. Pool probe `tests/spikes/SEC-280/consumer` (Go).
- **Cluster.** Runner `ubuntu-24.04`. kind v0.30.0 with Kubernetes v1.34.0, one node.
- **Database.** CloudNativePG operator 1.29.0, from chart `cloudnative-pg` 0.28.0, the version the platform pins. PostgreSQL 16.4, image `ghcr.io/cloudnative-pg/postgresql:16.4`, as the platform uses.
- **OpenBao.** OpenBao 2.7.2 from chart `openbao` 0.30.7. Standalone, pebbledb storage, Shamir 1-of-1 unseal. The CSI provider 2.0.3 comes from the same chart.
- **CSI driver.** Secrets Store CSI driver 1.6.2, Secret sync off, rotation on. Poll every 30 s, or 300 s in the token job.
- **Two regions.** Two namespaces of one kind cluster: `acme-a` holds Cluster `pg-a`, `acme-b` holds Cluster `pg-b`. They form a distributed-topology pair (`replica.self/primary/source`) with TLS streaming. Each region has its own OpenBao (`bao-a`, `bao-b`).
- **The switch.** A planned switchover: set `replica.primary` on the primary to demote it, then promote the other cluster with the demotion token.
- **Roles and data.** Group roles `appdb_rw` and `appdb_ro`. Management role `openbao_dbadmin` (CREATEROLE, member of both groups). Static role `app_static` with no `passwordSecret`. Control role `app_static_ctl` with a `passwordSecret`. Table `t`, owned by `appdb_rw`.
- **OpenBao configuration.** Mount `db/`. One connection per cluster: `sslmode=require`, scram-sha-256, `allowed_roles=acme.*`. Dynamic roles: 1 h default, 24 h maximum, 90 s for the expiry tests. Static role: 720 h. The creation and revocation statements are the specified ones. Kubernetes auth role `workload`: token 15 min, audience `openbao`.
- **Jobs.**
  - Steps 1–4 on the two-region pair.
  - Switch window: a baseline and two remedies.
  - Token lifetime: token renewal, and a CSI mount of dynamic credentials.
  - Step 5: OpenBao stopped for 30 minutes under four connection pools.

## Measured values

### Setup (runs 1–4)

- The pair became healthy in 20–31 s for A and 25–31 s for B.
- `openbao_dbadmin` has `rolsuper` false.
- `managed.roles` has no field for the ADMIN OPTION. Issuing a user failed: "permission denied to grant role appdb_rw". It needed an extra superuser `GRANT appdb_rw, appdb_ro TO openbao_dbadmin WITH ADMIN OPTION`.
- With the operator's grant (INHERIT true), the management role can read table `t`.
- PostgreSQL 16 gives the creator of a role a membership in it with ADMIN only: INHERIT false, SET false, grantor `postgres`.

### Step 2: FAIL as specified (runs 1–4)

- **Revocation fails at once.** Revoking a fresh user with the specified statements failed before the operator did anything: "permission denied to reassign objects". `REASSIGN OWNED` needs the privileges of the dynamic user, and the creator membership has no INHERIT. The lease and the user both stayed.
- **The operator removes the management role's memberships.** On its next reconcile, the operator removed the membership of `openbao_dbadmin` in every dynamic user (3 of 3 rows in each run). The trigger was any change to `managed.roles`. The cause: the operator revokes any membership of a managed role that is not in its `inRoles`.
- **The dynamic users themselves are untouched.** Their attributes, password hash and validity did not change. Logins still worked. The operator lists them as `not-managed`. From then on OpenBao can never drop them.
- **Variant B.** The management role is taken out of `managed.roles` and set up by SQL with `createrole_self_grant = 'set, inherit'` and admin grants. The reconcile then removed nothing, and revocation dropped the user. PASS. But the management role can read data.
- **Variant C (chosen).** The management role is also outside `managed.roles`.
  - It holds only the ADMIN OPTION (INHERIT false, SET false) on the group roles and on each static role.
  - `createrole_self_grant` is not set.
  - The creation statement adds `ALTER ROLE "{{name}}" SET role TO 'appdb_rw'`.
  - Revocation is `DROP ROLE IF EXISTS` only.

  The results: the management role cannot read `t` ("permission denied"), also while a dynamic user exists. Objects that users create belong to `appdb_rw`. A reconcile changed nothing. Revocation dropped the user. PASS.
- **Limit of variant C.** A user that runs `SET ROLE NONE` and then creates an object cannot be dropped ("cannot be dropped because some objects depend on it"). Its lease stays.
- **Under variant C the specified statement fails.** The specified `REASSIGN … TO appdb_rw` fails ("permission denied to reassign objects"). So "no read on data" and the specified revocation statements cannot both hold.

### Step 3: FAIL as specified (runs 1–4)

- **OpenBao cannot set the password.** A role with no `passwordSecret` starts with no password. OpenBao could not set one: "permission denied to alter role". PostgreSQL 16 requires the ADMIN OPTION on the role, and `managed.roles` cannot declare it.
- **The extra grant is removed.** With an extra `GRANT app_static TO openbao_dbadmin WITH ADMIN OPTION, INHERIT FALSE, SET FALSE`, OpenBao created and rotated the role, and logins worked. The operator's next reconcile revoked that grant. The next rotation failed. FAIL.
- **Variant with the management role kept in `managed.roles`.** Its `inRoles` lists `app_static`, and the ADMIN OPTION is added on top by SQL. The operator kept the grant (admin true, inherit false) through reconciles, and two rotations worked. This variant works for static roles. Dynamic users still fail as in step 2.
- **The operator leaves the password alone (variants B and C).**
  - The hash was unchanged after a reconcile.
  - It was unchanged after an instance restart, which took 184–188 s.
  - It was unchanged after the other region's operator became primary: A's password still logged in on B.
- **Control role.** OpenBao rotated `app_static_ctl`, which has a `passwordSecret`. A metadata-only touch of that Secret made the operator reset the password to the Secret's value. OpenBao's password then failed. So the role must have no `passwordSecret`.
- **CSI.** A pod reading `db/static-creds` saw OpenBao's password. After a rotation the mounted file changed in 70, 65, 74 and 90 s (runs 1–4, poll every 30 s). A login with the mounted files worked.
- **Across a switch.** Each region's OpenBao keeps its own static role.
  - Region B could not create its static role while B was a standby ("cannot execute ALTER ROLE in a read-only transaction").
  - After the switch, region A could not rotate.
  - When B created its static role after the switch, B set a new password, and A's copy failed ("password authentication failed").

### Step 1: PASS (runs 1–4; switch-window job, runs 3–4)

- **Issued users survive a switch.** A user issued by A wrote on B after the switch. Earlier users also logged in. Users replicate with the database.
- **Only the primary region can issue.** B, as a standby, failed with "cannot execute CREATE ROLE in a read-only transaction". After the switch, A failed the same way and B issued.
- **The standby's configuration is accepted.** B's connection configuration was accepted while B was a standby, because the check passes on a hot standby. The standby fails only when it issues, not when it is configured.
- **Old leases are stuck until the region is primary again.**
  - Renewing or revoking A's lease through A failed while A was a standby.
  - After the switch back, the revoke worked.
  - B's users could not be revoked by B after the switch back. They stayed in the database with working logins.
- **A lease that expires during a switch.** OpenBao retried revocation at growing intervals, about 12, 50 and 70 s. In runs 3 and 4 the fourth attempt fell after A was primary again and succeeded. In run 2 it fell inside the switch back and failed.
- **Switch timing.**
  - The demotion token appeared at 5–6 s.
  - Existing connections took writes on the new primary from about 7–9 s.
  - New connections were refused ("the database system is shutting down") from 9–10 s until 190–195 s.

  The instance logs show why. After promotion the instance restarts because `archive_mode` changed. Its smart shutdown waits for client sessions, and the only one on the standby was OpenBao's idle connection (`openbao_dbadmin`, 1 session). The fast shutdown came after 180 s.
- **Remedy 1.** With OpenBao `max_connection_lifetime=5s` there was no session on the standby. New connections were writable from 7 s, and the new primary was ready at 11 s (runs 3 and 4).
- **Remedy 2.** With CloudNativePG `smartShutdownTimeout: 15`, new connections were refused only from 10 s to 23 s. The new primary was ready at 26–27 s.

### Step 4: FAIL as specified (runs 1–4)

- **As specified, revocation fails** with "permission denied to reassign objects" (see step 2).
- **On time with variant B.** The server dropped the user 90–95 s after issue, for a 90 s lease.
- **An open session is not ended.** It kept running, and `psql` exited 0 at the end. But it lost every privilege it had through the group role: after 18 good ticks, 52 statements failed with "permission denied for table t".
- **New logins** failed with "password authentication failed".
- **A user that created a table in the application database is never dropped.** Revocation runs in the connection's database (`postgres`), so `REASSIGN` cannot reach `appdb`. The drop fails ("cannot be dropped because some objects depend on it"), the expired lease stays, and OpenBao retries.
- **The `SET role` creation variant.** The table belonged to `appdb_rw`, and the user was dropped at 92–95 s.
- **The terminate variant (runs 2–4).** Revocation first runs `pg_terminate_backend` for the user. The session ended at revocation ("terminating connection due to administrator command"), and `psql` exited 2.

### The login token limits the dynamic user (runs 2–4)

- A dynamic lease ends when the login token that read it ends. It does not matter that the lease is longer. With a 1 h lease and a 2 min token, the user was dropped 123 s after the read. The OpenBao log shows the token's lease revoked, then the `db/creds` lease.
- Renewing the token every 60 s kept the user for 5 min. After the renewals stopped, the user was dropped 124 s later (run 4).
- A CSI mount of `db/creds` with a 2 min token and a 300 s poll (run 4):
  - the login worked from 0 s;
  - logins were refused from 122 s;
  - a new user worked from 355 s.

### Step 5: FAIL as specified (runs 1–4)

**The probe.** A Go `database/sql` pool on lib/pq: 16 open, 4 idle, 30-minute lifetime, as in the chargeback store.

- It logs in with the `workload` token (15 min) on every fetch.
- It fetches new credentials at half the lease.
- It refuses credentials with less than 1 minute left.
- Load: 4 workers each send 1 query per second, plus one pinned connection.

**Run 1.** The outage started 2 minutes after the pools did.

- *1 h pool.* No errors during the 30-minute outage, because OpenBao revoked nothing while it was down. At restart, OpenBao at once revoked the 1 h lease together with its expired 15-minute token. The pooled connections then failed for 7.8 minutes: 1,890 errors, "permission denied for table t" and "invalid role OID". This lasted until they reached their 30-minute lifetime.
- *15-minute pool.* It refused new connections from 28.0 to 30.4 minutes after the stop: 143 errors, "no credentials valid for one more minute".

**Runs 2 and 3.** 20 minutes of normal operation, then the outage.

- All three pools broke at minute 15.2, while OpenBao was still running: the first login tokens expired and took the users with them.
- Not one query succeeded during the 30.4-minute outage.
- The pools recovered at minute 50.8–51.0, after OpenBao came back.
- Query errors in total:
  - 1 h pool: 4,634 and 4,637.
  - 15-minute pool: 4,757 and 4,760.
  - 1 h pool whose revocation also ends sessions: 4,619 and 4,622. That consumer kept using the dropped user ("password authentication failed").

**Run 4, fixed consumer.** It refreshes at half of the shorter of the lease and the token. It fetches again when a login is refused. Its revocation ends sessions.

- 0 query errors in 20 minutes of normal operation.
- 0 query errors in the 30.5-minute outage, with 7,320 queries answered.
- 0 query errors afterwards.
- Only the pinned connection failed, once at each revocation (minute 15.3 and minute 50.5, "driver: bad connection"), and reconnected.

In the same run the three unfixed pools failed again from minute 15.2 to 50.5, with 4,613–4,746 errors each.

## What follows for the plan

**1. Database engine package (SEC-290).** Set the management role up outside `managed.roles`, with a bootstrap SQL or a superuser Job, as the chosen variant:

- ADMIN OPTION only (INHERIT false, SET false) on `<database>_rw`, `<database>_ro` and each static role;
- no `createrole_self_grant`;
- the creation statement adds `ALTER ROLE "{{name}}" SET role TO '<database>_rw'`;
- the revocation statements end the user's sessions and then run `DROP ROLE IF EXISTS`. Leave out `REASSIGN OWNED` and `DROP OWNED`.

Static-role users stay in `managed.roles` with no `passwordSecret`. The management role's password needs a delivery outside the operator.

**2. The session-ending statement under the chosen variant.** Variant C was measured with `DROP ROLE` only. Ending sessions was measured under variant B. Under variant C the management role may need `pg_signal_backend` to end another role's sessions. That combination was not measured and needs one check.

**3. Check SEC-G13.** `rolsuper` false is not enough: it was false in every failing configuration. Assert that the management role cannot read a table of the application database.

**4. Consumers of dynamic users (SEC-300 and the credentials package).**

- Refresh at half of the shorter of the lease and the login token, or renew the token.
- Fetch again when a login is refused.
- Otherwise the 15-minute `workload` token cuts every 1 h user at minute 15.
- The other option is to keep `default_ttl` no longer than the token's lifetime.
- The planned CSI mount of `db/creds` with a 3600 s poll and a 15-minute token leaves the user dead for most of each hour. This follows from the measured mechanism. That exact pair was not run.

**5. Switchover.** Set OpenBao `max_connection_lifetime` (5 s measured) on each region's connection, or lower `smartShutdownTimeout`. Otherwise every promotion refuses new connections for about 3 minutes.

**6. Leases across a switch.** Leases issued by the old primary region cannot be renewed or revoked until that region is primary again. Users issued by the new primary are orphaned after a switch back. The plan needs an owner for those leftover users.

**7. Static roles across regions.** One OpenBao must own each static role at a time. After a switch the new primary region must take the role over, and pods must read that region's OpenBao. A second OpenBao that sets the password invalidates the first one's copy.

**8. Step 1 decision.** Users stay usable after a switch. The 15-minute fallback in the plan is not needed for that reason. The token finding in point 4 stands on its own.

**9. Ownership in the application database.** Objects created in the application database must not belong to dynamic users. The revocation statements run in the connection's database and cannot reach them.

## What later tasks must take into account

Not measured in CI, and why:
- The two "regions" were two namespaces of one single-node kind cluster, so one CloudNativePG operator managed both Clusters. There was no mesh, no cross-region latency and no separate API servers.
- OpenBao had one member per region, with pebbledb and a manual 1-of-1 unseal. There was no static seal and no HA.
- The CSI mount of db/creds was run with a 2-minute token and a 300 s poll, not the planned 15 minutes and 3600 s. The dead time per hour at the planned values is inferred.
- The point where OpenBao gives up retrying a revocation (marks it irrevocable) was not observed.
- The combination "management role with ADMIN only, plus revocation that ends sessions" was not run. It may need pg_signal_backend, and that is one check for the package after this one.

What later packages must take into account:
- SEC-290 cannot meet its own precondition (PASS for steps 2 and 3) as specified. Its role setup and statements need an amendment along the chosen variant first.
- SEC-300's consumer must size refresh to the login token, not to the lease.
- The 3-minute switch window comes from OpenBao's idle connection on the standby. It affects whoever owns the continuum switchover.

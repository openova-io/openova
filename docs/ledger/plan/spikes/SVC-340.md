# SVC-340 result: credential rotation on a native cache

Date: 2026-11-13
Branch: `spike/SVC-340` in openova-io/openova. This is a lab branch and is never merged.
Workflow: `.github/workflows/spike-svc-340.yaml`. Scripts: `tests/spikes/SVC-340/plugin_path.sh` and `tests/spikes/SVC-340/cloud_api.sh`.

outcome: not-run

## Question

Can the credentials of a native cache be rotated without the cloud console? A native cache here means the cloud's managed Redis-compatible service (DCS). There are two candidate paths:

- Path 1 is the OpenBao Valkey database plug-in. It works only if the cache leaves its access-control (`ACL`) commands open.
- Path 2 is the cloud API resource that resets a cache password.

The design allows three outcomes: the plug-in works; only the cloud API works; neither works. If the plug-in or the cloud API works, a `cache` capability epic may be written. If neither works, no native cache is offered and no contract is written.

## Why the outcome is not-run

The deciding test needs two things: a test cache instance on the live cloud, and the Sovereign's cloud account. A CI job has neither, so that test was not run.

CI measured everything else:
- what the plug-in needs from a cache;
- what the plug-in does to a cache;
- what survives a cache restart and what reaches a replica;
- how the pinned cloud provider changes a cache password.

The part still open is listed under "What is left". Until it runs, the acceptance of this lab test is not met: no outcome word of the design can be recorded.

## What was run

Everything ran in GitHub Actions on runner image ubuntu-24.04 (version 20261101.360.1) with Docker 28.0.4. One workflow has two jobs, and a push to the spike branch starts it.

Job `plugin-path`:
1. Reads the platform pins from the repository:
   - bp-openbao uses the upstream chart `openbao` 0.16.0. Its server image tag is 2.3.1 (read with helm 3.16.3 `helm show values`). bp-openbao does not override it.
   - bp-valkey uses the image `bitnamilegacy/valkey:8.1.3-debian-12-r3`.
2. Starts OpenBao `quay.io/openbao/openbao` in dev mode for tags 2.1.0, 2.2.0, 2.3.1, 2.4.0, 2.5.0, 2.6.5 and 2.7.2, and lists the database plug-ins built into each.
3. On OpenBao 2.3.1, the platform's server version, runs one sequence against each cache stand-in. All containers are on one Docker network. The steps are:
   - Configure the connection with `plugin_name=valkey-database-plugin` and user `default`.
   - Create a dynamic role with ACL rules `~spike:* +@read +@write +@connection`. Issue a credential, log in with it and write a key. Write a key outside the pattern. Revoke the lease and log in again.
   - Have the admin create a user `spikeapp`. Put a static role on it, rotate it, and test the old and the new password.
   - Run `rotate-root`. Test the old admin password, then issue a credential again.
   - Restart the cache container and check which credentials still work. Issue three times. Then write the connection again with the original password and issue once more.
4. The cache stand-ins are:
   - the bp-valkey image with a password (Valkey 8.1.3);
   - the same image with `ACL` closed (`VALKEY_DISABLE_COMMANDS=FLUSHDB,FLUSHALL,ACL`, which writes `rename-command ACL ""`);
   - upstream `valkey/valkey:8.1.3` with an ACL file;
   - `redis:7.0` (7.0.15);
   - `redis:6.2` (6.2.24);
   - `redis:6.2` with `rename-command ACL ""`;
   - `redis:5.0` (5.0.14);
   - the bp-valkey image as it ships today, with auth off.
5. Two primary/replica pairs of `valkey/valkey:8.1.3`. In the first, OpenBao uses the `default` user. In the second, OpenBao uses a dedicated admin user.
6. Restart controls, in runs 3 and 4: a cache is restarted once without a root rotation and once after one, on OpenBao 2.3.1 and on 2.7.2.

Job `cloud-api-path`:
1. Reads the pinned huaweicloud provider version from `infra/providers/huawei/.terraform.lock.hcl`: 1.91.0.
2. OpenTofu 1.8.5 installs that provider and dumps its schema.
3. Configures the provider with fake credentials, a closed local auth URL and a region that does not exist. Plans a DCS instance and a DCS account, builds a state from each planned object, then plans a password change with `-refresh=false`. No call reaches any cloud.
4. Clones the provider source at tag v1.91.0 (commit e44a578508c9, sparse checkout). Prints the password schema, the update path, the declared API calls and the documentation of both resources.

## Measured values

### 1. Which OpenBao has the plug-in (runs 1-4)

| OpenBao | `valkey-database-plugin` built in |
|---|---|
| 2.1.0 | no |
| 2.2.0 | no |
| 2.3.1 (the platform's server) | yes |
| 2.4.0, 2.5.0, 2.6.5, 2.7.2 | yes |

`redis-database-plugin` is built into the same versions. The platform's OpenBao needs no plug-in install step.

### 2. Plug-in with ACL open (runs 1-4)

The result was the same on four stand-ins: the bp-valkey image, Valkey with an ACL file, Redis 7.0 and Redis 6.2.
- The connection is accepted. A dynamic credential is issued as user `V_TOKEN_<ROLE>_<random>_<time>` with TTL 600 s.
- The new user logs in and writes `spike:k`: `OK`. Writing `other:k` returns `NOPERM`, so the ACL rules are applied.
- After the lease is revoked, the user is gone: `WRONGPASS`.
- Static role on an existing user: OpenBao replaces the user's password when the role is created, and the initial password is refused at once. `rotate-role` changes the password again. The old one is refused and the new one works.
- `rotate-root`: the original admin password is refused at once. OpenBao keeps issuing with the new one.

### 3. Plug-in with ACL closed (runs 1-4)

The stand-ins are the bp-valkey image with `ACL` disabled, and Redis 6.2 with `rename-command ACL ""`.
- `ACL WHOAMI` returns `ERR unknown command 'ACL'`.
- The connection config is still accepted, because logging in works.
- Issuing a credential fails with `ERR unknown command 'ACL'`. The static user cannot be created. `rotate-root` fails with `failed to update user`, and the original password keeps working.

Redis 5.0 has no ACL in the engine. There the connection itself is refused: `ERR wrong number of arguments`. The plug-in always logs in with a user name and a password.

The plug-in sends only three cache commands: `ACL SETUSER`, `ACL DELUSER` and `ACL GETUSER` (OpenBao source and the errors above). When those commands are closed, it can do nothing.

### 4. What survives a cache restart (runs 1-4)

After a container restart, on every stand-in with ACL open:
- A dynamic user issued before the restart is refused (`WRONGPASS`).
- The static user's rotated password is refused. In the ACL-file stand-in the account comes back with the initial password from the file.
- The admin (`default`) password is back to the original.
- After a root rotation, OpenBao cannot issue:
  - In the full sequence (runs 2-4) the requests fail with `EOF`, then hit a 60 s `context deadline exceeded`.
  - In the restart probe (run 4, OpenBao 2.3.1 and 2.7.2) the error is `error verifying connection: response returned from Conn: WRONGPASS`.
  - It stays broken across three attempts. It recovers only when the connection is written again with the original admin password.
- Control without a root rotation (runs 3 and 4, OpenBao 2.3.1 and 2.7.2): the first one or two requests fail with `EOF`. Within 5 to 10 s, issuing works again.

The plug-in's changes therefore live only in the cache's memory. The plug-in never calls `ACL SAVE`, and even an ACL file does not keep its changes. A restart undoes every rotation and removes every dynamic user. If the root password was rotated, OpenBao is locked out.

### 5. Replication (runs 2-4)

- A dynamic user created through the primary does not exist on the replica (`WRONGPASS`). The data that user wrote does reach the replica (`GET spike:r` returns `1`). ACL changes are not replicated.
- OpenBao on the `default` user: after `rotate-root` and a replica restart, replication is down. The replica reports `master_link_status:down` and logs `Unable to AUTH to PRIMARY: -WRONGPASS`.
- OpenBao on a dedicated admin user: `rotate-root` works. The admin user does not exist on the replica, and replication stays up after a replica restart.

### 6. bp-valkey as shipped (runs 1-4)

bp-valkey ships with auth off. The plug-in refuses an empty password (`password cannot be empty`). Against a default user with no password, it accepts any non-empty password.

### 7. Cloud API path in the pinned provider (runs 1-4; the instance plan from run 2 on)

- Provider 1.91.0 has the resources `huaweicloud_dcs_instance` and `huaweicloud_dcs_account`.
- `huaweicloud_dcs_instance.password` is optional, sensitive and not ForceNew.
  - A password change plans `~ update in-place` and `Plan: 0 to add, 1 to change, 0 to destroy`. Only `password` changes.
  - The update calls `POST /v2/{project_id}/instances/{instance_id}/password/reset`.
- `huaweicloud_dcs_account.account_password` is required, sensitive and not ForceNew.
  - A change plans `~ update in-place`. Only `account_password` changes.
  - The update calls `PUT /v2/{project_id}/instances/{instance_id}/accounts/{account_id}/password/reset` and waits until the account has finished updating.
- The documented values of `account_role` are `read` and `write` only. `account_type` is `normal` or `default`.
- `rename_commands` is documented only for Redis 4.0 and 5.0, and only for `command`, `keys`, `flushdb`, `flushall`, `hgetall`, `scan`, `hscan`, `sscan` and `zscan`.
- The provider configured and planned with fake credentials. No cloud API call was made, so whether the cloud accepts these calls is not measured.

## What the measurements decide, and what they do not

- The plug-in path needs three things from the native cache:
  - (a) `ACL` commands open to the account OpenBao uses;
  - (b) that account allowed to create users and change passwords;
  - (c) ACL changes kept through the cache's restarts and master/standby switch-overs.
- CI shows that (a) is a hard requirement. It also shows that plain Redis and Valkey do not give (c) on their own. Whether the cloud's managed cache gives (a), (b) and (c) can only be measured on the live cloud.
- Accounts that the cloud API creates have the role `read` or `write`. If these roles cannot run `ACL` (to be checked live), only the cache's default account could act as OpenBao's admin. The cloud also holds that account's password, and whether a change made inside the cache stays consistent with the cloud is also to be checked live.
- The cloud API path exists in the provider the platform already pins. Both the instance password and an account password change as an in-place update. Whether the live cloud exposes these DCS endpoints to the Sovereign's account is not measured.

## What is left (needs the live cloud)

One session on the live cloud needs:
- the Sovereign's cloud account (AK/SK);
- DCS quota for one small Redis 6.0 or 7.0 master/standby instance;
- a runner or pod inside the instance's VPC.

Steps:
1. Run `ACL WHOAMI`, `ACL SETUSER`, `ACL DELUSER` and `ACL GETUSER` as the default account, and as a `write` account created through the API.
2. If these commands are open: configure `valkey-database-plugin` (OpenBao 2.3.1) against the instance and run the same sequence as `plugin_path.sh`. Then restart the instance and trigger a master/standby switch through the API, and check which credentials survive.
3. Through the API, or through `huaweicloud_dcs_instance` / `huaweicloud_dcs_account` with provider 1.91.0, reset the instance password and an account password. Measure how long it takes until the new password works and the old one is refused. Check that no console step is needed.
4. Delete the instance.

The outcome word follows from steps 2 and 3:
- `plug-in` if step 2 passes, including survival through the restart and the switch;
- `cloud-api` if only step 3 passes;
- `neither` if both fail.

## What follows for the plan

- No `cache` contract, definition or Blueprint is written. That stays as the design says until the live session gives the outcome.
- The live session needs a scheduled slot with a cloud account and a test instance. It cannot run in CI.
- CI already shows these limits of the plug-in. They also apply to the in-cluster bp-valkey implementation of any later cache epic:
  - OpenBao should use a dedicated admin user, not `default`. Rotating `default` breaks replication when the replicas log in with it.
  - Plug-in users and rotated passwords are lost on every cache restart. After a root rotation, OpenBao stays locked out until the connection is written again with the original password. A design must either persist ACL changes (the plug-in does not) or avoid root rotation, and consumers must issue new credentials after a restart.
  - Plug-in users exist only on the primary, so a failover loses them.
  - bp-valkey ships with auth off, and the plug-in needs a password. Auth must be on wherever the plug-in is used.
  - OpenBao 2.3.1 or later is needed, because 2.1.0 and 2.2.0 lack the plug-in. The platform's server is 2.3.1.

## What later tasks must take into account

I ran the CI part in 4 of the 5 allowed runs, and all 4 passed. The outcome is not-run because the deciding test needs a test DCS instance and the Sovereign's cloud account on the live cloud, and CI has neither. Three things are not measured:
- whether the managed cache leaves ACL commands open to the default account or to an account created through the API;
- whether ACL changes survive the managed cache's restarts and master/standby switches;
- whether the DCS password-reset endpoints accept the Sovereign's credentials.

What is measured:
- OpenBao 2.3.1 (the platform's server) has valkey-database-plugin built in; 2.1.0 and 2.2.0 do not.
- The plug-in fully works when ACL is open: issue, key-scope enforcement, revoke, static rotation and root rotation.
- The plug-in does nothing when ACL is closed. Redis 5.0 refuses the connection.
- Every plug-in change is lost on a cache restart, even with an ACL file. After a root rotation OpenBao is locked out (WRONGPASS) until the connection is written again with the original password. A control without root rotation recovers in 5-10 s.
- ACL users are not replicated. Rotating the default user breaks replication; a dedicated admin user does not.
- The pinned huaweicloud provider 1.91.0 changes both the instance password and an account password in place, through POST .../password/reset and PUT .../accounts/{id}/password/reset.
- API-created DCS accounts can only have the role read or write.

For later packages:
- Keep the cache contract unwritten until a live session gives plug-in, cloud-api or neither.
- Schedule that session with a cloud account, DCS quota and a pod inside the VPC.
- Any cache epic, including the in-cluster bp-valkey implementation, must handle three things: a dedicated OpenBao admin user, loss of plug-in state on restart and failover (no root rotation unless ACL changes are persisted), and bp-valkey shipping with auth off.

The branch spike/SVC-340 (head 73310e8) stays in place as the evidence.

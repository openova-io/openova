# NET-280 Lab test: the overlay profile (result)

Date: 2026-11-19, one session, on origin/main 9ef70b131a. Type: lab test on the `local` provider pack through CI, two regions with two nodes each. Outcome: **NODE-OVERLAY**.

- Under the profile's network rule (the node addresses of the two regions reach each other on one UDP port, 51871, and on nothing else), only a node overlay forms the mesh. Cilium tunnel mode with WireGuard, and the platform's own data path (native routing with Cilium WireGuard), never connect it: 0 of 1 remote clusters ready after 600 s, in every run. The mesh needs TCP 12379 to the remote node address before WireGuard has a peer in the other region.
- The node overlay is a host WireGuard device `wg0` on UDP 51871 on every node. The other region's pod and node ranges are routed into it, and Cilium runs native routing with its own encryption off, pod MTU 1400 and `wg0` named as a device. In that form the connectivity test gave exactly the baseline's result (the same 20 failed actions, all harness classes). The three cases of NET-120 matched the baseline in the form with overlay addresses; in the final form a harness defect stopped them after the pause of case A.
- With TCP 12379 added to the rule, tunnel mode also matches the baseline. The platform's own data path does not: case A of NET-120 failed in 3 of 3 runs, and host to remote pod fails.
- The pass rule as written cannot be met on this harness by any data path, the baseline included. Section 4 lists the classes that fail everywhere.
- During a 5-minute partition, the remote backend stays in a global Service on every data path. 38 to 61 % of the dials failed.

## Question

Two clusters whose nodes reach each other only on one UDP port. Can they form a Cilium ClusterMesh that carries pod traffic and global Services, and which data path does it?

- Test (a): Cilium tunnel mode with WireGuard and an MTU that Cilium computes.
- Test (b): a node overlay with Cilium native routing, and Cilium encryption off between the clusters.

Pass rule: the Cilium connectivity test and the three cases of NET-120. Outcomes: `TUNNEL`, `NODE-OVERLAY` (that data path becomes the `overlay` profile) or `NONE` (a multi-region Sovereign needs a provider with a private link).

- Region A has nodes 172.30.1.10 (control plane) and .20, pods 10.42.0.0/16. Region B has 172.30.2.10 and .20, pods 10.43.0.0/16. The pack puts every machine on one Docker bridge.

### The profile rule

The lab script applies it after `local-pack.sh up`:

1. Each machine's `eth0` gets its region's /24 instead of the bridge's /16, with the default route via the bridge gateway (`onlink`). The two regions become two routed subnets, with the runner as the router between them. ICMP redirects are off on both sides. `br_netfilter` is on, so bridged frames pass the same filter.
2. Cilium's direct routes into the other region are deleted (8 routes in every run).
3. The runner's `DOCKER-USER` chain drops everything between `172.30.1.0/24, 10.42.0.0/16` and `172.30.2.0/24, 10.43.0.0/16`, except UDP to port 51871 between the two node ranges.
4. Variant "+TCP": stateless ACCEPT rules for TCP to and from port 12379 between the node ranges, above the DROP.

### The data paths

| Name | Cilium values on top of the kit's | Mesh endpoint |
|---|---|---|
| baseline | none: native routing, Cilium WireGuard with node encryption, MTU 1420; no profile rule | control-plane node address, port 12379 |
| tunnel, test (a) | `routingMode: tunnel`, `tunnelProtocol: vxlan`, `autoDirectNodeRoutes: false`, `MTU: 0`, WireGuard with node encryption | node address |
| native-wg | `directRoutingSkipUnreachable: true`; otherwise the platform's own data path | node address |
| overlay b1, test (b) | `autoDirectNodeRoutes: true`, `directRoutingSkipUnreachable: true`, `encryption.enabled: false`, `MTU: 1400` | the peer's overlay address |
| overlay b2 | as b1 | node address |
| overlay b3 | as b1, and `devices: [eth0, wg0]` | node address |

The overlay, on every node:

- `wg0`, a host WireGuard device, listens on UDP 51871 with MTU 1420 and keepalive 25 s. Its peers are the nodes of the other region; each peer's allowed IPs are its node address /32 and its own `podCIDR`. In b1 `wg0` also has an overlay address in 10.199.0.0/24, which the peer accepts too; in b2 and b3 it has no address.
- The other region's pod range is routed into `wg0` with the node address as source.
- The other region's node range is routed into `wg0` by a policy rule (priority 151, table 5128). `wg0` marks its own UDP packets (fwmark 0x5128), and a rule at priority 150 sends marked packets to the main table, so the tunnel's own packets leave on `eth0`.
- The keys are made on the runner and applied by `wg setconf` from a side container that joins the node's network namespace. Nothing is installed on a node.
- A first form, b0, had overlay addresses, MTU 1420 and no route for the node range.

### Order of one run

First a probe without the rule. Then the rule and a probe, the Cilium values with a restart of the agents, the operator and the mesh server, and the overlay where it applies. Tunnel and native-wg then wait 600 s for the mesh under the rule, and get the +TCP rule. Then:

1. wait for the mesh, up to 600 s;
2. the multi-cluster connectivity test: `cilium connectivity test --context region-a --multi-cluster region-b --service-type ClusterIP --test-concurrency 4 --flow-validation disabled --hubble=false`;
3. an echo Deployment and a global Service `both` (shared, no affinity) in each region;
4. the largest ICMP payload with DF set that passes, from a pod and from a host to a pod of the other region;
5. a 5-minute partition: the runner drops everything between the two regions' ranges, and a pod in A dials `both` about every 3 s;
6. `mesh-test.sh run`: cases A, B and C, each with a 5-minute `docker pause` of region B.

The earlier runs (marked "cases first" below) ran step 6 before steps 2 to 5. A connectivity test after five pauses of region B is not used for the comparison.

### 5. MTU

The largest ICMP payload with DF set that passed:

| Data path | Pod to remote pod | Above it |
|---|---|---|
| baseline, native-wg | 1312 (packet 1340) | refused locally, `mtu=1340` |
| tunnel | 1342 (packet 1370) | refused locally, `mtu=1370` |
| overlay b0, pod MTU 1420 | 1382 (packet 1410) | lost without an error |
| overlay b1, b2, b3, pod MTU 1400 | 1372 (packet 1400) | refused locally, `mtu=1400` |

Host to host through `wg0` carried a 1392-byte payload (packet 1420). With pod MTU 1420 and `wg0` MTU 1420, the pod path carries at most a 1410-byte packet, and the 10 bytes above it are lost without an error. With pod MTU 1400, the limit is the pod's own MTU, and a larger packet is refused with an error.

### 7. Facts found on the way

- With `encryption.enabled: false` and a restart of the agents, Cilium 1.19.3 removed its own `cilium_wg0` on every node (4 of 4 nodes, in 5 runs), so the overlay could bind UDP 51871.
- Cilium takes `wg0` as a device by itself only when `wg0` has an address. Named in `devices`, it is taken without one.
- The pack's `local-pack.sh up` connects the mesh without `kvstoremesh`; `mesh-test.sh` turns it on.

## Answer

- `TUNNEL` cannot meet the profile's network rule. The mesh is a TCP connection from each cluster to the other's endpoint, and Cilium learns the WireGuard peers of the other cluster from the mesh. With one UDP port the mesh never forms. The same holds for the platform's own data path.
- With one more rule, TCP 12379 between the node ranges, tunnel mode forms the mesh and matches the baseline on the connectivity test and on the cases. The platform's own data path does not.
- `NODE-OVERLAY` meets the rule. In form b3 it matches the baseline on the connectivity test exactly. On the cases of NET-120 it matched the baseline in forms b1 and b2, and in b3 up to the harness defect after the pause of case A.
- The outcome word is **NODE-OVERLAY**. The `overlay` profile is the node overlay of form b3.

## What follows for the plan

The build package of the `overlay` profile (none exists in the plan yet):

1. On every node, a host WireGuard device on the profile's one UDP port, with no address of its own. Its peers are all nodes of the other regions; a peer's allowed IPs are its node address /32 and its `podCIDR`.
2. Routing: the other regions' pod ranges go into the device with the node address as source. The other regions' node ranges go into the device by a policy rule; the device marks its own packets, and a second rule sends marked packets to the main table.
3. Cilium: `routingMode: native`, `autoDirectNodeRoutes: true`, `directRoutingSkipUnreachable: true`, `encryption.enabled: false`, `devices` naming the node's own device and the overlay device, and `MTU` at most the device MTU minus 20 (1400 under a device MTU of 1420).
4. The mesh endpoint stays at the node address, port 12379; the overlay carries it. No overlay address range is needed in the network registry.
5. New platform-owned state: each node's public key and endpoint must reach every node of the other regions before the mesh exists. The provisioner or the network registry carries them; the mesh cannot, because it rides on the overlay.
6. A move from Cilium WireGuard to the overlay on the same port first turns Cilium's encryption off and restarts the agents.
7. The cases of NET-120 are to be repeated on form b3 once the harness defect after the pause is fixed.

For the pass rule: the connectivity test runs with `--service-type ClusterIP`, and the three classes that fail on the baseline (section 4) are judged against the baseline, not as failures. The "restarts" assertion of NET-120 fails on every data path; it belongs to NET-120's harness, not to a profile.

For step MESH-P of NET-131: on every data path, a partitioned remote cluster stays "ready" and its backends stay in a global Service for 5 minutes. Local affinity, or the removal of remote backends on loss, is decided there.

## What later tasks must take into account

- The outcome is NODE-OVERLAY. The `overlay` profile is the node overlay of form b3 in "What follows for the plan". Tunnel mode needs TCP 12379 between the regions' node addresses, which the profile does not allow.
- The overlay needs per-node keys and endpoints distributed before the mesh exists: platform-owned state that the provisioner or the network registry must carry.
- Pod MTU 1400 under a device MTU of 1420. At 1420 the pod path loses packets of 1411 to 1420 bytes without an error.
- The other regions' node ranges must go through the overlay too, by a policy rule that keeps the device's own marked packets on the main table. Without it, host to remote pod, remote host ports and node to node fail, and Cilium drops packets with `FIB lookup failed`.
- The overlay device has no address and is named in Cilium's `devices`. With an address, cross-region host traffic leaves with that address and host policies deny it; without the device named, host ports across the overlay fail.
- The connectivity test on the platform runs with `--service-type ClusterIP`, because the NodePort ban is enforced; its node-port tests then fail by construction.
- NET-120's harness: the "restarts" assertion fails on every data path because `kvstoremesh` exits when the pause expires its lease, and after a pause the agent on region B's worker can become unreadable (kubelet `502`).
- For NET-131 MESH-P: a partitioned remote cluster stays ready, with its backends in global Services, for 5 minutes; 38 to 61 % of the dials to a two-backend Service failed. Recovery took 12 to 34 s, with 0 restarts.
- The platform's own data path (native routing with Cilium WireGuard), even with TCP 12379 open, failed case A in 3 of 3 runs and lost its `kvstoremesh` link after the paused cases. It is no fallback for the overlay profile.

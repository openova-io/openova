# SOV-321 Spike: the Sovereign's own mail server on a running Sovereign (result)

Date: 2026-11-19, one session, on origin/main effdd3ea7d. Type: spike. Outcome:

- **The chart as on main sends no sign-in code, on either release.** On its pin `v0.16.3` the server ignores the chart's TOML, starts in bootstrap mode with no mail listener, and has no REST API (`404`). On `v0.15.5`, the last TOML and REST release, the server runs from the chart's file, but the setup Job cannot finish and the server presents a certificate for `localhost` only.
- **The path works on `v0.15.5` with eight measured changes.** With them the catalyst-api's own sender delivered the sign-in code over STARTTLS with the certificate checked, authenticated with the credential the setup Job mirrored, and the message was read back from the mailbox.
- **Certificate:** the submission host needs a certificate whose name covers `mail.<fqdn>` (its own or the wildcard `*.<fqdn>`; both passed) and whose issuer the catalyst-api trusts. The sender always checks it and never sends without TLS.
- **DNS record:** nothing publishes `mail.<fqdn>`. On the standing test environment the name resolves through the zone's wildcard to the gateway address, where TCP 587 does not answer.
- **Admission:** in Phase 1 everything is admitted. After the hand-over the StatefulSet is denied until its image is pulled through the proxy, and the setup Job is denied because its container declares no resource requests.

## Question

The chart `platform/stalwart-sovereign/chart` is the Sovereign's own mail server. SOV-320 made its setup Job an ordinary bounded Job; SOV-322 puts the chart back into the kit and points the sign-in mail at it. Before that, four points must be measured:

1. **Certificate.** Is the sign-in code delivered over STARTTLS with the certificate checked, and which certificate does the submission host need?
2. **DNS record.** How does the record of `mail.<fqdn>` get published, and what does the name resolve to today?
3. **Admission.** Are the namespace, the objects and the images of the chart admitted under the policies the kit enforces?
4. **Principal calls.** Do the setup Job's calls to the mail server (wait for the admin API, create or update the submission principal, read it back) work?

### 2. The DNS record of `mail.<fqdn>`

On the standing test environment (both regions, read-only):

- The Sovereign's zone is answered by the parent's three name servers. Its variables say `DNS_MODE: delegated` and `MAIL_MODE: local`, but the Sovereign's own DNS service did not answer a query from outside.
- The zone holds a wildcard address record. `mail.<fqdn>` has no record of its own: it resolves through the wildcard to the same address as any unused label (`sov321-probe-label.<fqdn>` was tried) and as the zone apex. The console name has a record of its own, at another address.
- At the wildcard's address, TCP 443 answers. TCP 25 and TCP 587 do not answer (connect timed out after 6 s).
- The zone has no MX record and no TXT record at its apex.
- No namespace `stalwart` exists: the mail chart is not installed (its kit slot was removed on 2026-05-05, `clusters/_template/bootstrap-kit/kustomization.yaml` lines 382 to 392).
- No Service in either region carries an `external-dns.alpha.kubernetes.io/*` annotation. external-dns (sources `service`, `ingress`, `gateway-httproute`, `platform/external-dns/chart/values.yaml` lines 106 to 109) writes to the Sovereign's own PowerDNS (`--pdns-server=http://powerdns.powerdns.svc.cluster.local:8081`) and logs `All records are already up to date` once a minute.
- The Cilium address pool `sovereign-vip` of each region holds one address, and 0 of 1 are free: two LoadBalancer Services (the cluster-mesh API server and the PowerDNS service) share it through `lbipam.cilium.io/sharing-key: sovereign-vip`.
- CoreDNS forwards everything outside `cluster.local` to the node's resolvers. Its custom blocks are `cutover-registry-pin.server` (the Sovereign's registry name pinned to a cluster address, written by `platform/self-sovereign-cutover/chart/templates/03-harbor-prewarm-job.yaml` around line 907) and `github-ipv4.server`. Nothing pins `mail.<fqdn>`.
- The catalyst-api sends sign-in mail today to the parent's relay: `smtp-host` in `catalyst-system/sovereign-smtp-credentials` and in `catalyst-system/catalyst-openova-kc-credentials` is `mail.openova.io`.

By reading:

- The chart's mail Service (`platform/stalwart-sovereign/chart/templates/service-mail.yaml`) has no annotation by default (`service.mail.annotations: {}`). external-dns's `service` source takes a Service's names only from the `external-dns.alpha.kubernetes.io/hostname` or `internal-hostname` annotation, or from `--fqdn-template` (external-dns `v0.15.1`, `docs/sources/service.md`, "Domain names"). The kit passes no `--fqdn-template`. So nothing publishes `mail.<fqdn>` for the chart.
- The mirror Secret the setup Job writes sets `smtp-host` to `mail.<fqdn>` (`setup-job.yaml`, step 4), and the catalyst chart takes `smtp-host` from that Secret before its own default (`products/catalyst/chart/templates/catalyst-openova-kc-credentials-secret.yaml`, the source-wins lookup). So once the chart is installed, the catalyst-api dials `mail.<fqdn>:587` and resolves it through CoreDNS to the node's resolvers.

### 4. The setup Job's calls to the mail server

**Release v0.16.3, the chart's pin** (run 44480749890, job `lab-sov321-func (v0.16.3)`):

- The image runs `stalwart --config /etc/stalwart/config.json` (entrypoint and command of the image) and reads nothing under `/opt/stalwart`, where the chart mounts `config.toml`. `/etc/stalwart` was empty. The chart's `ADMIN_PASSWORD` is not used.

**Release v0.15.5, the last TOML and REST release** (runs 44480749890, 44485071435, 44488506846 and 44490853357):

## Answer

1. **Certificate.** Yes, the sign-in code goes over STARTTLS with the certificate checked, always: Go's `net/smtp` starts TLS when offered and checks the name, the server offers `PLAIN` only after STARTTLS, and every wrong certificate failed the send (C2, C3, C4). The submission host needs a certificate (a) whose name covers the host the catalyst-api dials, `mail.<fqdn>` (its own certificate and the wildcard `*.<fqdn>` both passed, the Service name did not), (b) whose issuer the catalyst-api trusts (an issuer outside its trust store failed), (c) declared in the server's configuration and mounted into its pod (the chart declares none today).
2. **DNS record.** Nothing publishes `mail.<fqdn>`: the chart's Service has no external-dns annotation, no Service of the standing test environment has one, and the kit gives external-dns no name template. The name resolves through the zone's wildcard to the gateway address, where TCP 587 does not answer. A name only for the catalyst-api inside the cluster needs a CoreDNS pin of `mail.<fqdn>` to the mail Service's cluster address, the same mechanism as `cutover-registry-pin.server`. A public name needs an address, and the region's address pool has none free unless the Service shares it through the pool's sharing key.
3. **Admission.** In Phase 1 every object is admitted. After the hand-over, the StatefulSet is denied by `harbor-proxy-pull` until `global.imageRegistry` points at the proxy, and the setup Job is denied by `resource-requests` (and by `harbor-proxy-pull` while the image is not proxied). Everything else, the mail Service with its `nodePort: 0` included, is admitted.
4. **Principal calls.** On the pinned `v0.16.3` they cannot work: the REST API is gone (`404`) and the TOML is ignored. On `v0.15.5` the chart's calls fail in four ways (no `curl` in the image, no admin, `/api/health` is `404`, an absent principal is `200` and taken as present), and its Job then writes a mirror whose credential the server does not know (C8). With these eight changes the sign-in code was delivered (C9):
   1. a fallback admin in the TOML whose secret is the chart's `ADMIN_PASSWORD`;
   2. a setup Job image that has `curl`;
   3. the wait asks `/healthz/ready`;
   4. the Sovereign's domain is created as a principal before the submission principal;
   5. the submission principal is created when the body says `notFound`, whatever the status code (done by hand in the lab);
   6. a certificate for `mail.<fqdn>` declared in the TOML and mounted;
   7. the catalyst-api trusts its issuer (the lab used `SSL_CERT_FILE` with the lab CA);
   8. `mail.<fqdn>` resolves to the mail Service inside the cluster (the lab used a host alias).

## What later tasks must take into account

SOV-322 puts the chart into the kit and points sign-in mail at it. On today's chart it would install a mail server that sends nothing. Before or inside SOV-322, by the measurements above:

1. **Release.** The chart is written for the TOML and REST releases, but pins `v0.16.3`. Either pin `v0.15.5` (measured here, with the changes of point 4 of the answer), or rewrite the chart for `v0.16` (`/etc/stalwart/config.json`, management over JMAP or `stalwart-cli apply`, `STALWART_RECOVERY_ADMIN`, a 587 listener declared explicitly, addresses as account names, a public TLD for domains). The `v0.16` way is not measured here and needs a lab run of its own. Whether `v0.15.5` is still patched upstream was not checked.
2. **Setup Job** (`platform/stalwart-sovereign/chart/templates/setup-job.yaml`): an image with `curl`, through the proxy and pinned by digest; wait on `/healthz/ready`; create the domain first; judge every answer by its body (`"error"`), never by the status alone; give the container resource requests and limits; drop the send-as call (it answers `400`, and the send worked without it); do not give the Job's pod the Services' selector labels (or narrow the Services' selector), so it is never an endpoint of them. Rename `MIRROR_SECRET_NAME` if `secret-not-in-env` must stay clean.

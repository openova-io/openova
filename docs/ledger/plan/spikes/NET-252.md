# NET-252 result: HTTPS through the front listener, and cilium-envoy memory with the filter under load

- Measured: 2026-11-19, 13:50 to 23:46 UTC, two CI runs on hosted runners, one job at a time, no cloud account.
- Outcome: **HTTPS**. A front listener in the Gateway's namespace terminates TLS with the Gateway's own certificates for two host names and meets the pass rule of NET-270 over HTTPS on the public port 443.
- Memory: with the filter `cilium-envoy` held 319 to 321 MiB through four hours of load, in two jobs, about 265 MiB more than without it (54 MiB), and did not grow. The run without the filter was cancelled after 1 h 42 min of its four hours; its numbers are reported as measured.

## Question

Decision record 0038 (WF2, WF8) builds the firewall on a front listener that the platform writes in front of the Cilium gateway listener. NET-270 proved it on plain HTTP only, and did not measure memory over time. Two questions, on the reference class of NET-270 (k3s, Cilium 1.19.3 as pinned in `platform/cilium/chart/Chart.yaml`, the gateway in the host network):

- **HTTPS.** Does a front listener in the Gateway's namespace terminate TLS with the Gateway's certificates for two host names and meet the pass rule over HTTPS: a clean request 200, a cross-site-scripting request 403 and an SQL injection request 403 for both host names, every route of both hosts answering, and a new HTTPRoute served?
- **Memory.** How much memory does `cilium-envoy` use with the filter and without it, under the same load, for four hours each? The release notes of coraza-proxy-wasm 0.6.0 warn of memory growth.
- **Outcomes.** `HTTPS`: the pass rule holds over HTTPS. `NONE`: it does not; then a new decision record replaces WF1 to WF3 with the second tier of NET-270 before NET-254 starts. The memory numbers are reported with either outcome.

**The front listener.** A CiliumEnvoyConfig `nslab-front` in namespace `web` with the annotation `cec.cilium.io/use-original-source-address: "false"`. One Envoy listener with the TLS inspector and one filter chain per host name: the chain matches the server name, terminates TLS with the certificate the Cilium operator already serves for that host (by its SDS name), and its HTTP connection manager runs the filter and then the router on the gateway's own HTTPS route configuration. As applied on port 443 (wasm configuration shortened; the directives are those of NET-270):

    apiVersion: cilium.io/v2
    kind: CiliumEnvoyConfig
    metadata:
      name: nslab-front
      namespace: web
      annotations: {cec.cilium.io/use-original-source-address: "false"}
    spec:
      resources:
      - "@type": type.googleapis.com/envoy.config.listener.v3.Listener
        name: front
        address: {socketAddress: {address: 0.0.0.0, portValue: 443}}
        listenerFilters:
        - name: envoy.filters.listener.tls_inspector
          typedConfig: {"@type": type.googleapis.com/envoy.extensions.filters.listener.tls_inspector.v3.TlsInspector}
        filterChains:
        - filterChainMatch: {serverNames: [a.example], transportProtocol: tls}
          transportSocket:
            name: envoy.transport_sockets.tls
            typedConfig:
              "@type": type.googleapis.com/envoy.extensions.transport_sockets.tls.v3.DownstreamTlsContext
              commonTlsContext: {tlsCertificateSdsSecretConfigs: [{name: cilium-secrets/web-a-tls}]}
          filters:
          - name: envoy.filters.network.http_connection_manager
            typedConfig:
              "@type": type.googleapis.com/envoy.extensions.filters.network.http_connection_manager.v3.HttpConnectionManager
              statPrefix: front-a
              useRemoteAddress: true
              httpFilters:
              - name: envoy.filters.http.wasm      # coraza; left out in memory-without-filter
              - name: envoy.filters.http.router
              rds: {routeConfigName: web/cilium-gateway-gw/listener-secure}
        - # the same for b.example with cilium-secrets/web-b-tls and statPrefix front-b

**Probe.** Every probe is a curl from the node over HTTPS with the server name and the Host header of the host, checked against the lab CA, and an `openssl s_client` read of the served certificate's serial:

    hc(){ curl -s -o /dev/null -w '%{http_code}' -m 5 --cacert ca.crt -H "Host: $1" --resolve "$1:$2:$NODE_IP" "https://$1:$2$3"; }
    hc a.example 443 /                                   # clean
    hc a.example 443 '/?q=<script>alert(1)</script>'     # cross-site scripting
    hc a.example 443 '/?id=1%27%20OR%20%271%27%3D%271'   # SQL injection
    openssl s_client -connect "$NODE_IP:443" -servername a.example </dev/null | openssl x509 -noout -serial

Each probe line covers both host names: clean, cross-site scripting and SQL injection on `/`, the route `a.example/hostname`, the route `b.example/echo?msg=hello`, and the served certificate of each host.

**Job `https`.** (1) The front listener on port 8443 beside the Gateway. (2) The Gateway's two listeners moved to port 18443 (`kubectl -n web patch gateway gw --type=json` on `/spec/listeners/0/port` and `/spec/listeners/1/port`), then the front listener on port 443. (3) A new HTTPRoute `route-a2`: `a.example` path prefix `/hostname` to `echo-b`, read through port 443 every 0.5 s by the body, which names the pod that answered. (4) The certificate of `a.example` rotated: Secret `a-tls` replaced with a new certificate, the served serial read every 0.5 s. (5) Request bodies: POST form bodies. (6) Restarts of the Cilium operator, the `cilium-envoy` DaemonSet and the Cilium agent, one after the other. The job fails unless the pass rule holds on port 443 at step 2 with the Gateway's certificates, the new route is served, and the pass rule holds after each restart.

**Jobs `memory-with-filter` and `memory-without-filter`.** The same cluster, the Gateway on 18443, `route-a2`, and the front listener on 443; the only difference is the filter list (`[wasm, router]` or `[router]`). Then `cilium-envoy` is restarted, 30 s idle, and vegeta sends a fixed rate of 200 requests per second over HTTPS for eight windows of 30 minutes (4 h), keep-alive, HTTP/1.1, round robin over 8 targets: `GET a.example/`, `GET a.example/hostname`, `GET b.example/`, `GET b.example/echo?msg=hello`, `POST b.example/echo` with a 1014-byte form body, `GET a.example/?q=<script>alert(1)</script>` (encoded), `GET b.example/?id=1' OR '1'='1` (encoded), `GET a.example/`. Six clean requests and two attacks in eight. Every 60 s the job reads the `VmRSS` and `VmHWM` of the `cilium-envoy` process from `/proc`, the `anon` memory of its container cgroup, and the Envoy admin `/memory` (heap of the Envoy allocator).

## Measured values

### The operator's listener with HTTPS

- CiliumEnvoyConfig `cilium-gateway-gw`, resources: Listener `listener`, RouteConfiguration `listener-insecure`, RouteConfiguration `listener-secure`, Cluster `web:echo-a:80`, Cluster `web:echo-b:80`.
- In the host network the one Listener binds every port of the Gateway (`0.0.0.0:443`) with the TLS inspector and three filter chains: plain text to `listener-insecure`; server name `a.example` with SDS certificate `cilium-secrets/web-a-tls` to `listener-secure`; server name `b.example` with `cilium-secrets/web-b-tls` to `listener-secure`.
- The operator copies each certificate the Gateway names into namespace `cilium-secrets` as `<namespace>-<name>` (here `web-a-tls`, `web-b-tls`). These names follow the rule in https://github.com/cilium/cilium/blob/v1.19.3/operator/pkg/model/translation/envoy_listener.go: `toTransportSocket` (line 431) names a certificate `<secrets namespace>/<namespace>-<name>`, and `httpsFilterChains` (line 320) writes one filter chain per certificate with the server names it serves, each to the route configuration `listener-secure`.
- A CiliumEnvoyConfig may name those SDS secrets: a name that already holds a `/` is kept as written (https://github.com/cilium/cilium/blob/v1.19.3/pkg/ciliumenvoyconfig/cec_resource_parser.go `qualifySdsSecretConfig`, line 893, calls `ResourceQualifiedName` of `pkg/policy/api/utils.go`, line 133, without `ForceNamespace`). The route configuration name is forced into the object's namespace, as NET-270 found, so the front listener lives in the Gateway's namespace.
- Baseline, the Gateway's own listener on 443, no firewall: both hosts `clean=200 xss=200 sqli=200`, every route 200, served serials equal the Secrets.

## Answer

**HTTPS.**

- The front listener terminates TLS for both host names with the certificates the Gateway names, through the SDS names the Cilium operator gives them (`cilium-secrets/<namespace>-<secret>`), and serves a rotated certificate without a change of its own.
- Through it, on the public port 443, a clean request returns 200, a cross-site-scripting and an SQL injection request return 403 for both host names, every route answers, a new HTTPRoute is served within 0.5 s, and all of this holds through restarts of the operator, Envoy and the agent.
- With the filter, `cilium-envoy` used 315 MiB idle and 319 to 321 MiB through four hours of load, in each of two jobs: about 265 MiB more than without it (53 MiB idle, 54 MiB under load). It did not grow: after the first hour it changed by less than 0.1 MiB per hour. The memory growth that the release notes of coraza-proxy-wasm 0.6.0 warn of did not show in 2880000 requests per job.
- With the filter the request time inside Envoy was 1.05 ms at the median, 3.06 ms at p95 and 4.06 ms at p99; without it, under 1 ms up to p99.9 (200 requests per second, 4 vCPU).

## What later tasks must take into account

1. The front listener takes the Gateway's certificates by their SDS names, `cilium-secrets/<namespace>-<secret>`, which the operator writes for the Secrets a Gateway listener names. A front listener naming a Secret that no Gateway listener names was not measured, so the Gateway keeps its HTTPS listeners, on the internal port, while a front listener serves them.
2. One filter chain per certificate, matched by server name, with the TLS inspector, as the operator writes its own. A request whose server name matches no chain was not measured.
3. Here the Gateway's move to the internal port and the front listener's apply were two steps, and port 443 answered nothing between them (`000`) until the front listener's first answer, 1 to 2 s after its apply. Decision record 0038 makes them one commit; NET-257 measures that window under load.
4. The front listener as written offers no ALPN, so clients speak HTTP/1.1. A front listener that offers HTTP/2 was not measured.
5. Coraza logs every matched rule at Envoy log level `critical`. Under attack traffic the Envoy log grows with every blocked request.
6. The filter's memory is fixed, about 265 MiB per `cilium-envoy` at concurrency 4, with a peak of about 368 MiB at start, on every edge node that binds a front listener. A different concurrency, a run longer than four hours, and other traffic (more attacks, larger bodies, many TLS handshakes) were not measured.
7. Not measured: more than one node, two regions, the reference cloud, a front listener for a Gateway with a wildcard host name, HTTP/2, and the last 2 h 18 min of the four hours without the filter.

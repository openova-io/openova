# ACC-030 result: per-session credentials through the mount; object lock

Date: 2026-11-13. Type: lab test. Evidence: branch `spike/ACC-030` of openova-io/openova. The branch is never merged, and its head is fc2c2770840690451f6e0ce0d66ef4b04980615e.

The design scores each item on its own. It has no single outcome word. **PASS** here means two things. Every item that is scored PASS or FAIL passed. No W2 package is held back by (a), (b), (d) or (h).

Item (c) found a defect that no decision line covers. A database user issued through the mount lives only as long as the mount's OpenBao login token: 5 minutes with role `access-session`. It does not live for the 1-hour lease. A 55-minute database session therefore cannot work as designed. This must be amended before ACC-132.

## The question

Can a session pod get credentials that are issued for it alone? The pod has no service-account token. The credentials come through the Secrets Store CSI mount with the OpenBao provider. The test covered an SSH certificate, an exec client certificate scoped to one pod, and a dynamic database user. It also asked:
- which identity a pod inside an Organization's virtual cluster presents;
- what the exec proxy must trust;
- whether SeaweedFS enforces object lock;
- whether transit signs with `ed25519`;
- how the mounted files behave when the driver rotates them.

## Measured results

### (a) `ssh/issue` through the mount: PASS
- **SecretProviderClass.** `provider: openbao`, `openbaoAddress`, `roleName: access-session`, `audience: openbao`. Two objects on `ssh/issue/acc.spike.target1`, each with `method: PUT` and `secretArgs: {valid_principals: alice, key_type: ed25519, key_id: <session uid>, ttl: 5m}`. They use `secretKey: private_key` and `secretKey: signed_key`.
- **Files.** `private-key` is 387 B and starts `-----BEGIN OPENSSH PRIVATE KEY-----`. `public-key` is 1762 B, type `ssh-ed25519-cert-v01@openssh.com`. Both have mode 0644 and owner 0:0.
- **Certificate.** Key ID = the session UID. Principal `alice`. No critical options. Extensions: `permit-pty` only. Valid for 330 s: issued 30 s back-dated, 5 min forward.
- **One pair.** The key and the certificate are one pair.
- **Logins.** An SSH login as `alice` to an sshd with `TrustedUserCAKeys` succeeded. A login as `bob` was refused with "Permission denied (publickey)".
- **One call.** OpenBao counted one successful `ssh/issue` for the two objects. The provider shares one call per mount for objects with the same `secretPath` and `method`.
- **Negative check.** A pod in namespace `other` asking for `ssh/issue/acc.spike.target1` got 403 "permission denied", because the policy is templated on the namespace.

### (b) `pki/issue` with a URI name: PASS; the templated `allowed_uri_sans`: PASS
- **Own namespace.** Pod `access-sb` in `spike`, with role `access-session`, used `pki/issue/access-exec-self` and `secretArgs: {common_name: session-<uid>, uri_sans: urn:openova:access:exec:spike:access-sb:tool, ttl: 5m}`. The keys were `certificate`, `private_key` and `issuing_ca`. The mount PASSED.
- **`exec-cert`.**
  - CN `session-<uid>`.
  - SAN `URI:urn:openova:access:exec:spike:access-sb:tool`, plus `DNS:session-<uid>`, which OpenBao adds from the CN.
  - EKU TLS client authentication. EC P-256. Lifetime 330 s. Issuer: the `pki` intermediate.
- **`exec-key`.** Starts `-----BEGIN EC PRIVATE KEY-----` and matches the certificate.
- **`exec-ca`.** One certificate, equal to the `pki` intermediate.
- **One call.** One successful `pki/issue` served the three objects.
- **Template refusal.** The same role, asking for a URI with namespace `other` from namespace `spike`, got 400 "URI Subject Alternative Names were provided via the API which are not valid for this role".
- **Platform role.** A pod in `guacamole` with role `access-session-platform` and `pki/issue/access-exec` got a URI for another namespace (`spike:target:app`). PASS.

### (c) `db/creds` through the mount: PASS for the mount; what happens to the user
- **Mount.** Objects `db-username` and `db-password` on `db/creds/spike.access-session.billing.ro`, with method GET and keys `username` and `password`. PASS. The mounted pair logs in. One `db/creds` read served all three objects.
- **Pod deletion.** Nothing happens. Ten seconds after deletion the user still existed, its lease still existed, and a login with it worked.
- **The user's life is bound to the login token.**
  - The provider logs in with the pod's token. The OpenBao login token has a TTL of 300 s.
  - The lease belongs to that token, so OpenBao revokes the lease when the token expires. The lease itself is 1 h (`lease_duration` 3600).
  - Revocation was attempted 299 s after the mount in the items job, and at 300–301 s in all four rotation jobs. This happened whether or not the pod still existed.
- **With the design's revocation statements, PostgreSQL 16 refuses.**
  - The error is `permission denied to reassign objects (SQLSTATE 42501)`. OpenBao retries it at 318 s, 363 s and later.
  - The user stays and logins keep working: they still worked at 420 s.
  - An explicit `lease revoke` failed with the same error (exit 2).
  - Users pile up: 9 were left after the 120 s rotation run.
- **With the contrast connection user, revocation works.** The lease was revoked at 299 s while the pod was still running.
  - New logins with the mounted pair failed: `role "..." does not exist`.
  - A connection opened at mount time failed its next statement with `ERROR: invalid role OID`.
  - The files did not change.
  - An explicit `lease revoke` succeeded, and the user was dropped.
- **A 1-hour login token keeps the lease.** In (i), the lease of the pod whose role has a 1-hour login token was still present after ten minutes.
- **The lease ID can be read.** An object with no `secretKey` writes the whole response JSON to a file. Its keys are `data`, `lease_duration` (3600), `lease_id`, `renewable` (true), `request_id` and `warnings`, with `lease_id` = `db/creds/<role>/<id>`. That file also holds the password. `secretKey: lease_id` fails with `key "lease_id" does not exist at the secret path`, because the provider reads keys only under `data`.

### (d) A pod without a service-account token: PASS
Three session pods had `automountServiceAccountToken: false` and no token directory inside the container. They mounted (a), (b) and the platform PKI object. The driver gets the token from the kubelet through `tokenRequests`.

### (e) A pod inside the virtual cluster with virtual service account `access-session`: not accepted
- **Sync off (`org1`, the platform setting).** The host pod runs as service account `vc-workload-vcluster`. Role `access-session` refused it at login with 403 "service account name not authorized".
- **Sync on (`org2`).** The host account is `access-session-x-apps-x-vcluster`, and the refusal is the same 403.
- **Control.** The same pods with role `workload` mounted (PASS in both). So the refusal comes from the role's bound name and not from the mount.

### (f) What the exec proxy needs in its client authority file
The proxy was built from this tree, with `TLS_CLIENT_CA_FILE` set to each candidate file and `CLIENT_CERT_ALLOWED_SUBJECTS=session-<uid>`. The client certificate came from the mount of (b) (platform role). For pki2, the client certificate was issued on `pki2`.

| File given to the proxy | Certificates in it | Client sends the leaf only | Client sends leaf + issuing CA |
|---|---|---|---|
| `ca.crt` of a cert-manager Secret, issuer on `pki/`, intermediate set-signed alone (SEC-250 layout) | the intermediate | accepted | accepted |
| `issuing_ca` file from the mount | the intermediate | accepted | accepted |
| `GET /v1/pki/ca_chain` | the intermediate | accepted | accepted |
| the root alone | the root | refused: "unknown ca" | accepted |
| `ca.crt` of a cert-manager Secret, issuer on `pki2/`, set-signed with intermediate + root | the root | refused | accepted |
| `GET /v1/pki2/ca_chain` | intermediate + root | accepted | accepted |

- **What "accepted" means.** The TLS handshake completes and `/healthz` returns 200. The exec path passes authentication and stops at the namespace allow-list (403 "namespace not in AllowedNamespaces"). A certificate of the same authority whose CN is not allow-listed gets 401.
- **Secret contents.** cert-manager's `tls.crt` holds the leaf plus the intermediate. `ca.crt` is the root-most certificate that the signing mount knows. Under the SEC-250 layout that is the intermediate.

### (g) SeaweedFS 4.22, bucket created by the chart's hook with `objectLock: true`
- **Hook.** It created the bucket and logged "Object Lock: enabled Versioning: enabled". Over the S3 API, versioning was `Enabled` and `ObjectLockEnabled` was `Enabled`.
- **Locked PUT.** A PUT with `x-amz-object-lock-mode: COMPLIANCE`, a retain-until date one day ahead, metadata `chain` and `prev`, and `Content-MD5` returned 200 with a version ID. HEAD showed the mode, the date and the metadata.
- **Delete of the locked version.**
  - With the administrator credential: 403 AccessDenied.
  - With `x-amz-bypass-governance-retention`: 403.
  - With the read-only credential: 403.
  - In a DeleteObjects batch: a per-key AccessDenied.
  - The version's bytes were unchanged afterwards.
- **Retention changes.** Shortening the retention: 403. Changing it to GOVERNANCE: 403. The retention read back unchanged.
- **Overwrite.** A PUT of the same key made a new version. The locked version still read the original bytes.
- **Delete without a version ID.** It created a delete marker (204). The latest GET gave 404, and the locked version still read back.
- **GOVERNANCE mode.** Delete of the version was refused for the administrator, both with and without bypass (403).
- **No default retention.** An object PUT without lock headers had no retention and its version could be deleted (204).
- **A bucket-scoped broker identity** (`Read,Write,List` on the bucket, added with `weed shell s3.configure`):
  - a locked PUT: 200;
  - delete of the version: 403;
  - delete without a version ID: 204 (delete marker);
  - a PUT to another bucket: 403.
- **Listing of 1,201 locked objects under one prefix.** They were written in 4.4 s.
  - ListObjectsV2 page 1: KeyCount 1000, IsTruncated true, with a continuation token.
  - Page 2: KeyCount 201.
  - The paginated total was 1201, all distinct and in sorted order.
  - ListObjects v1: 1000 plus NextMarker.
  - ListObjectVersions in pages: 1201 in total.
  - With `MaxKeys=1500`, SeaweedFS returned all 1201 keys in one page.
- **Below the S3 API.** `weed shell fs.rm -r` on the filer path removed the locked object and all its versions: GET of the version then gave 404, with no versions left. `weed shell s3.bucket.delete` was refused with "bucket has objects with active Object Lock retention or legal hold".

### (h) Transit `ed25519`: PASS
- **Key.** `transit/keys/access-recordings` with type `ed25519`, `exportable` false. A login with role `access-binder` worked.
- **Signing.** `transit/sign` returned `vault:v1:` plus a 64-byte signature. `transit/verify` gave `valid: true` on the original bytes and `valid: false` with one byte changed.
- **Offline check.** The public key read from the key endpoint verified the signature with python `cryptography`.
- **Refusal.** A session token (role `access-session`) got 403 on `transit/sign`. `prehashed=true` was accepted.

Each pod mounted the objects of (a), (b) and (c). Samples were taken every 30 s.

## What follows for the plan

- **Gating items.** (a), (b), (d) and (h) PASS. Nothing is held back. ACC-131 uses the mount for kind `ssh`. Role `access-exec-self` with the namespace template stands. The key type stays `ed25519`.
- **Names for ACC-104, ACC-105, ACC-131 and ACC-132.**
  - Object attributes: `method: PUT`, `secretArgs` (a map sent as the JSON body) and `secretKey`. Use the address parameter `openbaoAddress` (SEC-140).
  - Response keys: `ssh/issue` gives `private_key` (OpenSSH format) and `signed_key`. `pki/issue` gives `certificate`, `private_key` (SEC1 EC) and `issuing_ca`. `db/creds` gives `username` and `password`.
  - Objects with the same `secretPath` and `method` in one class share one call. Arguments are not part of that cache key, so one class must never hold two different argument sets for one path and method.
  - Files are mode 0644, owned by root. A per-object `filePermission` exists but was not measured.
- **Amendment needed before ACC-132.** A dynamic database user from the mount lives only as long as the provider's login token: 5 min with role `access-session`.
  - When the user is dropped, `db-proxy` cannot open new server connections. Open connections fail their next statement.
  - Measured remedy: a login token of 1 h kept the lease for the whole ten minutes.
  - The architect should give database sessions a login role whose token lifetime is at least the longest database session (55 min), or change the cap on database sessions.
- **For the secrets area (SEC-290, SEC-280, SEC-G13).** On PostgreSQL 16 the design's revocation statements fail when the management role holds only `CREATEROLE` with defaults. Users are then never dropped.
  - Measured fix: `ALTER ROLE <management role> SET createrole_self_grant = 'set, inherit'`. With it, revocation succeeds.
  - The SEC-G13 check "user absent after its lifetime" would fail without this fix.
- **(e).** Not accepted, so nothing changes. ACC-G05 gains a negative sub-step: role `access-session` from a virtual-cluster pod gives 403 "service account name not authorized".
- **(f) Chosen form.** Keep the cert-manager `Certificate`. Its `ca.crt` is the issuing intermediate, and that is enough for a client that sends only its leaf.
  - This holds only while SEC-250 set-signs `pki/` with the intermediate alone. If the root is imported into `pki/`, `ca.crt` becomes the root and a leaf-only client is refused.
  - `GET /v1/pki/ca_chain` works in both layouts.
  - Whether guacd sends a chain is measured by ACC-020.
- **(g).** The lock is enforced through the S3 API: delete and overwrite of a locked version do not succeed. ACC-111 writes the lock headers on every chunk and on the manifest; there is no default retention. ACC-G06 keeps its delete checks, with three corrections:
  - A credential with SeaweedFS `Write` (the broker's) can always add a delete marker (204). "Refused any delete" holds only for deletes of a version.
  - Governance bypass is refused even for the administrator.
  - `verify` must page by continuation token, because SeaweedFS can return more than 1,000 keys in one page.
- **Founder decision 5.** The founder should be told this fact: anyone with shell access to the store (`weed shell`, filer) removed a locked version within seconds. Compliance mode in this store therefore protects against S3 credentials, including the store's administrator key, but not against the operator of the cluster.
- **(i) at 3600 s.** Files are not issued again during a session, so the reconnect rule applies: a late reconnect after the 5-minute credential ends with `credential-expired`. There is one database user per pod, so the "more than 3" condition does not arise.
  - At 120 s there would be 4 users per pod, which is why the interval must not drop below the database lease.
  - If rotation ever happens during a session, the agent must check that the key and certificate it read are one pair, and read again if not.

# SOV-060 Spike: born-local node registry list (result)

Outcome: no

## Question

A node lists two endpoints for every canonical registry name: the Sovereign's own registry first, the origin registry second. k3s runs with `--disable-default-registry-endpoint`, and a wildcard entry `"*"` sends every other name to the local registry only. Seven questions:

- E1: When the first endpoint refuses connections, does a pull succeed through the second?
- E2: When the first endpoint answers "not found" (empty hosted project), does a pull succeed through the second?
- E3: Once the first endpoint holds the image, does the second get no request at all?
- E4: Does a name with no entry of its own fail, with no request leaving for a public address?
- E5: Do E1 to E3 still hold with the Dragonfly proxy first and its upstream set to the local registry?
- E6: Does removing the second endpoint from the file take effect on a running node, with no k3s restart?
- E7: When the first endpoint answers 401 or 503, does a pull still succeed through the second?

## What was run

Everything ran in GitHub Actions in openova-io/openova, on branch `spike/SOV-060`, which is never merged. The workflow is `.github/workflows/spike-sov-060.yaml` and the scripts are in `tests/spikes/SOV-060/`. Four runs: 43360822454, 43364610864, 43365718319 and 43367656916 (called runs 1 to 4 below). Each job builds everything on a fresh GitHub-hosted runner (ubuntu-24.04 image 20261101.360.1, Docker 28.0.4, tcpdump 4.99.4).

Node job (`node.sh`):
- k3s v1.31.4+k3s1 (the pin in the provider modules), which embeds containerd v1.7.23-k3s2. It is installed by the k3s install script with `--disable-default-registry-endpoint`. The packaged components are disabled, so no pod pulls anything else.
- The local registry is Harbor v2.14.3 (the platform's Harbor version), offline installer, HTTPS with a test CA. Projects are hosted and public, as the cutover chart creates them. There is one extra private project. A robot account with pull rights on every project is the node's login.
- The origin is a plain registry (`registry:2.8.3`) on port 5443. Its access log and its own request log are the evidence of every request it receives.
- The registry file follows the planned form: two endpoints per name with the `proxy-<x>/$1` rewrite, one entry for the local registry host, one for the origin host (local first), and the wildcard.
- To measure one behaviour per row on one node, some names get a different first endpoint:
  - a name that does not resolve;
  - an address that drops packets (inside a separate network namespace);
  - TLS endpoints with a certificate for other names, or a self-signed one;
  - Python stubs that answer 503, or 401 with a token endpoint that also refuses;
  - the local Harbor reached under a name whose login is wrong.
- Every case is one `crictl pull` through the node's CRI, the path the kubelet uses. For each case the job keeps the new lines of the origin, Harbor, stub, containerd and dfdaemon logs. tcpdump records every DNS lookup and every TCP SYN on all interfaces.
- Two controls prove the capture can see egress: C1 has no wildcard entry; C2 has the wildcard but no flag.

Dragonfly job (`dragonfly.sh`):
- Dragonfly manager and scheduler v2.5.0 and dfdaemon v1.4.0, which are the images of upstream chart 1.7.0 used by the platform's Dragonfly slot. They start from upstream's docker-compose deployment at v2.5.0.
- dfdaemon runs on the host network with its proxy on 127.0.0.1:4001. Its configured upstream (`proxy.registryMirror.addr`) is the local Harbor, with the test CA.
- The node list for quay.io is in the planned order: proxy, local registry, origin.

Run history:
- In run 1 the Dragonfly stack never started. MariaDB's health check passed during first-time setup, the manager exited, and compose started nothing after it. Run 1's E5 verdict printed `yes` with the proxy refusing every connection. That check could not fail, so run 1 is not evidence for E5. The verdict was fixed: it now needs a reachable proxy that carried requests to the local registry.
- Runs 2 and 3 measured E5. Run 3 also measured the fallback order that the decision rule names, and a hand-written hosts.toml across a k3s restart.
- Run 4 repeated the node job and added TLS-failure cases and a pull through the local-host entry.

## Measured values

One-layer test images were used, so each pull makes 4 requests to whichever endpoint serves it: manifest HEAD, manifest GET, and two blobs. containerd tries the first endpoint for each of the 4 requests separately.

### Gating rows

| Row | Result | Runs |
|---|---|---|
| E1 | yes | 1, 2, 4 |
| E2 | yes | 1, 2, 4 |
| E3 | yes | 1, 2, 4 |
| E4 | yes | 1, 2, 4 |
| E5 | no | 2, 3 |
| E6 | no | 1, 2, 4 |
| E7 | yes | 1, 2, 4 |

### E1: yes (runs 1, 2, 4)

The local registry's front was stopped, so connections were refused. Pulls succeeded in 0.2 / 0.3 / 0.1 s. The origin received 4 requests and the local registry logged none. containerd logged `connect: connection refused` and moved to the next host.

Other ways the first endpoint can fail:
- Name does not resolve: pulled in 0.2 / 0.3 / 0.2 s.
- Trusted certificate for other names (run 4): pulled in 0.1 s. containerd reported "x509: certificate is valid for ..., not wrongcert.local.test".
- Self-signed certificate (run 4): pulled in 0.1 s. containerd reported "x509: certificate signed by unknown authority".
- Address drops packets: pulled in 120.2 / 120.2 / 120.1 s. That is a 30 s connect timeout on each of the 4 requests.

### E2: yes (runs 1, 2, 4)

The hosted project existed and was empty. Harbor answered 401, issued a token, and then answered 404 for the manifest and for each blob. containerd logged "trying next host - response was http.StatusNotFound". It took the image from the origin in 0.2 / 0.2 / 0.2 s, with 4 origin requests and 10 local requests.

If the project itself does not exist, Harbor answers 401 and never 404. The pull still falls through, in 0.1 to 0.2 s.

### E3: yes (runs 1, 2, 4)

The image was pushed into the local project. Pulls took 0.1 to 0.2 s. The local registry served the manifest and blobs with 200. The origin received 0 requests: both its access log and its own request log were empty for the case.

Names addressed through the origin host entry (runs 1, 2, 4) and through the local host entry (run 4) were also served locally, with 0 origin requests.

### E4: yes (runs 1, 2, 4)

Two names with no entry of their own were pulled:
- `registry.example.invalid/x/y:1`
- `mcr.microsoft.com/oss/kubernetes/pause:3.6` (a real public registry that is not on the list)

Both failed in 0.1 s. The local registry was asked and answered 401. The capture saw 0 DNS lookups of either name and 0 SYN to any address of mcr.microsoft.com.

A listed name that exists nowhere (`quay.io/spike/absent:1`) also failed, with 0 lookups of quay.io.

The controls show the capture does see egress when it happens:
- C1, no wildcard, flag set: the mcr image was pulled from the public registry, with 8 / 8 / 12 lookups and 6 SYN. `registry.example.invalid` was looked up 2 times.
- C2, wildcard present, flag removed: the absent quay.io image caused 6 lookups and 2 SYN to quay.io. The mcr image was pulled from the public registry after the local registry refused it.

So the flag and the wildcard are both needed. Neither alone keeps the node closed.

There is one side effect. The wildcard maps any unlisted host onto local paths: `registry.example.invalid/proxy-quay/spike/e3:1` was pulled from the local registry. No request goes outside, but local paths answer under any host name.

### E5: no (runs 2, 3)

In the planned order (proxy, local, origin), dfdaemon v1.4.0 did not use its configured upstream. containerd adds `?ns=<registry>` to every request it sends to a mirror endpoint, and this dfdaemon routes by that parameter before its configured address. So every request went to `https://quay.io`; the proxy's log shows `https://quay.io/v2/proxy-quay/spike/.../blobs/...` answered 401.

| Run | Local registry state | Lookups of quay.io | SYN to quay.io | Pull time |
|---|---|---|---|---|
| 2 | refuses | 24 | 24 | 2.9 s |
| 2 | empty | 20 | 20 | 2.8 s |
| 2 | holds the image | 18 | 18 | 2.6 s |
| 3 | refuses | 28 | 26 | 1.2 s |
| 3 | empty | 26 | 26 | 1.3 s |
| 3 | holds the image | 10 | 10 | 0.9 s |

The proxy then returned EOF or an error, and containerd fell through to the local registry and the origin. Pulls succeeded, and the origin was unused once the local registry held the image. But the proxy carried 0 requests to the local registry, and every pull reached the public internet.

With the proxy stopped, pulls fell through in 0.2 to 0.3 s (runs 1, 2, 3).

### E5h: the same three cases with a header (runs 2, 3)

The hosts.toml entry for the proxy endpoint was given the header `X-Dragonfly-Registry = ["https://<local registry>"]`. All three cases pulled: 0.6 / 0.3 / 1.3 s in run 2 and 1.0 / 0.3 / 1.2 s in run 3. There were 0 lookups of quay.io. The proxy carried 16 requests to the local registry, including ranged blob reads through its P2P path. The origin was unused once the local registry held the image.

### The rule's fallback order, local registry then proxy then origin (run 3)

- Local registry empty: the proxy went to quay.io before the origin was tried, with 14 lookups and 10 SYN.
- Local registry holds the image: the proxy was never used, and there were no lookups.

### Hand-written hosts.toml (run 3)

The file had no k3s header line and was for a name that is not in registries.yaml. It survived a k3s restart unchanged (hash 671e84e49ff43a37). With it:
- Local registry holds the image: pulled in 1.4 s. The proxy carried 10 requests to the local registry. Origin 0, lookups 0.
- Local registry empty: pulled in 0.3 s through the origin. The proxy carried 6 requests. Lookups 0.

### E6: no (runs 1, 2, 4)

The origin was removed from registries.yaml on the running node. After 45 s the generated quay.io hosts.toml had the same hash (7482512bd602afcb in all three runs). The next pull still took the image from the origin, with 4 requests.

Two other changes were tried:
- k3s's own one-endpoint render was written directly over the quay.io hosts.toml. This took effect on the next pull with no restart: the pull failed and the origin received 0 requests.
- After `systemctl restart k3s` (2 to 3 s on a node with no pods), k3s rendered the edited registries.yaml and the origin was unused.

So k3s reads registries.yaml only at start, while containerd reads hosts.toml on every pull. k3s rewrites the hosts.toml of every name that registries.yaml lists each time it starts.

### E7: yes (runs 1, 2, 4)

- First endpoint answers 503: pulled through the origin in 0.3 s; the stub logged 4 requests.
- First endpoint answers 401, and its token endpoint refuses too: pulled through the origin in 0.3 s.

Harbor variants:
- Private project with a wrong login (runs 2, 4): Harbor issued a token and then answered 401. containerd repeated each of the 4 requests 6 times, about 1.5 s apart. The pull succeeded through the origin in 33.4 / 33.2 s.
- Public project with a wrong login (runs 1, 2, 4): Harbor issued a token anyway and served the image in 3.1 to 3.2 s. No 401 happens for a public project.
- Harbor's front up but its core stopped, so every request gets 502: fell through in 12.4 / 32.1 / 12.4 s.

## Decision

E1, E2, E3 and E4 are `yes`. E6 is `no`. The gating set (E1, E2, E3, E4, E6) is therefore not all `yes`, so the outcome is `no`. E5 is also `no`, and E7 is `yes`.

## What follows for the plan

1. SOV-130 may proceed. Its own precondition, `yes` on E1 to E4, holds. Keep the flag and the wildcard together: the controls show that each one alone leaves a path to public registries.
2. SOV-160 needs no change. E2 and E7 are `yes`, so the gateway route does not have to wait until the local projects are filled.
3. SOV-250 (registry-pivot) is affected by E6 `no`. The rule says it restarts k3s agents one at a time. The measured alternative is to write hosts.toml directly, which takes effect at once. Because k3s rewrites the hosts.toml of every name listed in registries.yaml on each start, the writer must then also update registries.yaml. Or the canonical names stay out of registries.yaml and their hosts.toml files are owned directly; k3s leaves those alone.
4. E5 `no`, and the rule's remedy does not fix it. Placing the proxy after the local registry still sends requests to the public registry whenever the local registry lacks an image, which covers the whole time before the closure copy. When the local registry has the image, the proxy is never used. The form that works, as measured, is the header `X-Dragonfly-Registry: https://<LOCAL_REGISTRY_HOST>` on the proxy endpoint in hosts.toml. registries.yaml has no field for request headers, so the proxy endpoint must be written into hosts.toml directly, by the provider module at boot and by registry-pivot afterwards. Until then, keep the proxy out of the node list. This goes to the architect before the Dragonfly slot is used on a born-local node.
5. Time costs to plan for:
   - Before the local registry exists, its address should refuse connections or not resolve. An address that drops packets costs 30 s on every request; a one-layer image took 120 s.
   - The node's login must be right before any private local project is listed. A real Harbor 401 costs about 8 s per request.
6. The wildcard maps unlisted host names onto local paths. This is not egress, but the network area should know it.

## Not measured in CI

These need one single-region spike environment from lane A, or the local provider pack:
- the real gateway or load balancer in front of the local registry before its route exists (whether it refuses, drops, or presents another certificate on a real cloud);
- a real parent Harbor with proxy-cache projects as the origin;
- k3s agents on separate nodes;
- real image sizes;
- Dragonfly installed by its Helm chart as a DaemonSet;
- the effect of a k3s restart on running pods.

## What later tasks must take into account

The seven rows are E1 yes, E2 yes, E3 yes, E4 yes, E5 no, E6 no, E7 yes, so the outcome is no. Each node row was reproduced three times (runs 1, 2, 4) and E5 twice (runs 2, 3).

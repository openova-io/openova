# Lab test AIP-031: one sandbox substrate shared by Organizations, with grants scoped to each Organization

Outcome: **pass**, with one addition that the upstream chart does not offer (a rule in the actor router). Date of the runs: 2026-11-19. Upstream versions as in lab AIP-030: kagent 1.0.1, Agent Substrate charts 1.0.0, router dataplane agentgateway v1.7.0.

## Question

Lab AIP-030 ran one kagent install per Organization on one shared Agent Substrate (T3). The upstream installer makes every Organization's controller a bootstrap owner of the Substrate API, and a bootstrap owner is a global owner. Can each controller instead be limited to its own atespace, so that it can neither read nor change another Organization's actors, while its own agents keep working? The question has two layers, and each was measured:

- the control plane: the Substrate API (`ate-api-server`), which authorizes every call against its OpenFGA model;
- the data plane: the actor router (`atenet-router`), through which a controller sends each turn to an actor, naming it in the header `ate-target-actor: <atespace>/<actor>`.

## Measured values

### S1, installer default (negative control): the controller of `org-a` acts on `org-b`

Substrate values written by `kagent install` and extended for `org-b` as in AIP-030: `bootstrapOwners` = the controllers of `org-a` and `org-b`, `system:serviceaccount:ate-system:ate-client` and the platform principal; `ingressAllowedSPIFFEIDs` = both controllers; one `namespacePolicies` entry per Organization.

- All 7 calls on `org-b` and all 5 global calls were let through: the reads answered `OK`, or `NotFound` for the access policies, which did not exist yet; SuspendActor on `org-b`'s actor answered `OK`, a real change; DeleteActor with the wrong UID answered `Aborted` (authorized, precondition failed); the policy update answered `InvalidArgument` (authorized, refused by the handler); CreateAtespace created `spike-x-3586`.
- Data plane: through the router, the identity of `org-a` turned `org-b`'s suspended actor to `ACTOR_STATE_RUNNING` and got the actor's own answer, HTTP 200 with an A2A JSON-RPC error body (`"code":-32600,"message":"invalid request"`, domain `a2a-protocol`).
- A turn on `org-b` afterwards completed. The probe set can therefore see a cross-Organization reach; this is the result S2 must turn around.

### S2, grants scoped to each Organization's atespace: pass

Change: `ateApi.authorization.bootstrapOwners` = `[spiffe://cluster.local/ns/catalyst-system/sa/substrate-admin]` only (Helm upgrade exit 0); the controllers and `ate-client` removed. The platform principal created one access policy per atespace: `org-a` grants `editor` to `user:spiffe://cluster.local/ns/org-a/sa/kagent-controller`, `org-b` the same for its controller (both `OK`). Both controllers were restarted.

- Own atespace: 3 of 3 calls `OK`.
- `org-b`: 7 of 7 refused with `PermissionDenied`, each naming the principal and the missing relation, for example `principal "user:spiffe%3A//cluster.local/ns/org-a/sa/kagent-controller" lacks "can_get" on "actor:org-b/session-..."`, `lacks "can_suspend"`, `lacks "can_delete"`, `lacks "can_update_access_policy" on "atespace:org-b"`.
- Global: 5 of 5 refused (`can_list_actors`, `can_list_atespaces`, `can_list_workers`, `can_get_access_policy`, `can_create_atespace` on `global:root`).
- Own grants: the update of `org-a`'s policy refused (`lacks "can_update_access_policy" on "atespace:org-a"`): an editor cannot widen its own atespace.
- The runtime kept working: after the restart a turn on `org-a` and one on `org-b` completed; a new Agent `probe2` in `org-a` (a new ActorTemplate with its golden snapshot) was Ready in 12 s (attempt 2: 25 s) and its turn completed. The two controllers logged 0 `PermissionDenied` lines from the restart to the end of S2.

### S3, a fresh Organization under the scoped model: pass

`org-c`'s controller was added to `ingressAllowedSPIFFEIDs` and `namespacePolicies` and to nothing else; kagent installed in `org-c` (Helm exit 0); Agent `probe` applied.

- Without its atespace and grant the Agent stayed `Ready=False`, reason `RuntimePreparationFailed`, message `Runtime preparation failed (PermissionDenied)`, for 240 s. The controller logged every 30 s: `reconcile ActorTemplate org-c/probe-1085efa6b651: rpc error: code = PermissionDenied desc = permission denied: principal "user:spiffe%3A//cluster.local/ns/org-c/sa/kagent-controller" lacks "can_get" on "actor_template:org-c/probe-1085efa6b651"`.
- The platform principal then created atespace `org-c` and its policy (`editor` for the controller of `org-c`), both `OK`. The Agent became Ready 11 s later (attempt 2: 9 s), without a controller restart, and a turn completed.

### S4, the data plane: fails as shipped; passes with a router rule

- Under the scoped API grants of S2, the identity of `org-a` still reached `org-b`'s actor through the router: `ACTOR_STATE_SUSPENDED` before, `ACTOR_STATE_RUNNING` after, HTTP 200 with the actor's A2A answer. The control (`org-b`'s own identity) gave the same.
- This is the upstream design of v1.0.0: the router's only check is the caller's SPIFFE ID against `ingressAllowedSPIFFEIDs` (chart template `atenet-router.yaml` line 48), "Any ID on the allowlist may use the ingress router to contact any actor" (`cmd/atenet/internal/router/README.md` line 216), and the dataplane calls `ResumeActor` with its own identity and a request that names only the actor (agentgateway v1.7.0 `crates/agentgateway/src/http/substrate/ingress.rs` lines 329 to 345), under its system role `ingress_router`, which holds `can_resume` in every atespace (`cmd/ateapi/internal/authz/model.fga` line 174). Upstream's threat model claims the opposite ("Ingress checks the caller's permission on the target actor", `docs/security/threat-model.md` T-04); the measurement agrees with the README and the source.
- The rule. The router's ConfigMap `atenet-router-agentgateway-config` got one more `directResponse` condition in the policy block shared by its actor routes (HTTP and gRPC): when `ate-target-actor`, in the request headers or the CONNECT headers, does not start with the atespace paired with the caller's `source.spiffeId`, the router answers 403 before any resume. The pairs were the three controllers and their atespaces. The ConfigMap was replaced and the router restarted (rollout exit 0, no error in its log).
- With the rule: `org-a` to `org-b` over HTTP got 403 (`ate-target-actor names an atespace this caller may not reach`) and the actor stayed `ACTOR_STATE_SUSPENDED`; the same over gRPC got `PermissionDenied ... 403 (Forbidden)` and the actor stayed suspended; `org-b` to its own actor and `org-a` to its own actor both turned `SUSPENDED` to `RUNNING`; turns on `org-a`, `org-b` and `org-c` through their controllers all completed.

### Other measured facts

- Turns: attempt 1, 11 of 11 `TASK_STATE_COMPLETED`; attempt 2, 10 of 11. The one refused turn was the first on `org-b`, sent 0.2 s after its Agent became Ready and before any grant was changed: kagent answered A2A error -32004 `input was not accepted; retry after the session becomes available` (reason `KAGENT_SEND_NOT_ACCEPTED`, `retryAfterMs` 100). Every later turn on `org-b` completed. It is a readiness race of kagent, not an isolation result; the setup record `ORGB` of attempt 2 is `fail` for it alone.
- Removing `ate-client` from the bootstrap owners broke nothing that the run used.
- The Substrate chart offers no value for router policies: its `atenetRouter` values are `requestParking`, `requestTimeout`, `ingressAllowedSPIFFEIDs` and resources (chart 1.0.0 `values.yaml`). The rule can only be added after rendering.

## Answer

- **Control plane: yes, as upstream ships it, by configuration.** With the platform's own principal as the only bootstrap owner and one access policy per atespace granting `editor` to that Organization's controller, a controller can read and change only its own atespace. Every call on another Organization, on the global scope and on its own grants was refused, and the runtime kept working (turns, a new Agent, a new Organization). `editor` is enough; `owner` is not needed and would let a controller change its own grants.
- **The platform creates each atespace.** Creating an atespace needs a global owner, so a controller without global ownership cannot start in a new Organization until the platform principal has created the atespace (named as the Organization's host namespace) and its access policy. Then it recovers by itself within seconds.
- **Data plane: no, as upstream ships it; yes with one router rule.** Scoped API grants do not reach the router: any identity on its allow-list can resume and talk to any actor of any Organization. A per-caller rule in the router's configuration, pairing each controller's SPIFFE ID with its atespace, closes it, measured over HTTP and gRPC, while every Organization still reaches its own actors.

## What follows for the plan

1. The restriction set after AIP-030 ("the agent runtime with the sandbox for the Sovereign's own Organization only, until AIP-031 passes") can be lifted when the install of the runtime carries both measures below. Until then it stays.
2. **Bootstrap owner.** The Substrate API's `bootstrapOwners` lists one principal: a platform component's own pod-certificate identity. Never an Organization's controller, never `ate-client`.
3. **Atespace and grant per Organization.** That platform principal creates the atespace named as the Organization's host namespace and writes its access policy, `editor` for `spiffe://cluster.local/ns/<organization>/sa/kagent-controller`, when the Organization's runtime is installed. It deletes them when the Organization is removed, and never reuses an atespace name (upstream's known limitation: grants are keyed by name, `docs/guides/authorization.md`, "Known limitations").
4. **Router rule.** `ingressAllowedSPIFFEIDs` alone is not isolation. The router's ConfigMap carries the per-caller atespace rule measured in S4, regenerated with `ingressAllowedSPIFFEIDs` whenever an Organization is added or removed, by a post-render step because the chart has no value for it. The router was restarted after the change; whether it reloads the file by itself was not measured.
5. A view that lists workers across the cluster belongs to the platform, not to an Organization: kagent's Substrate summary calls the global `ListWorkers` (kagent v1.0.1 `go/core/internal/service/system/substrate.go` line 210), which S2 refused for the controller. The summary view itself was not exercised.

## What later tasks must take into account

- AIP-203 (`platform/kagent`, and with it the per-cluster Substrate values): `bootstrapOwners` is the one platform principal; the controller's grant is the atespace access policy (`editor`), never the bootstrap list; the atespace and its policy exist before the Organization's install, created by the platform principal; the router ConfigMap carries the per-caller atespace rule, kept in step with `ingressAllowedSPIFFEIDs` by a post-render step. Its check should repeat the cross-Organization probe of S2 and S4 (a refused API call and a 403 from the router).
- Callers of an agent (ops-records and others) retry a `SendMessage` that kagent answers with A2A error -32004 after the `retryAfterMs` it names (measured once, right after an Agent became Ready).
- AIP-202 (host-side fence): the router admits every namespace at the network layer (chart NetworkPolicy `atenet-router`, ingress on all its ports from anywhere), and every controller must reach it, so a network rule cannot separate Organizations there. The separation is the router rule; the fence keeps the callers rule of AIP-030 T10.
- The component that holds the platform principal and writes atespaces and policies is not chosen here; it needs a pod certificate of the podidentity signer and network access to the API (its namespace labelled `ate.dev/api-access=true`).
- Not measured, and what it needs: the CONNECT tunnel path of the router (port 8444, used by `kubectl ate proxy actor`) under the rule (the rule covers CONNECT headers, but only port 443 was probed); whether the router reloads its ConfigMap without a restart; the Kubernetes credential provider's `namespacePolicies` across Organizations (configured per atespace, not probed); deleting an Organization's atespace; more than one node; an upstream release whose router checks the caller's atespace grant itself, which would make the rule unnecessary (the README calls richer policies "post-GA").

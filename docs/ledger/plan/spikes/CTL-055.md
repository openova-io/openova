# CTL-055: Gitea push mirror between two Giteas on one database

## Question

The writer region's Gitea and a follower region's Gitea share one database, and each keeps its own repository disk. Can Gitea's built-in push mirror, with "sync on commit" turned on, carry every commit from the writer's disk to the follower's disk? We measured this over ten commits. The answer feeds decision record 0027 on how the follower gets its copy of Git.

## Answer

Yes, on Gitea 1.22.3. That is the version in chart gitea-10.5.0, which the platform pins. In each of three separate runs, all ten commits made through the writer's API reached the follower's disk. Each took 2.7 to 3.6 seconds. At the end the follower's disk was identical to the writer's. The mirror needs one setting, and using it brings several conditions, listed under "What follows".

## What was run

- **Where.** GitHub Actions in openova-io/openova, on branch `spike/CTL-055` (never merged). The workflow is `.github/workflows/spike-ctl-055.yaml` and the script is `tests/spikes/CTL-055/measure.sh`. Hosted runner ubuntu-24.04 (image 20261101.360.1), Docker 28.0.4, Helm 3.22.1.
- **Versions.** We read chart gitea 10.5.0 from dl.gitea.com. Its appVersion is 1.22.3 and it is rootless by default. Image `gitea/gitea:1.22.3-rootless`, with git 2.45.2 inside. Database `postgres:16`, server version 16.16.
- **Set-up.** One Postgres and two Gitea containers on one Docker network: A is the writer and B the follower.
  - Each Gitea has its own data volume, so its own repository disk.
  - Each has its own SECRET_KEY and INTERNAL_TOKEN, as two separate chart installs would.
  - Both use the same database. Both keep sessions in the database, require sign-in and run without Redis, so each has its own local queue. These are the platform chart settings that matter here.
  - A token created on A works on B (HTTP 200), because the token table is shared.
- **Steps.**
  1. Create an organisation and repository r1 on A. B's API shows the repository, but B's disk does not have it. Run B's `reinit_missing_repos` task, as today's follower job does.
  2. Create a push mirror on A for r1. Address `http://gitea-b:3000/ctl/r1.git`, a token as the password, an 8-hour interval, sync on commit on. First try default settings, then `[migrations] ALLOWED_DOMAINS=gitea-b`.
  3. Make ten commits one after another through A's batch contents API (`POST /repos/{owner}/{repo}/contents`), the call the planned commit library uses. After each commit, check B's disk every 0.1 s (`git rev-parse` inside B's container) until the commit is there.
  4. Make ten commits back to back. Then make one commit by `git push` over HTTP to A.
  5. Make a branch and a pull request on A, then a commit. Run the existing job's method once for comparison (`clone --mirror` from A, `push --mirror --force` to B), then make one more commit.
  6. Have B run the shared mirror row: once through B's sync API, once through B's mirror cron with the row made due. Then do the same on A.
  7. Add one repository webhook on r1 (a single row in the shared table) pointing at a test listener, and count deliveries from each Gitea. Then run `resync_all_hooks` on B and make three more commits.
  8. Create repository r2 after set-up and add its mirror before B has r2's directory. Then run B's reinit task and make another commit.
- **Outcome rule**, written in the script before the first run: the answer is yes if three things hold. The mirror can be created with at most one documented setting. All ten sequential commits reach B's disk by sync on commit, each within 60 s. B's disk ends equal to A's.

## Measured values

| Measure | Run 1 | Run 2 | Run 3 |
|---|---|---|---|
| Sequential commits on B's disk | 10/10 | 10/10 | 10/10 |
| Time per commit to B's disk, min / median / max (ms) | 2754 / 2766 / 3346 | 2725 / 2735 / 3638 | 2702 / 2830 / 3419 |
| B's main branch and tree equal to A's at the end | yes | yes | yes |
| Burst: last of 10 commits on B after the last API answer (ms) | 187 | 48 | 184 |
| Burst commits added on B | 10 | 10 | 10 |
| `git push` to A, time until on B (ms) | 2044 | 1988 | 2137 |

The values below are from run 3 unless a run is named. Where earlier runs measured the same thing, they agree.

- **Creating the mirror.** With default settings: HTTP 401 "Permission denied", because the follower's address is a private IP. With only `[migrations] ALLOWED_DOMAINS=gitea-b`: HTTP 200, in all three runs. `ALLOW_LOCALNETWORKS` was not needed.
- **Where the mirror lives.**
  - In the database: one row in the shared table `push_mirror`. B's API lists it too (1 row).
  - On disk: the remote is in the git config of A's copy only (`url`, `mirror` and two `push` refspecs). Its URL carries the credentials.
  - B's copy has no remote, and the address stored in the database has no credentials.
- **Creating the mirror pushes nothing.** B's disk was still empty 10 s later. The first commit then carried the whole history.
- **Pull-request refs.**
  - A's disk had `refs/pull/1/head`. After the mirror ran, B's disk did not (runs 1 to 3).
  - The job's method did carry it (exit 0).
  - The next mirror run then removed it from B again (runs 2 and 3).
- **When the follower runs the shared row** (runs 2 and 3):
  - Asking B to sync returned HTTP 500. B logged `No such remote 'remote_mirror_…'` and set the row's `last_error` to "Unexpected error". A's next run reset it to empty.
  - The cron path behaved the same. B's mirror cron with the row due wrote "Unexpected error"; A's cleared it.
  - No branch head moved on either disk.
- **Gitea hooks on the follower's copy** (runs 2 and 3; webhook counts from run 3).
  - A's copy has Gitea's 4 hook files. B's copy, made by `reinit_missing_repos`, has 0.
  - With no hooks, B did nothing when it received a push. B made no mirror runs over the 20-plus commits. The webhook was sent by A only (A 1, B 0). The activity feed got 2 rows per commit, which is normal.
  - After `resync_all_hooks` on B (4 files), every commit still arrived (3621, 2754 and 2909 ms). But B now ran the mirror itself on each received push: 3 runs, all failed. Four seconds after each commit, the shared row read "Unexpected error". The webhook was sent by both A and B (3 and 3). The activity feed got 4 rows per commit instead of 2.
- **Repository created after set-up (r2).**
  - B had no directory for r2, yet the mirror was created (HTTP 200).
  - The first commit did not reach B within 30 s. A's row said "push failed: fatal: Could not read from remote repository".
  - After B's reinit task, the next commit arrived in 2476 ms (2341 and 2556 in runs 1 and 2). It also carried the earlier commit, and the row error cleared.
- **Side finding for CTL-050 (spike S1).** On Gitea 1.22.3, `POST /api/v1/admin/hooks` returned 201 but stored a row with repo_id 0, owner_id 0 and is_system_webhook false. That is a default webhook, not a system webhook:
  - It never fired for r1, which already existed: 0 deliveries during r1 commits in run 2.
  - It was copied into r2 when r2 was created (row 3, repo_id 2), and it delivered r2's commits.

## Outcome

push-mirror: yes

## What follows

These points are for decision record 0027 (CTL-800), which owns the region-loss contract.

1. **The mirror can replace the one-minute pull job** while the database is shared. A commit reaches the follower's disk in about 3 s, instead of up to 60 s plus the job's run time. It is not free; points 2 to 8 are the conditions.
2. **One setting.** The Gitea chart values gain `[migrations] ALLOWED_DOMAINS`, naming the follower's Gitea host as seen from the writer's region. Do not use `ALLOW_LOCALNETWORKS=true`. It is not needed, and it would let anyone import from any in-cluster address.
3. **Two steps for every repository, in this order.**
   - First, the follower creates the directory (its `reinit_missing_repos` task, or an equivalent).
   - Then the writer creates the mirror.
   - In the wrong order, a commit is not copied until the next commit after the directory exists.
   - Something must do this for each new repository: a call from the code that creates repositories, or a reconciler. Existing repositories need a one-time backfill. Today's job does this work by polling.
4. **Do not judge health from the row's `last_error`.** The follower writes its own failure into the shared row whenever it runs the mirror: through the API, through its cron, or on every received push once its copy has Gitea hooks. Judge health by comparing the writer's and the follower's branch heads. With any periodic interval, whichever region's cron reaches the row first runs it, and on the follower that run fails. We did not test whether an interval of 0 (sync on commit only) is accepted.
5. **Follower webhooks.** The follower's Gitea sends a webhook for a received push only if its copy has Gitea's hooks. Copies made by `reinit_missing_repos` have none. Today's job also pushes into copies made that way; we infer the same result for the job but did not measure it. If the follower's Flux is to be triggered by its own Gitea's webhook (CTL-130), there are two choices. Run `resync_all_hooks` on the follower after each reinit and accept point 4 plus doubled feed rows. Or trigger the follower's Flux another way.
6. **Pull-request refs are not copied.** A mirror run also deletes any that another method put on the follower. A follower promoted to writer would have pull requests whose head refs are missing from its disk. This matters to CTL-700 (pull-request mode) and to the promotion runbook.
7. **Promotion.** The mirror works in one direction only, and its remote exists only on the writer's disk. When the follower becomes the writer, each repository's mirror must be created again in the other direction, with its credential, and the old rows deleted.
8. **A comment in the public repo needs correcting.** The comment in `clusters/_template/sovereign-region/multi-region-follower/kustomization.yaml` gives two reasons against the push mirror. This test does not support either one on Gitea 1.22.3:
   - "Credentials are encrypted with each region's SECRET_KEY": the credential sits in the writer's repository config, and the mirror worked with two different keys.
   - "The follower's cron pushes its stale copy": the follower's run fails on the missing remote and pushes nothing.
   The package that replaces the job should correct the comment.
9. **CTL-050 and CTL-130.** On Gitea 1.22.3 the admin hook endpoint creates a default webhook, not a system webhook. Spike S1 should confirm this, and CTL-130 should not rely on that endpoint as written.

## Not measured in CI

- **Two real regions.** We could not test ClusterMesh routing from the writer to the follower's Gitea, the network policy that egress needs, or cross-region delay. Today only the follower has a stub Service for the writer, not the other way round. These all add time to the 3 s.
- **The database across regions.** In production the shared CNPG database is reached over the mesh. Here it was local to both Giteas.
- **The follower region's Flux Receiver** reacting to the follower's webhook. That belongs to S1, CTL-050 and CTL-130.
- **Also not covered:** region loss and promotion, long runs, large repositories, LFS, wikis, and Gitea versions after 1.22.3.

The first three need a two-region Sovereign, or two kind clusters joined by Cilium ClusterMesh in CI.

## What later tasks must take into account

What CI could not measure: the run used two Giteas on one Docker network, not two regions. Four things are still open: ClusterMesh routing from the writer to the follower's Gitea plus the network policy it needs (today only the follower has a stub Service for the writer); a shared CNPG database reached across the mesh; cross-region delay on top of the measured 2.7 to 3.6 s; and the follower region's Flux Receiver. Region loss, promotion and Gitea versions after 1.22.3 were not tested either. The first three need a two-region Sovereign, or two kind clusters joined by ClusterMesh. Everything else was measured in three green runs, and all three said yes.

What later packages must take into account:
- CTL-800 / record 0027:
  - The mirror needs `[migrations] ALLOWED_DOMAINS=<follower host>`; `ALLOW_LOCALNETWORKS` is not needed.
  - Every repository needs, in order, the follower directory (`reinit_missing_repos`) and then a mirror created on the writer. That means a caller at repository creation and a one-time backfill, so it is not zero code.
  - The shared row's `last_error` is unreliable: the follower writes "Unexpected error" whenever it runs the row. Monitor by comparing branch heads.
  - Pull-request refs are not copied, and mirror runs delete them on the follower.
  - On promotion, every mirror must be created again in the other direction.
- CTL-130 / follower Flux push trigger: the follower sends webhooks only if its copy has Gitea hooks, and copies made by `reinit_missing_repos` have none. Running `resync_all_hooks` fixes that, but then the follower also runs the mirror on every received push (failing each time) and the activity feed doubles.
- CTL-050 S1: on Gitea 1.22.3, `POST /api/v1/admin/hooks` stored a default webhook (repo_id 0, owner_id 0, is_system_webhook false), not a system webhook. It did not fire for existing repositories and was copied into new ones. CTL-130 as written relies on that endpoint.
- Public repo: the comment in `clusters/_template/sovereign-region/multi-region-follower/kustomization.yaml` gives two reasons against the push mirror that this test refutes on 1.22.3 (the SECRET_KEY encryption claim and the stale-copy push claim). Correct it when the job is replaced.

Branch `spike/CTL-055` is left in place as evidence, three pushes used of five: `.github/workflows/spike-ctl-055.yaml` and `tests/spikes/CTL-055/measure.sh`.

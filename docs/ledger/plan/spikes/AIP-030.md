# Lab test AIP-030: agent runtime proof (kagent 1.x on k3s, Cilium, vcluster)

Outcome: **fail**, on test T1 only. Date of the runs: 2026-11-14. The machine-readable values are in `docs/ledger/plan/spikes/AIP-030.yaml`.

## Question

Does kagent 1.x, with its Agent Substrate and the gVisor sandbox class, run once per Organization on the platform's cluster class (k3s with the platform's Cilium)? Does it run inside an Organization vcluster? Which node changes and which baseline-policy exceptions does it need? And do these work:

- the caller's bearer passed through unchanged to the model gateway and to the tool server `openova-mcp`;
- egress limits on the sandbox;
- a database credential without a Secret object;
- isolation of one install's API from the pods of other Organizations?

The tests are T1 to T11. T1 to T6, T9 and T10 are mandatory; T7, T8 and T11 are informative.

## Answer

- Agent Substrate v1.0 cannot run on the reference class as pinned today (k3s v1.31.8) nor on the planned 1.33 line. It needs the `certificates.k8s.io/v1beta1` PodCertificateRequest and ClusterTrustBundle APIs, which Kubernetes serves only from 1.35 and only with three feature gates on. T1 therefore fails on the reference class as it stands, and the outcome is **fail**.
- On k3s v1.35.10 with those gates and the platform's Cilium values, every other mandatory test passed in host namespaces: T3, T4, T5, T6, T9 and T10. T1's install and gVisor isolation work there with no node change beyond the Kubernetes version and gates. T2 passed only with six additions, one of them a paid feature of upstream vcluster avoided by a host-side WorkerPool.
- The design's "Actor pod with a gVisor RuntimeClass" does not exist: Actors run inside gVisor worker pods, with no node runtime binary and no RuntimeClass.

## What follows for the plan

1. **Kubernetes line.** The nodes are not moved to a newer Kubernetes line with beta gates for this alone. The platform's k3s line advances by its routine upgrade tasks, one minor version at a time (1.33, then 1.34, then 1.35). The sandbox class is offered on an installation when its line reaches 1.35 and the kit sets the three gates and the v1beta1 runtime-config. AIP-201 carries the gates as a condition, not as a change of its own; with vcluster placement every Organization vcluster's API server would need them too.
2. **Placement.** `host-namespace`: kagent runs in the Organization's host namespace, not inside its vcluster. Every mandatory test was measured there; the vcluster path needed six additions, one of them a paid upstream feature.
3. **Policy exceptions.** The Pod Security exceptions listed in the YAML record (the atelet's hostPath; the worker's capabilities, unconfined profiles and hostPath) are to be granted only to the substrate's own namespace by name, never to an Organization's namespace. The atelet already lives in `ate-system`. The worker does not: the WorkerPool is a namespaced object next to the Harness that names it, and its gVisor worker pod ran in each Organization's namespace (`org-a`, `org-b`, `org-v`; `pods.txt` of the run 4 artifact). Granting the worker's exception to the substrate's namespace alone therefore needs the WorkerPool, and so the worker, in that namespace, referenced from an Organization's Harness. That layout was not measured; it bears on AIP-031, AIP-201 and AIP-203. The worker Deployment is created by Substrate's controller, not by Flux: its exclusions from `flux-managed` and `harbor-proxy-pull`, and its requests through the WorkerPool template, are packaging work of the chart.
4. **Organization isolation in the shared substrate.** Every Organization's controller is a global owner in Substrate. Spike AIP-031 measures whether a controller can be limited to its own atespace. Until it passes, the agent runtime with the sandbox is planned for the Sovereign's own Organization only.
5. **Substrate is per cluster.** One `ate-system` per cluster holds the API, controller, identity provider, router, egress, credential provider, RustFS, the atelet DaemonSet, the certificate controller and its own database. Only kagent is per Organization.
6. **Runtime-issued identity.** The upgrade trigger for `actorJwt` is not met: one issuer per cluster and no agent-name claim. Keep tokens minted by catalyst-api with `tokenPassthrough`.

## What later tasks must take into account

- AIP-201 (node preparation): the list is the Kubernetes version and gates in `nodePreparation` of the YAML record, nothing else. No `runsc` binary, no containerd handler, no RuntimeClass, no sysctl.
- AIP-203 (`platform/kagent`): chart `oci://ghcr.io/kagent-dev/kagent/helm/kagent`, version 1.0.1, which meets the 30-day age rule from 2026-12-12 (the Substrate 1.0.0 charts from 2026-12-06). The chart needs a post-render patch so the controller reads its database URLs from a ConfigMap, with Pod Certificates as the credential, because the upstream chart insists on a Secret reference. It sets `global.watchNamespaces` to the Organization and carries the callers NetworkPolicy of T10.
- AIP-202 (host-side fence): the callers rule of T10 (ingress to the controller pods from `catalyst-system`, `ate-system` and the Organization's own namespace) is the measured shape.
- Callers of an agent (ops-records and others) speak A2A 1.0 JSON-RPC (`SendMessage`, `GetTask`, `CancelTask`, role `ROLE_USER`, text parts) at `http://kagent-controller.{organization}.svc.cluster.local:8083/agents/{organization}/{agent}`, where `{organization}` is the Organization's host namespace. The template was measured with the same release name in two Organizations.
- AIP-031: measures atespace-scoped grants for each Organization's controller.
- Not measured in CI, and what it needs: real reference-class nodes (operating system, kernel, AppArmor), more than one node, and a k3s upgrade of a kept cluster to 1.35 (a non-production Sovereign); the AIP-010 model gateway instead of the scripted backend, and agent tokens minted by catalyst-api (a throwaway RS256 token of the same claim shape was used); the local pack (gVisor needed no nested virtualisation on the runner, but the pack was not run, so the sandbox class is listed for `cloud` only); a global Service from a second region through replicated Services; kagent without global Substrate ownership; T5, T6, T9 with Pod Certificates and T10 under vcluster placement; behaviour after Substrate's one-year CA lifetime (upstream states the CA is never renewed); load beyond one worker and a handful of short turns; whether the existing `httproutes` custom-resource sync of the Organization renderer hits the same paid-feature check (only the WorkerPool entry was measured).

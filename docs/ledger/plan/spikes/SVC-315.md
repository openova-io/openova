# SVC-315 result: managed PostgreSQL through the cloud API on the National Cloud

Date: 2026-11-13, 06:44 to 07:01 UTC (17 minutes).
Where: a lab session against the live reference cloud, not CI. There is no CI run.

outcome: yes

## Question

Can the Sovereign's cloud account create, read and delete one managed PostgreSQL instance (the cloud's RDS for PostgreSQL) through the cloud API? What must the operator allow for that?

The design allows two outcomes. On yes, epic SVC-310 may start and CLD-222 may be scheduled. On no, the epic does not start and no postgres contract is written.

## What was run

- The account is the one the reference environment was installed with. Its access key and secret key were loaded into shell variables only.
- Read-only probes came first. They were signed REST calls (SDK-HMAC-SHA256) to the region's RDS, VPC and IAM endpoints.
- Then OpenTofu 1.12.0 ran with the provider `huaweicloud/huaweicloud` 1.91.0. That is the version in the lock file of the Huawei pack. The provider block overrode the `iam`, `vpc` and `rds` endpoints to the region's own hosts, the same way the pack's `main.tf` does for other services.
- OpenTofu created four things: a new VPC, a subnet, a security group with no rules, and one RDS for PostgreSQL instance. It then destroyed all four.
- In between, signed REST calls read the instance. They also created, listed, changed and deleted one database and one database account inside it.
- Every created name started with `nslab-svc-315-`. No existing resource was changed.

### 2. Create

| Call (made by the provider) | Answer |
|---|---|
| `POST /v1/{project}/vpcs` | 200, done in 6 s |
| `POST /v3/{project}/vpc/security-groups`, then 4 x `DELETE .../security-group-rules/{id}` (default rules) | 200, done in 1 s |
| `POST /v1/{project}/subnets` | 200, done after 1 min 56 s |
| `POST /v3/{project}/instances` (PostgreSQL 17, `rds.pg.c6.large.2`, `HIGH` 40 GB, single) | 202. Status `BUILD`, with a job id |
| `GET /v3/{project}/jobs?id={job}` (32 polls) | Job `CreatePostgresqlSingleHAInstance`: Running 12 %, 38 %, 62 %, 88 %, then `Completed` |

- The instance create was accepted at 06:49:56. The job completed at about 06:55:38. The provider reported "Creation complete after 5m56s" with status `ACTIVE`.
- About 110 s of the subnet time was spent elsewhere. The subnet set no DNS list, so the provider asked the public cloud's DNS service host for the region for default name servers. That host does not resolve. The provider logged "retries exhausted" and then created the subnet.
- Each time it starts, the provider also calls two hosts that fail:
  - the public Huawei billing host `bss.myhuaweicloud.com`, which answers 401 `APIGW.0301` "Incorrect IAM authentication information";
  - the region's IAM `/v3/auth/domains`, which answers 404 `APIGW.0101`.
  
  Both are logged as warnings, and the run went on.
- No call was refused for lack of rights.

### 3. Read

`GET /v3/{project}/instances?name=nslab-svc-315-pg` answered 200 with these fields:

- `type: Single`, flavor as requested, PostgreSQL 17, `complete_version 17.9.260200`, port 5432.
- Volume `HIGH`, 40 GB. Charge mode `postPaid`. Time zone UTC.
- `enable_ssl: true`. Admin user `root`. Maintenance window 18:00-22:00.
- Backup window 02:00-03:00, kept 1 day, as requested.
- One private IP, no public IP, and no private DNS name. Disk encryption off.
- Right after `ACTIVE`, the status became `BACKING UP`. That is the first automatic backup.
- The quota showed 1 of 50 used.

### 4. Database and account calls inside the instance (signed REST, 0.1 to 0.7 s each)

| Call | Answer |
|---|---|
| `POST .../instances/{id}/database` (name, `character_set UTF8`) | 202 `{"resp":"successful"}` |
| `POST .../instances/{id}/db_user` (name, password) | 202 |
| `POST .../instances/{id}/db_privilege` (database, user, `readonly false`, `schema_name public`) | 200 |
| `GET .../instances/{id}/database/detail` | 200. The new database (owner `root`, UTF8, collation C) and `postgres` (owner `rdsAdmin`) |
| `GET .../instances/{id}/db_user/detail` | 200. `root`: not superuser; has CREATEROLE, CREATEDB and REPLICATION. New user: login only |
| `POST .../instances/{id}/db_user/resetpwd` | 200 |
| `POST .../instances/{id}/password` (root password reset) | 200 |
| `DELETE .../instances/{id}/db_user/{user}` while its database still existed | 400 `DBS.01010378` "role ... cannot be dropped because some objects depend on it" |
| `DELETE .../instances/{id}/database/{db}`, then `DELETE .../db_user/{user}` | 202, then 202. The lists then show only `postgres` and `root` |

All of these calls were accepted while the instance was `BACKING UP`.

### 5. Delete

- `DELETE /v3/{project}/instances/{id}` answered 202, even during `BACKING UP`. The instance was gone from the list after 16 s, and the quota was back to 0 used.
- For about 2.5 minutes after that, the subnet and the security group could not be deleted. There were 41 refusals: 409 `VPC.0209` "subnet is still used" and 409 `VPC.0602` `SecurityGroupInUse`. The provider kept retrying. The cloud recorded the instance's final deletion at 06:59:34, and the network resources were gone at 06:59:41.
- Read checks after the destroy:
  - instance list by name: 0;
  - VPC: 404 `VPC.0105`;
  - subnet: 404 `VPC.0202`;
  - security group: 404 `VPC.9904`;
  - `DELETE` of the instance id: 404 `DBS.280022` "Selected instances not found".
- Recycle bin: `GET /v3/{project}/recycle-instances` shows one entry for the deleted instance. The entry holds one backup, created 7 s after the delete call, and is kept until 7 days later.
  - `DELETE /v3/{project}/recycle-instances/{id}` answered 404 `APIGW.0101`.
  - `DELETE /v3/{project}/backups/{id}` answered 400 `DBS.201214` "The backup file does not exist".
  - There is no published call that purges the entry. It ends when the retention ends. Retention is a project-wide setting, and it was not changed.

## Outcome

**yes.** With the account of the reference environment, a managed PostgreSQL instance was created, read and deleted through the cloud API. Its databases, accounts, privileges and passwords were managed through the same API. No call was refused for lack of rights.

## What the operator must allow

- For the account that was tested: nothing more. It passed every call needed to create and delete RDS instances, databases and accounts, and VPCs, subnets and security groups.
- The minimum role set is not measured, because the IAM read APIs are not published (`APIGW.0101`). A narrower account would need, at least, RDS create, read and delete on the project. It would also need to use the VPC, subnet and security group the instance joins.
- RDS instance quota for the instances wanted. The project has 50.
- A network path from where the module runs to the region's RDS endpoint.
- The recycle-bin retention. A deleted instance's backup stays for 7 days under the current project setting, and the API cannot purge it. The operator owns that setting.

## What follows for the plan

- Epic SVC-310 may start, and CLD-222 may be scheduled.
- SVC-330 sets `spec.services.postgresinstances` to `available: true` for the Huawei pack. Its reason cites this record.
- For CLD-222 (`day2/postgresinstance`):
  - add an `rds` endpoint override to the provider's `endpoints` block. The pack lists `iam`, `ecs`, `vpc`, `evs`, `ims`, `obs`, `elb`, `tms`, `kms` and `nat`, but not `rds`;
  - set a DNS list on any subnet the module creates, so the provider does not lose about 2 minutes on the public DNS host;
  - expect about 6 minutes to create an instance. Deleting the instance takes about 16 s, but the network stays held for about 3 minutes, so teardown must retry on `VPC.0209` and `VPC.0602`;
  - check a version against the flavor list, not the datastore list. Version 16 is listed but has no flavor. Use 17 (or 13 to 15).
- The endpoint of an instance is a private IP with port 5432. There is no private DNS name. The binding must carry the address.
- TLS is on by default. The admin user `root` is not a superuser.
- The `databases[]` Contexts can be made through the RDS API without SQL: database, user, privilege and password reset. A user can be dropped only after its database.
- The root password and user passwords can be reset through the API.
- Deleted instances leave a backup in the recycle bin for 7 days. Data-deletion promises must say so.

## What later tasks must take into account

Outcome yes: the account of the reference environment created, read and deleted one RDS for PostgreSQL 17 instance through the cloud API, with no extra rights. The work used signed REST calls plus OpenTofu with the pinned huaweicloud provider 1.91.0, and took 17 minutes. Later tasks must take these into account:
(1) The Huawei pack's provider block has no rds endpoint override. CLD-222 must add one.
(2) A subnet with no DNS list makes the provider retry the public cloud's DNS host for about 110 s.
(3) Creating an instance takes about 6 minutes. Deleting it takes 16 s, but the subnet and security group stay in use for about 2.5 more minutes (409 VPC.0209 and VPC.0602), so teardown must retry.
(4) PostgreSQL 16 is listed but has no flavor. Use 17.
(5) The instance has a private IP only and no private DNS name. TLS is on. The admin user root is not a superuser.
(6) Databases, accounts, privileges and password resets all work through the RDS API. Drop the database before its user (otherwise DBS.01010378).
(7) A deleted instance leaves a recycle-bin entry with one backup for 7 days (a project-wide policy). No published API purges it: APIGW.0101 and DBS.201214.
(8) The IAM read APIs are not published (APIGW.0101), so the minimum role set was not measured.
(9) At every start the provider calls the public billing host (401 APIGW.0301). Its effect when egress is blocked is not measured.
(10) Another lab's VPC (nslab-net-290-vpc, not mine) now uses the 4th of 5 VPCs in the project. A later lab that needs a VPC may hit the quota.
Not measured: placement in a Sovereign's own VPC with a connection from a pod, the HA and replica flavors, and behaviour after cutover.

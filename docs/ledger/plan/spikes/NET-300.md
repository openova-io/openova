# NET-300: Region separation on the reference cloud (lab test result)

Date: 2026-11-13. Type: lab test, read-only. Result line: **NONE**

## Question

Does the reference cloud give the project a second availability zone, or a second site with its own endpoints? Is there a private link between them?

Two sources disagree. The provider module says the region has one zone (`infra/providers/huawei/versions.tf`, and `huawei_az` in `variables.tf`). The `Sovereign` kind says the region exposes zones a, b and c (`products/catalyst/chart/crds/sovereign.yaml`, field `az`). This test measured what the account can see.

## What was run

- Signed REST calls (AK/SK, SDK-HMAC-SHA256) to the region's public API gateway. They ran on 2026-11-13 from 06:45 to 06:50 UTC.
- The account is the one the live two-region Sovereign hw307 was installed with. The credentials were loaded into the shell only for each call.
- Only GET calls were made. Nothing was created, changed or deleted. A final read found nothing with the test prefix.
- DNS queries for other region names went to the public resolver and to the authoritative name server of the cloud's domain.

## Other measured facts

- Storage disaster recovery (SDRS) is not published (404 `APIGW.0101`).
- These services are published and empty: backup vaults (CBR), VPC endpoints, managed Kubernetes (CCE) and DNS.
- The compute flavors say `operate:live_migrate_supported: true`. A live migration can move a server to another host, so H1 is one reading at one moment.
- The public resolver failed some lookups during the run ("Temporary failure in name resolution", and timeouts on names that do not exist). Retries worked. The authoritative server answered every time.
- The module comment was right. The `Sovereign` kind's text about zones a, b and c is wrong for this account, because zones b and c are refused.

## What is left

- This run did not send the written question to the operator. The account cannot list its regions, because IAM is not published at the gateway. So the API cannot rule out a second site with other endpoints, or one under another account. The question needs the founder's channel to the operator: "Is there a second availability zone or a second site for this account, and a private link between them?" If the answer names a second site with its endpoints, the outcome becomes SITE.
- Anti-affinity was not tried. To test whether the scheduler keeps the servers of an anti-affinity group apart (or uses the fault-domain feature the quota hints at), two small VMs in one group are needed. This question did not need them.

## What follows for the plan

- The outcome is **NONE**. Every multi-region record on this cloud stays labelled "one failure domain". No disaster-recovery claim is made for this cloud.
- The provider module gets no second provider configuration. The one-zone default of `huawei_az` stays.
- NET-210 and NET-212: the record's `zone` field shows the same zone for every region. The gate must never count two regions here as separate failure domains.
- The `az` description in the `Sovereign` kind should be corrected. It names zones b and c, which this account refuses.
- Within one zone, the only separation left is between hosts, and today it is not used. The two regions share a host. Region b's control plane shares a host with 3 of its workers. A follow-up package should place each region's nodes in an anti-affinity server group (at most 7 per group) and test it.
- A database "ha" flavor on this cloud stays in one zone. Its standby does not survive the loss of the zone.

# SEC-271 result: the policy engine verifies a signature with no public log

Outcome: **Q1 YES, Q2 YES, Q3 NO.** The two YES answers each need a setting that the design does not name yet.

| Question | Answer | Condition |
|---|---|---|
| 1. The installed engine verifies a key-signed image with no route to a transparency log | YES | The engine needs a local TUF mirror and the policy needs a log URL. As the platform ships the engine today, the answer is NO. |
| 2. The engine reads signatures from the Sovereign's own registry | YES | The image name must point at the own registry. A CEL rewrite in the policy can make it do so. `source.repository` alone does not work. |
| 3. The closure copy carries the signature artifacts | NO | Measured in the lab and on the running reference Sovereign. One setting of the copy tool fixes it. |

## The question

Can the engine the platform already runs check a release-key signature at admission when the Sovereign cannot reach any public sigstore service? The plan asked three things:

1. Does the engine verify a key-signed image that has no log entry, with no route to a log? Which field turns the log check off?
2. Can the engine read the signatures from the Sovereign's own registry?
3. Does the closure copy (the harbor-prewarm step of the cutover) carry the signature artifacts into the own registry?

It also asked for the list of image references.

## What was run

- **Where.** The reference cloud (Huawei Cloud Stack, the region of the provider module), in the project the reference Sovereign was installed with. Everything was created with OpenTofu and deleted at the end.
- **Machine.** One VM, 2 vCPU and 4 GB (flavor s7n.large.2), Ubuntu 22.04. It had its own network and security group.
  - Inbound: SSH from one host only.
  - Outbound: the metadata service only.
  - There was no Internet egress at any time. Every binary and image was copied in over SSH.
- **Cluster.** k3s v1.31.4+k3s1, single node. This is the platform's k3s pin.
- **Engine.** Kyverno chart 3.8.0 with app v1.18.0, the same version the reference Sovereign runs. Only the admission controller ran, as one replica.
  - The registry CA came from `admissionController.caCertificates.data`.
  - The verification cache was off (`--imageVerifyCacheEnabled=false`), so every result is a fresh check.
- **Registries.** Two distribution registry 2.8.3 instances with TLS and a private CA, and no authentication:
  - "origin" stands in for ghcr.io;
  - "own" stands in for the Sovereign's registry.
- **Signing.** cosign v2.4.1, `sign --key <throwaway key> --tlog-upload=false`. FND-061 had not delivered a release key, so the lab used a throwaway one.
- **Test images.** All three are busybox 1.36 (amd64) under `<origin>/openova-io/openova/`:
  - `lab:1`, signed with the release key;
  - `lab-unsigned:1`, not signed;
  - `lab-otherkey:1`, signed with a second key.
- **Closure copy.** The cutover's own copy command: skopeo v1.15.2 (the same static build), `copy --insecure-policy --retry-times 5 --multi-arch all`, with TLS verification on.
- **Policies.**
  - `ImageValidatingPolicy` of API `policies.kyverno.io/v1`, action Deny, on pod CREATE. The rule was `images.containers.map(i, verifyImageSignatures(i, [attestors.release])).all(e, e > 0)`.
  - The legacy `ClusterPolicy` with `verifyImages` was run as a comparison.
- **The measurement.** Each test created one pod and recorded whether admission allowed or denied it, the time it took and the engine's message.
- **Live probe.** Read-only. Image references were read from the running reference Sovereign (both regions). Signature tags were read from ghcr.io and from its own registry.

## Measured values

### No route (lab)

- Name lookup for rekor.sigstore.dev failed.
- curl to the Rekor, the sigstore TUF CDN and ghcr.io exited with code 6 (no name resolution).
- curl to an Internet address timed out (exit 28).
- `cosign sign --key ... --tlog-upload=false` worked with no route: exit 0, under 1 s. The signature tag `sha256-<digest>.sig` appeared in the origin.
- The cosign CLI:
  - `verify --insecure-ignore-tlog=true` gave exit 0;
  - `verify` without that flag gave exit 1 after 8 s: "getting Rekor public keys ... error updating to TUF remote mirror".

### Q1: the engine as the platform ships it (TUF off, no mirror): NO

- The policy had `ctlog.insecureIgnoreTlog: true` and `insecureIgnoreSCT: true`. The signed image was denied after 8.1 s.
- The engine log: "failed to build cosign verification opts: Failed to initialize TUF client ... failed to download 13.root.json ... lookup tuf-repo-cdn.sigstore.dev".
- The same result came with no `ctlog` block at all, with `rekorPubKey` set, and with both `rekorPubKey` and `ctLogPubKey` set.
- The unsigned and wrong-key images were denied for the same reason, so no real check took place.

### Q1: the engine with a local TUF mirror and a log URL: YES

- **The mirror.** A local HTTP copy of the public sigstore TUF repository: root versions 1 to 16, timestamp, snapshot, targets and 11 target files, 200 KB in all.
  - Engine flags: `--enableTuf=true --tufMirror=<local URL>` (chart `features.tuf.enabled`, `features.tuf.mirror`).
  - With the mirror only, the error changed to "getting Rekor public keys: rekor URL must be provided".
- **Mirror and log URL.** `ctlog.url` was also set, to the public Rekor URL, which the VM could not reach. The results:
  - the signed image was allowed in 169 ms;
  - the unsigned image was denied ("no signatures found");
  - the wrong-key image was denied ("invalid signature when validating ASN.1 encoded signature").
- **Control.** The same policy with the mirror switched off was denied after 8.2 s with the TUF error.
- **The fields in Kyverno 1.18.0.** The log check is switched off by `spec.attestors[].cosign.ctlog.insecureIgnoreTlog: true`. A key-only check also needs:
  - `ctlog.insecureIgnoreSCT: true`;
  - a non-empty `ctlog.url`;
  - the two engine flags above.
- **Mirror traffic.** Each check fetched `timestamp.json` again and probed for the next root version: 13 checks gave 13 fetches and 13 "not found" answers for root 17.
- **Expiry.** The copied timestamp expired six days after the copy. What happens after it expires was not measured.
- **Legacy rule.** The legacy `ClusterPolicy` `verifyImages` rule of the same engine was run with `rekor.ignoreTlog: true` and `ctlog.ignoreSCT: true`, and with no mirror and no route:
  - the signed image was allowed in 135 ms and pinned to its digest;
  - the unsigned image was denied ("no signatures found");
  - the wrong-key image was denied ("invalid signature").
  - It never contacted TUF.
- **Digest pinning.** The ImageValidatingPolicy left the image as a tag. It did not pin the digest.

### Q2: signatures read from the own registry: YES, with a rewrite

- **The image name points at the own registry, and the signature is there.** Allowed: 157 ms with the policy, 111 ms with the legacy rule.
- **The image name points at the origin, and the origin is unreachable.** This stands in for ghcr.io after the egress block.
  - Plain policy: denied in 95–107 ms. "dial tcp ... connection refused" at the origin. The engine resolves the tag at the registry the name points at.
  - `source.repository` pointing at the own registry: denied with the same error. The tag is resolved at the origin before signatures are read.
  - The legacy `repository` field: denied with the same error.
  - A CEL `images` extractor that rewrites the origin host to the own host, with the glob on the own host:
    - the signed image was allowed in 167 ms;
    - a copy with no signature was denied;
    - an image missing from the own registry was denied ("manifest unknown").
- **Globs.** `<host>/openova-io/*` matched `<host>/openova-io/openova/<name>:<tag>`: the engine ran verification for it. The `*` crosses path segments.

### Q3: the closure copy: NO

- **Lab.** The prewarm command copied `lab:1` with the same digest. The own registry then held tags `['1']` and no `sha256-<digest>.sig`. The engine denied it ("no signatures found").
- **Variant.** The same command with `use-sigstore-attachments: true` in `/etc/containers/registries.d` also copied the signature tag. The own registry held `['1', 'sha256-<digest>.sig']`, and the cosign CLI and the engine both accepted it.
- **Live, read-only, on the running reference Sovereign.** Seven images were in its own registry with the same digest as on ghcr.io. ghcr.io holds a signature for each of them. The own registry holds a signature for none of them (0 of 7). Three repositories in the own registry held 0 signature or attestation tags among 16, 3 and 25 tags. On ghcr.io the same repositories hold 81, 44 and 6 `.sig` tags.

- **Network quota.** The project's VPC quota is 5. All 5 were in use at start (the environment 2, the bastion 1, two parallel lab tests 2). Creation was refused with "The request could not be processed due to conflict in the request" for 7 minutes, until a parallel test released one.

## What follows for the plan

1. **SEC-272 cannot ship the policy as drafted** (a key plus the log switch only). On a Sovereign with no route to the public sigstore mirror, it fails every platform image after about 8 s. The policy needs:
   - `ctlog.insecureIgnoreTlog: true`, `ctlog.insecureIgnoreSCT: true` and a non-empty `ctlog.url`;
   - the engine values `features.tuf.enabled: true` and `features.tuf.mirror` pointing at a mirror inside the Sovereign.
2. **The mirror is a copy of public sigstore metadata.** It must be served at every check, and its timestamp expires after about a week, so something must refresh it. The other choice is the legacy `verifyImages` rule, which works with no mirror. Which one to use is the area owner's decision.
3. **SEC-272 is blocked by Q3.** It may start only when the closure copy carries signatures. The measured fix is one line for the cutover's copy: `use-sigstore-attachments: true` in the skopeo registries.d configuration. That change belongs to the Sovereign-lifecycle area.
4. **The policy must rewrite origin names.** On a cut-over Sovereign many pods still name ghcr.io, and the engine resolves tags there. The policy needs a CEL `images` rewrite from each origin host to the own registry host, with its globs on the own registry name. The values default `ghcr.io/openova-io/*` covers both ghcr shapes but not the own registry name.
5. **Q1 does not drop SEC-272 to SEC-274.** The answer is YES with conditions, not NO.

- Multi-arch index images. Only a single-arch image was used.

**Facts later packages need:**
- Today's ghcr.io signatures are keyless, made in CI with a Rekor entry, and exist only for some images. No release public key was in the repository when this ran.
- Images built for one Sovereign by the overlay path (tags `<env>-<sha>`) exist only in the own registry and carry no signature.
- The Kyverno chart silently drops a boolean false in `extraArgs`. `--set ...imageVerifyCacheEnabled=false` rendered no flag; `--set-string` worked.
- Parallel lab tests compete for the project's 5 VPCs and 10 elastic IPs. Plan for waits, or run fewer labs at once.

## What later tasks must take into account

SEC-272 needs a different policy and engine setup from the draft:
- Policy fields: `ctlog.insecureIgnoreTlog`, `ctlog.insecureIgnoreSCT` and a non-empty `ctlog.url`.
- Engine values: `features.tuf.enabled=true` and `features.tuf.mirror` pointing at a TUF mirror inside the Sovereign.
- The mirror must be served at every check and refreshed about weekly, because its timestamp expires.

The legacy verifyImages rule works offline with no mirror, if the owner prefers it.

SEC-272 may not start until the Sovereign-lifecycle area makes the cutover's skopeo copy carry signatures. One line was measured to do it: `use-sigstore-attachments: true` in registries.d. Today 0 of 7 copied images on the live Sovereign carry their ghcr.io signature.

The policy must also:
- rewrite origin host names (ghcr.io) to the own registry name with a CEL `images` extractor, because `source.repository` alone fails when the origin is unreachable;
- glob on the own registry name;
- give the engine a credential for the own registry, which refuses anonymous reads. This was not measured.

Image patterns:
- `ghcr.io/openova-io/openova/*`
- `ghcr.io/openova-io/*` (agenity, chargeback, chargeback-docrender, openova-mcp)
- `registry.<sovereign-domain>/openova-io/openova/*`

Not measured: Harbor, registry authentication, mirror expiry, multi-arch indexes, the Audit action.

Process: one scratch error file was briefly written under /tmp during the read-only probe and deleted at once.

# NET-330 result: a bridged secondary network for virtual machines beside Cilium

- Date: 2026-11-19. Three CI runs from 12:02 to 14:14 UTC; the measured run is 44534812384, whose lab step ran from 13:58 to 14:13 UTC.
- Where: GitHub Actions, a hosted runner (kernel 7.0.0-1019-azure, 4 vCPU, 15983 MiB, `/dev/kvm` present). The local provider pack `infra/providers/local` with one region: a control-plane machine and one worker machine, so two nodes. k3s `v1.31.8+k3s1` and Cilium 1.19.3 with the values of the shared boot template, and the reduced kit installed by Flux. The reference pack `huawei` was not used: its nodes expose no `/dev/kvm` (INF-020), so no virtual machine can run there.
- **Outcome: `attachment: BESIDE-WITH-CHANGE`, `address: KEPT-IF-PINNED`, `policy: NONE`.** A bridged second network attaches beside Cilium only after Cilium's `cni.exclusive` is set to `false`. A virtual machine keeps its MAC and its IP on it across a live migration to the other node; across a stop and start it keeps its MAC only when its spec names the MAC. Neither a NetworkPolicy enforced by Cilium nor the MultiNetworkPolicy agent stops traffic to a virtual machine on that network.

## Question

How does a second, bridged network sit beside the pod network on the reference class (k3s, Cilium 1.19.3 in native routing with WireGuard and kube-proxy replacement)? Does a virtual machine keep its address on it? What policy covers it?

## Outcome words

The plan left them to this package. They are fixed here.

- `attachment`: `BESIDE` when a NetworkAttachmentDefinition gives a pod and a virtual machine a second interface on a node bridge while the pod network stays as it is; `BESIDE-WITH-CHANGE` when that holds only after a named change to the platform's Cilium values; `NONE` when it does not hold.
- `address`: `KEPT` when the machine's MAC and IP are the same after a live migration to another node and after a stop and start, and a peer on the network reaches that IP at that MAC; `KEPT-IF-PINNED` when that holds for the MAC only if the VirtualMachine spec names it; `LOST` otherwise.
- `policy`: `CILIUM` when a NetworkPolicy enforced by Cilium also stops traffic on the second network; `OTHER` when Cilium does not and a named second mechanism does, measured; `NONE` when no mechanism measured stops it.

## Measured values

**Beside the pod network.**
- With the template's values Cilium runs with `cni-exclusive=true`. Before Multus the CNI folder of each machine held `05-cilium.conflist` only, and `/opt/cni/bin` held `cilium-cni` and `loopback` only. `containerd`'s configuration names no CNI folder, so it reads `/etc/cni/net.d` and `/opt/cni/bin`.

## What the source and documentation say (read, not measured)

- Cilium 1.19.3: `cni.exclusive: true` is the chart default (https://github.com/cilium/cilium/blob/v1.19.3/install/kubernetes/cilium/values.yaml line 798). When it is true the agent watches the CNI folder and renames every other `.conf`, `.conflist` or `.json` file to `*.cilium_bak` (https://github.com/cilium/cilium/blob/v1.19.3/daemon/cmd/cni/config.go lines 202 to 243 and 455 to 490). `platform/cilium/chart/values.yaml` and the boot template's `cilium-values.yaml` (`infra/providers/_shared/cloudinit-control-plane.tftpl` lines 392 to 464) do not set it.
- KubeVirt user guide (https://github.com/kubevirt/user-guide/blob/4d7860dcec4827fd7fbc6f6fad2323e8a0f19e44/docs/network/interfaces_and_networks.md): live migration is not allowed with `bridge` binding on the pod network; with `masquerade` a migrated or restarted machine has a different pod address; the `bridge` plugin has a `macspoofchk` setting.
- KubeVirt to Kubernetes support (https://github.com/kubevirt/sig-release/blob/main/releases/k8s-support-matrix.md, read 2026-11-19): Kubernetes 1.31 is listed only for KubeVirt 1.4, 1.5 and 1.6, all marked end of life for it; 1.7 starts at 1.32, 1.8 at 1.33, 1.9 at 1.34. The stable KubeVirt is v1.10.0 (`stable.txt` of the release bucket). The reference class runs k3s `v1.31.8+k3s1`.
- multi-networkpolicy-iptables: `--network-plugins` defaults to `macvlan` (`pkg/server/options.go` line 76 at the commit above); the repository has no release tag.
- The `huawei` pack gives every server one network card, with `source_dest_check = false` (`infra/providers/huawei/main.tf` lines 1558 to 1566 and 1636 to 1641). Its security group admits all UDP from every region's node subnet and pod range (`ingress_pod_cidr_udp` over `mesh_ingress_cidrs`, lines 230 to 233 and line 683), so VXLAN on port 4789 between node addresses would pass it. Not measured: no virtual machine runs on that pack (INF-020).

## What later tasks must take into account

- **No package of the plan builds the second network.** INF-820 waits for it and MIG-201 and MIG-202 depend on it. The package that builds it holds: `cni.exclusive: false` in `platform/cilium/chart/values.yaml` and in the boot template's `cilium-values.yaml` (the template installs Cilium before Flux holds it, so both must say it, or the first boot renames the Multus file again), knowing that Cilium then no longer clears foreign CNI files; a Multus thick Blueprint; the `bridge` and `static` plugins on every node, which k3s does not put in `/opt/cni/bin`; a node bridge and its uplink per pack, a second card or VLAN (underlay A) or VXLAN between node addresses (underlay B); the MTU of the segment written into each NetworkAttachmentDefinition (`"mtu"`), since a 1500-byte interface on a 1450-byte VXLAN segment loses large frames; and what covers the network, below.
- **INF-810** (`bp-kubevirt`, `bp-cdi`). No maintained KubeVirt release lists Kubernetes 1.31: either the reference class moves to a Kubernetes version a maintained release supports, or the Blueprint pins KubeVirt 1.6, whose support for 1.31 has ended. It still needs `/dev/kvm`, which the `huawei` pack lacks (INF-020).
- **INF-820** (Composition `virtualmachine-kubevirt`). It keeps refusing `network.privateAddress` until the package above merges. When it maps the field, it writes the MAC into the interface (`macAddress`), or the MAC changes at every start (`vm2`), and it writes the IP into the guest's cloud-init: with `ipam: {}` the cluster neither assigns nor reports it.
- **INF-830** (gate check INF-G10). On the local pack every live migration between two machines of one runner fails with "Attempt to migrate guest to the same host" unless each launcher gets its own host UUID, as step 6 did. A check that migrates there needs that, or a pack whose nodes are separate hosts.
- **MIG-200, MIG-201, MIG-202** (Forklift route `kubevirt`, NetworkMap destination type `multus`). The destination maps to a NetworkAttachmentDefinition of type `bridge` like `l2` above. The MAC survives a live migration and survives a restart only when the spec names it. Measured loss per successful live migration: 0.6 s and 8.2 s; one failed attempt lost 33.4 s.
- **NET-150, NET-160 and NET-090** (default deny and its guards). Cilium's policy does not reach the second network: a namespace whose virtual machine sits on it is open there whatever its NetworkPolicy says, and the dial rows of the policy chart must not claim that network. The MultiNetworkPolicy agent covers pods on it but not virtual machines with `bridge` binding.
- **NET-050** (decision record 0019, node encryption). Frames on the second network cross between nodes unencrypted, outside WireGuard, in both underlays. Decision record 0019 names it as an exception or requires an encrypted uplink.
- **Repeat** the lab on the first pack whose nodes expose `/dev/kvm` and have a real second card or VLAN, before INF-820 maps `privateAddress`.

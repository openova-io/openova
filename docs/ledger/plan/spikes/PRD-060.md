# PRD-060 result: vector search with row-level trimming on the platform's PostgreSQL

Date: 2026-11-13
Extension tested: `vector` 0.8.6 in the chart's image (PostgreSQL 16.15)
Evidence branch: `spike/PRD-060` in openova-io/openova. It is never merged.

## Summary

| Check | Result |
|---|---|
| Extension in the chart's image | Present: `vector` 0.8.6. Iterative index scans work. Not outcome B. |
| Search as designed, reader through source grants | Recall at 10 is 0.926. Warm p95 is 70 ms. Fails on recall. |
| Search as designed, reader through per-document lists | Recall at 10 is 0.926 to 0.929. Warm p95 is 419 to 434 ms. Fails on recall and latency. |
| Repeat with `chunk` partitioned by source, source reader | Recall at 10 is 0.9985. Warm p95 is 7.7 ms. Holds. |
| Repeat with `chunk` partitioned by source, per-document reader | Every query hit the 30 s timeout. EXPLAIN ANALYZE took about 67 s per query. Fails. |
| Chart's default instance size (500m CPU, 512 MiB) | p95 is about 3.0 s (source reader) and 3.5 s (per-document reader). The index does not fit in memory. |

The design's search fails the bar (recall at 10 of at least 0.95 and p95 under 200 ms), so the outcome is C. The one repeat with `chunk` partitioned by source holds for readers who get access through source grants. It fails for readers who get access only through per-document reader lists. Under the outcome rule, the lead architect therefore reopens the decision to keep vectors in the platform's PostgreSQL. The measured cause of the remaining failure is row-level security, not vector search. This narrows what reopening that decision has to solve (see "What follows for the plan").

## The question

1. Does the PostgreSQL image that the platform chart pins carry the `vector` extension at a version with iterative index scans (0.8.0 or later)?
2. Does the store's trimmed search hold recall at 10 of at least 0.95 against an exact scan, with p95 latency under 200 ms? The test conditions are one million chunks of 1,024 dimensions and a principal that reads one percent of documents. The search is the transaction as designed: principals set as a transaction setting, `hnsw.iterative_scan = relaxed_order`, source filter, `ORDER BY` cosine distance, `LIMIT 10`, all values bound. It runs as the query role under forced row-level security.
3. Outcome C: does it hold after partitioning `chunk` by source and repeating once?

**Repeat with `chunk` partitioned by source (run 2)**

- Build: filling the 1,000 partitions and building their indexes took 170.5 s in 4 sessions (0.4 s per partition index). All 1,000 HNSW indexes attached to the parent index. Total size 13.4 GiB, of which 7.63 GiB is HNSW.
- **p1:** recall at 10 was 0.9985 (lowest 0.8). Pass 1 p95 was 12.0 ms. Pass 2 p50 was 6.8 ms and p95 7.7 ms. No rows were out of order. Plan: `Limit -> Merge Append ->` 10 partition index scans.

**Policy checks (both runs)**

- The chunk policy's body reused on `document` gives a policy on `document` that reads `document` itself. Any read of `document` or `chunk` then fails with `infinite recursion detected in policy for relation "document"`.
- A `document` policy that tests the row's own columns works and returns the expected rows.
- An empty principal list returns 0 rows.
- A session without the setting fails with `unrecognized configuration parameter "cortex.principals"`.

## What follows for the plan

- **Not outcome B.** The chart's image carries `vector` 0.8.6, which has iterative scans. No image request is needed today. The tag `16` is floating, so a later image could carry another version. The store should check `extversion` (0.8.0 or later) at start and fail visibly.
- **Outcome C, and the repeat fails for one reader shape.** As written on one table, the search misses recall for both readers. The extra settings do not lift the source reader to 0.95; the best was 0.9425, from fetching 40 and re-sorting. Partitioning by source fixes source-scoped reads completely (0.9985 at 7.7 ms). Readers who have only per-document grants spread over many sources fail in both layouts. The rule then says the lead architect reopens the decision to keep vectors in PostgreSQL. The measured cause should frame that review:
  - The per-document reader's cost is row-level security, not the vector index. On one table, the planner hashes the chunk policy and scans every document on every query: about 370 ms that grows with the document count. On the partitioned table, it checks the policy on about 137,000 rows.
  - A dedicated vector store would need the same one-percent document filter, in its own filter language. Moving vectors only helps if that store can filter a small document set cheaply.
  - Two other ways out stay on PostgreSQL. Neither was measured as a whole. (1) Partition by source for source-granted reads, and give readers with only per-document grants a separate path over their few documents. The exact plan here took 0.5 to 1.3 s for about 10,000 rows, so that path would need a cheaper row check. (2) Use a policy form whose row check the planner cannot hash.
- **For the store package (PRD-202), whichever way the review goes:**
  - The `document` read policy must test the row's own columns. A policy on `document` that reads `document` fails with infinite recursion (measured).
  - `SET LOCAL hnsw.iterative_scan` is required. Without it, 99.6% of one-percent queries return fewer than 10 rows.
  - `relaxed_order` returns rows out of distance order in about one query in three. The store must re-sort. Fetching 40 and re-sorting cost about 45 ms more at p95 for p1.
  - The trimming never leaked a row in about 13,000 measured searches.
- **Sizing.** One million 1,024-dimension chunks take 13.3 GiB, of which 7.6 GiB is the HNSW index. With the chart's default 500m CPU and 512 MiB, p95 is about 3 s, because every search reads the index from disk. The first pass after a build on the runner was already 400 to 456 ms at p95. The PostgreSQL that holds this product's chunks needs memory for its index (about 8 GiB per million chunks of this size), not the chart default.

## What later tasks must take into account

Everything above was measured in CI. These were not, and they need a Sovereign with the product, about one day:

- An instance managed by CloudNativePG, with the operator's GUCs and the platform's real cloud volumes. Latency from disk differs from the runner's local disk.
- Concurrent searches, and searches during index inserts. All runs used one client, and the index was built in bulk after the load.
- The embedding model PRD-080 chooses. Recall depends on how its vectors are distributed. A public 1,024-dimension multilingual model was used here.
- Grants that follow topic. Here sources and per-document lists were assigned by hash, so a reader's documents are spread at random through the vector space.

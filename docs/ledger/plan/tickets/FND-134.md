# FND-134 — A conformance run runs the pull request's own catalyst-api image

## In plain words

**The problem today.** The conformance run of a pull request installs the kit charts of that pull request, but it always runs the catalyst-api image that was published from main. A pull request that changes the API and adds a check of that change fails its own run, because the pack runs an API without the change; a first such pull request failed exactly this way.

**What changes.** When a pull request changes a source of the catalyst-api image, its conformance run builds that image from the tree, loads it into every machine of the pack, runs it, and names the image it ran by digest. A pull request that changes this path builds and runs the image of its own tree, so the path is proven before it merges.

**Done means:**

- The local pack prints, from the source, whether the catalyst-api image of a run comes from the tree or is the pinned one, and which changed path made it come from the tree.
- A changed file of the Containerfile of catalyst-api, or in a folder that it copies, takes the image from the tree; a file beside those folders keeps the pinned image.
- A run with the image of the tree builds it without pushing it, loads it into every machine of both regions under one digest, and passes only when every catalyst-api pod of the primary region runs that digest.
- The log and the job summary name the image the API ran, with its digest, or the pinned image and the image id it ran as.
- A pull request that changes the pack script or the conformance workflow builds and runs the catalyst-api image of its own tree.
- A pull request that changes no source of the image runs the pinned image, as before.

The rest of this ticket is the exact instruction for the model that does the work.

## 2. End goal
The job `conformance-local` of a pull request or a merge group that changes a path the catalyst-api image is built from builds that image from the tree of the commit under test, never pushes it, loads it into the containerd of k3s on every machine of the local pack, and makes the console release `bp-catalyst-platform` run it; the job passes only when every pod of the Deployment `catalyst-system/catalyst-api` of the primary region reports the digest of that image as its imageID. The paths are read from the Containerfile `products/catalyst/bootstrap/api/Containerfile`, which `.github/workflows/catalyst-build.yaml` builds with the root of the tree as its context: the Containerfile itself and every source it copies from that context. A pull request that changes none of them runs the pinned image, as today, and the run names that image and its imageID. A pull request or merge group that changes `scripts/local-pack.sh` or `.github/workflows/conformance-local.yaml` also lists the Containerfile among its changed paths, so its own run builds and runs the image of its tree. This is the pattern of FND-133 for kit charts, applied to the image of the API. A person sees it in the log of the step "Up (two regions)" (`catalyst-api: TREE, ...`, `api image: <machine> holds ... as ...@sha256:...`, `region-a: catalyst-api: runs ...:tree-... of the tree as ...@sha256:...`), in the job summary "catalyst-api image of the local pack" and in the last line of `bash scripts/local-pack.sh charts --changed <file>`.

## 3. The model (the law)
1. **The paths that build the image.** `api_sources <tree>` prints `API_CONTAINERFILE` (`products/catalyst/bootstrap/api/Containerfile`) and the source of every `COPY` of it that is not `--from` another stage, relative to the root of the tree, a folder without its trailing slash, sorted. On `main` these are `core/controllers`, `core/services/shared`, `infra/providers`, `products/catalyst/bootstrap/api`, its `go.mod` and `go.sum`, and the Containerfile. An `ADD`, the JSON form, a continued line, a pattern, the whole context or a path outside the tree makes it exit 1: which paths build the image is then unknown, and the plan fails rather than guess. The wider trigger paths of `catalyst-build.yaml` (the console UI, the chart) build other images; they do not change this image and take nothing from the tree.
2. **The plan.** `api_plan <tree> [<file>]` prints `tree<tab><path>` for the first changed path that is one of those paths or lies in one of those folders, and `pinned<tab>-` otherwise or without a file; a file named that does not exist exits 1. `api_report` turns it into one line, which `charts` prints last.
3. **The build and the load.** With `tree`, `up` builds the image before the apply (`api_build`: `docker build` of the Containerfile with the root as context, `BUILD_SHA` the short commit, no provenance and no SBOM, at most `API_IMAGE_ATTEMPTS`=2 attempts of `API_IMAGE_ATTEMPT_LIMIT`=600 s), named `ghcr.io/openova-io/openova/catalyst-api:tree-<the first 12 hex digits of the commit of the tree>`; it is never pushed and no registry is written. When the boot template is complete in every region, `api_load_pack` saves it once and imports it into the containerd of k3s on every machine of the pack (`machines`: the control-plane machine of each region and its workers), tags it by digest with `ctr images tag`, as the run in self of the workflow loads its suite image, and stops the run unless every machine holds it under one digest.
4. **The console release runs it.** `tree_patch <tag> <namespace>` adds to the one entry of FND-133 a patch that gives the HelmRelease `bp-catalyst-platform` the value `images.catalystApi.tag: <tag>`; the tag must be `tree-` and 12 hex digits. Without arguments `tree_patch` is what FND-133 made. `tree_redirect` reads the tag from `LOCAL_PACK_DIR/api-tag`. The chart renders the image as `ghcr.io/openova-io/openova/catalyst-api:<tag>` with `imagePullPolicy: IfNotPresent`, so the kubelet uses the loaded image.
5. **The judge.** After the console's API is available, `up` waits, within `CORE_LIMIT`, until `api_judge` passes in every region: in the primary region the Deployment names that image, has handled its generation, every replica is updated and available, it has exactly that many live pods, and the container `catalyst-api` of each is Ready with the imageID `ghcr.io/openova-io/openova/catalyst-api@<digest>`. Without `tree` the same wait accepts any image and names the image and imageID that run. A secondary region holds no catalyst-api (slot 13 suspends the console release there): that is said, not judged. The image is still loaded on its machine. A Deployment read that fails other than NotFound waits, its error kept.
6. **A change of the path is proven by its own run.** The step "Decide whether the pack runs" has the env `API_PROBE: products/catalyst/bootstrap/api/Containerfile`. When its changed paths name `scripts/local-pack.sh` or `.github/workflows/conformance-local.yaml` exactly, it appends `$API_PROBE` to `$RUNNER_TEMP/changed-paths.txt` and prints a notice, beside the probe of FND-133. A path that only resembles one of the two names appends nothing. No file of the image changes.
7. **What the run says.** Every line of the plan, of the build (with the docker image id), of each machine's digest and of each region's verdict goes to the log and to `LOCAL_PACK_DIR/api-image.txt`; the step "catalyst-api image of this run (summary)" writes that file into the job summary whenever the job runs; `collect` copies it, `api-build.log` and `api/` into the evidence.
8. No chart version line changes. No Python is added: no new file, and no Python line in the script or the workflow. No Service of type NodePort and no node port anywhere.

+# api_load <machine> <ref> <archive>: imports the image <ref> (the docker save of it in <archive>)
+# into the containerd of k3s on the machine and makes its reference by digest <repository>@<digest>
+# with ctr images tag, as the run in self of conformance-local.yaml does (the import's own
+# --digests makes none for a named image in the containerd of k3s v1.31.8), so that a pod that runs
+# it reports that reference as its imageID. Prints the digest. Exit 1, naming the step, when the
+# import fails or the machine then holds no digest or no reference by digest for it.
+api_load() {

+  docker exec -i "$m" /usr/local/bin/k3s ctr -n k8s.io images import --all-platforms --base-name "$repo" - < "$3" > /dev/null \
+    || { echo "api_load: $m did not import $ref" >&2; return 1; }
+  got=$(docker exec "$m" /usr/local/bin/k3s ctr -n k8s.io images ls "name==$ref" < /dev/null | awk -v ref="$ref" '$1 == ref {print $3}')

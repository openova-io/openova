# INF-112 — Chart templates and image for the inventory controller

## In plain words

**The problem today.** The machine inventory has its two resource kinds and its controller program, but nothing runs the program. The API image does not contain it, and the Blueprint's chart has no Deployment, no access rules and no built-in source, so no Machine is ever written.

**What changes.** The API image carries the controller program. When the chart is switched on, it runs the program with access rules limited to what it needs, and it renders the source that lists the cluster's own Nodes. At its defaults the chart still renders nothing.

**Done means:**

- The catalyst-api image holds the machine controller program beside the API.
- Switched on and given an image, the chart renders one Deployment of the inventory controller, its service account, its access rules and one source of type nodes.
- Switched on without an image, the chart refuses to render.
- No access rule of the chart grants anything on Secrets.
- At its defaults the chart renders nothing, and the NodePort guard inspects the chart switched on.
- A test of the chart checks all of this, and its self-test proves that each of its rules can fail.

The rest of this ticket is the exact instruction for the model that does the work.

## 2. End goal
The Blueprint `bp-machine-operations` can run its inventory controller. The catalyst-api image holds the program `/usr/local/bin/machine-controller`. The chart, when its value `enabled` is true and its value `image` names that image, renders the Deployment `machine-controller-inventory` with its service account, a ClusterRole that reads Nodes and MachineSources and writes Machines and the status of MachineSources, a Role for its leader-election Lease, and the built-in `MachineSource` `nodes` in namespace `catalyst-infra`. No rule grants anything on Secrets. At its defaults the chart renders nothing, as before. The test `platform/machine-operations/chart/tests/render.sh` checks all of this on every pull request that changes the chart. No kit slot installs the chart yet.

## 3. The model (the law)
1. **The image.** The build stage of `products/catalyst/bootstrap/api/Containerfile` builds `./cmd/machine-controller` the way it builds `./cmd/catalyst-dns`: `CGO_ENABLED=0 GOOS=linux go build -ldflags="-s -w"`, then `upx -q --best --lzma`. The final stage copies it to `/usr/local/bin/machine-controller`. The image's entry point stays `/catalyst-api`; the chart starts the controller with its own `command`.
2. **The switch.** The chart renders nothing until the value `enabled` is true (default `false`). The workflow that publishes a chart (`.github/workflows/blueprint-release.yaml`) renders it at its defaults and stops when that render fails, and `Chart.yaml` already carries `catalyst.openova.io/smoke-render-mode: default-off`, which allows an empty default render. So an empty `image` at the defaults must not fail; it fails only once the chart is switched on.
3. **The image value.** `image` (default `""`) is one full image reference. When `enabled` is true and `image` is empty, the render fails with the message `bp-machine-operations: .Values.image is empty. Set it to the catalyst-api image that holds /usr/local/bin/machine-controller.`
4. **The Deployment.** `machine-controller-inventory` in the release namespace: one replica; strategy `Recreate` (the repository guard `scripts/check-single-replica-rollout.py` requires it for one replica); service account `machine-controller-inventory`; one container `machine-controller` with the command `/usr/local/bin/machine-controller --controllers=inventory`; liveness probe `/healthz` and readiness probe `/readyz` on container port 8081 (the binary serves health there); requests `cpu: 20m`, `memory: 64Mi`, limit `memory: 256Mi`; non-root user 65534 (the image's user), read-only root file system, no privilege escalation, every capability dropped, the runtime's default seccomp profile.
5. **The ClusterRole `machine-controller-inventory`** grants exactly: `get`, `list`, `watch` on `nodes`; `get`, `list`, `watch`, `create`, `update`, `patch`, `delete` on `machines`; `get`, `update`, `patch` on `machines/status`; `get`, `list`, `watch` on `machinesources`; `update`, `patch` on `machinesources/status`. These are the calls the controller makes (field 4). No rule names `secrets`, and no rule uses the wildcard `*` for a resource or a verb.
6. **Leader election.** A Role `machine-controller-inventory-leader-election` in the release namespace grants `create` on `leases` (a create cannot be limited by name), `get` and `update` on the Lease `machine-controller-inventory` only, and `create` and `patch` on `events` (the controller library records an Event when the Lease changes hands). A ClusterRoleBinding and a RoleBinding bind the two roles to the service account `machine-controller-inventory` of the release namespace.
7. **The built-in source.** When `enabled` and `sources.nodes.enabled` (default `true`) are both true, the chart renders `MachineSource` `nodes` in namespace `catalyst-infra` with the spec `{type: nodes}` and nothing else.
8. **The test.** `tests/render.sh` renders the chart four times and checks rules R1 to R8 (written at its head). `tests/render.sh --self-test` proves that each rule can fail. It needs bash, Helm and Python 3 with PyYAML, which both the chart test job and the acceptance job have.
9. **The NodePort guard sees the templates.** `chart/ci/nodeport-render-values.yaml` sets `enabled: true` and an image, so the guard's second render holds every template of the chart.
10. **The documents say what ships.** `platform/machine-operations/README.md` and the description in `Chart.yaml` say that the chart runs the controller; neither says any longer that the templates come later.
11. **Not in this ticket.** No version line changes: the release writer sets chart versions after the merge. No kit slot, no namespace, no network policy, no chart value that carries a whole object.

def docs_of(path):
    with open(path, encoding="utf-8") as f:
        return [d for d in yaml.safe_load_all(f) if isinstance(d, dict)]


def load():

def key(d):
    m = d.get("metadata") or {}
    return (d.get("kind"), m.get("namespace"), m.get("name"))


def find(docs, k):
    found = [d for d in docs if key(d) == k]
    return found[0] if len(found) == 1 else None


def triples(rules):
    out = set()
    for r in rules or []:
        names = r.get("resourceNames") or [""]
        for g in r.get("apiGroups") or []:
            for res in r.get("resources") or []:
                for v in r.get("verbs") or []:
                    for n in names:
                        out.add((g, res, v, n))
    return out

    for cp in container.get("ports") or []:

# bp-machine-operations

Machine operations on the machines a Sovereign runs on, starting with an
inventory of the cluster's own Nodes.

## Role in Catalyst

Control-plane plumbing, not an Application a User installs. The kinds of the
API group `machines.openova.io` belong to this Blueprint: they arrive with its
chart and are absent where it is not installed. They are not platform
entities. See [`docs/ARCHITECTURE.md`](../../docs/ARCHITECTURE.md) for the
place of a Blueprint in the model.

## What this version ships

The chart holds the two custom resource definitions, in `chart/crds/`, and the
templates of the inventory controller:

| Kind | Written by | Meaning |
|---|---|---|
| `MachineSource` | chart values or Git | One place machines are read from. Type `nodes` lists the Kubernetes Nodes of the cluster. |
| `Machine` | the inventory controller only | One machine a source saw. An observation, never committed to Git. |

The inventory controller is the binary `machine-controller` of the
catalyst-api module (`products/catalyst/bootstrap/api/cmd/machine-controller`),
built into the catalyst-api image as `/usr/local/bin/machine-controller`. Its
code is in `products/catalyst/bootstrap/api/internal/machines/`. The chart runs
it as the Deployment `machine-controller-inventory` in the release namespace:
one replica, the command
`/usr/local/bin/machine-controller --controllers=inventory`, and the service
account of the same name. Its ClusterRole reads Nodes and MachineSources,
writes Machines and the status of MachineSources, and grants no verb on
Secrets. A Role in the release namespace covers its leader-election Lease. The
chart also renders the built-in source `nodes` (type `nodes`) in namespace
`catalyst-infra`.

## How the inventory works

- A Machine is identified by its namespace, its source and the source's own
  identifier. A Machine of class `node` is named after its Node.
- An enumeration that fails, or that cannot read every scope, marks nothing.
- After a complete enumeration, an `Active` Machine that the source did not
  list becomes `Stale`. The time since it was last seen is never the test.
- If that would mark more than `spec.stale.holdPercent` (default 20) of the
  source's active Machines, and at least `spec.stale.holdMinimum` (default 10),
  nothing is marked: `status.held` and the condition `StaleHold` are set. Set
  `spec.stale.releaseHoldFor` to `status.held.enumerationId` to apply the sweep.
- A Machine that a source lists again becomes `Active` and keeps `firstSeen`.
- A Machine that is stale for `spec.stale.retireAfter` (default `720h`)
  becomes `Retired`; after a further `spec.stale.purgeAfter` (default `2160h`)
  it is deleted.
- Each Machine carries exactly five labels, written by the controller:
  `machines.openova.io/class`, `ownership`, `os-family`, `phase` and `source`.

## Configuration

| Value | Default | Meaning |
|---|---|---|
| `enabled` | `false` | Switches the chart on. At `false` it renders nothing; only the definitions are installed. |
| `image` | `""` | The catalyst-api image, as a full reference. Required when `enabled` is true: the render fails while it is empty. |
| `sources.nodes.enabled` | `true` | Renders the built-in source `nodes` in `catalyst-infra`. |

`chart/tests/render.sh` checks what the chart renders. Run it with
`--self-test` to see that each of its rules can fail.

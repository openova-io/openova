# FND-011 — CI bumps chart versions; pull requests may not

## In plain words

**The problem today.** Authors bump a chart's version and its pins by hand in each pull request, and a guard forces them to. Two open pull requests can claim the same version, so a second guard exists only to catch that. The version and its pins also land in separate commits, which turns checks red in between.

**What changes.** After a merge, CI bumps the version of each chart the merge changed and pushes it together with the chart's pin, its Blueprint version and its catalogue entry in one commit. A pull request that changes one of those values fails, and the guard that forced authors to bump stops judging pull requests.

**Done means:**

- A pull request that changes the version of an existing chart, a Blueprint version, a catalogue pin or a bootstrap-kit pin fails the check that guards these values.
- A pull request that changes a chart and leaves its version alone no longer fails a version check.
- When such a change reaches main, the release workflow publishes the chart under the next patch version and pushes that version with every pin and catalogue line in one commit.
- The four charts whose own build workflow writes their version are not bumped a second time, and their push run publishes nothing.
- The workflow that made two pull requests compete for one version is deleted.
- The runbook tells authors not to edit version lines.

The rest of this ticket is the exact instruction for the model that does the work.

## 2. End goal
A pull request no longer writes a chart version or a pin. The new check `no release-owned value changes in a pull request` (workflow `check-release-owned-lines`, script `scripts/check-release-owned-lines.py`) fails a pull request or merge group that changes a version value of a chart, Blueprint, catalogue-seed entry or bootstrap-kit slot that exists before and after it. After the merge, the build job of `.github/workflows/blueprint-release.yaml` (the release writer) sees that the push changed files of a chart and left its version as it was. It writes the next patch version into that chart's `Chart.yaml` before it packages and publishes the chart, and its commit step pushes `Chart.yaml` together with the slot pin, `blueprint.yaml`, the catalogue seed and the generated catalogue: all five version sites in one commit. The guard that made authors bump stops judging pull requests, and the workflow that stopped two pull requests from claiming one version is deleted. Three new cases of `scripts/check-release-lockstep-writer.py` run the release writer's own steps and prove the one commit.

## 3. The model (the law)
1. **Release-owned values.** A pull request does not change these values of a file that exists on both sides of the change. `scripts/check-release-owned-lines.py pr` refuses each one with a line `REFUSED R<n> <path>: ...` and exits 1:
   - R1: the top-level `version:` of `platform/<x>/chart/Chart.yaml` and `products/<x>/chart/Chart.yaml`. A chart of `type: library` is exempt: it is never published, and its consumers pin its version.
   - R2: the top-level `appVersion:` of `products/catalyst/chart/Chart.yaml`, which the deploy jobs write together with its version.
   - R3: the first line `  version:` (the spec version) of a manifest of `kind: Blueprint` at `platform/<x>/blueprint.yaml`, `products/<x>/blueprint.yaml` or `products/<x>/chart/blueprint.yaml`.
   - R4: the spec version and the source version of each entry, matched by name, of `products/catalyst/chart/templates/catalog-seed/blueprints.yaml`.
   - R5: the chart pin (the first line `      version:`) of a slot file `clusters/_template/bootstrap-kit/<file>.yaml`.

   A file or a seed entry that the change adds or deletes is exempt. Values are compared without quotes and without a trailing comment. The `appVersion:` of every other chart is the upstream version of what the chart installs, and an upgrade changes it in a pull request, so it is not release-owned.
2. **The guard runs on every pull request and merge group.** Workflow `.github/workflows/check-release-owned-lines.yaml`, job `pr` (name `no release-owned value changes in a pull request`): `--self-test` first, then `pr --base <base> --head <head>` over the change from the merge base. It has no path filter, and it has the `merge_group` trigger.
3. **The push job waits for the release-writer identity.** The same workflow has a job `push` (name `a push to main comes from the merge queue or the release writer`). It runs only on a push to `main` and only when the repository variable `RELEASE_WRITER_LOGIN` is set. It fails when the account that pushed is neither `github-merge-queue[bot]` nor that login. Nothing in this ticket sets the variable: package FND-017 does, when it moves every bot writer to that login and switches the merge queue on. Before that, every merge is a push by a person, so the job would be red on every merge.
4. **The release writer bumps the chart version.** A new first step of the build job, id `bump_chart`, runs before the step `chart` (`Read chart metadata`). It writes the next version when all of these hold: the run has a push range (`github.event.before` is set and not all zeros); the chart's `Chart.yaml` existed at `before`; a file under `<path>/chart` changed between `before` and `github.sha`; the chart's `version:` is the same at both ends; the chart is not `type: library`; and the chart is not one of the four of item 5. The next version is the patch number plus one of the higher of the checked-out version and the version on `origin/main`. A version that is not `MAJOR.MINOR.PATCH` stops the job with an error. The step writes only the top-level `version:` line and outputs `bumped=true`, `chart_yaml` and `prev_version`. In every other case it outputs `bumped=false` and changes nothing. A run started by `workflow_dispatch` has no push range, so it publishes the version as it stands, as today.
5. **Four charts are versioned by their own build workflow.** `products/catalyst` (`catalyst-build.yaml`), `platform/guacamole` (`build-bp-guacamole.yaml`), `platform/newapi` (`build-bp-newapi.yaml`) and `platform/k8s-ws-proxy` (`build-k8s-ws-proxy.yaml`) each bump their own `Chart.yaml` version on a push that changes the chart and then dispatch the release workflow. For these four, `bump_chart` outputs `defer=true` when their version did not move in the push, and the step `chart` then outputs `skip=true`. Every later step of the build job is skipped, so a push run publishes nothing and never overwrites a published version with other content.
6. **One commit.** The commit step stages `Chart.yaml` when `bump_chart` bumped it, with the pin, `blueprint.yaml`, the seed and the generated catalogue that the existing steps write. It runs also when only the chart version moved. Its message names the chart bump. On a push retry it writes the published version again after `git reset --hard origin/main`; when `origin/main` already carries a higher version it stops with an error and never moves the version back.
7. **Push runs of one chart run one after the other.** The build job gets `concurrency: group: blueprint-release-${{ github.event_name }}-${{ matrix.path }}` with `cancel-in-progress: false`. The next version is read from `origin/main`, so two push runs of one chart must not compute it at the same time. Dispatch runs keep their own group and are not held behind push runs.
8. **The bump guard no longer judges pull requests.** `.github/workflows/check-chart-version-bumped.yaml` loses the three chart path filters and the step `Every touched chart must bump its version`. It keeps its self-test, which runs when the script or the workflow changes. Its title becomes `Chart-version-bumped guard (self-test)`; its job name `Chart-version-bumped guard` stays.
9. **Deleted:** `.github/workflows/check-chart-version-claim.yaml`. No pull request claims a version any more. Its script `scripts/check-chart-version-not-claimed-by-open-pr.py` stays: `scripts/bump-chart-version.sh` calls it and stops without it, and the deploy jobs call that script.
10. **The proof.** `scripts/check-release-lockstep-writer.py` runs the step `bump_chart` first, resolves `github.<dotted name>` references from its case context, and gains three cases. `release`: a commit changes `platform/keycloak/chart/values.yaml` and no version; the writer must land the next version at all five sites, and its last commit must carry `Chart.yaml`, `blueprint.yaml`, the seed, both generated catalogue files and the slot. `release-retry`: the same with a rival commit that forces the retry. `umbrella-defer`: the same change to `products/catalyst`; the writer must push nothing and the step `chart` must skip. These three cases do not run the repository-wide gates of the older cases.
11. **The runbook.** Section `### 2.4 Chart-version collision (parallel fix-authors)` of `docs/RUNBOOKS.md` becomes `### 2.4 Chart versions are written by CI`. It says: do not edit version lines; it lists the refused values; it names the release writer and the four charts of item 5.
12. **Nothing else changes.** No other workflow, no build workflow of item 5, no bump script, no chart, no pin, no catalogue file. No path is added to `docs/ledger/deleted-paths.txt`. All the content comes from the embedded patch.

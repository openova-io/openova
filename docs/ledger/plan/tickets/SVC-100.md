# SVC-100 — Function tests: admission, infrastructure and control-plane charts

## In plain words

**The problem today.** The admission policies, the workload reloader, the Crossplane core, the Crossplane composite definitions and the vcluster chart source count as working when their objects exist. Nothing tests that the policies are loaded, that a changed ConfigMap really rolls the workloads that use it, that Crossplane serves its package API, that the composite types are served, or that the chart source has fetched its index.

**What changes.** Each of the five charts gets one test Pod that asks the cluster about the thing the chart installs, or makes a change and waits for its effect, and checks the answer. A render check per chart holds the Pod to the contract. The existing composition test of the Crossplane definitions chart learns to leave the test objects out of the objects it counts.

**Done means:**

- Each of the five charts renders one test Pod with the hook test, a deadline of 300 seconds and the restart policy Never, and renders none where its own switches turn every tested object off.
- The policy test waits for every policy of its release to be Ready, and the definitions test for every composite definition of its release to be Established, and both take the names from the chart's own templates.
- The reloader test changes a scratch ConfigMap and passes only when Reloader rolls a scratch Deployment that names it within 60 seconds, and it removes both objects again.
- The Crossplane test passes only when the Provider list answers and the core has an available replica; the chart source test only when the vcluster HelmRepository is Ready.
- A render test per chart fails when that chart's test Pod breaks the contract, and it runs on every pull request that changes the chart.
- The service-model guard counts five more charts with a function test, and the composition test of the definitions chart still counts exactly eight ClusterRoles of its own.

The rest of this ticket is the exact instruction for the model that does the work.

Each of the five charts has a render test `chart/tests/function-test-render.sh`, which CI runs with the chart's other tests on every pull request that changes the chart. ## 3. The model (the law)
1. **The contract.** It is section 4.5 of `docs/RUNBOOKS.md` and the checker `scripts/check-function-test.py` (package SVC-060; package SVC-070 added ClusterRole and ClusterRoleBinding to the kinds allowed beside the Pod). A chart that has a function test ships one file `chart/templates/tests/function-test.yaml`. It renders one Pod named `<release>-function-test`, with the annotations `helm.sh/hook: test` and `helm.sh/hook-delete-policy: before-hook-creation,hook-succeeded`, the label `catalyst.openova.io/function-test: "true"`, `restartPolicy: Never` and `activeDeadlineSeconds: 300`. It exits 0 on pass and non-zero on fail, and its last line is `FUNCTION-TEST <pass|fail> <chart name> <reason>`. It needs nothing outside the cluster, uses an image the chart already uses or one the kit already pulls, renders nothing when the chart renders nothing it could test, never creates or reads a Secret, and every container requests cpu and memory. Every call of a test to the API server has a time limit of 15 seconds, so each test ends well inside its 300 seconds.
2. **The five tests.** Each `function-test.yaml` is the block of field 5 of the same name, byte for byte. The image of each is `harbor.openova.io/proxy-dockerhub/alpine/k8s:1.31.4`, or `functionTest.image`. None of the five charts uses a kubectl image of its own; the kit pulls this one for `bp-cnpg` and `bp-kyverno` (P5).

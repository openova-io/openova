# SOV-190 — The console reads the mode from the API

## In plain words

**The problem today.** The sovereign-admin console decides whether it runs on the mothership or on a Sovereign by comparing the browser's host name with one fixed company address, and it guesses the Sovereign's name from the shape of the host. An Organization console served by a Sovereign is therefore given the wrong Sovereign name. The API already answers the mode on the route the console calls, and nothing in the console reads that answer.

**What changes.** The console asks the API once at start and takes the mode and the Sovereign's name from the answer. The fixed company address leaves the mode code and the router, and the count of such addresses in the console falls by two.

**Done means:**

- The console takes its mode from the API: the answer mothership gives the provisioning wizard, the answer sovereign gives the Sovereign console.
- An Organization console served by a Sovereign carries that Sovereign's name, not the Organization's own domain.
- When the API cannot be read, the console starts in the mothership mode, as it did before for a host it could not place.
- The build-time override still sets the mode without asking the API.
- The mode is not stored in the browser.
- The count of company addresses written into the console falls from 21 to 19, and its baseline falls with it.

The rest of this ticket is the exact instruction for the model that does the work.

## 2. End goal
The sovereign-admin console (`products/catalyst/bootstrap/ui`) learns its operating mode from the catalyst-api, never from the host name. At start it sends one request, `GET ${API_BASE}/v1/sovereign/self`, and takes `mode` and `sovereignFQDN` from the JSON answer: `mothership` becomes the console mode `catalyst-zero` (the provisioning wizard), `sovereign` becomes `sovereign` with the Sovereign's name the API gives. The module-level value `DETECTED_MODE`, which 38 other console files already read, is filled from that answer before any of them runs. The router's own host-name test is replaced by `DETECTED_MODE`. The build-time override `VITE_CATALYST_MODE` still wins and costs no request. The source-address guard of the console falls from 21 counted lines to 19, and its baseline with it.

## 3. The model (the law)
1. **One source of the mode.** `products/catalyst/bootstrap/ui/src/shared/lib/detectMode.ts` reads `GET ${API_BASE}/v1/sovereign/self` once. The route is the one package SOV-180 extended (`products/catalyst/bootstrap/api/internal/sovself/sovself.go`): on a Sovereign it answers 200 with `deploymentId`, `sovereignFQDN`, `mode` and further fields; on the mothership it answers 404 `not-a-sovereign` with `mode` `mothership`. Both bodies carry `mode`, so the console reads the JSON body and ignores the HTTP status.
2. **The mapping.** `modeFromSelf(body)` (exported) gives:
   - `mode` `mothership`: `{ mode: 'catalyst-zero', sovereignFQDN: null }`, whatever `sovereignFQDN` says.
   - `mode` `sovereign`: `{ mode: 'sovereign', sovereignFQDN }` with the trimmed `sovereignFQDN` when it is a non-empty string, else `null`.
   - anything else (no object, no `mode`, another value): `{ mode: 'catalyst-zero', sovereignFQDN: null }`.
3. **When the answer cannot be read** (the request fails, takes longer than `SELF_TIMEOUT_MS` = 5000 milliseconds, or the body is not JSON) the result is `{ mode: 'catalyst-zero', sovereignFQDN: null }`. That is the value the old code gave for a host it could not place, so a local development server and the unit tests behave as before.
4. **Once, before any reader.** `export const DETECTED_MODE: ModeResult = await detectMode()` is a top-level await. Every module that imports `detectMode.ts` waits for it, so the router, which builds its route tree from `DETECTED_MODE.mode` at module load (`router.tsx` line 2307), sees the final value. `detectMode()` becomes `async`; no production code calls it (only test mocks name it).
5. **The override.** When `VITE_CATALYST_MODE` is set, `detectMode()` returns it as before (`sovereignFQDN` is `VITE_SOVEREIGN_FQDN` in mode `sovereign`, else `null`) and makes no request.
6. **No host name, no storage.** `detectMode.ts` contains no host name and does not read `window.location`; the request path comes from `API_BASE` (`src/shared/config/urls.ts`). The answer is kept only in the module value, never in `localStorage` or `sessionStorage`.
7. **The router.** `const isCatalystZero` in `src/app/router.tsx` becomes `DETECTED_MODE.mode === 'catalyst-zero'`; its comment and the comment of `indexRoute` say that the mode comes from the API.
8. **Deleted:** the constant `CATALYST_ZERO_HOSTNAME`, the function `sovereignFQDNFromHostname`, every host-name branch of `detectMode()`, the router's comparison `window.location.hostname === 'console.openova.io'`, and the unit tests of the host-name rules (including the `it.fails` tripwire of issue 5895, which this change resolves).
9. **Tests.** `detectMode.test.ts` is rewritten against the API answer: 20 tests. `resolveSovereignFQDN.test.ts` mocks `./detectMode` with the value the start-up read gives on each host, because its old set-up relied on the host-name rule; its 8 tests and the module `resolveSovereignFQDN.ts` are otherwise unchanged.
10. **The guard.** Guard G1 (`scripts/check-upstream-literals.sh`) counts the console scope at 19 after the change (the two deleted lines are `detectMode.ts` line 24 and `router.tsx` line 40). The baseline line `console=21` of `scripts/upstream-literals-baseline.txt` becomes `console=19` in the same change.
11. **Comments of the mode type.** The two comments of `src/shared/constants/env.ts` that describe the host-name rule say that the mode comes from the API. No code of that file changes.

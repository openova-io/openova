# NET-222 — Blueprint data without tiers

## In plain words

**The problem today.** Forty-two Blueprints still place their application in a tier (mgmt or rtz), and one Blueprint names a vcluster as its default placement. No tier namespace exists on a Sovereign any more, so an application of such a Blueprint is written into a namespace that is not there, its release fails, and it blocks the other applications of that Organization in that region. The old topology matrix document still describes the tiers as if they were the design.

**What changes.** Every Blueprint places its application on the host, in the Organization's own namespace, and the catalogue that the console and the API read says the same. The topology matrix document is gone and recorded as deleted.

**Done means:**

- No Blueprint file of the platform or of the products carries a tier other than empty, and none has a default placement.
- No Blueprint that an Organization can install carries a non-empty tier.
- The catalogue seed, the API catalogue and the console catalogue carry no tier mgmt, dmz or rtz, and they are in step with the Blueprint files.
- The topology matrix document is deleted and listed among the deleted paths.
- The codemod is in the repository, and running it again changes nothing.
- The cluster identifiers of the topology keep their form, so the Blueprint schema, the admission check and the application controller read them as before.

The rest of this ticket is the exact instruction for the model that does the work.

# Blueprint data without tiers (NET-222). A codemod, run once over every tracked
# platform/<name>/blueprint.yaml and products/<name>/blueprint.yaml:
#   - a topology placement tier mgmt, dmz or rtz becomes '' (the host: the

function ind(s) { match(s, /^ */); return RLENGTH }
function flush() {
  if (keys > 0) printf "%s\n%s", dp, kept
  dp = ""; kept = ""; keys = 0
}
BEGIN { dp = ""; kept = ""; keys = 0; dpi = -1; api = -1 }

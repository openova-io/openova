# CTL-242 — Catalogue edits are stored as the edited card fields only

## In plain words

**The problem today.** A catalogue edit of a Blueprint, made on its card, through Edit IaC or by curating it, is committed as a whole copy of the Blueprint, and the catalogue reconciliation applies that copy over the live object with force. When the platform later upgrades the Blueprint, the older copy is applied again and puts the old version and the old contract fields back.

**What changes.** Where the platform's catalogue seed also writes every other field of the live Blueprint, the committed copy holds only the Blueprint's name, its card fields and its visibility, and every other field keeps the value the platform writes. Where no live Blueprint exists, or the reconciliation alone writes one of its other fields, the whole Blueprint is committed as before.

**Done means:**

- After a card edit or a curate of a Blueprint whose other fields the platform's catalogue seed also writes, the file the catalogue reconciliation applies holds only the name, the card fields and visibility.
- An upgrade of such a Blueprint by the platform is no longer forced back to the version of an earlier edit.
- Where no live Blueprint exists, or the reconciliation alone writes one of its other fields, the whole Blueprint is committed as before, so no field is lost and a missing Blueprint can still be created.
- The per-Blueprint copy that the catalogue reads stays the whole Blueprint.
- The handler package of catalyst-api does not grow.

The rest of this ticket is the exact instruction for the model that does the work.

## 2. End goal
On a Sovereign, a sovereign-admin edits the card of a Blueprint that the chart's catalogue seed installed (or curates it, or edits it through Edit IaC). The file that catalyst-api commits to `clusters/<fqdn>/catalog-sovereign/<bp>.yaml` on the branch `catalog-sovereign` of the local Gitea repository `openova/openova`, which the Kustomization `catalog-sovereign` applies server-side with force, is then only `apiVersion`, `kind`, `metadata.name`, the card fields and `spec.visibility`. Where a partial file would lose a field or could not create the object, the whole Blueprint is committed as today.

## 3. The model (the law)
1. The three catalogue writers (the card edit, `writeCatalogEditToGit`; Edit IaC, `HandleCatalogBlueprintIaCEdit`; curate, `HandleBlueprintCurate`) reach the Flux file through one trunk, `writeCatalogSovereignAggregatorBytes` in `products/catalyst/bootstrap/api/internal/handler/catalog_edit_git.go`. The trunk decides the form of the file; no writer decides it for itself.
2. The partial object is `blueprintedit.Partial` (new file `products/catalyst/bootstrap/api/internal/blueprintedit/partial.go`): `apiVersion`, `kind`, `metadata.name` and each path of `blueprintedit.Editable` (the card fields and `spec.visibility` of SVC-200) that the document holds, and nothing else.
3. The trunk reads the in-cluster Blueprint of that name through the catalog client's cluster reader (`chainedCatalogClient.getFromCluster`) and passes it to `blueprintedit.FluxPayload`. The file is the partial object only when the Blueprint exists and every spec field outside `Editable` that Flux's apply owns in `metadata.managedFields` (the managers `kustomize-controller`, `before-first-apply` and `kubectl...`, whose fields a forced server-side apply of kustomize-controller takes over) is owned by a second manager too. A server-side apply removes a field that its manager owned before and no longer sets, unless another manager owns it; and a partial object cannot create a Blueprint, because the definition requires `spec.version`.
4. Otherwise the file is the whole canonical Blueprint, exactly as before this package. A read of the in-cluster Blueprint that fails for another reason than "not found" fails the write with an error; it does not fall back silently.
5. The per-Blueprint read source `catalog-sovereign/<repo>/blueprint.yaml` stays the whole document in every case: the catalog service and catalyst-api's catalogue read path and install path read it whole.
6. The handler package shrinks by 3 lines. `scripts/baselines/api-structure.json` is lowered by its own tool, `python3 scripts/check-api-structure.py --write-baseline`, and only its entry `handler_lines` changes.
7. No chart changes, no chart version line, no Python file, no live system.

# CLD-023 — Delete the Hetzner-only Compositions, their definitions and orphan manifests

## In plain words

**The problem today.** Six Crossplane definitions and their Compositions for day-two changes to clusters, regions, node pools, load balancers, peerings and node actions work on one cloud only, and nothing writes them any more since the write routes were removed. Beside them sit an older set of five Hetzner definitions, a disabled floating-address template, a Hetzner-only folder of Crossplane manifests and a workflow that tests the native Hetzner provider. A Hetzner installation still installs that provider at first boot, although nothing uses it.

**What changes.** The dead definitions, Compositions, test fixtures, manifests and the workflow are deleted, and every Sovereign installs the same Crossplane provider from the same path. The tests, the stored fingerprint of the first-boot file, the list of deleted paths and the stored counts of written source addresses follow the deletion.

**Done means:**

- The Crossplane claims chart renders exactly one definition and one Composition, the cloud adoption pair, unchanged.
- No file under platform, clusters or infra, apart from documents, names the native Hetzner provider group or its two configuration names.
- A new Hetzner installation installs its Crossplane provider from the same folder as a Huawei installation, and the Huawei first-boot file is unchanged.
- The chart test, the first-boot render test and the Go tests that read the deleted files pass with the files gone.
- Every deleted path is listed in the list of deleted paths, and the provider-name baseline no longer lists them.
- The stored counts of written source addresses fall with the deletion, and their guard still fails when one address is added to the cluster template.

The rest of this ticket is the exact instruction for the model that does the work.

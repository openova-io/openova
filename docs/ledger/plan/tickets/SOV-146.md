# SOV-146 — The child Kustomizations of first boot are also files under clusters/_template/root

## In plain words

**The problem today.** First boot writes five Flux Kustomizations inline into the control-plane user data, which is close to the size the clouds accept. A later task makes first boot apply one root Kustomization that takes the five from Git instead, but the five do not exist as files in Git yet, and nothing proves that such files would give a Sovereign exactly what the template gives it today.

**What changes.** The five Kustomizations become files in the kit, with one small folder for each kind of region that the template knows, and a check proves on every pull request that each folder builds the same five documents as the template. The template and every running Sovereign stay as they are.

**Done means:**

- The kit holds the five child Kustomizations of first boot as files, each with the comments it has in the boot template.
- Each kind of region the boot template knows (provider, region layout and region role) has exactly one folder that builds its Kustomizations.
- A check compares, for every provider, region layout and region role, what the template renders with what the matching folder builds, and a pull request that makes them differ turns red.
- The check proves with its own self-test that each of its rules can fail.
- The boot template is unchanged, so the user data of a new Sovereign is byte for byte what it was.

The rest of this ticket is the exact instruction for the model that does the work.

## 3. The model (the law)
1. The boot template does not change. It is in field 14 only so that this package holds the lock `cloud-init`. Work step 6 proves it is unchanged.
2. The branches. The template chooses its Kustomizations by three conditions: the provider is `hetzner` or not (the path of `sovereign-tls` gains `-hetzner`, and `sovereign-region-bootstrap` is not rendered); the region layout (`base` when `replica_region_canonical_label` is empty, `multi-region` when this region is the primary region, `multi-region-follower` otherwise), which only the path of `sovereign-region-bootstrap` reads; the region role (`infrastructure-providers` only when `sovereign_region_role` is `primary`). There is one folder for every branch, also for the two that no module reaches today (layout `base` or `multi-region` with role `secondary`), so that any input keeps exactly today's set:
   - `clusters/_template/root/<layout>-<role>` for a provider that is not `hetzner`: `base-primary`, `base-secondary`, `multi-region-primary`, `multi-region-secondary`, `multi-region-follower-primary`, `multi-region-follower-secondary`.
   - `clusters/_template/providers/hetzner/root/<role>` for `hetzner`, where the layout changes nothing: `primary`, `secondary`.
3. Paths, not keys. A folder is chosen by its path. No key is added to the ConfigMap `sovereign-variables`, so `docs/contracts/c5-kit-keys.txt` and `tests/fixtures/variables/today.env` do not change and no byte is added to the user data.
4. The only value the five read from an input is the annotation `openova.io/wildcard-cert-issuer-tag` of `sovereign-tls`. In the file it is `"${WILDCARD_CERT_ISSUER}"`, the key of `sovereign-variables` that the template fills from the same input `wildcard_cert_issuer`. The root Kustomization of SOV-154 substitutes it. No other `$` stands in a value of the folders; the one comment of the template that wrote `$${WILDCARD_CERT_ISSUER}` says `WILDCARD_CERT_ISSUER` in the file.
5. Each folder other than `base-primary` holds only a `kustomization.yaml` with the fields `apiVersion`, `kind`, `resources` (the folder `base-primary`) and `patches`. A patch is one inline patch without a target: it either sets `spec.path` or removes one object with `$patch: delete`. A folder is referred to as a folder, never as a file outside it.
6. Provider names stay in the provider's overlay. Every file that names a provider outside a comment lies under `clusters/_template/providers/hetzner/`; the shared folder and the script name none (the check `check-provider-leaks.py` of the workflow `tree-guards` counts them).
7. The check (`scripts/check-root-kustomization-parity.py`, embedded in the patch of field 20) has two rules and a self-test that makes each fail. R1: each folder builds the Kustomizations that the template renders for its branch, compared object by object. R2: `clusters/_template/root` holds exactly the six folders of point 2, and a provider overlay with a `root` folder belongs to a provider pack and holds exactly `primary` and `secondary`. Exit code 0 when both hold, 1 when one fails, 2 when it meets something it cannot judge.
8. The workflow `.github/workflows/check-kit-render-equivalence.yaml` gains the script in both path filters and two steps in its one job, after the existing steps: the self-test, then the check. No job is added.
9. Nothing is deleted. SOV-154 deletes the five from the template and deletes the check.

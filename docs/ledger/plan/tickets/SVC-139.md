# SVC-139 — The function tests of bp-openbao, bp-reloader and bp-valkey wait for their subject within the bound

## In plain words

**The problem today.** On the second fresh two-region installation of 20 November the function tests of the secret store, of Reloader and of the cache failed once, while their subject was still starting, and were never run again. The store's test gave up a minute before its role was written, Reloader's test changed its ConfigMap before Reloader was watching, so the change was lost, and the cache's test was killed at its deadline without printing a word.

**What changes.** Each of the three tests waits for what it tests for as long as its release may take to install, then judges as before. Reloader's test changes the ConfigMap only once Reloader is ready, and the cache's test prints why it failed when it is stopped at its deadline.

**Done means:**

- A store, a Reloader or a cache that comes up ten minutes after the install passes its test, and one that never comes up fails it, naming what the test waited for.
- Reloader's test changes its ConfigMap only after Reloader is ready.
- The cache's test, stopped at its deadline while it still waits, prints the fail line naming the PING and its last answer.
- The kit gives each of the three releases one waiting time, equal to its install timeout and to the time the installer waits for the test.
- The kit's test of that waiting time no longer lists the three as owed, and it renders the store's chart with a stand-in for the value the cluster supplies at install.

The rest of this ticket is the exact instruction for the model that does the work.

## 2. End goal
On a fresh two-region installation the function tests (the `helm test` hooks of `templates/tests/function-test.yaml`, run by Flux once after an install) of bp-openbao, bp-reloader and bp-valkey pass when their subject comes up within the time their release may take to install, and fail naming the subject when it never does. They use the mechanism of SVC-137 exactly: T is `functionTest.timeoutSeconds`, the test Pod's `activeDeadlineSeconds`; the wait ends 60 seconds before T; the kit states T once per release as `spec.values.functionTest.timeoutSeconds: 900`, equal to `spec.install.timeout: 15m`, with `spec.test.timeout: 15m`; without the value the chart default of 300 seconds holds. bp-openbao asks the health endpoint and then the login for the role `external-secrets` (written by the release's own Deployment `openbao-config`) until T - 60. bp-reloader waits for a ready replica of Reloader's own Deployment (`reloader-reloader` in the kit) until T - 125, gives it 5 seconds, changes its scratch ConfigMap by T - 120 and judges for 60 seconds, so it ends by T - 60. bp-valkey sends PING until T - 60, and traps TERM: stopped at its deadline it prints the `FUNCTION-TEST fail` line naming the PING and its last answer. The three leave the list `owed` of `tests/e2e/bootstrap-kit/function_test_bound_test.go`, whose B5 render now gives every `valuesFrom` `targetPath` of a release a stand-in value (bp-openbao's test renders only with `seal.stanza`, which slot 08 takes from a ConfigMap). A person sees this on the pull request: the three charts' `chart/tests/*.sh`, `Test — Bootstrap Kit / manifest-validation` and the acceptance commands are green.

## 3. The model (the law)
1. A function test proves the function its own release delivers, in its own region; all three subjects are delivered by the test's own release, so no `testNeeds` entry (B3) and no install-timeout change: the three install with `timeout: 15m` and `disableWait: true`, so T is 900.
2. The test waits for its subject itself, then judges as before, and fails naming a subject that never comes up. Its bound T is stated once, as `spec.values.functionTest.timeoutSeconds`; the chart makes it the test Pod's `activeDeadlineSeconds`, its waits end by T - 60, and `spec.test.timeout` equals the install timeout. Without the value the chart default of 300 holds, so the default render and `scripts/check-function-test.py` (rule FT8) do not change.
3. Reloader acts only on a change it sees (`reloadOnCreate` and `syncAfterRestart` false in the subchart), so the change of the scratch ConfigMap comes after Reloader is ready, never before; a longer judgement after a lost change cannot pass.
4. A test that the kubelet stops at its deadline still ends with its `FUNCTION-TEST fail` line: bp-valkey's shell is PID 1 and ignores TERM without a handler, so it traps TERM and prints what it was waiting for and the last answer.
5. The guard's list `owed` only shrinks: the three are removed and no name is added. Its B5 render gives a stand-in value to every `valuesFrom` `targetPath` that `spec.values` does not set (Flux merges `spec.values` over `valuesFrom`); a path that is not plain dotted is refused. This is a change of the guard's own file, not a second mechanism.
6. No `dependsOn`, no `install.disableWait`, no chart version and no `Chart.yaml` changes.

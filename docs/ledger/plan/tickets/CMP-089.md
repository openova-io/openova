# CMP-089 — The trivy operator stays within its memory in every region

## In plain words

**The problem today.** In one region of a two-region Sovereign the trivy operator is killed for memory again and again: 105 restarts in two days at a limit of 1Gi, while the other region's operator, from the same chart and the same values, never restarted. The operator's Go runtime does not know the container's limit, so it lets its heap grow until the kernel kills it, and the health check of the releases and pods stays red on this container alone.

**What changes.** The operator's container gets twice the memory limit and a Go soft limit set below it, so the Go runtime collects before the kernel kills. A chart test proves both values in the rendered Deployment, also with the values the kit passes, and shows that each of its rules fails on a render that breaks it.

**Done means:**

- The rendered trivy operator Deployment carries limits.memory 2Gi and exactly one environment variable GOMEMLIMIT with the value 1800MiB, for the chart alone and with the values of the kit's trivy slot.
- The chart test tests/operator-memory.sh passes on the pull request under the yq and Helm of the release, and it fails on the values of main.
- The scan Jobs keep their own limits (cpu 1, memory 512Mi) and the operator still runs at most two scan Jobs at a time.
- The chart's version line and the kit's trivy slot do not change in the pull request.
- After the next pair is installed, the gate check FND-G04 no longer names the trivy operator.

The rest of this ticket is the exact instruction for the model that does the work.

## 3. The model (the law)
1. The operator's container carries `resources.limits.memory: 2Gi`. Its requests (`cpu: 100m`, `memory: 256Mi`) and its cpu limit (`500m`) do not change.
2. The operator's container carries exactly one environment variable `GOMEMLIMIT`, set through the upstream chart's `extraEnv`, with the value `1800MiB`. The value is in the Go runtime's syntax (`MiB`, not the Kubernetes `Mi`, which Go refuses), at most 90% of the container limit (room for the memory the Go runtime does not count: stacks, the binary, cgo, page cache of the container), and above the old limit of 1Gi.
3. Model 1 and 2 hold for the chart alone and with the values that slot 30 of the kit passes. Slot 30 does not change: it passes only the vulnerability database's registry and repository, and no region overlay of `clusters/_template/sovereign-region/` names trivy, so both regions of a Sovereign render the same operator.
4. The scan Jobs do not change: their own resources (`trivy.resources`: requests `cpu: 100m`, `memory: 256Mi`; limits `cpu: 1`, `memory: 512Mi`), the scan concurrency (`operator.scanJobsConcurrentLimit: 2`) and the report lifetimes stay as on `main`.
5. The chart's own `version:` line is not changed: the release writer moves it after the merge.
6. `tests/operator-memory.sh` is run by CI as `bash <script> <chart dir>`, under the yq and Helm that the release pins. Its Case 1 renders the chart alone, its Case 2 renders it with the values of slot 30 as Flux passes them, and its Case 3 is its self-test: one render per rule that breaks the rule, each of which must be refused by that rule.

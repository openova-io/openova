# FND-141 — Flight workflow: one fresh installation with pre-flight and leftover sweep

## In plain words

**The problem today.** A fresh installation of a candidate is made by hand today: a person wipes the standing environment, waits, checks what the wipe left, fires the new one and starts the gate, in an order that only the runbook holds. The fire also resets the acceptance ledger before the new environment exists, against the documented order. Nothing tells anyone when a fresh installation is due.

**What changes.** One workflow runs the whole flight in order, fail-closed at every step, and its weekly run says when a flight is due. The lifecycle script gains the commands the workflow needs and a self-test, and its fire no longer resets the ledger.

**Done means:**

- Starting the workflow by hand with the one live deployment wipes it, waits for the end of the wipe, sweeps what it left, fires the candidate after the pre-flight gate and runs the gate on the new deployment, in that order.
- The workflow refuses before anything is wiped when the named deployment is not the one live deployment, when the standing deployment is younger than seven days without the stage-exit input, or when the candidate's cloud-init is over its size limit.
- The weekly run fires nothing; it fails, and says why, when a first-boot file changed since the standing candidate and that deployment is seven days old or older.
- The fire of the lifecycle script no longer resets the acceptance ledger; the reset stays as its own command for after ready.
- The lifecycle script's self-test runs without any network and makes each new command fail once.
- The guard of the parent's access lists the new workflow, so its use of that access is held to the guard's rules.

The rest of this ticket is the exact instruction for the model that does the work.

## 2. End goal
`.github/workflows/release-train.yaml` makes one flight: one fresh installation of a candidate, in the order of `docs/RUNBOOKS.md` sections 0.7 and 0.8. Started by hand with `wipe_existing` (the one live deployment) and `nodes_requested`, its job `cut` checks the rules of a flight, cuts or takes the candidate `rc/<id>` and runs the cloud-init size gate on it; job `flight` wipes the standing environment, waits for the end of the wipe, sweeps what it left and fires the candidate behind the pre-flight gate; job `ready` waits for the new deployment and checks that the gate's region kubeconfigs name it; job `gate` calls `foundation-gate.yaml` in parent execution with the deployment, the wiped one, its leftover count and the pre-flight numbers; job `verdict` prints the verdict of the records on `main`. The weekly run fires nothing and fails when a flight is due. `scripts/sovereign-lifecycle.sh` gains the commands `standing`, `wipe-result`, `wait-ready`, `kubeconfig`, `kubeconfig-match` and `--self-test`; its `fire` takes `FIRE_REQUEST`, prints `PREFLIGHT=`, `LEFTOVERS=` and `DEPLOYMENT_ID=`, and no longer resets the acceptance ledger. `scripts/check-gate-parent-access.py` lists the new workflow.

## 3. The model (the law)
1. One run is one flight: at most one fire, never retried inside the run. The concurrency group `release-train` never cancels a running flight.
2. Nothing is wiped unless `wipe_existing` names the one live deployment the mothership lists. A flight is at most one a week (the standing deployment is seven days old or older); a second flight of the standing candidate in a row needs `stage_exit`, which is not held to the seven days. A candidate that is the standing one needs `stage_exit`.
3. The cloud-init size gate (`scripts/cloudinit-size-check.sh both`) runs on the candidate before the wipe; a surface over its limit refuses the flight. The worst-case numbers and limits go into the run's summary.
4. The wipe is accepted only on HTTP 202; `wipe-result` waits for its end; `sweep` must pass; then `fire` runs the sweep once more and the pre-flight gate, and creates the deployment only after both pass. A fire that is refused leaves no environment.
5. The fire never resets the acceptance ledger; `reset-uat` stays a command for a person to run after ready (`docs/RUNBOOKS.md` section 0.3).
6. The weekly run fires nothing. It fails when a first-boot file (`infra/providers/`, `clusters/_template/bootstrap-kit/`, `scripts/expected-bootstrap-deps.yaml`) changed since the candidate of the standing deployment and that deployment is seven days old or older. A flight is started by hand because only a person names the environment it wipes.
7. The workflow has a top-level `env:` with exactly two keys, each on a line of its own: `TRAIN_CAPABILITIES` (first value `multi-region`) and `TRAIN_PROVISION_REQUEST`, a JSON object the fire merges into its request body. A later package changes these lines and nothing else of the workflow.
8. The jobs are `cut`, `flight`, `ready`, `gate`, `verdict`, in that order. No job repairs anything and no job publishes a release (FND-144 adds that after `verdict`).
9. The jobs that use the parent's access run in the environment `gate`, and the workflow is on the list of `scripts/check-gate-parent-access.py`, whose rules then hold it.
10. A new command of the lifecycle script fails closed: exit 1 on a refusal, 3 when it cannot measure, never 0 without the answer it waits for. Its self-test makes each fail once, with a stand-in for `curl` and no network.

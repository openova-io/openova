# FND-045 — The pin-sync audit names the release writer for a drift of release-owned lines and does not fail on one in flight

## In plain words

**The problem today.** A chart release reaches main as two commits: first the chart version, then, after the chart is published, the bootstrap-kit pin that names it. The hourly pin audit fails when it runs between the two, and its message tells a pull request to move the pin, which no pull request may do: only the release writer writes either line. On 26 November the hourly run failed on a release whose pin followed two and a half minutes later.

**What changes.** Every drift line names the release writer, the commit that started the drift and its age, and no text asks a pull request to move a pin. On a full sweep a drift younger than one hour is printed IN FLIGHT and passes; an older one fails as before. A self-test proves each verdict and runs in the workflow before the audit.

**Done means:**

- A chart version that passed its pin less than an hour ago is printed IN FLIGHT and does not turn the hourly run red.
- A chart version that passed its pin an hour ago or more still fails the hourly run, and so does a pin that is past its chart.
- Every drift line names the release writer workflow and the commit that started the drift, with its age.
- No message of the audit asks a pull request to change a pin.
- A pull request that moves a chart version or a pin by hand still fails, however recent the change.
- The workflow runs the audit's self-test before it runs the audit.

The rest of this ticket is the exact instruction for the model that does the work.

## 2. End goal
The pin-sync audit (`scripts/check-bootstrap-kit-pin-sync.sh`, job `pin-sync-audit` of the workflow `Test — Bootstrap Kit (kind cluster + Flux)`) tells the truth about who owns a drift. Both sides of the pair it judges, a chart's top-level `version:` and the chart pin of its kit slot, are written only by the release writer, `.github/workflows/blueprint-release.yaml`. Every `DRIFT` and `IN FLIGHT` line names that writer; no text asks a pull request to move a pin. On a full sweep (schedule, push, workflow_dispatch) a drift is timed from the commit that set the chart's version past the pin. Younger than the hourly cron it is printed `IN FLIGHT` and does not fail: the writer is between its two commits. Older, it fails as today. The pull-request mode (`--changed-only --base`) keeps its verdicts. A `--self-test` proves every verdict on a fixture repository, and the workflow runs it before the audit.

## 3. The model (the law)
1. **Both lines are release-owned.** The chart's top-level `version:` (R1) and the slot's first `      version:` line (R5) are release-owned lines of `scripts/check-release-owned-lines.py`. The release writer sets the chart version, publishes the chart, then sets the pin. The audit says so in every drift line (`the writer of both lines is .github/workflows/blueprint-release.yaml`) and in its failure text. The full-sweep fix names the writer's run and its re-run command; the pull-request fix says to take the change of these lines out of the pull request. The words `in this PR` appear in no output.
2. **The start of a drift.** On a full sweep, for a chart whose version is past its pin, the start is the newest commit on HEAD's first-parent line that changed the chart's `Chart.yaml` and whose parent held the pin value as `version:` there. A commit that created the file, or a root commit, wrote the version too, so it is the start. A later version bump keeps the start of the first commit past the pin. The walk reads at most 500 commits of that file.
3. **In flight.** The age is the current time minus the start's commit time. When `0 <= age < 3600` seconds (the hourly cron `17 * * * *` of the workflow) the line is `  IN FLIGHT <name>: chart=<v> pin=<p> (file: <slot>) — <commit 12> set the chart's version past the pin at <UTC time>, <age> s ago; the writer of both lines is .github/workflows/blueprint-release.yaml` and it does not count as a drift. The summary prints the count in flight; the final line is `PASS: no bootstrap-kit pin drift is older than the hourly cron; <n> in flight, written by .github/workflows/blueprint-release.yaml.`
4. **Still a failure on a full sweep.** An age of 3600 seconds or more; a pin that is past its chart (`sort -V`), which no release in flight does because the writer sets the chart first; and a start that is not in the history read (a shallow checkout, or more than 500 commits back). Each is a `DRIFT` line that names the writer, and the run exits 1.
5. **The pull-request mode is unchanged in its verdicts.** With `--changed-only --base <ref>` a drift the base has is `INHERITED` and passes; any other drift fails, however young, and its line says `this change moves a release-owned line`.
6. **The self-test.** `--self-test` copies the audit and its library into a fixture repository with one chart `bp-x` and its slot, and asserts the exit code, the line, the commit and the age of eleven cases: in sync; 600 s past the pin (IN FLIGHT, and its PASS line); the pull-request mode adding and inheriting a drift; a shallow clone; 7200 s past the pin; the fix text naming the writer and no `in this PR`; a later bump 60 s ago keeping the first start; a pin past its chart; a root commit. It exits 1 when one case is wrong. The job `pin-sync-audit` runs it before the audit step.
7. **The release-writer guard follows.** The case `mid-release` of `scripts/check-release-lockstep-writer.py` builds main between the two commits of an umbrella release, seconds old. It expected the full audit to exit 1 with `DRIFT`; it now expects exit 0 with `IN FLIGHT bp-catalyst-platform: chart=<v>`. The edit changes two lines in place and adds none. No new Python is written anywhere.
8. **Deleted:** the failure text `Root cause: ... was NOT bumped in lockstep.` and `Fix: either (a) update the bootstrap-kit pin in this PR to match ...` of the audit.

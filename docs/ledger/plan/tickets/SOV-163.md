# SOV-163 — The platform repositories Job runs in the primary region only and stops at once on a refused login

## In plain words

**The problem today.** The Job that creates the platform repositories in Gitea decides where it runs from two region ids that a Sovereign upgraded in place does not carry, so it runs in every region. Each region signs in with its own copy of the admin password while the regions share one Gitea database, so one region is refused, and the Job then keeps trying for up to an hour before it fails without saying why.

**What changes.** The Job runs only on the primary control plane, which every control plane knows about itself. A refused sign-in stops the Job at once with a message that names the admin user and the Secret whose password Gitea refused.

**Done means:**

- On a secondary control plane the platform repositories Job is not rendered, also when the region ids are missing or name that region the writer.
- On the primary control plane, and on a Sovereign with one region, the Job is rendered as before.
- A sign-in that Gitea refuses ends the Job after one request with exit code 3 and a message naming the admin user and the Secret gitea/gitea-admin-secret, and the Job is not retried.
- A Gitea that does not answer yet is still waited for, and any other failure is still retried.
- The render test of the chart proves each of these rules and fails when one is broken.

The rest of this ticket is the exact instruction for the model that does the work.

## 3. The model (the law)
1. **Files.** The four files of field 14 change only by the block `SOV-163.patch` at the end of field 20, byte for byte.
2. **Where the Job renders.** When `platformRepos.enabled` is true, `platformRepos.follower` is not true, and `platformRepos.writerRegionId` is empty or equals `platformRepos.regionId`. `follower` is compared as text (`toString`), so the YAML boolean `true` and the string `"true"` both mean a follower. The writer rule of SOV-160 is kept unchanged; the follower rule is added to it, so a follower never renders the Job, also when its region ids name it the writer.
3. **Slot 10** passes `platformRepos.follower: ${SECONDARY_HR_SUSPEND:=false}`, unquoted, so Flux substitutes a YAML boolean. Cloud-init writes `SECONDARY_HR_SUSPEND` on every control plane (`"false"` on the primary, `"true"` on each secondary), outside the block that writes the two region ids. A kit without the key renders the primary's value, `false`. The chart default is `follower: false`.
4. **A refused login.** Every API call of the Job checks its answer: on 401 the script prints `[platform-repos] FATAL: Gitea refused user <user> (401 on <method> <path>) with the password of Secret <namespace>/<secret> of this region.`, then one line on why (each Gitea start sets the admin password in the shared database from its own region's Secret; the region whose Gitea started last holds it; not retried), then Gitea's answer body, and exits 3. `<namespace>/<secret>` comes from the env `ADMIN_SECRET`, the release namespace and `giteaAdmin.secretName` (default `gitea-admin-secret`): the name, never the password.
5. **No retry of a refusal.** The Job spec holds `podFailurePolicy.rules` = one rule `action: FailJob`, `onExitCodes: {containerName: ensure, operator: In, values: [3]}`. The pod's `restartPolicy` is `Never`, as that field needs.
6. **Unchanged.** Any answer other than 200 and 401 to `GET /user` is still waited for, 60 times 10 seconds apart; any other failure still exits 1 and is retried up to `backoffLimit: 6` within `activeDeadlineSeconds: 3600`. The calls, their bodies, the Job's name hash, its image, its security settings and its admin Secret volume (the same name, now through one template variable) do not change. The Job never deletes or patches anything.
7. Nothing is deleted. No `Chart.yaml` and no version or pin line changes: CI writes versions after the merge (package FND-011). No Python and no Go line is added.

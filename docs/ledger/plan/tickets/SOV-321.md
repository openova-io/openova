# SOV-321 Spike: the Sovereign's own mail server on a running Sovereign (result)

Date: 2026-11-19, one session, on origin/main effdd3ea7d. Type: spike. Outcome:

- **The chart as on main sends no sign-in code, on either release.** On its pin `v0.16.3` the server ignores the chart's TOML, starts in bootstrap mode with no mail listener, and has no REST API (`404`). On `v0.15.5`, the last TOML and REST release, the server runs from the chart's file, but the setup Job cannot finish and the server presents a certificate for `localhost` only.
- **The path works on `v0.15.5` with eight measured changes.** With them the catalyst-api's own sender delivered the sign-in code over STARTTLS with the certificate checked, authenticated with the credential the setup Job mirrored, and the message was read back from the mailbox.
- **Certificate:** the submission host needs a certificate whose name covers `mail.<fqdn>` (its own or the wildcard `*.<fqdn>`; both passed) and whose issuer the catalyst-api trusts. The sender always checks it and never sends without TLS.
- **DNS record:** nothing publishes `mail.<fqdn>`. On the standing test environment the name resolves through the zone's wildcard to the gateway address, where TCP 587 does not answer.
- **Admission:** in Phase 1 everything is admitted. After the hand-over the StatefulSet is denied until its image is pulled through the proxy, and the setup Job is denied because its container declares no resource requests.

## Answer

1. **Certificate.** Yes, the sign-in code goes over STARTTLS with the certificate checked, always: Go's `net/smtp` starts TLS when offered and checks the name, the server offers `PLAIN` only after STARTTLS, and every wrong certificate failed the send (C2, C3, C4). The submission host needs a certificate (a) whose name covers the host the catalyst-api dials, `mail.<fqdn>` (its own certificate and the wildcard `*.<fqdn>` both passed, the Service name did not), (b) whose issuer the catalyst-api trusts (an issuer outside its trust store failed), (c) declared in the server's configuration and mounted into its pod (the chart declares none today).
2. **DNS record.** Nothing publishes `mail.<fqdn>`: the chart's Service has no external-dns annotation, no Service of the standing test environment has one, and the kit gives external-dns no name template. The name resolves through the zone's wildcard to the gateway address, where TCP 587 does not answer. A name only for the catalyst-api inside the cluster needs a CoreDNS pin of `mail.<fqdn>` to the mail Service's cluster address, the same mechanism as `cutover-registry-pin.server`. A public name needs an address, and the region's address pool has none free unless the Service shares it through the pool's sharing key.
3. **Admission.** In Phase 1 every object is admitted. After the hand-over, the StatefulSet is denied by `harbor-proxy-pull` until `global.imageRegistry` points at the proxy, and the setup Job is denied by `resource-requests` (and by `harbor-proxy-pull` while the image is not proxied). Everything else, the mail Service with its `nodePort: 0` included, is admitted.
4. **Principal calls.** On the pinned `v0.16.3` they cannot work: the REST API is gone (`404`) and the TOML is ignored. On `v0.15.5` the chart's calls fail in four ways (no `curl` in the image, no admin, `/api/health` is `404`, an absent principal is `200` and taken as present), and its Job then writes a mirror whose credential the server does not know (C8). With these eight changes the sign-in code was delivered (C9):
   1. a fallback admin in the TOML whose secret is the chart's `ADMIN_PASSWORD`;
   2. a setup Job image that has `curl`;
   3. the wait asks `/healthz/ready`;
   4. the Sovereign's domain is created as a principal before the submission principal;
   5. the submission principal is created when the body says `notFound`, whatever the status code (done by hand in the lab);
   6. a certificate for `mail.<fqdn>` declared in the TOML and mounted;
   7. the catalyst-api trusts its issuer (the lab used `SSL_CERT_FILE` with the lab CA);
   8. `mail.<fqdn>` resolves to the mail Service inside the cluster (the lab used a host alias).

# CLD-185 — Hetzner control-plane cloud-init with the post-back on fits the module size guard

## In plain words

**The problem today.** A Hetzner control-plane cloud-init that carries the kubeconfig post-back is larger than the module's size guard, so a real Hetzner plan stops before any server is made. The module tests pass only because their render has no post-back and is smaller than a real one. The next change to the boot template also needs about 1,200 more bytes.

**What changes.** Seven files that cloud-init writes travel gzip-packed in the boot template, which cuts about 4,500 bytes from each Hetzner render and about 2,100 from each Huawei render. A new Hetzner module test renders the post-back at real size and requires 1,200 bytes of room under each guard.

**Done means:**

- A Hetzner control-plane render with the kubeconfig post-back on stays at least 1,200 bytes under the module's size guard, for the primary and for a secondary region.
- A Hetzner module test renders the post-back at that real size; it fails on the template as it was before.
- Every file a new node writes at first boot has the same bytes and the same permissions as before; seven of them only travel packed.
- The Huawei renders get smaller, and no size guard is raised or removed.
- The stored golden hashes of the render test match the new render.

The rest of this ticket is the exact instruction for the model that does the work.

## 2. End goal
The Hetzner module can plan a real Sovereign again. Its control-plane cloud-init with the kubeconfig post-back on (a deployment identifier and a bearer token set) is today 34052 bytes for the primary region and 35184 for a secondary region, above the module's plan-time guards of 32576 and 32256 (the Hetzner hard cap is 32768). After this change seven `write_files` entries of the shared template `infra/providers/_shared/cloudinit-control-plane.tftpl` carry their text gzipped and base64-encoded, with `encoding: gz+b64`, which cloud-init decodes before it writes the file. The renders become 29475 and 30656 bytes: 3101 and 1600 bytes under the guards, enough for the about 1160 bytes that SOV-134 adds to every control-plane render. Every file on the node keeps its bytes and its mode. A new run of the Hetzner module test renders the post-back with two regions and fails when a render leaves less than 1200 bytes under its guard.

## 3. The model (the law)
1. Seven entries of `write_files` in the shared template travel packed: `/etc/rancher/k3s/registries.yaml`, `/var/lib/catalyst/ghcr-pull-secret.yaml`, `/var/lib/catalyst/harbor-robot-token-secret.yaml`, `/var/lib/catalyst/pdm-basicauth-secret.yaml`, `/var/lib/catalyst/object-storage-secret.yaml`, `/var/lib/catalyst/cloud-credentials-secret.yaml` and `/var/lib/catalyst/crossplane-provider.yaml`. Each keeps its `path` and `permissions` lines; the line after `permissions` is `    encoding: gz+b64`; its `content` is the base64 text of the gzipped file.
2. The four bootstrap Secrets (ghcr-pull, harbor-robot-token, pdm-basicauth, object-storage) keep their text lines in the template, unchanged and at the same place. The line `    content: |` becomes `    content: ${base64gzip(<<-EOT`, and the two lines `      EOT` and `    )}` follow the last line of the text. The heredoc removes the common indentation of six spaces, so the packed text is the text the plain block held.
3. The three provider-injected files (registries, cloud-credentials, Crossplane provider) are packed by one expression each: `${base64gzip(format("%s\n", chomp(replace(<input>, "/(?m)^[ ]*#( |$).*\n/", ""))))}`. The `replace` removes the comment lines that the modules remove from the plain render today (the same regular expression as the `replace` around `templatefile` in both modules). `chomp` and the one `\n` give the single final newline that the plain YAML block (`content: |`) gave.
4. A file on the node does not change by one byte, nor its mode. Every other entry of `write_files`, every `runcmd` item and every other key of the render stay as they are. No new runcmd item, no new input of the template, no change to a module, no change to what any caller passes.
5. The size guards stay exactly as they are: `infra/providers/hetzner/main.tf` is not changed (32576 for the primary render, 32256 for a secondary render, 30720 for workers).
6. The Hetzner module test `infra/providers/hetzner/tests/multi_region.tftest.hcl` gains the run `post_back_render_fits_the_size_guards_with_room`. It sets a deployment identifier, a 64-character bearer token (the length the API issues: 32 random bytes in hex) and two regions (`hel1`, `nbg1`). It asserts that both renders carry the post-back that reads `/var/lib/catalyst/parent-bootstrap.kubeconfig`, that the primary render is at most 31376 bytes and the secondary render at most 31056 bytes (each guard minus 1200), and that the packed cloud-credentials file is the provider's Secret body without its comment lines. Before the change the plan of this run fails on the guards themselves.
7. The golden values in `infra/providers/_shared/tests/golden.auto.tfvars.json` are the hashes of the new render of the two fixtures (the render text changes; the files it writes do not).
8. A comment block in the template, above the registries entry, says which files are packed and why. Comment lines are removed from the render, so the comment costs no byte.
9. Nothing is deleted.

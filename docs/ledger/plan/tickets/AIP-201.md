# AIP-201 — Node preparation for the sandbox class, exactly as the spike recorded

## In plain words

**The problem today.** The isolated runtime of the agent plane needs two certificate APIs that Kubernetes serves only from version 1.35 and only with three feature gates turned on. Lab test AIP-030 measured that this is the whole node preparation it needs. The boot templates do not carry the gates, and they cannot carry them unconditionally: a k3s server older than 1.35 refuses to start with them.

**What changes.** The boot templates turn the gates on exactly when the installed k3s line is 1.35 or later, and add nothing before that. The nodes therefore gain what the runtime needs when the routine k3s upgrades reach 1.35, without any upgrade of their own.

**Done means:**

- On the k3s version the platform installs today, the rendered boot data of every node is unchanged; the stored render values of the shared template still match.
- With k3s v1.35.10+k3s1 the control-plane boot data starts k3s with the three gates on the API server, controller manager, scheduler and kubelet and with certificates.k8s.io/v1beta1 served.
- With k3s v1.35.10+k3s1 the worker boot data of both cloud modules starts the kubelet with the three gates.
- The offline test of each cloud module fails when the gates are missing on 1.35 or present below it.
- No runtime binary, container runtime handler, RuntimeClass or kernel setting is added to any node.

The rest of this ticket is the exact instruction for the model that does the work.

## 2. End goal
The node preparation that lab test AIP-030 recorded (`docs/ledger/plan/spikes/AIP-030.yaml`, key `nodePreparation`) is carried by the boot templates as a condition on the k3s line. When a Sovereign installs k3s 1.35 or later, every control-plane node starts k3s with `--feature-gates=ClusterTrustBundle=true,ClusterTrustBundleProjection=true,PodCertificateRequest=true` on the API server, the controller manager, the scheduler and the kubelet, and with `--runtime-config=certificates.k8s.io/v1beta1=true` on the API server; every worker starts its kubelet with the same gates. Below 1.35 nothing is added, and the rendered boot data is the same bytes as before. The offline `tofu test` suites of both cloud modules prove both sides.

## 3. The model (the law)
1. The node preparation is exactly the list of the lab record: the k3s version condition, the gates on four components, the v1beta1 runtime-config. Nothing else: no `runsc` binary, no containerd handler, no RuntimeClass, no sysctl (`docs/ledger/plan/spikes/AIP-030.md`, section "What later tasks must take into account", first item).
2. The gates are a condition, not a change of their own. The nodes are not moved to a newer Kubernetes line for this package; the k3s line advances by the routine upgrade packages (SOV-725, SOV-726 and their successors). This is the decision written in `docs/ledger/plan/spikes/AIP-030.md`, section "What follows for the plan", item 1.
3. The condition is `tonumber(split(".", k3s_version)[1]) >= 35`, a template directive on the k3s command line itself. `k3s_version` is validated by every module as `vMAJOR.MINOR.PATCH+k3sN`, so element 1 is the minor. A k3s server below 1.35 does not start with the gates (v1.31 and v1.33: `unrecognized feature gate: PodCertificateRequest`; v1.34: the API is only v1alpha1 and the API server does not become ready), so the condition is required, not cautious.
4. Below 1.35 the rendered user data is unchanged byte for byte: the directive renders to nothing, and the added explanation lines are comment lines that every module strips. The golden render of the shared template keeps its stored values.
5. The server line keeps the text ` ${k3s_extra_args} ` and ends with `--write-kubeconfig-mode=0600"`; the directive stands between them. The secretbox flags and every other flag of the line do not change.
6. The shared template names no cloud. The worker lines live in each cloud module's own worker template.
7. The local pack's worker template does not change: the lab record lists the runtime for the cloud packs only (`localPack: not-measured`).
8. The Pod Security exceptions and policy exclusions of the lab record are not node preparation. They belong to the chart of the agent runtime (AIP-203).

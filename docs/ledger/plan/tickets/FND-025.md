# FND-025 — The rulesets name the release-writer key; a push outside the queue is judged by what it changes

## In plain words

**The problem today.** The release writer is now a deploy key of the repository, but the two ruleset files still name a team as the one actor allowed past them. The guard on pushes to the main branch only compares a login, and a push made with the deploy key carries the login of the person who added the key, so the guard cannot tell the release writer from that person. A new write key added by any administrator would pass the rulesets unnoticed, and the candidate cut still pushes with a token that no longer exists.

**What changes.** The ruleset files name the deploy key as their one bypass actor. The push guard judges what a push outside the merge queue changes: only version values in release-owned files and new gate records may change. The drift check also compares the repository's write deploy keys with a recorded fingerprint, and the candidate cut pushes with the deploy key.

**Done means:**

- Both ruleset files name the deploy key, and nothing else, as the actor allowed past them.
- A push to main outside the merge queue that changes only version values in release-owned files, or adds a gate record, passes the push guard, whoever it is recorded under.
- A push to main outside the merge queue that changes any other line or file fails the push guard.
- The drift check fails when the repository holds a second write deploy key, another key, or none.
- The candidate cut pushes its ref with the release-writer deploy key, and no workflow names the old token any more.
- The self-tests of both guards pass and show that every rule can fail.

The rest of this ticket is the exact instruction for the model that does the work.

1. The release-writer identity is one write deploy key of this repository; its private half is the secret `RELEASE_WRITER_KEY`. Its fingerprint is `SHA256:YZJe4pHt/nNNy1G4ukuT2aluNiXF++ZSA4x3xUn2uuM`. No team, no machine account and no token is named anywhere.

3. Because the bypass covers every write key, the drift check compares the write deploy keys with `.github/rulesets/deploy-keys.json`. A write key is one whose `read_only` is not `true`. A second write key, another key, or none is a finding. A read-only key cannot push and is not judged.
4. A push with a deploy key carries the login of the person who added the key. So the push guard does not compare logins. A push whose actor is `github-merge-queue[bot]` passes without being judged. Every other push is judged by what `git diff <before> <after>` changes, file by file:
   - P1. A gate record is a file `docs/ledger/acceptance/<name>.json`. A push may add one. It may not change or delete one.
   - P2. A site file exists before and after the push and is one of: a `Chart.yaml`, `blueprint.yaml`, catalogue-seed or slot file of the rules R1 to R5 of the `pr` command; `products/catalyst/bootstrap/api/internal/catalog/blueprints.json`; `products/catalyst/bootstrap/ui/src/shared/constants/catalog.generated.ts`; a chart's `values.yaml` or a template under `(platform|products)/<x>/chart/templates/`. In it only version values may change: in each hunk of `git diff -U0`, blank lines left out, each removed line equals the added line in the same place once quotes, a trailing ` # comment` and every version value are taken out. A version value is a sha256 digest (`sha256:` or `sha256-` and 64 hex digits), a UTC time stamp such as `2026-11-14T12:15:17.718Z`, a semantic version such as `1.4.10` or `v2.0.0-rc.1`, or a commit id of 7 to 40 hex digits.
   - Every other change is refused: an added or deleted site file, a changed gate record, any other path, and in a site file a line that changes more than a version value, or a line added or removed.
5. The job `push` stays idle until the repository variable `RELEASE_WRITER_LOGIN` exists, as today. The variable is the switch; its value is no longer read.
6. The `pr` command and its rules R1 to R5 do not change.
7. The cut of a candidate pushes `rc/<id>` with the release-writer key, because `rc.json` lets only the key create a ref under `rc/`. The secret `RELEASE_WRITER_TOKEN` is named nowhere after this ticket.
8. The drift workflow keeps the trigger `workflow_dispatch` only. No schedule is added: the drift check reads the bypass list and the deploy keys, which needs an administrator's read right, and it is run on a schedule outside this repository.
9. The `--body FILE --team-id N` command of the drift check stays as it is; with no team in the files it prints the file's body unchanged.

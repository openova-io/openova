# FND-018 — The release writer leaves main in step: no pin goes backwards, and the umbrella follows a catalogue move

## In plain words

**The problem today.** Two release runs of one chart can finish out of order, and the older one then writes its version over the newer one: on 13 November the bootstrap-kit pin of the platform chart went back from 1.4.1952 to 1.4.1951. Separately, when a component chart is released alone, its catalogue pins move inside the platform chart, but nothing releases the platform chart again, so main holds pins that no published platform chart carries and a pull-request check turns red until an unrelated image build happens to bump it.

**What changes.** Every version site the release writer touches keeps a higher version it finds, on the first write and on every retry, and the run says so and ends green. After every release run, a new job releases the platform chart again when a catalogue pin is newer than its last version, by the same bump-and-dispatch path the image builds use.

**Done means:**

- A release run of an older version that finishes after the run of a newer version leaves the bootstrap-kit pin, the Blueprint manifest and the catalogue at the newer version.
- Such a run says in its log and in its summary which site it left alone, and it finishes green.
- Versions are compared as numbers: 1.10.0 counts as higher than 1.9.9.
- When a release moves a component's catalogue pins, the platform chart gets a higher version and its own release is started, and that release moves the platform chart's bootstrap-kit pin.
- After that, the check that every catalogue pin is carried by a released platform chart passes on main.
- Several component releases close together share one platform release.

The rest of this ticket is the exact instruction for the model that does the work.

## 2. End goal
The release writer (the build job of `.github/workflows/blueprint-release.yaml`) never moves a version site backwards. When two runs of one chart finish out of order, the run of the older version finds the newer version at the kit pin, the Blueprint manifest, the catalogue seed (and with it the generated catalogue) and `Chart.yaml`, leaves each of them alone, says so in its log and summary, and ends green, on its first write and on every retry. Every comparison of two versions in the release writer goes through one helper that compares MAJOR, MINOR and PATCH as numbers. A new job `umbrella-follow` runs after every release run: when a catalogue pin on `main` is newer than the last version of the umbrella chart `bp-catalyst-platform`, it bumps the umbrella with `scripts/push-chart-version-bump.sh` and dispatches this workflow for `products/catalyst`, exactly as the image builds do; that dispatched run publishes the umbrella and moves its kit pin (slot 13). Three new cases of `scripts/check-release-lockstep-writer.py` run the workflow's own steps and prove both.

## 3. The model (the law)
1. **One version comparison.** `scripts/sync-catalog-seed-pin.py --order <present> <published>` prints `higher`, `same` or `lower`: how `<present>` compares with `<published>`, MAJOR, MINOR and PATCH each as a number (1.4.1952 is higher than 1.4.1951; 1.10.0 is higher than 1.9.9). It exits 2 when either value is not `MAJOR.MINOR.PATCH`. With `--site <text>`, a `higher` result also prints `::notice title=Newer version kept::<text> holds <present>, above the <published> this run published: left as it is (FND-018).` to standard error and appends `- Newer version kept: ...` to the file named by `$GITHUB_STEP_SUMMARY`. The Python function behind it, `version_order`, is the same function the seed rule of item 2 uses. No `sort -V` remains in the workflow.
2. **No site goes back.** A site that already holds a version higher than the one the run published is left as it is:
   - the kit pin, in the step `bump_pin` (first write) and in `rewrite_pin` of the commit step (retry);
   - `blueprint.yaml` `spec.version`, in the step `bump_blueprint` (which then outputs `bumped=false` and its `bp_file`) and in `rewrite_blueprint`;
   - the catalogue seed's `spec.version` and `source.version`, in `sync_seed()` of `scripts/sync-catalog-seed-pin.py`, which the step `sync_seed` and the retry's `resync_seed` both call; the generated catalogue is rebuilt from the Blueprint manifests and so follows them;
   - `Chart.yaml` `version:`, in `rewrite_chart` of the retry. It used to stop the run with the error `Chart version moved`; it now leaves the higher version and the run goes on.
   Each kept site is named in the log and in the summary (item 1). A run that finds every site at or above its version pushes nothing and ends green. The step `Summary` no longer says that a pin which did not move is "not in the kit": its two lines for an unmoved kit pin and an unmoved Blueprint manifest say "not moved by this run" and point at the notes.
3. **The step `bump_chart`** computes the next version from the higher of the checked-out and the `origin/main` version with the helper of item 1 instead of `sort -V`. Its result is unchanged.
4. **The concurrency group of the build job stays** `blueprint-release-${{ github.event_name }}-${{ matrix.path }}`. GitHub keeps one pending run per group and cancels the older pending one. A push run of a chart that its own build workflow versions publishes nothing (`defer=true`), so in a group shared with dispatched runs it could cancel the pending dispatched run that publishes, and that release would be lost. A comment above the group says this. Runs of one chart may therefore finish out of order, and item 2 makes that harmless.
5. **The umbrella follows a catalogue move.** A new job `umbrella-follow` (name `Umbrella follows a catalogue move (FND-018)`) needs `detect` and `build`, runs with `always()` whenever the matrix is not empty, and holds one concurrency group, `blueprint-release-umbrella-follow`, with `cancel-in-progress: false`. Its permissions are `contents: write`, `actions: write`, `pull-requests: read`. It checks out `main` with full history and runs `python3 scripts/check-umbrella-republish-gate.py --ref origin/main`:
   - exit 0: nothing to do; output `pushed=false`;
   - exit 1: it runs `scripts/push-chart-version-bump.sh products/catalyst/chart/Chart.yaml "deploy(bp-catalyst-platform): bump chart version"`, the command `catalyst-build.yaml` and `services-build.yaml` use, and on a push it outputs `pushed=true` and `next_version`; its next step then runs `gh workflow run blueprint-release.yaml --repo <repository> --ref main -f blueprint=catalyst -f tree=products`, the dispatch the image builds use;
   - any other exit: the job fails and bumps nothing.
   The dispatched run publishes the umbrella and its step `bump_pin` moves slot 13. Because the job reads `origin/main` when it starts, several releases close together share one umbrella release, and a pending job that a newer one replaces loses nothing. The gate itself is not changed and has no baseline.
6. **The proof.** `scripts/check-release-lockstep-writer.py` gains three cases. `stale`: a newer run of `platform/keycloak` lands every site first, then the steps of the older run find those values in their tree; every site must stay at the newer version, the log and the summary must name the kit slot, `platform/keycloak/blueprint.yaml` and the catalogue seed, and nothing may be pushed. `stale-retry`: the older run writes its own version first, the newer run lands before its push, and the retry resets to `origin/main`; the same must hold. `release-umbrella`: a merged change to `platform/keycloak` is released, then the steps of `umbrella-follow` run with a stand-in `gh` that answers the pull-request listing with an empty list and records the dispatch, then the dispatched umbrella run is simulated; the keycloak sites must be at the next version, the umbrella chart at a higher version, its kit pin equal to it, the dispatch recorded, and `scripts/check-umbrella-republish-gate.py --ref HEAD` must pass on the pushed tree. The harness's `run_step` also passes a case's extra environment and keeps each step's log and summary for these checks.
7. **Nothing else changes.** No chart, no version line, no pin, no catalogue file, no other workflow, no other script. All the content comes from the embedded patch.

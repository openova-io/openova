# CMP-012 — Guard: legacy policy count may only fall; the upgrade acknowledgement value is forbidden

## In plain words

**The problem today.** 47 policies of the platform still use the two old kinds that the policy engine stops executing from version 1.20 on. Nothing stops a change from adding one more. Nothing stops a change from setting the upstream chart value that lets an engine upgrade go on while such policies do nothing.

**What changes.** The existing check of old-kind policies also compares their number in each file with a baseline file, and it refuses the acknowledgement value. A change that adds an old-kind policy turns red; a change that removes one lowers the baseline in the same pull request.

**Done means:**

- A pull request that adds an old-kind policy to a chart template turns red, and the check names the file.
- A pull request that removes an old-kind policy and leaves the baseline as it was turns red, so the baseline can only go down.
- A pull request that writes the upstream acknowledgement value into a chart or cluster file turns red, and the check names the file.
- On the repository as it is, the check is green and reports 47 old-kind policies in 29 files.
- The check still refuses an engine at version 1.20 or later while an old-kind policy remains.
- The check proves on every run, on throw-away repositories, that each of its rules can fail.

The rest of this ticket is the exact instruction for the model that does the work.

## 2. End goal
The guard `scripts/check-kyverno-legacy-policies.sh`, which package FND-110 added, gets two more rules and a baseline file. Rule A: no file that Git tracks under `platform/`, `products/` or `clusters/` holds the text `acknowledgeLegacyPoliciesNotEnforced`, the upstream engine chart value that acknowledges legacy policies that are not enforced. Rule B: the number of legacy Kyverno policy objects in each chart template file equals its entry in the new file `scripts/baselines/kyverno-legacy.json`, so the number can only fall, and a change that removes a legacy policy lowers the baseline in the same change. The rule of FND-110 stays: an engine at 1.20 or later while a legacy policy object remains fails. Every run prints the line `legacy_policy_objects=<total>`; on the repository today it prints `legacy_policy_objects=47`. The step that FND-110 added to the job `check-repo-hygiene` already runs the guard and its self-test on every pull request, so no workflow changes. This package migrates, deletes and upgrades nothing.

## 3. The model (the law)
1. One definition of a legacy policy object, the one FND-110 wrote and that this package does not change: the files Git tracks whose path matches `^(platform|products)/(.*/)?templates/`; a file is cut into documents at each line that starts with `---`; a document with a line that starts with `apiVersion: kyverno.io/` holds one object per line that is exactly `kind: ClusterPolicy` or `kind: Policy` (the value may be quoted, spaces may end the line; indented and comment lines never count). Rule B counts with the same function, `legacy_counts`.
2. Rule A. The files read are the files Git tracks under `platform/`, `products/` and `clusters/`, read with `git grep -l -F`. A file that holds the text `acknowledgeLegacyPoliciesNotEnforced` anywhere is a finding, and the guard prints the line `kyverno-legacy-policies: FAIL, <path> holds acknowledgeLegacyPoliciesNotEnforced; that value is forbidden`. Files outside those three trees are not read, so the plan files under `docs/` and the guard itself, which name the value, are not findings. Rule A has no baseline: the value never appears.
3. Rule B reads `scripts/baselines/kyverno-legacy.json` from the repository root. Its form is fixed: a JSON object with exactly the keys `schema`, `counts` and `allow`; `schema` is `openova.io/guard-baseline/v1`; `allow` is the empty list (this guard takes no allow entry: every legacy object belongs to the policy-engine area and leaves); `counts` has exactly one key, `legacy_policy_objects`, whose value maps a repository path to a whole number of 1 or more. A file absent from the map is allowed zero. Any other form is a finding that names what is wrong.
4. Rule B compares each file's count with its entry. A count above its entry fails with `kyverno-legacy-policies: FAIL, <path> holds <n> legacy policy objects, the baseline allows <m>`. A count below its entry fails too, with `kyverno-legacy-policies: FAIL, <path> holds <n> legacy policy objects, the baseline still says <m>; lower the baseline in the same change`. A file at zero leaves the baseline: an entry of 0 is refused.
5. After the engine version has been read, every run prints one line `legacy_policy_objects=<total>`, where the total is the sum of all legacy policy objects. A run that cannot read the engine version stops before it, as under FND-110.
6. The guard exits 0 only when rule A, rule B and the rule of FND-110 all hold. Then its last line is the `ok` line of FND-110, unchanged. Exit code 1: a finding, or the engine version or the baseline cannot be read. Exit code 2: a wrong argument.
7. `--self-test` keeps the 26 cases of FND-110 line for line and adds 21: one failing case for each part of rules A and B, and passing cases that show what is not a finding. It builds every case in a throw-away repository; a case that brings no baseline gets the exact baseline of its own tree. It ends with the line `self-test: 47 cases passed, 0 failed`.
8. The baseline file is written by this ticket with the counts measured at the commit named in field 4: 29 files, 47 objects. Its keys are sorted and indented by two spaces, one path per line, so that a later package changes one entry by one line.
9. The guard needs bash, git, a POSIX awk, `grep`, `sed`, `tr`, `mktemp` and `python3` with its standard library. The job `check-repo-hygiene` already runs `python3`.
10. No workflow changes. The guard and the baseline are exactly the result of the patch of field 5, byte for byte. Nothing is deleted.

# SEC-162 — OpenBao 2.7.2, static seal, self-initialisation and declared audit device, as one change

## In plain words

**The problem today.** OpenBao opens with one unseal key that a setup job keeps as a Secret in the same namespace, so whoever can read that Secret owns every value in OpenBao. A second job generates a root token from that key on every upgrade, and the newer OpenBao release refuses that path, so the platform cannot upgrade. No audit device is on.

**What changes.** OpenBao moves to 2.7.2. It reads its seal key from a file on its control-plane node, opens itself after every restart, initialises an empty store by itself with a root token it throws away at once, and writes an audit line to its output for every request. The setup jobs, the unseal loop and the stored key are gone, and two gate checks prove it on every Sovereign.

**Done means:**

- A fresh installation unseals and initialises itself, with no job and no stored unseal key or root token.
- After the OpenBao pod is deleted, the new pod is open again within a minute, with no step by anyone.
- The seal key file on each control-plane node is readable by the OpenBao user only and holds 32 bytes.
- Every request to OpenBao, also a refused one, leaves an audit line in the server output.
- A request for a root token without a token is refused.
- The configuration reconciler still logs in and keeps every policy and role as before.
- Gate checks SEC-G03 and SEC-G05 are required and run on every region.

The rest of this ticket is the exact instruction for the model that does the work.

## 2. End goal
The chart `platform/openbao/chart` (bp-openbao) runs OpenBao 2.7.2 on the upstream chart 0.30.7. The server reads the seal block that the Sovereign's seal profile carries (ConfigMap `flux-system/sovereign-seal-profile`, contract `docs/contracts/c8-seal-provider.md`, written by SEC-152) from the new ConfigMap `openbao-seal-config`, and the 32-byte key file of its control-plane node from `/var/lib/catalyst/seal`, mounted read-only. It unseals itself on every start. On the first start of an empty store it initialises itself: it enables the Kubernetes auth mount, configures it, writes the policy `openbao-config-admin` and binds the role `openbao-config-admin` to the service account `openbao-config`, with a root token that OpenBao revokes at once, and it makes no recovery key. The server configuration declares the audit device `stdout/`. The chart has no init Job, no auth-bootstrap hook, no recovery-seed Secret, no unseal loop and no root-generation script. The gate checks SEC-G03 (seal) and SEC-G05 (audit) are `required` and implemented in `tests/acceptance/sovereign/internal/suite/check_sec_seal.go`. A new kind workflow proves the fresh path in a real pod on every pull request that changes the chart.

## 3. The model (the law)
1. The upstream dependency is `openbao` 0.30.7 (`Chart.yaml`); `values.yaml` pins the server image tag `2.7.2` and keeps `catalystBlueprint.upstream.version` equal to the dependency.

The update strategy stays `OnDelete`. The agent injector is off.
3. New template `templates/seal-config.yaml`: ConfigMap `openbao-seal-config` with `seal.hcl` (the value `seal.stanza`, trimmed), `initialize.hcl` (only when `selfInit.enabled`, default true) and `audit.hcl` (only when `audit.enabled`, default true). With an empty `seal.stanza` (the chart default) nothing renders: the server pod cannot mount the ConfigMap and does not start. It fails closed and never comes up with a Shamir seal. 4. `initialize.hcl` holds one block `initialize "platform"` with four `update` requests, in this order: `sys/auth/<mount>` `{type = "kubernetes"}`; `auth/<mount>/config` `{kubernetes_host = "https://kubernetes.default.svc"}`; `sys/policies/acl/openbao-config-admin` with the text of `openbao.configAdminPolicy` as one JSON-quoted string; `auth/<mount>/role/openbao-config-admin` bound to service account `openbao-config` of the release namespace only, policy `openbao-config-admin`, `token_ttl = "15m"`, `token_max_ttl = "1h"`. `<mount>` is `kubernetesAuth.mountPath` (default `kubernetes`). The policy text equals the payload of the first operation of the reconciler's desired state, so a later chart version changes it through the reconciler.
5. `audit.hcl` is exactly the file device `stdout/` with `file_path = "stdout"` and the description "Audit to standard output; collected by the log pipeline.". Nothing in the chart enables an audit device through the API.

+## Bootstrap Procedure
+
+1. Catalyst bootstrap (Phase 0 of Sovereign provisioning) deploys OpenBao as **independent Raft cluster per region** (no stretched cluster — see [`docs/SECURITY.md`](../../docs/SECURITY.md) §5).
+2. **Seal (SEC-162, OpenBao 2.7.2, upstream chart 0.30.7):** cloud-init writes a 32-byte key file `/var/lib/catalyst/seal/openbao-seal-<id>.key` (mode 400, owner `100:1000`) on every control-plane node and applies ConfigMap `flux-system/sovereign-seal-profile`, whose key `stanza` is the seal block (contract [`docs/contracts/c8-seal-provider.md`](../../docs/contracts/c8-seal-provider.md)). Bootstrap-kit slot 08 passes that stanza to `seal.stanza` through `valuesFrom`. The chart renders it into ConfigMap `openbao-seal-config` (`chart/templates/seal-config.yaml`); the server loads that ConfigMap as an extra configuration directory and mounts the node directory read-only at `/openbao/seal`. The server runs on control-plane nodes only and unseals itself on every start, with no step by anyone. No Secret holds a key, and there is no init Job and no unseal loop. Without a stanza no `openbao-seal-config` renders and the server pod does not start: it fails closed and never comes up with a Shamir seal.
+3. **Self-initialisation:** on the first start of an empty store the `initialize` block of `openbao-seal-config` (`selfInit.enabled`, default on) enables the Kubernetes auth mount (`kubernetesAuth.mountPath`), points it at the in-cluster API server, writes policy `openbao-config-admin` and binds role `openbao-config-admin` to the service account `openbao-config` of the release namespace (token TTL 15m, max 1h). OpenBao runs it with a root token that it revokes at once, and it makes no recovery key. An initialised store never runs it again. The server's service account holds `system:auth-delegator` (`chart/templates/auth-delegator-rbac.yaml`) for the token reviews.
+3a. **Declarative configuration (1.2.72, ADR-0015, Refs #7067):** every ACL policy, auth role, auth mount and identity object the chart needs is desired state in ConfigMap `openbao-config-desired` (`chart/templates/_config.tpl`). The `openbao-config` Deployment applies it every 60 s, idempotently (`chart/files/openbao-config-reconcile.sh`). It logs in as k8s-auth role `openbao-config-admin`, whose policy covers configuration surfaces only: no secret data, no `sys/raw`, no seal, no delete. It can rewrite its own policy, which is the first operation of the desired state, but not its own role, and the only secrets mount it may enable is `secret/`. In every payload it replaces the text `AUTH_ACCESSOR_KUBERNETES` by the accessor of its login mount. A chart bump is therefore the whole change; there is no root token and no manual root step. Configure under `kubernetesAuth.*`.
+3b. **Audit:** the server configuration declares the file audit device `stdout/` writing to standard output (`audit.enabled`, default on). OpenBao 2.7 refuses an audit device enabled through the API.
+4. Between regions peer push is configured (see the architecture section above). OpenBao does not replicate.
+5. ESO configured with local-region ClusterSecretStores; every region reads from its local OpenBao replica via ESO Kubernetes auth (TokenReview), never cross-region.
+6. Initial secrets created via K8s + PushSecrets, never plaintext in Git.
+
+**No SOPS:** Credentials entered interactively during bootstrap, never stored in Git. See [`docs/SECURITY.md`](../../docs/SECURITY.md).
+
+**Existing Sovereigns:** a store initialised with the Shamir seal of chart 1.2.x is not opened by this chart; its migration is a procedure of its own (SEC-170). A test Sovereign is provisioned again instead.

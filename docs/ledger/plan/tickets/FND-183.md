# FND-183 — Scheduled backups of the platform databases

## In plain words

**The problem today.** No platform database is copied anywhere. The shared database chart renders its database clusters with no backup, so a lost region or a lost volume loses every row of the platform's databases. Decision record 0036 fixes the schedule, the retention and the place in the bucket, and nothing builds it.

**What changes.** The shared database chart gives each database cluster it renders a continuous archive of its write-ahead log and a daily base backup in the Sovereign's bucket, as soon as its installation names the bucket. The Secret register lists the Secret that holds the bucket's key pair.

**Done means:**

- An installation that names the bucket gets one daily base backup per database cluster at 02:00 and a continuous archive of the write-ahead log, kept 30 days.
- The copies of a cluster lie under database/<region>/<namespace>/<cluster>/ of the bucket, so two regions and two clusters never share a path.
- The bucket's key pair is read from a Secret in the cluster's namespace that the Secret register lists; the chart writes no Secret.
- An installation that names the bucket but leaves out its endpoint, the region or the Secret fails to render instead of running without a copy.
- An installation that names no bucket renders exactly what it renders today.

The rest of this ticket is the exact instruction for the model that does the work.

## 2. End goal
The chart `platform/postgres/chart` gives every database cluster it renders the database row of decision record 0036 as soon as the installation names the Sovereign's bucket (`backup.objectStore.bucket`): the cluster archives its write-ahead log continuously and a `ScheduledBackup` takes a base backup daily at 02:00, both under `s3://<bucket>/database/<region>/<namespace>/<cluster>/`, with a recovery window of 30 days. ## 3. The model (the law)
1. **Values** (`platform/postgres/chart/values.yaml`, new block `backup`): `schedule` `"0 0 2 * * *"` (the operator's six fields, seconds first), `retentionPolicy` `"30d"`, `region` `""`, `objectStore.bucket` `""`, `objectStore.endpoint` `""`, `objectStore.secretName` `object-storage`. There is no `enabled` value: a backup needs a bucket, and naming the bucket is what switches it on. No chart version change.
2. **Without a bucket nothing changes.** With `backup.objectStore.bucket` empty no `ScheduledBackup` renders and no Cluster carries `spec.backup`; every other object renders as before.
3. **With a bucket, the rest is required.** `backup.region`, `backup.objectStore.endpoint` and `backup.objectStore.secretName` must be non-empty, or the render fails with `bp-postgres: backup.<key> is required when backup.objectStore.bucket is set`. A half-wired installation never runs without a copy.
4. **The Cluster** that the release renders (the primary or singleton of `templates/cluster.yaml`, or the replica half of `templates/replica-cluster.yaml`; exactly one per release) carries `spec.backup.retentionPolicy` = `backup.retentionPolicy` and `spec.backup.barmanObjectStore` with `destinationPath` `s3://<bucket>/database/<region>/<namespace>`, `serverName` = the Cluster's own name, `endpointURL` = `backup.objectStore.endpoint`, and `s3Credentials` `accessKeyId`, `secretAccessKey` and `region` from the Secret `backup.objectStore.secretName`, keys `s3-access-key`, `s3-secret-key` and `s3-region` (the keys of the Sovereign's object-storage Secret, `clusters/_template/bootstrap-secrets/object-storage.yaml`). So the copies lie under `database/<region>/<namespace>/<cluster>/`, record 0036 B1.
5. **The ScheduledBackup** `<cluster>-daily` in the Cluster's namespace (new `templates/backup.yaml`, same render gates as the Cluster): `schedule` = `backup.schedule`, `method: barmanObjectStore`, `backupOwnerReference: self`, `immediate: true` (one base backup when it is created, so that the archive has a base from the start), `cluster.name` = the Cluster's name.
6. **No Secret object in the chart.** The operator takes a static object-store key only as a Secret reference (record 0036 B3). The chart references the Secret and renders none: no new line `kind: Secret` in a chart template (guard G3) and no new line naming a key reference of the guard G10 count. The Secret is register entry `database-backup-bucket`: namespace `shared-data`, name `^object-storage$`, class K, removal `none`, review by `2027-11-01`.
7. **The test** `platform/postgres/chart/tests/backup-render.sh` prints `  PASS  B1 ` to `  PASS  B6 `: B1 the default render; B2 the singleton with a bucket (law 4, law 5, no Secret rendered); B3 the replica half; B4 the three required values; B5 a changed schedule and retention; B6 the register entry. It needs helm and yq and no Python.

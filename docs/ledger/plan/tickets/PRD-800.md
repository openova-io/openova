# PRD-800 — Adapter template for a second bank

## In plain words

**The problem today.** The open-banking product reaches core banking only through its ledger port, and a bank or a partner must write the program that serves that port in front of its own core-banking system. Today nothing shows them where to start: there is no starting program and no description of what each operation needs from core banking.

**What changes.** The product gains an adapter template, a small program that serves every operation of the port and answers that each one is not implemented yet, and a guide that says what core banking must supply for each operation and how to prove the adapter with the conformance program.

**Done means:**

- The adapter template builds and serves the ledger port over TLS, with a health service.
- Every operation of the template answers that it is not implemented, except the capabilities, which name nothing.
- The conformance kit run against the template fails with exactly two findings: the capabilities name no currency, and the thirteen operations the template does not serve are never called.
- The guide names, for each of the fourteen operations of the port, what the core-banking system must supply, and shows the output of the conformance program against the template as it is.
- Every test of the product passes on the pull request, and the linter and the security scan find nothing new.

The rest of this ticket is the exact instruction for the model that does the work.

## 2. End goal
The open-banking product `products/fingate` has an adapter template and a guide for the authors of ledger adapters. The folder `products/fingate/adapter-template` is a Go program that serves the ledger port `openova.fingate.ledger.v1.Ledger` over gRPC and TLS, with the standard gRPC health service. Every operation of the port answers `UNIMPLEMENTED`, except `GetCapabilities`, which answers empty lists. The conformance kit run against the template fails with exactly two failed checks: `capabilities: currencies is empty` and `every-operation-called: not called:` followed by the 13 operations the template does not serve, and a test asserts this. The guide `products/fingate/docs/writing-an-adapter.md` maps each of the 14 operations of the port to what a core-banking system must supply, and tells the author to run the conformance program until it passes. An author copies the folder into a repository of their own and fills in the operations one by one.

## 3. The model (the law)
1. **The program** `products/fingate/adapter-template`, package `main`, in the Go module `products/fingate` (no `go.mod` of its own). File `main.go`: flags `--listen` (default `:8443`), `--cert-file` and `--key-file` (PEM files, both required). The certificate is read once, at start. TLS 1.2 is the lowest version accepted. The server registers the ledger port and the standard gRPC health service, `SERVING` for the empty service name and for `openova.fingate.ledger.v1.Ledger`. On SIGTERM or SIGINT it stops: health goes to `NOT_SERVING`, calls in flight get 10 seconds. Exit code 0: stopped by a signal; 1: the server failed while it served; 2: it could not start.
2. **The ledger** (file `ledger.go`). The type `ledger` embeds `ledgerv1.UnimplementedLedgerServer` and writes each of the 14 operations as a method of its own, with a comment that names what the core-banking system must supply. `GetCapabilities` returns empty lists of resources, payment types and currencies. Each other method returns the gRPC code `UNIMPLEMENTED` with the message `<operation> is not implemented by this adapter yet`.
3. **The tests.** `ledger_test.go` and `main_test.go` use only public packages (the port's generated code and gRPC), so an author's copy keeps them: every operation is called and answers as rule 2 says, the list of operations called equals the port's; the program serves the port and the health service over TLS and stops with exit code 0; a wrong start ends with exit code 2. `kit_test.go` is the platform repository's own check and imports the internal package `internal/ledgertest`; the guide tells the author to delete it in a copy. Its test `TestKitFailsWithTheUnimplementedOperations` runs the kit against the template and asserts that the failed checks are exactly these two lines, in this order:
   ```
   capabilities: currencies is empty
   every-operation-called: not called: ResolveCustomer, ListAccounts, GetAccount, ListBalances, ListTransactions, ListBeneficiaries, ListStandingOrders, ListDirectDebits, ListScheduledPayments, GetParty, CheckFunds, SubmitPayment, GetPayment
   ```
   and that the kit called `GetCapabilities` only.
4. **The guide** `products/fingate/docs/writing-an-adapter.md`: how to start from the template; the rules for every operation (transport, formats, error codes, pages); one paragraph per operation with what core banking must supply; how to build and run `fingate-ledger-conformance` against an adapter with a fixture; and the exact output of that program against the template as it is.
5. **No adapter of a named core-banking product** is added to this repository. A real adapter is written in the bank's or a partner's repository.
6. **No new dependency.** The code uses `google.golang.org/grpc v1.85.0` (with its packages `health` and `test/bufconn`) and `google.golang.org/protobuf`, which `products/fingate/go.mod` already requires. `go.mod` and `go.sum` do not change.
7. **No poll and no generated code.** No file of the change calls `time.Sleep`, `time.Tick` or `time.NewTicker`, and none holds a `//go:generate` directive.
8. **No build output in the tree.** `go build` is always run with `-o /dev/null` in this ticket. A plain `go build ./...` inside the folder writes the program `adapter-template` into it; that file is not part of the change.
9. Nothing else changes: the port, the kit, the conformance program, the test bank of PRD-502, the product's `README.md`, every workflow and every baseline stay as they are.

```go
// Command adapter-template is the starting point of a ledger adapter: a program that serves the
// ledger port of the open-banking product, openova.fingate.ledger.v1.Ledger, over gRPC and TLS,
// in front of one bank's core-banking system.
//
// As it is, every operation answers UNIMPLEMENTED and GetCapabilities answers empty lists. The
// author of an adapter copies this folder into a repository of their own and fills in the
// methods of ledger.go, one operation at a time, until the conformance program
// fingate-ledger-conformance passes against it. The guide is
// products/fingate/docs/writing-an-adapter.md in the platform repository.
//
// Usage:
//
//	adapter-template --cert-file <tls.crt> --key-file <tls.key> [--listen :8443]
//
// The certificate and key are PEM files. They are read once, at start. The server also answers
// the standard gRPC health service, for the empty service name and for
// openova.fingate.ledger.v1.Ledger. It stops on SIGTERM or SIGINT.
//
// Exit codes: 0 stopped by a signal; 1 the server failed while it served; 2 it could not start
// (a wrong flag, a certificate that cannot be read, an address that cannot be listened on).
package main

import (
	"context"
	"crypto/tls"
	"errors"
	"flag"
	"fmt"
	"io"
	"net"
	"os"
	"os/signal"
	"path/filepath"
	"syscall"
	"time"

	"google.golang.org/grpc/credentials"
	"google.golang.org/grpc/health"
	healthpb "google.golang.org/grpc/health/grpc_health_v1"

	ledgerv1 "github.com/openova-io/openova/products/fingate/api/ledger/v1"
)

// stopGrace is how long a stop waits for calls in flight before it closes every connection.
const stopGrace = 10 * time.Second

func main() {
	ctx, stop := signal.NotifyContext(context.Background(), syscall.SIGTERM, os.Interrupt)
	defer stop()
	os.Exit(run(ctx, os.Args[1:], os.Stderr, nil))
}

func run(ctx context.Context, args []string, stderr io.Writer, listening func(net.Addr)) int {
	fs := flag.NewFlagSet("adapter-template", flag.ContinueOnError)
	fs.SetOutput(stderr)
	listen := fs.String("listen", ":8443", "the address to serve the ledger port on")
	certFile := fs.String("cert-file", "", "the PEM file of the server certificate; required")
	keyFile := fs.String("key-file", "", "the PEM file of the certificate's private key; required")
	if err := fs.Parse(args); err != nil {
		return 2
	}
	usage := func(err error) int {
		_, _ = fmt.Fprintf(stderr, "adapter-template: %v\n", err)
		return 2
	}
	if fs.NArg() > 0 {
		return usage(fmt.Errorf("unexpected argument %q", fs.Arg(0)))
	}
	if *certFile == "" || *keyFile == "" {
		return usage(errors.New("--cert-file and --key-file are required"))
	}
	cert, err := tls.LoadX509KeyPair(filepath.Clean(*certFile), filepath.Clean(*keyFile))
	if err != nil {
		return usage(err)
	}
	lis, err := net.Listen("tcp", *listen)
	if err != nil {
		return usage(err)
	}

	creds := credentials.NewTLS(&tls.Config{MinVersion: tls.VersionTLS12, Certificates: []tls.Certificate{cert}})
	s := grpc.NewServer(grpc.Creds(creds))
	ledgerv1.RegisterLedgerServer(s, newLedger())
	hs := health.NewServer()
	hs.SetServingStatus(ledgerv1.Ledger_ServiceDesc.ServiceName, healthpb.HealthCheckResponse_SERVING)
	healthpb.RegisterHealthServer(s, hs)
```

````markdown
# Writing a ledger adapter

The open-banking product reaches core banking through one typed port, the gRPC service `openova.fingate.ledger.v1.Ledger` in [`api/ledger/v1/ledger.proto`](../api/ledger/v1/ledger.proto). A ledger adapter is a program that serves this port in front of one bank's core-banking system. The product's own test bank, which serves made-up data, is the first adapter. The adapter of a real core-banking system is written in the bank's or a partner's own repository, never in this one.

This guide says what the core-banking system must supply for each operation of the port, and how to prove the adapter with the conformance program.

## Start from the template

1. Copy the folder [`adapter-template`](../adapter-template) into your repository. It is a complete program: it serves the port over gRPC and TLS, with the standard gRPC health service, and stops on SIGTERM. Every operation answers `UNIMPLEMENTED`, and `GetCapabilities` answers empty lists.
2. Delete `kit_test.go` in your copy. It imports the conformance kit, an internal package of this repository, and builds only here.
3. Keep the import path of the port package, `github.com/openova-io/openova/products/fingate/api/ledger/v1`. It lies in the Go module `github.com/openova-io/openova/products/fingate`: require that module at the commit of this repository whose port you serve. Never edit the generated files of the port.
4. Fill in the methods of `ledger.go`, one operation at a time, in the order of the sections below. Each method's comment names what the core-banking system must supply.
5. Run the conformance program after each operation (see "Prove the adapter"). The adapter is done when it exits with code 0.

The template reads its certificate once, at start. If your certificate issuer renews the files in place, serve the certificate through `GetCertificate` of `tls.Config` and read the files again when their modification time has changed.

## Rules for every operation

- **Transport.** gRPC over TLS 1.2 or later. The certificate comes from the Sovereign's internal issuer or is one the bank supplies.
- **Formats.** An amount is a decimal string that matches `^\d{1,13}$|^\d{1,13}\.\d{1,5}$`. A currency is an ISO 4217 code of three capital letters. A time is RFC 3339. A credit or debit indicator is `Credit` or `Debit`.
- **Error codes.** `NOT_FOUND`: an unknown customer, account or payment. `PERMISSION_DENIED`: the account exists but is not the customer's. `FAILED_PRECONDITION`: the bank refuses the payment; the status message says why. `UNIMPLEMENTED`: a resource or payment type that `GetCapabilities` does not name. `UNAVAILABLE`: the core-banking system cannot answer now and a retry is safe. `ALREADY_EXISTS`: an idempotency key reused with different content.
- **Pages.** A list request carries `page_token` and `page_size`. Return at most `page_size` items and a `next_page_token`; an empty `next_page_token` ends the list. Walking a list with pages of one and with pages of two must give the same items in the same order, and no item twice.
- **What the port does not carry.** The port has no consent, subscription, token or event operation. Version 1 carries domestic payments only: immediate, scheduled and standing order.

## What each operation needs from core banking

**GetCapabilities.** The optional resources the bank serves, any of `beneficiaries`, `standing-orders`, `direct-debits`, `scheduled-payments` and `party`; the payment types, any of `domestic`, `domestic-scheduled` and `domestic-standing-order`; and the currencies of its accounts, at least one. No value may repeat. Fill this in first: the conformance kit stops here while the list of currencies is empty.

**ResolveCustomer.** A lookup from the identity a customer signed in with, a `scheme` and a `subject` (and optional `attributes`), to the bank's own customer identifier, returned as `customer_id`, with a `display_name`. An unknown subject is `NOT_FOUND`. Two different people resolve to two different identifiers.

**ListAccounts.** Every account of the customer: identifier, currency, type and sub-type, nickname, scheme name and identification (such as a sort code and account number), holder name, status and opening time. An unknown customer is `NOT_FOUND`.

**GetAccount.** One account of the customer, field for field the same as its entry in `ListAccounts`. An unknown account is `NOT_FOUND`; another customer's account is `PERMISSION_DENIED`.

**ListBalances.** At least one balance per account, each with its type code, amount and currency, credit or debit indicator and the time it was taken.

**ListTransactions.** The booked transactions of one account, in pages, between the times `from` and `to`: identifier, amount, credit or debit indicator, status, booking time, value time, information, reference, counterparty name and identification, and the balance after the transaction where the bank has it. The conformance run needs an account of its test customer with at least two transactions.

**ListBeneficiaries, ListStandingOrders, ListDirectDebits, ListScheduledPayments.** Optional, one per resource of `GetCapabilities`. The payees saved on an account; its standing orders with frequency, next and final payment, creditor and status; its direct-debit mandates with the previous collection; its future-dated payments with execution time, amount and creditor. A resource the bank does not serve is left out of `GetCapabilities`, and its operation keeps answering `UNIMPLEMENTED`.

**GetParty.** Optional, resource `party`. The customer when `account_id` is empty, otherwise the holder of that account: identifier, type, name, e-mail and phone.

**CheckFunds.** Whether one account of the customer can pay an amount in its currency now, and the time of that answer.

**SubmitPayment.** The bank accepts one payment of a type that `GetCapabilities` names: debtor account, amount, creditor name, scheme and identification, reference, end-to-end identifier, an execution time for a scheduled payment, and the recurrence for a standing order (frequency code, first payment time, number of payments, first amount). It answers with a payment identifier, a status (`pending`, `accepted`, `settled` or `rejected`) and the time of that status. The same idempotency key with the same content returns the same payment; the same key with other content is `ALREADY_EXISTS`. A payment the account cannot make is `FAILED_PRECONDITION` with a message.

**GetPayment.** The current status of a payment that `SubmitPayment` returned. An unknown payment is `NOT_FOUND`.

## Prove the adapter

The conformance program `fingate-ledger-conformance` calls every operation of the port and prints one line per check, `PASS` or `FAIL` with the reason, then the number of checks passed and of operations called. It submits real payments: run it against a test system of the bank only, never against customers' accounts.

1. Build the program in a checkout of this repository:
   ```sh
   cd products/fingate && go build -o /tmp/fingate-ledger-conformance ./cmd/fingate-ledger-conformance
   ```
2. Write the fixture, a JSON file that describes the test data of your system: `customer` and `other_customer` (each an object with `scheme` and `subject`, resolving to two customers that both hold an account), `debtor_account_id` (an account of `customer`), `amount` (an amount that account can pay), `refused_amount` (an amount it cannot pay), and `creditor_name`, `creditor_scheme_name` and `creditor_identification` (the payee of every test payment). An unknown key is an error.
3. Start your adapter, then run the program against it:
   ```sh
   /tmp/fingate-ledger-conformance --target <host:port> --fixture <fixture.json> --ca-file <ca.pem>
   ```
   Exit code 0: every check passed. 1: a check failed. 2: the run could not start.

```

As you fill in the operations in the order of this guide, the kit gets further: more checks run, and each operation it reaches leaves the `not called` line. The adapter is done when the program exits with code 0 and prints `operations called: 14/14`.
````

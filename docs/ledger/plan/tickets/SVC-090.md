# SVC-090 — Function tests: network, names and edge charts

## In plain words

**The problem today.** The network, the gateway definitions, the name server, the DNS writer, the gateway listener values, the secondary-region routes and the two network-policy charts count as working when their objects exist. Nothing tests that names resolve and Services answer, that the zones are served with authority, that the routes are accepted, or that the default deny and the per-namespace isolation really keep traffic out.

**What changes.** Each of the eight charts gets one test Pod that asks the service it installs a question, or tries a connection that must be refused, and checks the answer. A render check per chart holds the Pod to the contract. The existing policy check of the plane-isolation chart learns to ignore the new test folder and the test objects.

**Done means:**

- Each of the eight charts renders one test Pod with the hook test, a deadline of 300 seconds and the restart policy Never, and renders none where its own gate switches it off.
- Each test asks its service a question and checks the answer; the two policy tests check that a connection from outside the allowed namespaces is not made.
- A render test per chart fails when that chart's test Pod breaks the contract, and it runs on every pull request that changes the chart.
- The service-model guard counts eight more charts with a function test.
- Every test policy that limits where its Pod may send lets it reach cluster DNS, and the network guard lists each test file outside the policy chart that brings a policy as a named exception of this task.
- The policy check of the plane-isolation chart passes with the test folder present, and still fails when a policy template asks the cluster for data or the chart renders an object it does not expect.

The rest of this ticket is the exact instruction for the model that does the work.

## 3. The model (the law)
1. **The contract.** It is section 4.5 of `docs/RUNBOOKS.md` and the checker `scripts/check-function-test.py` (package SVC-060; package SVC-070 added ClusterRole and ClusterRoleBinding to the kinds allowed beside the Pod). A chart that has a function test ships one file `chart/templates/tests/function-test.yaml`. It renders one Pod named `<release>-function-test`, with the annotations `helm.sh/hook: test` and `helm.sh/hook-delete-policy: before-hook-creation,hook-succeeded`, the label `catalyst.openova.io/function-test: "true"`, `restartPolicy: Never` and `activeDeadlineSeconds: 300`. It exits 0 on pass and non-zero on fail, and its last line is `FUNCTION-TEST <pass|fail> <chart name> <reason>`. It needs nothing outside the cluster, uses an image the chart already uses or one the kit already pulls, renders nothing when the chart's own gate renders nothing, never creates a Secret, and every container requests cpu and memory. Every network call of a test has a time limit, so each test ends well inside its 300 seconds.
2. **The eight tests.** Each `function-test.yaml` is the block of field 5 of the same name, byte for byte. The image of each is `harbor.openova.io/proxy-dockerhub/alpine/k8s:1.31.4`, or `functionTest.image`.

The ServiceAccount of the file has no binding. |
   | `bp-gateway-api` | always (no master gate) | the discovery document `/apis/gateway.networking.k8s.io/v1` lists the resource `gateways`, and the definition `gateways.gateway.networking.k8s.io` has the annotation `gateway.networking.k8s.io/bundle-version` equal to the chart's annotation `catalyst.openova.io/upstream-gateway-api-version` and the condition `Established` `True`.

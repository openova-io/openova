# CTL-223 — Settings, Menu accepts console pages as menu candidates

## In plain words

**The problem today.** The left menu of the Sovereign console can only offer two kinds of candidates: a Blueprint that declares a console entry, and an installed Application with a user interface. A console page that no Blueprint delivers, such as a filtered view of Resources, cannot be offered to the sovereign-admin at all, so the only way to put it on the left would be a fixed menu entry that every Sovereign gets.

**What changes.** The API gains a list of console pages that are menu candidates, kept in a new package beside the handler, and Settings, Menu and the left menu accept these candidates. The list starts empty; later tasks add their pages to it.

**Done means:**

- The menu candidate list of the API has a third source, page, whose identifiers have the form page:<name>.
- A page candidate is off until the sovereign-admin switches it on, and can then be renamed, ordered and nested under a fixed menu item like any other candidate.
- Saving an override for a page identifier that no listed page carries is refused with a message that names the identifier.
- An Organization console never receives or shows a page candidate.
- Settings, Menu shows a page candidate with the source page, and the left menu shows it once it is switched on.
- The handler package of the API is smaller than before, and no fixed entry is added to the left menu.

The rest of this ticket is the exact instruction for the model that does the work.

## 2. End goal
The page Settings, Menu of the sovereign-admin console lists menu candidates of three sources: `blueprint`, `application` and the new `page`. A candidate of source `page` comes from the list `pages` of the new Go package `products/catalyst/bootstrap/api/internal/consolemenu`: its identifier is `page:<name>`, its label, route, order and icon come from the list, and it is off by default. `GET /api/v1/sovereigns/{id}/console-ui/sidebar-entries` returns it after the Blueprint and Application candidates, but never to an Organization session. `PUT /api/v1/sovereigns/{id}/console-ui/sidebar-overrides` accepts an override of a listed page and refuses an override of a page identifier that the list does not hold. The console keeps the source `page` (it no longer turns an unknown source into `blueprint`), Settings, Menu shows it with its own badge, and the left menu renders a page candidate once it is switched on. The list starts empty: this ticket adds the source, not a page. The handler package of the API shrinks by 16 lines, because the wire type of an entry moves into the new package, and its baseline is lowered by its own guard.

## 3. The model (the law)
1. A menu candidate has exactly one of three sources: `blueprint`, `application` or `page`. The names are the constants `SourceBlueprint`, `SourceApplication` and `SourcePage` of `internal/consolemenu`.
2. A candidate of source `page` comes from one line of the list `pages` in `internal/consolemenu/consolemenu.go`. A line is a `Page`: `Name` (lower-case letters, digits and hyphens, a letter or a digit at each end, at most 63 characters), `Label` (at most 40 characters, not empty), `Route` (a console path that starts with one `/` and holds no space), `Order` (0 to 100) and `Icon` (an SVG path in the form of `spec.consoleUI.sidebarIcon`, may be empty). The test `TestPages_TheListIsValid` checks every line with `CheckPages`.
3. The list starts empty: `var pages = []Page{}`. This ticket adds no page. Its tests prove the source with the test entry `page:test-view`, which exists in the test files only.
4. The candidate of a page has the identifier `page:<Name>`, its label, route, order and icon from the line, `enabled: false` and `defaultEnabled: false`. `collectSidebarDefaults` puts the page candidates after the Blueprint and Application candidates, in the order of the list as `consolemenu.Pages()` returns it (sorted by name).
5. An override of a page candidate works like any other: it switches the page on, renames it, re-routes it, orders it and nests it under a mappable fixed item. The stored shape of an override (`entries[]` with `id`, `enabled`, `label`, `route`, `order`, `parent`) and the ConfigMap `catalyst-system/console-ui-sidebar` are unchanged.
6. The identifier rule admits a Blueprint name, `app:<application-name>` and `page:<page-name>`; its error text names the three forms. An override whose identifier starts with `page:` and names no page of the list is refused with the problem `entries[<i>].id: page:<name> is not a console page of this Sovereign`. Blueprint and Application identifiers are not checked against what exists, as before.
7. An Organization session never gets a candidate of source `page`. On the server `blueprintSourcedOnly` keeps source `blueprint` only; in the console the filter of `visibleEntries` in `SovereignSidebar.tsx` keeps source `blueprint` only. Both already do that and are not changed in code; their comments now name page candidates.
8. The wire shape of a merged entry is unchanged. The struct moves from `console_ui.go` to `consolemenu.Entry` with the same fields and the same JSON names; `console_ui.go` keeps the name `SidebarEntry` as a type alias. The limits of a label and an order become the constants `LabelMaxRunes`, `OrderMin` and `OrderMax` of the new package, with the same values 40, 0 and 100.
9. The handler package does not grow. `console_ui.go` loses 16 lines net. The entry `handler_lines` of `scripts/baselines/api-structure.json` is lowered by exactly 16 by the guard itself (`--write-baseline`), and no other entry changes.
10. No fixed menu entry is added. `products/catalyst/bootstrap/ui/src/pages/sovereign/sovereignNav.ts` is not changed, and `SovereignSidebar.tsx` changes in two comments only.
11. The console type `SidebarEntrySource` is `'blueprint' | 'application' | 'page'`. `normaliseEntry` keeps `page` as `page`. Settings, Menu shows a page candidate with an emerald badge that reads `page`, and its text says that listed console pages are candidates too. The title of the Reset button of a row reads `Reset this entry to its default`, because a default is no longer only that of a Blueprint or an Application.

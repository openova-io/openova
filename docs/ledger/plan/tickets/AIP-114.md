# AIP-114 — Scripted back end: the stub subcommand

## In plain words

**The problem today.** The alias for gate checks needs a back end that answers without any credential and with token counts a check can compute. The model meter has no such back end today, so no check can prove a tool round trip or a metered stream end to end.

**What changes.** The meter binary gains a second mode that is a small scripted model: it echoes the caller, or calls the first tool it is offered, and reports token counts from a fixed formula. Tests prove its answers, its streams and that the meter publishes exactly the formula for a call on it.

**Done means:**

- The command model-meter stub listens on port 8081 and stops cleanly on SIGTERM.
- A request with tools gets one call of the first tool with the identifier call_stub_1 and the arguments {}, unless its last message is a tool result, which is echoed back.
- A request without tools gets the text echo: followed by the last user text, and a list of content parts is read as its text parts joined.
- The token counts are the request body length and the answer length divided by 4, rounded up, with no cached tokens.
- A streamed answer carries the usage chunk only when the caller asked for usage, and every path other than POST /v1/chat/completions gets 404.
- The meter, in front of the stub, publishes a usage event whose measures equal the stub's formula.

The rest of this ticket is the exact instruction for the model that does the work.

## 2. End goal
The model meter binary (`core/services/model-meter`) has three subcommands: `serve` (default), `stub` and `version`. `model-meter stub` listens on `:8081` and is the scripted back end of the alias `conformance-echo` (`docs/contracts/model-contract.md`, back-end key `stub`). It answers `POST /v1/chat/completions` by fixed rules, with token counts a gate check can compute from the request and the answer, so that the gate checks AIP-G02 and AIP-G03 (packages AIP-130 and AIP-140) can exercise the gateway, the meter and the bus with no credential. The change is the four files of the block `AIP-114.patch`; nothing else changes.

## 3. The model (the law)
1. Subcommand. `model-meter stub` listens on `meter.StubAddr`, `:8081`, serves the handler of `meter.NewStub()`, and exits 0 after SIGINT or SIGTERM (graceful shutdown, 10 seconds). It exits 1 when it cannot open or keep its listener. Any unknown first argument prints `model-meter: unknown subcommand "<arg>"; use serve, stub or version` to standard error and exits 2. `serve` and `version` behave as before.
2. Routes. Only `POST /v1/chat/completions` is served. Any other method or path gets 404 with the error body of the model contract and code `not_found`. A body that is not a JSON object of a chat-completions request gets 400 `invalid_request`.
3. Answer, applied in this order. (a) When the last message has the role `tool`, the answer is the text `echo:` followed by that message's content, even when the request has tools. (b) Otherwise, when the request has tools, the answer is one tool call of the first tool: identifier `call_stub_1`, type `function`, arguments `{}`, finish reason `tool_calls`, content `null`. (c) Otherwise the answer is the text `echo:` followed by the content of the last message with the role `user` (`echo:` alone when there is none), finish reason `stop`.
4. Content. A message content that is a string is read as it is. A content that is a list of parts is read as the `text` of its parts of type `text`, joined with nothing between them. Anything else reads as the empty text.
5. Usage, deterministic. `prompt_tokens` is the byte length of the request body as received, divided by 4 and rounded up. `completion_tokens` is the byte length of the answered text, or of the arguments `{}` for a tool call, divided by 4 and rounded up. `prompt_tokens_details.cached_tokens` is 0. `total_tokens` is their sum. The answer's `model` is the request's `model`.
6. Stream. With `"stream": true` the answer is server-sent events, each chunk flushed: one chunk with the delta (the text, or the tool call with `index` 0), one chunk with an empty delta and the finish reason, the usage chunk (empty `choices`, the usage of rule 5) only when `stream_options.include_usage` is true, then `data: [DONE]`. Without `"stream": true` the answer is one `chat.completion` JSON object with the usage of rule 5.
7. Behind the meter. The meter forwards a streamed request with `include_usage` set to true, so the stub always sends the usage chunk to the meter; the meter holds it back from a caller that did not ask. The usage event of a call on the stub has the measures `llm.tokens.input` = the stub's `prompt_tokens` (no cached tokens), `llm.tokens.output` = its `completion_tokens`, and `llm.requests` = 1.
8. Nothing is deleted. `go.mod`, `go.sum`, `meter.go`, `stream.go` and the `Containerfile` do not change.

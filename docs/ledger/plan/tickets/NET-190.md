# NET-190 — Route admission by owner

## In plain words

**The problem today.** Every listener of the two public Gateways of a Sovereign accepts web routes from any namespace of the cluster. So a route written in an Organization's namespace can claim a host name of the platform itself, such as the console. The rule that should stop this, that a listener admits only the routes of its owner, is written nowhere.

**What changes.** The listeners of the shared Gateway and the fixed console listeners admit routes only from the platform namespaces that own a route today. The network guard keeps that list and checks that every route the platform installs lives in a namespace on it.

**Done means:**

- No listener of the shared Gateway, and none of the fixed listeners of the console Gateway, admits routes from all namespaces.
- Every listener named in the bootstrap kit and in the listener chart admits exactly the same thirteen platform namespaces.
- A platform route added in a namespace that the list does not hold turns the network guard red.
- A copy of the list that differs from the list turns the network guard red.
- The network guard holds no counted entry for the two files that admitted all namespaces.

The rest of this ticket is the exact instruction for the model that does the work.

## 2. End goal
A Sovereign has two Gateways in `kube-system`: the shared Gateway `cilium-gateway` and the console Gateway `cilium-gateway-console`. Two sources write the shared Gateway's listeners: the Gateway document of kit slot `01-cilium.yaml`, and the `sovereign-tls` Kustomization, which fills `listeners:` of the same Gateway from the ConfigMap that the chart `bp-sovereign-tls-vars` renders. That chart also renders the fixed listeners of the console Gateway (console, api, marketplace). After this ticket every one of these listeners admits HTTPRoutes only from the thirteen kit namespaces that own a route, instead of from all namespaces. The list lives in one new file, `scripts/network-guards-allowlist.yaml`. Network guard G4 of `scripts/check-network-guards.py` gains three rules: the two copies of the list (the slot's listeners and the chart's `routeNamespaces` value) equal the list; every HTTPRoute that a kit slot installs lives in a listed namespace; and the list holds nothing that no route needs. The four listener sites in Go code that add an Organization's own listeners are not changed here.

## 3. The model (the law)
1. A listener of `kube-system/cilium-gateway`, and a fixed listener of `kube-system/cilium-gateway-console`, admits HTTPRoutes by this block and no other:
   ```yaml
   allowedRoutes:
     namespaces:
       from: Selector
       selector:
         matchExpressions:
           - key: kubernetes.io/metadata.name
             operator: In
             values: [the list]
   ```
   The list is, in this order: `catalyst-system`, `chargeback`, `gitea`, `grafana`, `guacamole`, `harbor`, `keycloak`, `kube-system`, `newapi`, `oidc-gate`, `openbao`, `powerdns`, `powerdns-admin`. Kubernetes sets the label `kubernetes.io/metadata.name` on every namespace to its name.
2. The list is the set of namespaces of the HTTPRoutes that the kit installs: the `targetNamespace` of each `bootstrap-kit` slot whose chart has an HTTPRoute template in the release namespace, plus `kube-system` for the Hubble UI route template, whose namespace is a value with the default `kube-system`. It holds no namespace that owns no such route.
3. An Organization's routes never attach to these listeners. They attach to the Organization's own listeners on the console Gateway, which code in `core/controllers/organization/internal/controller/tenant_console_tls.go` and `products/catalyst/bootstrap/api/internal/handler/org_console_tls.go` adds; those four sites keep `from: All` until NET-191.
4. `scripts/network-guards-allowlist.yaml` holds the list (key `namespaces`) and the route templates whose namespace is neither the release namespace nor a fixed name (key `templates`, each entry `path`, `namespace`, `reason`; `namespace` is a listed name or the word `organization`). It has two copies, and both must equal it: the `values` of every listener of every Gateway document in `clusters/_template/bootstrap-kit/01-cilium.yaml`, and the value `routeNamespaces` in `platform/sovereign-tls-vars/chart/values.yaml`.
5. The chart template `platform/sovereign-tls-vars/chart/templates/configmap.yaml` builds the admission block once from `.Values.routeNamespaces` and uses it for all six listener dictionaries. With an empty `routeNamespaces` and a Sovereign FQDN set, the render fails with the message `routeNamespaces is empty: the Gateway listeners would admit no HTTPRoute`. With no Sovereign FQDN the chart still renders nothing.
6. G4 counts no `from: All` offence in `clusters/_template/bootstrap-kit/01-cilium.yaml` or in `platform/sovereign-tls-vars/chart/templates/configmap.yaml`, so their two lines leave `scripts/network-guards-baseline.tsv`. The other G4 lines (two Go files of NET-191) stay.
7. The three new rules of G4 have no baseline: one breach fails the check at once. Each rule has a case in `self-test` that makes it fail.
8. No chart `version:`, no slot pin and no other file changes. After the merge, the release workflow publishes the changed chart under its next patch version and moves the pin of slot `12a-bp-sovereign-tls-vars.yaml` in its own commit.

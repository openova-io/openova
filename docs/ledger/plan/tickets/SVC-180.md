# SVC-180 — Screens group by class; the dead branch goes

## In plain words

**The problem today.** Every installed Blueprint shows on the Applications page in one undivided grid, so the sovereign-admin's own applications sit among some sixty pieces of cluster plumbing. The class each Blueprint now declares is shown as a chip and does nothing else: no screen groups or filters by it, and a sovereign-admin who wants, say, the data services on the left menu has no way to get them there. The detail page still decides whether to show connection details from an old wizard grouping instead of the Blueprint's own declaration.

**What changes.** Applications and Catalog show their cards in sections by class, and the platform components move from Applications to Resources, which groups and filters the installed Blueprints by class with the filter in the address. Each class view of Resources is offered in Settings, Menu as a candidate that is off until the sovereign-admin switches it on.

**Done means:**

- The Applications page shows its cards in sections by class, in the order applications, data services, network and security services, AI services, infrastructure, and shows no card of class platform-component; a note links to the platform components in Resources.
- The Catalog page shows its cards in sections by class, and an Organization user never sees a platform component there, not even with Show unlisted.
- Resources groups the HelmReleases and the Applications by class with a Class column, and a class filter writes the class into the address, so a reload or a shared link opens the same view.
- Settings, Menu lists one class view of Resources per class, each off by default, and switching one on puts that filtered view on the left menu.
- The Connection section of an Application shows when its Blueprint is shareable, and no code decides it from the wizard grouping any more.
- No page and no fixed left menu entry is added.

The rest of this ticket is the exact instruction for the model that does the work.

## 2. End goal
Every Blueprint says its class (`spec.class`, SVC-170), and the sovereign-admin console now uses it. One file, `products/catalyst/bootstrap/ui/src/shared/constants/classes.ts`, holds the six classes in their grouping order with a singular and a plural label each; every screen that names a class reads it. The Applications page (`/apps`) shows its cards in one section per class and no card of class `platform-component`; a note links to the class view of the platform components in Resources. The Catalog page (`/catalog`) shows its cards in one section per class, and an Organization user never sees a platform component there. Resources (`/cloud`) is the unified view: its HelmReleases list (one row per installed Blueprint) and its Applications list group their rows by class with a Class column and a class filter whose value is the search parameter `class` of the address; a reload of that address returns the same view. The API list of console pages of `internal/consolemenu` holds one class view per class, `page:class-<class>`, with the plural label and the route `/cloud?view=list&kind=helmreleases&class=<class>`, off by default, so Settings, Menu offers each class view and the sovereign-admin decides which one shows on the left. The detail page of an Application shows its Connection section when the Application's Blueprint is shareable; `isServiceApp` and its use of the wizard grouping are deleted. No page, no route path and no fixed menu entry is added.

## 3. The model (the law)
1. The class values and their order are `application`, `data-service`, `network-security-service`, `ai-service`, `infrastructure`, `platform-component` (`CLASS_ORDER` of `classes.ts`). The labels are: Application / Applications, Data service / Data services, Network and security service / Network and security services, AI service / AI services, Infrastructure / Infrastructure, Platform component / Platform components. The plural labels are those the Catalog page already used; the singular labels are decided by this ticket.
2. The class of a Blueprint is `BLUEPRINT_BY_ID[bp-<name>].class` of the generated catalogue (`classOfBlueprint`, with or without the `bp-` prefix). A Blueprint the catalogue does not know is an `application`, the default class, as the Catalog page already does for a live-only card.
3. `groupByClass` returns one group per class that has an item, in `CLASS_ORDER`, and keeps the order of the items inside a group. A group title is the plural label and the number of its items.
4. The Applications page groups its instance cards by the class of the instance's Blueprint and its Blueprint cards by the class of the Blueprint. It drops every card of class `platform-component`; when it dropped one, and the session is not an Organization's, it shows the note `sov-apps-platform-note` with a link `sov-apps-platform-link` to `resourcesClassRoute('platform-component')`. The outer container keeps `data-testid="sov-apps-grid"`; each section is `sov-apps-class-<class>` and holds an `.apps-grid` `sov-apps-class-grid-<class>`. Every card keeps its `data-testid`.
5. The Catalog page groups its cards the same way: the outer container keeps `data-testid="sov-catalog-grid"`; each section is `sov-catalog-class-<class>` with an `.apps-grid` `sov-catalog-class-grid-<class>`. Its local label table `CLASS_LABEL` is deleted; the chip of a live-only card is the plural label of `classes.ts`. When the session is an Organization's (`useConsoleScope().orgScoped`), and while the scope is still loading, the page drops every card of class `platform-component`, also with `?unlisted=1`.
6. Resources: both cloud routes of `src/app/router.tsx` accept the search parameter `class` when it is one of the six values and drop it otherwise. `K8sListPage` takes three optional props: `blueprintOf` (the Blueprint of a row), `classFilter` and `onClassFilterChange`. With `blueprintOf` the list groups its rows by class (a header row `cloud-<kind>-class-group-<class>` per group), adds a Class column with the singular label, shows a select `cloud-<kind>-class-filter` (All classes and the six plural labels), keeps only the rows of `classFilter`, and says `cloud-<kind>-class-empty` when the filter keeps no row. Without `blueprintOf` a list renders as before. `K8sListPage` reads no router state; the hook `useClassFilter` of `cloud-list/useClassFilter.ts` reads `class` from the address and writes it with a navigation to the same route.
7. The HelmReleases list passes the Blueprint of a release (its chart when that is `bp-<name>`, else its name when that is one); the Applications list passes `spec.blueprint` (else `spec.blueprintRef.name`). No other list is class-aware.
8. A class in the address opens the list view (when the address names no view) and, when it names no kind, the kind `helmreleases`; `CloudPage` and `CloudListView` keep `class` in every navigation they make (view switch, kind switch, Sovereign switch, the canonical address). The graph view ignores it.
9. The list `pages` of `internal/consolemenu/consolemenu.go` holds six lines, one per class, in the class order: `Name` `class-<class>`, `Label` the plural label, `Route` `/cloud?view=list&kind=helmreleases&class=<class>`, `Order` 60 to 65, no icon. Each projects to a candidate `page:class-<class>` that is off by default, like every page candidate. The test `classes.test.ts` reads these six lines and fails when a label or a route differs from `classes.ts`.
10. `AppDetail.tsx` has no `isServiceApp`. The Connection section shows when `BLUEPRINT_BY_ID[<the Application's Blueprint>].shareable` is true; the prop is `showConnection`.
11. Deleted: `isServiceApp` (5 lines that name it), the local `CLASS_LABEL` of `CatalogPage.tsx`. Not added: a page, a route path, an entry of `sovereignNav.ts` or `SovereignSidebar.tsx`.

+/**
+ * classes.ts — the Blueprint classes (spec.class) as the console shows them.
+ *
+ * Every screen that names a class reads its label here: the Applications
+ * page and the Catalog page group their cards by class, and Resources groups
+ * and filters the rows that carry a Blueprint by class. The class of a
+ * Blueprint comes from the build-time catalogue (catalog.generated.ts, written
+ * by scripts/generate-catalog.py from each blueprint.yaml); a Blueprint the
+ * catalogue does not know is an application, the default class.
+ *
+ * The class views of Resources are menu candidates of the source page
+ * (products/catalyst/bootstrap/api/internal/consolemenu). Their labels and
+ * routes there must equal CLASS_LABELS[c].plural and resourcesClassRoute(c);
+ * classes.test.ts reads that Go list and fails when the two disagree.
+ */
+
+import { BLUEPRINT_BY_ID, type BlueprintClass } from './catalog.generated'
+
+export type { BlueprintClass }
+
+export interface ClassLabel {
+  /** One thing of the class: "Data service". */
+  singular: string
+  /** The class as a group: "Data services". */
+  plural: string
+}
+
+/** The six classes, in the order every screen groups them. */
+export const CLASS_ORDER: readonly BlueprintClass[] = [
+  'application',
+  'data-service',
+  'network-security-service',
+  'ai-service',
+  'infrastructure',
+  'platform-component',
+]
+
+/** The screen labels of each class. */
+export const CLASS_LABELS: Readonly<Record<BlueprintClass, ClassLabel>> = {
+  application: { singular: 'Application', plural: 'Applications' },
+  'data-service': { singular: 'Data service', plural: 'Data services' },
+  'network-security-service': {
+    singular: 'Network and security service',
+    plural: 'Network and security services',
+  },
+  'ai-service': { singular: 'AI service', plural: 'AI services' },
+  infrastructure: { singular: 'Infrastructure', plural: 'Infrastructure' },
+  'platform-component': { singular: 'Platform component', plural: 'Platform components' },
+}
+
+/** The class of a Blueprint the catalogue does not know. */
+export const DEFAULT_CLASS: BlueprintClass = 'application'
+
+/** The class whose rows the Applications page leaves to Resources. */
+export const PLATFORM_CLASS: BlueprintClass = 'platform-component'
+
+export function isBlueprintClass(value: unknown): value is BlueprintClass {
+  return typeof value === 'string' && (CLASS_ORDER as readonly string[]).includes(value)
+}
+
+/** The class of a Blueprint, from its id with or without the bp- prefix. */
+export function classOfBlueprint(id: string | null | undefined): BlueprintClass {
+  if (!id) return DEFAULT_CLASS
+  const full = id.startsWith('bp-') ? id : `bp-${id}`
+  return BLUEPRINT_BY_ID[full]?.class ?? DEFAULT_CLASS
+}
+
+export interface ClassGroup<T> {
+  cls: BlueprintClass
+  label: ClassLabel
+  items: T[]
+}
+
+/**
+ * groupByClass — one group per class that has an item, in CLASS_ORDER. The
+ * items of a group keep their order. A class missing from `order` drops its
+ * items.
+ */
+export function groupByClass<T>(
+  items: readonly T[],
+  classOf: (item: T) => BlueprintClass,
+  order: readonly BlueprintClass[] = CLASS_ORDER,
+): ClassGroup<T>[] {
+  const byClass = new Map<BlueprintClass, T[]>()
+  for (const item of items) {
+    const cls = classOf(item)
+    const list = byClass.get(cls)
+    if (list) list.push(item)
+    else byClass.set(cls, [item])
+  }
+  const out: ClassGroup<T>[] = []
+  for (const cls of order) {
+    const list = byClass.get(cls)
+    if (list && list.length > 0) out.push({ cls, label: CLASS_LABELS[cls], items: list })
+  }
+  return out
+}
+

+
+/** The Resources list that a class view opens: one row per installed Blueprint. */
+export const RESOURCES_CLASS_KIND = 'helmreleases'
+
+/** The address of the class view of Resources for one class. */
+export function resourcesClassRoute(cls: BlueprintClass): string {
+  return `/cloud?view=list&kind=${RESOURCES_CLASS_KIND}&${RESOURCES_CLASS_PARAM}=${cls}`

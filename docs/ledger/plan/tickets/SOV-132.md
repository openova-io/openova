# SOV-132 — Nodes boot with a local-first registry file, a wildcard entry and the public fallback off

## In plain words

**The problem today.** A new node reads its registry list from text written by hand into each provider module and worker template. That text names the parent's registry addresses directly, ignores the registry list and the origin addresses that the parent now writes into the variables document, and never names the Sovereign's own registry. A node can also still fall back to a public registry when a mirror fails.

**What changes.** Each provider module builds the node registry file from the variables document, by the same rule as the platform's registry contract, and every server and agent node writes that file and starts k3s with the public fallback off. A name outside the list is asked of the Sovereign's own registry only.

**Done means:**

- Every control plane and every worker of both providers writes the same registry file, built from the variables document of the installation.
- In that file every listed registry name asks the Sovereign's own registry first and its origin second; names served at the root have no rewrite; the origin host has an entry of its own only when it is not one of the listed names.
- A name outside the list has the Sovereign's own registry as its only endpoint, and every k3s server and agent starts with --disable-default-registry-endpoint.
- The parent's pull login is written only for an origin registry that serves a proxy project; the reference cloud keeps the ghcr.io rewrite of the hosted project.
- No registry address is written into the two provider modules or their worker templates, and the guard that counts source addresses has a lower count for the infrastructure.
- The tests of both provider modules prove the file for a child's document, for a document without origin addresses and for a Sovereign that consumes only its own registry, and the worst-case start-up data, measured with the registry file the module builds and not an empty map, stays within every cloud's limit.
- The pre-fire image check reads the node registry map from where the modules now build it, and still fails on a host that no mirror of that map serves.

The rest of this ticket is the exact instruction for the model that does the work.

## 2. End goal
Each provider module builds `/etc/rancher/k3s/registries.yaml` from its input `variables` (contract C5) with the rule of `upstream.Variables.RegistriesYAML` in `core/controllers/pkg/upstream/upstream.go`: one entry per key of `REGISTRY_PROXY_PROJECTS_JSON` with the endpoints `https://<LOCAL_REGISTRY_HOST>` and, while `SOVEREIGN_CONSUME` is `origin`, the origin of that name (`ORIGIN_PROXY_ENDPOINTS_JSON`, else `<ORIGIN_REGISTRY_SCHEME>://<ORIGIN_REGISTRY_HOST>`), with the rewrite to its project path when the path is not empty; then an entry for `LOCAL_REGISTRY_HOST`, an entry for `ORIGIN_REGISTRY_HOST` (while `origin`, unless it is a proxy name), and the wildcard `"*"` with the local registry only. The control plane (shared template) and every worker (both worker templates) write that one file, and every k3s server and agent starts with `--disable-default-registry-endpoint`. A person can observe it in the worst-case render of the size check and in the two module tests: a child's document renders ten entries, the origin addresses of the document and no address of the module.

## 3. The model (the law)
1. **One rule, from the document.** The file is built only from `var.variables` and `var.harbor_robot_token`. The rule is written as the same locals in both modules (`node_registry_local`, `node_registry_origin_on`, `node_registry_projects`, `node_registry_origin_host`, `node_registry_origin`, `node_registry_hosted_rewrites`, and `registry_mirror_yaml_<provider>`), so a later reader compares two equal texts.
2. **Entries.** Per proxy name N with path P: `endpoint` is the local registry, then (while `origin`) `ORIGIN_PROXY_ENDPOINTS_JSON[N]` when present and not empty, else the default origin; `rewrite` is `{"(.*)": "P/$1"}` when P is not empty. Then `LOCAL_REGISTRY_HOST` with the local registry only; `ORIGIN_REGISTRY_HOST` with local then default origin, only while `origin` and only when it is not a key of `REGISTRY_PROXY_PROJECTS_JSON` (the skip of SOV-135); and `"*"` with the local registry only, no rewrite.
3. **Hosted rewrites.** `node_registry_hosted_rewrites` replaces the rewrite of a name, as the `hostedRewrites` argument of the Go rule does. It is empty on the second provider. On the reference cloud it holds the two `ghcr.io` rules of the hosted project `openova-io` (#4049) exactly as the module rendered them before: `^openova-io/openova/(.*)` to `openova-io/openova/$1`, and the anchored catch-all to `proxy-ghcr/$0`.
4. **The pull login.** `configs` carries the robot login `robot$openova-bot` with `var.harbor_robot_token` for the host (with port) of every origin address that serves at least one name with a non-empty path, and for nothing else. Decided on precedent (the pull login is written for the origin registry of the parent): an origin that serves only a name at its root and is not a registry of the parent (`https://xpkg.upbound.io` in a child's document) gets no login, because a wrong login sent to a public registry fails a pull that works anonymously. No login is written for `LOCAL_REGISTRY_HOST`: the module has none at first boot, and its projects are created public by the hand-over chart.
5. **One text for every node.** The shared template writes the file packed as before (`encoding: gz+b64`, unchanged expression). Both worker templates take the new argument `registry_mirror_yaml` in place of `harbor_robot_token` and write `${indent(6, chomp(registry_mirror_yaml))}` under `content: |`; their own text of the file, with its addresses, is deleted. File modes stay: `0600` on the control plane and the second provider's workers, `0644` on the reference cloud's workers.
6. **JSON form.** The module writes the file with `jsonencode`: JSON is YAML, k3s reads it, and it is the shortest text (measured: 636 and 664 bytes less on the worst-case workers of the two providers than `yamlencode`, which also writes the 202-character `ghcr.io` rule as a `? key` pair).
7. **The flag.** `--disable-default-registry-endpoint` is added to the three `INSTALL_K3S_EXEC` lines: in the shared template between `--disable=local-storage` and `--cluster-cidr=` (the place no existing assert reads; the AIP-201 asserts read the text before `--write-kubeconfig-mode=0600`), and right after `agent` in both worker templates.
8. **No address in the modules.** Every `212.72.24.20` and `https://harbor.openova.io` line of the two modules and the two worker templates is deleted. Guard G1 (`scripts/check-upstream-literals.sh`) counts 18 lines in scope `infra` instead of 46; the baseline line `infra=46` becomes `infra=18`. The other baseline lines do not change.
9. **The module tests.** The top-level document of both module tests becomes a child's in the form of SOV-135: the eight names (`harbor.openova.io` and `xpkg.upbound.io` with an empty path, no `public.ecr.aws`), an origin for every name, and `ORIGIN_REGISTRY_HOST` `ghcr.io` (a proxy name). A new run `node_registry_file_follows_the_variables_document` in each compares the decoded file with the whole expected object and reads the file and the flag in the control-plane and worker renders. The worst-case run of each (whose document has no origin per name and an origin host that is not a proxy name) gains one assert for that branch of the rule.
10. **The size-check reference render.** `scripts/cloudinit-size-check.sh` renders each worker template with a reference fixture of its own; that fixture passes `registry_mirror_yaml` instead of `harbor_robot_token`, or the template does not render and the gate fails. Revision 2: the value it passes is the registry file the module builds for the worst-case document, never `mirrors: {}`; an empty map leaves out about 1.2 KB of the worst-case worker (the reviewer of pull request 8438), so the size gate would measure less than a node writes.
11. **The pre-fire image check reads the module's map (revision 2).** `scripts/check-mothership-proxy-image-path.sh` resolves every Phase-1 image the way the node resolves it, from the node registry map. Today it finds that map with a regular expression over the heredoc `registry_mirror_yaml_huawei` of `infra/providers/huawei/main.tf` (its line 154) and stops with `FATAL: registry_mirror_yaml_huawei heredoc not found` (line 156) when the heredoc is gone, so the required check `Reject non-mirror-served Phase-1 image hosts`, which runs its self-test, turns red, and the fire's pre-flight run (line 609) exits 2. After this change it reads the map from where the modules now build it: the rule of field 3 applied to a variables document (the module tests' child document in its self-test; the installation's own document in the pre-fire run), with the reference module's hosted rewrites. It still fails on a host that no mirror of that map serves. Its self-test needs no OpenTofu: neither the acceptance job nor the job of the required check has it.
12. **A Sovereign that consumes its own registry only (revision 2).** With `SOVEREIGN_CONSUME` `local` the file lists for every proxy name the local registry only, has no entry for `ORIGIN_REGISTRY_HOST`, and `*` keeps the local registry only.

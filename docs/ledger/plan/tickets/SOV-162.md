# SOV-162 — The registry finds and heals a cached image index whose children are gone

## In plain words

**The problem today.** A pull-through project of the registry can keep a cached image index whose child manifest or config blob is gone from the registry's storage while its database still lists it. Every pull of that image then fails on every node, although the upstream registry serves it, and the registry never repairs it by itself. Today only a hand deletion of the cached artifact by the registry administrator repairs it.

**What changes.** The registry chart carries a scheduled check that finds such an index and deletes it, so that the next pull fetches the image whole. Each repair is reported as an Event and counted in a metric, a failed read deletes nothing, and a hosted project is never touched.

**Done means:**

- A cached index whose child manifest answers not found is deleted by the next pass of the check, and an Event names the index and the missing child.
- A cached index whose child's config blob answers not found is deleted the same way, together with that child when the child carries a tag of its own.
- An index whose children and config blobs all answer is left alone.
- A hosted project is never listed, read or changed.
- A read that fails for another reason deletes nothing for its index and is counted as a read failure.
- The check is on by default, runs as a scheduled job with no endless loop, and its counters survive an upgrade and are served for scraping.
- A test of the chart proves these rules on every pull request that changes the chart: it renders the check and runs its script against stand-ins for the registry and the cluster.

The rest of this ticket is the exact instruction for the model that does the work.

## 2. End goal
The registry chart `bp-harbor` (installed on the parent and as every Sovereign's own registry) carries a scheduled check of its pull-through (proxy cache) projects. Every hour a pass of the CronJob `<release>-proxy-cache-integrity` reads, for each tagged artifact that is an image index in a project with a `registry_id`, each child manifest the index references and that child's config blob, through harbor-core's `/v2`, the path every pull takes. When one answers 404 the pass deletes that cached index (and a missed child that is still listed because it carries its own tag), so the next pull fetches the image whole from upstream; it writes a Kubernetes Event `ProxyCacheArtifactHealed` that names the index, its tags and what was missing, and adds one to `harbor_proxy_cache_integrity_healed_total`. A read that answers anything else, or nothing, deletes nothing. A hosted project is never listed. The counters live in a ConfigMap that the pass writes, and a small Deployment serves them on port 9090 at `/metrics.txt`. A person sees it this way: a damaged cached image that today fails every pull until an administrator deletes it by hand is gone within the hour, the next pull succeeds, and `kubectl get events -n <namespace>` shows what was healed.

It removes no line. Nothing else changes: no `Chart.yaml`, no `blueprint.yaml`, no slot file (CI writes versions, package FND-011; the check needs no value of slot 19).
2. **What renders.** With `proxyCacheIntegrity.enabled` true (the default) the template renders six objects in the release namespace: a ServiceAccount, a Role and a RoleBinding named `<release>-proxy-cache-integrity`; a ConfigMap of that name holding `check.sh`; a `batch/v1` CronJob of that name (schedule `proxyCacheIntegrity.schedule`, default `17 * * * *`; `concurrencyPolicy: Forbid`; `backoffLimit: 0`; image `proxyCacheIntegrity.image`, the `alpine/k8s:1.31.4` image the chart already uses, through a proxy project; user 1001, read-only root file system, cpu and memory requests; the admin Secret `harborAdmin.secretName` mounted read-only at `/etc/harbor-admin`); and a Deployment `<release>-proxy-cache-integrity-metrics` (one replica, `proxyCacheIntegrity.metricsImage` = busybox 1.36 through a proxy project, `httpd` on `metricsPort` 9090, tcp liveness and readiness probes, requests, pod annotations `prometheus.io/scrape: "true"`, `prometheus.io/port: "9090"`, `prometheus.io/path: /metrics.txt`, the counters ConfigMap mounted optional). With `enabled` false nothing renders. No environment variable name holds `PASSWORD`, `TOKEN`, `KEY` or `SECRET` (the policy `secret-not-in-env`).
3. **The Role** allows exactly: `create` on `events`; `create` on `configmaps`; `get` and `patch` on the one ConfigMap `<release>-proxy-cache-integrity-metrics`. Nothing outside the release namespace.
4. **A pass**, in this order. (a) List every page (100 per page, at most 1000 pages) of `GET /api/v2.0/projects` as `admin`. (b) Keep the projects whose `registry_id` is above 0: the pull-through projects. A project without one, or with 0 or null, is hosted and is never listed further. (c) For each repository of such a project, list its artifacts (`?with_tag=true`; Harbor's default list leaves out the children of an index) and keep those that have a tag and whose `manifest_media_type` is `application/vnd.oci.image.index.v1+json` or `application/vnd.docker.distribution.manifest.list.v2+json`. (d) Get one pull token per repository from `/service/token?service=harbor-registry&scope=repository:<repository>:pull`. (e) For each child digest in the index's `references`: `GET /v2/<repository>/manifests/<child>`; on 200 read `.config.digest` and `GET /v2/<repository>/blobs/<config>`. A 404 of either is a miss. Any other answer, or none, is a failed read. Layers are never read.
5. **Healing.** An index with a failed read is left as it is and counts one read failure. An index with at least one miss and no failed read is deleted with `DELETE /api/v2.0/projects/<project>/repositories/<repository, its slashes as %252F>/artifacts/<digest>`: 200 counts one heal and writes one Event (core `v1`, type Warning, reason `ProxyCacheArtifactHealed`, on the CronJob, with `--field-manager=catalyst-harbor-proxy-cache-integrity`); 404 means another region deleted it already and counts nothing; any other answer counts one read failure. After a heal, each missed child that `GET .../artifacts/<child>` still lists (it carries a tag of its own) is deleted too.
6. **Counters.** At the end of a pass the totals `healed_total`, `missing_total` and `read_failures_total` of the ConfigMap `<release>-proxy-cache-integrity-metrics` (key `metrics.txt`, Prometheus text, each name prefixed `harbor_proxy_cache_integrity_`) grow by the pass's counts; the gauges `indexes_checked`, `children_checked`, `last_pass_ok` and `last_pass_timestamp_seconds` are set. The pass writes the ConfigMap with `kubectl apply --server-side --field-manager=catalyst-harbor-proxy-cache-integrity`. The chart does not render that ConfigMap, so an upgrade never resets it. The pass exits 1 when it counted a read failure, so its Job ends failed; otherwise 0.
7. **No polling loop.** The schedule is the CronJob's; no manifest of the chart holds `while true` or `while :`. The guard `scripts/check-no-new-polling.py` stays at its baseline.
8. **The cause, as far as the chart and the pinned upstream show it** (field 4): Harbor serves a pull by digest from its own storage whenever its database lists the artifact and never falls back to upstream, so a storage object lost behind a database row stays broken; retention and the untagged clean-up of garbage collection do not remove a child while its tagged index stays. The README section records this with the upstream file and line of each statement.

+### Proxy-cache integrity check (SOV-162)
+
+A pull-through (proxy cache) project can hold a cached image index that answers
+200 while a child it references answers `manifest unknown` (404), or a child's
+config blob answers 404, although the upstream registry serves both. Every pull
+of that image then fails, on every node that pulls it, until the cached
+artifact is deleted; the next pull then fetches the image whole.
+
+Why Harbor does not recover by itself (pinned upstream Harbor v2.14.3, chart
+goharbor/harbor-helm 1.18.3; source at
+<https://github.com/goharbor/harbor/tree/v2.14.3>):
+
+- A pull by digest is served from the registry's own storage as soon as
+  Harbor's database lists the artifact (`src/controller/proxy/controller.go`
+  lines 172-180, `src/controller/proxy/local.go` lines 54-64); storage is not
+  asked, and there is no fallback to upstream. A blob is served locally when
+  storage answers that it exists (`local.go` lines 84-86). So a manifest or
+  blob that storage has lost while the database still lists it stays broken.
+- An index pulled by tag is served for 7 days from the cache of manifest lists
+  (`controller.go` line 47, lines 209-228), whatever is left in storage, so the
+  index keeps answering 200.
+- Not the cause in this version: retention and the untagged clean-up of
+  garbage collection. Every pull-through project gets a retention policy at
+  creation (keep what was pulled in the last 7 days, daily;
+  `src/server/v2.0/handler/project.go` lines 64-65 and 242-249,

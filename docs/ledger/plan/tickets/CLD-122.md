# CLD-122 — The wizard renders providers, credentials, regions and flavors from the profile

## In plain words

**The problem today.** The deployment wizard of the console keeps its own lists of clouds, regions and machine sizes, and its own credential form for one cloud. They drift from the provider packs and from the installation documents an operator adds, so a cloud the platform can build on cannot be chosen and a cloud it has no pack for is offered.

**What changes.** The wizard asks the providers routes of the API which clouds there are and what each one offers, and renders its cloud, credential, region, zone and flavor choices from those answers. Its own lists are deleted.

**Done means:**

- The provider step shows one card per cloud that the providers route lists, and fills each region with a region, a zone and flavors of the chosen cloud's profile.
- A wizard without a session is asked to sign in on the provider step; an empty list says that no cloud is offered and keeps Continue disabled.
- The credentials step shows one input per credential field of the profile, a secret one masked, and none when the profile takes the operator's credentials.
- The body that the wizard posts to create a Sovereign carries the cloud, its installation, the credential map and per region the cloud region, zone and flavors, and no field of one named cloud.
- No file of the console holds a list of providers, regions or machine sizes, and the wizard pages and the deployment entity name no cloud outside their tests and one generated file.

The rest of this ticket is the exact instruction for the model that does the work.

## 2. End goal
The deployment wizard of the sovereign-admin console (`products/catalyst/bootstrap/ui`, steps 3 Provider, 7 Credentials and 8 Review) renders what the providers routes of CLD-121 serve and nothing of its own. The new client `products/catalyst/bootstrap/ui/src/lib/providers.api.ts` reads `GET /api/v1/providers` and `GET /api/v1/providers/{provider}?installation=<name>`. The provider step shows one card per listed cloud, and per region a region, a zone, a control-plane flavor, a worker flavor and a worker count of the chosen cloud's profile. The credentials step shows one input per `credentials.fields` entry of the profile and validates the map with `POST /api/v1/credentials/validate`. The review posts `POST /api/v1/deployments` with `provider`, `installation`, `credentials` and `regions[]` of `{provider, cloudRegion, zone, controlPlaneSize, workerSize, workerCount}`. `shared/constants/providerSizes.ts` (the machine sizes of five clouds), its test, `PROVIDER_REGIONS` of `entities/deployment/model.ts`, the headquarters-to-provider map of the provider step and the unused `widgets/cloud-provider-card` are deleted. A person sees it in the tests of `src/pages/wizard/steps`, among them `StepReview.profile-body.test.tsx`, which walks steps 3, 7 and 8 against mocked routes of one pack with an installation and asserts the posted body.

## 3. The model (the law)
1. **Two routes, nothing else.** The wizard reads the clouds, the credential fields, the regions, the zones, the flavors, the default flavors, the storage class and the display prices only from `GET /api/v1/providers` and `GET /api/v1/providers/{provider}`, through `lib/providers.api.ts`. It asks without `?include=all`, so it lists only the entries whose `lifecycle` is `proven`. An answer that is not 200, or a body without the list (`providers`) or without `regions`, `compute.flavors` and `credentials.fields`, is thrown as `ProvidersApiError` with the status and the error code of the body; it is never read as an empty list.
2. **No browser storage of a profile.** A profile is held in the memory of the step that reads it (`useProfile`), never in the store. The credential map and its validated flag are dropped by the store's `partialize`, beside the SSH private key and the registrar token, so they never reach `localStorage`.
3. **One cloud per Sovereign.** The store holds `provider` (the pack) and `installation` (the installation document, `''` for the pack alone). The type `CloudProvider` is `string`. Choosing another cloud (`setProvider`) wipes every per-region choice, the credential map and its validated flag. A first visit, or a stored cloud the list no longer holds, takes the first listed cloud.
4. **Per region.** The store holds per region `regionCloudRegions` (a region code of the profile), `regionZones` (new: a zone of that region), the two flavors and the worker count. Region i takes the i-th region of the profile, round the list, with its `defaultZone`; its flavors are the profile's `compute.defaults` when offered in that region, else the first offered one. A flavor without `regions` is offered in every region. A region keeps a flavor the new region offers and replaces one it does not. A profile whose `capabilities.multiRegion` is false refuses two or more regions: Continue stays disabled and the notice `step-provider-one-region` sends the user back to the one-region topology.
5. **Without a session.** A 401 of the list shows the notice `step-provider-sign-in` with a button that opens the PIN sign-in dialog; after a sign-in the list is read again. A 401 is never shown as "no cloud". An empty list shows `step-provider-no-cloud` and keeps Continue disabled.
6. **Credentials.** One input per credential field (`key`, `label`; `secret` masked; `required` marked, and validation waits for every required value). A value that does not match the field's `pattern` is refused by the API with a 400 that names the field. Source `operator`: no input, Continue allowed. Source `either`: Continue allowed with nothing typed, validation needed once a value is typed. Source `user`: validation needed. Validation posts `{provider, installation, credentials}`; a 400 that names a `field` shows the message at that input and keeps Continue disabled. Every changed value must be validated again.
7. **The create body.** `provider`, `installation` (absent when empty), `credentials` (absent when no value was typed; each value trimmed), `regions[]` with the one provider in every entry, `sshPublicKey`, `storageClass` and every field the review sent before that names no cloud. Not sent: `hetznerToken`, `hetznerProjectID`, `objectStorageRegion`, `objectStorageAccessKey`, `objectStorageSecretKey`, and the singular `region`, `controlPlaneSize`, `workerSize`, `workerCount`. The API reads what is sent: `provisioner.Request.Validate` mirrors `regions[0]` into the singular fields, and the Object Storage fields are filled from the credential map by `legacyCredentialFields` (`products/catalyst/bootstrap/api/internal/provisioner/provisioner.go`).
8. **Prices.** A flavor shows a price only when its profile gives one. A total is shown only when every machine has a price in one currency and one period. The wizard adds no price of its own.
9. **Region separation unchanged.** The provider step shows `site` when every region has its own cloud region and `none` otherwise, with the notice word for word for `none`, as NET-213 made it (the rule of `core/cmd/sovereign-ops/internal/sovereignobject/separation.go`). The request now carries a zone, but the separation does not read it: whether a zone separation counts is open in NET-300, and the plan's earlier decision keeps `site` or `none` until then.
10. **Deleted.** `src/shared/constants/providerSizes.ts` and `providerSizes.test.ts`; `src/widgets/cloud-provider-card/CloudProviderCard.tsx` (nothing imports it); in `model.ts` `PROVIDER_REGIONS`, the union of five cloud names, `regionProviders`, `providerTokens`, `providerValidated`, `hetznerToken`, `hetznerProjectId` and the four Object Storage fields; in `store.ts` their setters and `applyProviderToAll`; in `StepProvider.tsx` the headquarters-to-provider map; in `StepReview.tsx` the logos and names of five clouds.
11. **Not changed.** The API, every chart, the dialogs `components/CrudModals/*` and `pages/sovereign/DecommissionPage.tsx` (CLD-123), and the generated `src/pages/wizard/steps/componentGroups.generated.ts`.

+async function read(path: string): Promise<unknown> {

+export type Loaded<T> =

+function useLoaded<T>(key: string | null, load: () => Promise<T>): Loaded<T> | null {
+  const [loaded, setLoaded] = useState<{ key: string; value: Loaded<T> } | null>(null)
+  useEffect(() => {
+    if (key === null) return
+    let live = true
+    load().then(
+      (value) => { if (live) setLoaded({ key, value: { state: 'ready', value } }) },
+      (error: unknown) => {

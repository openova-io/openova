# FND-022 — Scope fence, dependency gate and CI-run acceptance

## In plain words

**The problem today.** Nothing stops a pull request from changing files outside its task, from being merged before the task it depends on, or from being merged without its proof being run. Today that rests on each agent's discipline.

**What changes.** CI gets three checks for every pull request that belongs to a task: it changed only the files of its task; the code was in the state the ticket expected; the task's proof commands pass. A pull request that is not part of the plan is left alone.

**Done means:**

- A pull request that changes a file outside its task turns red.
- A pull request whose required earlier task is not merged turns red.
- The proof commands of the task run in CI, not only on the agent's machine.
- An agent can run the same judgement on its own machine before it pushes.
- An agent can ask whether the checks of a pull request have finished, and the tool waits by itself while they run.
- A pull request outside the plan is not judged, unless it touches the plan's own files.

The rest of this ticket is the exact instruction for the model that does the work.

## 2. End goal
After this ticket every pull request to `main` gets three checks from the workflow `work-package`. They judge work packages. The check `scope` fails when the pull request of a work package changes a file outside the paths of its package, when a dependency is not merged or its gate check is not green, when the done marker is missing, or when the change is larger than the budget. The check `precondition` runs the precondition of the package at the commit the branch was cut from. The check `acceptance` runs the acceptance commands of the package. A pull request that is not a work package passes the three checks with the notice `not a work package, not judged`, unless it changes a file of the plan itself. An executor can run the judgement of `scope` and the acceptance commands in the checkout before the push, and can ask `python3 scripts/plan.py checks --pr <number>` whether every check on a pull request has finished green. With the flag `--wait` that command waits by itself while a check has not finished, so no session waits with `sleep`.

## 3. The model (the law)
1. `scripts/plan.py` after this ticket is the file of FND-021 with the block `FND-022.patch` applied, byte for byte. `.github/workflows/work-package.yaml` is the block `work-package.yaml`, byte for byte.
2. This ticket changes one file, creates one file and adds its marker file. It deletes nothing.
3. The plan on `main` decides. `check-pr`, and `precondition` and `accept` when they are given a pull request, read `docs/ledger/plan.yaml` and `docs/ledger/gates.yaml` at the base commit. They never read the copy in the branch. So a branch cannot change the commands that judge it.
4. The fence judges work packages. A pull request is a work package when its branch is `wp/<ID>` or `wrong/<ID>-rev<N>`, or when its body holds a line `Work-Package: <ID>`. For any other pull request `check-pr`, `precondition` and `accept` print `not a work package, not judged` and exit 0. There are two exceptions:
   - A pull request that is not a work package and changes one of the plan's own files is always judged. It is judged as a plan change, as if its body said `Work-Package: PLAN`. The plan's own files are `docs/ledger/plan.yaml`, `docs/ledger/gates.yaml`, `docs/ledger/stability.yaml`, every file under `docs/ledger/plan/`, `scripts/plan.py` and `scripts/acceptance-gate.py`.
   - A pull request whose author is `dependabot[bot]` is judged as FND-910, and needs no line, once the plan gives FND-910 a `ticket_rev` of 1 or more. Before that it is not a work package.
5. `check-pr --base B --head H --body-file F [--branch R] [--author A]` compares the merge base of B and H with H. It prints one line per failure and exits 1 when there is one. It needs no pull request: before the push an executor runs it in the checkout of the branch as `check-pr --base origin/main --head HEAD --body-file <file>`. Its rules:
   - Rule 1. The body holds exactly one line `Work-Package: <ID>`. The package exists in the plan and is not dropped. The id `PLAN` is accepted when every changed file is `docs/ledger/plan.yaml`, `docs/ledger/gates.yaml`, `docs/ledger/stability.yaml`, `docs/contracts/README.md`, or lies under `docs/ledger/plan/tickets/` or `docs/adr/`.
   - Rule 2. Every changed file is matched by the `touches` of the package, or is one of its own three files: `docs/ledger/plan/done/<ID>.yaml`, `docs/ledger/plan/wrong/<ID>-rev<N>.yaml`, `docs/ledger/plan/found/<ID>.md`. A package that flips or implements a check may also change `docs/ledger/gates.yaml`, and there only the `state` and `implementation` of those checks. A package of type `delete` may also add lines at the end of `docs/ledger/deleted-paths.txt`.
   - Rule 4. Every package in `depends_on` and `after` is merged. Every check flipped by a package in `depends_on` is green.
   - Rule 5. The pull request adds the done marker, and its `ticket_rev` equals the plan's. A repeatable package adds no marker.
   - Rule 6. The change is inside the budget of the package: files added or modified, and changed lines. A deleted file counts as one line and no file. The package's own three files (the done marker, a wrong report, the found file) are not counted.
   - A pull request that carries only a wrong report of its package is judged by rules 1 and 2 alone.
6. Rule 3 (no release-owned line changes) is not in this tool: the guard of FND-011 is its check. Rule 7 (closed and frozen paths) is added by FND-040.
7. `precondition` runs the one precondition command with `bash -c` and compares the trimmed output with `expect`. `accept` runs each acceptance command with `bash -euo pipefail -c`, in order, and stops at the first that does not exit 0. A package without a precondition, or without an acceptance command, fails: nothing to run is not a pass. For a plan change, and for a pull request that carries only a wrong report, both commands print a line that starts with `nothing to run` and exit 0. With `--id <ID>` both commands need no pull request: they read the plan file of the checkout and run there.
8. `checks --pr N [--wait]` reads the check runs on the head commit of pull request N, and the workflow runs of that commit. That is one reading. Its rules:
   - A check is a name in one workflow on one event. Two workflows may give a job the same name: those are two checks, and neither hides the other. A check run whose workflow the code host does not name is a check of its own.
   - The code host can answer with several runs of one check on one commit, for instance after the body of the pull request was edited. Each check is judged by its newest run: the one with the latest `started_at`, and of two that started together the one with the higher id. A run without a start time has not started, so it is the newest. An older run of the same check does not count, red or green.
   - The tool also asks the code host with `filter=latest`, so the code host leaves out the runs that it counts as replaced itself.
   - A run is green when it has finished with `success`, `skipped` or `neutral`. A check that has not finished is never green.
   - A check run that finished red while its workflow run has not finished counts as not finished: the job was started again, or other jobs of its workflow still run. The workflow run of a check run is the one whose `check_suite_id` equals the `check_suite.id` of the check run. It has not finished when its `status` is not `completed`. The line of such a check is `unfinished <name> (workflow-running, <conclusion>)`. This rule holds with and without `--wait`.
   - A reading is 0 when every check has finished green, 1 when one check has finished red, and 2 when one check has not finished or there is none yet.
   - Without `--wait` the command reads once. The reading is its exit code.
   - With `--wait`, a reading 0 ends the command at once. After a reading 2 the command waits 20 seconds and reads again, as long as fewer than 90 seconds have passed since it started. Then the last reading is the answer. After a reading 1 the command waits 20 seconds once and reads again: a second reading 0 or 1 is the answer, and after a second reading 2 the command goes on as after any reading 2. So a red result is always read twice, and a check that was started again is not reported red. The command never waits after its last reading.
   - With `--wait`, a reading that fails (a `gh` call exits with an error) counts as a reading 2 for its round. When the last reading failed, the command prints the failure and exits 3. Without `--wait` a reading that fails ends the command with exit code 3.
   - With `--wait` only: when the answer is 2 and nothing of the head commit has started for 90 minutes, the exit code is 4, and the last line is `checks on <first 12 characters of the commit>: not finished for 90 minutes`. "Started" is the newest `run_started_at` among the workflow runs of the head commit, and `created_at` for a run that has no `run_started_at`. For a head commit without a workflow run it is the committer date of that commit.
   - Only the last reading is printed: one line per check, and one line that starts with `checks on`.
   - The three numbers are constants at the head of the file: `WAIT_STEP = 20` and `WAIT_TOTAL = 90`, in seconds, and `STUCK_MINUTES = 90`. The waiting is one function that gets the reading, the wait and the clock as arguments. The self-test gives it a clock and a wait of its own, so the self-test never really waits.
   - Exit codes of `checks`: 0 every check has finished green; 1 one check has finished red; 2 one check has not finished, or there is none yet; 3 the tool could not read the checks; 4 one check has not finished and nothing has started for 90 minutes.
9. The workflow never writes text from a pull request into a script. The body, the branch name and the author reach the shell as environment variables only.
10. The job `acceptance` checks out the whole history with every branch, and stops when `origin/main` is not in the checkout: an acceptance command may compare the change with `origin/main`. The job installs Python with PyYAML, Go, Node with npm and Helm.
11. No acceptance command may call `checks`: the acceptance job has no `gh`.

+def wait_checks(read, sleep, clock, wait):
+    """The answer of the command checks: (exit code, the lines of the last reading). read() gives (code, lines, started) or
+    raises Unread. started is when something of the head commit last started, on the scale of clock(), in seconds.
+    Without wait there is one reading. With wait:
+      a reading 0 is the answer at once;
+      after a reading 2 the command waits WAIT_STEP and reads again, while fewer than WAIT_TOTAL seconds have passed since it
+      started; then the last reading is the answer;
+      after a reading 1 it waits WAIT_STEP once and reads again: red is the answer only when two readings in a row gave it,
+      so a check that was started again is not reported red;
+      a reading that failed counts as a reading 2 for its round; when the last reading failed, the answer is 3 and the one
+      line is the failure;
+      the answer 2 becomes 4 when nothing of the head commit has started for STUCK_MINUTES.
+    It never waits after its last reading."""
+    begin, red = clock(), False
+    while True:
+        try:
+            code, lines, started = read()
+        except Unread as failure:
+            code, lines, started = 3, [str(failure)], None
+        if not wait or code == 0 or (code == 1 and red) or (code in (2, 3) and clock() - begin >= WAIT_TOTAL):
+            break
+        red = code == 1
+        sleep(WAIT_STEP)
+    if wait and code == 2 and clock() - started >= STUCK_MINUTES * 60:
+        code = 4
+    return code, lines

# SVC-060 — Function-test convention and the data charts

## In plain words

**The problem today.** A chart counts as working when its Pods run. Nothing tests that what a chart installs does its job: that a database takes a write, that a cache gives a value back, that a bucket keeps an object. No chart of the platform ships such a test, and no written rule says what one must look like.

**What changes.** The five data charts each get one test Pod that writes and reads back through the service the chart installs, or asks it a question and checks the answer. Each of the five charts gets a new version, and every place that pins it moves with it. The runbook states the contract for such a test, and a render check holds each of the five charts to it.

**Done means:**

- The runbook has a section that states the function-test contract and what each of the five tests asserts.
- Each of the five charts renders one test Pod with the hook test, a deadline of 300 seconds and the restart policy Never.
- Each test writes and reads back, or sends a request and checks the answer, and none of them creates a Secret.
- Where a chart's own gate switches it off, the test renders nothing.
- A render test per chart fails when that chart's test Pod breaks the contract, and it runs on every pull request that changes the chart.
- Each of the five charts, and the platform chart that carries the catalogue, has a new version; the kit and the catalogue pin the new versions, and the version guard passes.
- The service-model guard counts five charts with a function test.

The rest of this ticket is the exact instruction for the model that does the work.

## 2. End goal
`helm test` on a release of `bp-cnpg`, `bp-postgres`, `bp-valkey`, `bp-seaweedfs` or `bp-nats-jetstream` runs one Pod that exercises what the chart installs and prints one last line `FUNCTION-TEST pass|fail <chart name> <reason>`. Each chart has a render test, `chart/tests/function-test-render.sh`, which CI runs with the chart's other tests on every pull request that changes the chart: it renders the chart in each relevant shape and checks the test Pod with `scripts/check-function-test.py`. The runbook `docs/RUNBOOKS.md` has a new section 4.5 that states the contract, so the later packages that add tests to other charts follow it. The service-model guard reads `G6.function-test-charts=5`. Each of the five charts carries its next patch version (bp-cnpg 1.0.17, bp-postgres 0.2.34, bp-valkey 1.1.7, bp-seaweedfs 1.3.2, bp-nats-jetstream 1.3.6), and every place that pins it follows: its `blueprint.yaml`, its kit slot, the catalogue seed and the generated catalogue. The umbrella chart `bp-catalyst-platform`, which carries the catalogue seed, takes its next version, and its kit slot pins it. The check `Chart-version-bumped guard` passes on the pull request.

## 3. The model (the law)
1. **The contract.** A chart that has a function test ships exactly one file `chart/templates/tests/function-test.yaml`. It renders one Pod named `<release>-function-test`, with the annotations `helm.sh/hook: test` and `helm.sh/hook-delete-policy: before-hook-creation,hook-succeeded`, the label `catalyst.openova.io/function-test: "true"`, `restartPolicy: Never` and `activeDeadlineSeconds: 300`. Besides the Pod the file may render only a ServiceAccount, a Role, a RoleBinding, a NetworkPolicy or a CiliumNetworkPolicy, each with the same two annotations. The test writes then reads, or sends a request and checks the response, against what the chart installs. It exits 0 on pass and non-zero on fail, and its last line is `FUNCTION-TEST <pass|fail> <chart name> <reason>`. It needs nothing outside the cluster. It uses an image the chart already uses, or one the kit already pulls. It renders nothing when the chart's own gate renders nothing. It reads a credential only from a file mounted from the chart's own Secret, and it never creates a Secret. Every container requests cpu and memory.
2. **The five tests.** Each `function-test.yaml` is the block of field 5 of the same name, byte for byte. What each one does and when it renders:

   | Chart | Renders when | Image | The test passes when |
   |---|---|---|---|
   | `bp-cnpg` | the release creates the webhook configurations (helper `bp-cnpg.webhookConfigsCreated` is `true`) | `harbor.openova.io/proxy-dockerhub/alpine/k8s:1.31.4` (the chart's webhook-gate image), or `functionTest.image` | a server-side dry-run create of a minimal `Cluster` named `function-test-probe` is accepted. A ServiceAccount, Role (verb `create` on `clusters` of `postgresql.cnpg.io`) and RoleBinding of the same file give the Pod that right. |
   | `bp-postgres` | `enabled` is not `false` and the API `postgresql.cnpg.io/v1` is served. These are the first two clauses of the gate of `templates/cluster.yaml` line 29. The test leaves out that gate's third clause (`not bp-postgres.renderReplicaHalf`), so unlike `cluster.yaml` it also renders on a replica half | the instance image `bp-postgres.imageRef` | mode `none` (empty `databases`): passes with the reason `no databases declared`. Mode `ready` (helper `bp-postgres.isReplicaSide`): `pg_isready` reaches the region's Cluster. Mode `write` (all other cases): it mounts the role Secret of the first entry of `databases`, logs in as its owner, and when `pg_is_in_recovery()` is `f` creates, fills, reads and drops a table; when it is `t` it passes after the login. A NetworkPolicy of the same file lets the Pod reach cluster DNS (`kube-system`, `k8s-app: kube-dns`, port 53 UDP and TCP) and port 5432 of the Pods `cnpg.io/cluster: <local Cluster>`. |
   | `bp-valkey` | always (the chart has no gate) | the chart's Valkey image | `SET`, `GET` and `DEL` of a random key on `bp-valkey.serviceHost` give the value back. The Pod carries the label `<fullname>-client: "true"` that the subchart's NetworkPolicy admits. With `valkey.auth.enabled` it mounts the password from the subchart's Secret. For a release name that does not contain `valkey`, `bp-valkey.serviceHost` names a Service the subchart does not render; the test dials it on purpose, as consumers do, and this ticket does not change the helper. |
   | `bp-seaweedfs` | `seaweedfs.s3.enabled` and `seaweedfs.s3.enableAuth` are true and `seaweedfs.s3.existingConfigSecret` is empty | `harbor.openova.io/proxy-dockerhub/alpine/k8s:1.31.4`, or `functionTest.image` | through `http://<fullname>-s3.<namespace>.svc.cluster.local:<port>` it creates a bucket, puts, gets and compares one object, deletes the object and the bucket, signed with the admin keys of `<fullname>-s3-secret`. |
   | `bp-nats-jetstream` | always (the chart has no gate) | the nats-box image of the nats subchart | on `nats://<fullname>.<namespace>.svc.cluster.local:<port>` a scratch stream acknowledges one message sent with `nats request`, a pull consumer reads it back, and the stream is deleted. |

   `<fullname>` is computed in each template the way the subchart computes it: `fullnameOverride`, else the release name when it contains the chart name (`valkey`, `seaweedfs`, `nats`, or the subchart's `nameOverride`), else `<release>-<name>`.
3. **The checker.** `scripts/check-function-test.py` is the block of field 5 of that name, byte for byte. It reads a `helm template` render on stdin and checks the documents whose `# Source:` line is `<chart>/templates/tests/function-test.yaml` against rules FT1 to FT12 (listed in its header). With `--absent` it checks that the file renders nothing (rule FT13). `--self-test` shows each rule failing on a render of its own. Exit 0 pass, 1 a rule broken, 2 unreadable input.
4. **The render tests.** Each chart gets `chart/tests/function-test-render.sh`, the block of field 5 of that name, byte for byte. Each first runs the checker's self-test, builds the chart's dependencies when `charts/` is empty, then renders every shape of the table above and checks it. CI's workflow `Chart tests (PR)` runs every `chart/tests/*.sh` of a changed chart; so these run on every later pull request that changes one of the five charts.
5. **The runbook.** `docs/RUNBOOKS.md` gets the section `### 4.5 Function test of a chart`, the block `runbooks-4.5.md` of field 5, inserted directly before the line `---` that precedes `## §5 — Demo / operator walks`. Nothing else in the file changes. It is a third-level heading on purpose: a new second-level heading would need a state marker.
6. **The baseline.** In `scripts/service-model-baseline.yaml` the line `  G6.function-test-charts: 0` becomes `  G6.function-test-charts: 5`. No other line changes.
7. **Nothing else changes.** No `values.yaml`, no other template, no other kit slot, and no line of an existing chart file other than the version lines of item 8. Two of the new templates (cnpg and seaweedfs) hold the image reference `harbor.openova.io/proxy-dockerhub/alpine/k8s:1.31.4` as a default value. It is part of the embedded block: you copy it and type no tag. The render test of `bp-valkey` has one line that ends in `|| true`: `labels=$(grep -c -F 'cache-valkey-client: "true"' "$TMP/cache.yaml" || true)`. It keeps `grep -c` from ending the script under `set -e` when it counts zero; the next line then fails with the count it found. It is part of the embedded block and weakens no check, so rule of conduct 8 is kept. No kit slot sets `spec.test`, so Flux runs none of these tests yet; package SVC-130 switches them on.     import yaml
    out = []
    for chunk in SPLIT.split(text):

        except yaml.YAMLError as e:

            continue
        if not isinstance(doc, dict):
            raise Unreadable("a document is not a mapping")
        out.append((m.group(1) if m else "", doc))
    return out

### 4.5 Function test of a chart

**Chart contract.** Every chart installed by a kit slot of the foundation ring, and every chart whose Blueprint is to be `supported`, ships exactly one file `chart/templates/tests/function-test.yaml` that renders one Pod with:

```yaml
metadata:
  name: {{ .Release.Name }}-function-test
  annotations:
    helm.sh/hook: test
    helm.sh/hook-delete-policy: before-hook-creation,hook-succeeded
  labels:
    catalyst.openova.io/function-test: "true"
spec:
  restartPolicy: Never
  activeDeadlineSeconds: 300
```

**Rules.** The test proves the chart's function, not its presence: it performs at least one write-then-read or request-then-response against the thing the chart installs. It exits 0 on pass and non-zero on fail. It prints one last line of the form `FUNCTION-TEST <pass|fail> <blueprint name> <one-line reason>`. It needs no network access outside the cluster. It uses an image the chart already ships or one already mirrored for the kit. It must render nothing when the chart's own master gate renders no resources. It must finish within 300 seconds. It reads a credential only from a file mounted for the test Pod or from the chart's own existing Secret; it never creates a Secret.

**How this repository applies it.**

- The `<blueprint name>` of the last line is the `name` of the chart's `Chart.yaml`, written as `{{ .Chart.Name }}`.
- Besides the Pod, the file may render only a ServiceAccount, a Role, a RoleBinding, a NetworkPolicy or a CiliumNetworkPolicy for the test, each with the same two hook annotations. A namespace under the platform's default-deny policy needs such a policy so that the test Pod can reach cluster DNS and the service it tests. Every container of the Pod requests cpu and memory: the policy that enforces requests matches Pods.
- Each such chart has a render test `chart/tests/function-test-render.sh`. It pipes `helm template` into `python3 scripts/check-function-test.py --chart <chart name> --release <release>`, and adds `--absent` for each gate under which the test must render nothing. The checker's rules are listed in its header; `--self-test` shows that each can fail. CI runs the render test with the chart's other `chart/tests/*.sh`.
- `python3 scripts/check-service-model.py` counts the charts that carry such a file (`G6.function-test-charts`). The pull request that adds one raises that count in `scripts/service-model-baseline.yaml` by one.
- `helm test <release>` runs the tests. Flux runs them only for a HelmRelease that sets `spec.test.enable: true`.

What each test asserts:

| Chart | The test passes when |
|---|---|
| `bp-cnpg` | The admission webhooks accept a server-side dry-run create of a minimal `Cluster`. It renders only when the release creates the webhook configurations. |
| `bp-postgres` | Logged in as the owner of the first entry of `databases[]`, it creates a table, inserts a row, reads it back and drops the table. A server in recovery passes after the login. |

# CLD-105 — Post-apply and apply-error hooks become capability interfaces

## In plain words

**The problem today.** After a successful apply the provisioning engine calls a hook variable that only one cloud adapter sets, behind a check of that cloud's name. Its retry loop holds that cloud's own list of failure texts and parses that cloud's resource names. Adding a cloud, or changing which of its failures deserve a retry, means editing the shared engine.

**What changes.** The cloud adapter itself says what runs after an apply and which of its apply failures are retried; the engine asks it through two capability interfaces and keeps no knowledge of one cloud for these two steps.

**Done means:**

- The engine has no post-apply hook variable and no list of failure texts of one cloud; it asks the adapter through the capability interfaces.
- On the Huawei cloud the same apply failures as before are retried with the same reasons shown, and a compute instance that fails three times in a row on the scheduler failure still stops the retries.
- A failed NAT address rotation after the apply is reported and does not fail the provision.
- The read-after-create inconsistency of OpenTofu is retried on every cloud, as before.
- The lines of the engine's main file that name a cloud fall from 34 to 21; the VPC pre-flight keeps its lines until CLD-115.

The rest of this ticket is the exact instruction for the model that does the work.

## 2. End goal
After `tofu apply` the engine runs the adapter's `providers.PostApplier`, reached with `providers.As`, instead of the hook variable `NATEIPPreflightHook` behind `req.Provider == "huawei"`. On a failed `tofu apply` it asks the adapter's `providers.ApplyErrorClassifier` whether to retry, with which reason, and which resource addresses the failure names, instead of its own list of Huawei failure texts and its parser of Huawei compute names. The Huawei adapter implements both in a new file `internal/providers/huawei/capabilities.go`; the behaviour of a Huawei provision is the same as before. The VPC pre-flight, its two hooks and `providers.Preflighter` stay as they are; they are CLD-115.

## 3. The model (the law)
1. `providers.ApplyErrorClass` (`internal/providers/capabilities.go`) gains `Addresses []string` (the resource addresses the failure names) and `StopOnRepeat bool` (stop the retries when an address of this failure has failed three consecutive times).
2. `internal/providers/huawei/capabilities.go` (new) declares that `*Provider` implements `providers.PostApplier` and `providers.ApplyErrorClassifier`.
3. `PostApply` calls `RotateBlocklistedNATEIPs` (through the package variable `rotateNATEIPs`, which only a test reassigns) with the deployment ID, the Sovereign FQDN and the credentials `access_key`, `secret_key`, `project_id` and `region` of `in.Spec`. A failed rotation is written to `in.Progress` as `EIP pre-flight check failed (non-fatal ...` and `PostApply` returns no error; a rotation of N > 0 addresses writes `Wave 5.93: rotated N blocklisted NAT EIPs before Phase 1`. It never asks for a re-apply.
4. `ClassifyApplyError` calls retryable exactly the texts the engine matched: `Common.0021`, `CollectInfoTask-fail`, `conflict in the request` together with `error allocating EIP` or `error creating`, `VPC.2030`, and `Provider produced inconsistent result after apply`. The reasons are the engine's former labels: `HCS EIP-conflict (quota / propagation)`, `HCS VPC-conflict (quota / propagation)`, `HCS resource-conflict (quota / propagation)`, otherwise `HCS Common.0021 (CollectInfoTask-fail)`. `Addresses` are the texts after `with huaweicloud_compute_instance.` (trailing comma removed); `StopOnRepeat` is true when the text holds `Common.0021`.
5. The engine's `classifyApplyError(provider, stderr)` takes the adapter's class when it implements `ApplyErrorClassifier`, makes `Provider produced inconsistent result after apply` retryable on every cloud (#3142), and gives a retryable class without a reason the reason `transient apply failure`.
6. The engine's `applyFailures.record(class)` counts each address of a retryable failure, forgets every address the failure does not name, and returns the addresses that have now failed three consecutive times when the class stops on a repeat; the engine then fails the provision with the reason, the addresses and the deployment ID. Otherwise it waits the same backoff and retries as before, showing the class's reason.
7. After a successful `tofu apply` the engine calls `PostApply` of an adapter that implements `providers.PostApplier`, with `capabilitySpec(req)` and a `Progress` that emits on the stage `post-apply`. An error fails the provision (`post-apply: ...`); `ReapplyNeeded` runs `tofu apply -input=false -no-color -auto-approve -parallelism=2` once more.
8. `capabilitySpec(req)` is `req.providerSpec()` without every credential whose value is `RedactedMarker`, as `Request.Credential` reads it; the request's own map is not changed.
9. Deleted: `natEIPPreflightFunc`, `NATEIPPreflightHook` and its block after `tofu apply` in `internal/provisioner/provisioner.go`, `extractFailedAddrs`, `lastFailedAddrs`, `isTransient` and `errLabel` there, and the line `provisioner.NATEIPPreflightHook = RotateBlocklistedNATEIPs` in `internal/providers/huawei/provider.go`.
10. Kept: `VPCQuotaHook`, `VPCReclaimHook`, the inline VPC pre-flight with its `req.Provider == "huawei"` guard, `VPCQuotaPreflight` and `VPCReclaimPreflight`. They are CLD-115.
11. All seven paths change only through the patch `CLD-105.patch` of this ticket.

+// failures of `tofu apply` that a backoff and a re-plan fix.
+//   - Common.0021 / CollectInfoTask-fail (Wave 5.132): the scheduler's
+//     per-worker info task timed out; the instance gets a new name salt.
+//   - "conflict in the request" on an EIP, VPC or other create (Waves 5.143

+func (p *Provider) ClassifyApplyError(stderr string) providers.ApplyErrorClass {
+	has := func(s string) bool { return strings.Contains(stderr, s) }
+	conflict := has("conflict in the request") && (has("error allocating EIP") || has("error creating"))
+	retryable := has("Common.0021") || has("CollectInfoTask-fail") || conflict || has("VPC.2030") ||
+		has("Provider produced inconsistent result after apply")

+		return providers.ApplyErrorClass{}
+	}
+	reason := "HCS Common.0021 (CollectInfoTask-fail)"
+	switch {
+	case has("error allocating EIP"):
+		reason = "HCS EIP-conflict (quota / propagation)"
+	case has("error creating VPC"):
+		reason = "HCS VPC-conflict (quota / propagation)"
+	case has("error creating") && has("conflict in the request"):
+		reason = "HCS resource-conflict (quota / propagation)"
+	}
+	return providers.ApplyErrorClass{Retryable: true, Reason: reason, Addresses: failedComputeAddrs(stderr), StopOnRepeat: has("Common.0021")}

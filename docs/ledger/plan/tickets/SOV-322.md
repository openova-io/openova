# SOV-322 — Sign-in mail from the Sovereign's own server: kit slot, settings, and the parent seed deleted

## In plain words

**The problem today.** A new Sovereign sends its sign-in codes through the parent's mail server, with the parent's own mailbox credential, which the parent copies into the Sovereign at first boot. The Sovereign's own mail server chart exists but is not installed, and as it stands it could not send a code: its server release ignores the chart's settings, its setup Job cannot finish, and the server has no certificate that a mail client accepts.

**What changes.** The bootstrap kit installs the Sovereign's own mail server, with a certificate for its submission host and a setup Job that works against the server release it pins. The sign-in code goes from the console to that server with a credential made in the cluster, and the parent's mailbox credential is no longer copied.

**Done means:**

- The bootstrap kit has slot 95, which installs the mail server chart without making the kit wait for it, and only when the Sovereign's mail mode is local.
- The setup Job creates the Sovereign's domain and the submission account, judges each answer of the server by its body, pins the submission host to the server inside the cluster, and only then writes the mail settings Secret.
- The server presents a certificate for mail.<fqdn> from the Sovereign's certificate issuer and declares the administrator the setup Job uses.
- The catalyst-api reads the mail settings Secret for every sign-in code, so a Secret written after the console started is used without a restart, and the console's network policy lets it reach the mail server.
- No code of the catalyst-api writes a mail credential into a Sovereign; the seed and its test are deleted.
- The chart test proves each new rule of the chart and its setup Job, and fails when one of them is broken.

The rest of this ticket is the exact instruction for the model that does the work.

## 2. End goal
On a fresh Sovereign whose `MAIL_MODE` is `local` (the default of every cloud), bootstrap-kit slot 95 installs the chart `platform/stalwart-sovereign` into namespace `stalwart`. The mail server runs release v0.15.5 with a certificate for `mail.<fqdn>` from the Sovereign's `WILDCARD_CERT_ISSUER`. Its setup Job creates the domain and the submission account `noreply` with a password generated in the cluster, pins `mail.<fqdn>` to the mail Service in the CoreDNS extension ConfigMap, and then writes `catalyst-system/sovereign-smtp-credentials`. The catalyst-api reads that Secret on every sign-in code and submits the code to `mail.<fqdn>:587` over STARTTLS with that credential. The parent no longer writes its own mailbox credential into the new Sovereign: `sovereign_smtp_seed.go`, its test and its call are deleted. The kit never waits for mail.

## 3. The model (the law)
1. The parent copies no mail credential into a Sovereign. No code of the catalyst-api writes `catalyst-system/sovereign-smtp-credentials`; the only writer is the setup Job of the Sovereign's own mail server.
2. The setup Job writes that Secret only after the server knows the credential (the principal is confirmed) and after `mail.<fqdn>` resolves to the server inside the cluster (the pin is written). A reader never gets a credential the server does not know or a host that does not reach it.
3. The server release v0.15.5 answers HTTP 200 to almost every admin call, also when it refuses one; a refusal is the body `{"error":"<name>",...}`, a success the body `{"data":...}`. The Job judges every admin answer by its body, never by the status code alone. It waits on `/healthz/ready`, which answers without credentials (`/api/health` answers 404 on this release).
4. The server's file declares the administrator the Job calls the API as: `[authentication.fallback-admin]` with user `admin` and the secret `%{env:ADMIN_PASSWORD}%`. It holds no `[auth.dkim]` rule; the server's own rule applies.
5. The submission host is `mail.<fqdn>`, the name in the certificate, never a Service name. The certificate is one name, `mail.<fqdn>`, from `certificate.issuerName`; the pod mounts it at `/opt/stalwart/tls` and starts only once it is issued; reloader restarts the pod when it is renewed.
6. Inside the cluster `mail.<fqdn>` is pinned to the cluster address of the mail Service by a separate `.server` block in the key `stalwart-sovereign-mail-pin.server` of `kube-system/coredns-custom`, merge-patched (other keys stay), the same mechanism as cutover step 03 pins the registry name.
7. The chart's Services select the server's pods only (label `app.kubernetes.io/component: mail-server`). The Job's pod keeps the selector labels, so the chart's NetworkPolicy still selects it, and is never an endpoint. The StatefulSet's own selector does not change.
8. With `mailMode` other than `local` the chart renders no object. The kit passes `${MAIL_MODE:=local}`: a Sovereign made before `MAIL_MODE` was a variable has no such key.
9. After the hand-over the admission policies stay satisfied: both images come through `global.imageRegistry` (the kit passes the proxy), the Job's container has CPU and memory requests and limits, and no env entry of the Job with a plain value has a name with PASSWORD, TOKEN, KEY or SECRET.
10. The catalyst-api reads `catalyst-system/sovereign-smtp-credentials` for every sign-in code and uses it as a whole when it has host, user and password; otherwise its environment answers. It never mixes the two credentials. The read lives in a new package; the handler package does not grow.
11. The kit slot sets `install.disableWait` and `upgrade.disableWait` to `true`, depends only on `bp-cert-manager` and `storage-ready`, runs in the primary region only, and no slot depends on it. The mail Service is ClusterIP: no address of the region's pool, no node port.
12. Deleted: `products/catalyst/bootstrap/api/internal/handler/sovereign_smtp_seed.go`, its test, its call in `kubeconfig.go` and its client factory field in `handler.go`.

+// On a Sovereign the setup Job of its own mail server (bootstrap-kit slot

+// Settings is where and as whom a sign-in code is submitted.
+type Settings struct {
+	Host, Port, From, User, Pass string

+// Addr is host:port for net/smtp.

+// ClientFor builds the client that reads the Secret. A test replaces it; an
+// error or a nil client means no in-cluster identity, and Resolve answers
+// from the environment.
+var ClientFor = func() (kubernetes.Interface, error) {
+	cfg, err := rest.InClusterConfig()
+	if err != nil {
+		return nil, err
+	}
+	return kubernetes.NewForConfig(cfg)
+}

+// FromEnv returns the settings of the process environment, with the
+// defaults of the catalyst-api for host, port and sender.
+func FromEnv() Settings {
+	s := Settings{
+		Host: os.Getenv("CATALYST_SMTP_HOST"),
+		Port: os.Getenv("CATALYST_SMTP_PORT"),
+		From: os.Getenv("CATALYST_SMTP_FROM"),
+		User: os.Getenv("CATALYST_SMTP_USER"),
+		Pass: os.Getenv("CATALYST_SMTP_PASS"),
+	}
+	if s.Host == "" {
+		s.Host = defaultHost
+	}
+	if s.Port == "" {
+		s.Port = defaultPort
+	}
+	if s.From == "" {
+		s.From = defaultFrom
+	}

+// Resolve returns the settings of the Secret when it holds a host, a user
+// and a password, and the settings of the environment otherwise: when the
+// Secret is absent, unreadable or incomplete, or when the process has no
+// in-cluster identity. It never mixes the two credentials.
+func Resolve(ctx context.Context) Settings {
+	env := FromEnv()
+	cli, err := ClientFor()

+		return env
+	}
+	ctx, cancel := context.WithTimeout(ctx, readBudget)
+	defer cancel()
+	sec, err := cli.CoreV1().Secrets(Namespace).Get(ctx, ObjectName, metav1.GetOptions{})
+	if err != nil || sec == nil {
+		return env
+	}
+	return fromSecret(sec.Data, env)
+}

+	}
+	if s.From == "" {
+		s.From = env.From
+	}

# CLD-106 — Operator credentials from mounted files

## In plain words

**The problem today.** The control plane takes the cloud credentials of the mothership's own account from four environment variables that the chart fills from a Kubernetes Secret. A credential in an environment variable is visible to anyone who can read the pod's definition or its process environment, and the Secret object rests in the cluster store. Platform credentials must arrive as mounted files instead.

**What changes.** The control plane reads those credentials only from files that the Secrets Store CSI driver mounts read-only from OpenBao. The chart no longer sets the four variables or names the Secret, and mounts the files only where a secret provider class is named.

**Done means:**

- The control plane reads the operator cloud credentials only from files in the directory of its flag, by default /var/run/secrets/openova, and never from an environment variable.
- A create request that relies on the operator credentials is refused with a named error when a credential file cannot be read.
- Credentials in a request still win over the operator files, and a wipe or janitor sweep without credentials still falls back to the operator files.
- Neither Deployment manifest of the chart sets the four retired variables or names the Secret huawei-operator-creds.
- By default the chart mounts no credential volume; when a secret provider class is named it mounts one read-only at the default directory, and the mothership manifest names catalyst-api-cloud-credentials.
- Moving a reader back to the environment, or renaming the flag, turns the tests red.

The rest of this ticket is the exact instruction for the model that does the work.

## 2. End goal
After this package catalyst-api has one source for the cloud credentials of the operator's own account: the files `cloud-credential.<provider>.<key>` in the directory of its new flag `--cloud-credentials-dir`, default `/var/run/secrets/openova`, where the Secrets Store CSI driver (SEC-211) mounts them read-only from OpenBao. The create handler, the wipe and janitor fallback and `provisioner.New` read the files; nothing reads `CATALYST_HUAWEI_ACCESS_KEY`, `CATALYST_HUAWEI_SECRET_KEY`, `CATALYST_HUAWEI_PROJECT_ID` or `CATALYST_HUAWEI_REGION` any more. Both Deployment manifests of `products/catalyst/chart` lose those four variables and every reference to Secret `huawei-operator-creds`. The Helm template mounts a CSI volume only when `catalystApi.cloudCredentials.secretProviderClass` names a class (default `""`, so a Sovereign mounts nothing), and the mothership's literal manifest names `catalyst-api-cloud-credentials`. A new chart test proves the three renders and the Go default.

## 3. The model (the law)
1. The operator cloud credentials of catalyst-api come only from the files `cloud-credential.<provider>.<key>` in the directory of flag `--cloud-credentials-dir`. Its default is the constant `provisioner.DefaultCloudCredentialsDir` = `/var/run/secrets/openova`; `provisioner.RegisterFlags` registers the flag and `cmd/api/main.go` calls it before `flag.Parse()`. `provisioner.ReadOperatorCredentials(dir)` returns the files by provider and key; a directory that does not exist reads as no credentials; a file whose name has not that form is an error.
2. Three readers use the files: the create handler in `internal/handler/deployments.go` (a file that cannot be read answers HTTP 500 with error `operator-credentials-unreadable`), the wipe and janitor fallback `deploymentCredentials` in `internal/handler/wipe.go`, and `provisioner.New` (field `OperatorCredentials`). Credentials in the request body win over the files, key by key.
3. No Go file outside tests names the four variables. Tests that set them do so to prove that they are ignored.
4. Both `products/catalyst/chart/templates/api-deployment.yaml` and `products/catalyst/chart/templates/api-deployment-kustomize.yaml` lose the four variables and every reference to Secret `huawei-operator-creds`. No Secret volume and no `envFrom` replaces them.
5. The Helm template renders volume `cloud-credentials` (`csi.driver: secrets-store.csi.k8s.io`, `csi.readOnly: true`, `csi.volumeAttributes.secretProviderClass: <the value>`) and its read-only mount at `/var/run/secrets/openova` on container `catalyst-api` only when `catalystApi.cloudCredentials.secretProviderClass` is not empty. Its default in `values.yaml` is `""`. The literal manifest carries the same volume and mount, naming `catalyst-api-cloud-credentials`.
6. The variables `CATALYST_HUAWEI_NAT_EIP_*` (the EIP store) are other variables and stay.
7. No new Python, no NodePort, no change to a live system.

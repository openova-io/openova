## Answer

- **Where the sign-in lives: (a), on the workspace's volume.** A person signs in to unmodified Claude Code inside the workspace. Claude Code is the party that spends the refresh token, and it writes the successor back to its own file, under its own lock (E1, E2B, E3). A copy read by mount, as in (b), cannot take the successor back. The mount would go stale after the first refresh, and keeping it current needs a second writer. That second writer is the failure E4 shows.
- **Whose identity the tool path carries: (b), an agent token.** Option (a) cannot be built with the pinned daemon:
  - the gate passes no token upstream;
  - the daemon reads none;
  - the agent acts between a person's requests, after a request-time token has gone.

  An agent token of at most one hour works for reading, once the tool server reads it from a file at every call (arm C). `create_application` needs the acting person's tier admin on that token (arm D), and nothing issues such a token today.
- **The outcome as shipped is fail:** T2, T3 and the create half of T4.

# FND-133 — The conformance run of a pull request installs the kit charts of that pull request, proven by a run of its own

## In plain words

**The problem today.** The conformance run of a pull request installs the kit charts that were published from main, not the charts the pull request changes. A first repair was merged and taken back out: on the first pull request that changed a kit chart its run waited 40 minutes and failed, although both charts had been switched to the tree, because the run read the wrong kind of object and never saw them. That repair had never run its new path before it was merged.

**What changes.** The conformance run of a pull request takes each kit chart that the pull request changes from the tree of the pull request again, and reads the state of each chart from the object Flux writes. A pull request that changes this path installs one kit chart from the tree in its own run, so the path is proven before it merges.

**Done means:**

- The local pack prints, from the source, each release of its kit with its chart, its version and where the chart comes from.
- A changed file in the folder of a kit chart, or in the folder of a library chart that it packages, takes that chart from the tree of the pull request; a file beside the folder takes nothing from the tree.
- The run reads the state of a chart from the tree from the HelmChart object of Flux, and keeps the error of a read that fails in its evidence.
- A pull request that changes the pack script or the conformance workflow installs the policy chart from its own tree in both regions.
- The conformance run of the pull request that delivers this is green and names the policy chart as installed from the tree in both regions.
- A pull request that changes no kit chart and not this path installs every chart from the published registry, as before.

The rest of this ticket is the exact instruction for the model that does the work.

## 2. End goal
The job `conformance-local` of a pull request or a merge group installs, in every region of the local pack, each kit chart that the change touches from the tree of the commit under test, and passes only when each of them is installed from that tree. This is the change of FND-132 (pull request 8954, merge commit `1de13c93ec`), which pull request 8973 (merge commit `c009504d1e`) took off `main`, brought back with its defect repaired: the pack reads the HelmChart of a release as `helmcharts.source.toolkit.fluxcd.io`, because on k3s the short name `helmchart` is the HelmChart kind of `helm.cattle.io`, and keeps the error of a read that fails beside it. A pull request or merge group that changes the tree path itself (`scripts/local-pack.sh` or `.github/workflows/conformance-local.yaml`) also lists `platform/kyverno-policies/chart/Chart.yaml` among its changed paths, so its own run installs `bp-kyverno-policies`, a release of the kit core, from the tree in both regions. A person sees it in the log of the step "Up (two regions)" (`region-a: kit charts of the tree: bp-kyverno-policies: installed from the tree: ...`), in the job summary "Kit charts of the local pack" and in `bash scripts/local-pack.sh charts --changed <file>`.

The error of a HelmChart read that fails is kept in `<region>-<release>-helmchart.err` of `tree/`, which `collect` copies with the other files of `tree/`.
3. **A change of the tree path is proven by its own run.** The step "Decide whether the pack runs" has the env `TREE_PROBE: platform/kyverno-policies/chart/Chart.yaml`. When it runs the job in full on a pull request or a merge group and its changed paths name `scripts/local-pack.sh` or `.github/workflows/conformance-local.yaml` exactly, it appends `$TREE_PROBE` to `$RUNNER_TEMP/changed-paths.txt` and prints a notice. The plan then takes `bp-kyverno-policies` from `./platform/kyverno-policies/chart` of the tree, in both regions. A path that only resembles one of the two names appends nothing. No file of the chart changes.
4. **The self-test's stand-in answers as k3s does.** Its stand-in docker answers `get helmchart <name>` with the NotFound of `helmcharts.helm.cattle.io` and serves the HelmChart only to `get helmcharts.source.toolkit.fluxcd.io`; a case proves that a HelmChart that cannot be read waits and that its error is kept.
5. No chart version line changes. No Python is added: no new file, and no Python line in the script or the workflow (two comment lines of the script name `python3` among its tools, as before). No Service of type NodePort and no node port anywhere.

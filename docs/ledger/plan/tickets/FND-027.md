# FND-027 — A moved funnel pin rebuilds the provisioning image; the openclaw build writes no seed pin

## In plain words

**The problem today.** The chart versions that a new Organization's apps install are compiled into the provisioning service's image. The release job moves that list when it publishes one of those charts, but its commit is marked so that it starts no build, so the running service keeps installing the old versions. The openclaw build also writes the catalog entry of its chart itself, minutes before the release moves the compiled list, and in that window a test on main is red.

**What changes.** When the release commit moves the compiled list, the release job starts the provisioning build once. The openclaw build stops writing the catalog entry, and the release moves the catalog entry and the compiled list in one commit.

**Done means:**

- A release of a funnel chart that moves the compiled chart list starts exactly one run of the provisioning build on main, also when its push had to be retried.
- A release that leaves the compiled chart list as it was starts no provisioning build.
- The openclaw build commits no catalog-seed line; the release commit after it moves the catalog seed and the compiled chart list together.
- The release guard proves all three by running the workflow's own steps, and fails on the workflows as they were before this task.
- The release commit still starts no workflow by itself.

The rest of this ticket is the exact instruction for the model that does the work.

## 2. End goal
After a release of one of the four funnel charts (bp-openclaw, bp-stalwart-tenant, bp-newapi, bp-agenity), the provisioning service installs the new chart version without a hand step. A person sees it in the Actions tab: the `build` job of `Blueprint Release` that pushed a commit moving `DefaultHRAppChartVersions` has a step "Provisioning image: dispatch its build when the funnel pin moved", and a run of `Build & Deploy Catalyst Backend Services` (`.github/workflows/services-build.yaml`) started by `workflow_dispatch` on `main` follows it. A release that does not move the funnel pin has that step skipped. The openclaw controller build (`.github/workflows/openclaw-controller.yaml`) commits only its chart values, `Chart.yaml` and `blueprint.yaml`; the release commit that follows moves the bp-openclaw catalog-seed pins and the funnel pin together. The guard `scripts/check-release-lockstep-writer.py` proves all of it by running the workflows' own steps.

## 3. The model (the law)
1. The funnel pin is the constant `DefaultHRAppChartVersions` in `core/services/provisioning/gitops/helmrelease_apps.go`. The provisioning service reads `CATALYST_HR_APP_CHART_VERSIONS` with that constant as the default (`core/services/provisioning/main.go`), and no chart sets the variable. So the running service installs the pin its image was compiled with.
2. Only `.github/workflows/services-build.yaml` builds the provisioning image. It starts on a push under `core/services/**` or by `workflow_dispatch`. One run builds every service of its matrix (auth, catalog, gateway, tenant, domain, billing, provisioning, notification, metering-sidecar) from the commit it runs on; its job `deploy` writes that commit's short hash into `images.orgTag` of `products/catalyst/chart/values.yaml`, bumps the umbrella chart version and dispatches `blueprint-release.yaml -f blueprint=catalyst -f tree=products`. This ticket does not change that workflow.
3. The commit that the release writer pushes (the step "Commit + push bootstrap-kit pin bump + blueprint.yaml lockstep" of the job `build` of `.github/workflows/blueprint-release.yaml`) keeps `[skip ci]` at the end of its first line. Its push starts no workflow.
4. That commit step gets the id `lockstep_push`. Right after the push that succeeded, and only then, it writes the step output `funnel_moved`: `true` when the pushed commit changed `core/services/provisioning/gitops/helmrelease_apps.go` against its parent, otherwise `false`. A run that pushes nothing (nothing staged, or main already carries the versions) writes no output.
5. A new step of the job `build`, right after the commit step, with the id `dispatch_provisioning`, runs when `steps.chart.outputs.skip != 'true' && steps.lockstep_push.outputs.funnel_moved == 'true'`. It runs `gh workflow run services-build.yaml --repo <repository> --ref main` with the job token. One job runs it at most once, because the commit step's retry loop ends at the first push that succeeds. The dispatch is in the job `build` and not in a follow job like `umbrella-follow`: only the commit step knows whether the commit it pushed moved the funnel pin; a follow job sees one output of a matrix, and main read later cannot tell which commit moved it. A push run that releases several funnel charts dispatches once per chart.
6. The workflow-level permission `actions` of `blueprint-release.yaml` becomes `write` (it was `read`). The job `build` has no permissions block of its own and keeps none.
7. `.github/workflows/openclaw-controller.yaml` writes no catalog-seed line: its step "Bump catalog-seed bp-openclaw version pins" and its env `CATALOG_SEED` are deleted, and the seed file is not among the `paths` of its deploy-bump step. It still writes the controller and runtime image tags into `platform/openclaw/chart/values.yaml`, bumps the patch version of `platform/openclaw/chart/Chart.yaml` and `platform/openclaw/blueprint.yaml`, commits them through `./.github/actions/deploy-bump` and dispatches `blueprint-release.yaml -f blueprint=openclaw -f tree=platform`. The dispatched run reads the version from `Chart.yaml`, and its step `sync_seed` moves the seed, the generated catalog and the funnel pin in its one commit.
8. The guard `scripts/check-release-lockstep-writer.py` runs the step `dispatch_provisioning` after the commit step in every case of its common path, with its `gh` stand-in on `PATH`, and counts the calls `workflow run services-build.yaml ... --ref main`. A case that moves the funnel pin expects 1 (`funnel`, `funnel-retry`, `funnel-seed-ahead`, `funnel-openclaw`); every other case expects 0. A case that names an expected count fails when the step does not exist. The new case `funnel-openclaw` makes the openclaw build's commit from the `paths` of the deploy-bump step of `openclaw-controller.yaml` (resolving `${{ env.NAME }}` from that workflow's env) and fails when those paths hold the seed file; the release commit must carry the seed and the funnel pin. The new case `no-dispatch` releases bp-keycloak (it moves the seed and has no funnel pin) and expects 0. The 17 cases that exist keep passing. Because the guard now reads `openclaw-controller.yaml`, its workflow `.github/workflows/check-release-lockstep-writer.yaml` also triggers on that file.
9. `docs/RUNBOOKS.md` section 2.4 says that the release job dispatches the provisioning build when its commit moved the funnel pin, and that a build workflow that bumps a chart writes no seed line and no funnel pin.
10. Nothing is deleted except the openclaw seed step and its env line. No file is created.

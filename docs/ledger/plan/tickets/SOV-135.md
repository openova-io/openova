# SOV-135 — The mothership registry name is a proxy name served at the root, with an origin address per provider

## In plain words

**The problem today.** The variables document that a parent writes for a new Sovereign cannot be turned into the node registry file. The renderer refuses it, because the registry host of the parent is also one of the listed registry names. The document also has no entry for the name under which the images of the platform are pulled, it lists two registries that no origin serves through a proxy project, and it gives no origin address per name. The task that makes nodes boot from this document cannot start.

**What changes.** The document lists the registry name of the platform images and the Crossplane package registry as names served at the root, drops the one name nothing pulls from, and carries an origin address for every name. The renderer accepts a document whose origin host is one of the listed names.

**Done means:**

- The renderer turns the document of a new Sovereign into a node registry file without an error.
- Every registry name of the document has exactly one entry in that file, and the two names served at the root have no path rewrite.
- Every name has an origin address: the registry of the parent, or on the reference cloud the registry address inside that cloud.
- The Crossplane package registry has its own public address as origin on every cloud.
- The registry name that nothing pulls from is gone from the list.
- The path of Crossplane packages is unchanged.
- The guard that counts source addresses in the code passes, with its count for the API raised by exactly the three lines this task adds.

The rest of this ticket is the exact instruction for the model that does the work.

## 2. End goal
A parent writes the variables document (contract C5) of every new Sovereign in `childVariables` (`products/catalyst/bootstrap/api/internal/provisioner/provisioner.go`). After this ticket that document can be rendered into the node registry file by `upstream.Variables.RegistriesYAML` without an error. Its key `REGISTRY_PROXY_PROJECTS_JSON` lists eight registry names. Two of them, `harbor.openova.io` and `xpkg.upbound.io`, have an empty path: a registry serves them at its root. The name `public.ecr.aws` is gone. Its key `ORIGIN_PROXY_ENDPOINTS_JSON` names an origin address for each of the eight names. The address is `https://harbor.openova.io`, or the address that the adapter of the provider registers, and for `xpkg.upbound.io` it is `https://xpkg.upbound.io` on every provider. No node, chart or module reads the two keys differently after this ticket: SOV-132 makes the nodes boot from them.

## 3. The model (the law)
1. **The closed list.** The key set of `REGISTRY_PROXY_PROJECTS_JSON` is the closed list of registry names a node may pull from. The document that `legacyOwnVariables` returns holds exactly these eight names and paths:

   | name | project path |
   |---|---|
   | `docker.io` | `proxy-dockerhub` |
   | `registry-1.docker.io` | `proxy-dockerhub` |
   | `quay.io` | `proxy-quay` |
   | `gcr.io` | `proxy-gcr` |
   | `registry.k8s.io` | `proxy-k8s` |
   | `ghcr.io` | `proxy-ghcr` |
   | `harbor.openova.io` | empty |
   | `xpkg.upbound.io` | empty |

   The line of `public.ecr.aws` is deleted. The line of `xpkg.upbound.io` loses its path `proxy-xpkg`. The line of `harbor.openova.io` is new.
2. **An empty path means served at the root.** The node asks the registry for the image under the path the image name already has. The renderer writes no rewrite for such a name, and the registry-projects Job of the Harbor chart creates no project for it. Both behave so today; this ticket changes neither.
3. **Every name has an origin address.** `childVariables` fills `ORIGIN_PROXY_ENDPOINTS_JSON` with one entry per name of the closed list. The address of a name is the first of these that exists:
   1. the entry of the name in `legacyOriginByName`, a new map in `provisioner.go` with the one entry `xpkg.upbound.io` to `https://xpkg.upbound.io`;
   2. the entry of the provider in `OriginRegistryByProvider`, a new exported map in `provisioner.go`, empty in that file. The provider name is `req.Provider`, trimmed and in lower case;
   3. the new constant `legacyOriginRegistry`, `https://harbor.openova.io`.
4. **The address of a cloud lives in the adapter of that cloud.** The guard `scripts/check-provider-leaks.py` refuses one more line in `provisioner.go` that names a provider or its address. So the address `http://212.72.24.20:5000` is written in a new file of the adapter, `products/catalyst/bootstrap/api/internal/providers/huawei/origin_registry.go`. Its `init()` sets `provisioner.OriginRegistryByProvider["huawei"]`. This is the pattern of `NATEIPPreflightHook` and `VPCQuotaHook`, which the same adapter sets from `init()` in `provider.go`. No other adapter registers an address.
5. **Why `xpkg.upbound.io` differs.** No registry of the parent serves a proxy project for `xpkg.upbound.io` (field 4). So the name is served at the root and its origin is its own public registry. A first boot then gets the provider package from where it gets it today.
6. **The renderer.** `RegistriesYAML` writes one more entry for `ORIGIN_REGISTRY_HOST` while `SOVEREIGN_CONSUME` is `origin`. When that host is itself a key of `REGISTRY_PROXY_PROJECTS_JSON`, the entry of the name stands and the renderer writes no second entry. Today it returns the error `would have two mirror entries` instead. A local registry host that is a proxy name is still refused.
7. **The package path stays.** `REGISTRY_PATH_XPKG` stays `proxy-xpkg`, in `legacyOwnVariables` and as the default of the contract. It is no longer equal to the project path of `xpkg.upbound.io`. The description of `REGISTRY_PATH_XPKG` in the contract file `docs/contracts/c5-upstream-variables.schema.json` and in its copy `core/controllers/pkg/upstream/contract/c5-upstream-variables.schema.json` says so: the sentence `Equal to the proxy project of xpkg.upbound.io, so one copy serves both the package manager and the nodes.` becomes `It need not equal the project path of xpkg.upbound.io in REGISTRY_PROXY_PROJECTS_JSON: that name may be served at the root, with an empty path.` Both files stay byte for byte equal.
8. **The baseline of guard G1.** `scripts/check-upstream-literals.sh` counts the lines that hold a source address. This ticket adds three such lines in scope `api`: the constant `legacyOriginRegistry`, the entry of `legacyOriginByName` and the constant `projectRegistry` of the adapter. The line `api=17` of `scripts/upstream-literals-baseline.txt` becomes `api=20`. The guard's own `--write-baseline` refuses to raise a number, so the edit script of this ticket writes the line. The rise is decided: the three lines are transitional, and SOV-940 deletes them with `legacyOwnVariables`.
9. **Nothing else changes.** No chart, no kit file, no provider module, no fixture and no existing test changes. Nothing is deleted except the two map lines of item 1.

		"ORIGIN_PROXY_ENDPOINTS_JSON", `{"ghcr.io":"`+near+`","registry.parent.example.net":"`+parent+`","root.example.net":"https://root.example.net"}`,
	)

		t.Fatalf("the document breaks a rule of the contract: %v", errs)

		t.Fatalf("the origin host is a proxy name and the document is refused: %v", err)

	want := map[string]mirror{
		"ghcr.io":                     {Endpoint: []string{local, near}, Rewrite: map[string]string{"(.*)": "proxy-ghcr/$1"}},

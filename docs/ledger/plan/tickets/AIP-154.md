# AIP-154 — An agent token acts for a person of tier admin, for create_application only

## In plain words

**The problem today.** The agent workspace of an Organization must be able to install an Application for the person who asked for it, but its short-lived agent token is capped below the tier that installing needs and may change nothing at catalyst-api. Nothing can say that an agent acts for a person who holds that tier.

**What changes.** An agent token can name the person it acts for. catalyst-api writes that only after it has itself read that the person is an administrator of the Organization, and such a token may install an Application and nothing else more than before.

**Done means:**

- A token asked for on behalf of an administrator or owner of the Organization names that person and acts at tier admin.
- A token asked for on behalf of anyone else, or for an Organization that does not list the person, is refused.
- The tier is read from the Organization when the token is issued; a request cannot state it.
- Such a token may install an Application in its Organization and change nothing else.
- The tool server offers create_application to such a token and to no other agent token.
- Every agent token without the claim behaves as before.

The rest of this ticket is the exact instruction for the model that does the work.

## 2. End goal
catalyst-api issues agent tokens at `POST /api/v1/internal/agent-tokens` (package `products/catalyst/bootstrap/api/internal/agenttoken`, contract `docs/contracts/model-contract.md` section 2). Today an agent token carries tier viewer or developer, `agenttoken.MutationsAllowed` is empty, and the tool server caps an agent token at developer, while `create_application` needs tier admin. So the agent workspace cannot install an Application. After this ticket the request may name an acting person (`"actingPerson": "<email>"`). catalyst-api reads the Organization object (`orgs.openova.io/v1`, named by the slug) and writes the claim `acting_person` (`{"email": "<email, lower case>", "tier": "admin"}`) only when the person's role in its `spec.owners` is `admin` or `owner` at that moment. The claim has two readers. At catalyst-api, `MutationsAllowed` gains the one entry `POST /api/v1/org/applications` for a token with the claim. At the tool server, such a token takes its tier, admin, from the claim, so `tools/list` offers `create_application` and a call of it reaches `POST /api/v1/org/applications`. Who the workspace names as the acting person is AIP-155's.

## 3. The model (the law)
1. A request without `actingPerson` is served exactly as on `main`: the same claims, the same refusals, the same audit event.
2. `actingPerson` is an email address (at most 64 characters, `@`, at most 189 characters, no blank). It is compared in lower case. Anything else is 422 `invalid-request`. The request carries no tier for the person: any further field is 422 as on `main`.
3. The person's tier is read by catalyst-api at every issue, after the caller is admitted (`unauthorized-sa` and `caller-not-allowed` come first): the role of the entry of `spec.owners` of the Organization object `<organization>` whose `email` equals the person's, in any letter case. Role `admin` or `owner` gives the claim. Any other role, no entry, or no Organization is 403 `acting-person-not-admin`. A read that fails is 502 `organization-read-failed`. No refusal holds a token or writes an audit event.
4. The claim is `acting_person: {"email": "<email, lower case>", "tier": "admin"}`. Its tier is always `admin`, for an owner too. The token's own `tier` claim is the tier the request asked for, viewer or developer, as on `main`. The audit event gains ` acting_person=<email>` at the end of its detail.
5. `MutationsAllowed` has exactly one entry: `POST` on the whole path `/api/v1/org/applications`, minimum tier viewer, for a token whose `acting_person` names an email and the tier `admin` (`Acting: true`, `ActsForAdmin`). A token without that claim matches no entry; a token with it matches no other method or path.
6. `auth.Claims` (`internal/auth/session.go`) gains `ActingPerson *ActingPerson` (claim `acting_person`), so the claim survives the session check that runs before `Restrict`.
7. At the tool server an agent token's tier stays the `tier` claim capped at developer. A token with `acting_person` takes the tier admin from it; the claim must name an email and the tier `admin`, or the token is refused. Everything else of an agent token is checked as on `main`.
8. The Organization object is read with a client of the cluster catalyst-api runs in, built in the package on first use. `New` keeps its signature, so the route table and `cmd/api` do not change. catalyst-api may already read Organizations.

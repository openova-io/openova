# FND-019 — The release writer moves the pin of a chart that several kit slots install

## In plain words

**The problem today.** Some charts are installed by several bootstrap-kit slots: the database chart bp-postgres is pinned by three. When such a chart is released, the release writer moves all three pins in the working tree, but its commit step hands the three file names to git as one name. The commit step fails, so the published chart is never pinned and the release stops half done.

**What changes.** The commit step stages each pinned slot file on its own, on the first attempt and on every retry. The release-writer guard gains two cases that run the real release steps for bp-postgres and fail when a pin is left behind.

**Done means:**

- A release of bp-postgres moves the pins of slots 16a, 16c and 16d to the new version.
- The commit that the release writer pushes holds all three slot files with the chart, its Blueprint manifest and the catalogue files.
- When another commit lands first and the push retries, the retry commit again holds all three slot files.
- The release-writer guard fails on the release workflow as it was before this task, and passes after it.

The rest of this ticket is the exact instruction for the model that does the work.

## 2. End goal
When a chart that several bootstrap-kit slots install is released, the job `build` of `.github/workflows/blueprint-release.yaml` moves the pin of every one of those slots and pushes all of them in the one commit that also carries the chart version, the Blueprint manifest and the catalogue files. This holds on the first push and on a retry after another commit landed first. Today the database chart `bp-postgres` is that case: slots 16a, 16c and 16d pin it. The guard `scripts/check-release-lockstep-writer.py` runs the workflow's own release steps for `bp-postgres` in two new cases, `multi-slot` and `multi-slot-retry`, and a person sees both pass in the log of the check `run the release writer and assert all five sites converge`.

## 3. The model (the law)
1. The step `bump_pin` of the job `build` writes its output `pin_file` as the paths of every slot file it moved, separated by single spaces. This stays as it is. Slot file names hold no space.
2. The commit step reads that output as `PIN_FILE`. Wherever it stages or rewrites a pin, it takes each path of `PIN_FILE` on its own: `for pf in ${PIN_FILE}; do`. It never passes the whole value as one path.
3. On the first attempt, each path is staged with `git add "$pf"`.
4. On a retry after `git reset --hard origin/main`, each path is rewritten with `rewrite_pin "$pf"` and, when that rewrote it, staged with `git add "$pf"`; `did_pin=1` is set when at least one was rewritten. A slot that already holds the version, or a newer one, is left alone, as `rewrite_pin` decides today.
5. Nothing else of the release writer changes: the steps `bump_chart`, `chart`, `bump_pin`, `bump_blueprint`, `sync_seed`, the commit message, the push and the summary stay as they are.
6. The guard gets two cases with the key `multi_slot=True`. Its in-scope precheck refuses such a case when fewer than two kit slots pin the case chart, so the case can never prove the single-slot path by accident. Both cases release a merged change to `platform/postgres` and reuse the existing assertions of a merged-change case: every site at the next version, every slot file in the last commit. `multi-slot-retry` also lands a rival commit first, so the push retries.

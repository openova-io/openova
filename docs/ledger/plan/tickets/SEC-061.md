# SEC-061 — A sign-in succeeds while the node that runs a region's Keycloak is drained

## In plain words

**The problem today.** Each region runs one Keycloak. On a fresh two-region install of 20 November a coordinated node restart moved the Keycloak of the first region, and for about a minute nothing in that region reached a Keycloak: the owner's PIN sign-in failed with a gateway error, and so did every sign-in the region's gateway received. The acceptance check of coordinated restarts never restarts the node that runs Keycloak, so it cannot see this.

**What changes.** While a region's own Keycloak is away, its gateway and the platform engine use the other region's Keycloak, which shares its sessions and codes. The restart check also restarts the node that runs Keycloak in each region, signs the owner in while that Keycloak is away, and afterwards requires the two Keycloaks to form one cluster again and to accept each other's codes.

**Done means:**

- While a region's Keycloak is away, the region's Keycloak service sends its callers to the other region's Keycloak, and back to its own as soon as that one is ready.
- The platform engine of the first region may reach the Keycloak of the other region, so the PIN sign-in no longer depends on the Keycloak of its own region.
- The restart check restarts the node that runs Keycloak in each region and fails when a sign-in of the owner, made while that Keycloak is away, is answered other than 200.
- After the restarts the check fails when the two Keycloaks do not form one cluster naming the current Keycloak of each region within 10 minutes, and when a code that one region's Keycloak issued is refused by the other's.
- The tests of the check run without a cluster and have a failing case for each new rule.

The rest of this ticket is the exact instruction for the model that does the work.

## 2. End goal
On a two-region Sovereign, kured drains the worker that runs `keycloak/keycloak-0` of a region for a coordinated reboot. While that Pod is away, Service `keycloak/keycloak`, which the gateway's route for `auth.<fqdn>` and every in-cluster caller use, has the other region's Keycloak as its backend, because it is a Cilium ClusterMesh global, shared Service with local affinity; the two Keycloaks are one Infinispan cluster, so either answers every step of a sign-in. catalyst-api, whose PIN sign-in calls that Service (`EnsureUser`), may reach the other region's Keycloak Pod, because the policy `catalyst-system/baseline-default-deny` admits the Keycloak Pods of every cluster on their HTTP port. Gate check INF-G01 proves it in its node-reboot run: in each region it also restarts the worker that runs Keycloak, signs the owner in through the public `auth.<fqdn>` at every reading while that Pod is away, and fails on any answer other than 200; after the last region it requires each region's Keycloak to report one cluster that names the current Keycloak of every region within 10 minutes, and a sign-in whose code one region's Keycloak issues and the other's redeems, in both directions. The tests of the check need no cluster and run on every pull request.

## 3. The model (the law)
1. **The files are fixed.** The change is the block `SEC-061.patch` at the end of field 20, applied by work step 4. It changes four files and creates two chart tests; the seven files have the checksums of work step 6 afterwards.
2. **The mechanism is the Service.** The plan named two candidates: a second Keycloak replica per region, or the call answered by the other region. This ticket takes the second, built at the Service and not in `products/catalyst/bootstrap/api/internal/handler/auth.go`: the Service serves the gateway, catalyst-api and every other in-cluster caller at once, where a change of the engine's code would serve the engine alone. It follows the repository's own pattern: the console's Services are global and shared (`products/catalyst/chart/templates/ui-service.yaml` lines 12 to 14), and the rule of NET-133 gives a global Service whose backends run in more than one region `service.cilium.io/affinity: "local"` (network guard G6). bp-keycloak sets `keycloak.service.annotations` to `service.cilium.io/global: "true"`, `service.cilium.io/shared: "true"`, `service.cilium.io/affinity: "local"`. The subchart puts them on Service `keycloak` (port 80, the backend of the chart's HTTPRoute) and not on `keycloak-headless`. Without a mesh the annotations do nothing. Locked by the new chart test `platform/keycloak/chart/tests/service-global-local-affinity.sh`.
3. **catalyst-system may reach the other region's Keycloak.** Rule 4 of `baseline-default-deny` (`products/catalyst/chart/templates/network-policies/baseline-catalyst-system.yaml`) names the keycloak namespace without the cluster key, so Cilium matches it in the local cluster only (rule 3b of the same policy records that trap for the Continuum observers). A new rule 3c admits the Pods `k8s:io.kubernetes.pod.namespace: keycloak`, `k8s:app.kubernetes.io/name: keycloak` of every cluster (`io.cilium.k8s.policy.cluster` with `Exists`) on TCP 8080, the Keycloak container's HTTP port, the same idiom as rule 3b and as `keycloak-backchannel-ingress.yaml`. It is a rule of the existing policy, not a new policy object (network guard G2 counts policy objects per file). Locked by the new chart test `products/catalyst/chart/tests/baseline-cnp-keycloak-every-region.sh`.
4. **The node choice.** In step 3 of a region, when a worker other than the chosen one runs the Pod `keycloak/keycloak-0` in phase Running, it is chosen as well; when the chosen worker runs it, one restart covers both; a Keycloak Pod on a control-plane node is not drained (kured never restarts one) and nothing is added. Every chosen worker gets a sentinel Pod; kured restarts them one after the other (its concurrency is one) and kured, not the check, picks the order of the two restarts. The time limit counts one kured round (period + lock release delay) per chosen worker, plus 15 minutes. Every rule of step 7 that named the worker names each chosen worker.
5. **The sign-in during the drain.** From the first reading in which the Keycloak Pod of a chosen worker is no longer a workload Pod on that worker (gone or being deleted) until the first reading in which a new Pod `keycloak-0` is Ready, the check signs the owner in at every reading the way the console's SPA does: an authorization request of the public client `catalyst-ui` with PKCE (S256) and `kc_idp_hint=catalyst-pin` to `https://auth.<fqdn>/realms/sovereign`, every redirect followed by the check itself (each cookie sent only to the host that set it, the console session only to `api.<fqdn>`), the code redeemed at the token endpoint, and the Keycloak session ended again with its refresh token. A sign-in answered other than 200 fails the step at once, naming the code and the host and path that answered; a drain in which no sign-in was made (the new Pod was Ready by the next reading) fails too. Each sign-in is kept in the evidence `keycloak_sign_ins`.
6. **What the run must hold.** A new step after journey J1: the run holds the owner's console session and step D0.1 recorded `sovereignFQDN`; otherwise the step fails and no node is touched.
7. **One cluster after the reboot.** After the last region, when every region passed, the check reads `kubectl logs --timestamps` of container `keycloak` of `keycloak/keycloak-0` in every region every 5 seconds until each region's last cluster view (an `ISPN000094` line, or an `ISPN000093` line for a view that the merge of two partitions made) lists exactly the current Keycloak of every region (the local address of each Pod's last `ISPN000079` line). It fails 10 minutes (`rebootKCJoin`) after the last Keycloak Pod a reboot moved was first read Ready (after the step's start when none was moved), naming each region's view: a view of one member, a view that names a Pod no longer running; and it fails when the views list every member but their lines were written after that bound. A healthy join measured 33 seconds on 20 November; a failed one gave up after about 3 minutes.
8. **A code across the regions.** With two regions or more, the check then forwards a local port to Service `keycloak/keycloak` (port 80) of every region and signs the owner in once for every ordered pair: the authorization and broker steps sent to one region's Keycloak, the code redeemed and the session ended at the other's. An answer other than 200 fails, naming the pair, the code and the error (`invalid_grant` when the regions do not share their codes).
9. **What stays as it is.** Every rule of the check before this ticket stays with its reasons: journey J1 first; one region after the other; the settings from kured's arguments; the install hold; the window rule of the upgrade Plans; the span the check writes for its run and writes back (INF-054); kured kept off control-plane nodes; the node choice by the registry front; no image wait before the reboot; the 180-second bound of every moved controller (INF-057); every fail-at-once rule; the recovery at the time limit. The check writes only with `kubectl create`, `wait` and `delete` and through the variables document, as before; it adds reads (`kubectl logs`, a port forward) and sign-ins, each of which ends the Keycloak session it opened.
10. **The manifest entry stays.** `docs/ledger/gates.yaml` is not changed: a change of `asserts` is the architect's plan data. Field 9 gives the text.
11. **Not changed:** `products/catalyst/bootstrap/api/**`, `clusters/_template/bootstrap-kit/09-keycloak.yaml`, every `Chart.yaml` and its version line (CI writes chart versions), `products/catalyst/chart/values.yaml`. Nothing is deleted.

# FND-017 — The workflows that push to main themselves push under the release-writer identity

## In plain words

**The problem today.** Jobs that write to the main branch by themselves, such as the release writer and the deploy jobs, push with the workflow's own token. That token cannot be allowed past a protected main branch, so main cannot be protected without stopping every release. Nothing checks that a job which pushes to main does it the right way.

**What changes.** These jobs push with one repository deploy key instead, and mark each such commit so that it starts no workflow. A new check lists every job that pushes to main and fails when one pushes without the key. The twenty jobs that push through the shared deploy-bump action stay on a list that may only shrink.

**Done means:**

- Every job that pushes to main by itself sets up the deploy key in a step before its push, except the twenty jobs that push through the shared deploy-bump action.
- Every commit that these jobs push carries the marker that tells GitHub to start no workflow for it.
- The repository hygiene check fails a pull request that adds a job pushing to main without the key, or adds a job to the list of exceptions.
- The key is read only from the repository secret and is never printed.
- The release workflow is still started by its explicit dispatch steps, as before.

The rest of this ticket is the exact instruction for the model that does the work.

## 2. End goal
After this ticket, every workflow job that commits and pushes to `main` by itself pushes with one repository deploy key, the release-writer key, whose private half is the secret `RELEASE_WRITER_KEY`. The jobs are: the jobs `build` and `umbrella-follow` of `blueprint-release.yaml`, the chart-bump step of the job `deploy` of `catalyst-build.yaml`, the job `deploy` of `services-build.yaml`, the job `live` of `acceptance-sovereign.yaml` and the job `flip` of `sso-uat-flip.yaml`. Each such job runs the new composite action `.github/actions/use-release-writer` before its first push. The action runs `scripts/ci/use-release-writer.sh`, which points only the push address of `origin` at GitHub over ssh with that key. Every commit these jobs push ends its first line with `[skip ci]`, so that a push made with the key starts no workflow, exactly as a push with the workflow token starts none today. A new guard, `scripts/check-bot-writers.py`, runs in the workflow `check-repo-hygiene` on every pull request. It lists every job that pushes to main, and it fails when one pushes without the key, when a commit of a keyed job lacks `[skip ci]`, or when the list `docs/ledger/bot-writers.txt` gains a line. That list names the twenty jobs that still push through `.github/actions/deploy-bump` with the workflow token; FND-024 moves them and empties it. A person sees the result in the job log of `check-repo-hygiene` (the step "Every job that pushes to main pushes with the release-writer key" prints 25 jobs) and in the commits on main after the merge, which carry `[skip ci]`.

## 3. The model (the law)
1. The release-writer identity is one write deploy key of this repository. Its private half is the secret `RELEASE_WRITER_KEY`. No machine account, no team and no token are used. The secret `RELEASE_WRITER_TOKEN` is not used by any job this ticket changes.
2. A job that pushes to main runs the step `uses: ./.github/actions/use-release-writer` with `key: ${{ secrets.RELEASE_WRITER_KEY }}` before its first push. The action is a step of its own and has no `run:` of its own in the calling workflow, because `scripts/check-release-lockstep-writer.py` runs the `run:` steps of the job `umbrella-follow` and the commit step of the job `build` in a test harness, where no key exists.
3. The script reads the key only from the environment. It writes it under `$RUNNER_TEMP` with mode 600, pins GitHub's ed25519 host key, sets `core.sshCommand`, and changes only the push address of `origin`. Fetches keep the https address and the checkout's token. It fails when the key is empty and prints nothing.
4. Every commit pushed with the key holds `[skip ci]` in its first line. The hand dispatches `gh workflow run blueprint-release.yaml` stay where they are; they still start the release.
5. In the job `deploy` of `catalyst-build.yaml` the key step comes after the step that uses `./.github/actions/deploy-bump`. That action's commit has no `[skip ci]`; pushed with the key it would start `catalyst-build` again on its own commit.
6. The list `docs/ledger/bot-writers.txt` only shrinks. It lives under `docs/` because `scripts/check-sandbox-word.py` counts the files outside `docs/` that hold the word "sandbox", and one listed workflow is `build-bp-newapi-sandbox-bridge.yaml`.
7. Nothing of this ticket applies a ruleset or sets the repository variable `RELEASE_WRITER_LOGIN`. Nothing is deleted.

+joined to the next. A key step has "uses: ./.github/actions/use-release-writer". A push step's script
+holds a git push that names main in a refspec or names no refspec, or calls push-chart-version-bump.sh;
+or the step uses a local action that pushes. An action pushes without the key when one of its push
+steps has no key step before it.

+           pushes without the key is exempt only in a job named in the list.

+           and its commit does not hold [skip ci].

+           holds [skip ci]: a push with the key starts the push workflows, and [skip ci] stops that.
+  list     docs/ledger/bot-writers.txt names jobs, "<workflow path> <job id>" per line, "#" starts a
+           comment line. A line for a job without an exempt step fails.

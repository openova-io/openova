# SOV-220 — The console's step list comes from the status response

## In plain words

**The problem today.** The console draws the cutover progress card from a list of eleven steps that is written into its own code. A step that the server runs and the list does not name is dropped and never shown, so a shorter hand-over chain could not be shown at all. The card also counts its progress against that fixed list, not against what the server reports.

**What changes.** The card draws one row for each step that the server's status answer lists, in the order the steps run, and counts its progress against the number of steps the server reports. Known steps keep their titles, the three steps of the shorter hand-over chain get titles, and a step the console does not know is shown under its own name.

**Done means:**

- A status answer with six steps shows six rows, in the order the steps run.
- A status answer with today's eleven steps shows the same eleven rows, in the same order, as before.
- A step name the console does not know is shown, with its name as the title.
- While a cutover runs, the percentage counts against the number of steps the server reports, not against the rows already shown.
- The console's unit tests and its type check pass.

The rest of this ticket is the exact instruction for the model that does the work.

## 2. End goal
The sovereign-admin console shows the progress of the sovereignty cutover in one card, `CutoverProgressCard`. After this ticket the rows of that card are the steps that the response of `GET /api/v1/sovereign/cutover/status` lists, and nothing else: six steps give six rows, eleven steps give eleven rows. The rows appear in the order the steps run, although the API lists step names alphabetically. A step name the console has no title for is shown under its own name instead of being dropped. The percentage and the "Step N of M" line count against the larger of the number of rows and the response's `totalSteps`. The three steps of the shorter hand-over chain (`ownership-pivot`, `upstream-flip`, `parent-release`) have titles. A person sees the result in the unit tests of field 18 and, on a running Sovereign, in the card itself.

## 3. The model (the law)
1. A step name is a string that matches `^[a-z0-9-]{1,40}$`: lower-case letters, digits and dashes, 1 to 40 characters. `isCutoverStepID` in `products/catalyst/bootstrap/ui/src/shared/types/cutover.ts` returns `true` exactly for such strings. Before this ticket it returned `true` only for the eleven names of the list `CUTOVER_STEPS`.
2. The type `CutoverStepID` is a branded string: the union of the known names (the new type `KnownCutoverStepID`) and `string & { readonly __brand: 'CutoverStepID' }`. A known name can be written as a literal; any other string becomes a `CutoverStepID` only through `isCutoverStepID`.
3. The known names are the eleven names of `CUTOVER_STEPS` and the three names `ownership-pivot`, `upstream-flip` and `parent-release`. Each known name has a title (`label`) and a description. The function `cutoverStepDef(name)` returns them. For an unknown name it returns the name itself as the title and an empty description.
4. The rows of the card are the function `cutoverStepRows(status.steps)`: the records of the parsed status response, each exactly once, and no other row. The card no longer adds a pending row for a step that the response does not list.
5. Order of the rows: the known names in this order, which is the order the steps run: `gitea-mirror`, `harbor-projects`, `harbor-prewarm`, `ownership-pivot`, `upstream-flip`, `registry-pivot`, `parent-release`, `flux-gitrepository-patch`, `helmrepository-patches`, `catalyst-api-env-patch`, `gitea-token-mint`, `vcluster-registry-pivot`, `crossplane-provider-pivot`, `egress-block-test`. Unknown names follow them, in the order of the response. So today's eleven names keep today's order, and the six names of the shorter chain come out as `harbor-prewarm`, `ownership-pivot`, `upstream-flip`, `registry-pivot`, `parent-release`, `egress-block-test`.
6. The parsed status carries `totalSteps`, read from the response field of the same name. The card's total is the larger of the number of rows and `totalSteps`. The percentage is the number of `done` records over that total, rounded, and `0` when the total is `0`. The header line says `Step <done> of <total>` and `All <total> steps completed.`.
7. `CUTOVER_STEPS` keeps its eleven entries, their order and their text. It still seeds the first paint (`buildInitialCutoverStatus`) and the start dialog of `SovereigntyCard.tsx`. Neither of those changes in this ticket.
8. No wire field name changes. The parsing of the overall state (`tethered`, `sovereign`) and its tests do not change. No file of the API changes.
9. Two private things are deleted, nothing else: the card's helper `recordFor` and the set `CUTOVER_STEP_IDS` in `cutover.ts`.
10. The four files of field 14 are changed by the embedded patch `SOV-220.patch` and by nothing else.

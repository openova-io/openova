# BSS-141 — The cost-source credential is never a Kubernetes Secret

## In plain words

**The problem today.** An Organization can name a Kubernetes Secret that holds the read-only cloud credential of a cost source, and the billing engine reads that Secret and copies the credential into its database. The credential of an application then rests in etcd as a Secret object, which the platform does not allow. The engine already has the right path: the credential is entered in its console or API and stored encrypted with its own key.

**What changes.** The engine never reads a Secret. A cost source declared on an Organization is registered and stays pending until its credential is entered in the engine. The Organization can no longer name a credential Secret.

**Done means:**

- The billing engine's Organization sync contains no call that reads a Kubernetes Secret, and the ratchet of the billing area allows none.
- A cost source declared on an Organization is registered pending, with no credential, and a resync neither duplicates it nor stores a credential.
- The Organization definition, its valid sample, its Go types and the engine's README no longer mention credentialRef.
- The schema bundle of the sovereign-admin API matches the changed Organization definition.
- The engine's chart carries a new appVersion, so the changed binary is built under a new image tag.

The rest of this ticket is the exact instruction for the model that does the work.

## 2. End goal
The billing engine (`products/chargeback`, Blueprint `bp-chargeback`) watches Organizations and turns each entry of `spec.costSources[]` into a cost source of its own. Today an entry may carry `credentialRef`, the name and key of a Kubernetes Secret in the Organization's namespace; the engine then reads that Secret, seals the access key pair with its master key, stores it and verifies the source. After this ticket the engine reads no Secret at all. A declared source is registered and stays `pending`, with no credential, until a person enters the credential in the engine's console or through `POST /api/v1/sources/{id}/credential`, which already seals it with the engine's own key and verifies it. The Organization definition has no `credentialRef` any more, so an Organization cannot ask for a credential Secret. The Organization sync no longer holds a Kubernetes clientset, a keyring or a verifier, because it has nothing to read, seal or verify.

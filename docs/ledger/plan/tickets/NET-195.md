# NET-195 — Organization listener: client-certificate validation or TLS passthrough, by the outcome of PRD-050 (conditional, dropped until PRD-050 closes)

## In plain words

**The problem today.** A back end that must check a client certificate itself, such as an open-banking interface, cannot do so behind the console gateway of a Sovereign: the gateway ends every TLS session for an Organization's host names and asks for no client certificate. The lab test PRD-050 found that the gateway's own client-certificate check cannot be used on the pinned versions, and that a passthrough listener for one exact host works beside the Organization's HTTPS listener on the same port.

**What changes.** An Organization can name up to four hosts under its own domain whose TLS sessions the gateway passes unopened to the back end. The organization controller writes one passthrough listener per named host and removes it when the name is dropped or the Organization is deleted.

**Done means:**

- An Organization that lists a host label has one TLS passthrough listener for exactly that host on the console Gateway, on the port of its HTTPS listener.
- That listener admits only TLS routes, and only from the Organization's own namespace and the namespace of its console route.
- The console host and a label that is not lower-case letters and digits get no listener, and the Organization resource refuses more than four labels.
- A label removed from the list loses its listener on the next reconcile, deleting the Organization removes all of them, and the listeners of other Organizations stay as they are.
- A second reconcile with nothing changed writes nothing.
- Organizations whose listeners only the platform API writes get no passthrough listener yet: that is the second piece of this plan entry.

The rest of this ticket is the exact instruction for the model that does the work.

## 2. End goal
PRD-050 closed with outcome B (`docs/ledger/plan/spikes/PRD-050.md` line 1): the Organization listener cannot verify a client certificate on the pinned Cilium and Gateway API, so a back end that needs mutual TLS gets a TLS passthrough listener for its exact host. After this ticket an Organization names such hosts in a new optional field, `spec.tenantPublic.passthroughHosts` (the leftmost labels of hosts `<label>.<subdomain>.<parentDomain>`; empty on every Organization that needs none). The organization controller, in the same read-modify-write of the console Gateway `kube-system/cilium-gateway-console` that writes the Organization's listener pair, writes one listener per label in the shape PRD-050 ran (answer 8): name `console-tls-<slug>-<label>`, `hostname` the exact host, `protocol: TLS`, `tls.mode: Passthrough`, the port of the Organization's HTTPS listener, and `allowedRoutes` of the pair (`orglistener.AllowedRoutes`) with `kinds: [{kind: TLSRoute}]`. It does so in every region it writes the pair into, removes a listener whose label left the list, removes all of them with the pair when the Organization is torn down, and leaves every other listener as it is. This is the first piece of the plan entry: the platform API's writer of the Organization listeners (internal Organizations) and its reaper of orphaned listeners are the second piece (field 11).

## 3. The model (the law)
1. The field is `spec.tenantPublic.passthroughHosts`: a list of strings, each matching `^[a-z0-9]{1,63}$`, at most 4 items, a set (`x-kubernetes-list-type: set`). It is optional and empty by default: an Organization without it is unchanged. It is a field of the existing Organization, not a new kind.
2. A label is letters and digits only, so the name `console-tls-<slug>-<label>` has one owner also when slugs hold hyphens: `orglistener.IsPassthroughListenerOf(name, slug)` cuts the prefix `console-tls-<slug>-` and accepts only a label of that form. The label `console` never gets a listener (the Sovereign's console host in every Organization's zone).
3. `orglistener.PassthroughListeners(slug, zone, labels, port, consoleRouteNamespace)` returns one listener per valid label, once per label, sorted by label, each exactly:
   ```yaml
   - name: console-tls-<slug>-<label>
     hostname: <label>.<zone>
     port: <port of console-https-<slug>>
     protocol: TLS
     tls:
       mode: Passthrough
     allowedRoutes:
       kinds:
         - kind: TLSRoute
       namespaces: <the block of orglistener.AllowedRoutes(slug, consoleRouteNamespace)>
   ```
4. `orglistener.MergePassthrough(listeners, slug, want)` returns the list with the Organization's passthrough listeners made equal to `want`: a missing one is appended, one that differs in a field `want` sets is replaced in place, one `want` does not hold is removed, every other listener is kept in its order. A field the API server defaults and `want` does not set is no difference, so a second pass reports unchanged.
5. The controller calls the merge as pass 3 of `ensureConsoleOrgListener` (one Update with the pair) and with `want` empty in `removeConsoleOrgListener` (one Update with the pair's removal). `orgConsoleTLSNamesForOrg` carries the field into `orgConsoleTLSNames.PassthroughHosts`, so the up-path, the teardown and the post-condition verifier read one value.
6. No HTTPRoute names a passthrough host: answer 9 of PRD-050 shows that a terminating session asking for that host gets HTTP 404, and the back end of the host is reached only through the passthrough listener.

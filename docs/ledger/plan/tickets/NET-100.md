# NET-100 — Network registry output and validator

## In plain words

**The problem today.** The addresses, cluster names and cluster identifiers of a Sovereign are spread over the locals of the provider modules. Nothing publishes them as one record, and nothing checks that the ranges of different regions stay apart. With three or more regions a node range can fall inside the range that holds the pods, and nothing limits the number of regions.

**What changes.** Each provider module publishes one network record of its Sovereign, and a check script tests such a record against named rules. The reference module accepts at most six regions and, with three to six, keeps every node range out of the pod ranges. One- and two-region Sovereigns keep the ranges they have. A Sovereign that already runs with three or more regions keeps its ranges only if its node base is not in the list of moved bases that the ticket prints; the architect compares that list with the running Sovereigns before the merge.

**Done means:**

- Both provider modules have the output network_registry, a JSON record of the Sovereign's network.
- The check script passes a valid record, and it fails a record that breaks one of its eight rules and names that rule.
- The module test of the reference provider compares the record of one, two and three regions with records that the check script passes.
- The reference module refuses more than six regions.
- With three to six regions no node range of the reference module lies in the pod supernet; with one or two regions every node range stays where it was.
- A Sovereign of three or more regions gets new node ranges only when its node base is in the list of moved bases.
- The provider contract lists the new output and describes the record and its rules.

The rest of this ticket is the exact instruction for the model that does the work.

## 2. End goal
Both provider modules under `infra/providers/` publish the output `network_registry`: the JSON text of one object that records every address, cluster name and cluster identifier of the Sovereign. `infra/providers/PROVIDER-INTERFACE.md` section 2.1 describes its fields and its eight rules, and `infra/providers/_contract/contract.json` lists it as the sixth output. `scripts/check-network-registry.py <file>` checks a record and prints one line per broken rule. The module test of the reference provider (`infra/providers/huawei`) compares the output for one, two and three regions with three documents under `scripts/tests/check-network-registry/`, and the check script's self-test passes those three and fails one document per rule. The reference module refuses more than six regions. With three to six regions it keeps every node range out of the pod supernet `10.40.0.0/13`; with one or two regions its ranges do not move. The workflow `infra/huawei — OpenTofu validate + test` runs the module test and the check script's self-test.

## 3. The model (the law)
1. Each module has `output "network_registry"` with `value = jsonencode(local.network_registry)`. Its type is a string.
2. The record is one object with exactly these fields: `podSupernet`, `mtu`, `regionSeparation`, `controlPlaneAccess` (with `adminCIDRs` and `provisionerCIDRs`) and `regions`. Each entry of `regions` has `code`, `cloudRegion`, `az`, `clusterName`, `clusterID`, `nodeCIDR`, `podCIDR`, `serviceCIDR`, `edgeAddress`, `egressAddresses`, and `meshEndpoint` (`ips`, `port`) only when the record has more than one region. The types and ranges are those of section 2.1 of `infra/providers/PROVIDER-INTERFACE.md` as the patch of this ticket writes it.
3. The reference module fills the record from its own values. `podSupernet` is the new local `pod_supernet`: `10.42.0.0/15` for one or two regions, `10.40.0.0/13` for three to six. `mtu` is 1420. `regionSeparation` is `site` when every region has a different cloud region, `zone` when cloud regions repeat but every pair of cloud region and zone is different, and `none` otherwise and for one region; in this module every region has `var.huawei_region` and `var.huawei_az`, so it is `none`. Both access lists are empty: the module has no sovereign-admin or provisioner source list yet. Per region: `code` the region code; `cloudRegion` `var.huawei_region`; `az` `var.huawei_az`; `clusterName` and `clusterID` from `local.cluster_mesh_name_by_region` and `local.cluster_mesh_id_by_region`, unchanged; `nodeCIDR` `local.region_subnet_cidr`; `podCIDR` and `serviceCIDR` from `local.region_cluster_cidr` and `local.region_service_cidr`; `meshEndpoint` the region's control-plane EIP and `var.clustermesh_proxy_port`; `edgeAddress` the address of the gateway ELB EIP `huaweicloud_vpc_eip.elb_primary`; `egressAddresses` the region's NAT EIP, then its control-plane EIP.
4. The second module (`infra/providers/hetzner`) fills the record for the region `primary` and every region of `local.secondary_regions`, in the order of `local.all_region_keys`. `code` is that region key; `cloudRegion` the location; `az` `none`; `clusterName` and `clusterID` the mesh name and identifier the template receives; `nodeCIDR` the region subnet; `edgeAddress` the region's load balancer; `egressAddresses` the public IPv4 of every node of the region. It has no `meshEndpoint`. `regionSeparation` is `site` when every region has a different location, else `none`.
5. The reference module refuses more than six regions: a second `validation` block on `var.regions` in `variables.tf`.
6. Node ranges of the reference module. For one or two regions the base of the node ranges is computed exactly as before. For three to six regions the new local `cidr_base_free_shifts` lists every shift `s` in `0..15` for which no region octet `raw + s + 10*idx` lies in `[40, 47]` (the pod supernet) or in `[96, 95+N]` (the service ranges). The base keeps the shift of the old rule (the new local `cidr_base_old_shift`) when that shift is in the list, and otherwise takes the first shift of the list. So a Sovereign of three or more regions moves only when one of its node ranges lies in the pod supernet or in the service ranges. Pre-flight P6 prints every base that moves.
7. `scripts/check-vpc-cidr-no-pod-overlap.py` parses the new lines of `main.tf`, models both rules, enumerates every hash byte for one to six regions, and fails when a node octet lands in a band, when a free placement of the old rule is moved, or when the supernet band does not hold six pod octets. Its self-test proves each new parse and assertion can fail.
8. `scripts/check-network-registry.py` checks one record against eight rules: `document-shape`, `unique-cluster-id`, `unique-cluster-name`, `unique-ranges`, `supernet-covers-pods`, `supernet-excludes-nodes-and-services`, `mesh-endpoint-when-multi-region` and `no-any-source`. It reads the object, or the JSON string that `tofu output -json network_registry` prints. Exit code 0 is a valid record, 1 a broken rule, 2 a usage error or an unreadable file. Its `--self-test` checks every `valid-*.json` and every `invalid/<rule>.json` under `scripts/tests/check-network-registry/`. It uses the Python standard library only.
9. The reference module test gains four runs at its end: `network_registry_one_region`, `network_registry_two_regions`, `network_registry_three_regions` and `network_registry_seven_regions_refused`. The first three compare the output with `valid-one-region.json`, `valid-two-regions.json` and `valid-three-regions.json`; the second also asserts that the node VPC ranges of the two-region fixture do not move; the third asserts that the base moves from 45 to 48; the fourth expects the region count validation to fail.
10. `infra/providers/_contract/contract.json` lists `{"name": "network_registry", "type": "string"}` as its sixth output. `infra/providers/PROVIDER-INTERFACE.md` moves `network_registry` from the reserved names to the outputs and gains section 2.1.
11. `.github/workflows/infra-huawei-tofu.yaml` also starts on a change of `scripts/check-network-registry.py` or `scripts/tests/check-network-registry/**`, and runs `python3 scripts/check-network-registry.py --self-test` before the module test. Its comment on the node-range guard names `N=1..6`.
12. No `resource`, `data`, `module`, `moved` or `variable` block is added or removed in either module. The only new blocks there are the two outputs.

+"""check-network-registry.py - check a Sovereign's network registry (NET-100).
+
+The network registry is the output `network_registry` of every provider module
+under infra/providers/: a JSON object with the pod supernet, the MTU, the
+region separation, the control-plane access lists, and per region the cluster
+name and identifier, the node, pod and service ranges, the mesh endpoint, the
+edge address and the egress addresses. Its form is described in
+infra/providers/PROVIDER-INTERFACE.md, section 2.

+Usage:
+  check-network-registry.py <file>     check one document
+  check-network-registry.py --self-test
+                                       check every document under
+                                       scripts/tests/check-network-registry/
+
+<file> holds the registry object, or the output of
+`tofu output -json network_registry`, which is the object as a JSON string.

+  document-shape                        the fields, their types and ranges

+  supernet-excludes-nodes-and-services  no nodeCIDR or serviceCIDR intersects

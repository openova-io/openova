# FND-020 — A pull request is not red because main was between two commits of a release

## In plain words

**The problem today.** A release of the platform chart reaches main as two commits minutes apart: first its new version, then, after the chart is published, the bootstrap-kit pin that names it. A component release likewise moves its catalogue entries one commit before the platform chart that carries them is released. A pull request tested on a copy of main taken in between fails two checks for a difference that main itself has, although the change touches no version and no pin; on 13 November five tasks stopped with complete work for this reason.

**What changes.** The pin audit and the umbrella republish gate compare a pull request with the main it was merged onto and fail only on a difference the change adds; a difference main already had is printed as inherited. The release-writer guard judges its pin check the same way and gains a case that builds both in-between states and proves both directions.

**Done means:**

- A pull request that touches no version and no pin passes the pin audit and the umbrella republish gate while main sits between the two commits of a release.
- A pull request that moves a chart version, a bootstrap-kit pin or a catalogue pin by hand still fails them.
- The release-writer guard passes its control case on such a main, and still fails when the release writer leaves a pin behind.
- The output of both checks names each inherited difference, so nothing is hidden.
- A wrong base reference makes the pin audit fail instead of passing silently.

The rest of this ticket is the exact instruction for the model that does the work.

## 2. End goal
A pull request is judged on its own change. The pull-request leg of the job `pin-sync-audit` (workflow `Test — Bootstrap Kit (kind cluster + Flux)`) runs the kit pin audit and the umbrella republish gate against `HEAD^1`, the main that the change was merged onto, and a difference that main already has there is printed as `INHERITED` and does not fail. ## 3. The model (the law)
1. **The decision: judge against the base; the release stays as it is.** A release of the umbrella chart `bp-catalyst-platform` is two commits on main: `scripts/push-chart-version-bump.sh` pushes the new `version:` of `products/catalyst/chart/Chart.yaml` (called from `catalyst-build.yaml`, `services-build.yaml` and the job `umbrella-follow` of `blueprint-release.yaml`), and the dispatched run of `blueprint-release.yaml` pushes the kit pin of slot 13 after it has published the chart. A component release adds a third shape: its one commit moves its catalogue entries in `products/catalyst/chart/templates/catalog-seed/blueprints.yaml`, and the job `umbrella-follow` releases the umbrella only after that commit (it `needs` the job `build`). Merging the umbrella's version and pin into one commit would not remove that third window, because the umbrella must be published after the component. So this ticket does not change any release step. It changes the two checks so that they judge what a change adds.
2. **The pin audit, `scripts/check-bootstrap-kit-pin-sync.sh --changed-only --base <ref>`.** It checks every chart (as the full sweep does), not only the charts whose `Chart.yaml` the change touched. A pair of chart version and kit pin that differ is `INHERITED` when `<ref>` holds the same chart version in that `Chart.yaml` and the same pin in that slot file; it is printed as `  INHERITED <name>: chart=<v> pin=<p> (file: <slot>) — <ref> has the same drift; not added by this change` and does not fail. Any other differing pair is a `DRIFT` and fails, as before. So a change that moves a chart version or a pin by hand fails, and a release writer that leaves a pin behind fails. A `<ref>` that is not a commit exits 2 (it used to pass silently). The full sweep (no `--changed-only`) is unchanged.
3. **The umbrella republish gate, `scripts/check-umbrella-republish-gate.py --ref <ref> --base <base>`.** Without `--base` it is unchanged. With `--base` it also evaluates `<base>`; a failure that `<base>` has too (same entry, same field, same version, same commit that last wrote the line) is printed as `  INHERITED ...` and does not count. A change that moves a catalogue pin by hand rewrites the line, so blame names the change's own commit and the failure is new. Its self-test gains the two cases: an inherited failure exits 0 with `--base` and 1 without it, and an added failure exits 1 with `--base`.
4. **The pull-request leg of `pin-sync-audit`** in `.github/workflows/test-bootstrap-kit.yaml` uses `base="$(git rev-parse HEAD^1)"` instead of `github.event.pull_request.base.sha`. On a pull request the checkout is the merge of main and the branch, so `HEAD^1` is by construction the main the tested merge was made on; the payload's base commit is the one the event recorded, which need not be that commit. `.github/workflows/work-package.yaml` and `.github/workflows/gate-manifest.yaml` already take the base as `HEAD^1`. The republish-gate step runs the gate's self-test (its standard output, which holds the `FAIL` lines of its fixtures, goes to `/dev/null`; its verdict on failure is on standard error), then the gate with `--ref HEAD --base HEAD^1` on a pull request and with `--ref HEAD` on every other event. The push and schedule legs are unchanged.
5. **The release-writer guard.** Its function `assert_repo_gates` (used by the cases `bump`, `retry`, `umbrella` and `noop`) runs the pin audit as `--changed-only --base <the commit of the tested tree>` and prints each inherited line. The control case `noop` says so in its description. A new case `mid-release` builds two states of main in a scratch repository and asserts, by exit code and output:
   - window 1, the umbrella's version moved and its pin not yet: the full audit exits 1 with `DRIFT bp-catalyst-platform`; a change that touches no pin exits 0 with `INHERITED bp-catalyst-platform`; a change that moves `platform/keycloak`'s chart version by hand (the state a writer leaves when it forgets the pin), a change that moves its kit pin by hand, and a change that moves the umbrella's kit pin to another version each exit 1 with `DRIFT`;
   - window 2, `bp-keycloak`'s catalogue pins moved and the umbrella not yet released: the gate exits 1; a change that touches no pin exits 0 with `--base HEAD^1` and prints `INHERITED`; a change that moves the catalogue pin by hand exits 1 with `--base HEAD^1`.
   The workflow `check-release-lockstep-writer.yaml` also starts on a change to the two scripts, since the guard now runs them.
6. **Nothing else changes.** No baseline is added and no guard is weakened: every difference a change adds still fails, and every inherited one is printed. No version line, no pin, no release step, no other workflow. All the content comes from the embedded patch.

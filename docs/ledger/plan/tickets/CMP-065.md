# CMP-065 — Mutate policies to MutatingPolicy: inject-gitea-source-secretref

## In plain words

**The problem today.** The mutate policy that adds the local Gitea credential reference to Flux sources is still written in the engine's legacy policy kind, which the engine line after the current one no longer serves. The chart's function test and its render test know only the two validating kinds, so a policy of the new mutating kind would never be checked for readiness.

**What changes.** The policy is written in the new mutating kind, in the same file and under the same name, and its test suite gives the same results and the same patched objects as before. The function test waits for every mutating policy of the release, and its render test fails when it does not ask for one.

**Done means:**

- The policy chart renders one MutatingPolicy, inject-gitea-source-secretref, and its template holds no legacy policy kind.
- The suite of the policy has six cases and passes on the new kind with the same patched objects the legacy policy produced.
- A copy of the policy in the suite that is not the current render turns the pull request red.
- The chart's function test waits for the MutatingPolicy to report ready, and its render test fails when the function test does not ask for every MutatingPolicy of the render.
- The legacy policy guard counts 25 objects.

The rest of this ticket is the exact instruction for the model that does the work.

## 3. The model (the law)
1. **In place.** The template keeps its path, its `metadata.name` `inject-gitea-source-secretref`, its labels and annotations, its values keys `compliancePolicies.injectGiteaSourceSecretRef.enabled`, `secretRefName` and `giteaHostMarker` and their defaults. Nothing the policy changes on an object changes.
2. **Shape.** `apiVersion: policies.kyverno.io/v1`, `kind: MutatingPolicy`; `spec.evaluation.admission.enabled: true` and `spec.evaluation.background.enabled: false` (the legacy `background: false`, so the reports controller needs no read of the Flux kinds); `spec.matchConstraints.resourceRules` with operations `CREATE` and `UPDATE` on `gitrepositories`, `helmrepositories` and `ocirepositories` of `source.toolkit.fluxcd.io`, every version (the legacy rule matched the three kinds by name); two match conditions, `url-targets-local-gitea` (the URL contains the host marker) and `secretref-absent` (the source has no `spec.secretRef`); one mutation, a JSON patch that adds `/spec/secretRef` with the configured name. A JSON patch needs no schema of the Flux kinds.
3. **Same results.** The suite was green on the legacy render first (kyverno CLI v1.19.2). Then only `policy.yaml` (the new render) and one key of each result (`rule: inject-secretref-on-local-gitea-source` became `isMutatingPolicy: true`) changed; the resources, the five expected results and the three patched resources are the same files and give the same output. A sixth case, a local Gitea source whose `secretRef` names no Secret, is left as it is on both kinds (the legacy add-when-missing anchor `+(secretRef)` left it; the new condition `secretref-absent` is false for it).
4. **Current copy.** `tests/suites-current.sh` lists the suite in `SUITES`, accepts a MutatingPolicy in checks C2 and C4, and prints `ALL PASS: 20 suites current`; its self-test gains two cases (12).
5. **Function test.** `templates/tests/function-test.yaml` collects the MutatingPolicy names of the rendered policy templates into `MUTATING_POLICIES`, grants `get` on `mutatingpolicies` of `policies.kyverno.io` beside the two existing kinds, and waits for `status.conditionStatus.ready` of each MutatingPolicy as it does for each ValidatingPolicy. `tests/function-test-render.sh` compares the three kinds of the render with the three lists of the test and fails when the default render holds no MutatingPolicy or the test role does not name `mutatingpolicies`.
6. **Baseline.** `scripts/baselines/kyverno-legacy.json` loses the entry of the template (26 to 25 objects).
7. **One difference, by convention.** The legacy rule named no operation; the new policy matches `CREATE` and `UPDATE` only, as the policies rewritten by CMP-062 to CMP-064 do.

# SEC-232 — Roll-out: platform/valkey

## In plain words

**The problem today.** The Valkey chart still carries a branch that makes up a random password for each keyspace credential when password auth is turned on. That branch is never reached on a Sovereign, because auth is off, and if it were reached the password would not be the server's own: nothing gives the server that value. It is the chart's one random site, so the secret guards still list the chart.

**What changes.** The branch is gone: a keyspace credential carries only the address of the keyspace, and turning auth on while keyspaces are declared stops the render with a message that says why. What a Sovereign runs today renders exactly as before.

**Done means:**

- The secret guard that counts random values made up by chart templates finds none under the Valkey chart, and its allow-list has no line for it.
- The keyspace credential Secret of a render carries exactly four keys: host, port, index and uri, with no password in the uri.
- A render with password auth on and a keyspace declared fails, and the message names the keyspace.
- At the chart's default values and at the values of kit slot 17 the render is byte for byte what it was before, so an upgrade changes no object, restarts no Pod and keeps every Secret value.
- All five chart tests of the Valkey chart pass.

The rest of this ticket is the exact instruction for the model that does the work.

## 2. End goal
After this ticket the chart `platform/valkey/chart` has no random site. Its one site was the auth branch of `templates/context-secrets.yaml` (a `lookup` of the live Secret and `randAlphaNum 32`, lines 41 to 49 of `main`, and the `password` key and the password-carrying `uri`, lines 76 to 78). The spike `docs/ledger/plan/spikes/SEC-227.md` (row V1 and plan edit E5) found that this Secret, `newapi-keyspace-credential`, holds no secret value: the server runs without a password and kit slot 17 does not turn it on, so the branch is never reached. The branch is removed. A keyspace declared while `valkey.auth.enabled` is true now fails the render with the message `bp-valkey: keyspace "<name>" is declared with valkey.auth.enabled true; ...`, because a password minted by this chart was never the server's own. The chart test `tests/contexts-render.sh` case 3 asserts the new behaviour, and the line of the chart leaves the allow-list of guard G2. The Secret itself stays (its name is the Context credential the reflector pushes into `newapi` and the console shows), so the count of guard G4 for the chart stays 1.

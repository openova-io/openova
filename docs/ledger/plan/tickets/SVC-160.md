# SVC-160 — One generator, part 2: the seed becomes generated

## In plain words

**The problem today.** Every installed Sovereign holds a catalogue seed, the list of Blueprint objects its catalogue starts from, and that file of more than 5,000 lines is written by hand. The Blueprint files now say what the seed says, and a check proves it, but nothing writes the seed from them: a change to a Blueprint must still be copied into the seed, and the release writer still edits the seed with a script of its own.

**What changes.** The catalogue generator writes the seed from the Blueprint files, as it already writes the catalogue the console and the API embed, and the check that proves every generated file current covers the seed too. The hand-written seed, its equality check and the release writer's own seed edits are gone; four seed objects that no Blueprint file declares are gone with them.

**Done means:**

- The seed's first line says that the catalogue generator writes it, and the generator registry lists it.
- A hand edit of the seed turns the check of the generated files red.
- For every Blueprint the seed holds, the generated object says what the hand-written object said in every field the platform reads, and the set of listed Blueprints is unchanged.
- The seed no longer holds the four objects that no Blueprint file declares, and it holds no other new or missing object.
- A release of a chart writes the seed by running the generator, and the guard that replays the release writer proves it.
- The gate check that compares a Sovereign's seeded objects with the candidate's seed exists and is expected to fail until the class and lifecycle contract is delivered.
- No guard baseline rises, except the count of seed exclusions, which starts at the number of the new exclusion file's entries.

The rest of this ticket is the exact instruction for the model that does the work.

## 2. End goal
`products/catalyst/chart/templates/catalog-seed/blueprints.yaml` (the seed) is the set of Blueprint objects every Sovereign holds from its first install. Until now it is written by hand, a check (`scripts/check-seed-equals-blueprints.py`, SVC-159 and SVC-163) proves that the Blueprint files say what it says, and the release writer edits its versions with `scripts/sync-catalog-seed-pin.py`. After this ticket `scripts/generate-catalog.py` writes the seed as its third output, with the projection that check proved; the job "regenerate and prove no diff" of `.github/workflows/check-catalog-generated-drift.yaml` proves it current and `scripts/generator_registry.py` lists it; the check is deleted; the release writer runs the generator in place of its two sync calls. Nothing an installed Sovereign or a user reads from the seed changes, except that the four objects no Blueprint file declares leave it.

## 3. The model (the law)
1. The seed holds one object for every Blueprint file the generator reads (`platform/<name>/blueprint.yaml`, `products/<name>/blueprint.yaml`) that no `seed-exclusions.yaml` names. A shared file `platform/_catalog/seed-exclusions.yaml` names the others, each with its reason; a provider's Blueprint (a folder its `infra/providers/<provider>/pack.yaml` lists in `spec.charts`) is named in that provider's own `infra/providers/<provider>/seed-exclusions.yaml`, never in the shared file. Its 25 entries are exactly the Blueprint files that have no seed object today.
2. An object's `spec` is the file's `spec` without the keys no reader reads from the object (`upgrades`, `owner`, `observability`, `outputs`, `dependsOn`, the keys the deleted check left out), with `spec.source` derived (kind HelmRepository, type oci, url `oci://ghcr.io/openova-io`, chart the Blueprint's name, version its version) and `card.category` taken from a category data file when the file has none. A Blueprint file that carries `spec.source` is an input error.
3. The version is the file's `spec.version`, except: a Blueprint that `platform/_catalog/chart-locations.yaml` maps to a chart folder takes that chart's version, written as the template `{{ .Chart.Version | quote }}` when the folder is `products/catalyst/chart`, the chart that holds the seed (one entry, `bp-catalyst-platform`; the generator names no Blueprint); a Blueprint without a chart folder takes the version `scripts/expected-unpublished-catalog-seed-pins.yaml` registers for it. A seeded Blueprint with neither a chart folder, a chart location nor a registered pin is an input error.
4. The labels are `catalyst.openova.io/managed-by: catalog-seed`, `catalyst.openova.io/origin: openova-public` and `catalyst.openova.io/curation: openova-public`, then the file's labels, then the two of the Helm release. Every literal `{{` and `}}` of a value is escaped for Helm. A quoted scalar is double-quoted and a list of scalars is written `[a, b]`, because the line readers of the seed expect both.
5. The categories of the data files reach outputs 1 and 2 too. A data file entry that names no Blueprint file, names one twice or outside its owner's file, or gives a category to a Blueprint that is not seeded or whose file carries one, is an input error. Every new rule has a self-test case that fails.
6. The four seed objects that no Blueprint file declares (`bp-continuum`, `bp-n8n`, `bp-prometheus`, `bp-redis`) are not generated. No code reads them by name (field 4 item 5); the three of them that the register of unpublished pins named leave the register, and `bp-continuum` keeps running from its kit slot.
7. The release writer runs `python3 scripts/generate-catalog.py` after it has written versions, in place of its two calls of `scripts/sync-catalog-seed-pin.py "${CHART_NAME}"`; its version comparisons (`--order`) stay. The lockstep-writer guard replays the generator in its three places, and the three continuum cases expect no seed entry.
8. Rule R4 of `scripts/check-release-owned-lines.py` is retired: the seed is a generated file, judged at its Blueprint files by R3 and by the no-diff check, and a push judges it with the other generated files (P2).
9. The umbrella republish gate (`scripts/check-umbrella-republish-gate.py`) blames each seed pin line. Generating the seed rewrites every line, so with `--base` (a pull request) a failure whose entry and field hold the same version on the base is UNMOVED and does not count: the change moved no pin. Without `--base` (main) the rewritten lines still fail until the umbrella is released after the change, which the release of the changed umbrella chart does.
10. Check SVC-G01 is implemented in `tests/acceptance/sovereign/internal/suite/check_svc_catalogue.go` and set to `expected-fail`: the seeded Blueprint objects of the primary region are exactly those the candidate's seed names, and each says its class and lifecycle, which SVC-170 delivers.
11. Baselines only fall, with one entry set: the seed's line leaves `scripts/provider-leak-baseline.tsv` (judged at its sources), `charts` of `scripts/upstream-literals-baseline.txt` falls by the four source lines that leave, `G3.hand-seed-blueprints` falls to 0; `G7.seed-exclusions` counted 0 because its file did not exist, and it starts at the 23 entries of the shared file.

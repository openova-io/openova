# CMP-079 — Validate policies to ValidatingPolicy: forbid-nodeport-service and the live check that reads it

## In plain words

**The problem today.** The ban on NodePort Services is still written in the engine's legacy policy kind, which the engine line after the current one no longer serves. Until the hand-over the bootstrap window holds it at Audit, so a NodePort created then is recorded and admitted. The live check of the ban, and the account that runs it, read only the legacy kind.

**What changes.** The ban is written in the new validating kind under the same name and denies whatever the values and the window say; its suite gains four Services and gives the same verdicts on both kinds. The live check and the conformance account read the new kind, and accept the legacy object at Enforce only in a region the new chart has not reached yet.

**Done means:**

- The policy chart renders forbid-nodeport-service as a ValidatingPolicy that denies with the chart defaults, after the hand-over, and with its action value set to Audit.
- The suite of the policy judges ten Services: seven are refused, two are admitted and the labelled cert-manager solver is skipped.
- The live check passes a region whose ban denies, and a region that still runs the legacy policy at Enforce; it fails a region whose ban is at Audit or absent, and one whose cluster does not serve the new kind.
- The conformance account can read the ban of either kind and its two kind definitions, and nothing more about policies.
- The legacy policy guard counts one object fewer: 21 on the base of this ticket.

The rest of this ticket is the exact instruction for the model that does the work.

## 3. The model (the law)
1. **In place.** The template keeps its path, its `metadata.name` `forbid-nodeport-service`, its labels and annotations, and its values keys `compliancePolicies.forbidNodePortService.enabled`, `action` and `excludeNamespaces` with their defaults. No values key is removed.
2. **A fixed Deny.** `spec.validationActions: [Deny]`, written in the template as `forbid-local-path-storage` writes it. The template reads neither the helper `bp-kyverno-policies.action` nor `bp-kyverno-policies.actions`, so the ban denies during the bootstrap window too, and the value `action` is no longer read (it stays: the local pack's policy values set it to Enforce, and `products/catalyst/bootstrap/api/internal/compliance/policyfiles_test.go` lines 449 and 450 check that). The plan entry names the fixed Deny. A NodePort is forbidden on this platform without exception, so no case of the values weakens the ban.
3. **Shape.** `apiVersion: policies.kyverno.io/v1`, `kind: ValidatingPolicy`; `spec.evaluation.background.enabled: true` (the legacy `background: true`); one resource rule: `services` of the core group, version `v1`, operations `CREATE` and `UPDATE`, as the policies rewritten by CMP-063 and CMP-084 match.
4. **The exclusions are match conditions** (an object they spare is not judged, a skip): `exclude-namespaces` (the helper `bp-kyverno-policies.excludeNamespacesExpr` over `excludeNamespaces`, empty by default, so no namespace is spared, kube-system included) and `exclude-acme-http01-solver`, which spares a Service of type NodePort that carries the label `acme.cert-manager.io/http01-solver: "true"`. The legacy policy spared the labelled solver in its NodePort rule only; a labelled LoadBalancer is still judged. A solver-shaped name without the label is no carve-out (#5564), nor is the label with another value.
5. **The two rules become two validations.** A Service of type NodePort is refused. A Service of type LoadBalancer is refused unless `allocateLoadBalancerNodePorts` is `false`; an unset value counts as `true`, as the API server allocates then. Each message is the legacy text; it no longer repeats the namespace and name, which the denial and the policy report name.
6. **Same verdicts.** The suite was green on the legacy render first (window closed, Enforce; kyverno CLI v1.19.2), each result naming one of the two legacy rules: 20 results over the ten Services. Then `policy.yaml` became the new render (the chart defaults) and each result lost `rule:` and gained `isValidatingPolicy: true`: one result per Service, `fail` where a legacy rule failed, `skip` for the labelled solver the legacy NodePort rule excluded, `pass` for the rest. The four new Services are cases 7 to 10: a NodePort in kube-system, the solver label with the value `"false"`, a LoadBalancer with the solver label, a LoadBalancer with `allocateLoadBalancerNodePorts: true`.
7. **Current copy.** `tests/suites-current.sh` lists the suite after `flux-managed`; its checks already accept a ValidatingPolicy (CMP-062).
8. **The window test.** `tests/bootstrap-window.sh` counts the policies that enforce in a render; with the defaults it counts 2 (`forbid-local-path-storage` and `forbid-nodeport-service`), not 1. `tests/nodeport-enforce-5491.sh` asserts `[Deny]` in five cases of the values (the defaults, `bootstrapMode=false`, `sovereignConsume=local`, `action=Audit`, and `action=Audit` with `bootstrapMode=false`) and refuses to pass when the policy does not render as a ValidatingPolicy; its former assertion that the window holds the ban at Audit is removed, because the ban no longer does. `values.yaml` changes in two comments only.
9. **The live check reads the new kind.** Phase 2 of `scripts/check-live-nodeports.sh` reads `spec.validationActions` of the ValidatingPolicy `forbid-nodeport-service` and passes when it holds `Deny`. Where the cluster does not serve the kind `validatingpolicies.policies.kyverno.io` it fails (before, a cluster without the legacy kind only warned and exited 0). Where the new object is absent, it reads the legacy ClusterPolicy of the same name and passes only at `Enforce`: the local pack of `conformance-local` installs the published chart (field 4), and FND-G05 is required there, so a check that read only the new kind would fail this pull request and every region until the pin follows the published chart. This follows CMP-G02, which has read ClusterPolicy, ValidatingPolicy and MutatingPolicy since pull request 8889. A ValidatingPolicy at Audit fails even beside a legacy object at Enforce. Phase 1, the sweep of live node ports, does not change.
10. **The conformance account reads both kinds, by name.** Its ClusterRole keeps six rules: get on the definitions `clusterpolicies.kyverno.io` and `validatingpolicies.policies.kyverno.io` (one rule), and get on `forbid-nodeport-service` of `clusterpolicies` and `validatingpolicies` of the groups `kyverno.io` and `policies.kyverno.io` (one rule); no list, no other definition, no Secret, no exec. The test and the workflow's own role and its `kubectl auth can-i` checks say the same.
11. **Baseline.** `scripts/baselines/kyverno-legacy.json` loses the entry of the template (22 to 21 objects on the base of this ticket).

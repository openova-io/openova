# SOV-143 — The Secret register lists parent-bootstrap-token, with SOV-435 as the package that removes it

## In plain words

**The problem today.** At first boot every region of a new Sovereign creates a token Secret for the service account with which the parent reaches it. The register of the Secret objects that the platform allows does not list that Secret, so nothing records why it exists or which task removes it.

**What changes.** The register gains one entry for that Secret: transitional, with its consumer, its reason and the task that removes it at the parent release.

**Done means:**

- The register of Secret objects holds exactly one entry with the id parent-bootstrap-token, for the namespace kube-system and the name parent-bootstrap-token.
- The entry has the class T, names SOV-435 as the task that removes it and has the review date 2027-11-01.
- No other entry of the register matches the Secret kube-system/parent-bootstrap-token.
- The guard of the register passes in the check tree-guards with the new entry.

The rest of this ticket is the exact instruction for the model that does the work.

The file `scripts/secret-guard-baselines/secret-object-register.yaml`, the register of every Secret object that the platform allows in a platform namespace, holds one more entry: the Secret `kube-system/parent-bootstrap-token`. The first-boot template `infra/providers/_shared/cloudinit-control-plane.tftpl` creates that Secret, of type `kubernetes.io/service-account-token`, for the ServiceAccount `kube-system/parent-bootstrap`, whose token the parent uses to reach the region. ## 3. The model (the law)
1. The register has exactly four top-level fields, in this order: `schema`, `allowedUnmatched`, `entries`, `metadataAccess`. An entry has exactly the fields `id`, `namespace`, `name`, `class`, `consumer`, `reason`, `removal` and `reviewBy`. `name` is a pattern matched against the whole Secret name. An entry of class U or T names a removal package (three capital letters, a dash, three digits), and the guard fails it once its `reviewBy` date is past. These rules are checked by `scripts/secret-object-register.py`; this ticket does not change them.
2. This ticket adds one entry, the eight lines of field 16 step 1, at the end of the list `entries`: directly above the line that starts with `metadataAccess:`. Its values:
   - `id: parent-bootstrap-token`
   - `namespace: kube-system`
   - `name: "^parent-bootstrap-token$"`
   - `class: T`: the Secret exists only until the parent release. It is not class K, because it is not kept.
   - `consumer`: the token of the kubeconfig that each region posts back to the parent at first boot.
   - `reason`: Kubernetes keeps a ServiceAccount token without expiry only in a Secret of type `kubernetes.io/service-account-token`.
   - `removal: SOV-435`
   - `reviewBy: "2027-11-01"`, the review date of every other entry.
3. No other line of the register changes: not the header comment, not `allowedUnmatched`, not another entry, not `metadataAccess`. No other file changes.

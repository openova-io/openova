# CTL-231 — Resource browser: Git-owned objects refused, break-glass for the rest

## In plain words

**The problem today.** The resource browser of the console writes objects of the cluster directly, also objects whose desired state Git owns, so Flux undoes the change or the object drifts from Git. For a few Flux objects it pretends to open a pull request in a repository that nothing creates, and without Gitea it answers with an invented link. No direct write leaves a durable record of who made it and why.

**What changes.** An object that Git owns is refused with a clear answer that names its owner. Any other object is written only by the owner tier with a written reason, and each such write is recorded before and after it. The pretend pull request is gone.

**Done means:**

- Scaling, editing, applying or deleting an object that Git owns answers 409 managed-by-git with the name of the owner, and nothing is written.
- A multi-document apply that contains one Git-owned object applies none of its documents.
- Writing any other object needs the owner tier and a reason of at least ten characters; an admin gets 403 and a missing reason gets 400.
- An allowed write is recorded on the audit stream before it runs and after it ends, and it is not made when the stream does not take the record.
- A dry-run still validates any object, Git-owned or not.
- No route answers with a pull-request link any more, and the mutating-route contract marks the six write routes as done.

The rest of this ticket is the exact instruction for the model that does the work.

## 2. End goal
The six write entry points of the resource browser in catalyst-api use the package `products/catalyst/bootstrap/api/internal/clusterwrite` (merged with CTL-230): scale (POST and PUT `.../scale`), update (PUT `.../{kind}/{ns}/{name}`), apply (POST `.../apply`), delete (DELETE `.../{kind}/{ns}/{name}`) and the multi-document apply (POST `/api/v1/sovereigns/{id}/k8s/apply`). Each reads the live object first. An object that Git owns is refused with 409 `managed-by-git` and its owner, and nothing is written. Any other object is written only by break-glass: the owner tier and a reason of ten characters or more, recorded on the audit stream before the write and after it. The pretend pull-request path is deleted. The handler package gets smaller, and contract C9 and the two guard baselines say so.

## 3. The model (the law)
1. **Order of the gates on each write entry point.** First the route's own tier gate `requireResourceMutationAuth` (admin or owner), as today. Then the request is parsed and checked as today. Then the live object is read. Then `clusterwrite.Allow` (for the multi-document apply: `clusterwrite.Owner` for every document, then one `clusterwrite.BreakGlass`). Then the write. Then the `Finish` that `Allow` or `BreakGlass` returned is called with the error of the write (nil on success).
2. **Git-owned object.** `clusterwrite.Owner` decides: a Flux label (`kustomize.toolkit.fluxcd.io/name`, `helm.toolkit.fluxcd.io/name`, `app.kubernetes.io/managed-by: flux`), a Flux owner reference, or a kind of the intent lock (this holds also for an object that does not exist yet). The answer is 409 `{"error":"managed-by-git","code":"409","owner":"<owner>","detail":"..."}`. Nothing is written and no audit event is recorded.
3. **Any other object: break-glass.** The caller must have the owner tier (tier claim `owner` or realm role `catalyst-owner`; a request without claims passes, as at every gate of the resource browser today) and send a reason of at least 10 characters. Without the tier: 403 `break-glass-owner-only`. Without the reason: 400 `break-glass-reason-required`. When the audit stream does not take the intent event: 503 `audit-unavailable`, and nothing is written. These answers are written by `clusterwrite`; the handler only returns.
4. **Where the reason comes from.** Scale, update, apply and multi-document apply: the body field `reason` (each of these request types gains a field `Reason` with the JSON name `reason`). Delete: the query parameter `reason`.
5. **The multi-document apply** reads every document (kind, live object) before it writes any. When Git owns one of them, the whole request answers 409 and no document is applied. Otherwise one break-glass record covers the request: verb `apply`, resource `documents`, name the list `<Kind> <namespace>/<name>` of its documents joined by `, `. Its result is `error` when at least one document failed (`<n> of <m> documents failed`).
6. **Dry-run is not a write.** `POST .../dry-run` keeps its behaviour: no owner check, no break-glass, no audit. A real apply always reads the live object (also when the YAML carries a resourceVersion), because `clusterwrite` needs it; a dry-run reads it only when the YAML omits the resourceVersion, as today.
7. **Deleted.** `openFluxManagedPR` (the pull request in `<org>/cluster-config`, the repository name `cluster-config`, the invented URL `.../pulls/synthetic-<n>`), `isFluxManaged`, the constants `fluxManagedByLabel`, `fluxManagedByValue`, `fluxOwnerSuffix`, the 202 answer with `giteaPRUrl`, the fields `Flux` and `GiteaPRUrl` of a multi-apply result entry, and the request fields `commitMessage` of the update and of the multi-document apply. The body decoder refuses unknown fields, so a request that still sends `commitMessage` answers 400 `invalid-body`.
8. **Not changed.** Restart, exec, job retry and the reconciler actions (CTL-232). The number of direct cluster write calls in each file (the guard `scripts/check-no-direct-cluster-write.py` and its baseline stay as they are): the same `Patch`, `Update`, `Create` and `Delete` calls remain; only reads (`Get`) are added. No new file in the handler package. Routes and `cmd/api/main.go` are not changed.
9. **Contract C9.** The six write routes of batch F get `package: CTL-231, done: true`. The five operations that still name CTL-230 (job retry, reconcile, two exec routes, restart) get `package: CTL-232`; they stay `done: false`. After this no entry names CTL-230, which changed no route.
10. **Baselines.** `open_cluster_writers` of `scripts/baselines/mutating-routes.json` falls by six (six entries of class K become done). `handler_lines` and `handler_methods` of `scripts/baselines/api-structure.json` fall (`openFluxManagedPR` was a method; `applyOneDoc` becomes the method `readMultiApplyDoc` and the function `applyMultiApplyDoc`). Each is written from the tree by the command of its step; a baseline only goes down.

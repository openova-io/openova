# CLD-070 — Decision record and truthful contract documents

## In plain words

**The problem today.** The written contract for cloud provider modules is not true. Neither module meets it, and a second copy for one provider maps outputs that do not exist. Two component documents list Crossplane providers for six clouds, although only two clouds have a module and four of those providers are installed nowhere. The decisions on how the platform abstracts a cloud are recorded nowhere in the repository.

**What changes.** A decision record states the cloud abstraction contract and the alternatives that were rejected. The provider document shows the contract as a target, the false copy is deleted, and the two provider tables show what is installed today.

**Done means:**

- Decision record 0016 exists, is marked accepted, and is listed in the index of decision records.
- The provider module document states contract version 1, and its first heading says that this is a target which no test enforces yet.
- The Hetzner copy of the provider document is gone, and no file points at it.
- The provider tables of the OpenTofu and the Crossplane documents name only the two clouds that have a module, with the Crossplane packages that are really installed.
- No code, no chart and no workflow changed.

The rest of this ticket is the exact instruction for the model that does the work.

Written by work package CLD-070. The decision was taken on 2026-11-12. The four points of ADR-0011 that it replaces are listed under "What changes in ADR-0011". The order of the hand-over steps is not decided here. Decision record 0017 (work package SOV-620) records it.

## Context

Measured on `main` at commit `1de1896b3`, on 2026-11-13.

- Two OpenTofu modules create the cloud resources of a Sovereign: `infra/providers/huawei/` and `infra/providers/hetzner/`. Both render one shared bootstrap template, `infra/providers/_shared/cloudinit-control-plane.tftpl`.
- The shared template takes eight strings that the provider module supplies. It also tests the provider name on 23 lines.
- Both modules declare the same 33 common variables. Three of them have a different default in the two modules, and `regions` has a different type in each.
- The written module contract, `infra/providers/PROVIDER-INTERFACE.md`, listed eight required outputs. The Hetzner module emits three of them. The provisioning engine reads four outputs. No test compared a module with the document. A second document of the same name, in the directory of the Hetzner module, mapped that module to outputs it does not emit.
- The Go port `CloudProvider` in `products/catalyst/bootstrap/api/internal/providers/provider.go` has five methods. Provisioning does not go through it. The handlers call the shared engine in `internal/provisioner`, and the `Provision` method of both adapters has no caller.
- Crossplane core is version 1.18.0 (`platform/crossplane/chart/Chart.yaml`). `provider-opentofu` is installed on every Sovereign, and `provider-hcloud` on a Hetzner Sovereign only (`clusters/_template/infrastructure/providers/`). The state of every Workspace is a Kubernetes Secret (`clusters/_template/infrastructure/base/provider-config-opentofu.yaml`).
- The API registers 24 routes that change infrastructure. They write claims in the API group `infra.openova.io`, in the namespace `catalyst-day2`. No manifest in this repository defines that group or creates that namespace.
- Six Compositions for day-2 changes sit beside the adoption Composition in `platform/crossplane-claims/chart/templates/compositions/`. None of the six has a Huawei implementation. Ten more manifests in `platform/crossplane/compositions/` are installed by nothing.
- The Huawei module carries the values of one installation as defaults. The route job for pod address ranges and the repair of load-balancer members are Huawei code that sits in a shared chart and in the provisioning API.

So a new cloud cannot be added by adding files, the written contract is not true, and the day-2 write surface does not work on the cloud in use.

## Decision

There is one provider-neutral contract with four parts: a Go port, an OpenTofu module contract, a cloud profile and a provider pack. OpenTofu creates a Sovereign. Crossplane then takes ownership by running the same OpenTofu modules inside the Sovereign. The decisions are numbered K1 to K18.

| Decision | What is decided |
|---|---|
| K1 Port | Keep the Go port `CloudProvider` and its registry. Delete its `Provision` method. The shared engine `provisioner.Provision` stays the one entry point for provisioning and becomes provider-neutral. It drives an adapter through six required methods (`Name`, `Normalize`, `TfVars`, `ValidateCreds`, `ListServers`, `Wipe`) and through optional capability interfaces, which an adapter implements only when it needs them. A handler never imports an adapter package and never compares a provider name with a literal. |
| K2 Module contract | One OpenTofu module contract, version 1, kept as a machine-readable file, `infra/providers/_contract/contract.json`. Version 1 starts with 33 common variables, one `regions` type, five outputs, one rule for resource names and 14 inputs of the shared bootstrap template. A Go test and a `tofu test` find the modules by directory and fail when a module differs from the file. A later work package that changes the contract changes the file, and the tests follow the file. `infra/providers/PROVIDER-INTERFACE.md` is the readable form of the contract. |
| K3 Cloud profile | One data file per cloud, `profile.yaml`, in the pack. It is a file format. It is not a custom resource, and it is not copied into a cluster object. The module reads its own profile and sets three neutral Flux substitutes from it. catalyst-api reads the profile files in its image. The values of one installation (endpoint domain, image, zone, API address range) are a second document of the same schema. It is supplied at run time as a labelled ConfigMap and is never stored in this repository. A field enters the schema only together with the code that reads it. |
| K4 Provider pack | A pack is four directories that share one name and are declared by `pack.yaml`: the module `infra/providers/<name>/`, the overlay `clusters/_template/providers/<name>/`, the adapter `products/catalyst/bootstrap/api/internal/providers/<name>/` and, where needed, plug-in charts `platform/<name>-*/`. Adding a cloud adds files under these four roots and regenerates the generated files. A script proves that nothing else changed. |
| K5 Kit selection | Cloud-init sets one overlay path. The releases that belong to one cloud leave the shared bootstrap kit and move into that cloud's overlay. Core slots depend on one neutral release, `storage-ready`. The suspend flags that carry a provider name are deleted. |
| K6 Dead write surface | Delete the 24 infrastructure mutation routes, their claim writer, the six day-2 Compositions with their six definitions, and the ten manifests that nothing installs. They are not repaired. Work packages CLD-021, CLD-022 and CLD-023 do this. |
| K7 Hand-over and day-2 changes | OpenTofu provisions. At hand-over Crossplane takes ownership by running the same OpenTofu modules inside the Sovereign as `provider-opentofu` Workspaces. One base Workspace runs the bootstrap module (network, control-plane nodes, load balancer, addresses). It changes only in a declared maintenance window. Unit Workspaces run small modules of the pack, one for each thing that changes day to day. A Workspace that takes over existing resources is observed first, and becomes managed only after a plan with zero changes. Crossplane always has an implementation, because it wraps the pack's own module. A pack may later use a native Crossplane provider inside a Composition, with no change to the contract. There is no Cluster API and no second OpenTofu runner. |
| K8 Crossplane version | Move to Crossplane 2 before any new definition is written. The path is three ordinary upgrade steps: 1.19, 1.20, then the highest 2.4 patch release of that day (work packages CLD-061, CLD-062 and CLD-065). New definitions use the version 2 form: namespaced, no claims, pipeline mode. |
| K9 Workspace state | Workspace state lives in the Sovereign's object bucket, through the `s3` back end. OpenTofu encrypts it before it is written, with a key from OpenBao. No state is kept in a Kubernetes Secret. No Workspace may hold a real resource until gate check CLD-G05 has read the stored object and found ciphertext. One offline backup of the key, held by the sovereign-admin, can decrypt the state when OpenBao is down. A restore drill proves it. |
| K10 First definition | This area writes one provider-neutral definition: `NodePool`. It merges only in the pull request that also carries two Compositions for it, one for the Huawei pack and one for the `local` pack. So it never exists with a single implementation. For a capability contract of the service model (object storage is the first), this area ships only the pack's side: the unit module `day2/<contract>` and the Composition `<contract>-native`. `XCloudAdoption` stays as it is until the base Workspace replaces it. |
| K11 Huawei parameters | The Huawei pack targets a Huawei Cloud Stack installation: the on-premises form of Huawei Cloud, which answers the Huawei API at its own endpoints. Public Huawei Cloud is not a target. Endpoint domain, authentication address, region, zone, image, API address range, registry mirror and DNS API host become inputs that an installation document supplies. The code in this repository holds no value of an installation. |
| K12 Hetzner | Hetzner is proven again late, in a fixed time box, with one region only (epic CLD-180). That is the second-provider proof. Until then its profile is marked `unproven` and the wizard does not offer it. If the proof fails, work package CLD-190 retires Hetzner, and the hyperscaler pack becomes the second real provider. |
| K13 Files-only proof | The rule "a new cloud adds files only" is proven twice. First without a cloud account: the profile, adapter, overlay and unit module of the `local` pack are added under the additive check (work package CLD-088). Second on a real cloud (epic CLD-200; AWS unless another cloud is chosen before that epic starts). A script measures the proof: only added files under the four pack roots, plus regenerated files. Any other change is a defect of the contract and is fixed on `main` first. |
| K14 Leak guard | One scanner with two tiers of provider words, a list of allowed paths, and a baseline per file that can only fall (work package CLD-010). The values of an installation are a second rule: zero in code, and a falling baseline in tests and documents (work package CLD-164). |
| K15 Cloud controller | Cloud code that sits in shared charts or in the provisioning API (the Huawei route job, the repair of load-balancer members) moves to a Huawei plug-in chart that runs inside the Sovereign (epic CLD-150). Node events start both. The five-minute schedule of the route job stays, as a safety net only. |
| K16 One provider per Sovereign | Contract version 1 allows one provider per Sovereign. The per-region field `provider` leaves the module contract. |
| K17 Local pack | A pack named `local` implements the whole contract on one CI runner. OpenTofu starts local machines, the shared bootstrap template boots them, and they run a reduced kit. From its first version it brings up two clusters and a console address. It is the one hermetic environment: the gate suite, the two-cluster hand-over test and the two-cluster mesh test all run on it (epic CLD-085). |
| K18 Secret objects | This area handles no credential of an Application. The platform credentials that it needs as Kubernetes Secret objects are the exceptions listed below. No work package of this area may add a Secret object that is not in that list. |

### The Secret objects of K18

| Secret object | Holds | Why it is a Secret object, and who removes it |
|---|---|---|
| `huawei-operator-creds`, in the namespace of catalyst-api | The cloud credentials that the sovereign-admin of a mothership supplies for provisioning | catalyst-api reads it as environment variables today. Work package CLD-106 replaces it by mounted files. |
| `flux-system/cloud-credentials` | The Sovereign's own cloud credential | The releases of the storage driver, the cloud controller, the autoscaler and the network read it through a Secret reference. ## Alternatives rejected

K18 has no entry here: it is a list and a rule, and no other design was weighed for it.

- **K1.** (a) Make `CloudProvider.Provision` the entry point and move the engine into each adapter. Rejected: the `Provision` of both adapters only calls back into the shared engine, and the engine holds the proven retry and time-out logic. A copy in each adapter is a rewrite where an extension is enough. (b) Keep the present extension mechanisms (global function variables, a type assertion to one adapter, tests on the provider name) and add more hooks. Rejected: none of them can be found from the port. (c) Replace the port by Cluster API. Rejected: it has no usable Huawei provider.
- **K2.** (a) Keep the written document as the contract. Rejected: neither module meets it, and a second document was false. (b) Generate both modules from one template. Rejected: the modules differ in their resources for good reason; only the interface is common.
- **K3.** (a) A `CloudProfile` custom resource with a controller. Rejected: every reader can read a file or a ConfigMap, and a kind with no reconciler is dead weight. (b) One Flux substitute per flag, set in cloud-init. Rejected: Hetzner user-data is close to its size limit of 32 KiB, so the profile cannot travel there. (c) Installation values in the public pack. Rejected: that publishes the environment of one installation and makes the pack serve that installation only. (d) Render the profile into ConfigMaps with a generator and one more Flux Kustomization. Rejected: only three values reach Flux, and every other reader is catalyst-api, which has the files in its image.
- **K4.** One top-level directory `providers/<name>/` that holds everything. Rejected: the Go adapter must sit inside the Go module of the API, the overlay must sit under a path that the Flux source includes, and scripts, workflows and the image build refer to the Huawei module where it is. Moving proven code only to make the tree tidy is a cost with no gain.
- **K5.** (a) Rename the flags neutrally and keep one block per cloud. Rejected: the edits to shared files still grow with the number of clouds. (b) Give each overlay a release with one fixed name for core slots to depend on. Rejected: renaming a live HelmRelease makes Flux uninstall the storage driver. (c) Drop the storage dependency. Rejected: database releases would time out while their volumes are pending.
- **K6.** Repair in place (correct the API group, create the namespace, add the provider configurations). Rejected: after those repairs the Compositions still have no Huawei implementation, and the writer still bypasses Git. Every layer would be rewritten anyway.
- **K7.** (a) Native Crossplane providers on hyperscalers from the start. Rejected for version 1: on Huawei and Hetzner the implementation is the wrapped module in any case, and two engines double the supply-chain and secrets work. The contract allows it later, because a Composition is private to its pack. (b) A second OpenTofu runner. Rejected: one infrastructure control plane. (c) One Workspace for the whole Sovereign. Rejected: every Workspace is planned again at each poll, so one Workspace would put the whole Sovereign at risk in each run; hence base and unit. (d) Plain unit Workspaces committed to Git, with no definition in front, for good. Rejected: the commit would then name the provider's module path, so every writer would need a template shaped by the provider. It is accepted as the first step: the mechanism is proven with a plain unit Workspace before the definition exists (work package CLD-174).
- **K8.** (a) Write new definitions on 1.18 in the old form. Rejected: each would be written twice, because the old form is not accepted for version 2 resources. (b) Stay on 1.18. Rejected: upstream no longer maintains it.
- **K9.** (a) Keep the Kubernetes back end. Rejected: the state would hold credentials in etcd. (b) The Kubernetes back end with encryption. Rejected: the description of a cluster's infrastructure would be lost together with the cluster it describes.
- **K10.** (a) Define all the kinds that the deleted write surface wrote. Rejected: none of them could work, because they were written to an API group that nothing defines, and a definition without a consumer is shelfware. (b) Write an object-bucket definition here. Rejected: it had one implementation and no consumer in this area. (c) A node-pool schema with rollout strategy and health policy. Rejected for version 1: no code reads those fields. They can be added later, because every added field is optional.
- **K11.** (a) Leave the values as defaults of the module and document them. Rejected: the pack then serves one installation, and the values describe the environment of one installation in a public repository. (b) One pack per installation. Rejected: it copies a module of about 2,000 lines to change eight values.
- **K12.** (a) Retire Hetzner now. Rejected: until a third cloud is live, Hetzner is the only second implementation with a different shape (a load balancer made by a controller, one token supplied by the user, a size limit on user-data). Without it the contract is checked against one cloud and mocks. (b) Prove it again first, before the refactor. Rejected: that proves wiring which the refactor then changes.
- **K13.** A live third cloud before the second-provider proof. Rejected: a new module, new charts and a new account while the first two clouds are not yet green is the wrong order.
- **K14.** (a) Extend the existing vendor-coupling guard. Rejected: it matches three object-storage patterns and cannot see Huawei. (b) A hard zero from the first day. Rejected: the present leaks cannot be cleared in one change, and a guard that is switched off to merge is no guard. (c) One total in place of a baseline per file. Rejected: a total lets a new leak hide behind an unrelated clean-up.
- **K15.** (a) Keep the member repair in the mothership and repeat it on a timer. Rejected: the mothership would stay a standing writer into every Sovereign. (b) A shared "cloud controller" chart that loads provider code by name. Rejected: a shared chart would then carry provider wiring; a plug-in chart keeps it in the pack.
- **K16.** One module per region, so that regions can sit on different clouds. Rejected for version 1: one module creates the resources of one cloud, and no module can create a region on another cloud.
- **K17.** (a) No local pack; rely on a golden render and a live cloud. Rejected: the written contract already drifted once with no conformance run, and a contributor without a cloud account would have no proof at all. (b) Local clusters made by a cluster tool that skips the shared bootstrap template. Rejected: the template and its inputs are the larger half of the contract. (c) Build the whole local pack before the port exists. Rejected: it would add a third set of provider branches to shared code and then remove them.

## What changes in ADR-0011

ADR-0011 stays the record of the adoption seam. Four of its points change.

1. State. The seam of ADR-0011 keeps Workspace state in a Kubernetes Secret. State moves to the Sovereign's bucket and is encrypted (K9).
2. Version. The seam was written for Crossplane 1.18. It moves to Crossplane 2 (K8).
3. Shape. ADR-0011 adopts each cloud resource with its own observe-only Workspace behind `XCloudAdoption`. One base Workspace and unit Workspaces replace that shape (K7). `XCloudAdoption` stays until the base Workspace exists.
4. Native Hetzner definitions. ADR-0011 left them in place as the day-2 path for Hetzner. They are deleted (K6).

## Consequences

- A new cloud is added by adding files under four roots. A script and a pack that runs in CI prove this on every pull request.
- The documents state a target until the conformance tests exist. `infra/providers/PROVIDER-INTERFACE.md` says so in its first heading, and work package CLD-090 changes that heading when the tests enforce the contract.
- Cloud drift is found by a poll of the Workspaces. Changes of intent stay driven by events.
- Version 1 of `NodePool` has a fixed number of nodes: no autoscaling, no rollout strategy and no replacement on failed health.
- The `local` pack proves the contract and the hand-over mechanics. It does not prove a cloud: load balancer, volumes and quotas are stand-ins there. The run on the real cloud covers those.
- Hetzner is not offered until it is proven again.

# OpenTofu provider module contract — `infra/providers/<name>/`

## Contract version 1: target, not yet enforced

This document states the contract that every provider module under `infra/providers/<name>/` will meet. It is a target. No test enforces it yet, and neither module meets all of it today: section 7 lists what was measured. The decision record is [ADR-0016](../../docs/adr/0016-cloud-abstraction-contract.md).

Two work packages make it real. CLD-080 publishes the contract as a machine-readable file, `infra/providers/_contract/contract.json`. CLD-090 brings the modules into line, adds the conformance tests of section 6 and changes the heading above. From CLD-080 on, the file is the source and this document is its readable form. Where the two differ, the file wins.

A module receives three classes of variable.

1. **Contract variables.** The 33 of section 1. Every module declares every one.
2. **Engine extras.** Neutral variables that the provisioning engine writes today and that not every module declares. OpenTofu accepts an undeclared variable in a variables file with a warning, and the engine relies on that. The list is closed: `domain_mode`, `dynadot_key`, `dynadot_secret`, `ha_enabled`, `pool_domain`, `sovereign_subdomain`, `sovereign_deployment_id`, `parent_domains`, `qa_fixtures_namespace`, `qa_organization`, `qa_test_session_enabled`, `provider`, `region`, `control_plane_size`, `worker_size`, `worker_count`, `retry_attempt`, `object_storage_region`, `object_storage_access_key`, `object_storage_secret_key`, `object_storage_bucket_name`. A module may declare any of them. No entry is added without a change of the contract. This class is not a place for new variables.
3. **Adapter variables.** Variables whose name or meaning belongs to one cloud, such as `hcloud_token` or `huawei_access_key`. The Go adapter of that cloud supplies them.

variable "regions" {
  type = list(object({

    cloud_region       = string
    availability_zone  = optional(string, "")

    control_plane_size = string
    worker_size        = string
    worker_count       = number

  validation {

### 5. Module rules

- **Boot data never replaces a node.** Every compute resource that sets boot data (`user_data`) lists it in `lifecycle.ignore_changes`. A bootstrap template that renders differently must never plan the replacement of a node.
- **No node port.** A front door reaches a node on a host port: 443 and 80, and 53 (TCP and UDP) for the DNS front end. A module never declares a load-balancer target or a firewall rule in the range 30000 to 32767.
- **One control-plane node per region.** A second or third control-plane node per region is a change of the contract, with a work package of its own.

### 6. Conformance tests (added by CLD-090)

1. A Go test, `TestProviderPacks`, lists the directories under `infra/providers/` whose name does not start with `_`. For each it compares the declared variables, outputs and template inputs with `contract.json`, and it asserts the first two rules of section 5.
2. Each module has `tests/contract.tftest.hcl`. Its body is the same in every module. It plans the module for one region and for two regions and asserts `contract_version` and the keys of `control_plane_ips_per_region`.
3. CI finds the modules by directory. No workflow holds a list of provider names.

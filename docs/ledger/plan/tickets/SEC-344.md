# SEC-344 — Upstream pods to injection: Grafana

## In plain words

**The problem today.** Grafana gets the client secret of its single sign-on from a Kubernetes Secret, which an external-secrets object copies out of OpenBao and the pod reads as environment variables. Each such Secret is a copy of a credential outside OpenBao, and the exception register allows this one only until Grafana can read a mounted file.

**What changes.** Grafana reads the client secret from a file that the secrets store driver mounts straight from OpenBao, and the sign-on bridge writes that value with an identity that may write it but never read it. The Secret, its external-secrets object and its exception entry are gone.

**Done means:**

- Rendering the Grafana chart produces no Secret for the sign-on client secret and no external-secrets object, even where that interface exists.
- Grafana's configuration reads the client secret from a mounted file, and the mounted volume names the OpenBao path of the Grafana namespace.
- The sign-on settings that are not secret, among them the identity-provider hint and the root address, render with the same values as before.
- The sign-on bridge writes the client bundle of Grafana to that path, logging in as an identity that may create and update it but never read it, and a refused login or write fails that reconcile.
- OpenBao renders that write-only identity, bound to the account of the bridge with the OpenBao audience.
- The exception register no longer lists the Grafana sign-on Secret, and the allow-lists of the secret guards no longer hold a line for the Grafana chart.

The rest of this ticket is the exact instruction for the model that does the work.

## 2. End goal
The Grafana pod of bp-grafana signs users in through Keycloak with a client secret that it reads from the file `/var/run/secrets/openova/client-secret`, mounted by the Secrets Store CSI driver from OpenBao path `mounted/data/<release namespace>/shared/sso-oidc/e1` (route 1 of the result of SEC-335, `docs/ledger/plan/spikes/SEC-335.md`: `$__file{}` in `grafana.ini`). No Secret object carries the client secret any more: the chart's ExternalSecret and the Secret `grafana-sso-oidc-credentials` are gone, and so is the class U register entry `grafana-sso-oidc`. The value is written to that path by bp-sso-bridge, which already creates the Keycloak client and its secret, with a producer identity of bp-openbao that may create and update the path and never read it.

## 3. The model (the law)
1. **No Secret for the client secret.** bp-grafana renders no ExternalSecret and no document that names `grafana-sso-oidc-credentials`, also where the External Secrets API exists. The template `platform/grafana/chart/templates/sso-oauth-source-externalsecret.yaml` is deleted and `grafana.envFromSecret` is no longer set. The one Secret of the render stays the upstream admin login `grafana`.
2. **The mount (route 1 of SEC-335).** `grafana.ini` sets `client_secret = $__file{/var/run/secrets/openova/client-secret}`. The grafana container mounts volume `openova-secrets` read-only at `/var/run/secrets/openova`; the volume is a CSI volume of driver `secrets-store.csi.k8s.io`, read-only, SecretProviderClass `grafana-sso`.
3. **SecretProviderClass `grafana-sso`** (new template `platform/grafana/chart/templates/sso-mounted.yaml`, rendered when `sso.enabled`): provider `openbao`, `roleName: workload`, `audience: openbao`, `openbaoAddress` from the new value `sso.openbaoAddress`, one object `client-secret` from key `client_secret` of `mounted/data/<release namespace>/shared/sso-oidc/e1`, and no `secretObjects`, so the driver never writes a Secret. The OpenBao role `workload` lets every pod read the shared subtree of its own namespace (`platform/openbao/chart/templates/_config.tpl` lines 146 to 153 and 396 to 398); nothing in bp-openbao's reading side changes.
4. **The settings that are not secret** come from ConfigMap `grafana-sso-settings` of the same template, as `GF_` variables through `grafana.envFromConfigMaps`, which override `grafana.ini`: always `GF_AUTH_GENERIC_OAUTH_CLIENT_ID` (`sso.clientId`); with `sso.sovereignFqdn` also the authorize URL (with `?kc_idp_hint=<sso.idpHint>` unless the hint is empty), the token and userinfo URLs of realm `sso.realm` and `GF_SERVER_ROOT_URL`. These are the values the deleted ExternalSecret produced. `sso.externalSecretStoreName` and `sso.refreshInterval` are removed with it.
5. **The writer.** bp-sso-bridge writes, for a HelmRelease whose values carry `sso.mountedCopy: true`, the same client bundle it writes to `secret/sso/<clientId>` also to `mounted/data/<targetNamespace>/shared/sso-oidc/e1` (function `openbao_put_mounted` of the reconciler script). For that write it logs in as role `producer-sso-bridge` with a projected service-account token for audience `openbao` (3600 seconds, `/var/run/secrets/openbao/token`), passed in as `OPENBAO_PRODUCER_ROLE` and `OPENBAO_PRODUCER_JWT_FILE`. A failed login or a write answered with a code other than 200 or 204 fails the reconcile of that HelmRelease, which the next tick retries. Without `mountedCopy` nothing below `mounted/` is written.
6. **The producer identity.** bp-openbao's value `producers` gains the entry `sso-bridge` (service account `sso-bridge-reconciler` of namespace `sso-bridge`, path `+/shared/sso-oidc/e1`). The existing producer rule of SEC-192 renders it as policy `producer-sso-bridge` (create and update on `mounted/data/+/shared/sso-oidc/e1`, read and delete on its metadata, no read of a value) and role `producer-sso-bridge` (audience `openbao`, 15 minutes, at most one hour). This follows the precedent of SEC-192: a value written into the mounted path of another namespace is written with a write-only producer identity. The entry `catalyst-api` is unchanged.
7. **Kit slot 25** sets `sso.mountedCopy: true` beside `sso.skipExternalSecret: true`, which stays so that bp-sso-bridge never brings the Secret back through its own ExternalSecret. Its edge to bp-external-secrets stays: it changes together with `scripts/expected-bootstrap-deps.yaml`, which this package does not touch.
8. **The register and the allow-lists**, as in every roll-out package of the secret guards: the entry `grafana-sso-oidc` of `scripts/secret-guard-baselines/secret-object-register.yaml` is deleted; the line `platform/grafana/chart:0:1` of `check-secret-object-register.txt` and the line of the deleted template in `check-reflector-scope.txt` are deleted, because the chart's counts fall to zero. `allowedUnmatched` is not changed.
9. No new Python, no change to a live system, and no version line of a `Chart.yaml` changes.

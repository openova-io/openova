# SVC-080 — Function tests: GitOps, registry and certificate charts

## In plain words

**The problem today.** The GitOps controllers, the git server, the registry, the image mesh and the three certificate charts count as working when their Pods run. Nothing tests that the controllers are ready, that the git server and the registry answer, that a certificate is really issued, or that the issuers and the DNS webhook work. The gitea chart also leaves every file under a folder named tests out of its package, so a test hook added there would never ship.

**What changes.** Each of the seven charts gets one test Pod that asks the service it installs a question and checks the answer, and a render check per chart holds the Pod to the contract. The gitea chart leaves out only its own top-level test folder, so its test hook ships.

**Done means:**

- Each of the seven charts renders one test Pod with the hook test, a deadline of 300 seconds and the restart policy Never, and renders none where its own gate switches it off.
- Each test asks its service a question and checks the answer; the certificate test also has cert-manager issue one certificate and removes it again.
- A render test per chart fails when that chart's test Pod breaks the contract, and it runs on every pull request that changes the chart.
- The packaged gitea chart holds its test hook and still leaves out its render tests.
- The service-model guard counts seven more charts with a function test.
- The dragonfly test policy lets its Pod reach cluster DNS and the manager Pods, under any release name, and the network guard lists that test file as a named exception of this task.

The rest of this ticket is the exact instruction for the model that does the work.

## 2. End goal
`helm test` on a release of `bp-flux`, `bp-gitea`, `bp-harbor`, `bp-dragonfly`, `bp-cert-manager`, `bp-cert-manager-issuers` or `bp-cert-manager-powerdns-webhook` runs one Pod that asks what the chart installs a question, checks the answer, and prints one last line `FUNCTION-TEST pass|fail <chart name> <reason>`. Each of the seven charts has a render test `chart/tests/function-test-render.sh`, which CI runs with the chart's other tests on every pull request that changes the chart. The `.helmignore` of `bp-gitea` anchors its pattern `tests/` to the chart root, so `templates/tests/` is rendered and packaged while `chart/tests/` stays out of the package. The service-model guard counts seven more charts with a function test. The one test file that renders a CiliumNetworkPolicy (`bp-dragonfly`) lets the test Pod reach cluster DNS and has a named exception line in `scripts/network-guards-exceptions.tsv`, so the network guards stay green with an unchanged baseline. No version line and no pin changes: CI writes chart versions after the merge.

## 3. The model (the law)
1. **The contract.** It is section 4.5 of `docs/RUNBOOKS.md` and the checker `scripts/check-function-test.py` (package SVC-060; package SVC-070 added ClusterRole and ClusterRoleBinding to the kinds allowed beside the Pod). A chart that has a function test ships one file `chart/templates/tests/function-test.yaml`. It renders one Pod named `<release>-function-test`, with the annotations `helm.sh/hook: test` and `helm.sh/hook-delete-policy: before-hook-creation,hook-succeeded`, the label `catalyst.openova.io/function-test: "true"`, `restartPolicy: Never` and `activeDeadlineSeconds: 300`. The test sends a request and checks the response against what the chart installs. It exits 0 on pass and non-zero on fail, and its last line is `FUNCTION-TEST <pass|fail> <chart name> <reason>`. It needs nothing outside the cluster, uses an image the chart already uses or one the kit already pulls, renders nothing when the chart's own gate renders nothing, never creates a Secret, and every container requests cpu and memory. Every network call of a test has a time limit, so each test ends well inside its 300 seconds.
2. **The seven tests.** Each `function-test.yaml` is the block of field 5 of the same name, byte for byte. The image of each is `harbor.openova.io/proxy-dockerhub/alpine/k8s:1.31.4` (the chart's own value for it where it has one: `catalyst.stuckHelmReleaseRecovery.image` of `bp-flux`, `crdGate.image` of `bp-cert-manager` and `bp-cert-manager-issuers`), or `functionTest.image`.

   | Chart | Renders when | The test passes when |
   |---|---|---|
   | `bp-flux` | `flux2.sourceController.create` or `flux2.kustomizeController.create` is not `false` | for each of those two controllers that the subchart creates, at least one Pod `app=<controller>` is Running in the namespace, and `GET http://<Pod IP>:9440/readyz` answers 200 for every such Pod. A ServiceAccount, Role (get and list `pods`) and RoleBinding give the Pod that right. |
   | `bp-gitea` | always (no master gate) | `GET http://<fullname>-http.<gitea.namespace or release namespace>.svc.cluster.local:<gitea.service.http.port, default 3000>/api/v1/version` answers 200 with a `version`. |
   | `bp-harbor` | always (no master gate) | on `<scheme>://<fullname>-core.<namespace>.svc.cluster.local:<port>` (http and 80, or https and 443 with `harbor.internalTLS.enabled`), `GET /v2/` answers 401 with a `WWW-Authenticate` header that starts with `Bearer realm=`, and `GET /api/v2.0/health` answers 200 with no `status` `unhealthy` or `unknown` and at least one `healthy`. |
   | `bp-dragonfly` | `dragonfly.manager.enable` is not `false` | `GET http://<fullname>-<dragonfly.manager.name, default manager>.<dragonfly.namespaceOverride, else the release namespace>.svc.cluster.local:<dragonfly.manager.restPort, default 8080>/healthy` answers 200. With the API `cilium.io/v2` a CiliumNetworkPolicy lets the test Pod reach cluster DNS and the manager Pods on the REST port. The policy names the manager Pods as the subchart labels and places them: `app=<fullname>` and `component=<dragonfly.manager.name>`, in the namespace `dragonfly.namespaceOverride`, else the release namespace. |
   | `bp-cert-manager` | always (no master gate) | a self-signed Issuer `<release>-function-test` and a Certificate `<release>-function-test` for `function-test.invalid`, Secret `<release>-function-test-tls`, created in the release namespace, give the Certificate the condition `Ready` `True` within 120 seconds; then, and also on failure, the test deletes the Certificate, the Issuer and that Secret. A ServiceAccount, Role (create, get and delete `issuers` and `certificates`; get and delete the one Secret by name) and RoleBinding give the Pod that right. |
   | `bp-cert-manager-issuers` | the chart renders at least one ClusterIssuer | every ClusterIssuer it renders (`letsencrypt-dns01-prod` with `certManager.issuers.dns01.enabled`, `letsencrypt-http01-prod` with `certManager.issuers.http01.enabled`) reports `Ready` `True` within 180 seconds. A ServiceAccount, a ClusterRole (get `clusterissuers`) and a ClusterRoleBinding, named `<namespace>-<release>-function-test`, give the Pod that right. |
   | `bp-cert-manager-powerdns-webhook` | `apiService.enabled` is true | `GET /apis/<webhook.groupName>/v1alpha1` through the Kubernetes API, which the APIService of the chart sends to the webhook Pod, answers with the group version `<webhook.groupName>/v1alpha1` and the kind `ChallengePayload`. The ServiceAccount of the file has no binding: reading a discovery document needs none. |

   `<fullname>` is computed the way the subchart computes it: `fullnameOverride`, else the release name when it contains the chart name (`gitea`, `harbor`, `dragonfly`, or the subchart's `nameOverride`), else `<release>-<name>`.

   `bp-cert-manager` has no master gate. Its subchart is a dependency without a `condition`, and the value `cert-manager.enabled` is a placeholder of the upstream chart that no template reads. So `cert-manager.enabled=false` switches nothing off: cert-manager is still installed, and the test still renders.
3. **The render tests.** Each chart gets `chart/tests/function-test-render.sh`, the block of field 5 of that name, byte for byte. Each first runs the checker's self-test, builds the chart's dependencies when `charts/` is empty, then renders every shape of item 2 and checks it with the checker (`--absent` for each gate under which the test renders nothing) and with exact text checks. The render test of `bp-cert-manager` also holds that `cert-manager.enabled=false` renders as many Deployments as the default render, so a gate added to the chart later cannot pass without the test following it. The render test of `bp-dragonfly` also compares the labels and the namespace of the policy's manager rule with the Pods of the manager Deployment of the same render: for the kit's release, for another release name and with `dragonfly.namespaceOverride`. The whole render of `bp-harbor` cannot be read by PyYAML (a document of the upstream redis StatefulSet holds a tab), so its render test gives the checker the render of the test file alone and counts the test label over the whole render in place of the checker's rule FT12. CI's workflow `Chart tests (PR)` runs every `chart/tests/*.sh` of a changed chart.
4. **The gitea package.** In `platform/gitea/chart/.helmignore` the two lines `# CI integration tests + their fixtures/helpers` and `tests/` become the four lines of step 30: a three-line comment and the line `/tests/`. Helm reads an unanchored `tests/` as every folder named `tests`, `templates/tests/` included; `/tests/` names only the chart's own `tests/`. Nothing else in the file changes.
5. **The baseline.** In `scripts/service-model-baseline.yaml` the value of the line `  G6.function-test-charts: <n>` rises by exactly 7, written by the command of step 31. The step adds 7 to the value it finds; it never writes a fixed number. No other line changes.
6. **The network guards.** Two rules hold for every test file that renders a policy.
   - Guard G2 of `scripts/check-network-guards.py` refuses a policy kind outside the policy chart unless the file has a line in `scripts/network-guards-baseline.tsv` or in `scripts/network-guards-exceptions.tsv`. The baseline may only shrink: its tool (`check-network-guards.py baseline`) refuses an added line. The exceptions file is for an object that a package's own work defines, with that package as owner. So step 32 appends one exception line for the dragonfly test file, owner `SVC-080`, and the baseline does not change.
   - `scripts/check-netpol-egress-completeness.py` (the check `Every constrained workload keeps cluster DNS`) renders every chart that has a policy template, test hooks included, with the API `cilium.io/v2`. With the test file `bp-dragonfly` becomes such a chart. Every group of policies that declares egress must allow 53/UDP and 53/TCP to the Pods `k8s-app: kube-dns` in `kube-system`; the dragonfly test policy does.
7. **Nothing else changes.** No `values.yaml`, no other template, no kit slot, no `Chart.yaml`, no `blueprint.yaml`, no version line and no pin. Package FND-011 is merged: CI writes the version of every chart a merge changed. No kit slot sets `spec.test`, so Flux runs none of these tests yet; package SVC-130 switches them on. Nothing is deleted.

# FND-041 — The suite selects only the checks that are Go files of the suite

## In plain words

**The problem today.** The acceptance suite runs every entry of the list of gate checks that is expected to fail or required in the place where it runs, and stops when it finds no check of its own for one. Some entries are proven by a script or by browser tests in a job of their own, so the suite has no check for them and stops before it starts. Today a run on the local pack stops this way at once, and a run in the cloud would stop the same way as soon as the sign-in check is marked expected-fail.

**What changes.** The suite reads where each entry is implemented and takes only the entries implemented by a Go file of the suite. An entry implemented elsewhere is left to its own job. An entry implemented by a Go file of the suite that has no check still stops the run, as before.

**Done means:**

- A run of the suite on the local pack with the list of gate checks of the repository no longer stops with the message that a check is not registered.
- An entry implemented by a script or by a folder of browser tests is not run by the suite and does not stop it, in the local place and in the cloud place.
- An entry implemented by a Go file of the suite that has no registered check still stops the run with that check named.
- The suite's unit tests prove all three rules, and every earlier test of the suite still passes.

The rest of this ticket is the exact instruction for the model that does the work.

## 2. End goal
The acceptance suite (`tests/acceptance/sovereign`) runs only the gate checks it owns. When it is given the gate manifest (the JSON export of `docs/ledger/gates.yaml`) it selects an entry only when the entry is `expected-fail` or `required`, lists the run's place in `runs_in`, and names a Go file of the suite as its `implementation`. An entry implemented by a script under `scripts/` or by a folder of browser specs is proven by its own job, and the suite leaves it out without an error. A selected entry with no registered check still stops the run with exit code 2 and the message `gate manifest: no registered check for <id>`. A person sees this when `sovereign-acceptance run --run-in local --manifest <export>` reaches its result line instead of stopping on `CLD-G02`.

## 3. The model (the law)
1. `ManifestCheck` in `tests/acceptance/sovereign/internal/suite/registry.go` reads the field `implementation` of each manifest entry (JSON key `implementation`, a string; absent means empty).
2. An entry is a check of the suite when its implementation, cleaned with Go's `path.Clean`, starts with `tests/acceptance/sovereign/` and ends with `.go`. This is the same kind that `scripts/acceptance-gate.py` rule 3 calls "a Go file under tests/acceptance/sovereign/".
3. `SelectChecks` selects an entry only when all four hold: its state is `expected-fail` or `required`; its `runs_in` lists the run's place; it is not destructive when the place is `self`; it is a check of the suite (point 2). The first three are unchanged.
4. An entry that fails point 2 is left out with no error and no output, even when a check with the same identifier is registered. That covers a script under `scripts/`, a folder under `products/catalyst/bootstrap/ui/e2e/gate/` or `core/marketplace/e2e/gate/`, any other path, and an empty implementation.
5. A selected entry without a registered check is an error that wraps `ErrManifest` and ends with `no registered check for <id>`. The binary exits 2 on it and writes no record. This is unchanged.
6. Nothing else changes: not the record, not `runChecks`, not the binary's flags, not `scripts/acceptance-gate.py`, not `docs/ledger/gates.yaml`, not a workflow.

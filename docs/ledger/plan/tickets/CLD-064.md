# CLD-064 — Convert the adoption Composition to pipeline mode

## In plain words

**The problem today.** The adoption Composition still uses the native Resources mode, which Crossplane 2 no longer has. The next Crossplane upgrade cannot be taken while it is in place. The function that Pipeline mode needs is not installed.

**What changes.** The function function-patch-and-transform is installed beside the OpenTofu provider, and the adoption Composition runs in Pipeline mode with one step of that function. What the Composition creates stays the same.

**Done means:**

- The rendered adoption Composition is in Pipeline mode, with one step that calls function-patch-and-transform.
- The step composes the same Workspace as before, from the same template, module and patches; each patch names its type.
- The providers layer of the template installs the function at version v0.11.2 from its upstream registry, and its pod declares CPU and memory requests.
- The guard on written source addresses passes, with its kit count raised by exactly the one new package line.
- The guard on the adoption endpoint hosts reads the module from the Pipeline input and still passes.
- On the next candidate, the gate check of the Crossplane upgrade finds every adoption claim and its Workspace Synced and Ready.

The rest of this ticket is the exact instruction for the model that does the work.

## 2. End goal
The Composition `opentofu-cloud-adoption.compose.openova.io` of the chart `bp-crossplane-claims` renders with `mode: Pipeline` and one pipeline step, `patch-and-transform`, that calls the Function `function-patch-and-transform`. The step's input `resources` is the list the Composition used in Resources mode. The list stays where it is in the template file, as a named template; the only additions to it are the patch and transform types that Resources mode assumed. The providers layer of the template (`clusters/_template/infrastructure/providers/base`) installs that Function, version `v0.11.2`, beside provider-opentofu, with a runtime configuration that gives its pod CPU and memory requests. Two guards follow the change: the source-address guard counts the one new package line, and the adoption endpoint guard reads the module from its new place. This is the conversion step between Crossplane 1.20 (CLD-062, merged) and Crossplane 2.4 (CLD-065), which no longer has Resources mode.

# NET-153 — Allow-list of the hand-over proof's deny-egress object

## In plain words

**The problem today.** During the sovereignty proof every public destination is denied, and only a short list of internal ranges stays open. That list comes from a chart default that holds the pod ranges of two regions only. On a Sovereign with three or more regions, the pods of the third region lose each other and the cluster DNS for the length of the hold, so the proof fails or proves nothing.

**What changes.** The kit slot of the cutover sets the list from the Sovereign's own variables: the pod supernet that holds the pod range of every region, and the one service range that holds the service range of every region. The deny-egress object and its other allow lists keep their shape.

**Done means:**

- A Sovereign with one or two regions keeps 10.42.0.0/15 and 10.96.0.0/12 open during the hold, and one with three to six regions keeps 10.40.0.0/13 and 10.96.0.0/12 open.
- The open pod range is read from the variable that first boot writes for native routing, so the hold and Cilium always name the same range.
- The cloud API ranges of the hold still come from the variable that first boot writes for them, unchanged.
- The kit still renders with both value sets and leaves no placeholder unsubstituted.
- The network guards pass, and the deny-egress object of the proof is still their only named exception owned by this package.

The rest of this ticket is the exact instruction for the model that does the work.

## 2. End goal
During cutover step 08 (`egress-block-test`) the Job applies a default-deny `CiliumClusterwideNetworkPolicy` to every region and keeps open only the ranges of its environment variable `ALLOW_CIDRS`, the cloud API ranges of `PROVIDER_API_CIDRS` and, on secondary regions, a few more. `ALLOW_CIDRS` is the chart value `egressTest.allowIntraClusterCIDRs`. After this ticket the bootstrap-kit slot `clusters/_template/bootstrap-kit/06a-bp-self-sovereign-cutover.yaml` sets that value to two ranges: `${CILIUM_NATIVE_ROUTING_CIDR}`, the pod supernet of the Sovereign that first boot writes into the ConfigMap `flux-system/sovereign-variables` (NET-110), and `10.96.0.0/12`, the range that holds the service range of every region. The chart default (`10.42.0.0/16`, `10.43.0.0/16`, `10.96.0.0/12`) is no longer used by any Sovereign installed from the kit. A person sees this in the pull request: acceptance A1 renders the slot with the kit's values once for two regions and once for three, renders the step-08 Job of the chart from the result, and finds `ALLOW_CIDRS` equal to `10.42.0.0/15 10.96.0.0/12` and `10.40.0.0/13 10.96.0.0/12`.

## 3. The model (the law)
1. Under `spec.values.egressTest` of the HelmRelease `bp-self-sovereign-cutover` in `clusters/_template/bootstrap-kit/06a-bp-self-sovereign-cutover.yaml`, `allowIntraClusterCIDRs` is the list of exactly two strings, in this order: `"${CILIUM_NATIVE_ROUTING_CIDR}"` and `"10.96.0.0/12"`. Both are quoted, so an empty substitution stays an empty string and never becomes a null item.
2. The pod range comes from the kit key `CILIUM_NATIVE_ROUTING_CIDR` and has no default, as in slot 01. It is the pod supernet: `10.42.0.0/15` for one or two regions, `10.40.0.0/13` for three to six. Each region's pod range `10.(42+index).0.0/16` lies inside it.
3. The service range is the one literal `10.96.0.0/12`. Each region's service range is `10.(96+index).0.0/16` and a Sovereign has at most six regions, so every service range (`10.96` to `10.101`) lies inside it, and with it the address of the API server, `10.96.0.1` in the first region. No kit key holds a service range, and this package adds none.
4. The other values of `egressTest` stay as they are: `enforceCIDRBlock: true`, `allowProviderCIDRs: ${PROVIDER_API_CIDRS_YAML:=[]}` (the cloud API ranges) and `localRegistryHostSubstr`. `secondaryRegions.extraEgressAllowCIDRs` is not set by the slot, as before.
5. The deny-egress object keeps its shape: no file of the chart changes, so the policy the Job applies differs only in the ranges of `ALLOW_CIDRS`.
6. The deny-egress object stays a named exception of network guard G2: the line of `scripts/network-guards-exceptions.tsv` that names `platform/self-sovereign-cutover/chart/templates/08-egress-block-test-job.yaml` with owner `NET-153` stays, and `python3 scripts/check-network-guards.py check` passes.
7. The comment above the new key names no cloud provider.
8. A Sovereign installed before NET-110 has no key `CILIUM_NATIVE_ROUTING_CIDR`. There the first range is the empty string, the Job drops it when it splits the list, and the hold denies pod-to-pod traffic: the proof fails and is not passed falsely. Slot 01 already needs the same key on such a Sovereign; the architect adds it. That is not a step of this ticket.

# SOV-721 — The kit's k3s moves to v1.31.14+k3s1, whose node mirror gives up on a peer that does not answer

## In plain words

**The problem today.** A node pulls an image first through the mirror the nodes share, then from the registry. On the k3s release the kit installs today the mirror puts no time limit on a request to a peer: a peer that accepts a connection and never answers holds the pull until the container runtime gives up after five minutes, and the pull then fails instead of trying the registry. A fresh install stopped this way when one peer sat behind a path that lost its large packets.

**What changes.** The kit installs k3s v1.31.14+k3s1, whose mirror gives up on a peer after one or two seconds per request and goes on to the registry. The registry-drain harness gets a case that reproduces such a peer and a control that shows the old release still hanging.

**Done means:**

- A new Sovereign on any provider module installs k3s v1.31.14+k3s1; the provisioner, the contract fixtures, the module tests and the goldens say the same version.
- The image list that the release v1.31.14+k3s1 publishes is kept in the repository beside the old one, as published.
- The harness self-test passes ten cases, and the dry runs show that case silent-peer runs the kit's k3s and case silent-peer-control runs v1.31.8+k3s1.
- In CI, a pull through a peer that drops its large packets finishes from the registry within 60 seconds on the new release, and is still waiting at 120 seconds on the old one.
- The two workflows that start a k3s server on a runner, the intent lock and the bootstrap flags, start the new release.

The rest of this ticket is the exact instruction for the model that does the work.

3. The workflows that start a k3s server on a runner start the kit's release: `intent-lock-apiserver` by the tag `v1.31.14-k3s1`, `tests/e2e/k3s-bootstrap-flags.sh` by that tag and the digest of its multi-platform index.
4. The harness reads the kit, it does not restate it. Case `silent-peer` runs the kit's k3s and flags; case `silent-peer-control` runs the same with k3s `v1.31.8+k3s1` (the script's constant `SILENT_CONTROL_K3S`) and the image list of that release. The registry runs on rd-agent-2 and rd-agent-1 takes the probe from it. A witness first proves the peer path: with no copy of the registry, rd-agent-2 takes the probe from rd-agent-1 through the nodes' mirror, then removes it. rd-agent-1 restarts (every connection the witness left open closes), its path MTU probing is turned off, and its registry port drops every outgoing packet of 1421 bytes or more. A TLS probe from the runner must complete a handshake before the drop and none within 10 seconds after it, or the case fails: the defect is then not reproduced.
5. Judgement: `silent-peer` passes a pull that finished within 60 seconds and a registry log that served the probe's manifest at least once. `silent-peer-control` passes a pull still running at 120 seconds; a pull that finishes there fails the run, because the harness then cannot see the defect.
6. The self-test has one case per new rule: the TLS judge (passes no handshake within the limit; fails a handshake, a refusal and a connect that never happened), the pull judge (passes the two good outcomes, fails six bad ones), and the dry runs of the two cases (the kit's version and the control's, each with its image list). Ten cases in all, no Docker.
7. Every wait stays bounded; a hang fails its case by name. No port is published, no NodePort and no hostPort. The cases run only in CI (privileged containers, `sudo iptables`, `sudo nsenter`).
8. Nothing is deleted.

# SOV-721 — The kit's k3s moves to v1.33.13+k3s2, whose node mirror serves imported images to its peers and gives up on a peer that does not answer

## In plain words

**The problem today.** A node pulls an image first through the mirror the nodes share, then from the registry. On the k3s release the kit installs today the mirror puts no time limit on a request to a peer, so a peer that accepts a connection and never answers holds a pull until the container runtime gives up after five minutes. The one later release of the same line bounds those requests but no longer offers imported images to the other nodes, so no release of that line passes both proofs.

**What changes.** The kit installs k3s v1.33.13+k3s2, whose mirror offers imported images to its peers and gives up on a silent peer and goes on to the registry. The registry-drain harness gets a case that reproduces such a peer, with a control that shows the old release still hanging and a witness that counts what the pulling node sends to the peer.

**Done means:**

- A new Sovereign on any provider module installs k3s v1.33.13+k3s2; the provisioner, the contract fixtures, the module tests and the goldens say the same version.
- The image list that the release v1.33.13+k3s2 publishes is kept in the repository beside the old one, as published.
- The harness self-test passes ten cases, and the dry runs show that case silent-peer runs the kit's k3s and case silent-peer-control runs v1.31.8+k3s1.
- In CI all seven registry-drain cases pass: the shared case recovers on the new release, a pull through a peer that never answers finishes from the registry within 60 seconds, and on the old release it is still waiting at 120 seconds.
- The workflows that start k3s on a runner start the new release, and the suite image carries kubectl v1.33.13, checked against its published checksum.
- No running cluster changes: the default reaches new installs only.

The rest of this ticket is the exact instruction for the model that does the work.

5. The harness reads the kit, it does not restate it. Case `silent-peer` runs the kit's k3s and flags; case `silent-peer-control` runs the same with k3s `v1.31.8+k3s1` (the script's constant `SILENT_CONTROL_K3S`) and the image list of that release. The registry runs on rd-agent-2 and rd-agent-1 takes the probe from it. A witness first proves the peer path: with no copy of the registry, rd-agent-2 takes the probe from rd-agent-1 through the nodes' mirror, then removes it. Then rd-agent-1's registry port sends nothing after its SYN-ACK, on every connection, by a rule in the raw table ahead of every rule k3s writes. A TLS probe from the runner must complete a handshake before that rule and none within 10 seconds after it, or the case fails: the defect is then not reproduced.
6. The witness of the measured pull counts the data packets rd-agent-2 sends to the silent port (100 bytes or more), not its SYNs: the node mirror of v1.33.13+k3s2 keeps the connection of the witness pull open, so the measured pull may send its request with no new SYN (lab test SOV-722, `docs/ledger/plan/spikes/SOV-722.md`). A pull with no such packet fails: the mirror never asked the silent peer.
7. Judgement: `silent-peer` passes a pull that finished within 60 seconds and a registry log that served the probe's manifest at least once. `silent-peer-control` passes a pull still running at 120 seconds; a pull that finishes there fails the run, because the harness then cannot see the defect.
8. The self-test has one case per new rule: the TLS judge (passes no handshake within the limit; fails a handshake, a refusal and a connect that never happened), the pull judge (passes the two good outcomes, fails six bad ones), and the dry runs of the two cases (the kit's version and the control's, each with its image list). Ten cases in all, no Docker.
9. Every wait stays bounded; a hang fails its case by name. No port is published, no NodePort and no hostPort. The cases run only in CI (privileged containers, `sudo iptables`, `sudo nsenter`).
10. Nothing upgrades a running cluster in place: the default applies to new installs only. Nothing is deleted.

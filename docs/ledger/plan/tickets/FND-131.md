# FND-131 — A run without journeys asserts only what the pack holds: discovery of the journey objects is left out, and the scope check is a cloud check

## In plain words

**The problem today.** The acceptance suite always looks up three things that only its journeys use: the own Organization of the Sovereign, the Environment of that Organization over both regions, and the Blueprint that the journeys install. A run that asks for no journey still looks them up. Where one of them does not exist, as on the local provider pack, that run fails in its discovery and then runs none of its gate checks.

**What changes.** A run that asks for no journey no longer looks the three up. It goes on with the discovery steps that every run needs and with its gate checks, and its record says which three steps were left out. A run that asks for a journey, and a discover run, look them up as before.

**Done means:**

- A run that asks for no journey passes its discovery on a Sovereign that has no own Organization.
- The record of such a run holds no step for the three lookups, neither as passed nor as skipped, and lists the three under the key discovery_not_requested of its subject.
- A run that asks for a journey still fails at the Organization lookup when the Organization is missing.
- A discover run still does all three lookups.
- Five new tests of the suite prove these cases, and every older test of the suite still passes.

The rest of this ticket is the exact instruction for the model that does the work.

## 2. End goal
A run of the acceptance suite in `tests/acceptance/sovereign` that requests no journey does not run the three discovery steps that only the journeys need: D0.3 (the Sovereign's own Organization), D0.4 (the Environment of that Organization over both regions) and D0.5 (the Blueprint). Such a run goes on with the discovery steps that every run needs (D0.1, D0.2, D0.6, D0.10) and with the gate checks. Its record holds no step for the three and names them in the list `discovery_not_requested` of its `subject`. A run that requests a journey, and a `discover` run, do exactly what they do today. A person sees it in five new tests of the suite, and later in the record of the first run without journeys.

This ticket does the first half of its title. The second half, "the scope check is a cloud check", is one line of `docs/ledger/gates.yaml` that a work package may not change. The architect changes it in a plan pull request (field 11).

## 3. The model (the law)
1. A run is of one of three kinds. A discover run: the binary was started with `discover` (`Config.ReadOnly` is true). A run with a journey: started with `run`, and the list of `--journeys` holds at least one entry that is not blank. A run without a journey: started with `run`, and the list holds no entry that is not blank.
2. Only a run without a journey changes. It does not run D0.3, D0.4 and D0.5. It runs D0.1, D0.2, D0.6 and D0.10, the gate checks, and in the cloud D0.11, as before.
3. A step that was not run gets no entry in the list `steps` of the record. It is not PASS: nothing was measured. It is not SKIP: a step of the discovery that is not PASS fails the run, and that rule stays.
4. Each step that was not run is named instead. Its identifier is appended to the list `discovery_not_requested` of the record's `subject`, in the order D0.3, D0.4, D0.5, and one line of the output says `not requested: the run requests no journey`.
5. The subject of a run without a journey holds no key `org`, `environment` or `blueprint`: the steps that write them did not run.
6. A discover run and a run with a journey record the same steps, in the same order, with the same evidence as today. Their subject holds no key `discovery_not_requested`.
7. The decision is taken in one place. `Execute` sets the field `noJourney` of the runner before the discovery, and the new method `journeyStep` reads it. The zero value of the field is false, so a runner that a test builds by hand runs every step.
8. `Finalize` in `result.go` is not changed. A step of the discovery that is not PASS still fails the run, and a requested journey that is not PASS still fails the run.
9. There is no new flag, no new environment variable and no mode variable. The record gets no new field: `subject` is a free object already.
10. Nothing is deleted.

// stepLine prints the steps of a run as "<journey> <id> <status>", in order.
func stepLine(run *Run) string {
	parts := []string{}
	for _, s := range run.Steps {
		parts = append(parts, s.Journey+" "+s.ID+" "+s.Status)
	}
	return strings.Join(parts, ", ")
}

// discoverOn runs the discovery of a run against a console. It returns the

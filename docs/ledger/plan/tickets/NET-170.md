# NET-170 — Organization fence: two host-side deny objects for the Organization's own pods

## In plain words

**The problem today.** The host namespace of an Organization has one host-side policy, and it only allows traffic. It lets every pod there reach the cluster API, and a policy that the Organization syncs out of its virtual cluster can open a way to other Organizations and to platform namespaces. The same policy also admits traffic from the node itself into every pod of the Organization.

**What changes.** Every Organization gets two host-side deny objects that fence the pods synced out of its virtual cluster, and a controller flag names the namespaces those pods may still reach. The host-side policy admits the gateway entities only.

**Done means:**

- The controller writes org-fence and org-fence-api into the host-side files of every Organization, in the shared tree and in its region copy.
- Both objects select only the pods the virtual cluster syncer wrote that are not session pods, so the platform stack in the namespace keeps its own policies.
- Each deny selector requires the namespace label and the cluster label, so it also reaches pods of the peer region and never a reserved identity.
- The flag --org-fence-allow-namespaces, default kube-system,keycloak, names the namespaces the egress deny exempts, and an invalid value stops the controller at start.
- The host-side policy of every Organization admits the entities ingress and remote-node and no longer host.
- A test fails when either object, its selector, its terms or the flag value differs from the specification.

The rest of this ticket is the exact instruction for the model that does the work.

## 2. End goal
For every Organization, the organization controller commits two more files into the host-side tree of the Organization's repository, `vcluster/host-apps/org-fence.yaml` and `vcluster/host-apps/org-fence-api.yaml`, and the same two files into the region copy `vcluster/region-baseline/host-apps/`. Both trees are applied by Flux to the Organization's host namespace `<slug>`. The two `CiliumNetworkPolicy` objects deny, for the pods that the virtual cluster syncer wrote into that namespace: ingress from any namespace but `<slug>` and `flux-system`; egress to any namespace but `<slug>` and the namespaces of the new controller flag `--org-fence-allow-namespaces` (default `kube-system,keycloak`); egress to the entities `host` and `remote-node`; and egress to the entity `kube-apiserver`. A deny rule wins over every allow rule in Cilium, and an Organization cannot change a host-side object, so nothing the Organization syncs can widen the fence. The existing host-side policy `allow-gateway-and-apiserver` stops admitting the entity `host`. The proof on a running environment is the gate check NET-G07, which NET-172 builds; this ticket flips nothing.

## 3. The model (the law)
1. Two new templates in `core/controllers/organization/internal/gitops/manifests.go`, `orgFenceTemplate` (file `org-fence.yaml`, object `org-fence`) and `orgFenceAPITemplate` (file `org-fence-api.yaml`, object `org-fence-api`). Both are `apiVersion: cilium.io/v2`, `kind: CiliumNetworkPolicy`, `namespace: {{ .AppNamespace }}` (the value `apps`, which the host-apps Flux Kustomization rewrites to `<slug>` by its `targetNamespace`, as for the existing host-side policy), and carry the labels `openova.io/organization: <slug>`, `openova.io/managed-by: catalyst`, `catalyst.openova.io/component: org-fence`.
2. The endpoint selector of both objects is exactly two terms: `{key: vcluster.loft.sh/managed-by, operator: Exists}` and `{key: access.openova.io/session, operator: DoesNotExist}`. The platform stack of the namespace and `vcluster-0` carry no `vcluster.loft.sh/managed-by` label and are not selected. Both objects set `enableDefaultDeny: {ingress: false, egress: false}` and have no allow section (`ingress`, `egress`).
3. `org-fence` has one `ingressDeny` rule with one `fromEndpoints` selector of three terms, in this order: `{key: k8s:io.kubernetes.pod.namespace, operator: Exists}`, `{key: io.cilium.k8s.policy.cluster, operator: Exists}`, `{key: k8s:io.kubernetes.pod.namespace, operator: NotIn, values: ["<slug>", "flux-system"]}`. It has two `egressDeny` rules: a `toEndpoints` selector of the same three terms with `values: ["<slug>", <each namespace of OrgFenceAllowNamespaces, in flag order>]`, and `toEntities: [host, remote-node]`. The two Exists terms name the namespace key and the cluster key, so Cilium does not narrow the selector to the policy's own namespace or to the local cluster, and a reserved identity (which carries neither label) is never denied. This is the form of `platform/postgres/chart/templates/dr-failback.yaml` lines 292-318.
4. `org-fence-api` has one `egressDeny` rule, `toEntities: [kube-apiserver]`, and no `ingressDeny`.
5. Neither object names the entity `world`, a `toCIDR`, a `toFQDNs` or the label `app: vcluster`. The fence denies no internet egress.
6. `Inputs` gains `OrgFenceAllowNamespaces []string`. `Render` sets it to `kube-system`, `keycloak` when it is empty. The constant `DefaultOrgFenceAllowNamespaces = "kube-system,keycloak"` and the function `ParseOrgFenceAllowNamespaces(value string) ([]string, error)` live in `manifests.go`: the function splits at commas, trims spaces, skips empty entries, refuses an entry that is not an RFC 1123 label (`k8s.io/apimachinery/pkg/util/validation.IsDNS1123Label`), and refuses a value that names no namespace.
7. `Render` adds both files under `vcluster/host-apps/`, and `vcluster/host-apps/kustomization.yaml` lists `org-fence.yaml` and `org-fence-api.yaml` with the two existing entries. `addRegionBaselineTrees` copies them into `vcluster/region-baseline/host-apps/` without a change of its own.
8. The host-side policy `allow-gateway-and-apiserver` lists the ingress entities `ingress` and `remote-node`; the line `- host` is deleted. Its comment says why `remote-node` stays: the gateway of the peer region reaches a pod as `remote-node` (`platform/newapi/chart/templates/crossregion-netpol.yaml` lines 26-37). Every other rule of that policy stays as it is.
9. `core/controllers/organization/cmd/main.go` registers the flag `--org-fence-allow-namespaces` with the default `gitops.DefaultOrgFenceAllowNamespaces`, parses it with `gitops.ParseOrgFenceAllowNamespaces` right after the logger is set up, exits with code 1 and the log message `invalid --org-fence-allow-namespaces` on an error, and passes the result to `Reconciler.OrgFenceAllowNamespaces`. `organization_controller.go` passes that field to `gitops.Render`.
10. The controller Deployment template passes the argument `--org-fence-allow-namespaces=kube-system,keycloak`.
11. Not done, by decision: no exemption for `app=vcluster`, no change to the API-server egress rule of the host-side policy, no change to `docs/ledger/gates.yaml`, no suite file.

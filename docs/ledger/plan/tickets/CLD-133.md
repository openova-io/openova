# CLD-133 — Secondary-region suspend keys are set for every provider

## In plain words

**The problem today.** On a Sovereign with two regions, the secondary control plane must keep the primary-only parts of the platform (the console umbrella and the slots that follow it) suspended, and run the edge that forwards the console hosts to the primary. The two switches that say so were written only by the reference cloud's own list of settings. A secondary control plane of the second provider never received them, fell back to the defaults and ran the primary-only parts in both regions.

**What changes.** The shared start-up template writes both switches for every control plane, computed from its region role. The reference cloud and the local pack stop writing their own copies, so each key is written once.

**Done means:**

- Every control plane of every provider receives SECONDARY_HR_SUSPEND and SECONDARY_EDGE_SUSPEND: false and true in the primary region, true and false in a secondary region.
- No provider pack sets either key itself; each key appears once in the settings a control plane receives.
- The reference cloud's control planes receive the same keys with the same values as before; only the place of the two keys in the list moves.
- Every file that first boot writes is unchanged except the Flux bootstrap document, and the worst-case start-up data stays within every cloud's limit.
- The render test of the shared template, the tests of the three provider modules and the size check pass.

The rest of this ticket is the exact instruction for the model that does the work.

## 2. End goal
The ConfigMap `flux-system/sovereign-variables` that the shared control-plane template `infra/providers/_shared/cloudinit-control-plane.tftpl` writes carries `SECONDARY_HR_SUSPEND` and `SECONDARY_EDGE_SUSPEND` for every provider, computed in the template's shared substitute list from the input `sovereign_region_role`, exactly as the reference pack's substitutes file computed them: `"false"`/`"true"` on the primary control plane, `"true"`/`"false"` on a secondary one. The reference pack's `infra/providers/huawei/provider-substitutes.yaml.tftpl` and the local pack's `infra/providers/local/main.tf` no longer set them, and the reference module no longer passes the region role to its substitutes file, which no longer reads it. A person can observe it in the worst-case render of the size check: the second provider's secondary control plane now carries `SECONDARY_HR_SUSPEND: "true"` and `SECONDARY_EDGE_SUSPEND: "false"`, and the reference cloud's ConfigMap holds the same keys and values as before.

## 3. The model (the law)
1. A substitute that depends only on an input every provider passes is computed once, in the shared list of the template. `sovereign_region_role` is passed by every module (`infra/providers/hetzner/main.tf`, `infra/providers/huawei/main.tf`, `infra/providers/local/main.tf`).
2. The two expressions are those of the reference pack, character for character: `SECONDARY_HR_SUSPEND: "${sovereign_region_role == "primary" ? "false" : "true"}"` and `SECONDARY_EDGE_SUSPEND: "${sovereign_region_role == "primary" ? "true" : "false"}"`. They stand directly after `SOVEREIGN_REGION_ROLE`, with the indentation of the list (twelve spaces).
3. Each key is written once into the ConfigMap: the reference pack's substitutes file and the local pack's `pack_substitutes` lose their copies (the local module inserts its keys into the same ConfigMap, so a copy there would be a duplicate key).
4. The reference pack's substitutes file reads no `sovereign_region_role` afterwards, so its `templatefile` call in `infra/providers/huawei/main.tf` stops passing it.
5. Nothing is packed differently and no limit changes. The comment that explains the keys is a comment line of the template, which the template drops before it packs the Flux document, so it costs no byte.
6. The reference cloud's ConfigMap keeps the same set of keys with the same values; the two keys only move from after `SOVEREIGN_CNPG_STORAGE_CLASS` to after `SOVEREIGN_REGION_ROLE`. The order of the keys of a ConfigMap's data has no meaning to Flux, but it is part of the bytes, so the reference cloud's two golden hashes (`golden_huawei` and its `flux-bootstrap.yaml` file hash) change too. No other file hash changes.

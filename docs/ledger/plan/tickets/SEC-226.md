# SEC-226 — A library value is seeded from the Secret that holds it today

## In plain words

**The problem today.** A chart that moves a value it holds today into the secrets library cannot say where that value is. On a Sovereign that already runs the chart, the birth Job finds the store's path empty and writes a new random value, so data encrypted under the old key, or a server that still holds the old password, stops working.

**What changes.** A mounted value can name the Secret and key that hold it today. The birth Job carries that value into the store once, generates a value only when no such Secret exists, and leaves a value the store already holds alone.

**Done means:**

- A mounted value that names an existing Secret is born with that Secret's value, in its own region and, when shared, in the peer region too.
- On a fresh install, where the named Secret does not exist, the value is a new random value of the stated length (43 characters in the test).
- A value the store already holds is kept even when the named Secret holds another value, and that Secret is not read.
- A named Secret without the named key fails the birth Job before anything is written, and no random value takes its place.
- The Job reads the Secret as its own service account, through a Role that grants get on the named Secrets and nothing else, and the value appears in no log line, argument or environment variable.
- The console chart and the Axon chart, the two charts that use the library today, render byte for byte what they rendered before.

The rest of this ticket is the exact instruction for the model that does the work.

## 2. End goal
A chart that declares a mounted value in `generatedSecrets` can name, with `seedFrom: {name, key}`, the Secret of the value's namespace that holds the value today. On a Sovereign that already runs the chart, the birth Job writes that Secret's key into the store's path the first time the path is absent; on a fresh install, where the Secret does not exist, it writes a new random value of the stated length; a value the store already holds is never read against the Secret and never replaced. The first user is SEC-246: the chargeback master key, mounted as a file, length 43 on a fresh install, so no stored credential becomes undecryptable when the chart moves to the library. A synced value with `seedFrom` is refused at render: the synced form is the second piece of this story (field 11). A chart without `seedFrom` renders exactly what it rendered before.

## 3. The model (the law)
1. `seedFrom` is a map of exactly `name` (a Secret name: at most 253 characters, `[a-z0-9]([-a-z0-9.]*[a-z0-9])?`) and `key` (a Secret key, `[-._a-zA-Z0-9]+`), on a mounted value that is not a placeholder. It names a Secret of the value's namespace: the library's `namespace` input when given, else the release namespace.
2. The birth plan line of a seeded value carries the source `seed:<name>/<key>` in place of `-`. Every other field of the line is as before.
3. Before anything is written, for each seeded line whose path is absent in this region, the Job reads the Secret. An answer 200 with the key and a value that is not empty and is printable ASCII passes; 404 passes (the value will be random); every other answer (403 too), a Secret without the key, an empty value and a value that is not printable ASCII end the run with exit 1 and nothing written, never a random value.
4. Write: a path that is absent gets the Secret's value when the Secret exists, else a new random value of `length` and `symbols`; reach `all` writes the same value to every peer. A path that holds a value keeps it and its Secret is not read. A second run writes and reads nothing.
5. The identity that reads: the Job's ServiceAccount `secrets-birth` of the value's namespace, with a projected token of the Kubernetes API's audience (`expirationSeconds: 600`) and the cluster CA from ConfigMap `kube-root-ca.crt`, both in a volume mounted at `/var/run/secrets/openova-birth-kube`. Role `secrets-birth-seed` grants `get` on `secrets` with `resourceNames` exactly the Secrets the plan names (unique, sorted), nothing else; RoleBinding `secrets-birth-seed` binds it to `secrets-birth`. The Job's environment gains `KUBE_API` (`https://kubernetes.default.svc`), `KUBE_NAMESPACE` and `KUBE_DIR`, which name places, never a value. All of this renders only when the plan has a seed.
6. The value passes only through pipes and the Job's private memory directory (`WORK_DIR`): never a process argument, an environment variable or a log line.
7. `seedFrom` on a synced value fails the render: its PushSecret reads one source and has no fallback.
8. Without `seedFrom` every object and the birth script are what the library rendered before, byte for byte (the seed functions of the script render only for a plan with a seed). No chart version line changes: the library stays at version 0.1.0.
9. Raising the epoch of a seeded value writes the Secret's value again at the new path while that Secret exists; to rotate, the chart drops `seedFrom` with the raise (README).

# FND-043 — An acceptance loop of a ticket stops at its first failing pass

## In plain words

**The problem today.** An acceptance command passes when it exits 0. A loop has the status of its last pass only, so a loop that checks three files can pass when the first two checks fail: one merged ticket checked three baseline entries that way. The guard of the acceptance commands reads pipes, not loops.

**What changes.** The guard also fails on a loop of an acceptance command whose body does not stop the command at a failing pass. A loop that stops at its first failing pass, also a nested one, still passes.

**Done means:**

- An acceptance command with a for, while or until loop whose body does not end a failing pass with exit 1 turns the pull request red and is named with its ticket and item.
- An exit with another code, an exit inside a subshell and an exit 1 under an if do not count as stopping the loop.
- A loop whose body stops on failure with || exit 1, also inside a group after ||, a nested loop or an if, passes.
- The two merged tickets whose loops the rule refuses are findings without their done markers and are not judged with them.
- The guard passes on the tickets of the repository that are not merged, and its own tests fail when the loop rule is taken out.

## 2. End goal
The guard `tools/guards/cmd/acceptance-exit`, which two steps of `.github/workflows/tree-guards.yaml` already run on every pull request, gets a second rule: a `for`, `while` or `until` loop of an acceptance command must hold `|| exit 1` (or `|| { ...; exit 1; }`) in its body, in the shell of the loop, so that the command stops at the loop's first failing pass. A person sees it in `cd tools/guards && go run ./cmd/acceptance-exit`, which prints `acceptance-exit: the acceptance commands of the <n> tickets not merged (of <m>) lose the status of no piped tested command and of no loop pass` and exits 0 on the repository, and which prints `FAIL docs/ledger/plan/tickets/<ID>.md A4 loop: a for loop whose body holds no ...` and exits 1 when a command breaks the rule.

## 3. The model (the law)
1. **The loop rule.** A `for`, `while` or `until` loop is a finding unless its body (after `do`, before `done`) holds `exit 1` right after `||` (newlines between them allowed), or `exit 1` inside a `{ ...; }` group that directly follows `||`. Only the word `exit`, unquoted, followed by the bare word `1` counts.
2. **What does not count.** `|| exit 0`, `|| exit 10`, `|| { ...; exit 2; }`, `&& exit 1`, a quoted `'exit' 1`, `{ ...; exit 1; }` not after `||`, `if ! ...; then exit 1; fi`, an `exit 1` in the loop's condition (before `do`), and an `exit 1` inside a subshell `( )`, a command substitution `$( )` or a process substitution `<( )`: such an exit leaves only that subshell.
3. **Nesting.** An `exit 1` of the rule ends the whole shell, so it counts for every loop of that shell around it: in a nested loop, an `if` or a group it stops each enclosing loop. An inner loop without one is its own finding, and an outer loop whose only exit is after the inner `done` (`for ...; do for ...; done || exit 1; done`) is still a finding for the inner loop.
4. **Command substitutions.** As for the pipe rule: a loop inside `$( )` is judged only when a variable is assigned the substitution (`out="$(for ...; done)"`), whose status the assignment has; as the argument of a command its status is lost either way, and it is not a finding.
5. **Position does not matter.** Under `bash -euo pipefail -c` a loop that stands as its own command stops at its first failing pass by errexit, and a loop in front of `&&` or `||`, in a condition or after `!` does not. The rule refuses every loop without the exit: the same command must keep its status in every position and under a plain `bash -c`.
6. **Unchanged.** The pipe rule, the findings for a command the guard cannot read and for an item with no command, the reading of field 18, the done markers that keep a merged ticket from being judged, and the exit codes 0, 1 and 2 stay as they are. Only the closing lines name the new rule.
7. **Go, not Python.** The rule is Go in the same command (standard library only); `scripts/ticket-lint.py` does not grow.

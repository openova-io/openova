# FND-157 — A gate run reads the storefront's sign-in code from a mailbox on the Sovereign under test

## In plain words

**The problem today.** The storefront check of the acceptance gate signs a new customer in with a code that is mailed to them. It can only read that code from a mailbox whose server, login and password the gate run is given from outside, and no run has one, so the check stops at its first step. A Sovereign now runs its own mail server, but nothing on it holds a mailbox the gate can read.

**What changes.** The Sovereign's mail server makes a mailbox for the gate, with a password made and kept inside the cluster. The storefront check reads its sign-in code from that mailbox when the run is given no other one, through the cluster's own API, so no person's mailbox and no password outside the cluster is needed.

**Done means:**

- On a Sovereign with its own mail server, the setup Job makes the gate's mailbox and keeps its password only in a Secret in the cluster, written after the mail server has confirmed the mailbox, and never replaced.
- Running the setup Job again keeps the same password, and a failed step leaves no Secret that the server does not know.
- When the run is given no mailbox, the storefront check finds that Secret in the region that holds it, reads the code through a port forward of that region with the server's certificate checked, and signs in a new address of the mailbox per run.
- The password appears in no record, log or evidence of the run.
- The chart test proves each rule of the new Job step and fails when one of them is broken; the earlier chart test still passes with all its rules.

The rest of this ticket is the exact instruction for the model that does the work.

## 2. End goal
On a Sovereign whose mail server is installed (bootstrap-kit slot 95, chart `platform/stalwart-sovereign`, namespace `platform`), the setup Job makes the principal `conformance` with the one address `conformance@<fqdn>` and a password it generates from `/dev/urandom`, reads it back, and only then creates the Secret `platform/stalwart-sovereign-conformance` with the keys `address`, `user`, `password`, `imap-host`, `imap-service` and `imap-port`. A later run takes the password from that Secret and never replaces it. Gate check BSS-G01, when none of `BSS_GATE_MAILBOX_IMAP`, `BSS_GATE_MAILBOX_USER`, `BSS_GATE_MAILBOX_PASSWORD` and `BSS_GATE_MAILBOX_ADDRESS` is set, reads that Secret with the kubeconfig of the region that holds it, starts `kubectl port-forward` to the Service and port the Secret names for each read of the mailbox, checks the server's certificate against `mail.<fqdn>`, and signs its new customer in as `conformance+<run>@<fqdn>`, which the server delivers into the same INBOX. With all four variables set it reads the gate lane's mailbox as before.

## 3. The model (the law)
1. The password of the gate's mailbox is made inside the cluster, by the setup Job, and is kept only in the Secret `<release namespace>/<conformanceMailbox.secretName>`. It is never printed, never in a Helm value, never in evidence or a log of the suite.
2. The Secret is created only after the server has confirmed the principal with that password (read back after the write). It is created once and never replaced: a later run reads the password from it and sets the principal to it. A run that finds no Secret makes a new password and sets the principal to it before it creates the Secret.
3. The principal has the one address `<user>@<fqdn>`. The server's file does not set `sub-addressing`; release v0.15.5 then delivers `<user>+<tag>@<fqdn>` into that principal's INBOX (field 4 item 6).
4. The new Job step runs after the mirror Secret is written and before the DKIM write-back, so the sign-in mail of the console never waits for it. Every answer of the server is judged by its body, as the other steps do. A failure exits 1 and the Job retries.
5. The Job may create a Secret in the release namespace and read the mailbox's Secret by name; it may not update, patch, delete, list or watch a Secret there. With `conformanceMailbox.user` empty, the Job makes no call about the mailbox and has no right to create a Secret.
6. BSS-G01 takes the gate lane's mailbox when all four `BSS_GATE_MAILBOX_*` are set, the Sovereign's when none is set, and fails at step 1 with no request when some but not all are set or when no region holds the Secret.
7. The suite reaches the server only through the region's API server (`kubectl port-forward service/<imap-service> :<imap-port>`, the helper `portForward` that check ISO-G01 uses). No Service, NodePort or address is created. The certificate is checked against `imap-host`, not against the local address.
8. The suite records the Secret's place, the region, the Service and the address in evidence, never the password or its base64.
9. No Python is added. The chart test is shell, the suite code is Go.

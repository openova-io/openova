# SOV-336 — The registry install creates the proxy project of the vulnerability database

## In plain words

**The problem today.** Each region's registry is set up at install with hosted projects only. The vulnerability scanner needs its database from the region's own registry, and nothing in that registry can fetch the database from the parent. After hand-over the scanner has no source for a fresh database.

**What changes.** At install the registry gets one pull-through project, named by the first part of the database path in the variables document, that fetches through the parent's registry. A region whose variables name no parent registry gets no such project.

**Done means:**

- The install Job of a region whose variables name a parent registry creates an endpoint to that registry and a public pull-through project for the database on it.
- A second run of the Job changes nothing and passes.
- An existing endpoint that points elsewhere, or an existing database project that is not a pull-through project of that endpoint, fails the Job with its name.
- A region whose variables name no parent registry gets neither the endpoint nor the project, and the other projects stay exactly as before.
- A database path whose project is also a hosted project, or a scheme other than https and http, refuses to render.

The rest of this ticket is the exact instruction for the model that does the work.

1. New chart values under `registryProjects` of `platform/harbor/chart/values.yaml`: `vulnDBPath` (default `proxy-vulndb/aquasecurity/trivy-db`, the contract default of `REGISTRY_PATH_VULN_DB`), `origin.host` (default empty) and `origin.scheme` (default `https`).
2. Slot 19 passes them from contract C5: `vulnDBPath: ${REGISTRY_PATH_VULN_DB:=proxy-vulndb/aquasecurity/trivy-db}`, `origin.host: ${ORIGIN_REGISTRY_HOST:=}`, `origin.scheme: ${ORIGIN_REGISTRY_SCHEME:=https}`. `ORIGIN_REGISTRY_HOST` has no contract default, so a Sovereign whose variables carry no contract keys renders an empty host.
3. Render rule: the database project is the first path segment of `vulnDBPath`, and it exists only when `origin.host` is not empty and that segment is not empty. Otherwise the Job is rendered with `VULNDB_PROJECT` and `VULNDB_ORIGIN_URL` empty and makes no endpoint and no project. An empty host is allowed by the contract only for a Sovereign fed by offline bundles; such a region has no origin to pull through.
4. `origin.scheme` must be `https` or `http` (the enum of `ORIGIN_REGISTRY_SCHEME`); any other value fails the render with `registryProjects.origin.scheme must be https or http`. The check runs on every render.
5. The database project must not also be a hosted project of the Job (a first segment of a proxy-projects path or of the five `paths`); that fails the render with `registryProjects.vulnDBPath: the project <name> is also a hosted project`.
6. The endpoint is named `<project>-origin`, has type `docker-registry`, `insecure: false` and no credential (anonymous pull). It is read back by its exact name, `GET /api/v2.0/registries?q=name%3D<name>`. An existing endpoint whose URL is not `VULNDB_ORIGIN_URL` is reported, the project is not created, and the Job fails after every item.
7. The project is created with `{"project_name":"<project>","public":true,"registry_id":<id>,"metadata":{"public":"true"}}`. It is public so that pods and nodes pull it without a pull secret, like the other proxy projects. An existing project whose `registry_id` is not that endpoint's id is reported, and the Job fails after every item.
8. The hosted-project rule of the Job (a hosted project must have no `registry_id`) does not apply to the database project; it still applies to every other project, unchanged.
9. The Job name hash also covers the database project and the origin URL, so a change of either runs the Job again.
10. Nothing else changes: the public and private project lists, the Job's image, security context, resources and volumes stay as they are.

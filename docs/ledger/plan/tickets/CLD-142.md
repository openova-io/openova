# CLD-142 — Neutral storage gate

## In plain words

**The problem today.** The database operator of the bootstrap kit waits for two cloud-specific disk-driver releases, one per cloud. So shared kit code names both clouds, every Sovereign must install both drivers, and a new cloud would need a third entry. What the database really needs, a durable default storage class, is checked nowhere.

**What changes.** A small neutral release, storage-ready, succeeds only when the storage class the Sovereign was given is the cluster default. The database operator waits for it instead of for the disk drivers.

**Done means:**

- The bootstrap kit has a slot storage-ready whose release succeeds only when the storage class named by the kit key SOVEREIGN_CNPG_STORAGE_CLASS is the cluster default.
- The gate gives up after 10 minutes and fails, so that Flux tries again; an empty class name fails at once.
- The database operator slot depends on Flux and storage-ready, and names no disk-driver release.
- The new chart's own test renders it, runs its script against a stub, and passes on the pull request.
- The kit dependency, placement and ratchet checks stay green, and the generated catalogue and slot inventory list the new chart and slot.

The rest of this ticket is the exact instruction for the model that does the work.

## 2. End goal
Every region of a Sovereign installs one more bootstrap-kit release, `storage-ready`, from the new chart `bp-storage-ready` in `platform/storage-ready`. Its only content is a hook Job that runs before the release installs or upgrades. The Job looks at the StorageClass whose name the kit key `SOVEREIGN_CNPG_STORAGE_CLASS` gives. When that class carries the annotation `storageclass.kubernetes.io/is-default-class: "true"`, the Job exits 0 and the release becomes Ready. Otherwise it checks again every 5 seconds; after 10 minutes it exits 1, the install fails, and Flux retries it. The database operator release `bp-cnpg` (slot 16) depends on `bp-flux` and `storage-ready`, and no longer on the two disk-driver releases `bp-hcloud-csi` and `bp-huawei-evs-csi`. A person can see this in the slot files, in the generated slot inventory `docs/generated/bootstrap-slots.md`, and in the chart's own test, which runs the Job's script against a stub `kubectl`.

# bp-storage-ready

The neutral storage gate of the bootstrap kit: a release that becomes Ready
only when the Sovereign's durable default StorageClass exists.

## Role in Catalyst

Control-plane plumbing, installed on every region by bootstrap-kit slot 15b
(`clusters/_template/bootstrap-kit/15b-storage-ready.yaml`) as HelmRelease
`storage-ready`. Never a catalog item (`visibility: unlisted`). See
[`docs/ARCHITECTURE.md`](../../docs/ARCHITECTURE.md) for the bootstrap kit.
Slots that bind volumes depend on `storage-ready` and on no cloud-specific
disk-driver release; the first is `bp-cnpg` (slot 16). A PVC created before the
default class exists keeps an empty class and stays Pending; the gate prevents
that.

## What it ships and how to configure it

One pre-install and pre-upgrade hook Job, with a ServiceAccount, a ClusterRole
(`get` and `list` on StorageClasses) and its binding. The Job exits 0 when the
StorageClass named by `expectedClass` carries the annotation
`storageclass.kubernetes.io/is-default-class: "true"`. It checks every 5 seconds
for at most 10 minutes, then exits 1; Flux retries the release.

The one value, `expectedClass`, has no default and is required: an unset or
empty value fails the Job at once. Slot 15b sets it from the kit key
`SOVEREIGN_CNPG_STORAGE_CLASS`.

## Operational notes

- No data, no backup. Each region runs its own gate on its own cluster.
- A failed gate shows in the conditions of the HelmRelease `storage-ready` and
  in the log of the Job `storage-ready-gate` in `flux-system`.
- `bash platform/storage-ready/chart/tests/storage-ready-render.sh` renders the
  chart and runs the Job's script against a stub `kubectl`.

# FND-182 — Scheduled etcd snapshots to the Sovereign's object store

## In plain words

**The problem today.** Each control-plane server keeps its etcd snapshots on its own disk only. No snapshot leaves the node, so a lost node loses its snapshots, and the cluster store has no copy anywhere else. Decision record 0036 says where the copies go and how the server gets the key, and nothing builds it yet.

**What changes.** The first-boot template writes one k3s configuration file on every control-plane server. With it k3s snapshots etcd on the schedule of record 0036, keeps the 5 newest of each server and uploads each to the region's folder of the Sovereign's bucket, with the bucket's key pair in that file only.

**Done means:**

- The shared first-boot template writes /etc/rancher/k3s/config.yaml.d/etcd-s3.yaml with permissions 0600 on every control-plane server.
- The file sets the schedule 0 */12 * * *, the retention 5 and the folder etcd/<region>, and names the bucket's endpoint without its scheme, its region, its name and its key pair; an http endpoint also turns off TLS.
- The bucket's secret key appears in that file and in no other file a node reads in the clear, and no etcd snapshot flag is on the k3s command line.
- The render test proves the file for both fixtures and an http endpoint, and the golden values hold the new file.
- The start-up data of every node role stays under its size limit.

The rest of this ticket is the exact instruction for the model that does the work.

## 2. End goal
Every control-plane server of every region takes an etcd snapshot every 12 hours with k3s itself, keeps its 5 newest, and uploads each, uncompressed, to `etcd/<region>/` of the Sovereign's bucket, where `<region>` is the region's canonical label. The setting is one k3s configuration file, `/etc/rancher/k3s/config.yaml.d/etcd-s3.yaml`, that the shared first-boot template `infra/providers/_shared/cloudinit-control-plane.tftpl` writes with permissions `0600`. The bucket's key pair is in that file and nowhere else in the clear: not on the k3s command line, not in a Secret. This is the etcd row of decision record 0036 (B1) and its key rule (B3). The restore drill FND-G16 is FND-185.

## 3. The model (the law)
1. The template writes one plain `write_files` entry, path `/etc/rancher/k3s/config.yaml.d/etcd-s3.yaml`, permissions `'0600'`, no encoding. k3s v1.31 reads every file of `/etc/rancher/k3s/config.yaml.d` at start, also when `/etc/rancher/k3s/config.yaml` does not exist, each key as the server flag of that name.
2. The file holds exactly these keys: `etcd-snapshot-schedule-cron: "0 */12 * * *"`, `etcd-snapshot-retention: 5`, `etcd-s3: true`, `etcd-s3-endpoint` (the template input `object_storage_endpoint` with `https://` or `http://` and a trailing `/` cut off), `etcd-s3-region`, `etcd-s3-bucket`, `etcd-s3-folder: "etcd/<region_canonical_label>"`, `etcd-s3-access-key`, `etcd-s3-secret-key`. When the endpoint starts with `http://` the file also holds `etcd-s3-insecure: true`. Each string value is written with `jsonencode`, so any character of a key is a valid YAML double-quoted scalar.
3. The k3s install line does not change: no `--etcd-s3` and no `--etcd-snapshot` flag in the template (record 0036 B3: the process list would show the key).
4. Snapshots are not compressed (k3s' default; record 0036 B1). The file names are as k3s writes them, with the node name and the time.
5. The render test `infra/providers/_shared/tests` proves the file: the decoded content for the default fixture, the http form on the other fixture, mode `0600`, the secret key in no other file, no etcd flag on the command line. `render.tf` gains the variable `object_storage_endpoint` (default `https://s3.example.test`, the literal it replaces) and the output `etcd_s3`. `golden.auto.tfvars.json` is written by `scripts/update-cloudinit-golden.sh`, never by hand.
6. Nothing is compressed to make room: the start-up data stays under every cap of `scripts/cloudinit-size-check.sh`.

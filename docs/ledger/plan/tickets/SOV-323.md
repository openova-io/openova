# SOV-323 — Relay mode: sign-in mail through a relay with a credential for that child alone

## In plain words

**The problem today.** A new Sovereign always gets its own mail server for its sign-in codes. On a cloud where a mail server inside the Sovereign cannot send there is no other way: the variables document already has a relay mode, but the parent never sets it and the console never reads it.

**What changes.** A provisioning request can name a relay; the new Sovereign then sends its sign-in codes through that relay, signed in with a credential the relay issued for that Sovereign alone. A request without a relay gives a Sovereign with its own mail server, as before.

**Done means:**

- A provisioning request that names a relay host and a sender gives a Sovereign whose variables document says relay mode, with that host, the port, the sender and the name of the relay credential Secret; a request without a relay still gives local mode.
- A request that names a relay without a host or without a sender is refused before anything is provisioned.
- On a Sovereign in relay mode the console submits each sign-in code to the relay, as the sender of the variables document, signed in with the credential of the relay Secret; a test relay accepts it and refuses a credential issued for another Sovereign.
- In relay mode the console never uses the Secret of a local mail server or its own environment: without a complete relay credential the code goes to the relay unsigned and the relay refuses it.
- The Secret register lists the relay credential Secret as transitional, to be removed when the credential is mounted as a file.

The rest of this ticket is the exact instruction for the model that does the work.

## 2. End goal
A sovereign-admin who provisions a Sovereign on a cloud where a mail server inside the Sovereign cannot send names an SMTP relay in the provisioning request (`mailRelay`: host, optional port, sender). The parent writes `MAIL_MODE: relay`, `MAIL_RELAY_HOST`, `MAIL_RELAY_PORT`, `MAIL_FROM` and `MAIL_RELAY_SECRET: sovereign-mail-relay` into the new Sovereign's variables document; the request carries no credential. Kit slot 95 then installs no mail server (its chart renders nothing outside `local`). On every sign-in code the catalyst-api of that Sovereign reads its variables document, takes the relay's host, port and sender from it and the keys `smtp-user` and `smtp-pass` from `catalyst-system/sovereign-mail-relay`, the credential the relay issued for this Sovereign alone, and submits the code to the relay. It never falls back to the Secret of a local mail server or to its environment. A request without `mailRelay` gives `MAIL_MODE: local`, exactly as today.

## 3. The model (the law)
1. The variables document (ConfigMap `flux-system/sovereign-variables`, contract C5) decides the path of a sign-in code. With `MAIL_MODE` `relay`: host `MAIL_RELAY_HOST`, port `MAIL_RELAY_PORT` (empty: `587`, the contract default), sender `MAIL_FROM`, credential the keys `smtp-user` and `smtp-pass` of the Secret `catalyst-system/<MAIL_RELAY_SECRET>`. With any other value, without the key, or without a readable document: the path of SOV-322, unchanged (the Secret `catalyst-system/sovereign-smtp-credentials`, then the environment).
2. In relay mode neither `catalyst-system/sovereign-smtp-credentials` nor the environment (`CATALYST_SMTP_*`) is used. When the relay Secret is unnamed, absent, or lacks either key, the code goes to the relay with no credential and the relay refuses it. A code never reaches a mail server the document does not name.
3. The credential is never in the variables document, the provisioning request or anything the parent keeps. The request names only the relay's host, port and sender. The Secret's name is fixed: `sovereign-mail-relay` (`provisioner.MailRelaySecretName`).
4. A request whose `mailRelay` has no host or no sender is refused by `Request.Validate`, before anything is provisioned; `childVariables` refuses it again through contract rule 3 (`upstream.Validate`).
5. Without `mailRelay` the variables document is unchanged: `MAIL_MODE` `local` and empty relay keys, as the golden files of the provisioner hold them.
6. The handler package does not grow (`scripts/check-api-structure.py`): the relay read lives in `internal/signinmail`, the request field in `internal/provisioner`; the handler package gets a test file only.
7. The relay credential Secret has an entry of class T in the Secret register, removal SEC-224, which mounts the credential as a file.
8. Nothing else changes: no kit slot, no chart, no Service, no RBAC rule, no contract key, no node port.

# SVC-137 — The function tests wait for their subject in their own region within the bound of their release

## In plain words

**The problem today.** On a fresh installation the function tests of six foundation releases ran once, minutes before the thing they test was up, failed, and were never run again, because the installer runs a release's test only after an install or upgrade. One of them also judged the store of the other region, which an install of its own region does not deliver. Nothing in the repository says how long a test may wait, so each test chose its own few minutes.

**What changes.** Each of the six tests waits for what it tests, in its own region, for as long as its release may take to install, and then judges it as before. The kit states that time once per release, and a test of the kit fails when a tested release does not hold it.

**Done means:**

- A test whose subject comes up ten minutes after the install passes, and one whose subject never comes up still fails and names what it waited for.
- The store test reads only the store of its own region and may read no other.
- The kit gives each of the six releases one waiting time, equal to its install timeout and to the time the installer waits for the test.
- A test of the kit fails when a tested release waits shorter than its install timeout, unless the release is on a list of owed releases that only shrinks, and it names bp-openbao, bp-reloader and bp-valkey on that list.
- The runbook section on function tests states the rule.

The rest of this ticket is the exact instruction for the model that does the work.

## 2. End goal
On a fresh two-region installation the function tests (the `helm test` hooks of `templates/tests/function-test.yaml`, run by Flux once after an install) of six kit releases pass when their subject comes up within the time their release may take to install, and fail naming the subject when it never does. Each test waits for its subject itself until 60 seconds before its bound T, then judges exactly as before: bp-nats-jetstream the stream add, bp-cert-manager-powerdns-webhook the API group `acme.powerdns.openova.io/v1alpha1`, bp-external-secrets-stores the ClusterSecretStore of its own region only (never a peer store), bp-catalyst-edge-routes (release `bp-catalyst-secondary-edge`) every parent of every route Accepted, bp-dragonfly the manager's `/healthy`, bp-plane-isolation a ready address of its target before the refusal is judged. T is the release's install timeout in the kit, stated once as `spec.values.functionTest.timeoutSeconds` (900; 1800 for bp-plane-isolation, whose install timeout rises from 5m to bp-keycloak's 30m; the edge release gains `install.timeout: 15m`), with `spec.test.timeout` equal to it; without the value the chart default of 300 seconds holds. A Go test of the kit, `tests/e2e/bootstrap-kit/function_test_bound_test.go`, holds every HelmRelease that enables its test to that bound and lists the releases still owed by name, and `docs/RUNBOOKS.md` section 4.5 states the rule. A person sees this on the pull request: the six charts' `chart/tests/*.sh`, the kit's `manifest-validation` and the acceptance commands are green.

## 3. The model (the law)
1. A function test proves the function its own release delivers, in its own region. It never judges an object of another region.
2. It waits for its subject itself, then judges as before, and fails naming a subject that never comes up. Its one bound T is the install timeout of its release in the kit (`spec.install.timeout`, else `spec.timeout`, else Flux's 5 minutes).
3. A release whose test needs what another release delivers, and that cannot depend on it without moving behind it, has an install timeout no shorter than that release's.
4. T is stated once, as `spec.values.functionTest.timeoutSeconds` of the kit HelmRelease, a whole number of seconds. The chart makes it the test Pod's `activeDeadlineSeconds` and ends its wait 60 seconds before it; `spec.test.timeout` equals the install timeout, so Flux waits as long as the Pod may run. Without the value the chart default of 300 seconds (rule FT8 of `scripts/check-function-test.py`) holds under Flux's default test timeout of 5 minutes, so the default render and the checker do not change.
5. No `dependsOn` and no end of `install.disableWait` replaces the wait: no dependency edge of the kit changes.
6. The Go test of the kit holds every HelmRelease that enables its test to points 2 to 4 (rules B1 to B5 in its header). A release that breaks them and is not on its list `owed` fails it; a release on the list that no longer breaks them fails it until it is removed, so the list only shrinks.

+// ftbDuration reads the first of the given fields that is set, else the
+// fallback. It returns the value and the field it came from.
+func ftbDuration(doc map[string]any, fallback time.Duration, fields ...[]string) (time.Duration, string, error) {
+	for _, f := range fields {
+		raw := ftbDig(doc, f...)
+		if raw == nil {
+			continue
+		}
+		s, ok := raw.(string)
+		if !ok {
+			return 0, "", fmt.Errorf("%s is %v, not a duration", strings.Join(f, "."), raw)
+		}
+		d, err := time.ParseDuration(s)
+		if err != nil {
+			return 0, "", fmt.Errorf("%s: %w", strings.Join(f, "."), err)
+		}
+		return d, strings.Join(f, "."), nil
+	}
+	return fallback, "Flux's default", nil

+// ftbSubstitute applies Flux's post-build substitution with no variable set:
+// ${NAME:=default}, ${NAME:-default}, ${NAME=default} and ${NAME-default} give
+// the default, ${NAME} gives the empty text.
+var ftbVariable = regexp.MustCompile(`\$\{[A-Za-z_][A-Za-z0-9_]*(?::?[=-]([^}]*))?\}`)

+func ftbSubstitute(s string) string {
+	// A default may hold a further ${...}: the inner one is left by the first
+	// pass, so substitute until nothing changes.
+	for i := 0; i < 5; i++ {
+		next := ftbVariable.ReplaceAllStringFunc(s, func(m string) string {
+			return ftbVariable.FindStringSubmatch(m)[1]
+		})
+		if next == s {
+			break
+		}
+		s = next
+	}
+	return s
+}

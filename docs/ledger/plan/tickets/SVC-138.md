# SVC-138 — Every foundation release has a function test that check SVC-G06 can read

## In plain words

**The problem today.** On a fresh two-region installation four releases of the foundation ring never showed a passing function test. The reboot daemon has a test that the kit never switched on, the storage gate and the mail server have none, and the console's release has none either: a packaging rule of its chart drops any test folder. The check that reads the results expects a message that the installer never writes, so a release whose chart has no test reads as not settled instead of as having none, and a test that a release deliberately leaves out reads as never finished, so the secret store can never pass.

**What changes.** The four releases run a function test after their install, each waiting for what it tests as long as its release may take to install, and the check reads the message the installer really writes and judges only the tests a release runs.

**Done means:**

- The reboot daemon's test passes once every copy of the daemon is ready and the update settings of its node are in place.
- The storage gate's test passes only when its storage class is the one default class of the cluster.
- The mail server's test passes when the server greets with the SMTP code 220, and renders only when the mail server is installed.
- The console's test passes when both the console API and the console UI answer their health address with 200, and the packaged chart holds the test.
- Each of the four waits at most until a minute before its install timeout, then fails naming what never came up.
- The check of function tests reads a release whose chart has no test as having none.
- The check of function tests does not judge a test that a release deliberately leaves out, so the secret store passes on its own test.

The rest of this ticket is the exact instruction for the model that does the work.

## 2. End goal
On a fresh installation every release of the foundation ring that check SVC-G06 judges has a function test (`templates/tests/function-test.yaml`, run by Flux once after an install or upgrade) that can pass: bp-kured, storage-ready (chart bp-storage-ready) and bp-stalwart-sovereign enable their test with `ignoreFailures`, and bp-catalyst-platform, which enabled it already, gets one. Each test uses the mechanism of SVC-137: T is `functionTest.timeoutSeconds`, the test Pod's `activeDeadlineSeconds`; the test waits for its subject until T - 60, then judges and fails naming the subject that never came up; the kit states T once per release as `spec.values.functionTest.timeoutSeconds`, equal to `spec.install.timeout` and to `spec.test.timeout` (900 for the three, 15m; 1800 for bp-catalyst-platform, 30m); without the value the chart default of 300 holds. bp-kured's existing test waits for its DaemonSet `kured` and the node's two node-patch-config files; storage-ready's test passes when the class of `expectedClass` is the one default StorageClass; bp-stalwart-sovereign's test reads an SMTP banner 220 from the smtp port of the mail Service `<fullname>-mail`; bp-catalyst-platform's test asks GET /healthz of the Services catalyst-api (8080) and catalyst-ui (80) and passes on 200 from both. Check SVC-G06 reads a release without test hooks as `none` from the message helm-controller writes, which ends in `: no test hooks`, and does not judge a test hook that the release's `spec.test.filters` leaves out (bp-openbao, slot 08, excludes the upstream chart's `openbao-server-test`). ## 3. The model (the law)
1. A function test proves the function its own release delivers, in its own region, and waits for its subject itself within one bound T, stated once as `spec.values.functionTest.timeoutSeconds` (`docs/RUNBOOKS.md` section 4.5). The test Pod's `activeDeadlineSeconds` is T, the wait ends by T - 60, and `spec.test.timeout` equals `spec.install.timeout`. Without the value the chart default of 300 holds, so every default render keeps rule FT8 of `scripts/check-function-test.py`.
2. No subject of the four is another release's: no `testNeeds` entry (B3), no `dependsOn` and no `install.disableWait` change. bp-catalyst-platform runs in the primary region only, and the follower regions hold no backend of its two Services.
3. A chart's packaging rules must not drop its own test: a `.helmignore` pattern without a leading slash matches a folder of that name at any depth, so the umbrella's `tests/` (meant for the CI scripts in `chart/tests/`) becomes `/tests/`.
4. Check SVC-G06 reads `none` only from TestSuccess True with a message that ends in `: no test hooks` (helm-controller v1.1.0, `internal/reconcile/test.go`, `fmtTestSuccess`); the bare text `no test hooks`, which no release carries, reads as pending.
5. Check SVC-G06 judges only the test hooks Helm runs. helm-controller v1.1.0 hands `spec.test.filters` to Helm's `ReleaseTesting` (helm v3.16.1, `pkg/action/release_testing.go`), which skips a hook named by a filter with `exclude: true` and, when a filter without `exclude` names any hook, every remaining hook it does not name; a skipped hook is recorded in `testHooks` without a phase. Such a hook is not judged; when the filters leave out every hook the result is `none`; a failed hook that runs is still `fail`.
6. The lists only shrink: bp-catalyst-platform leaves `owed` of the kit's guard and `G6.foundation-without-function-test` of the service-model baseline; `G6.function-test-charts` rises by the three new tests, 32 to 35.
7. A test hook that runs kubectl sets up its API access with kube-access-lib (rule K2 of `tools/guards/cmd/kube-access`) and its chart declares that dependency (K3); a test that needs no API mounts no token.
8. No chart version, `blueprint.yaml`, `values.yaml` or version pin changes: the release writer publishes the charts after the merge. No Python is added: the render tests are shell, the guards Go.

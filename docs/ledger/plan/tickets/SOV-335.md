# SOV-335 — The variables document carries the path of the vulnerability database

## In plain words

**The problem today.** Inside a Sovereign the vulnerability scanner fetches its database from a public registry. After hand-over that registry is no longer reachable, so the database stops being refreshed. The variables document of a region has no value that says where the region's own registry keeps the database.

**What changes.** The variables document gains one optional value: the path of the vulnerability database on the region's own registry. A parent hands each child a path that goes through the child's own pull-through project. Later tasks create that project and point the scanner at it.

**Done means:**

- The published contract and its copy in the Go package list the new key with its default, and do not require it.
- A document without the key still passes the contract, and reading it gives the default.
- A child's document names the database path through the child's own pull-through project, built from the parent's path; a parent without a path gives the default.
- The Hetzner, Huawei and local provider modules accept a document with the new key, and every test document that carries the full key list carries it.
- The Hetzner first-boot files still fit their size guards.

The rest of this ticket is the exact instruction for the model that does the work.

## 2. End goal
The variables document of contract C5 (ConfigMap `flux-system/sovereign-variables`) has a 40th contract key, `REGISTRY_PATH_VULN_DB`: the repository path, without a tag, of the vulnerability database on the region's own registry. The scanner will read the database at `${LOCAL_REGISTRY_HOST}/${REGISTRY_PATH_VULN_DB}`. The key is optional, with the default `proxy-vulndb/aquasecurity/trivy-db`. Every new Sovereign gets it: the API builds a child's document with `upstream.Served` and `ToMap`, which writes every key, and the provider modules accept exactly the contract keys. A person sees it in the tests of the package `core/controllers/pkg/upstream` and in the module input `variables` of each new provision. This package changes no chart and no kit slot: SOV-336 creates the proxy project in the registry and SOV-337 points the scanner at the key.

## 3. The model (the law)
1. The key is `REGISTRY_PATH_VULN_DB`. It is a property of `docs/contracts/c5-upstream-variables.schema.json` with `"type": "string"` and `"default": "proxy-vulndb/aquasecurity/trivy-db"`. It is not in the list `required`, so the eight documents under `tests/fixtures/variables/` (`valid.yaml`, `invalid-rule1.yaml` to `invalid-rule7.yaml`) stay as they are and still pass or fail as before.
2. Meaning: the first path segment is the region's proxy project, a pull-through project to the origin registry (`ORIGIN_REGISTRY_SCHEME://ORIGIN_REGISTRY_HOST`). The rest is the path of the database on the origin registry. Harbor passes the path after the project name to the origin unchanged.
3. The project name is the Go constant `upstream.VulnDBProxyProject`, value `proxy-vulndb`.
4. `Served(parentFQDN, parent)` sets the child's `PathVulnDB` to `VulnDBProxyProject + "/" + parent.PathVulnDB` when `parent.PathVulnDB` is not empty. When it is empty, the child keeps the default. Today every child is served by `legacyOwnVariables` in `products/catalyst/bootstrap/api/internal/provisioner/provisioner.go`, whose registry is `ghcr.io` and whose `PathVulnDB` is empty; the default is therefore the path through the child's proxy project to `ghcr.io/aquasecurity/trivy-db`. That file does not change.
5. `Flipped` does not change the key: the flip still changes exactly `SOVEREIGN_CONSUME`, `REGISTRY_HOST` and `REGISTRY_SCHEME`.
6. Every file that holds the exact key list of the contract holds the new key: the validation lists of the three provider modules (`infra/providers/{hetzner,huawei,local}/variables.tf`), the file-level variables of the Hetzner and Huawei module tests, the two contract fixtures under `infra/providers/_contract/fixtures/`, the fixtures of `scripts/cloudinit-size-check.sh` and `scripts/lint-cloudinit.sh`, and the contract part of `tests/fixtures/variables/today.env`. In each the value is `proxy-vulndb/aquasecurity/trivy-db`.
7. The shared render fixture `infra/providers/_shared/tests/render.tf` keeps its 39 keys: `infra/providers/_shared/tests/cloudinit_render.tftest.hcl` counts them, and the golden hashes in `infra/providers/_shared/tests/golden.auto.tfvars.json` depend on them. Only the comment that says "exactly the 39 contract keys" is corrected.
8. Nothing else reads the key in this package. No kit slot, chart or provisioner file changes.

# SOV-131 — Provider modules take the variables map of the upstream contract

## In plain words

**The problem today.** The variables contract defines the values that describe a Sovereign region, but no provider module receives them. The switch that lets a new Sovereign start its hand-over by itself is a module setting of its own instead of a value of that contract. A module cannot tell whether it was given a complete document.

**What changes.** The provisioner builds the variables document of each new Sovereign, checks it against the contract and passes it to the module as one input. The module refuses a document without exactly the contract keys and reads the hand-over switch from it.

**Done means:**

- The provisioning of a new Sovereign writes a complete variables document, checked against the contract, into the inputs of its module.
- A provider module refuses, at plan time, a variables document that lacks a contract key or holds another key.
- A new Sovereign still starts the hand-over by itself unless the request says no, and the module now reads that switch from the document.
- Wiping a Sovereign that was provisioned before this change still works.
- The module tests and the provisioner tests fail when the document is missing or not wired.

The rest of this ticket is the exact instruction for the model that does the work.

## 2. End goal
Each provider module, `infra/providers/hetzner` and `infra/providers/huawei`, has a required input `variables`: the variables document of the region, a map of strings that must hold exactly the keys of contract C5 (`docs/contracts/c5-upstream-variables.schema.json`). The module input `fire_cutover_on_handover` is gone; the key `HANDOVER_AUTO` of the document takes its place and reaches the same cloud-init substitute `FIRE_CUTOVER_ON_HANDOVER` as before. The provisioner of the API (`products/catalyst/bootstrap/api/internal/provisioner/provisioner.go`) builds that document for every new Sovereign with the contract package `core/controllers/pkg/upstream`, checks it against the schema and the cross-field rules, and writes it as `variables` into `tofu.auto.tfvars.json`. A wipe of a Sovereign whose variables file was written before this change still runs, because the document is added to that file first. The module tests prove the input check and the wiring, and the provisioner tests prove the document. This is the first part of package SOV-131: the contract keys are not yet written into the ConfigMap `flux-system/sovereign-variables` (field 11).

## 3. The model (the law)
1. **The module input.** Both `variables.tf` files declare `variable "variables"` with `type = map(string)` and no default. A first validation requires that `keys(var.variables)` equals the sorted list of the 39 contract keys, written out in the block; the list is the `properties` of `docs/contracts/c5-upstream-variables.schema.json`, no more and no fewer. A second validation requires that `HANDOVER_AUTO` is `"true"` or `"false"`. The block replaces the block of `variable "fire_cutover_on_handover"` at the same place, so that input no longer exists.
2. **The wiring.** Every `templatefile()` call of the shared control-plane template keeps its template input `fire_cutover_on_handover`, now set to `var.variables["HANDOVER_AUTO"]`: two calls in `infra/providers/hetzner/main.tf` (primary and secondary regions) and one in `infra/providers/huawei/main.tf`. The template, its render test and its golden values do not change, so a Sovereign provisioned with the default request renders the same cloud-init as before (`FIRE_CUTOVER_ON_HANDOVER: "true"`).
3. **The document of a new Sovereign.** `childVariables(req, apiURL)` in `provisioner.go` returns `upstream.Served(parentFQDN, own).ToMap()` with these keys of the child filled in: `HANDOVER_AUTO` is `"true"` when `Request.FireCutoverOnHandover` is nil or true and `"false"` when it is false (the zero-touch default of today); `LOCAL_REGISTRY_HOST` is `registry.<sovereign FQDN>`, the host of the Sovereign's own Harbor (`clusters/_template/bootstrap-kit/19-harbor.yaml` line 420); `K3S_VERSION` is the constant `moduleK3sVersion` = `v1.31.8+k3s1`, the default of `k3s_version` in both modules, which `writeTfvars` does not set; `MAIL_MODE` is `local`; `CLOUD_CREDENTIAL_MODE` is `supplied`; `ORIGIN_PARENT_API_URL` is `apiURL`, the address the new Sovereign calls back to (`catalyst_api_url`). Every other key is what `upstream.Served` gives: `SOVEREIGN_CONSUME` `origin`, the registry host and paths copied from the parent, every other key its contract default. The function fails, and with it `writeTfvars`, when `upstream.FromMap` or `Validate(<sovereign FQDN>)` refuses the document.
4. **The parent's own document.** `legacyOwnVariables(apiURL)` stands for the parent that runs the provisioner, because no parent has the ConfigMap `flux-system/sovereign-variables` with the contract keys yet. It reads no environment variable. The parent's name is the host of `apiURL` without a leading `console.` (`openova.io` for the default address). Its registry values are the ones every child uses today: `LocalRegistryHost` `ghcr.io` and `PathCharts` `openova-io`, the chart source of the kit (`oci://ghcr.io/openova-io`, and the same values in `tests/fixtures/variables/today.env`); the other paths at their contract defaults; the eight proxy projects `docker.io`, `registry-1.docker.io` (`proxy-dockerhub`), `quay.io` (`proxy-quay`), `gcr.io` (`proxy-gcr`), `registry.k8s.io` (`proxy-k8s`), `ghcr.io` (`proxy-ghcr`), `xpkg.upbound.io` (`proxy-xpkg`), `public.ecr.aws` (`proxy-ecr`), the same as the defaults of the registry-projects Job of package SOV-160; channel `stable`; no release key yet. Work package SOV-940 deletes this function.
5. **The tfvars file.** `writeTfvars` computes `apiURL` once, from `CATALYST_API_PUBLIC_URL` with the same default as before, uses it for `catalyst_api_url` and for the document, writes the document under the key `variables`, and no longer writes `fire_cutover_on_handover`.
6. **A wipe of an older Sovereign.** `Destroy` keeps the provision-time `tofu.auto.tfvars.json` of a Huawei deployment when the wipe request lacks the regions (#3140). Such a file written before this change has no `variables`, and `tofu destroy` needs every required input. In that branch `addVariablesIfMissing` adds the document, built from the request and the file's own `catalyst_api_url`; a file that already has `variables` is not changed.
7. **The Go module.** The API imports `github.com/openova-io/openova/core/controllers/pkg/upstream` (already a `replace`d dependency). Its `go.mod` gains the three indirect requirements that package brings, `github.com/evanphx/json-patch/v5 v5.9.0`, `github.com/pkg/errors v0.9.1` and `sigs.k8s.io/controller-runtime v0.19.0` (the version `core/controllers/go.mod` requires), and `go.sum` their six lines. No other requirement changes.
8. Nothing else changes: no template, no kit file, no chart, no contract file, no secret, no Service. The ConfigMap a new Sovereign gets is the same as before.

# AIP-150 — The tool server accepts agent tokens

## In plain words

**The problem today.** catalyst-api now mints short-lived agent tokens for in-cluster workloads, but the tool server does not know them. It would read an agent token like a person's session, take its tier from any role claim, and could send it to catalyst-api for a verdict that ignores the agent rules. Its HTTP transport also falls back to a long-lived bearer held in the pod when a request carries none.

**What changes.** The tool server accepts an agent token only when the token meets every agent rule, and gives it at most the developer tier, so an agent sees the read tools and never the create tool. A request over HTTP without its own bearer is unauthenticated, and the chart no longer wires a bearer into the pod.

**Done means:**

- An agent token signed by a trusted key that names that key, carries the tool audience, a known Organization, an agent name and a tier is accepted, and its tier is never above developer.
- An agent token that breaks any one rule is refused, and the shared-secret and unverified modes refuse every agent token.
- An agent token sees the six read tools and is refused the create tool, and whoami shows the agent name.
- An agent token that the server cannot verify is never sent to catalyst-api for a second opinion.
- A request over HTTP without an Authorization header carries no bearer, and the chart renders no bearer variable even when the old value is set.
- With a Sovereign name the chart renders the agent issuer once, as the console address of that Sovereign, and without one it renders none.
- The tool server chart carries appVersion 0.2.8 and the agent workspace chart 0.9.8, so both images that contain the changed binary are built under new tags.

The rest of this ticket is the exact instruction for the model that does the work.

## 2. End goal
The OpenOva tool server (`products/openova-mcp`, Blueprint `bp-openova-mcp`) verifies the bearer of every MCP call and turns it into an identity with a context, a tier and an Organization. catalyst-api already mints agent tokens: RS256 JWTs signed by its session signer, with the key identifier `kid` in the header, `aud` `["model-gateway", "platform-tools", "catalyst-api"]`, `typ` `agent`, `org_id`, `agent` and a `tier` of `viewer` or `developer`. After this ticket the tool server accepts such a token only when every agent rule holds, and it gives the token the tier of its `tier` claim, capped at developer: an agent sees the six read tools and is refused `create_application`. `whoami` shows the agent name. An agent token is never handed to catalyst-api's `/whoami` as a fallback. The HTTP transport reads the bearer from the `Authorization` header and from nothing else, and the chart neither wires `OPENOVA_MCP_BEARER` nor offers `auth.bearerSecret`; the stdio transport keeps its environment bearer until AIP-156. The chart sets `OPENOVA_MCP_AGENT_ISSUER` to `https://console.<sovereignFqdn>` when `sovereignFqdn` is set. The chart's `appVersion` moves from `0.2.7` to `0.2.8`. The agent workspace image (`products/agenity`) embeds the tool-server binary, so its `appVersion` moves from `0.9.7` to `0.9.8`; nothing else of `products/agenity` changes.

## 3. The model (the law)
1. A token is an agent token when its claim `typ` equals `agent` in any letter case (`strings.EqualFold`). Every other token is resolved exactly as today.
2. The resolver accepts an agent token only when all of these hold, each refusing on its own:
   a. the resolver is in RS256 mode and one key of its set verified the signature (the hs256 resolver and the insecure resolver refuse every agent token);
   b. the header `kid` is not empty and equals `identity.KeyID` of the key that verified it: the RFC 7638 thumbprint, the SHA-256 of `{"e":<e>,"kty":"RSA","n":<n>}` with base64url values without padding, written as base64url without padding (the same rule as `KeyID` of `products/catalyst/bootstrap/api/internal/handoverjwt/signer.go`);
   c. `aud` contains `platform-tools`;
   d. when `OPENOVA_MCP_AGENT_ISSUER` is set, `iss` equals it exactly;
   e. `exp` is present;
   f. `org_id` is not empty;
   g. `agent` matches `^[a-z][a-z0-9-]{1,62}$`;
   h. `tier` is a label of the ladder (`viewer`, `developer`, `operator`, `admin`, `org-admin`, `owner`, with or without the prefix `catalyst-`).
3. The tier of an agent token is its `tier` claim alone, capped at developer. Its `role`, `groups` and `capabilities` are not read, so no agent token reaches tier admin or the Sovereign context.
4. The existing instance pins apply to an agent token as to a session: the expected-issuer pin, the context pin (a Sovereign-mode instance refuses it, because it serves sovereign-admins only) and the org pin.
5. `Identity` gains the field `Agent string`, set from the claim `agent` of an accepted agent token and empty otherwise. `whoami` returns it under the key `agent`.
6. When the resolver refuses a bearer whose unverified `typ` is `agent`, the server returns that refusal and does not call catalyst-api's `/whoami`.
7. Over HTTP the bearer comes from the `Authorization` header or from the `_auth.token` argument, never from the process environment. `serveHTTP` takes no bearer and `httpTransport` holds none. The stdio transport keeps `OPENOVA_MCP_BEARER`.
8. The chart renders `OPENOVA_MCP_AGENT_ISSUER` with the value `https://console.<sovereignFqdn>` exactly once when `sovereignFqdn` is set, and not at all when it is empty. It renders no `OPENOVA_MCP_BEARER`; the value `auth.bearerSecret` is deleted from `values.yaml` and from the template.
9. Delete: the field `fallbackBearer` of `httpTransport`, the parameter `fallbackBearer` of `serveHTTP`, the parameter `processFallback` of `bearerFromRequest`, the `OPENOVA_MCP_BEARER` block of `chart/templates/deployment.yaml` and the `bearerSecret` block of `chart/values.yaml`.
10. Every image that contains the changed binary gets a new tag: the `appVersion` of `products/openova-mcp/chart/Chart.yaml` and that of `products/agenity/chart/Chart.yaml`, whose image embeds the tool-server binary (`products/agenity/image-version.conf`), each move one patch.

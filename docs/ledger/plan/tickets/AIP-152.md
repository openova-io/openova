# AIP-152 — The tool server reads its bearer from a file at every call

## In plain words

**The problem today.** The tool server inside the agent workspace reads its fallback bearer once, when it starts. A tool identity that lives at most one hour and is renewed while the workspace runs is never seen by it: it keeps calling the platform with the first bearer until that expires.

**What changes.** With a bearer file named in its environment, the tool server reads the file at every tool listing and every tool call, so a renewed bearer is used from the next call on with no restart. Without the file setting nothing changes.

**Done means:**

- A bearer replaced in the file between two calls is the one the next tool listing, the next tool call and the next request to catalyst-api use, with no restart.
- When the file is missing or empty the tool server has no fallback bearer: a tool call is refused as unauthenticated and the tool listing is empty, even if a bearer was read before or the old bearer variable is set.
- A bearer sent with the call itself still wins over the file.
- Without the file setting the tool server uses the old bearer variable, as before.
- The tool server chart carries appVersion 0.2.10 and the agent workspace chart 0.9.10, so both images that contain the changed binary are built under new tags.

The rest of this ticket is the exact instruction for the model that does the work.

## 2. End goal
The OpenOva tool server (`products/openova-mcp`, Blueprint `bp-openova-mcp`) runs as a stdio child inside the agent workspace. On a `tools/list` or `tools/call` that carries no `_auth` token it uses a fallback bearer, which today is the value of `OPENOVA_MCP_BEARER`, read once when the process starts. After this ticket, when `OPENOVA_MCP_BEARER_FILE` names a file, the stdio server reads that file at every `tools/list` and every `tools/call` and uses its content (spaces and line ends trimmed) as the fallback bearer, so a bearer that a renewing process replaces in the file (by rename) is used from the next call on, with no restart. A missing, unreadable or empty file means no fallback bearer: the call is refused as unauthenticated, never answered with a bearer read earlier or with `OPENOVA_MCP_BEARER`. Without `OPENOVA_MCP_BEARER_FILE` the server behaves as on main. The HTTP transport keeps no fallback bearer. The README names the variable, and the `appVersion` of the tool-server chart moves from `0.2.9` to `0.2.10` and that of the agent workspace chart (`products/agenity`), whose image embeds the tool-server binary, from `0.9.9` to `0.9.10`.

## 3. The model (the law)
1. With `OPENOVA_MCP_BEARER_FILE` set (not empty after trimming spaces), the fallback bearer of the stdio server is the trimmed content of that file, read at every `tools/list` and every `tools/call`; `OPENOVA_MCP_BEARER` is not used.
2. A file that is missing, unreadable or empty after trimming gives no fallback bearer. No bearer read earlier is kept or reused.
3. Without `OPENOVA_MCP_BEARER_FILE` the fallback bearer is `OPENOVA_MCP_BEARER`, read once at start, as on main.
4. A bearer in the call's `_auth.token` or `_meta._auth.token` still wins over the fallback (the precedence of `extractBearer` is unchanged).
5. The HTTP transport has no fallback bearer; each request's `Authorization` header is its only request-scoped bearer (unchanged, `http.go` is not touched).
6. The names of both variables appear once in the code, in the constants `fallbackVar` and `fallbackFileVar` of `main.go`; the tests use the constants. No file outside `docs/` that does not name the tool bearer today starts naming it (the rule G6 of `scripts/check-agent-plane.py`).

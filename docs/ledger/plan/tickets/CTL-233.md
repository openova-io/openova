# CTL-233 — Console: Git-owned objects show Managed by Git

## In plain words

**The problem today.** The platform API now refuses a direct write of an object that Git owns, and it writes any other object only when the request carries a reason. The resource views of the console still offer scale, edit and delete on every object and send no reason, so these writes fail with an error the views do not explain. The apply page still shows a pull-request link and a commit message that the API no longer has.

**What changes.** An object that Git owns shows Managed by Git with the name of its owner, and the views offer no scale, edit or delete for it. Every other scale, edit, delete and apply asks for a reason and sends it to the API.

**Done means:**

- The overview of an object whose labels or owner references name a Flux owner shows Managed by Git with that owner and offers restart, but no scale and no delete.
- The YAML tab of such an object shows Managed by Git with the owner and offers Validate but no Apply.
- When the API answers 409 managed-by-git to a scale, delete or apply, the view switches to Managed by Git with the owner from the answer instead of showing an error.
- Scale, delete, the YAML apply and the multi-document apply each send the reason the person typed: in the body, and for delete in the address.
- No resource view reads a pull-request link, sends a commit message or opens the edit pull request any more.
- The console type check, its tests and its lint limits pass.

The rest of this ticket is the exact instruction for the model that does the work.

## 2. End goal
The resource views of the sovereign-admin console (`products/catalyst/bootstrap/ui`) follow the write rules of the platform API. For an object that Git owns, the Overview tab shows "Managed by Git: <owner>" and offers no Scale and no Delete (Restart stays), and the YAML tab shows the same line and offers Validate (dry-run) but no Apply. The owner comes from the object's detail payload, by the same rules the API uses, or from the API's answer 409 `managed-by-git` when the payload does not show it. For every other object, scale, delete, the YAML apply and the multi-document apply page ask for a reason and send it to the API. The pretend pull-request path is gone from the console: no view reads `giteaPRUrl`, sends `commitMessage` or calls the edit pull-request route.

## 3. The model (the law)
1. **Owner in Git, from the payload.** A new function `gitOwner(obj)` in `src/pages/sovereign/cloud-list/resource.api.ts` returns a string or `null`. Its rules and their order are those of `Owner` in `products/catalyst/bootstrap/api/internal/clusterwrite/clusterwrite.go`; the first rule that matches wins:
   - the label `kustomize.toolkit.fluxcd.io/name` is not empty: `Kustomization <namespace>/<name>`, the namespace from the label `kustomize.toolkit.fluxcd.io/namespace` (without it: `Kustomization <name>`);
   - the label `helm.toolkit.fluxcd.io/name` is not empty: `HelmRelease <namespace>/<name>`, the namespace from `helm.toolkit.fluxcd.io/namespace`;
   - an owner reference whose `apiVersion` contains `fluxcd.io`: `<kind> <object namespace>/<name>` of that reference;
   - the label `app.kubernetes.io/managed-by` equals `flux` in any case: `Flux`.
   The annotation `catalyst.openova.io/managed-by` and the label `managed-by` no longer count: the API does not read them.
2. **Owner in Git, from the answer.** The API also refuses the kinds of its intent lock, which no label shows. Its answer is 409 with the JSON body `{"error":"managed-by-git","code":"409","owner":"<owner>","detail":"..."}`. A new class `ManagedByGitError` (field `owner`) and a function `managedByGitError(status, bodyText)` in `resource.api.ts` turn that answer into an error of that class. Every call of `resource.api.ts` that reads a JSON answer, and `multiApplyYAML` of `src/pages/sovereign/resources/resources.api.ts`, throw it on that answer. Any other non-2xx answer still throws a plain `Error` with `HTTP <status>: <body>`.
3. **Managed by Git.** The owner of a view is the owner from the payload, else the owner of a `ManagedByGitError` the view has received. While it is set:
   - `ResourceActions` shows `Managed by Git: <owner>. Change it in Git; scale and delete are not offered.` (test id `resource-actions-managed-by-git`), hides the replicas field, Scale, Delete, the delete confirmation and the reason field, and keeps Restart. Restart is an operation and needs no reason.
   - `YamlEditor` shows `Managed by Git: <owner>. Change it in Git; Apply is not offered.` in its existing line `yaml-editor-managed-by`, hides Apply and the reason field, and keeps Validate (dry-run), which the API allows for any object.
   - The apply page shows `Managed by Git: <owner>. Nothing was applied; change it in Git.` (test id `apply-managed-by-git`) instead of the error box.
   - The catalog's "Edit IaC" mode of `YamlEditor` (prop `onCommit`) commits to Git itself, so it never shows an owner and keeps its button.
4. **The reason of a break-glass write.** `scaleResource`, `applyYAML` and `deleteResource` take a last parameter `reason`. Scale sends `{ replicas, reason }`, apply sends `{ yaml, reason }`, delete sends the query parameter `reason` (URL-encoded) because a DELETE has no body. `multiApplyYAML` sends `{ yaml, reason }`. Each view has one reason field (`resource-actions-reason`, `yaml-editor-reason`, `apply-reason`). The console does not check the length; the API answers 400 `break-glass-reason-required` below 10 characters and 403 `break-glass-owner-only` without the owner tier, and the view shows that error as it shows any other.
5. **Deleted.** `isFluxManaged` and `isManuallyManaged` of `resource.api.ts`; the edit pull-request branch of `YamlEditor` (its call of `editPRBlueprint`, the PR link, `orgFromObject`, `editPathFromObject`, the test seam `fluxOverride` and the button label `Open PR`); the fields `flux` and `giteaPRUrl` of `K8sMultiApplyResultEntry`, the field `commitMessage` of `MultiApplyRequest`, and the commit-message field, the `pull request` badge and the `open PR` link of the apply page. The API dropped these fields and refuses a request that still sends `commitMessage`.
6. **Not changed.** Restart, the dry-run, the viewer-tier banner, the type-the-name delete confirmation, the routes, the API and `src/lib/catalog.api.ts`.

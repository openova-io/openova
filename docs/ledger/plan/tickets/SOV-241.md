# SOV-241 — Follower regions pivot the image registry of the other kit workloads that run there

## In plain words

**The problem today.** After the hand-over of a Sovereign with two regions, the follower region still pulls the images of three kit workloads from the public registry: the browser exec proxy, the remote-desktop gateway and the model gateway. The hand-over writes their registry setting in the writer region only. Only the Continuum controller is moved to the follower's own registry today.

**What changes.** The hand-over also points these three workloads at the follower region's own registry, the way it already does for the Continuum controller. The chart test of the follower region checks each of the four and fails when one of them is left out.

**Done means:**

- In a two-region render of the cutover chart, the in-region pivot Job of a follower region is given the slots of bp-continuum, bp-k8s-ws-proxy, bp-guacamole and bp-newapi.
- Run against a copy of the kit, that Job writes the local registry into the global.imageRegistry of each of the four slots, and of no other slot.
- Removing the follower mark of any one of the four turns the follower test red.
- The render of a single-region Sovereign does not change.
- Every chart test of the cutover chart passes.

The rest of this ticket is the exact instruction for the model that does the work.

## 2. End goal
On a Sovereign with two or more regions, hand-over step 06 runs an in-region pivot Job in every follower region. That Job already writes `global.imageRegistry: 'registry.<fqdn>'` into the follower's own copy of kit slot 62 (bp-continuum), because the entry of slot 62 in `imageRegistryPivot.additionalHRs` of `platform/self-sovereign-cutover/chart/values.yaml` carries `followerRegions: true`. After this ticket the entries of slot 51 (bp-k8s-ws-proxy), slot 52 (bp-guacamole) and slot 80 (bp-newapi) carry the same mark, so the same Job writes their seam too, in the same commit it already pushes. The test `platform/self-sovereign-cutover/chart/tests/follower-region-pivots.sh` names the four slots in a list `FOLLOWER_SLOTS`. For each it asserts that the rendered Job is given the slot and that, after the real rendered Job script ran against a bare Git origin holding the real kit, the slot's `global.imageRegistry` on the origin's `main` reads `registry.<fqdn>`. For each it has one mutant: the chart rendered with that entry's mark removed, which must leave the slot unwritten. The template is not changed, and the single-region render is byte-identical. A person sees it this way: on the next fresh two-region installation, after the hand-over chain, the DaemonSet `catalyst-system/k8s-ws-proxy` of the follower region runs an image of `registry.<fqdn>` and is ready.

## 3. The model (the law)
1. **What the mark means.** An entry of `imageRegistryPivot.additionalHRs` with `followerRegions: true`, whose `name` is not in `imageRegistryPivot.excludeHelmReleases`, puts its `slotFile` into the environment variable `IMAGE_REGISTRY_SLOT_FILES` of the in-region pivot Job (`templates/secondary-pivot-script-configmap.yaml` line 197). The Job's script replaces the value of the one line of that slot file that starts with six spaces and `imageRegistry:` by `'registry.<fqdn>'` (line 101) and pushes the result to the follower's own Git service. Step 07 reads the same list for the writer region and ignores the mark.
2. **When an entry is marked.** Only when its HelmRelease runs unsuspended in a follower region and the follower's own registry holds the images the chart moves. The comment above the list says so; this ticket keeps that rule.
3. **The three entries meet it.**
   - Their slot files carry no `suspend:` and no label `catalyst.openova.io/region-role`, and a HelmRelease of the kit without that label runs in every region.
   - Each slot file has exactly one line `      imageRegistry: ''`.
   - The image helpers of the three charts replace only the first part of a `ghcr.io/openova-io/...` reference: `ghcr.io/openova-io/openova/<name>` becomes `registry.<fqdn>/openova-io/openova/<name>`. Images from another registry are not changed by the value.
   - Step 03's follower leg lists every `ghcr.io/openova-io/` image of the follower's running pods, Deployments, StatefulSets, DaemonSets, CronJobs and Jobs, adds the images of the pinned charts, and copies each to `registry.<fqdn>/<path without ghcr.io>` in the follower's own registry. So every image the mark moves is there before step 06 runs.
4. **What the mark rolls in a follower.** bp-k8s-ws-proxy: its DaemonSet, onto `registry.<fqdn>/openova-io/openova/k8s-ws-proxy`. bp-guacamole and bp-newapi: in a follower whose database pair is switched on (the state after `ready`), these two charts render no workload whose image follows `global.imageRegistry`, so nothing rolls; in a follower without the pair, their Deployments roll onto images that step 03 copied from that region's own pods. Step 06 waits only for the follower's GitRepository, not for a roll.
5. **Slots 56 and 57 are skipped.** The flow server (slot 56) and the flow emitter (slot 57) leave the kit with CTL-346, which comes before this ticket. Neither is marked.
6. **The test owns the list.** `FOLLOWER_SLOTS` in the test is the list of slots the follower Job must write. A slot added to or removed from the marks changes that list in the same change.
7. **Nothing else changes.** No template, no `Chart.yaml` (the release writer sets the version after the merge), no slot file, no baseline. Nothing is deleted.

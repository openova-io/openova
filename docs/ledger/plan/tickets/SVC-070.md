# SVC-070 — Function tests: identity and secrets charts

## In plain words

**The problem today.** The secret store, the sign-in service, the single sign-on bridge, the sign-in gate and the two secret-sync charts count as working when their Pods run. Nothing tests that the store is unsealed, that the realm answers, that the bridge finishes a pass, that the gate sends a stranger to sign in, or that the secret-sync webhook and stores answer.

**What changes.** Each of the six charts gets one test Pod that asks the service it installs a question and checks the answer. A render check per chart holds the Pod to the contract, and the contract lets a test read objects that have no namespace.

**Done means:**

- Each of the six charts renders one test Pod with the hook test, a deadline of 300 seconds and the restart policy Never, and renders none where its own gate switches it off.
- Each test asks its service a question and checks the answer; none of them writes data or creates a Secret.
- A render test per chart fails when that chart's test Pod breaks the contract, and it runs on every pull request that changes the chart.
- The contract checker and the runbook allow a cluster-wide read role beside the test Pod, and the checker's self-test shows it.
- The service-model guard counts six more charts with a function test.
- Every test policy that limits where its Pod may send lets it reach cluster DNS, and the network guard lists each test file that brings a policy as a named exception of this task.

The rest of this ticket is the exact instruction for the model that does the work.

## 2. End goal
`helm test` on a release of `bp-openbao`, `bp-keycloak`, `bp-sso-bridge`, `bp-oidc-gate`, `bp-external-secrets` or `bp-external-secrets-stores` runs one Pod that asks what the chart installs a question, checks the answer, and prints one last line `FUNCTION-TEST pass|fail <chart name> <reason>`. Each of the six charts has a render test `chart/tests/function-test-render.sh`, which CI runs with the chart's other tests on every pull request that changes the chart. The contract checker `scripts/check-function-test.py` and section 4.5 of `docs/RUNBOOKS.md` admit a ClusterRole and a ClusterRoleBinding beside the test Pod, which the stores test needs and later packages need too. The service-model guard counts six more charts with a function test. The two test files that render a CiliumNetworkPolicy (`bp-sso-bridge`, `bp-oidc-gate`) let the test Pod reach cluster DNS, and each has a named exception line in `scripts/network-guards-exceptions.tsv`, so the network guards stay green with an unchanged baseline. No version line and no pin changes: CI writes chart versions after the merge.

## 3. The model (the law)
1. **The contract.** It is section 4.5 of `docs/RUNBOOKS.md` and the checker `scripts/check-function-test.py` (both from package SVC-060). A chart that has a function test ships one file `chart/templates/tests/function-test.yaml`. It renders one Pod named `<release>-function-test`, with the annotations `helm.sh/hook: test` and `helm.sh/hook-delete-policy: before-hook-creation,hook-succeeded`, the label `catalyst.openova.io/function-test: "true"`, `restartPolicy: Never` and `activeDeadlineSeconds: 300`. The test sends a request and checks the response against what the chart installs. It exits 0 on pass and non-zero on fail, and its last line is `FUNCTION-TEST <pass|fail> <chart name> <reason>`. It needs nothing outside the cluster, uses an image the chart already uses or one the kit already pulls, renders nothing when the chart's own gate renders nothing, never creates a Secret, and every container requests cpu and memory. Every network call of a test has a time limit, so each test ends well inside its 300 seconds.
2. **The six tests.** Each `function-test.yaml` is the block of field 5 of the same name, byte for byte.

   | Chart | Renders when | Image | The test passes when |
   |---|---|---|---|
   | `bp-openbao` | `autoUnseal.enabled` is true (only then does the chart initialise and unseal the store itself) | `harbor.openova.io/proxy-dockerhub/alpine/k8s:1.31.4`, or `functionTest.image` | `GET <address>/v1/sys/health?standbyok=true` answers 200 with `"initialized":true` and `"sealed":false`; and, when `autoUnseal.kubernetesAuth.enabled` is not `false`, a Kubernetes-auth login on `auth/<mountPath>` for the role `<role>` (default `external-secrets`) with the test Pod's own service-account token is refused with `service account name not authorized` or `namespace not authorized`. The address is `autoUnseal.baoAddress`, else `http://<subchart fullname>.<namespace>.svc.cluster.local:8200`. |
   | `bp-keycloak` | `sovereignRealm.enabled` is true | the same kubectl image, or `functionTest.image` | `GET http://<subchart fullname>.<namespace>.svc.cluster.local:<keycloak.service.ports.http, default 80>/realms/<sovereignRealm.name>/.well-known/openid-configuration` answers 200, and its `issuer` is `https://<gateway.host>/realms/<realm>` when `gateway.host` is set, else any issuer that ends in `/realms/<realm>`. |
   | `bp-sso-bridge` | `enabled` is true | the chart's own image (helper `bp-sso-bridge.image`), or `functionTest.image` | within 240 seconds, the log of the last 330 seconds of the Deployment `sso-bridge-reconciler` holds a line `tick complete in`: one reconcile pass that minted a Keycloak token and an OpenBao token has finished.    | `bp-oidc-gate` | at least one entry of `instances[]` is not disabled and has a hostname (helper `bp-oidc-gate.instanceHostname`) | the kubectl image, or `functionTest.image` | every such gate's Service `oidc-gate-<name>` answers an unauthenticated `GET /catalyst-function-test` with HTTP 302 to a Location that starts with `https://auth.<sovereignFQDN>/realms/<realm>/protocol/openid-connect/auth`. A ServiceAccount, Role (create `externalsecrets`) and RoleBinding give the Pod that right. The objects use `external-secrets.io/v1` when the cluster serves it, else `v1beta1`. |
   | `bp-external-secrets-stores` | the chart renders at least one ClusterSecretStore | `webhookGate.image` (the kubectl image), or `functionTest.image` | every ClusterSecretStore this release renders (`clusterSecretStore.name` when `clusterSecretStore.enabled`, and `<peerStores.namePrefix><peer>` for each peer of the helper `bp-external-secrets-stores.peers`) reports the condition `Ready` `True` within 180 seconds. A ServiceAccount, a ClusterRole (get `clustersecretstores`) and a ClusterRoleBinding give the Pod that right; their names are `<namespace>-<release>-function-test`. |

   `<subchart fullname>` is computed the way the subchart computes it: `fullnameOverride`, else the release name when it contains the chart name (`openbao`, `keycloak`, or the subchart's `nameOverride`), else `<release>-<name>`.
3. **The checker and the runbook.** A ClusterSecretStore has no namespace, so no Role can grant reading it, and the checker's rule FT4 refuses every kind beside the Pod other than ServiceAccount, Role, RoleBinding, NetworkPolicy and CiliumNetworkPolicy. This ticket adds `ClusterRole` and `ClusterRoleBinding` to that list: in the checker's header, in its constant `HELPERS`, and in a new self-test case `a ClusterRole and a ClusterRoleBinding beside the Pod are allowed`. Rule FT4 still refuses every other kind, a Secret among them. Section 4.5 of the runbook names the two kinds in its list and says when they are used. Nothing else in either file changes.
4. **The render tests.** Each chart gets `chart/tests/function-test-render.sh`, the block of field 5 of that name, byte for byte. Each first runs the checker's self-test, builds the chart's dependencies when `charts/` is empty, then renders every shape of item 2 and checks it with the checker (`--absent` for each gate under which the test renders nothing) and with a few exact text checks. CI's workflow `Chart tests (PR)` runs every `chart/tests/*.sh` of a changed chart, so these run on every later pull request that changes one of the six charts.
5. **The baseline.** In `scripts/service-model-baseline.yaml` the value of the line `  G6.function-test-charts: <n>` rises by exactly 6, written by the command of step 30. The step adds 6 to the value it finds; it never writes a fixed number. No other line changes.
6. **The network guards.** Two rules hold for every test file that renders a policy.
   - Guard G2 of `scripts/check-network-guards.py` refuses a policy kind outside the policy chart unless the file has a line in `scripts/network-guards-baseline.tsv` or in `scripts/network-guards-exceptions.tsv`. The baseline may only shrink: its tool (`check-network-guards.py baseline`) refuses an added line. The exceptions file is for an object that a package's own work defines, with that package as owner. So step 31 appends one exception line for each of the two test files, owner `SVC-070`, and the baseline does not change.
   - `scripts/check-netpol-egress-completeness.py` (the check `Every constrained workload keeps cluster DNS`) renders every chart that has a policy template, test hooks included, with the API `cilium.io/v2`. Every group of policies that declares egress must allow 53/UDP and 53/TCP to the Pods `k8s-app: kube-dns` in `kube-system`. The sso-bridge test policy names that rule beside the Kubernetes API; the oidc-gate test policy already did.
7. **Nothing else changes.** No `values.yaml`, no other template, no kit slot, no `Chart.yaml`, no `blueprint.yaml`, no version line and no pin. Package FND-011 is merged: CI writes the version of every chart a merge changed. No kit slot sets `spec.test`, so Flux runs none of these tests yet; package SVC-130 switches them on. Nothing is deleted.

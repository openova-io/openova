# AIP-157 — Nothing reads the long-lived bearer

## In plain words

**The problem today.** Since AIP-156 nothing mints the year-long Organization administrator bearer any more, but the two doors that install the agent workspace and the per-Organization tool server still point those installs at the Secret and the secret-store path of that bearer. The tool server, run as a child of the agent workspace, still takes a bearer from its environment when no bearer file is set, so a standing bearer handed to it in that way would still be used.

**What changes.** Both install doors stop wiring the bearer's Secret, its verify key and the secret-store path. The stdio tool server takes its fallback bearer only from the bearer file and never from the environment.

**Done means:**

- An agent workspace installed through the Application door or the BSS door carries only the Organization tenant host for its tool server, and no bearer Secret, verify-key Secret or secret-store path of a bearer.
- A per-Organization tool server installed through the Application door is stamped with exactly its mode, the Sovereign name, the Organization and its route, and no verify key of a seeded bearer.
- The stdio tool server with no bearer file answers a call without a token as unauthenticated, even when a valid bearer is set in its environment.
- The tool server's code, chart and README no longer name the environment bearer variable; the bearer-file variable stays.
- The agent-plane and API-structure guards pass with their stored numbers lowered by their own tools.

The rest of this ticket is the exact instruction for the model that does the work.

## 2. End goal
After this package no part of the platform reads or wires the year-long Organization administrator bearer whose writer AIP-156 deleted. The Application-CR install door (`defaultedParameters` in `products/catalyst/bootstrap/api/internal/handler/application_parameters.go`) no longer stamps `openovaMCP.bearerSecret`, `openovaMCP.rs256PubkeySecret` and `openovaMCP.mcpBearer.externalSecret` into a `bp-agenity` install, nor `auth.rs256PubkeySecret` into a per-Organization `bp-openova-mcp` install. The BSS-door GitOps overlay (`orgTenantBPAgenity` in `organization_gitops.go`) keeps `openovaMCP.tenantHost` and drops the same three keys. The stdio tool server (`products/openova-mcp/cmd/openova-mcp`) reads its fallback bearer only from the file `OPENOVA_MCP_BEARER_FILE` names; the environment variable it read before is gone from its code and README. The agent workspace chart has ignored these values since AIP-155 and reads its tool identity from the renewed bearer file, so nothing changes for a running workspace. The appVersion of `bp-openova-mcp` becomes 0.2.12 and that of `bp-agenity` 0.9.12, so the next release carries the tool server binary.

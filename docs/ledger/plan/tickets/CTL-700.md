# CTL-700 — Pull-request mode of the commit library

## In plain words

**The problem today.** Every change the platform commits to Git goes straight to the branch that the clusters apply. Some changes must wait until a second person has approved them, and the commit library has no way to hold a change for approval.

**What changes.** The commit library can put a change on a branch of its own and open a pull request for it, so that it reaches the clusters only when a person merges it. The package that commits intent objects passes this choice through and reports the change as waiting for approval. Nothing that runs today uses the new mode, and the default stays a direct commit.

**Done means:**

- A change in the new mode lands as one commit on its own branch, with one pull request into the main branch, and the main branch does not change.
- A change that changes nothing, or that names an outdated version of a file, creates no branch, no commit and no pull request.
- The same change sent again after a failure makes no second commit and returns the pull request that is already open.
- In the new mode the intent package answers at once with the status 202, the state awaiting-approval and the address of the pull request, and does not wait for the cluster.
- A change without the new mode is committed to the main branch exactly as before.
- The contract of the commit library describes the new mode.

The rest of this ticket is the exact instruction for the model that does the work.

## 2. End goal
The commit library `core/controllers/pkg/gitwrite` (CTL-110) gets a second way to deliver a change. `Change.Mode` is `""` or `"direct"`, which is today's direct commit, or `"pull-request"`. In the mode `"pull-request"` the library commits the files to a new branch `change/<ChangeID>`, opens a pull request from it into `main`, and returns its address in `Result.PullRequestURL`. `main` is not written. A person merges the pull request in Gitea, and the merge reaches the cluster like every commit to `main`. The package `products/catalyst/bootstrap/api/internal/intent` (CTL-160) passes the mode through: `Submit` takes it as an optional last argument, and in the mode `"pull-request"` it returns at once with the state `awaiting-approval`, the address of the pull request and the HTTP status 202, without waiting for the cluster. Contract C4 (`docs/contracts/C4-git-layout-and-commit-library.md`) gets the new fields and a semantics item 11. One embedded patch makes the whole change. No route, no console page and no controller uses the mode yet; its first user is AIP-245.

## 3. The model (the law)
The patch of this ticket is complete and embedded. These are the rules it implements, so that a reader can check them; you do not write any of it.

1. **The mode is a field.** `type Mode string` with `ModeDirect Mode = "direct"` and `ModePullRequest Mode = "pull-request"`. `Change.Mode` is the last field of `Change`; `Result.PullRequestURL` is the last field of `Result`. The zero value `""` means `ModeDirect`, so every existing caller keeps its behaviour. The mode is never the default.
2. **Refusals before any request to Gitea.** A mode other than `""`, `"direct"` and `"pull-request"` returns `ErrInvalid`. The mode `"pull-request"` with a base branch other than `main` (`Repo.Branch` other than `""` and `"main"`) returns `ErrInvalid`. The field checks, the path policy and the Secret scan run first, as for a direct change.
3. **The branch.** `func ChangeBranch(changeID string) string` returns `"change/" + changeID`. One change has one branch.
4. **Pull-request mode, in order** (`core/controllers/pkg/gitwrite/pullrequest.go`). (a) Read the files on `main`. If every file already has the wanted state, return the head of `main` with `Committed` false and create nothing. (b) If an `IfMatch` does not match the file on `main`, return `*ConflictError` and create nothing. (c) Create the branch `ChangeBranch(ChangeID)` from `main`; an existing branch is kept. (d) Read the files on the branch. If they already have the wanted state, an earlier call with the same change committed them: commit nothing again and take the head of the branch. Otherwise commit the files in one call of the batch API, with the author, committer and message of a direct commit. (e) Open a pull request from the branch into `main`, whose title is the summary and whose body is the commit message; when one is open already, the existing one is returned (the Gitea client's own handling of HTTP 409). (f) Return `Commit` (the commit on the branch), `Committed`, the files with their blob SHAs, and `PullRequestURL`. Nothing waits for the merge and nothing reads the pull request again.
5. **Errors.** A failure of Gitea is wrapped and classified as in a direct commit: HTTP 5xx, a time-out or a connection error is `ErrUnavailable`. A pull request without an address is an error.
6. **The in-memory Gitea** (`internal/giteadouble`) answers the two new calls as Gitea does: `POST .../branches` copies the old branch (`main` by default), answers 409 for an existing name; `POST .../pulls` opens a pull request, answers 404 for a missing head branch and 409 for an open one with the same head and base; `GET .../pulls` lists the open ones. Its branch-head call answers 404 for a branch other than `main` that nothing has read, written or created, which is what the client's "create the branch when it is missing" relies on. `PullRequests()` returns what it opened, and `URLBase` starts every address. It never merges. The fake writer (`gitwrite/fake`) runs the library against it, so the fake has the mode as well.
7. **intent.Submit.** The new last parameter `mode ...gitwrite.Mode` is optional; it may be given at most once, and an unknown value returns `ErrInvalid`, before any read or commit. Existing calls with no mode compile and behave as before. In the mode `"pull-request"`, when the library returns a `PullRequestURL`, `Submit` returns at once: `State` `awaiting-approval`, `PullRequestURL` the address, `Commit` the commit on the branch, `ETag` the blob SHA of the first file on the branch, `Applied` false, and it opens no cache watch. A change that is a no-op compared with `main` is not given to the library in that mode and is reported as a no-op, as before.
8. **The state and the status of an answer.** `Outcome.State` is `""` when the change was applied within `SyncWait`; `committed` (`StateCommitted`) when a change was committed or was a no-op but the cache did not show it applied in time; `awaiting-approval` (`StateAwaitingApproval`) in the pull-request mode. `func (o Outcome) Status(applied int) int` returns `applied` (the route's own status) when `State` is `""` and 202 otherwise. These are the `state` field and the status of the 202 answer of an intent route.
9. **The contract.** `docs/contracts/C4-git-layout-and-commit-library.md` shows `Mode`, the two new fields and `ChangeBranch` in its Go listing and states item 11 of its semantics, the rules 2 to 4 and 7 above.
10. **Not in this package.** No route, console listing, read route of pull requests or controller uses the mode (AIP-245 is its first user). No polling of a pull request's state. Per-robot tokens (CTL-126). No file outside the ten of field 14 changes.

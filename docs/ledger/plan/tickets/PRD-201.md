# PRD-201 — bp-bge chart to the serving rules

## In plain words

**The problem today.** The embeddings Blueprint runs two servers with floating model names, reads a model-hub token from a Secret into an environment variable, opens a public endpoint and ships its network policy switched off with the model hub open. It has no function test, and nothing proves that the image it names can load and serve a model under the platform's pod rules.

**What changes.** The chart serves one pinned embedding model and one pinned reranker from one CPU server, behind a ClusterIP Service that only the model gateway and the release's own test may reach. The token becomes one mounted file, a function test checks the vector length, and a test in CI runs the real image against both model sources.

**Done means:**

- With home or enabled false the chart renders only its Namespace.
- Every model is named by a digest or by a 40-character revision; a floating reference, a missing revision or an unknown parameter fails the render with a message that names it.
- No template of the chart contains secretKeyRef, and the product guard's baseline has no entry for it.
- The server runs as a numeric user with a read-only root, no capability and no service-account token, and its start-up probe allows 300 seconds.
- The network policy is on by default, admits the serving port only from the model gateway's namespace and from the function test, and opens the model hub, at public addresses only, only when asked; the tree's network guard renders that policy and finds cluster DNS in it.
- The chart's own test passes only when the server returns a vector of the declared dimensions.
- The chart tests of the pull request run the real server image: it fetches both models from the hub, the copies of both pulled from a registry by digest are byte for byte the packed files, and both answer an embedding and a rerank.

The rest of this ticket is the exact instruction for the model that does the work.

## 2. End goal
`platform/bge` is the CPU embeddings and rerank service of the model plane. Its chart runs one Infinity server (`docker.io/michaelf34/infinity:0.0.78-cpu@sha256:5401a057f16f82a7a1202369f674dc15695fe37d8517f3c0263fdfb88b2e2717`, MIT) that serves the embedding model `embedding` and the optional reranker `reranker` on port 7997, both with `--engine optimum --device cpu --lengths-via-tokenize`, under `--url-prefix /v1`. By default the models are `hf://ibm-granite/granite-embedding-107m-multilingual` at `d6cffd338414d6a1c1f5decfad5fec62eebc90d5` (384 dimensions) and `hf://cross-encoder/mmarco-mMiniLMv2-L12-H384-v1` at `1427fd652930e4ba29e8149678df786c240d8825`. The chart's parameters are the Blueprint's `configSchema` (`home`, `enabled`, `embedding`, `reranker`, `cache`), and the chart refuses at render what that schema refuses. With `home` or `enabled` false it renders the Namespace only; nothing installs the chart yet (PRD-208 adds the kit slot). A person sees it this way: the check `chart/tests/*.sh — platform/bge` of the pull request is green, and its log shows `model-load: all cases passed` after a real run of the server.

## 3. The model (the law)
1. The Service is `ClusterIP`. The chart renders no `HTTPRoute`, `Ingress`, `Gateway` or `GRPCRoute`, and the Blueprint declares no endpoint.
2. The chart renders the release namespace as a Namespace with the restricted Pod Security labels, always. Every other object renders only when `home` and `enabled` are both true.
3. The server image is named by digest. A model `source` is `oci://<host>/<path>@sha256:<64 hex>` or `hf://<owner>/<name>`; an `hf://` source needs `revision`, 40 lowercase hexadecimal characters, and an `oci://` source takes none. Both models come from the same kind of source. Any other value fails the render.
4. The Pod runs as user and group 10001 with `runAsNonRoot`, the `RuntimeDefault` seccomp profile, a read-only root file system, every capability dropped, no privilege escalation and `automountServiceAccountToken: false` on the Pod and on its ServiceAccount. `HOME`, `INFINITY_HOME` and, for `oci://` models, `HF_HOME` are on the `/tmp` emptyDir.
5. One embedding model and at most one reranker, served by one server, `replicas: 1`. The update strategy is `Recreate` when `cache` makes the weights a claim, otherwise a rolling update with no unavailable replica.
6. The start-up probe (`GET /health`, every 10 seconds, 30 failures) lets 300 seconds pass before a failure counts.
7. No credential is a value and no template contains `secretKeyRef`. A model-hub token is the object `hf-token` of the SecretProviderClass that `hubToken.secretProviderClass` names, mounted by the Secrets Store CSI driver at `/var/run/secrets/openova/hf-token`; `HF_TOKEN_PATH` names that file. A token with no `hf://` model fails the render.
8. An `oci://` model is a model image: its files are in `/model`, and it holds a statically linked `/bin/cp`. One init container per model runs `/bin/cp -R /model/. /models/<role>`; the server reads `/models` read-only with `HF_HUB_OFFLINE=1`. An `hf://` model is fetched by the server at its revision into `/models/hf` (`HF_HOME`).
9. The release's one NetworkPolicy, on by default, selects every Pod of the release. Ingress: the serving port, from namespace `networkPolicy.gatewayNamespace` (`model-gateway`) and from the release's function test. Egress: cluster DNS, the server's port, and TCP 443 to public addresses (every address except 10.0.0.0/8, 100.64.0.0/10, 169.254.0.0/16, 172.16.0.0/12 and 192.168.0.0/16) only when `networkPolicy.hubEgress` is true (default false). An `hf://` model with the policy on and the hub egress off fails the render.
10. `templates/tests/function-test.yaml` meets `docs/RUNBOOKS.md` section 4.5: it waits for `GET /health` until 60 seconds before its bound, posts one text to `/v1/embeddings` for `embedding.servedName`, and passes only when `.data[0].embedding` is a list of exactly `embedding.dimensions` numbers. Its Pod's name label is not the server's, so the Service never selects it.
11. Deleted: the TEI containers on ports 8080 and 8081, the two `secretKeyRef` uses, the values `bge.*`, `catalystBlueprint`, `serviceMonitor`, `hpa` and `configMap`, the templates `configmap.yaml`, `hpa.yaml` and `servicemonitor.yaml`, the Service annotations for the old gateway, the public endpoint, the active-active topology and the `metrics: prometheus` declaration of the Blueprint (no ServiceMonitor is rendered; it declares `metrics: none`).
12. Baselines only fall or count what was added: the product guard's G-P3 entry for bge goes, the secret register's allow-list line for the chart goes, and the count of charts with a function test rises by one.
13. The tree's DNS guard `scripts/check-netpol-egress-completeness.py` renders the chart with `home`, `enabled` and `networkPolicy.hubEgress` true (its `RENDER_VALUES` entry), so it judges the release's policy and not an empty render. The guard and its other entries do not change.

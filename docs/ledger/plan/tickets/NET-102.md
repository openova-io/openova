# NET-102 — Registry in the Sovereign status, checked against the live cluster

## In plain words

**The problem today.** Every provider module now outputs one record of the network of a Sovereign: its ranges, its MTU and the mesh name and number of each cluster. Nothing in a running Sovereign holds that record, and nothing checks that the clusters really run with those values. A wrong range or a wrong cluster number would go unseen until the mesh between the regions breaks.

**What changes.** The Sovereign object gets a place for the record in its status, in exactly the form the modules output. A new required gate check reads that record in every region and fails when the Cilium configuration of the region names another range, MTU, cluster name or cluster number.

**Done means:**

- The Sovereign definition describes status.network with the same fields, types and ranges as the network registry that the provider modules output.
- The first valid sample Sovereign carries a registry in its status, and that registry passes scripts/check-network-registry.py.
- The schema bundle of the sovereign-admin API matches the changed definition.
- Gate check NET-G08 is required in the gate manifest and names its file.
- NET-G08 fails a region when its Sovereign object is missing, has no registry, or names a pod supernet, MTU, cluster name or cluster number that differs from the Cilium configuration of that region.
- The tests of the new check run on every pull request without a cluster.

The rest of this ticket is the exact instruction for the model that does the work.

## 2. End goal
The cluster-scoped kind `Sovereign` (`sovereigns.catalyst.openova.io`, version `v1alpha1`) declares `status.network`: the network registry of the Sovereign, in exactly the form of the output `network_registry` of the provider modules (`infra/providers/PROVIDER-INTERFACE.md`, section 2.1), so that the writer of the Sovereign object can copy that output unchanged and `scripts/check-network-registry.py` can check what is stored. The first valid sample of `products/catalyst/chart/crds/tests/sovereign-sample-valid.yaml` carries such a registry, and the schema bundle `products/catalyst/bootstrap/api/internal/intent/crds/schemas.json` is regenerated from the changed definition. The acceptance suite has the gate check NET-G08 "Registry equals live values", in state `required`: in every region the one Sovereign object of that cluster holds `status.network`, and the ConfigMap `kube-system/cilium-config` of that region names the same pod supernet (`ipv4-native-routing-cidr`), the same MTU (`mtu`), and a cluster name (`cluster-name`) and cluster number (`cluster-id`) that one entry of `status.network.regions` holds.

## 3. The model (the law)
1. `status.network` of `products/catalyst/chart/crds/sovereign.yaml` is an object with exactly the five fields of the registry document: `podSupernet` (string), `mtu` (integer, 1280 to 9000), `regionSeparation` (`none`, `zone` or `site`), `controlPlaneAccess` (object with the two string lists `adminCIDRs` and `provisionerCIDRs`) and `regions` (list of 1 to 6 objects). All five are required inside `status.network`; `status.network` itself is optional, so every stored Sovereign object stays valid.
2. Each entry of `status.network.regions` has the ten required fields `code` (1 to 64 characters), `cloudRegion` and `az` (at least 1 character), `clusterName` (a lower-case label of at most 32 characters), `clusterID` (integer, 1 to 255), `nodeCIDR`, `podCIDR`, `serviceCIDR`, `edgeAddress` (strings) and `egressAddresses` (list of at least one string), and the one optional field `meshEndpoint` (object with the required `ips`, a list of at least one string, and `port`, an integer from 1 to 65535). The field names are those of the validator `scripts/check-network-registry.py` (its sets `TOP_KEYS`, `ACCESS_KEYS`, `REGION_KEYS`, `REGION_OPTIONAL` and `MESH_KEYS`). The rules between fields (unique cluster names and numbers, ranges that do not overlap, the supernet) stay in that validator. The definition carries no CEL rule for them. Every field of `status.network` is read in this change: NET-G08 reads `podSupernet`, `mtu`, `clusterName` and `clusterID`; the validator reads the whole registry of the sample (acceptance check A4); acceptance check A3 compares every field name with the validator.
3. Nothing else of the definition changes: not `spec`, not `status.regions`, not the printer columns. The definition names no cloud provider in the new text.
4. The first document of `products/catalyst/chart/crds/tests/sovereign-sample-valid.yaml` (sample 1, one region `fsn1`) gains a `status` with a one-region registry that `scripts/check-network-registry.py` accepts. The test `TestValidateSamples` of `products/catalyst/bootstrap/api/internal/intent` validates the first document of each sample file against the definition, so this sample proves that the schema accepts a registry.
5. `products/catalyst/bootstrap/api/internal/intent/crds/schemas.json` is written by its own test (`INTENT_WRITE_SCHEMAS=1`) and by nothing else. Only its line of the Sovereign kind changes.
6. Gate check NET-G08 is one file, `tests/acceptance/sovereign/internal/suite/check_network_registry.go`, that calls `RegisterCheck` in `init()`. It records one step per region, `NET-G08.<n>`. A step reads, with `kubectl get` only, the Sovereign objects of the region and the ConfigMaps of `kube-system`. It fails when the region has no Sovereign object or more than one; when the object has no `status.network`; when `cilium-config` is missing or lacks one of the keys `ipv4-native-routing-cidr`, `mtu`, `cluster-name`, `cluster-id`; when `ipv4-native-routing-cidr` and `podSupernet` name different networks; when `mtu` differs; when no entry of `status.network.regions` has the `cluster-name` of the region as `clusterName`; or when `cluster-id` differs from the `clusterID` of that entry. It records the names of the Sovereign objects, the four live values and the registry values it compared.
7. The test file `check_network_registry_test.go` uses the fake kubectl of `fake_kubectl_test.go`. It holds one passing case for each way a value may be written and one failing case for each failure of item 6. The two new files hold no `//nolint` and no `#nosec` comment.
8. In `docs/ledger/gates.yaml` the entry NET-G08 moves from `state: not-built` to `state: required` and gains the line `implementation: tests/acceptance/sovereign/internal/suite/check_network_registry.go`. No other line of the file changes.
9. No cluster is changed. Until the writer of the Sovereign object fills `status.network`, NET-G08 fails on every Sovereign with the reason "has no Sovereign object" or "has no status.network". That is the truth, and the check must not hide it.

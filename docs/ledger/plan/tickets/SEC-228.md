# SEC-228 — A library value given from outside: source external, no generator, no PushSecret

## In plain words

**The problem today.** A Secret whose value is given from outside, such as a cloud credential or a value another chart writes, cannot move into the secrets library today. The library always adds a generator and a push for a synced value, so where the store holds no value yet it makes one up, and a cloud credential must never be made up. Nobody has shown either what the secrets controller does with a Secret that Helm created and kept when a library value of the same name replaces it.

**What changes.** A synced value can say that it is given from outside. It is then only read from the store, never generated or pushed, and it names who writes it; until that writer has written it, nothing is written. A test against the pinned controller release shows what happens to a Secret that Helm kept.

**Done means:**

- A value marked as given from outside renders no generator and no push in any region, only the ExternalSecrets that read it.
- Its ExternalSecret and each copy read the value's path in the store, with the template and the joined values, and name who writes that path.
- A value given from outside without a named writer, with a length, symbols, a region setting or mounted copies, or joined with a generated value, fails the render with a message that says why.
- While the store's path is empty the ExternalSecret is not ready and writes nothing, so no value is ever made up.
- A test against the pinned External Secrets release shows that an ExternalSecret that owns its target takes over a Secret Helm kept (the same object), is refused when its template does not carry the kept Secret's type, and creates nothing while the store's path is empty.
- The console, Axon and metrics charts, the charts that use the library today, render byte for byte what they rendered before.

The rest of this ticket is the exact instruction for the model that does the work.

## 2. End goal
A chart that declares a synced value in `generatedSecrets` can mark it `source: external`: a value given from outside, such as a cloud credential that the hand-over writes (SEC-229) or a value another chart produces. Such a value renders no Password generator and no PushSecret, in the primary region or any other; its ExternalSecret `<name>` and each of its copies only read `openova/apps/<ns>/<name>/e<epoch>`, with the `template`, `copies` and `join` of SEC-219, and carry the annotation `secrets.openova.io/writer` with the required input `writer`, who writes that path. While the path is absent the ExternalSecret is not ready and writes nothing, so a value given from outside is never generated. The chart test `chart/tests/eso-takeover/` holds the fact X3 of the spike SEC-227 at the pinned External Secrets release 0.10.7: an ExternalSecret with `creationPolicy: Owner` whose target is a Secret that Helm created and kept (`helm.sh/resource-policy: keep`) takes that object over. A chart without `source`, or with `source: generated`, renders exactly what it rendered before.

## 3. The model (the law)
1. `source` is an input of a synced value: `generated` (the default) or `external`. Any other value fails the render. `source` and `writer` on a mounted value fail the render.
2. A value with `source: external` renders no Password, no PushSecret and no line of the birth plan, in every region.
3. Its ExternalSecret `<name>` and each copy read `openova/apps/<ns>/<name>/e<epoch>` (property `password`, key `password`) and each joined value at its own path under its own name, with SEC-219's `template`. Each carries the annotation `secrets.openova.io/writer` with the value of `writer`, beside `secrets.openova.io/register-id`.
4. `writer` is required on an external value that is not joined: a string of printable ASCII, not blank. It is refused on a generated value and on a joined value (one writer writes every path of one Secret).
5. An external value takes no `length`, `symbols`, `sharedAcrossRegions` or `mountedCopies`: it is never generated or pushed here. A `join` names only values of the same source.
6. While the path is absent the ExternalSecret is not ready and writes nothing: the library sets no `deletionPolicy` (default `Retain`). A value given from outside is never generated by the library.
7. The register entry of `registerId` names the writer: the register's fields are fixed (`id`, `namespace`, `name`, `class`, `consumer`, `reason`, `removal`, `reviewBy`), and an entry is added by the package that adds its Secret (the header of `scripts/secret-guard-baselines/secret-object-register.yaml`), so the roll-out that adds the entry writes the writer into its text. The library names it on the object, in the annotation.
8. Without `source`, or with `source: generated`, every object is what the library rendered before, byte for byte. No chart version line changes: the library stays at version 0.1.0.
9. Fact X3, tested at External Secrets 0.10.7: an ExternalSecret with `creationPolicy: Owner` whose target is a Secret that Helm created and kept takes the object over (the same uid, the ExternalSecret its controller owner); a `template` sets its `type` and a Secret's type cannot change, so a template without the kept Secret's own type is refused and the Secret stays Helm's; while the store's path is absent nothing is written and none is created. The test builds External Secrets, so no workflow runs it: it is run again when the pin moves (README).

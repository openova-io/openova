# SEC-154 — Flux renders bootstrap Secrets from one seed: pull login, object storage

## In plain words

**The problem today.** Every control-plane node still carries the registry pull login and the object storage login in its start-up data as whole Secret manifests. Only their values need to be there before Flux runs; the rest costs bytes against the start-up data limit of the cloud. The guard that lets a Secret template into Git checks the form of a template but not where its values come from, so a template whose value sits in a committed file would pass.

**What changes.** First boot writes only the values of these two Secrets, into the one seed Secret it already creates, and Flux renders them from files in Git. The cloud account credentials stay in the start-up data exactly as they are today: moved the same way they would make the start-up data of one cloud larger, because they carry a whole worker's first-boot text that travels compressed today. A Sovereign installed earlier adds the missing values to its seed from its own Secrets before anything renders from it. The guard now also refuses a template whose names can come from a committed file, and a Flux file it cannot read.

**Done means:**

- A fresh control-plane node's start-up data holds no manifest of the pull login or the object storage login, only their values in the seed file, on both clouds and in both region roles, and it writes the cloud credentials file exactly as before.
- The pull login and the object storage login that Flux renders from the seed have the same names, namespaces, types, keys, values and reflector annotations as the ones first boot wrote before.
- On a Sovereign installed before the change, whose seed lacks these values, the seed gets them from its live Secrets before anything renders from it, no value the seed already holds changes, and a second run changes nothing; when one of these Secrets, a key or a value is missing, nothing is written, the log names it and the kit waits.
- Guard G1 refuses a Secret template whose name is also an inline substitute or a key of a committed ConfigMap source, whose folder no Kustomization renders from a Secret, or whose Kustomization it cannot read, and passes every template on the tree.
- Every control-plane start-up data surface of both clouds and both region roles is smaller than on main and every worker surface is the same, as the size check records against the base of the pull request; nothing is packed that is not packed today.
- The check that renders every root of the kit passes, unchanged.
- The required check that the Flux controllers carry a pull credential passes: it finds the pull login in its template, which Flux renders before the kit; it still fails when the login has no source, sits in another namespace, or the kit does not wait for it.

The rest of this ticket is the exact instruction for the model that does the work.

## 2. End goal
The control-plane start-up data of every pack carries no manifest of `ghcr-pull` or `object-storage` (namespace `flux-system`). Their values join the five values of SEC-153 in `/var/lib/catalyst/bootstrap-seed.env`, from which first boot creates the seed Secret `flux-system/bootstrap-seed`, and they are templates under `clusters/_template/bootstrap-secrets`, which the Flux Kustomization `bootstrap-secrets` renders with its path of main. `cloud-credentials` stays as on main: the packed `write_files` entry of the template, applied server-side and shredded with the seed file (revision 2). Every control-plane surface of the worst-case start-up data of both providers and both region roles is smaller than on main and every worker surface is the same; the check `packs` records the comparison with the base of the pull request. A Sovereign installed between SEC-153 and this change holds the two Secrets and a seed without their values: the Job `bootstrap-seed-build`, which runs again because its template changes, adds them from the live Secrets before `bootstrap-secrets` may render. Guard G1 (`tools/guards/cmd/secret-templates`) passes a template only when every name it references comes only from a Secret source of the Kustomization that renders it, and reports a Flux Kustomization it cannot read. The guard `scripts/check-flux-controller-pull-credential.sh` (the required check "Flux controller ServiceAccounts carry a pull credential") finds `ghcr-pull`, the Secret that bp-flux's ServiceAccount patch names, in its template, counted only because the Kustomization `bootstrap-kit` waits for `bootstrap-secrets` (revision 3).

## 3. The model (the law)
1. Start-up data carries values, not manifests. Each byte added to the template must be there before Flux and OpenBao exist: the kit's first pull uses `ghcr-pull` (every kit HelmRelease, kit key `REGISTRY_PULL_SECRET`), the network and storage drivers of slots 01, 50, 55, 55a and 55b and Crossplane's OpenTofu provider read `cloud-credentials`, the registry and backup charts (slots 19, 34) read `object-storage`; no secret store exists before Flux. Names, namespaces, types, keys and reflector annotations are files in Git.
2. The seed file gains, after the five lines of SEC-153: `GHCR_PULL_DOCKERCONFIGJSON` (the whole `.dockerconfigjson`, one value under one name, base64-encoded; the same bytes first boot wrote before), `OBJECT_STORAGE_ENDPOINT`, `OBJECT_STORAGE_REGION`, `OBJECT_STORAGE_BUCKET`, `OBJECT_STORAGE_ACCESS_KEY`, `OBJECT_STORAGE_SECRET_KEY` (base64-encoded; each fills two keys of `object-storage`). Nothing of `cloud-credentials` (revision 2).
3. `cloud-credentials` stays in first boot exactly as on main (revision 2): the `write_files` entry `/var/lib/catalyst/cloud-credentials-secret.yaml` with the module's body, packed (`encoding: gz+b64`) as on main, applied with `--server-side` with the seal profile, and shredded with the seed file on the line of the seed's create. The design rule: a value that is large and specific to a provider (a cloud credential document) never enters the start-up data twice, and never in a wider encoding than it has on main. The second provider's body carries `hcloud-cloud-init`, a worker's whole first-boot text for the node autoscaler (7,275 bytes as one raw seed line, measured): on main it travels compressed inside the packed body, so moved into the seed it grew that provider's control plane by 2,461 and 2,360 bytes. Flux's substitution cannot unpack a packed document or take one key of it, and the readers read separate keys, so no template of references can carry it smaller. A template that does not parse the body cannot hide a broken body either: a body that does not parse fails `kubectl apply`, and `(exit $?)` stops first boot, as on main. It leaves first boot with SEC-198.
4. No pack overlay (revision 2): `clusters/_template/providers/<pack>/bootstrap-secrets` does not exist; the two templates are in the shared folder.
5. The Kustomization `bootstrap-secrets` (`clusters/_template/root/base-primary/bootstrap-secrets.yaml`) keeps the path of main, `./clusters/_template/bootstrap-secrets`; only its comment changes, to name the six Secrets it renders. No root child takes its path from a variable: `scripts/check-kit-render-equivalence.sh` renders every root and every path its files name as literal folders and stops on a variable (its line 107), and it stays unchanged. Order, substituteFrom (the Secret `bootstrap-seed`, never optional) and wait stay as SEC-153 made them.
6. The upgrade path. `build-seed.sh` reads which keys the seed holds (none when it does not exist) and, for each value the seed lacks, reads the live Secret that holds it: the entries of `SEED_ENTRIES` (now in the Job's environment, eleven lines: the five of SEC-153, `ghcr-pull` and the five of `object-storage`) by the rule of SEC-153 (a Secret that cannot be read, a missing key, an empty value or a value that is not base64 text stops it, and the log names the Secret and the key). It reads no `cloud-credentials` (revision 2), and the only `--ignore-not-found` it uses is the probe for the seed itself. Then it creates the seed (no seed yet) or adds the lacking keys with one merge patch of `stringData` read from a file in memory (`--field-manager=catalyst-bootstrap-seed`). It never changes or removes a key the seed holds, so a value first boot wrote stays; when anything is missing it writes nothing and exits 1, the Job fails, `bootstrap-secrets` and the kit wait, and no live Secret is rendered from a seed that lacks its value. Its rights gain `get` on the two Secrets and `patch` on the seed by name. The script holds no `${...}` form (as on main): the kit render check models Flux's substitution on every root and cannot judge `${line%%=*}`, though `bootstrap-seed` has no `postBuild`.
7. The Job runs again on an installed Sovereign because `SEED_ENTRIES` is part of its immutable template: a change of it makes Flux (`force: true` on `bootstrap-seed`) replace the Job, and `bootstrap-secrets` waits for `bootstrap-seed` at the same revision (dependsOn, wait). A Secret that joins the seed joins that list.
8. Guard G1, the source of a template's names. Every name a Secret template under `clusters/` references under `data` or `stringData` must come only from a `postBuild.substituteFrom` entry of kind `Secret` of each Flux Kustomization under `clusters/` that renders the template's folder, directly or through an overlay that builds it (a `${VAR}` in a path stands for any one folder; a folder without a `kustomization.yaml` renders every folder below it, as Flux generates one). A finding: the name is also a key of that Kustomization's inline `postBuild.substitute`; the name is a key of a ConfigMap that its `substituteFrom` names and that is a manifest tracked in the repository (a file, a chart template or the first-boot template; not under `docs/`); the Kustomization names no `substituteFrom` entry of kind `Secret` or its `postBuild` cannot be read; no Kustomization renders the folder. Revision 2: a document under `clusters/` whose text names `kind: Kustomization` and an `apiVersion` of `kustomize.toolkit.fluxcd.io/`, and that the reader cannot parse or that is not a mapping, is a finding that names its file, never skipped: the guard cannot tell which folder it renders, so it fails closed. A file with a finding is not a template, so G1 counts its `kind: Secret` line. The rule is in Go (`tools/guards/cmd/secret-templates/sources.go`, standard library only, with a reader of block YAML); its tests are `TestTemplateNameFromInlineSubstituteIsAFinding`, `TestTemplateNameFromTrackedConfigMapIsAFinding`, `TestTemplateNameWithoutASecretSourceIsAFinding`, `TestTemplateNameFromTheSecretSourcePasses` and `TestTemplateNameInAnUnreadableKustomizationIsAFinding`. A name in a label or an annotation is not judged, as metadata is not.
9. Guard G6 (`scripts/check-reflector-scope.sh`) counts the per-Org pattern of the `ghcr-pull` reflector lists (#4246, #4423) once. The finding moves with the manifest: its allow-list line `infra/providers/_shared/cloudinit-control-plane.tftpl:1` becomes `clusters/_template/bootstrap-secrets/ghcr-pull.yaml:1`; the list keeps its 19 lines and no scope is added. The render test asserts `ghcr-pull`'s annotations through test (c), so no copy of the pattern is added.
10. Deleted: the `write_files` entries `ghcr-pull-secret.yaml` and `object-storage-secret.yaml` and their `-f` and shred arguments. No new Python, no new image, no NodePort, no new packed entry, no raised limit.
11. The render check of the upgrade tests flags an empty rendered value, as on main (revision 2): no rendered Secret carries an empty placeholder once `cloud-credentials` is not rendered from the seed.
12. The start-up data may not grow on any provider (revision 2). The proof needs OpenTofu, which the acceptance job does not install (it has only git, the shell, Python with PyYAML, Go, Node and Helm), so it is a step of the check `packs` (`.github/workflows/cloud-init-size.yaml`): it renders the base of the pull request (the first parent of its merge commit) and the head, each with its own `scripts/cloudinit-size-check.sh both`, prints base, head and change for each of the eight surfaces, warns on growth, and fails when a tree cannot be measured or the two trees do not render the same surfaces. It is a record, not a gate on growth (SOV-153 makes every surface larger by design); this ticket's record must show every control-plane surface smaller and every worker surface equal. The saving is recorded, with no threshold.
13. A test renders the second provider's secondary region (revision 2): the module test asserts that its render carries the values of `ghcr-pull` and `object-storage` in the seed file, no manifest of either, and the packed credential file.
14. The pull credential of the Flux controllers has a source the guard can see (revision 3). bp-flux's ServiceAccount patch (`clusters/_template/bootstrap-kit/03-flux.yaml`) names the imagePullSecret `ghcr-pull`, and check 4 of `scripts/check-flux-controller-pull-credential.sh` requires that the bootstrap creates it in `flux-system`. On main it looks only in the first-boot template, so this change, which takes the manifest out of it, fails that required check. The guard accepts two sources, and only these: first boot (a line `name: <secret>` in `infra/providers/_shared/cloudinit-control-plane.tftpl`, as on main), or a document of kind `Secret` with that name in namespace `flux-system` in a file that `clusters/_template/bootstrap-secrets/kustomization.yaml` lists, which the Flux Kustomization `bootstrap-secrets` renders (`path: ./clusters/_template/bootstrap-secrets`), and ONLY together with the order: the Kustomization `bootstrap-kit`, which applies `03-flux.yaml`, lists `bootstrap-secrets` under `dependsOn` (`clusters/_template/root/base-primary/bootstrap-kit.yaml` lines 13 to 15, written by SEC-153; every root builds `base-primary`, and no root overlay patches that list). A template without that order, a template in another namespace and no source at all are findings, each naming the Secret. The rule is the shell function `secret_source` of the guard; no Python is added (the existing extractor stays). The self-test gains five cases: the template source with the wait of the kit passes; no source fails and names the Secret; a template in another namespace fails; a template without the wait of the kit fails; the first-boot source passes. The workflow `.github/workflows/check-flux-controller-pull-credential.yaml` also runs on a change of `clusters/_template/bootstrap-secrets/**` and of `clusters/_template/root/base-primary/**`, the folder that carries the order. Checks 1 to 3 of the guard (the patch, its selector, its anchors) do not change.
15. Two comments follow the change (revision 3): `clusters/_template/bootstrap-kit/03-flux.yaml` (lines 254 to 256 on main) says that `bootstrap-secrets` renders `ghcr-pull` from its template and the seed and that the kit waits for it, no longer that first boot applies `/var/lib/catalyst/ghcr-pull-secret.yaml`; `clusters/_template/root/base-primary/bootstrap-seed.yaml` (lines 1 to 14) names the six bootstrap Secrets the Job builds the seed from or adds to it, no longer four. Only comment lines of these two files change.

## 19. Rollback
Forward fix, not a plain revert, once a Sovereign has reconciled the change. A revert takes `ghcr-pull.yaml` and `object-storage.yaml` out of the shared folder, so Flux prunes what it applied, the two Secrets, on every Sovereign that reconciled the change; a Sovereign installed after the merge has no other source of them, because its first boot no longer writes them. To undo the change, a first change sets the annotation `kustomize.toolkit.fluxcd.io/prune: disabled` on the two manifests, and only after every Sovereign has reconciled it does the revert merge. Before any Sovereign has reconciled the change, reverting the squash commit is safe. `cloud-credentials` is not affected: first boot writes it before and after.

+// The source of a template's names (SEC-154).
+//
+// A template of references holds no value, only the name of one; Flux
+// substitutes the value when it builds the folder. So a template keeps its
+// value out of Git only when every NAME it references comes from a Secret of
+// the cluster. Every NAME referenced under data or stringData of a template
+// under clusters/ must therefore be supplied ONLY by a postBuild.substituteFrom
+// entry of kind Secret of each Flux Kustomization that renders the template's
+// folder, directly or through an overlay that builds it. Each of these is a
+// finding, and a file with a finding is not a template (G1 counts it):

+//	the NAME is also a key of the inline postBuild.substitute of that
+//	Kustomization (its value is in Git);
+//	the NAME is a key of a ConfigMap that a substituteFrom entry of that
+//	Kustomization names, where that ConfigMap is a manifest tracked in the
+//	repository (its value is in Git);
+//	that Kustomization names no substituteFrom entry of kind Secret, or its

+// Which folders a Flux Kustomization renders: its spec.path (a ${VAR} in it
+// stands for any one folder name, since Flux substitutes the path before it

+// through such a patch has no Kustomization and is a finding.

+// documentBounds is the document around line i whose fields stand at indent
+// base: it ends at a separator or at a line indented less than base; a blank
+// line, a comment and a template directive (%{ or {{ at its start) do not end it.
+func documentBounds(lines []string, i, base int) (int, int) {
+	inside := func(l string) bool {
+		t := strings.TrimSpace(l)
+		if t == "---" || strings.HasPrefix(t, "--- ") || t == "..." {
+			return false
+		}
+		return t == "" || strings.HasPrefix(t, "#") || strings.HasPrefix(t, "%{") || strings.HasPrefix(t, "{{") || indentOf(l) >= base
+	}
+	start, end := i, i+1
+	for start > 0 && inside(lines[start-1]) {
+		start--
+	}
+	for end < len(lines) && inside(lines[end]) {
+		end++
+	}
+	return start, end
+}

+type yLine struct {
+	indent int
+	text   string
+}

+var blockScalar = regexp.MustCompile(`(?:^-|:)\s+[|>][-+0-9]*$`)
+
+// parseYAML reads one document of block YAML: mappings, sequences, plain and
+// quoted scalars, comments and block scalars (skipped). A tab in the
+// indentation or a line that is neither an entry nor an item is an error.
+func parseYAML(doc []string) (*yNode, error) {
+	var ls []yLine
+	for i := 0; i < len(doc); i++ {
+		raw := strings.TrimRight(doc[i], " \r")
+		t := strings.TrimLeft(raw, " ")
+		if t == "" || strings.HasPrefix(t, "#") {
+			continue
+		}
+		if strings.HasPrefix(t, "\t") {
+			return nil, fmt.Errorf("line %d: a tab in the indentation", i+1)
+		}
+		ind := len(raw) - len(t)
+		t = stripComment(t)
+		ls = append(ls, yLine{ind, t})
+		if blockScalar.MatchString(t) {
+			for i+1 < len(doc) && (strings.TrimSpace(doc[i+1]) == "" || indentOf(doc[i+1]) > ind) {
+				i++
+			}
+		}
+	}
+	if len(ls) == 0 {
+		return null, nil
+	}
+	i := 0
+	n, err := parseBlock(ls, &i, ls[0].indent)
+	if err == nil && i < len(ls) {
+		err = fmt.Errorf("an entry at indent %d after the document's block", ls[i].indent)
+	}
+	return n, err
+}
+
+func isItem(t string) bool { return t == "-" || strings.HasPrefix(t, "- ") }
+
+func parseBlock(ls []yLine, i *int, ind int) (*yNode, error) {
+	if isItem(ls[*i].text) {
+		return parseSeq(ls, i, ind)
+	}
+	return parseMap(ls, i, ind)
+}
+
+func parseSeq(ls []yLine, i *int, ind int) (*yNode, error) {
+	n := &yNode{isSeq: true}
+	for *i < len(ls) && ls[*i].indent == ind && isItem(ls[*i].text) {
+		rest := strings.TrimLeft(strings.TrimPrefix(ls[*i].text, "-"), " ")
+		var item *yNode
+		switch _, _, isEntry := splitEntry(rest); {
+		case rest == "":
+			*i++
+			item = null
+			if *i < len(ls) && ls[*i].indent > ind {
+				var err error
+				if item, err = parseBlock(ls, i, ls[*i].indent); err != nil {
+					return nil, err
+				}
+			}
+		case isEntry:
+			at := ind + len(ls[*i].text) - len(rest)
+			ls[*i] = yLine{at, rest}
+			var err error
+			if item, err = parseMap(ls, i, at); err != nil {
+				return nil, err
+			}
+		default:
+			item = &yNode{scalar: unquote(rest)}
+			*i++
+		}
+		n.seq = append(n.seq, item)
+	}
+	return n, nil
+}
+
+func parseMap(ls []yLine, i *int, ind int) (*yNode, error) {
+	n := &yNode{isMap: true, m: map[string]*yNode{}}
+	for *i < len(ls) && ls[*i].indent == ind && !isItem(ls[*i].text) {
+		key, value, ok := splitEntry(ls[*i].text)
+		if !ok {
+			return nil, fmt.Errorf("%q is not an entry key: value", ls[*i].text)
+		}
+		*i++
+		child := null
+		switch {
+		case value != "":
+			child = &yNode{scalar: unquote(value)}
+		case *i < len(ls) && (ls[*i].indent > ind || ls[*i].indent == ind && isItem(ls[*i].text)):
+			var err error
+			if child, err = parseBlock(ls, i, ls[*i].indent); err != nil {
+				return nil, err
+			}
+		}
+		if _, dup := n.m[key]; !dup {
+			n.keys = append(n.keys, key)
+		}
+		n.m[key] = child
+	}
+	if *i < len(ls) && ls[*i].indent > ind {
+		return nil, fmt.Errorf("%q is indented more than its mapping", ls[*i].text)
+	}
+	return n, nil
+}
+
+// splitEntry splits `key: value` (a plain or quoted key); ok is false when the
+// text is not an entry.
+func splitEntry(t string) (string, string, bool) {
+	if t == "" || strings.ContainsAny(t[:1], "[{|>*&!%@`") {
+		return "", "", false
+	}
+	if t[0] == '"' || t[0] == '\'' {
+		end := strings.IndexByte(t[1:], t[0])
+		if end < 0 || !strings.HasPrefix(t[end+2:], ":") {
+			return "", "", false
+		}
+		return t[1 : end+1], strings.TrimSpace(t[end+3:]), true
+	}
+	for j := 0; j < len(t); j++ {
+		if t[j] == ':' && (j == len(t)-1 || t[j+1] == ' ') {
+			return t[:j], strings.TrimSpace(t[j+1:]), true
+		}
+	}
+	return "", "", false
+}
+
+// stripComment removes a comment ` #...` that follows a value outside quotes.
+func stripComment(t string) string {
+	quote := byte(0)
+	for j := 0; j < len(t); j++ {
+		switch c := t[j]; {
+		case quote != 0:
+			if c == quote {
+				quote = 0
+			}
+		case c == '"' || c == '\'':
+			if j == 0 || t[j-1] == ' ' || t[j-1] == ':' || t[j-1] == '-' {
+				quote = c
+			}
+		case c == '#' && (j == 0 || t[j-1] == ' '):
+			return strings.TrimRight(t[:j], " ")
+		}
+	}
+	return t
+}

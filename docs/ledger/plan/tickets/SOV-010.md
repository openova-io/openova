# SOV-010 — Record the cutover result of the baseline provision and correct the lifecycle documents

## In plain words

**The problem today.** The project instructions list the eleven cutover steps in the order of their file names, so the deny-egress proof looks like step 8 of 11. The cutover runs them in the order of a label, and by that label the proof is the last step. The decision record of the cutover says the same wrong thing, and the status document still names an old environment as the furthest any cutover got, although a new installation has since run the whole chain.

**What changes.** The project instructions list the steps in the order they run, with the proof last. The decision record gets a dated note with that order and the result of the baseline installation, and the status document states that result.

**Done means:**

- The eleven steps in the project instructions are in the order of the label bp.openova.io/cutover-order, and egress-block-test is item 11.
- The decision record of the cutover has one new dated note, and none of its old lines changed.
- The note says that the deny-egress proof is step 11 of 11 and that the baseline installation ran the hand-over chain to its end, and it links the baseline file.
- The status document no longer says that the furthest cutover ever was hw246; it states the baseline result and links the baseline file.

The rest of this ticket is the exact instruction for the model that does the work.

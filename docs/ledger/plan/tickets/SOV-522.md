# SOV-522 — The release stage applies the provider pivot again where a candidate changes a package line

## In plain words

**The problem today.** A Sovereign that has cut over cannot receive a release that changes the package line of a Crossplane Provider. The cutover rewrote that line to point at the Sovereign's own registry, and the release stage counts that rewrite as a conflict, so the delivery stops before anything moves.

**What changes.** The release stage recognises the cutover's rewrite of a Provider package line, takes the release's line and applies the same rewrite to it again. A change it cannot explain is still refused, with the file named.

**Done means:**

- A release that changes a Provider package line which the cutover rewrote is staged, and the staged file is the release's file with the line pointed at the Sovereign's own registry.
- The rewrite the stage applies is the one the cutover step runs, read from the same file; the cutover step rewrites exactly as before.
- A release that deletes such a Provider file deletes it in the staged commit.
- A Provider file the sovereign-admin changed by hand beyond the rewrite still stops the stage, with the file named and nothing moved.
- Where the cutover step's file is not there (a follower region, or a cutover chart of an earlier release), the stage refuses such a change as before.
- A release whose Provider line names a tag and no digest is refused with the file named, because the Sovereign's registry cannot serve a tag after the cutover.

The rest of this ticket is the exact instruction for the model that does the work.

## 2. End goal
A release candidate that changes the package line of a Crossplane Provider reaches a Sovereign that has cut over. Cutover step 11 (`crossplane-provider-pivot`) rewrote that line in the primary region's Git to the Sovereign's own registry (`harbor.<fqdn>/proxy-xpkg/...`). The stage of `PUT /api/v1/sovereign/release` now treats that rewrite as this region's pivot, as it already treats the kit-folder rewrites of steps 06 and 07: a conflicted Provider file whose region side is exactly step 11's rewrite of the merge base is taken from the candidate (deleted when the candidate deletes it) and step 11's rewrite is applied again on top of the candidate's line, with the bytes step 11 runs. Any other conflict is refused as today, with the file named and nothing moved.

## 3. The model (the law)
1. Step 11's package-line rewrite exists once: the key `provider-pivot.sh` of the ConfigMap `cutover-step-11-crossplane-provider-pivot`, holding `provider_pivot_target`, `split_pkg_ref`, `provider_pivot_files` and `provider_pivot_file`. Step 11 mounts that key of its own ConfigMap at `/provider-pivot`, sources it and calls these functions; it selects the same files and writes the same bytes and log lines as before. The caller defines `lookup_pkg_digest`.
2. The bootstrap's stage container (`release_job.go`): when the installed ConfigMap `cutover-step-11-crossplane-provider-pivot` carries a non-empty `provider-pivot.sh`, it mounts that key at `/provider-pivot` and sets `PROVIDER_PIVOT=/provider-pivot/provider-pivot.sh` and step 11's own `SOVEREIGN_FQDN`, `REGISTRY_PATH`, `UPSTREAM_HOST` and `MOTHERSHIP_PROXY_PREFIX`. When the ConfigMap is absent or has no such key (a cutover chart of an earlier release), the container is as before and no error is raised. A ConfigMap with the key whose container sets no `SOVEREIGN_FQDN`, `REGISTRY_PATH` or `UPSTREAM_HOST` is a dependency error (424).
3. `release-region.sh stage`: a conflicted file that `provider_pivot_files` lists, whose region side is exactly `provider_pivot_file` of the merge base, is explained (`how=provider`): taken from the candidate, or deleted when the candidate deletes it, and `provider_pivot_file` is applied to it after the merge, in the pivot commit. A package line that still names `UPSTREAM_HOST` or `MOTHERSHIP_PROXY_PREFIX` after that refuses the stage, nothing pushed. Every other conflict: phase `conflict`, the file named, nothing pushed.
4. The digest of the candidate's package is the one the candidate's line carries: `split_pkg_ref` reads it first, as step 11 does (the #4955 shape), and `clusters/_template/infrastructure/providers/base/provider-opentofu.yaml` on main is pinned so. The stage reads no digest map: `release-region.sh` makes no Kubernetes API call, step 03's map holds only what the cutover warmed, and the route's prewarm runs after the stage. So its `lookup_pkg_digest` finds none, and a candidate line with a tag and no digest, which step 11's host swap would turn into a tag of the proxy project that is not served after the cutover (#5232), refuses the stage (phase `refused`, exit 2), the file and the package named, nothing pushed.
5. Step 11 runs in the primary region only. A follower's stage Job gets no `PROVIDER_PIVOT`, and a Provider conflict there is refused as before.
6. The API's and the chart's copies of `release-region.sh` stay byte-identical; `files/release/contract` stays `1`; `release-run.sh` does not change.
7. The lines of the cutover chart's templates do not rise (`scripts/check-lifecycle-ratchets.sh`, `chart_lines` 20750): the moved code is written more compactly and a stale comment goes. No Python is added, no RBAC rule changes, no Service and no port of any kind.
8. `tests/step6490-secondary-gitea-mirror.sh` compares the whole single-region render with origin/main's. Like its axes 5 to 16, a new axis 17 leaves the step-11 document out of both trees while origin/main lacks `provider-pivot.sh`, and switches itself off once main holds it; the new chart test verifies the change. This path is not among the plan's touches: it is added here because the comparison fails on any change of step 11 otherwise.

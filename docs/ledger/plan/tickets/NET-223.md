# NET-223 — Application controller without the tier pivot

## In plain words

**The problem today.** The application controller still sends the release of a Blueprint or an Application that names a tier (mgmt, dmz or rtz) into that tier's namespace, through that tier's virtual cluster. No Sovereign has those namespaces or virtual clusters any more, so such a release fails and blocks the other applications of the Organization in that region. The code and the settings of that pivot are dead weight that a later port of the controller would carry along.

**What changes.** Every release is written into the Application's own namespace on the host cluster of its region, whatever tier an older object still names; such a tier is logged once and changes nothing. The cluster registry knows regions only.

**Done means:**

- The application controller has no map of tier namespaces, no tier settings and no code that sends a release into a virtual cluster.
- An Application or a Blueprint that still names a tier gets its release on the host cluster of its region, in the Application's namespace, and the controller logs the ignored tier once for that object.
- A cluster identifier is read as its region letter, with or without the old prefix, and the names of the per-region releases stay as they were.
- The tests of the controller and of the cluster registry pass, and new tests cover the ignored tier, the log written once per object and the reading of the region.
- The service-model ratchet counts two fewer Blueprint name literals in the controllers.

The rest of this ticket is the exact instruction for the model that does the work.

## 2. End goal
The application controller (`core/controllers/application`) no longer knows tiers. Every HelmRelease it renders, by the topology fan-out and by the per-region path, is written into the Application's own namespace with no `spec.kubeConfig` block, so the region's own Flux installs it on that region's host cluster (ADR-0015 D1). The map `VClusterPlacements`, its type, its defaults and its six environment variables `VCLUSTER_PLACEMENT_<TIER>_NS` and `_SECRET` are deleted, with the tier resolution (instance `spec.placement.vcluster`, Blueprint `spec.defaultPlacement.vcluster`, `spec.allowedPlacements`, `spec.placementSchema.vcluster`, topology `placement.tier`), the two pivot branches and the CNPG routing exception that only existed to undo the pivot. A tier that a stored Application or Blueprint still names changes nothing; the controller logs it once per object. The cluster registry `core/controllers/internal/clusterregistry` keeps the region half of a cluster identifier: `rtz-A`, `mgmt-B` and `A` read as a region; it writes `rtz-<region>`, the form the identifier pattern of the Blueprint kind admits until NET-227, so the per-region release names (`<app>-rtz-a`) do not change.

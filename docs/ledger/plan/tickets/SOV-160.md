# SOV-160 — Registry projects, the Organization Git token and the two repositories are created at install

## In plain words

**The problem today.** A new Sovereign's registry gets its projects only during the hand-over, so nothing can be pushed into it or served from it before then. Nothing creates the repository that will hold the provider pack, and the region repository appears only when a controller first writes to it.

**What changes.** Installing Harbor creates the registry projects, and installing Gitea creates the two platform repositories. Each is done by a Job that can run again without changing anything.

**Done means:**

- A newly installed Harbor has the public projects proxy-dockerhub, proxy-ecr, proxy-gcr, proxy-ghcr, proxy-k8s and proxy-quay and the private projects node-artifacts, openova-io and tofu-providers, and none of them is a pull-through project.
- The list of projects follows the registry keys of the variables contract when a Sovereign carries them, and the contract's defaults when it does not.
- The pull-through project for Crossplane packages is still created by the hand-over, as before.
- A newly installed Gitea in the writer region has the organisation openova and the private repositories sovereign-regions and provider-pack, each with a first commit on main. A repository that already has commits is not touched.
- Running either Job a second time changes nothing.
- Render tests of both charts prove these rules and fail when one is broken.

The rest of this ticket is the exact instruction for the model that does the work.

## 2. End goal
When a Sovereign is installed, its registry and its Git service are ready for the born-local work before any hand-over runs. The chart `bp-harbor` (bootstrap-kit slot 19) carries a Job that creates every project of the Sovereign's registry chain in this region's Harbor, each as a hosted project, never a pull-through project. The project names come from the registry keys of contract C5 (`docs/contracts/c5-upstream-variables.schema.json`), passed by slot 19 with the contract's defaults. The chart `bp-gitea` (bootstrap-kit slot 10) carries a Job that, in the writer region, creates the organisation `openova` and the private repositories `openova/sovereign-regions` and `openova/provider-pack`, each with a first commit on `main`. The Organization Git token is already minted at install by `bp-catalyst-platform`; this ticket proves that and adds no second minter. Two render tests, one per chart, prove every rule and fail when one is broken.

## 3. The model (the law)
1. **Files.** The four new files are the blocks of field 5, byte for byte. The four edited files change only by the block `SOV-160.patch` of field 5: each edit inserts lines after one anchor line and removes nothing.
2. **The registry Job** (`platform/harbor/chart/templates/registry-projects-job.yaml`). Rendered when `registryProjects.enabled` is true (the default). A plain `batch/v1` Job in the release namespace, not a Helm hook: slot 19 installs and upgrades with `disableWait: true`, so a hook would start before `harbor-core` answers, and a failed hook fails the release. Its name is `<release>-registry-projects-<8 hex>`, the hex being a hash of the project lists, the image and the chart version, so a changed input or a new chart version runs it again. It waits up to 90 times 10 seconds for `GET /api/v2.0/ping` on `http://<release>-core.<namespace>.svc.cluster.local`. It signs in as `admin` with the file `HARBOR_ADMIN_PASSWORD` of the Secret `harborAdmin.secretName` (default `harbor-admin`), mounted read-only. For each project it sends `POST /api/v2.0/projects` with the body `{"project_name":"<name>","public":<true|false>,"metadata":{"public":"<true|false>"}}` and no `registry_id`. Answer 201: created. Answer 409: it exists and is left as it is. Any other answer: the Job fails. Then it reads `GET /api/v2.0/projects/<name>`. A project whose body holds a non-zero `registry_id` is a pull-through project: the Job names it, goes on with the next project, and fails at the end.
3. **The registry projects.** Public: the first path segment of each value of `registryProjects.proxyProjectsJSON` (contract key `REGISTRY_PROXY_PROJECTS_JSON`, a JSON object from registry name to project path), each once; an empty value makes no project. When `proxyProjectsJSON` is empty the map `registryProjects.defaultProxyProjects` is used, which holds the contract's default. A JSON value that is not an object fails the render with `registryProjects.proxyProjectsJSON is not a JSON object`. Private: the first path segment of each of `registryProjects.paths.charts`, `.release`, `.providerPacks`, `.tofuProviders` and `.nodeArtifacts` (contract keys `REGISTRY_PATH_CHARTS`, `REGISTRY_PATH_RELEASE`, `REGISTRY_PATH_PROVIDER_PACKS`, `REGISTRY_PATH_TOFU_PROVIDERS`, `REGISTRY_PATH_NODE_ARTIFACTS`), each once, and none that is already public. Both lists are sorted. With the defaults: public `proxy-dockerhub proxy-ecr proxy-gcr proxy-ghcr proxy-k8s proxy-quay`, private `node-artifacts openova-io tofu-providers`.
4. **The Crossplane package project stays a pull-through project for now.** The project of `registryProjects.xpkgPath` (contract key `REGISTRY_PATH_XPKG`, default `proxy-xpkg`) is left out while `registryProjects.createXpkgProject` is false, the default. The hand-over's step `harbor-prewarm` pulls Crossplane packages through that project, so it must stay the pull-through project that the self-sovereign-cutover chart creates. A hosted project of that name made at install would answer "not found" there and break the hand-over. The package that replaces the prewarm with the closure copy sets the switch to true.
5. **The repositories Job** (`platform/gitea/chart/templates/platform-repos-job.yaml`). Rendered when `platformRepos.enabled` is true (the default) and `platformRepos.writerRegionId` is empty or equals `platformRepos.regionId`. The regions of a Sovereign share one Gitea database and keep one disk each, so only the writer region may create repositories; an empty `writerRegionId` means one region. A plain `batch/v1` Job, not a Helm hook (slot 10 also installs with `disableWait: true`), named `<release>-platform-repos-<8 hex>` by the same rule as item 2. It signs in with the files `username` and `password` of the Secret `giteaAdmin.secretName` (default `gitea-admin-secret`), mounted read-only, at `http://<the Gitea HTTP Service>.<namespace>.svc.cluster.local:3000`, the Service name being derived as `templates/httproute.yaml` derives it (`gitea-http` for the release `gitea`). It waits up to 60 times 10 seconds for `GET /api/v1/user` to answer 200. It creates the organisation `platformRepos.org` (default `openova`) with `{"username":"<org>","visibility":"public"}` when `GET /api/v1/orgs/<org>` answers 404; public is the visibility the repo bootstrap of `bp-catalyst-platform` gives it today. For each repository of `platformRepos.repos` (default `sovereign-regions`, `provider-pack`): when it is absent, it is created with `{"name":"<repo>","private":true,"auto_init":true,"default_branch":"main"}`, the settings the controllers use (`core/controllers/pkg/gitea/client.go`, `EnsureRepo`). When it exists and reports `"empty":true`, a `README.md` is committed on `main`. When it has commits, it is left as it is. The Job never deletes or patches anything.
6. **Slot 19** passes `registryProjects.proxyProjectsJSON`, `.paths.*` and `.xpkgPath` as `${KEY:=<contract default>}` substitutions of the six keys. The JSON value is quoted, so Flux substitutes it as a string; it has an empty default, and the chart then uses `defaultProxyProjects`. A Sovereign whose variables do not carry the contract keys (every Sovereign today) therefore gets the contract defaults. **Slot 10** passes `platformRepos.regionId` and `.writerRegionId` from the kit keys `SOVEREIGN_REGION_ID` and `SOVEREIGN_WRITER_REGION_ID`, each with an empty default.
7. **The Organization Git token** is already created at install, by `bp-catalyst-platform`: its pre-install hook in `products/catalyst/chart/templates/catalyst-gitea-token-secret.yaml` mints a Gitea token into the Secret `catalyst-gitea-token`, and `products/catalyst/chart/templates/org-services/provisioning-github-token.yaml` copies it into `org-services/provisioning-github-token`, key `GITHUB_TOKEN`, the Secret the Organization pipeline reads. This ticket adds no token minter: a second writer of that Secret would fight the copy rule of that template. Cutover step `gitea-token-mint` stays until package SOV-260 deletes it.
8. Nothing is deleted. No chart version line, no slot pin and no `Chart.yaml` changes: CI writes versions after the merge (package FND-011). No Secret is created. Every image comes through a proxy project, every container has cpu and memory requests, runs as non-root with a read-only root file system, and has no service account token.

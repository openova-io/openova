# PRD-503 — Keycloak consent extension

## In plain words

**The problem today.** The open-banking product needs the identity server to show the customer the consent a third party asked for, to record the customer's decision with the product, and to put the authorised consent into the tokens. Keycloak cannot do this by itself, and its pushed-request endpoint answers a failed client sign-in with the wrong error code, which the conformance suite fails. Nothing in the repository builds or tests such an extension.

**What changes.** A Keycloak extension adds the consent step, the consent claim in the tokens and the corrected endpoint. A workflow builds it inside the Keycloak image of the version the chart pins, runs its unit tests and an end-to-end test, and on the main branch publishes a signed image that carries it. The product's profile accepts only the consent carrier that the extension implements.

**Done means:**

- A pull request that changes the extension builds it inside the Keycloak image of the chart's version, runs its unit tests and an end-to-end test, and turns red when one of them fails.
- In the end-to-end test, a customer who signs in and allows one account gets an access token and an ID token that carry the consent identifier, and the stand-in API saw exactly the three calls, each with a valid signed token.
- A rejection, and every refusal of the API, sends the third party the error access_denied with the reason, and a later request without a consent never carries an earlier consent.
- A failed client sign-in at the pushed-request endpoint is answered with invalid_client.
- On the main branch the workflow publishes a signed image that holds exactly the tested provider archive.
- The product's profile refuses the consent carrier authorization-details.

The rest of this ticket is the exact instruction for the model that does the work.

## 2. End goal
The repository holds the Keycloak extension `fapi-consent` under `platform/keycloak/extensions/fapi-consent`, and the workflow `.github/workflows/build-keycloak-fapi.yaml` that builds and tests it. The extension does three things. Its consent step reads the consent identifier from the third party's authorisation request, makes the three calls of the product's internal authorisation API (read the consent, resolve the customer, post the decision), and shows the customer the consent page. Its protocol mapper writes the authorised consent into the access token and the ID token as the claim `openbanking_intent_id`. Its replacement of the pushed-request endpoint answers a failed client sign-in with `invalid_client`. On every pull request that changes it, the workflow builds the provider archive inside the upstream Keycloak image of the version the Keycloak chart pins, runs the unit tests and an end-to-end test (Keycloak with the archive, a test realm and a stand-in for the API, all on the runner), and checks that the image built from it holds the tested archive. On `main` the workflow pushes `ghcr.io/openova-io/openova/keycloak-fapi-consent:<short commit>` and signs it. The product's profile loader (`products/fingate/internal/profile`) accepts only the consent carrier `intent-claim`. A person sees it on the pull request: the check `build and test fapi-consent` is green, and its log ends the end-to-end test with `drive.py: 0 failed`.

## 3. The model (the law)
1. **The carrier is `intent-claim`.** The result record `docs/ledger/plan/spikes/PRD-040.md` (outcome A) measured it on the pinned Keycloak 26.3.3. The consent identifier is the string `value` of the essential ID-token claim `openbanking_intent_id` in the claims request: `{"id_token": {"openbanking_intent_id": {"value": "<id>", "essential": true}}}`. Keycloak keeps the claims request as the client note `claims` of the authentication session. A claim that is missing, not essential, not a string, empty, longer than 128 characters, or that holds a character outside printable ASCII is no consent (`ConsentRequest.consentId` returns null).
2. **The consent step** is the authenticator `fapi-consent` (`FapiConsentAuthenticator`, `FapiConsentAuthenticatorFactory`). It requires a user, so it stands after the flow that identifies the customer. A request without a consent passes it unchanged. For a request with a consent it calls, in this order, with the realm's Keycloak session:
   - `GET <authz-url>/internal/v1/authorisations/{consentId}?client_id=<client id>`; 404 is `consent-not-found`, 403 `client-mismatch`, 409 `not-awaiting`;
   - `POST <authz-url>/internal/v1/authorisations/{consentId}/customer` with `{"identity": {"scheme": <identity-scheme>, "subject": <the user name>, "attributes": {}}}`; 404 is `customer-unknown`, 502 `ledger-unavailable`;
   - it shows the page `fapi-consent.ftl` (the permissions or the payment, and the customer's accounts as check boxes), and on the answer posts `POST <authz-url>/internal/v1/authorisations/{consentId}/decision` with `{"customerId", "decision": "authorise" or "reject", "accounts", "acr", "authTime"}`; 409 is `not-awaiting`, 422 `account-not-owned`.
   Every other answer, no answer, or a body that cannot be read is `authorisation-unavailable`. The consent identifier is percent-encoded as one path segment.
3. **The decision.** Allow with no account shows the page again with the message `Choose at least one account.` and calls nothing. An account that was not offered is treated the same way. Allow sends the chosen accounts in the order they were offered. Deny posts `reject` with no account. `acr` is `1` when the customer signed in during this request and `0` when an existing session was reused (the authentication note `SSO_AUTH`). `authTime` is the authentication note `AUTH_TIME`, else the time of the decision, as RFC 3339 in UTC without fractions.
4. **Ends of the step.** When the decision call answers `{"state": "authorised"}`, the step stores the consent identifier as the client note `fapi-consent.consent-id` and succeeds. Every other end sends the OAuth error `access_denied` to the client's redirect address with the reason as `error_description`: `rejected` after Deny, otherwise the code of rule 2. Each login first sets the client note to the empty string, so a later login of the same client without a consent never carries an earlier consent.
5. **The token for the calls.** Each call carries `Authorization: Bearer <token>`, a token the extension signs itself with the realm's active PS256 key: issuer the realm (`Urls.realmIssuer`), audience `fingate-authz`, subject and authorised party `fapi-consent`, type `Bearer`, lifetime 60 seconds. No client secret is used or stored.
6. **The claim mapper** is the protocol mapper `fapi-consent-claim` (`FapiConsentClaimMapper`). It writes the client note `fapi-consent.consent-id`, when it is not empty, into the access token and the ID token as `openbanking_intent_id`, also on a refresh. It never copies a value from the claims request.
7. **The pushed-request endpoint.** `FapiParRootEndpoint` has the built-in provider identifier `par` and the order 100, so Keycloak serves it instead of the built-in one. Its `FapiParEndpoint` changes one answer: when the built-in client check fails with HTTP 401 it answers 401 with `invalid_client` instead of `invalid_request`. Everything else is the built-in endpoint.
8. **Options.** The step reads `authz-url` and `identity-scheme` from its SPI scope (`--spi-authenticator-fapi-consent-authz-url=<url>`, `--spi-authenticator-fapi-consent-identity-scheme=<scheme>`). Without both Keycloak still starts and every realm works; a login with a consent then ends with `authorisation-unavailable`.
9. **Build.** `build.sh` runs inside the upstream image `quay.io/keycloak/keycloak:<version>`, compiles the 8 main source files against the jars under `/opt/keycloak/lib/lib` with `java -m jdk.compiler` and `-Xlint:all,-processing,-serial -Werror` (every lint group except `processing` and `serial` is on, and a warning fails the build), runs the unit tests (`UnitTests`, a plain `main`, because the image holds no test framework), and writes the provider archive to standard output and nothing else there. The archive is reproducible: two builds of the same sources in the same image are the same bytes.
10. **The workflow** `build-keycloak-fapi` starts on a pull request and on a push to `main` that changes `platform/keycloak/extensions/fapi-consent/**`, `platform/keycloak/chart/values.yaml` or the workflow itself, and by hand. It takes the version from `keycloak.image.tag` of `platform/keycloak/chart/values.yaml`, the part before the first `-` (today `26.3.3`). Every run builds, runs the unit tests, runs `test/integration.sh`, builds the image of `Containerfile` from a context that holds only the archive, and checks that `/providers/fapi-consent.jar` in the image has the archive's SHA-256. Only a push to `main` logs in, pushes `ghcr.io/openova-io/openova/keycloak-fapi-consent:<first 7 characters of the commit>` and calls `./.github/actions/sign-and-attest` with the pushed digest.
11. **The image** is `docker.io/library/alpine:3.20` with the archive at `/providers/fapi-consent.jar`, user `65534:65534`. It runs nothing; a later chart change copies the archive from it.
12. **Deleted:** the value `authorization-details` from the accepted consent carriers of `products/fingate/internal/profile/profile.go`. A profile with that carrier is refused with the message `security.consentCarrier "authorization-details" is not intent-claim`.
13. Nothing else changes: no chart, no realm, no bootstrap-kit slot, no other product file. No file of the change uses the word that `scripts/check-sandbox-word.py` counts.

+# fapi-consent — the open-banking consent step for Keycloak
+
+A Keycloak extension for the open-banking product (`products/fingate`). It brings the consent
+identifier from a third party's authorisation request to the customer, records the customer's
+decision through the product's internal authorisation API, and writes the authorised consent
+into the tokens. It holds no business rule: the API decides, the extension carries.
+
+It is platform plumbing, not an Application Blueprint. The Keycloak chart
+(`platform/keycloak/chart`) does not load it yet; that is a later change of the chart. Once
+loaded, a realm uses it only when its browser flow and its clients name its providers, so every
+other realm is unchanged.
+
+## What it adds
+
+| Provider | SPI | Identifier | What it does |
+|---|---|---|---|
+| `FapiConsentAuthenticator` | authenticator | `fapi-consent` | The consent step of the browser flow, after the customer is identified. |
+| `FapiConsentClaimMapper` | protocol mapper | `fapi-consent-claim` | Writes the authorised consent into the access token and the ID token. |
+| `FapiParRootEndpoint` | OIDC extension | `par` (order 100) | Keycloak's pushed-authorisation-request endpoint, corrected in one answer. |
+
+### The consent carrier
+
+The carrier is `intent-claim` (the result record `docs/ledger/plan/spikes/PRD-040.md`, outcome A).
+The third party asks, inside the request object it pushes, for the essential ID-token claim
+`openbanking_intent_id` whose value is the consent identifier:
+
+```json
+{"id_token": {"openbanking_intent_id": {"value": "<consent id>", "essential": true}}}
+```
+
+A request whose claim is missing, not essential, not a string, empty, longer than 128 characters
+or holds a character outside printable ASCII carries no consent: the step lets it pass and its
+tokens carry no consent claim.
+
+### The consent step
+
+For a request that carries a consent, after the customer is identified (a sign-in or an existing
+session), the step makes the three calls of the internal authorisation API of `fingate-api`:
+
+1. `GET /internal/v1/authorisations/{consentId}?client_id=<client>` reads the consent.
+2. `POST /internal/v1/authorisations/{consentId}/customer` with
+   `{"identity": {"scheme": <identity-scheme>, "subject": <user name>, "attributes": {}}}`
+   resolves the customer and lists the customer's accounts.
+3. The step shows the consent page (`theme-resources/templates/fapi-consent.ftl`): the
+   permissions or the payment, and the accounts to choose. On the customer's answer it posts
+   `POST /internal/v1/authorisations/{consentId}/decision` with
+   `{"customerId", "decision": "authorise" or "reject", "accounts", "acr", "authTime"}`.
+
+`acr` is `1` when the customer signed in during this request and `0` when an existing session
+was reused, which is what Keycloak writes into the tokens of a realm without a
+level-of-authentication map. `authTime` is the time of the sign-in as RFC 3339 in UTC.
+
+When the API answers `{"state": "authorised"}`, the step stores the consent identifier as the
+client note `fapi-consent.consent-id`, and the mapper writes it into the tokens as the claim
+`openbanking_intent_id`, also into refreshed tokens. Every login clears that note first, so a
+later request of the same client without a consent never carries an earlier consent.
+
+Every other end of the step sends the OAuth error `access_denied` to the client's redirect
+address, with the reason as `error_description`:
+
+| Reason | When |
+|---|---|
+| `rejected` | the customer chose Deny |
+| `consent-not-found` | the first call answered 404 |
+| `client-mismatch` | the first call answered 403 |
+| `not-awaiting` | the first or the decision call answered 409 |
+| `customer-unknown` | the customer call answered 404 |
+| `ledger-unavailable` | the customer call answered 502 |
+| `account-not-owned` | the decision call answered 422 |
+| `authorisation-unavailable` | any other answer, no answer, or the options below are not set |
+
+Each call carries a bearer token that the extension signs with the realm's active PS256 key:
+issuer the realm, audience `fingate-authz`, subject and authorised party `fapi-consent`, valid
+for 60 seconds. The realm therefore needs an active RSA key for PS256.
+
+### The PAR correction
+
+Keycloak's pushed-authorisation-request endpoint answers a failed client authentication with
+HTTP 401 and `invalid_request`; RFC 6749 section 5.2 requires `invalid_client`. Keycloak 26.3.3,
+26.8.2 and its main branch have the same code, so no upgrade removes the need. `FapiParEndpoint`
+changes that one answer and nothing else.
+
+## Options
+
+Two options of the authenticator's SPI scope, set when Keycloak starts:
+
+| Option | Command-line form | Meaning |
+|---|---|---|
+| `authz-url` | `--spi-authenticator-fapi-consent-authz-url=<url>` | Base address of the internal authorisation API, for example the `:8081` listener of `fingate-api`. |
+| `identity-scheme` | `--spi-authenticator-fapi-consent-identity-scheme=<scheme>` | The scheme under which the API resolves the user name to a customer; the ledger adapter defines the schemes it knows. |
+
+Without both, Keycloak starts and every realm works; a login that carries a consent ends with
+`authorisation-unavailable`.
+

+
+These are realm settings, not part of this extension: the step `fapi-consent` (REQUIRED) after

+/**
+ * Reads the consent identifier from the claims request of an authorisation request.
+ *
+ * <p>The carrier is {@code intent-claim}: the third party asks for the essential ID-token claim
+ * {@value #CLAIM} with the consent identifier as its value, inside the signed request object it
+ * pushes to Keycloak. Keycloak keeps that claims request as the client note {@code claims} of the
+ * authentication session, and later of the client session.
+ */
+public final class ConsentRequest {
+
+    /** The claim that carries the consent identifier, in the request and in the tokens. */
+    public static final String CLAIM = "openbanking_intent_id";
+
+    /** The longest consent identifier accepted. */
+    public static final int MAX_LENGTH = 128;
+
+    private ConsentRequest() {
+    }
+
+    /**
+     * Returns the consent identifier of a claims request, or null when the request carries none.
+     *
+     * <p>The identifier is the string {@code value} of the member {@value #CLAIM} of the member
+     * {@code id_token}, and that member must say {@code "essential": true}. A request that is not a
+     * JSON object, a claim that is not essential, and a value that is empty, longer than
+     * {@value #MAX_LENGTH} characters or holds a character outside printable ASCII carry no consent.
+     */
+    public static String consentId(String claimsJson) {
+        if (claimsJson == null || claimsJson.isBlank()) {
+            return null;
+        }
+        JsonNode root;
+        try {
+            root = JsonSerialization.mapper.readTree(claimsJson.getBytes(StandardCharsets.UTF_8));
+        } catch (IOException e) {
+            return null;
+        }
+        if (root == null || !root.isObject()) {
+            return null;
+        }
+        JsonNode claim = root.path("id_token").path(CLAIM);
+        if (!claim.isObject() || !claim.path("essential").isBoolean() || !claim.path("essential").booleanValue()) {
+            return null;
+        }
+        JsonNode value = claim.path("value");
+        if (!value.isTextual()) {
+            return null;
+        }
+        String id = value.textValue();
+        if (id.isEmpty() || id.length() > MAX_LENGTH) {
+            return null;
+        }
+        for (int i = 0; i < id.length(); i++) {
+            char c = id.charAt(i);
+            if (c < 0x21 || c > 0x7e) {
+                return null;
+            }
+        }
+        return id;
+    }
+
+    /** Percent-encodes a value for one path segment: every byte outside the unreserved set. */
+    public static String pathSegment(String value) {
+        StringBuilder out = new StringBuilder();
+        for (byte b : value.getBytes(StandardCharsets.UTF_8)) {
+            int c = b & 0xff;
+            boolean unreserved = (c >= 'A' && c <= 'Z') || (c >= 'a' && c <= 'z') || (c >= '0' && c <= '9')
+                    || c == '-' || c == '.' || c == '_' || c == '~';
+            if (unreserved) {
+                out.append((char) c);
+            } else {
+                out.append('%').append(Character.toUpperCase(Character.forDigit(c >> 4, 16)))
+                        .append(Character.toUpperCase(Character.forDigit(c & 0xf, 16)));
+            }
+        }
+        return out.toString();
+    }

+def b64d(s):
+    return base64.urlsafe_b64decode(s + "=" * (-len(s) % 4))

+def mgf1(seed, length):
+    out = b""
+    counter = 0
+    while len(out) < length:
+        out += hashlib.sha256(seed + counter.to_bytes(4, "big")).digest()
+        counter += 1
+    return out[:length]

+def pss_verify(n, e, message, signature):
+    """RSASSA-PSS with SHA-256, MGF1 with SHA-256 and a 32-byte salt (RFC 8017 section 8.1.2)."""
+    hlen = 32
+    k = (n.bit_length() + 7) // 8
+    if len(signature) != k:
+        return False
+    s = int.from_bytes(signature, "big")
+    if s >= n:
+        return False
+    m = pow(s, e, n)
+    embits = n.bit_length() - 1
+    emlen = (embits + 7) // 8
+    if m.bit_length() > embits:
+        return False
+    em = m.to_bytes(emlen, "big")
+    if em[-1] != 0xBC or emlen < 2 * hlen + 2:
+        return False
+    masked, h = em[: emlen - hlen - 1], em[emlen - hlen - 1 : -1]
+    unused = 8 * emlen - embits
+    if unused and masked[0] >> (8 - unused):
+        return False
+    db = bytearray(a ^ b for a, b in zip(masked, mgf1(h, emlen - hlen - 1)))
+    if unused:
+        db[0] &= 0xFF >> unused
+    pad = emlen - 2 * hlen - 2
+    if any(db[:pad]) or db[pad] != 1:
+        return False
+    salt = bytes(db[pad + 1 :])
+    return hashlib.sha256(b"\0" * 8 + hashlib.sha256(message).digest() + salt).digest() == h

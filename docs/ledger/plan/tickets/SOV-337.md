# SOV-337 — The scanner reads the vulnerability database from the Sovereign's own registry

## In plain words

**The problem today.** Inside a Sovereign the vulnerability scanner fetches its database from a public registry. The region's own registry can already serve that database through a pull-through project, but the scanner is not told to use it. After hand-over the public registry may not be reachable, and the database stops being refreshed.

**What changes.** The scanner on every Sovereign reads its vulnerability database from the region's own registry, at the path the variables document names. A render test proves it for a Sovereign with the full variables and for one that carries only the older kit values.

**Done means:**

- On a Sovereign the scanner's settings name the region's own registry and the database path of the variables document.
- A Sovereign whose variables do not name its registry falls back to the registry name that every Sovereign has.
- The path the scanner reads is the path the registry install serves, and a test fails when the two differ.
- The scanner chart installed alone, outside a Sovereign, still reads the same public source as before.
- Nothing else of the scanner changes: its images, its Java database source and its scan limits stay as they are.

The rest of this ticket is the exact instruction for the model that does the work.

## 3. The model (the law)
1. Slot 30 passes exactly two values to the chart, under `spec.values` of the HelmRelease `bp-trivy`: `trivy-operator.trivy.dbRegistry: ${LOCAL_REGISTRY_HOST:=registry.${SOVEREIGN_FQDN}}` and `trivy-operator.trivy.dbRepository: ${REGISTRY_PATH_VULN_DB:=proxy-vulndb/aquasecurity/trivy-db}`.
2. The scanner reads `<dbRegistry>/<dbRepository>`: the upstream chart joins the two values with `/` into the key `trivy.dbRepository` of the ConfigMap `trivy-operator-trivy-config`.
3. `LOCAL_REGISTRY_HOST` is a required key of contract C5 and has no default. The fallback `registry.${SOVEREIGN_FQDN}` is the value the API writes into every child's variables and the host of the registry route of slot 19. Only a Sovereign whose variables carry no contract keys renders the fallback.
4. The default of `REGISTRY_PATH_VULN_DB` in slot 30 is the contract default, and the whole text of `dbRepository` in slot 30 equals the text of `vulnDBPath` in slot 19. The scanner must read the path that the registry serves.
5. The chart alone keeps the source of the upstream chart. `platform/trivy/chart/values.yaml` states it: `dbRegistry: mirror.gcr.io` and `dbRepository: aquasec/trivy-db`. These are the upstream chart's own defaults, so the default render of the chart does not change.
6. The comment in `platform/trivy/chart/values.yaml` that names `ghcr.io/aquasecurity/trivy-db` is replaced: the chart never rendered that address.
7. Nothing else changes: the Java database source (`mirror.gcr.io/aquasec/trivy-java-db`), the two images, the scan limits, the chart version and the version pin of slot 30 stay as they are.
8. Two named exceptions to rule of conduct 9. The fallback of item 3 is specified here. The two values of item 5 are read by the upstream chart's template, not by a file of this change.

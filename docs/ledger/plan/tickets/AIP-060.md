# ADR-0030 — Model plane: one gateway, one model contract, a simulation back end, agent tokens and metered usage

Status: Accepted
Date: 2026-11-13
Supersedes: ADR-0003

Written by work package AIP-060. It records how a caller inside a Sovereign reaches a model, how the caller proves who it is, how usage reaches the billing engine, how agents run, and what is retired. The interface that callers build against is published beside it: `docs/contracts/model-contract.md`. It replaces ADR-0003 as a whole (section "What happens to ADR-0003").

Terms used here:

- **Model plane**: the gateway, the meter and the back ends, together.
- **Alias**: a logical model name that a caller sends, such as `agent-default`. The gateway maps it to a back end.
- **Back end**: what answers a model request. Today the simulation back end, Axon. Later a self-hosted serving engine on GPUs.
- **Agent token**: a short-lived token that catalyst-api mints for one agent of one Organization.
- **Agent workspace**: Agenity, the per-Organization workspace of Blueprint `bp-agenity` (`products/agenity`).
- **Tool server**: `bp-openova-mcp` (`products/openova-mcp`), the platform's server of tools for agents and people.

## Context

Measured on `main` on 2026-11-13.

- Four components stand between a caller and a model, and none of them carries a model request on a Sovereign: Axon (`products/axon`), `bp-newapi` (`platform/newapi`), `bp-llm-gateway` (`platform/llm-gateway`) and `bp-anthropic-adapter` (`platform/anthropic-adapter`). The chart of `bp-llm-gateway` has no Deployment. The image of `bp-anthropic-adapter` is built by no source and no workflow of this repository.
- `bp-newapi` is bootstrap-kit slot 80 (`clusters/_template/bootstrap-kit/80-newapi.yaml`), so every Sovereign installs it. Its model channels are off by default (`platform/newapi/chart/values.yaml`). The signup funnel also lists it, beside `bp-openclaw` and `bp-agenity`, among the Applications that it installs into a new Organization (`products/catalyst/bootstrap/api/internal/handler/organization_funnel_apps.go`). Its channels, users and keys live in its own database, not in Git. ADR-0003 gives each user a gateway user and a key of its own, delivered as a Kubernetes Secret.
- Axon has no `blueprint.yaml` and no kit slot. Its chart pins the image tag `latest` and deploys a Valkey store and an Ingress (`products/axon/chart/values.yaml`). Its Claude path writes the caller's tool definitions into the prompt text (`products/axon/src/providers/claude.ts`). Its route never returns `tool_calls` and reports token usage as 0 (`products/axon/src/routes/chat-completions.ts`). No agent framework can use it as a model.
- The metering sidecar (`core/services/metering-sidecar`) sits in front of `bp-newapi`. It meters only responses of content type JSON, so a streamed call is not metered. It multiplies tokens by one flat price and publishes money on the subject `catalyst.usage.recorded` (ADR-0028, Context).
- The agent workspace calls the model provider directly, with no gateway and no metering. Its model credential is a Secret that an ExternalSecret fills from the Sovereign's OpenBao (`products/agenity/chart/templates/externalsecret-anthropic.yaml`). Its tool calls run on one bearer per Organization that catalyst-api seeds with tier `org-admin` and a life of one year (`products/catalyst/bootstrap/api/internal/handler/sovereign_mcp_bearer_seed.go`). catalyst-api also seeds the model login (`products/catalyst/bootstrap/api/internal/handler/sovereign_anthropic_seed.go`) and refreshes it (`products/catalyst/bootstrap/api/internal/handler/sovereign_anthropic_refresh.go`).
- The tool server has seven tools: six that read and one that writes, `create_application`, which needs tier admin (`products/openova-mcp/internal/tools/catalogue.go`).
- The signer that mints console sessions puts no key identifier in its tokens (`products/catalyst/bootstrap/api/internal/handoverjwt/signer.go`). Its key set is kept in a Secret under the key `signers.jwks`, and no HTTP route serves it.
- catalyst-api already authenticates an in-cluster caller that has no session: the caller sends its projected ServiceAccount token, a TokenReview resolves it, and an allow-list admits it (`products/catalyst/bootstrap/api/internal/handler/internal_auth.go`).
- No chart, Blueprint or kit slot of an agent runtime exists.

## Decision

**M1 One gateway, named.** The model gateway is agentgateway, installed as Blueprint `bp-model-gateway` in kit slot 81 (AIP-140). Spike AIP-010 confirms the choice with eight binary tests. If one test fails, the fallback is that the meter itself verifies the token and maps aliases, until an upstream gateway passes the same tests. `bp-newapi` is retired in both cases (epic AIP-180).

**M2 Placement.** One model plane serves a Sovereign. It runs in the host cluster of the primary region. Other regions reach it through a Cilium global Service. Organization virtual clusters reach it through a replicated host Service (AIP-170). The signup funnel no longer installs a gateway into an Organization (AIP-181).

**M3 One model contract.** Every caller uses one base URL, the aliases `agent-default` and `agent-fast`, and the OpenAI Chat Completions wire format. The alias `conformance-echo` serves gate checks only. The Anthropic Messages route is not offered, because no caller needs it. A change of back end never changes a caller. The contract is `docs/contracts/model-contract.md`.

**M4 The credential at the gateway is an agent token.** A caller authenticates with an agent token: a JWT that lives at most 60 minutes, signed by the Sovereign's own signer and carrying a key identifier (AIP-120). The gateway takes the Organization from the verified token only. No credential of the model plane is a Kubernetes Secret object. The gateway does not accept console sessions. Virtual keys, for an Organization Application that cannot obtain an agent token, are built by AIP-270 for their first consumer.

**M5 Axon is the simulation back end.** Until GPUs arrive, Axon is the back end of the aliases (epic AIP-100). It is rebuilt so that a caller's tools come back as tool calls and never run inside Axon; tool results are accepted in later turns; streaming is real; and usage numbers are real. Each login has exactly one Axon, and only Axon refreshes that credential (AIP-105). It reads the credential from OpenBao through a mount, never from a Secret object, and writes each refreshed version back (AIP-106, AIP-160). It becomes Blueprint `bp-axon` in kit slot 82 (AIP-106).

**M6 An agent is not a model.** The agent workspace is never placed behind a model interface, and it is not placed behind the gateway. It stays the per-Organization workspace beside the agent runtime of M7, on each Organization's own sign-in. Its own model path and its tool path stay. No credential supplied by one party serves another party: each Organization brings its own sign-in or key. AIP-155 replaces the credential seeded from the Sovereign with the Organization's own sign-in, delivered by a mount, and replaces the one-year bearer with a short-lived tool identity, as spike AIP-250 records. AIP-156 then deletes the bearer seed.

**M7 The agent runtime is kagent.** kagent 1.x is the runtime for declared agents, packaged as Blueprint `bp-kagent` with one installation per Organization and pinned to a patch release at least 30 days old (epic AIP-200). It merges only after spike AIP-030 has passed on k3s, Cilium and a virtual cluster.

**M8 An agent is a principal.** The platform service that starts an agent turn asks catalyst-api for an agent token through the internal-route mechanism of the Context, and passes it as the bearer. kagent forwards it to the gateway and to the tool servers. catalyst-api confines an agent token to its Organization with the existing Organization scope guard, and to read methods unless a table entry allows a write (AIP-120). An agent changes desired state only by proposing a pull request (AIP-245). Agents hold no cluster write credential. No token carries a person on whose behalf the agent acts.

**M9 Tool servers.** `bp-openova-mcp` stays the platform tool server. Agents see its six read tools. Its one write tool stays reserved to people: an agent token is capped at tier developer (AIP-150). One tool is added for agents, `propose_change`, with the fixer agent that is its first reader (AIP-245). Every platform tool server accepts the one audience `platform-tools`. Each later plane owns its own tool server under the convention that AIP-150 writes. The tool catalogue of the withdrawn Sandbox is not ported (ADR-0023).

**M10 Metering.** The metering sidecar becomes `model-meter` (`core/services/model-meter`), placed between the gateway and every back end (epic AIP-110). For every answered request, streamed or not, it publishes the one usage event of ADR-0028, `catalyst.usage.recorded.v1`: quantities per token class, no price. The Organization in it is the one the gateway asserted. The meter refuses a stopped Organization (AIP-275). The security fix AIP-040 comes first; its text is published with its ticket.

**M11 Operational records and bounded judges.** A small Go service with PostgreSQL, `ops-records`, delivered as Blueprint `bp-ops-records`, holds signals, incidents, problems and judgements (epic AIP-220). It drives the service-management flow in code. It calls agents as bounded judges: it offers a closed set of answers, validates the answer, and decides by rule when the agent is late. Its tables are domain objects of its Blueprint, not platform kinds. The caller entry it ships names one Organization, never all (AIP-226). The correlator, the investigator and the scribe ship first (epic AIP-240).

**M12 Proof, guardrails, cost.** Each exemplar agent ships an evaluation set. It is `supported` only while that set passes on the current alias mapping (check AIP-G11). Guardrails are a small library inside `ops-records` and inside the tool server (AIP-224). The cost of an agent is read from the meter's token counters, labelled by principal. The bill comes from the usage event.

**M13 Retirements.** Deleted: `bp-llm-gateway` and `bp-anthropic-adapter` (AIP-070); `bp-newapi` with its bridge sidecar, and `bp-openclaw` (epic AIP-180); the gateway client and the per-user key issuing in catalyst-api (AIP-182); the seeding and refreshing of the model credential in catalyst-api (AIP-190); Axon's vLLM provider, conversation store and Valkey (AIP-101). Axon itself stays until the switch-over of M14.

**M14 Switch-over.** When GPUs arrive, the alias mapping in Git changes from back end `simulation` to back end `selfhosted` (epic AIP-290). The evaluation sets run again. Then Axon is deleted (AIP-293). No caller changes.

## Alternatives rejected

**M1.** (a) Keep `bp-newapi`. Its state (channels, model names, users, keys) lives in its own database behind its own screens, not in Git. It keeps a credit ledger of its own beside the one billing product of ADR-0028. It has no per-request usage event, so a meter must be built in either case. (b) A gateway that keeps its state in a database: the same objection. (c) Write a gateway of our own from the start: one more gateway. The fallback of M1 is smaller: it adds token verification and an alias table to a proxy that the platform already owns, and only if the spike fails.

**M2.** (a) One gateway per Organization, as the funnel installs today: every Organization would hold a route to the model credential, and metering would have as many producers as Organizations. (b) One gateway per region: the simulation back end can exist only where the single login lives, so a second region would hold a gateway with nothing behind it.

**M3.** (a) Pass a provider's own OpenAI-compatible endpoint through: it does not serve a subscription login. (b) Offer only the Anthropic wire format: self-hosted serving engines and the agent runtime's gateway wiring use the OpenAI format.

**M4.** (a) A model key stored in a Secret object in each Organization: an Application credential never becomes a Secret object. (b) A token issuer per runtime installation: the gateway would have to trust one issuer per Organization. (c) One static key per Organization: it lives long, and it cannot tell one agent from another. (d) Accept console sessions at the gateway too: sessions carry no key identifier, the gateway selects its verification key by that identifier, and no caller needs it.

**M5.** (a) Leave Axon as it is: no agent framework can use it. (b) Replay every request as a text transcript only: simple and stateless, but the model never sees a real result of its own tool call. It stays as the fallback path inside Axon. (c) Rewrite Axon in Go: the agent kit that drives the login is a TypeScript library.

**M6.** Put the agent workspace behind an OpenAI-compatible wrapper as the model of the agent runtime. An agent runs its own tool loop with its own tools and system prompt. A caller that sends tool schemas and waits for `tool_calls` would get prose back, and two loops would compete. That is the defect Axon has today, with more moving parts.

**M7.** (a) One kagent per Sovereign with a namespace per Organization: its open-source authorizer allows every call, so namespaces would not separate callers. (b) The agent workspace as the only runtime: no declared agents, no approval gate per tool, one process per Organization.

**M8.** (a) Keep the shared one-year bearer: every tool call would run as Organization administrator in the owner's name. (b) Exchange a token at Keycloak for every turn: correct in general, but the tool server and catalyst-api already verify the signer's tokens, so a second issuer would add a system without removing one. (c) A new authentication mechanism for the issue route: catalyst-api already authenticates in-cluster callers by TokenReview. (d) Approval of each tool call inside the runtime as the human gate for a fix: it would add a second approval beside the merge of the pull request, with no screen to give it on. The merge is the gate.

**M10.** (a) Bill from gateway metrics or access logs: they are scraped or best-effort, and a gateway's own cost figure is an estimate. (b) Put the meter in front of the gateway: it would have to authenticate callers a second time and parse two wire formats. (c) A model-specific usage subject with its own payload: the billing engine already consumes one usage event for every meter; a second subject would be a second ingestion contract.

**M11.** (a) Agents drive the flow by calling each other: then no code holds the deadline or the state of an incident, and a late answer cannot be told from a repeated one. (b) A general workflow engine: a new dependency before the foundation is proven. (c) Incidents as custom resources in Git: they are many and operational, and business data belongs in a database. (d) A new platform kind for incidents: the entity model is fixed; these are domain objects of a service that arrives as a Blueprint.

**M13.** Rename the bridge sidecar of `bp-newapi`: it has no caller left once that chart goes, so it is deleted with the chart.

## What happens to ADR-0003

ADR-0003 is the contract of a hook that, for each new user, creates a user and a key in `bp-newapi` and delivers the key as the Secret `newapi-key-{user-uuid}`, which the per-user pod of `bp-openclaw` reads. ADR-0030 withdraws every part that the hook exists for: `bp-newapi` and `bp-openclaw` are retired (M1, M13), no per-user key is issued (M13), and no credential of the model plane is a Secret object (M4). The hook therefore has no work left, and ADR-0003 is superseded as a whole. Its body is not edited; its header names ADR-0030.

## Consequences

- One address, one wire format and one kind of credential serve every caller of a model. A change of back end is one commit to the alias mapping.
- Every answered model request yields one usage event with the verified Organization, and no price. The billing engine rates it (ADR-0028).
- Agents read through the tool server and catalyst-api within their Organization. They change desired state only through a pull request that a person merges.
- The agent workspace keeps working as it does today until AIP-155 replaces its two credentials. Its pillar-4 role does not change.
- Simulated usage is visible and not charged: no price item exists for a model alias in a shipped offer (ADR-0028, decision B9).
- Four components are retired, and the code in catalyst-api that issues per-user keys and seeds and refreshes the model login is deleted.

# Model contract

Status: published by work package AIP-060, with decision record 0030 (`docs/adr/0030-model-plane.md`).
Owner: area AIP, the agent plane. Only that area changes this file.

This file is the interface between every caller of a model inside a Sovereign and the model plane. It has four parts: the HTTP interface (section 1), the agent token (section 2), the identity headers between the gateway and the meter (section 3), and the usage event that the meter publishes (section 4). Each part names the work packages that build it. Until such a package has merged, its part is a specification only.

Conventions: in a table of fields, a field not listed is invalid. Times are RFC 3339 in UTC.

## 1. HTTP interface

### 1.1 Endpoint and routes

Base URL inside a Sovereign: `http://model-gateway.model-gateway.svc.cluster.local:8080/v1`. It is a ClusterIP Service only. It resolves in every region through a Cilium global Service, and inside every Organization virtual cluster through a replicated host Service (AIP-170).

| Method and path | Offered from | Purpose |
|---|---|---|
| `POST /v1/chat/completions` | AIP-140 | OpenAI Chat Completions. Every back end serves it. |
| `GET /v1/models` | AIP-140 | Lists the aliases as model objects. The field `owned_by` of each object is the back-end key of the alias. |

The Anthropic Messages route, `POST /v1/messages`, is not offered. No caller needs it. A package that brings its first caller adds it, together with a gate check of its own.

Request header: `Authorization: Bearer <credential>`. The credential is an agent token (section 2), or a virtual key once AIP-270 has built them. The gateway removes every request header whose name starts with `x-openova-`.

Back-end keys: `simulation` (Axon), `selfhosted` (a self-hosted serving engine), `stub` (a scripted back end for gate checks). AIP-320 adds `upstream`, the model plane of a parent Sovereign. An alias whose back end is not `simulation` or `upstream` keeps the request inside the Sovereign.

### 1.2 Aliases

| Alias | Meant for | Simulation phase | GPU phase |
|---|---|---|---|
| `agent-default` | Agents that decide, and tool use | back end `simulation`, upstream model `sim-default` | back end `selfhosted`, the served model name |
| `agent-fast` | Short reads and summaries | back end `simulation`, upstream model `sim-fast` | back end `selfhosted`, the same or a smaller model |
| `conformance-echo` | Gate checks only | back end `stub` | back end `stub` |

A request whose `model` is not an alias gets HTTP 404 with the error code `model_not_found`. A new alias is added by a work package that names its first reader. A change of back end is a change of the alias mapping in Git; it never changes a caller.

### 1.3 Request fields of `POST /v1/chat/completions`

"Native" means that the back end honours the field as the OpenAI specification says.

| Field | Simulation back end | Self-hosted back end |
|---|---|---|
| `model` | an alias, required | the same |
| `messages` with the roles `system`, `user`, `assistant` (with `tool_calls`) and `tool` | native for the roles; `system` messages are joined with a blank line and used as the system prompt | native |
| `messages[].content` as text parts | native | native |
| `messages[].content` as image parts (`image_url` with a `data:` URL) | from AIP-107; before that HTTP 400 `unsupported_content` | native if the model has vision |
| `tools` (type `function`) | native: returned as `tool_calls`, never run by the back end. A tool name longer than 56 characters gets HTTP 400 `tool_name_too_long` | native |
| `tool_choice` `auto` or `none` | native | native |
| `tool_choice` `required` or a named function | emulated by an instruction, not guaranteed; response header `x-openova-emulated: tool_choice` | native |
| `parallel_tool_calls: false` | enforced: only the first call is returned; the others are answered inside the back end as not run | native |
| `stream`, `stream_options.include_usage` | native: real deltas, including deltas of tool-call arguments | native |
| `response_format` `json_schema` | from AIP-107 through structured output; before that emulated by an instruction | native |
| `reasoning_effort` | mapped to an effort level `low`, `medium` or `high` | native if supported |
| `max_tokens`, `max_completion_tokens` | accepted, not enforced | native |
| `stop` | applied by cutting the output | native |
| `temperature`, `top_p`, `seed`, `presence_penalty`, `frequency_penalty`, `logit_bias`, `logprobs`, `top_logprobs` | accepted and ignored | native |
| `n` greater than 1 | HTTP 400 `unsupported_parameter` | native |
| `user`, `metadata`, `store` | ignored | ignored |

The fields `conversation_id`, `thinking`, `effort` and `profile`, which Axon accepts today, are not part of this contract.

### 1.4 Response

The response is the OpenAI `chat.completion` object, or a `chat.completion.chunk` stream. Every back end behaves as follows.

- Each entry of `choices[0].message.tool_calls[]` has a unique `id`, `type: function`, a `function.name` equal to the caller's tool name, and `function.arguments`, a JSON object encoded as a string. `finish_reason` is `tool_calls` when that list is not empty, and otherwise `stop`, `length` or `content_filter`.
- `usage.prompt_tokens`, `usage.completion_tokens` and `usage.total_tokens` are not zero for an answered request. `usage.prompt_tokens_details.cached_tokens` is present, and 0 when it is not known. The simulation back end also sets `usage.prompt_tokens_details.cache_write_tokens`.
- A stream sends, in this order: a first chunk with `delta.role`; content deltas as they are generated, and tool-call deltas with `index`; a chunk with `finish_reason`; a usage chunk with empty `choices`; then `data: [DONE]`. The meter removes the usage chunk when the caller did not ask for it.
- The response header `x-request-id` equals the identifier of the request in the usage event (section 4). The gateway sets it when the caller did not.

### 1.5 Errors

The body of an error is `{"error": {"message": "<text>", "type": "<type>", "code": "<code>"}}`.

| Status | `code` | When | What the caller does |
|---|---|---|---|
| 400 | `invalid_request`, `unsupported_parameter`, `unsupported_content`, `tool_name_too_long`, `missing_tool_results` | The request is wrong. The last code: a follow-up request has no result for a tool call that was returned. | Fix the request. |
| 401 | `invalid_token` | No token, a bad signature, an unknown key identifier, a wrong issuer, or the token expired. | Obtain a new token. |
| 403 | `organization_stopped` | The Organization is suspended or stopped for overage. The meter answers this, from AIP-275. | Stop. |
| 404 | `model_not_found` | `model` is not an alias. | Fix the request. |
| 429 | `rate_limit_exceeded` | The back end is at capacity, or the upstream limit was hit. Header `Retry-After: <seconds>`. | Wait, then retry. |
| 502 | `backend_error` | The back end failed. | Retry once. |
| 503 | `simulation_credential_invalid` | The simulation credential is absent, expired beyond refresh, or rejected. | Do not retry. A sovereign-admin must act. |
| 504 | `backend_timeout` | No first byte came within the first-byte time-out of the alias, a value of the gateway chart (AIP-140). | Retry once. |

## 2. Agent token

An agent token is a JWT signed with RS256 by the catalyst-api signer of the Sovereign, the signer that already mints console sessions (`products/catalyst/bootstrap/api/internal/handoverjwt/signer.go`). It differs from a session in three ways: its header carries a key identifier, it carries an audience claim, and it carries `typ: agent`. Sessions do not change. AIP-120 builds the issue route, the key set route and the verification at catalyst-api.

### 2.1 Format

Header: `{"alg": "RS256", "typ": "JWT", "kid": "<key identifier>"}`. The key identifier is the RFC 7638 thumbprint of the signer's public key: SHA-256, base64url without padding.

| Claim | Type | Value |
|---|---|---|
| `iss` | string | The session issuer of the Sovereign: the value that `pinIssuer()` in `products/catalyst/bootstrap/api/internal/handler/auth.go` returns. |
| `aud` | list of strings | `["model-gateway", "platform-tools", "catalyst-api"]`. `platform-tools` is the one audience of every platform tool server. |
| `sub` | string | `agent:<organization>/<agent>` |
| `typ` | string | `agent` |
| `org`, `org_id` | string | The slug of the Organization. |
| `agent` | string | The agent name, pattern `^[a-z][a-z0-9-]{1,62}$`. |
| `tier` | string | `viewer` or `developer`. Never higher. |
| `realm_access` | object | `{"roles": ["catalyst-<tier>"]}` |
| `role` | string | `openova-user`, the value that sessions carry. |
| `email` | string | `<agent>@<organization>.agents.invalid`. It is synthetic and not routable. It exists because handlers and the tool server read `email` as the actor. |
| `email_verified` | boolean | `false` |
| `caller` | string | The TokenReview user name of the workload that asked for the token: `system:serviceaccount:<namespace>:<name>`. |
| `iat`, `exp` | number | The life of a token is at most 3,600 seconds; the default is 1,800. |
| `jti` | string | A UUID. |

Every claim is required. There is no claim for a person on whose behalf an agent acts: no caller acts for a signed-in person, so none is built.

### 2.2 Issue route

`POST /api/v1/internal/agent-tokens` on catalyst-api, outside the session group, beside the other internal routes. Its entry in the mutating-route table (contract C9) has the write class `none`.

- Caller authentication: the mechanism that the internal routes use today, unchanged. The caller sends `Authorization: Bearer <projected ServiceAccount token>`, and a TokenReview resolves it (`products/catalyst/bootstrap/api/internal/handler/internal_auth.go`).
- Caller authorisation: the environment variable `CATALYST_AGENT_TOKEN_CALLERS`, a JSON list. Each entry is `{"caller": "<TokenReview user name>", "organizations": ["*"] or a list of slugs, "maxTier": "viewer" or "developer", "agents": ["*"] or a list of names}`. All four keys are required. The chart value is `agentTokens.callers`. Its default is exactly one entry, `{"caller": "system:serviceaccount:catalyst-system:catalyst-conformance", "organizations": ["conformance"], "maxTier": "viewer", "agents": ["conformance-probe"]}`, so that gate checks run on a fresh Sovereign. No other workload may mint a token until a commit of values adds its entry. A value that cannot be parsed makes the route answer 503 `agent-tokens-misconfigured`. It never falls back to allowing.
- Request body: `{"organization": "<slug>", "agent": "<name>", "tier": "viewer" or "developer", "ttlSeconds": <integer 60 to 3600>}`. `ttlSeconds` is optional; its default is 1,800. An unknown field is refused.
- Response 200: `{"token": "<jwt>", "expiresAt": "<RFC 3339 time>"}`.
- Errors, with the body `{"error": "<code>", "detail": "<text>"}` that the internal routes use today: 401 `missing-bearer`; 502 `token-review-failed`; 403 `unauthorized-sa` (the caller is in no entry); 403 `caller-not-allowed` (the Organization, the agent or the tier is outside the caller's entry); 422 `invalid-request`; 503 `signer-unavailable`; 503 `agent-tokens-misconfigured`.
- Every issue writes one audit event through the audit package (`products/catalyst/bootstrap/api/internal/audit/audit.go`) with the action `agent-token.issue` and the fields `caller`, `organization`, `agent`, `tier` and `jti`. The token itself is never logged.

Example:

```
POST /api/v1/internal/agent-tokens
Authorization: Bearer <ServiceAccount token of ops-records/ops-records>
{"organization": "acme", "agent": "correlator", "tier": "viewer", "ttlSeconds": 1800}

200 {"token": "eyJhbGciOiJSUzI1NiIsImtpZCI6Ik5Vd0…", "expiresAt": "2026-12-01T09:30:00Z"}
```

### 2.3 Key set route

`GET /api/v1/auth/signers.jwks` on catalyst-api, outside the session group, with no authentication. Response 200, `application/json`, `Cache-Control: max-age=300`:

```json
{"keys": [{"kty": "RSA", "use": "sig", "alg": "RS256", "kid": "<key identifier>", "n": "<modulus>", "e": "AQAB"}]}
```

It has one entry: the public key of the signer of this pod. The route returns public material only, so it may be reachable through the console address. The Secret key `signers.jwks` and its readers do not change.

### 2.4 Verification

At catalyst-api (AIP-120):

1. The claims type `Claims` in `products/catalyst/bootstrap/api/internal/auth/session.go` gains three fields: `Typ string` (claim `typ`), `Agent string` (claim `agent`) and `Audience []string` (claim `aud`, which may be a string or a list).
2. The validator uses the local signer key when the token has no key identifier (the rule today) or when its key identifier equals the local one. No other branch changes.
3. `claimsAreOrgScoped` in `products/catalyst/bootstrap/api/internal/handler/org_scope.go` also returns true when `Typ` is `agent`. From then on, the Organization scope guard and `orgScopeForRequest` confine an agent token to the Organization of its `org_id` claim, exactly as they confine an Organization session: denied by default outside the list of Organization-safe routes.
4. A new middleware, `agenttoken.Restrict`, runs after the Organization scope guard. For a token with `Typ` `agent`: if `Audience` does not contain `catalyst-api`, the answer is 401 `agent-token-wrong-audience`. `GET`, `HEAD` and `OPTIONS` pass. Any other method passes only when an entry of the table `agenttoken.MutationsAllowed` matches the method, the path pattern and the minimum tier; otherwise the answer is 403 `agent-token-forbidden`. The table is empty when AIP-120 merges. AIP-245 adds its one entry. For any other token the middleware does nothing.

At the tool server (AIP-150): the resolver accepts `typ: agent` only when `aud` contains `platform-tools`. The tier is the `tier` claim, capped at developer. The identity gains the field `Agent string`. `create_application` needs tier admin, so no agent token can call it.

At the gateway (AIP-140): the signature against the key set route, `iss` equal to the issuer of the Sovereign, the expiry, and `aud` containing `model-gateway`.

When an Organization is stopped, the meter refuses its requests (AIP-275). The issue route does not check the state of the Organization; a token is refused at the model plane within one request.

## 3. Identity headers between the gateway and the meter

The gateway sets these headers from the verified credential, after it has removed any header of the same name that the caller sent. The meter trusts them because only gateway pods may open connections to the meter (a network policy of the gateway chart, AIP-140).

| Header | Value for an agent token | Value for a virtual key (AIP-270) |
|---|---|---|
| `x-openova-organization` | the claim `org_id` | the Organization the key was registered for |
| `x-openova-principal-kind` | `agent` | `application` |
| `x-openova-principal` | the claim `agent` | the name of the key |
| `x-openova-alias` | the `model` that the caller sent | the same |
| `x-request-id` | the caller's value if it matches `^[A-Za-z0-9._-]{8,64}$`, otherwise a new ULID | the same |

Every header is required. Readers: the usage event reads the Organization and the alias; the counters and the log line of the meter read the principal kind and the principal; gate checks read `x-request-id`. A header with no reader is not added.

## 4. Usage event

The billing engine consumes exactly one usage event inside a Sovereign, `catalyst.usage.recorded.v1` (decision record 0028, decisions B8 and B9). The agent plane produces it and defines its fields. This section is the producer's side. The meter, `model-meter` (epic AIP-110), publishes it.

- Subject `catalyst.usage.recorded.v1` on the stream `CATALYST_ORG`.
- Envelope: CloudEvents 1.0 in structured JSON mode, with exactly eight attributes: `specversion` (`1.0`), `id`, `type`, `source`, `subject`, `time`, `datacontenttype` (`application/json`) and `data`. `type` is `io.openova.catalyst.usage.recorded.v1`. `source` is `model-gateway/<sovereign-fqdn>/<region-id>`. `subject` is the Organization slug. `id` is a ULID made once per request and kept across retries; it is sent as the JetStream message identifier (`Nats-Msg-Id`), and it is also the request identifier when the gateway made one.
- Consumer: the billing engine, durable `chargeback-usage` (BSS-131). It removes duplicates by `source` and `id`. Delivery is at least once.
- Registry: the subject has one entry in `docs/contracts/C3-event-subjects.yaml`, owned by area BSS, envelope `cloudevents`, delivery `at-least-once`, payload the Go type of the event in `core/services/model-meter`. AIP-111 adds the entry when it is absent, with the producer `model-meter`; the registry names a service by its folder under `core/services`. When the entry exists, AIP-111 adds `model-meter` to its producers if it is missing.

The `data` block. Every field is required.

```yaml
organization: acme               # string, pattern ^[a-z][a-z0-9-]{2,31}$. From x-openova-organization. Equals the envelope subject.
resource:
  kind: llm-model                # constant for this producer
  id: agent-default              # string. The alias that the caller asked for (x-openova-alias).
occurredAt: 2026-12-01T09:00:06Z # the time the response ended
measures:                        # list of 1 to 5 entries, each {meter, quantity}; quantity is an integer of 0 or more
  - {meter: llm.tokens.input, quantity: 304}
  - {meter: llm.tokens.cache_read, quantity: 1536}
  - {meter: llm.tokens.output, quantity: 212}
  - {meter: llm.requests, quantity: 1}
```

How the measures are computed from the usage block of the back end:

| Measure | Value |
|---|---|
| `llm.tokens.input` | `prompt_tokens` minus `prompt_tokens_details.cached_tokens` minus `prompt_tokens_details.cache_write_tokens`; never below 0 |
| `llm.tokens.cache_read` | `prompt_tokens_details.cached_tokens`, 0 when absent |

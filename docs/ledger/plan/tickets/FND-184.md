# FND-184 — Scheduled Git bundles of the Sovereign's repositories

## In plain words

**The problem today.** No Git repository of a Sovereign is copied anywhere. Gitea holds the only copy of the fleet repository and of every Organization's repositories, so a lost volume or a lost region loses them. Decision record 0036 fixes the schedule, the retention and the place in the bucket, and nothing builds it.

**What changes.** The Gitea chart gets a scheduled job that writes a bundle of every repository whose default branch moved to the Sovereign's bucket and keeps the newest ten, as soon as its installation names the bucket. The Secret register lists the Secret that holds the bucket's key pair.

**Done means:**

- An installation that names the bucket gets one scheduled job, every 15 minutes, in the region whose Gitea takes the writes, and none in another region.
- Each run writes one bundle of every repository whose default-branch head has no bundle yet, named after that head, and a clone of the bundle has that head and every branch and tag.
- A repository without a commit gets no bundle, the 10 newest bundles of each repository stay, and the bundles of a deleted repository are left alone.
- The bucket's key pair and the administrator login reach the job as mounted files and never appear on a command line; the chart writes no Secret, and the Secret it reads is listed in the Secret register.
- A refused upload or a refused repository list fails the run, and an installation that names the bucket but leaves out its endpoint or the Secret fails to render.
- An installation that names no bucket renders exactly what it renders today.

The rest of this ticket is the exact instruction for the model that does the work.

## 2. End goal
The chart `platform/gitea/chart` gives the Sovereign's Gitea the Git row of decision record 0036 as soon as the installation names the Sovereign's bucket (`gitBundle.objectStore.bucket`): a CronJob `<release>-git-bundle` in the release namespace, every 15 minutes, in the writer region only, writes `git bundle create --all` of every repository whose default-branch head has no bundle yet to `git/<owner>/<repository>/<head>.bundle` of the bucket, and keeps the 10 newest bundles of each repository. ## 3. The model (the law)
1. **Values** (`platform/gitea/chart/values.yaml`, new block `gitBundle`): `schedule` `"*/15 * * * *"`, `keep` `10`, `image` `"harbor.openova.io/proxy-dockerhub/gitea/gitea:1.22.3-rootless"` (the image of the Gitea Deployment), `scratchSizeLimit` `2Gi`, `objectStore.bucket` `""`, `objectStore.endpoint` `""`, `objectStore.secretName` `object-storage`. There is no `enabled` value: naming the bucket switches it on, as for the database row (FND-183). No chart version change.
2. **Without a bucket nothing changes.** With `gitBundle.objectStore.bucket` empty no CronJob renders; every other object renders as before.
3. **With a bucket, the rest is required.** `gitBundle.objectStore.endpoint`, `gitBundle.objectStore.secretName`, `gitBundle.keep` and `gitBundle.image` must be non-empty, or the render fails with `bp-gitea: gitBundle.<key> is required when gitBundle.objectStore.bucket is set`; `gitBundle.keep` below 1 fails with `bp-gitea: gitBundle.keep must be 1 or more`.
4. **One region.** The CronJob renders only when `platformRepos.writerRegionId` is empty or equals `platformRepos.regionId`: the region whose Gitea takes the writes, the gate of `templates/platform-repos-job.yaml`, which bootstrap-kit slot 10 already fills. The follower region's mirror is not touched and no second copy mechanism is added.
5. **The CronJob** (new `templates/git-bundle-cronjob.yaml`): `concurrencyPolicy: Forbid`; its `jobTemplate.metadata.labels` carry `app.kubernetes.io/managed-by: flux`, because the Job the CronJob controller creates is not an object of the release and the policy `flux-managed` matches Jobs (as `platform/openbao/chart/templates/backup-snapshot.yaml`); the pod runs as user 1000, non-root, with a read-only root file system, no service-account token, cpu and memory requests and limits; it mounts the administrator Secret `giteaAdmin.secretName` at `/etc/gitea-admin` and the keys `s3-access-key`, `s3-secret-key` and `s3-region` of `gitBundle.objectStore.secretName` at `/etc/object-storage`. No environment variable name contains PASSWORD, TOKEN, KEY or SECRET, and no `secretKeyRef` is added.
6. **One run.** It lists every repository with `GET /api/v1/repos/search` as the site administrator, page by page until a page lists none; reads each default-branch head with `git ls-remote <repository> HEAD`; a repository without a head gets no bundle; for a head with no object `git/<owner>/<repository>/<head>.bundle` in the bucket it clones the repository with `--mirror`, takes the head of the clone as `<head>`, runs `git bundle create --all` and `git bundle verify`, and puts the bundle at that key. It then deletes all but the `KEEP` newest objects `git/<owner>/<repository>/<commit id>.bundle` of each listed repository, newest by the bucket's last-modified time; it deletes no other key, and a repository that Gitea no longer lists keeps all its bundles. Requests to the bucket are path-style and signed with AWS signature version 4 by curl. The key pair and the administrator login reach curl on its standard input (`-K -`) and git through its environment, never a command line. A failed repository fails the run after the others; a refused repository list fails the run at once. The run keeps no state between runs.
7. **No Secret object in the chart.** The chart references the Secret and renders none: no new line `kind: Secret` in a chart template (guard G3). The Secret is register entry `git-bundle-bucket`: namespace `gitea`, name `^object-storage$`, class T (the Job reads files, and the injection mount does not reach namespace `gitea` yet), removal `SEC-342`, review by `2027-11-01`.
8. **The test** `platform/gitea/chart/tests/git-bundle-render.sh` prints `  PASS  G1 ` to `  PASS  G6 ` and `  PASS  R1 ` to `  PASS  R5 `: G1 the default render; G2 the CronJob with a bucket (laws 1, 5 and 7, the image equal to the Gitea Deployment's); G3 the required values; G4 a changed schedule and keep; G5 the writer-region gate; G6 the register entry; R1 to R5 run the rendered script with `sh` against real git on local bare repositories and a stand-in `curl` for the Gitea API and the bucket (R1 a first run, R2 a run with no new commit clones, writes and deletes nothing, R3 a new commit, R4 no credential on a command line, R5 the two failures). It needs helm, yq and git, and no Python.

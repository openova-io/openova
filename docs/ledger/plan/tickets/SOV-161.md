# SOV-161 — The pull robot of the local registry joins the pull secret at install

## In plain words

**The problem today.** A new Sovereign's pull Secret carries a login for the parent's registry only. The login for the Sovereign's own registry is added during the hand-over, and it is the registry's administrator account, so nothing can pull a private chart or image from the local registry before the hand-over, and what pulls later uses the administrator's password.

**What changes.** Installing Harbor creates a robot account that may only pull, and writes its login into the pull Secret under the local registry host. A Job does it, and it can run again without changing anything.

**Done means:**

- On a new Sovereign whose variables carry the local registry host, the pull Secret of flux-system holds a login for that host before any hand-over step runs, and every other login in it is unchanged.
- That login belongs to a robot account of the local registry that may pull from every project and do nothing else.
- Running the Job again leaves the robot and the Secret as they are; a login that no longer works is replaced by a new robot.
- Each region's Job uses a robot of its own, so two regions that share one registry database never replace each other's login.
- A Sovereign whose variables do not carry the local registry host, or carry the parent's host there, gets no Job.
- A test of the chart proves these rules on every pull request that changes the chart: it renders the Job, and it runs the script of the Job against stand-ins for the registry and the Secret.

The rest of this ticket is the exact instruction for the model that does the work.

## 2. End goal
When a Sovereign is installed, the pull Secret that Flux and the workloads use (`flux-system/<REGISTRY_PULL_SECRET>`, default `ghcr-pull`) already holds a login for the Sovereign's own registry (`LOCAL_REGISTRY_HOST`, for example `registry.<sovereign-fqdn>`), before any hand-over step runs. The login belongs to a system robot account of this region's Harbor that may pull from every project and do nothing else. The chart `bp-harbor` (bootstrap-kit slot 19) carries the Job that creates the robot and writes the login; slot 19 passes the host, the Secret name and the region from the Sovereign's variables. The Job can run any number of times: a working login is left alone, a missing or broken one is replaced. A test of the chart proves every rule: it renders the Job, and it runs the Job's own script against stand-ins for Harbor and for the Secret.

## 3. The model (the law)
1. **Files.** The two new files are the blocks `pull-robot-job.yaml` and `pull-robot-job.sh` of field 5, byte for byte. The two edited files change only by the two insertions of field 16 (steps 5 and 6): each inserts lines after one anchor line and removes nothing.
2. **When it renders.** `templates/pull-robot-job.yaml` renders only when `pullRobot.enabled` is true (the default), `pullRobot.host` is not empty, and `pullRobot.host` differs from `pullRobot.originHost`. An empty host means the Sovereign's variables do not carry `LOCAL_REGISTRY_HOST`; a host equal to the origin host would overwrite the login of the parent's registry. In both cases nothing renders. With the chart's own defaults (host empty) nothing renders.
3. **What renders.** Four objects. A ServiceAccount `<release>-pull-robot` in the release namespace. A Role and a RoleBinding of the same name in `pullRobot.secretNamespace` (default `flux-system`, the namespace that `docs/contracts/c5-upstream-variables.schema.json` names for the pull Secret): the Role allows only `get` and `patch` on the one Secret `pullRobot.secretName`, and the RoleBinding gives it to the ServiceAccount. A plain `batch/v1` Job `<release>-pull-robot-<8 hex>` in the release namespace, not a Helm hook (slot 19 installs with `disableWait: true`, as for the Job of `templates/registry-projects-job.yaml`). The hex is a hash of the host, the Secret namespace and name, the robot name, the image and the chart version, so a changed input or a new chart version runs it again. The Job uses that ServiceAccount with its token mounted, the image `pullRobot.image` (through a proxy project), runs as user 1001 with a read-only root file system, has cpu and memory requests and a memory limit, and mounts the admin Secret `harborAdmin.secretName` (default `harbor-admin`) read-only at `/etc/harbor-admin`. No environment variable name holds `PASSWORD`, `TOKEN`, `KEY` or `SECRET` (the cluster policy `secret-not-in-env` refuses those with a literal value).
4. **The robot.** Its name is `pullRobot.name` (default `local-pull`), followed by `-` and `pullRobot.regionKey` when that is not empty. The region key is written in lower case, each run of characters other than `a-z` and `0-9` becomes one `-`, and leading and trailing `-` are removed (`Hw-ME_east--1-` gives `local-pull-hw-me-east-1`). It is created with `POST /api/v2.0/robots` and the body `{"name":"<name>","description":"Pull login of the local registry, kept in the pull Secret by bp-harbor","level":"system","duration":-1,"disable":false,"permissions":[{"kind":"project","namespace":"*","access":[{"resource":"repository","action":"pull"}]}]}`: a system robot that never expires and may pull from every project, also projects made later. Harbor answers 201 with the full name (`robot$<name>`) and the secret; the secret is shown only in that answer. Each region names its own robot, because on a Sovereign with two regions the second region's Harbor may use the first region's database: a robot shared by both Jobs would have its secret replaced by whichever ran last.
5. **The script of the Job**, in this order. (a) Wait up to 90 times 10 seconds for `GET /api/v2.0/ping` of `http://<release>-core.<namespace>.svc.cluster.local`. (b) Read the pull Secret with `kubectl get secret -o json`, decode its key `.dockerconfigjson`, and require an `auths` object; otherwise fail before anything in Harbor changes. (c) Read `.auths["<host>"].username` and `.password`. (d) List the robots with `GET /api/v2.0/robots?page=1&page_size=100` as `admin` and find the one with level `system` whose name after the last `$` is the robot name. (e) When it exists, is not disabled, its full name equals the stored username, and the stored password is accepted by `GET /service/token?service=harbor-registry` (answer 200): print `... nothing to do` and exit 0. (f) Otherwise, when it exists: `DELETE /api/v2.0/robots/<id>` (answer 200), because its secret cannot be read back. (g) Create the robot as item 4 says; any answer but 201 fails the Job. (h) Check the new login with the token call of (e); a refusal fails the Job. (i) Set `.auths["<host>"]` to `{"username":<full name>,"password":<secret>,"auth":<base64 of "name:secret">}`, keep every other entry, and write the key back with `kubectl patch secret --type=merge`. Every failure prints a line starting `[pull-robot] FATAL:` and exits non-zero; the Job then retries (backoff limit 6).
6. **Slot 19** passes `pullRobot.host` from `LOCAL_REGISTRY_HOST`, `pullRobot.originHost` from `ORIGIN_REGISTRY_HOST`, `pullRobot.secretName` from `REGISTRY_PULL_SECRET` (default `ghcr-pull`, the contract default) and `pullRobot.regionKey` from the kit key `SOVEREIGN_REGION_KEY`, each as `${KEY:=default}`. The three values with an empty default are written in quotes. The quotes do not decide what the chart gets: Flux substitutes into the text and parses it again, so a value that becomes empty reaches the chart as the empty string or as null (the repository's own model of the substitution, in the header of `scripts/check-kit-render-equivalence.sh`, keeps no quote of the source). The template reads each of the three through `default ""`, so both give the same render; case 6 of the test renders both. A Sovereign whose variables do not carry `LOCAL_REGISTRY_HOST` renders no Job.
7. **The test and where it runs.** `tests/pull-robot-job.sh` has two parts. Cases 1 to 6 render the chart; they need bash, Helm and Python with PyYAML. Case 7 runs the Job's script against stand-ins for `curl` and `kubectl`; it needs `jq` and `base64` too, because the script itself calls them. Run as `bash <script> <chart dir>`, the way the chart-test jobs of CI run it, the test runs every case and fails when `jq` is missing: it never leaves case 7 out silently. Run with the word `render` as a second argument, it runs cases 1 to 6 only. Acceptance A1 uses `render`, because `jq` is not one of the tools of an acceptance command. The whole test is proven by the check `chart/tests/*.sh — platform/harbor` (field 10).
8. **Nothing else changes.** No file outside field 14. No chart version line, no slot pin and no `Chart.yaml`: CI writes versions after the merge (package FND-011). No Secret is created by the chart. No network policy is added. The hand-over chart is not changed.

# INF-051 — Check INF-G01: coordinated reboot, as a suite file

## In plain words

**The problem today.** Nodes that need a restart after a security update are restarted by kured, one node at a time and drained first. Nothing tests on a running Sovereign that this is what happens. A wrong setting could take two nodes out of service at once or leave a node out of service, and no acceptance run would notice.

**What changes.** The acceptance suite gains a check that asks kured to restart three nodes in each region and watches how it does that. The list of checks marks it as expected to fail for now, so it runs and is recorded and cannot fail a run yet.

**Done means:**

- The check touches no node unless the install journey of the same run passed.
- In each region it puts a pending restart on one control-plane node and two other nodes, and it fails when the region has fewer than three nodes.
- It fails when two nodes are out of service at the same time, when a node restarts without being taken out of service first, or when a node stays out of service longer than a drain may take.
- It fails when the three nodes have not restarted and returned to service within the time limit that follows from the settings of kured: 75 minutes with the settings the platform ships.
- It takes one region after the other and starts no region after one has failed.
- When the hours in which kured may restart nodes are closed, it waits for them before it touches a node, for at most 150 minutes.
- Its tests run on every pull request without a cluster, with one failing case for each rule.

The rest of this ticket is the exact instruction for the model that does the work.

## 2. End goal
The acceptance suite under `tests/acceptance/sovereign/` has one more gate check, INF-G01 (coordinated reboot), in the file `internal/suite/check_inf_g01.go`. When the suite runs in the cloud with the gate manifest, the check first looks at journey J1 of the same run. If J1 passed, it takes the regions one after the other. In a region it reads the settings of kured from the DaemonSet `kube-system/kured`, chooses one control-plane node and two other nodes, creates the file that tells kured "this node needs a reboot" on the three nodes, and then reads the Node objects every 5 seconds. It passes only when kured restarts the three nodes one at a time, each drained first, and every node of the region is schedulable and Ready again inside the time limit. The manifest `docs/ledger/gates.yaml` names the file and has the entry INF-G01 in state `expected-fail`: the check runs and is recorded, and it cannot fail a run. The tests of the check need no cluster and run on every pull request. The README of the suite and the package comment of `internal/kube` say what the check writes to a cluster.

This ticket does not make the check read the upgrade Plans, the pods of kured or the HelmReleases, and it does not set the entry to `required`. A later package of area INF adds those three and sets it to `required`.

## 3. The model (the law)
1. **The files are fixed.** `check_inf_g01.go` and `check_inf_g01_test.go` are the blocks of the same names at the end of field 20, each with its checksum. The README of the suite and `internal/kube/kube.go` are changed by the script `INF-051-edits.py` (the third block) and by nothing else. `docs/ledger/gates.yaml` is changed by the one command of work step 9 and by nothing else.
2. **The form of a check.** A gate check of the suite is one file in `tests/acceptance/sovereign/internal/suite/` that calls `RegisterCheck` in `init()` and holds the identifier of the check as a string constant. INF-G01 is the type `rebootCheck`. It calls `kubectl` through its field `kubectl` of the type `kubectlFunc`, reads the time through its field `now`, and waits through its field `wait`. The registered check holds `kube.Region.Run`, `time.Now` and a wait on a timer there. The tests put a fake cluster and a fake clock there.
3. **Journey J1 first.** Step `INF-G01.1` passes only when the run recorded at least one step of journey J1 and every one of them is PASS (the function `priorPassed`). When it fails the check ends: no namespace is created and no node is touched.
4. **One region after the other.** The regions are taken in the order of the run. A region is started only when every step of every region before it passed. Two regions never have pending reboots from this check at the same time.
5. **The settings come from kured itself.** In a region the check lists the DaemonSets of the namespace `kube-system` and takes the one named `kured`. None fails the step ("kured is not installed"). From the arguments of its container `kured` it reads `--period`, `--lock-release-delay`, `--drain-timeout` (Go durations, as `15m`), `--start-time` and `--end-time` (the form `HH:MM`), `--time-zone` (a name that `time.LoadLocation` knows) and `--reboot-sentinel` (only the file name is used). From its volume `sentinel` it reads the `hostPath` path: the folder of the node that holds the sentinel file. An argument that is absent or not in that form fails the step and is named. The check assumes no default.
6. **The time limit** of a region is 3 x (period + lock release delay) + 15 minutes. With the settings of the kit (`15m`, `5m`) it is 75 minutes. In the lab the second of two nodes was back at most 2266 seconds after the sentinel file was written (`docs/ledger/plan/spikes/INF-030.md`); one more round of 20 minutes for a third node gives about 58 minutes.
7. **The three nodes.** The check lists the nodes of the region. A node is a control-plane node when its label `node-role.kubernetes.io/control-plane` is `true`. The step fails when a node is unschedulable or not Ready already, when the region has fewer than three nodes, or when it has no control-plane node. The three nodes are: the first control-plane node by name; then the first two by name of the nodes that are not control-plane nodes; when fewer than two such nodes exist, the next control-plane nodes by name fill the gap.
8. **The reboot span.** kured restarts a node only between its start time and its end time, in its time zone. The check goes on at once when the span is open now and stays open for the whole time limit. Otherwise it looks at the time until the span opens the next time. When that is at most 150 minutes, it waits that long and goes on. When it is longer, the step fails and no node is touched. The days of the span (`--reboot-days`) are not read.
9. **The pending reboot.** The check creates the namespace `inf-reboot-<run>` (`<run>` is the result of `NewRunID` in lower case) and one Pod `sentinel-<n>` per chosen node, `<n>` counted from 0, with `kubectl -n <namespace> create -f -` and the Pod as JSON on standard input. The Pod: `nodeName` is the node; `restartPolicy: Never`; no service-account token and no service links; it tolerates every taint; one container `sentinel` with the image of the probe Pods of `sec_probe.go` (the constant `secProbeImage`), the command `touch /host/<file name>`, user 0, no privilege escalation, a read-only root file system, every capability dropped, the requests `cpu: 50m` and `memory: 32Mi` and the memory limit `128Mi`. It mounts the folder of rule 5 at `/host`, type `Directory`, writable. The check then waits with `kubectl -n <namespace> wait --for=jsonpath={.status.phase}=Succeeded pod --all --timeout=180s`.
10. **The namespace is always deleted.** Whenever the namespace was created, also when a Pod was refused or did not finish, the next step runs `kubectl delete namespace <namespace> --wait=false --ignore-not-found`, with a time limit of one minute of its own that does not end when the run is cancelled. The readings of rule 11 start only when the Pods finished and the namespace was deleted.
11. **The readings.** The check lists the nodes every 5 seconds. A listing that fails is no observation: it is counted and nothing is judged from it, because the API of a region with one control-plane node does not answer while that node restarts. From a listing that succeeds the check judges, in this order:
    - a node that is unschedulable in every listing for longer than drain timeout + lock release delay (20 minutes with the settings of the kit) fails the step: its drain does not finish, and it holds the reboot lock of the cluster;
    - two or more unschedulable nodes in one listing fail the step;
    - a chosen node whose `status.nodeInfo.bootID` differs from the value before, and that was never unschedulable in this or an earlier listing, fails the step: it restarted without a drain;
    - the step passes when each of the three nodes has a new boot identifier, no node is unschedulable and every node is Ready.
12. **The time limit ends the readings.** When the time since the Pods finished reaches the limit and the step has not passed, it fails with what the last listing showed.
13. **Availability is judged by the boot identifier and by `spec.unschedulable`,** never by the Ready condition: a node stays Ready through a reboot (`docs/ledger/plan/spikes/INF-030.md`). Ready is read only before the first reboot and for the end state.
14. **What the check never does.** It never restarts a node itself, never changes kured or its DaemonSet, and never patches an object. It writes with `kubectl create`, `wait` and `delete` only.
15. **The manifest.** The entry `INF-G01` of `docs/ledger/gates.yaml` moves from `state: not-built` to `state: expected-fail` and gains the line `implementation: tests/acceptance/sovereign/internal/suite/check_inf_g01.go`. No other field of the entry changes, and no other entry changes. The entry stays `destructive: true` and `runs_in: [cloud]`: the suite never selects the check in a run inside a Sovereign or on the local pack.
16. **Nothing is deleted** by this ticket.

// watch reads the nodes until the three chosen nodes have restarted and every
// node is schedulable and Ready, a rule is broken or the time limit ends.
func (c rebootCheck) watch(ctx context.Context, region kube.Region, k rebootSettings, chosen []string, before map[string]rebootNode, placed time.Time, ev Evidence) error {
	since, drained, oldIDs, newIDs := map[string]time.Time{}, map[string]bool{}, map[string]string{}, map[string]string{}
	for _, name := range chosen {
		oldIDs[name] = before[name].boot
	}
	readings, failed, most, last := 0, 0, 0, "no reading of the nodes succeeded"
	ev["boot_ids_before"], ev["boot_ids_after"] = oldIDs, newIDs
	for {
		nodes, err := c.nodes(ctx, region)
		now := c.now()
		if err != nil {
			failed++
		} else {
			readings++
		}
		ev["readings"], ev["failed_readings"], ev["seconds"] = readings, failed, int(now.Sub(placed).Seconds())
		if err == nil {
			down, notReady := []string{}, 0
			for name, node := range nodes {
				if !node.ready {
					notReady++
				}
				if !node.cordoned {
					delete(since, name)
					continue
				}
				down = append(down, name)
				if _, seen := since[name]; !seen {
					since[name] = now
				}
				if held := now.Sub(since[name]); held > k.drain+k.release {
					return fmt.Errorf("node %s has been unschedulable for %s, longer than drain timeout + lock release delay (%s): its drain does not finish", name, held, k.drain+k.release)
				}
			}
			sort.Strings(down)
			most = max(most, len(down))
			ev["most_unschedulable"] = most
			if len(down) > 1 {
				return fmt.Errorf("%d nodes are unschedulable at once: %s", len(down), strings.Join(down, ", "))
			}
			for _, name := range chosen {
				node := nodes[name]
				drained[name] = drained[name] || node.cordoned
				if node.boot == "" || node.boot == oldIDs[name] {
					continue
				}
				if !drained[name] {
					return fmt.Errorf("node %s has a new boot identifier and was never read unschedulable: it restarted without a drain", name)
				}
				newIDs[name] = node.boot
			}
			if len(newIDs) == len(chosen) && len(down) == 0 && notReady == 0 {
				return nil
			}
			last = fmt.Sprintf("%d of %d nodes restarted, %d unschedulable, %d not Ready", len(newIDs), len(chosen), len(down), notReady)
		}
		if now.Sub(placed) >= k.limit() {
			return fmt.Errorf("%s after the pending reboots were placed: %s", k.limit(), last)
		}
		if err := c.wait(ctx, rebootEvery); err != nil {
			return err
		}
	}
}

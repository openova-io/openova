# INF-054 — The node maintenance window is a setting of the sovereign-admin, at night in the Sovereign's own time zone by default

## In plain words

**The problem today.** Every Sovereign restarts its worker nodes for kernel updates at any hour from 00:30 to 22:00 UTC, which is the working day of most Sovereigns. On 20 November a drain at 04:33 local time moved the sign-in service and a sign-in failed during it. The window was made that wide only so that the acceptance check of node restarts would not have to wait for a night; the Sovereign's own time zone is known nowhere, and the keys that would set the hours are not even part of the variables contract.

**What changes.** The hours are a setting of the sovereign-admin in the Sovereign's variables document, by default 01:00 to 05:00 in the Sovereign's own time zone, which the installation request carries and the wizard proposes from the browser. The acceptance check no longer relies on a wide default: when the span is closed it opens a window for its own run through the same setting and restores it afterwards.

**Done means:**

- A new Sovereign's variables document holds SOVEREIGN_TIME_ZONE from the installation request (UTC when the request names none), and kured on it restarts nodes only between 01:00 and 05:00 in that zone unless the sovereign-admin changes KURED_START_TIME, KURED_END_TIME or KURED_TIME_ZONE.
- The variables contract lists the four keys as optional keys with their defaults and refuses a time that is not HH:MM and a zone that is not an IANA name; a request whose zone is not in the time zone database is refused.
- Step 1 of the wizard asks for the time zone of the Sovereign and proposes the browser's zone; the request carries the pick, else the proposal.
- The chart bp-kured and the fallbacks of kit slot 04b give the same night span, never the working day.
- Check INF-G01, when the span is not open for its run, writes a span for the run into the region's variables document, waits until kured runs with it, and afterwards writes the values before back, also when the run fails; its record names the document, the values before, the values written and the values restored.
- The worst-case node start-up data holds the four new keys and stays within every limit.

The rest of this ticket is the exact instruction for the model that does the work.

## 2. End goal
The hours in which kured may restart a node are a setting of the sovereign-admin: the keys `KURED_START_TIME`, `KURED_END_TIME` and `KURED_TIME_ZONE` of the Sovereign's variables document (ConfigMap `flux-system/sovereign-variables`, contract C5), now listed in the contract as optional keys and changed like every key of that document. Without them the span is the night 01:00 to 05:00 in the Sovereign's own time zone, the new optional key `SOVEREIGN_TIME_ZONE` (an IANA name, default UTC), which the parent writes from the installation request; step 1 of the wizard asks for it and proposes the browser's zone, and the API refuses a zone that is not in the time zone database. An empty `KURED_TIME_ZONE` is the Sovereign's zone. The chart `bp-kured` and the fallbacks of kit slot 04b give the same span. Check INF-G01 no longer depends on a wide product default: when the span is not open for its run it writes a span for the run into the region's variables document, waits until kured runs with it, and after the region's last step writes the values before back, also when a step failed; its record names both changes. The provider modules, their fixtures and the worst-case render of the node start-up data carry the four keys.

## 3. The model (the law)
1. **The change is the embedded patch.** The block `INF-054.patch` at the end of field 20, applied by work step 4, changes the 31 files and creates the 2 files of field 14 and nothing else; afterwards they have the checksums of work step 6.
2. **Four optional contract keys.** `docs/contracts/c5-upstream-variables.schema.json` and its byte-for-byte copy under `core/controllers/pkg/upstream/contract/` gain `SOVEREIGN_TIME_ZONE` (pattern of an IANA name, default `UTC`), `KURED_START_TIME` and `KURED_END_TIME` (pattern `HH:MM`, defaults `01:00` and `05:00`) and `KURED_TIME_ZONE` (empty or an IANA name, default empty: the Sovereign's zone). None is required. `upstream.Variables` gains one field per key (`TimeZone`, `KuredStartTime`, `KuredEndTime`, `KuredTimeZone`), so `ToMap` writes them and a document without them gets the defaults. `Served` gives a child the defaults, never the parent's values. No cross-field rule is added.
3. **Every reader of the full key set follows.** The three provider modules accept exactly the contract keys (`variables.tf`), so their lists, the two contract fixtures, the module tests, the fixtures of `scripts/cloudinit-size-check.sh` and `scripts/lint-cloudinit.sh`, `tests/fixtures/variables/today.env` and the two golden tfvars files gain the four keys. 4. **The worst case reads the contract's defaults.** `variables_doc` of `scripts/cloudinit-size-check.py` takes the default of every contract key that has one from the schema, as `upstream.Served` does, and names only the values the code fills otherwise, `SOVEREIGN_TIME_ZONE` among them with the longest name of the time zone database (`America/Argentina/ComodRivadavia`, 32 characters). That removes the 26 entries that repeated a default, so the file shrinks (5 lines added, 28 removed); the rendered start-up data is the same as before except the four new lines of the variables document.
5. **The parent writes the zone.** `provisioner.Request` gains `sovereignTimeZone`; `Validate` refuses a zone that `time.LoadLocation` does not know, and `Local`; the package embeds Go's copy of the time zone database (`time/tzdata`), because the API image has no zoneinfo files. `childVariables` writes the trimmed zone as `SOVEREIGN_TIME_ZONE`, leaves UTC when the request names none, and leaves the `KURED_*` keys at their defaults.
6. **The wizard asks.** The wizard state gains `sovereignTimeZone` (`''` until the operator picks one); step 1 shows a select `sovereignTimeZone` with UTC and the browser's IANA list, whose value is the pick or else the browser's zone (`browserTimeZone()`, UTC when the browser names none); the request of the review step carries the same value.
7. **The chart and the slot say the same.** `platform/kured/chart/values.yaml` sets `startTime: "01:00"`, `endTime: "05:00"`, `timeZone: UTC`. Slot 04b sets `${KURED_START_TIME:=01:00}`, `${KURED_END_TIME:=05:00}` and `${KURED_TIME_ZONE:=${SOVEREIGN_TIME_ZONE:=UTC}}` (an empty value takes the default, as in Flux). The chart test asserts both (its case 6).
8. **The check opens a window through the setting.** In step 4 of INF-G01, when the span is open for less than the time limit, the check reads `KURED_START_TIME` and `KURED_END_TIME` of `flux-system/sovereign-variables` of the region, writes the minute of now and that minute plus `rebootApply` (15 minutes) and the time limit plus one minute, both in kured's time zone, with one merge patch, and reads the DaemonSet of kured every 5 seconds until its arguments give that span and every Pod is updated and ready, at most `rebootApply`; past that the step fails and no node is touched. The evidence names the document, `values_before`, `values_set` and `applied_after`. After the region's last step, also when a step failed, the step `the reboot span of the variables document is restored` writes the values before back (a key the document did not have is removed with a null in the merge patch) and records `values_restored`. The wait for the span to open (`rebootMaxWait`, 150 minutes) is deleted. Every other rule of the check stays.
9. **What is deleted.** `rebootMaxWait` and its wait; the 26 default entries of `variables_doc`; the wide span 00:30 to 22:00 UTC from the chart, the slot, the chart test and the READMEs.

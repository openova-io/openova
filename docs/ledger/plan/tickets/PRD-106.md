# PRD-106 — CI workflow for the fingate module

## In plain words

**The problem today.** The open-banking product has a Go module whose tests run on pull requests, but nothing runs go vet on it, and nothing checks generated code. The next pieces of the product commit code that a generator writes from the standard's documents; a hand edit of that code, or a change of a document without the regenerated code, would go unnoticed.

**What changes.** The product gets a pull-request workflow of its own. It vets and tests the module, and it runs go generate and fails when that would change or add a file. Each check first proves on a throw-away module that it can fail.

**Done means:**

- A pull request that changes the open-banking product runs the product's own workflow, with two checks.
- A vet finding, a failing test or a module in which no test ran turns the first check red.
- A generated file that differs from what go generate writes, or one that go generate adds, turns the second check red.
- Each check proves on throw-away modules that it can fail before it judges the product, so a check that cannot go red is noticed.
- Every go test of the new workflow disables the test cache, as the repository's guard requires.

The rest of this ticket is the exact instruction for the model that does the work.

## 2. End goal
A pull request that changes anything under `products/fingate/`, or the workflow itself, runs the new workflow `.github/workflows/fingate-ci.yaml`. It has two jobs. The job `go vet and go test — products/fingate` runs `go vet ./...` and `go test -count=1 -v ./...` in `products/fingate` and fails on a vet finding, on a failed test, and when no test function ran. The job `go generate changes nothing — products/fingate` runs `go generate ./...` in every Go module under `products/fingate` and fails when a file under the folder changed or appeared. Before it judges the product, each job runs its own check on throw-away modules and stops red if a case that must fail passes, or if the clean case fails. The same workflow also runs on every push to `main` that changes the folder.

Self-test: a clean throw-away module passes; a module with a `fmt.Printf` format error (V1), a module whose test fails (V2) and a module without a test file (V3) each fail.
4. Job `generate`, named `go generate changes nothing — products/fingate`. Rule G1: no tracked file changed. Rule G2: no new file appeared. On a failure it prints the changed paths and the diff. Self-test: a throw-away repository whose module generates `out.txt` passes when `out.txt` is committed with the generated text, and fails when it is committed with other text (G1) or not committed (G2). The job prints how many `//go:generate` lines the folder holds; while it holds none, the check passes trivially.
5. Every `go test` line of the workflow carries `-count=1`, and no line of the workflow that starts with `if` contains the words `go test`: `scripts/check-go-test-count1.sh` reads such a line as a test run.
6. The workflow counts as a pull-request test of the module for `scripts/check-modules-tested.py`: its `on` block has `pull_request`, its jobs contain `go test`, and they name `products/fingate` standing alone.

# SVC-163 — The Blueprint files carry the seed's configSchema

## In plain words

**The problem today.** Every installed Sovereign holds a catalogue seed that is written by hand, and the seed is to be generated from the Blueprint files. The files already say what the seed says in every field except the configuration schema, the description of the settings a user may give an application: there 40 files disagree with the seed in 77 places, and the check that proves the equality leaves that field out. Generating the seed today would change the settings the install forms offer for those 40 Blueprints.

**What changes.** The 40 files carry the seed's configuration schema, absence included, and the equality check compares that field too: it leaves out no field that the platform reads, and its output names no exception. The seed itself does not change.

**Done means:**

- For every Blueprint the seed holds, its file says what the seed says in every field the platform reads, the configuration schema included.
- A file that carries a configuration schema the seed does not, or lacks one the seed carries, or differs from it in one setting, fails the equality check.
- The equality check prints one line, the number of seed objects equal to their files, and names no field it leaves out.
- The seed and the generated catalogue files are unchanged.
- No guard baseline rises: the provider-leak, access, service-model and upstream-literal guards pass.

The rest of this ticket is the exact instruction for the model that does the work.

## 3. The model (the law)
1. The hand-written seed is the truth for what an installation does. Where a Blueprint file and the seed disagree on `configSchema`, the file takes the seed's value, absence included: a file whose seed object has no `configSchema` loses its own, a file without one gains the seed's, a file that differs in part takes the seed's block. A value believed wrong in the seed is not corrected here; field 11 lists the ones found.
2. A text or value that a guard or a schema of the repository refuses would be corrected in the seed and in the file alike. Measured: none is refused (field 4 item 6), so the seed does not change.
3. The check compares every key of `spec` except the keys no reader reads from the object (`upgrades`, `owner`, `observability`, `outputs`, `dependsOn`), plus the label `catalyst.openova.io/companion`. The exemption of `configSchema` is removed with the output line that named it; nothing else of the check changes.
4. The self-test proves the new rule can fail: a `configSchema` that differs, one only the file has and one only the seed has are each one difference.
5. No other reader takes `configSchema` from a Blueprint file: the generator's outputs and `docs/generated/components.md` carry none, and no other script or workflow reads it (field 4 item 4). The install forms and the application controller read it from the Blueprint object, which the seed writes.
6. The baselines of the guards only fall: no line of `scripts/provider-leak-baseline.tsv`, of the access-guard baseline, of `scripts/service-model-baseline.yaml` or of the upstream-literals baseline rises.

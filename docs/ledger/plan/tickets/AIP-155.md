# AIP-155 — Agent workspace: the Organization's own sign-in by mount and a short-lived tool identity, as the spike record says

## In plain words

**The problem today.** The agent workspace of an Organization runs on a model sign-in copied from the Sovereign into a Secret, and on a tool bearer that lives for a year. A sign-in that several parties refresh is spent by the first of them, and the year-long bearer is a standing administrator key in every Organization.

**What changes.** A person signs in inside the workspace with the Organization's own plan, and the sign-in stays on the workspace's own volume. The tool server gets a short-lived token of the Organization from the platform and renews it without a restart.

**Done means:**

- The workspace chart renders no Secret and no ExternalSecret of a credential, and no container reads a model key or a long-lived tool bearer.
- A person signs in inside the workspace with the Organization's own plan, and a restart keeps the sign-in because it lives on the workspace's persistent volume.
- Only Claude Code refreshes that sign-in: the workspace daemon is pointed at a placeholder that it never refreshes.
- The tool server's bearer lives at most one hour and is renewed every third of its life, with no restart of anything.
- The agent acts for the Organization's owner, so it may install an Application while that person is an administrator or owner, and can only read otherwise.
- The model is offered the platform tools directly, without a search step.

The rest of this ticket is the exact instruction for the model that does the work.

## 2. End goal
The agent workspace (`products/agenity`, Blueprint `bp-agenity`) runs on the Organization's own sign-in and a tool identity of at most one hour, with the values of the lab test `docs/ledger/plan/spikes/AIP-250.md`. The home of Claude Code (`/home/chepherd/.claude` and `/home/chepherd/.claude.json`) lives on the workspace's persistent volume, the `state` claim, folder `claude-home`; a person signs in there with the Organization's plan, and the file Claude Code writes is the credential's only copy. The workspace daemon is pointed at a placeholder credential with no refresh token and a far expiry (`CHEPHERD_CLAUDE_CREDS_PATH`), so it never refreshes. The workspace runs as the ServiceAccount `agenity`, whose token is mounted only into two tool-identity containers: an init container makes one pass, a sidecar a pass every third of the bearer's life. A pass reads catalyst-api's public signer key set and asks `POST /api/v1/internal/agent-tokens` for an agent token of the release's Organization (agent `agenity`, tier `developer`, 3,600 seconds, acting for the Organization's owner when one is known), and writes each by rename into an in-memory folder that the workspace container mounts read-only. The tool server reads the bearer at every call (`OPENOVA_MCP_BEARER_FILE`, AIP-152) and gets the key set from its launcher. `ENABLE_TOOL_SEARCH=false` offers the platform tools up front. No Secret, no ExternalSecret of a credential, no seeding init container, no copy sidecar, no `ANTHROPIC_API_KEY` and no long-lived bearer remain. The README says that a sign-in counts when the agent answers.

## 3. The model (the law)
1. The chart renders no `Secret`, no `secretKeyRef` and no Secret volume; its only `ExternalSecret` is the sign-in gate's own Keycloak client secret, which renders only with a host (`templates/oidc-gate.yaml`, unchanged). The templates `externalsecret-anthropic.yaml` and `externalsecret-mcp-bearer.yaml` are deleted.
2. No container sets `OPENOVA_MCP_BEARER`, `ANTHROPIC_API_KEY` or `OPENOVA_MCP_RS256_PUBKEY_PEM`. No init container `seed-claude-creds` and no container `creds-resync` remain. The chart never writes, copies or reads `~/.claude/.credentials.json`.
3. The workspace container mounts `/home/chepherd/.claude` and `/home/chepherd/.claude.json` from the volume `state` (subPaths `claude-home/.claude` and `claude-home/.claude.json`); with `persistence.enabled` (the default) `state` is a volume claim template. The init container `workspace-home` writes the onboarding file only when it is absent or empty, and the daemon's lookup file `{"claudeAiOauth":{"accessToken":"daemon-lookup-placeholder","expiresAt":4102444800000}}` (no refresh token) into an emptyDir that the workspace container mounts read-only at `/var/chepherd/daemon-lookup`; `CHEPHERD_CLAUDE_CREDS_PATH` names it.
4. The Pod runs as `serviceAccountName: agenity` (value `toolIdentity.serviceAccount`) with `automountServiceAccountToken: false`; the chart renders that ServiceAccount, also with `automountServiceAccountToken: false` and no role. A projected token of it (`expirationSeconds: 3600`, the API server's own audience, which the TokenReview of catalyst-api expects) is mounted only into `tool-identity-init` and `tool-identity`.
5. The request body is `toJson` of `organization` (value `toolIdentity.organization`, else the release namespace, which is the Organization's slug), `agent` `agenity`, `tier` `developer`, `ttlSeconds` (value `toolIdentity.ttlSeconds`, 3600; a value outside 60 to 3600 fails the render) and, when there is one, `actingPerson`: the value `toolIdentity.actingPerson`, else the email of the first entry of `spec.owners` of the Organization object (`orgs.openova.io/v1`, named by the slug) with role `owner`, else with role `admin`, read with Helm `lookup` only when the cluster serves that kind; lower case. Who the agent acts for follows the shipped precedent: the one-year bearer that this replaces is minted for the Organization's owner (`products/catalyst/bootstrap/api/internal/handler/sovereign_mcp_bearer_seed.go` line 175), and the Organization object lists that owner with role `owner` (`org_tenant_org_cr.go` line 252). catalyst-api reads the role again at every issue (AIP-154).
6. A pass: `GET <api>/api/v1/auth/signers.jwks` into `signers.jwks`, then `POST <api>/api/v1/internal/agent-tokens` with `Authorization: Bearer <projected token>`; on 200 the field `token` goes to `bearer`. Each file is written to a hidden file of the same folder and renamed over the old one; a failed pass keeps the files it has. The bearer and the account token are never printed. `<api>` is `openovaMCP.catalystApiUrl`, else `https://console.<sovereignFqdn>`, the host the tool server already forwards to. The sidecar waits a third of the life after a pass and 30 seconds after a failed one; it exits on TERM.
7. The tool server's entry (in `CHEPHERD_EXTRA_MCP_JSON` and in the onboarding file) is `/bin/sh -c` with a launcher that exports the content of `signers.jwks` as `OPENOVA_MCP_RS256_PUBKEY_SET` when the file is not empty and then runs `openovaMCP.binaryPath`; its `env` holds only `OPENOVA_MCP_CATALYST_API_URL`, `OPENOVA_MCP_CONTEXT`, `OPENOVA_MCP_TENANT_HOST` (when known) and `OPENOVA_MCP_VERIFY`. The workspace container sets `OPENOVA_MCP_BEARER_FILE=/var/run/agenity-tools/bearer` and, with `agent.toolSearch: false` (the default), `ENABLE_TOOL_SEARCH=false`.
8. The egress policy keeps `toEntities: [world, cluster, host, remote-node]` on 443 and DNS on 53 UDP and TCP; its comment names `api.anthropic.com`, `platform.claude.com` and the console host, and says that only the person's browser reaches `claude.com`.
9. Every container has a liveness and a readiness probe (kyverno probes-present). The sidecar's probes cannot hide the dashboard: readiness asks only that its folder is writable. Its resources have requests equal to limits.
10. The one shell loop of the chart stays in `statefulset.yaml` (scripts/baselines/polling.json counts one there). The stored numbers of `scripts/check-agent-plane.py` are lowered to the measured counts, never raised; no new file matches its rules (the test writes the old bearer variable in two pieces).
11. No new Python: the proof is a shell chart test; the acceptance commands call existing tools only.

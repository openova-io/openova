# SOV-138 — No single Pod on the registry's pull path: Harbor's front, core and registry and the cluster DNS run two copies across nodes with a disruption budget

## In plain words

**The problem today.** After the sovereignty cutover every node pulls its images only from the Sovereign's own registry, and the registry's front, its core, its storage service and the cluster DNS each run as one Pod with no disruption budget. On a fresh install the reboot agent drained the one node that ran the front: its replacement could pull only through the front it was replacing, and most of the Pods moved off that node could not start again.

**What changes.** The front, the core, the storage service and the cluster DNS each run two copies on two nodes. A drain evicts one copy and waits while the other is not ready, so the drain of one node never removes the last copy.

**Done means:**

- A render of the registry chart with the object storage the kit uses gives the front, the core and the storage service two copies each, spread over nodes, and one disruption budget each that keeps one copy and selects only that component.
- A component set back to one copy gets no disruption budget, so a budget never blocks the drain of its node.
- The reboot chart renders, in the system namespace, an autoscaler that holds the cluster DNS at two copies and a disruption budget that keeps one copy.
- The guard that every disruption budget lets a drain finish passes on both charts and judges the new budgets.
- The registry chart's readme states the two copies, the budgets, the shared storage they need and what they cost.

The rest of this ticket is the exact instruction for the model that does the work.

## 2. End goal
After the sovereignty cutover a node pulls every image through its region's registry: the front `harbor-nginx`, the core `harbor-core` and the registry `harbor-registry` (with `registryctl`), and every one of them, and every caller, resolves names through the cluster DNS, the k3s CoreDNS. When this package is merged none of the four runs as a single Pod. bp-harbor runs the front, the core and the registry with two copies each, at most one more on any node than on another, and renders a PodDisruptionBudget of `minAvailable: 1` for each; bp-kured, the chart that drains the nodes, renders in `kube-system` a HorizontalPodAutoscaler that holds `Deployment/coredns` at two copies and a PodDisruptionBudget of `minAvailable: 1` on its Pods. A drain of any one node then evicts one copy of each and waits while the other copy is not Ready, so it never removes the last copy. A person sees this on the pull request: `chart/tests/pull-path-availability.sh` of bp-harbor and `chart/tests/coredns-availability.sh` of bp-kured pass, `Chart tests (PR)` of both charts and `check-budgets-allow-drain` are green, and the acceptance commands pass.

## 3. The model (the law)
1. The pull path of a region after the cutover is the front, the core, the registry and CoreDNS. None of them runs as a single Pod where two copies can run.
2. `harbor.nginx`, `harbor.core` and `harbor.registry` of `platform/harbor/chart/values.yaml` set `replicas: 2` and one `topologySpreadConstraints` entry: `maxSkew: 1`, `topologyKey: kubernetes.io/hostname`, `nodeTaintsPolicy: Honor`, `whenUnsatisfiable: DoNotSchedule`. The upstream chart adds each component's own `labelSelector`. `nodeTaintsPolicy: Honor` leaves out a node the Pod cannot run on, the cordoned node of a drain among them, so a region of two schedulable nodes still places the replacement.
3. `platform/harbor/chart/templates/pull-path-disruption-budgets.yaml` renders, for each of the three, one `policy/v1` PodDisruptionBudget named like its Deployment (the upstream `harbor.fullname` plus the component), in the release namespace, with `minAvailable: 1`, `unhealthyPodEvictionPolicy: AlwaysAllow` and the selector the upstream Deployment uses: `release`, `app` and `component`. It selects the Pods of its own Deployment and of no other.
4. A component gets its budget only at two or more copies: at one copy a budget of `minAvailable: 1` refuses every eviction and no drain of its node can finish (`scripts/check-budgets-allow-drain.py`, #7922). The front gets its budget only when the upstream chart renders the front (`expose.type` is neither `ingress` nor `route`).
5. Two registry copies share only the object store. Slot 19 sets `persistence.imageChartStorage.type: s3`, and with it the registry mounts no volume claim. A render that keeps `type: filesystem` on a ReadWriteOnce claim sets `harbor.registry.replicas: 1`; `values.yaml` and the README say so.
6. `platform/kured/chart/templates/coredns-availability.yaml` renders an `autoscaling/v2` HorizontalPodAutoscaler `kube-system/coredns` on the `apps/v1` Deployment `coredns` with `minReplicas: 2` and `maxReplicas: 2`, and a `policy/v1` PodDisruptionBudget `kube-system/coredns` with `minAvailable: 1`, `unhealthyPodEvictionPolicy: AlwaysAllow` and the selector `k8s-app: kube-dns` and nothing else. Both are in `kube-system` whatever the release namespace. The autoscaler raises a target below `minReplicas` before it reads any metric; the k3s manifest sets no replica count, so k3s never sets it back. No value is added to bp-kured's `values.yaml`.
7. Kept single: Harbor's redis (one StatefulSet with a ReadWriteOnce volume in the primary region, reached by the other region over the mesh, #5406; two unreplicated copies would split the sessions), `harbor-jobservice` and `harbor-portal` (not on the pull path). `updateStrategy: Recreate` stays. No kit slot, `Chart.yaml`, `blueprint.yaml` or version pin changes. No NodePort.

# CLD-132 — Remaining provider tests become injected inputs

## In plain words

**The problem today.** The shared boot template of the control plane still decides twenty of its steps by testing whether the provider is Hetzner or Huawei. A new cloud cannot use the template without editing it, and the user-data limit of the reference cloud is written twice, in its profile and in a file of the size check.

**What changes.** Each module now tells the template, with four plain inputs, which of those steps its cloud needs; the template no longer tests the provider name except in one path line that a later task removes. The size check takes the cloud limit from the pack profile, and a test proves that each module's gateway input agrees with its profile.

**Done means:**

- The shared boot template tests the provider name in one line only, the sovereign-tls path.
- The seven failure steps that chose their marker command by the provider name record their marker through the input fail_mark_cmd, and every pack ends its boot with the same final mark.
- The two failure steps of the kubeconfig post-back are not changed: they call the helper where a pack has one and write a plain marker file where it has none.
- The provider-pack test runs its template-inputs check for all three packs and fails when a module's gateway input disagrees with its profile.
- The Huawei user-data limit stands only in its profile, and the size check fails a worst-case file that writes the cloud limit itself.
- Every control-plane user data stays within its limit, and the pull request states the measured size of each surface before and after.
- The golden render changes once, and the local pack's Cilium values gain the gateway host-network block.

The rest of this ticket is the exact instruction for the model that does the work.

## 2. End goal
After this change the shared boot template `infra/providers/_shared/cloudinit-control-plane.tftpl` has exactly one line that tests the provider name: the `path:` line of the Kustomization `sovereign-tls` (package CLD-144 removes it). Every other such test is replaced by one of four template inputs that each module passes as a literal: `node_ipv4_only`, `fail_mark_cmd`, `render_region_kustomization` and `gateway_host_network`. Every module also passes `provider_overlay_path`, which the template does not read yet. The failure-mark helper `/var/lib/catalyst/mark` is written by the Huawei module's `provider_prelude` instead of by the template. The three arguments that the template no longer reads (`pdns_api_host`, `node_external_ip_value`, `clustermesh_proxy_port`) leave every call. `scripts/cloudinit-size-check.py` passes the limit of each pack's `profile.yaml` to that pack's `user_data_worst_case.py`, which no longer names the cloud limit itself. A person sees it on the pull request: `grep -cE 'provider *(==|!=) *"'` on the template prints `1`, the template-inputs sub-test of `TestProviderPacks` runs for the three packs, the checks `golden` and `packs` are green, and the pull-request body states the size of each control-plane surface before and after.

## 3. The model (the law)
1. The template tests the provider name in one place only: `path: ./clusters/_template/sovereign-tls%{ if provider == "hetzner" }-hetzner%{ endif }`. The argument `provider` stays in every call, because that line and the header comment `# Provider:  ${provider}` read it.
2. The other 20 tests become inputs, each exactly as listed:
   - `node_ipv4_only` (bool) gates the seven blocks that only an IPv4-only network needs: the sysctl file `/etc/sysctl.d/99-catalyst-disable-ipv6.conf`, the `sysctl -w` item that switches IPv6 off, the creation of the side-file `/var/lib/catalyst/github-ipv4-hosts`, the two extra pin hosts `api.github.com registry.${sovereign_fqdn}`, the append to the side-file, the CoreDNS step `coredns-custom`, and the background pre-pull of the Flux images. One more test only wrapped a comment block (the note `#4503 root cause`): its two directive lines are deleted, and its first line loses the words `(Huawei-gated note; the byte budget is Hetzner-only)`. The rest of the comment stays.
   - `fail_mark_cmd` (string) is a command prefix; the template appends the marker name. Each of the seven failure sites that tested the provider name writes `${fail_mark_cmd}<name>||true`: `k3s-install-FAILED`, `apiserver-healthz-FAILED`, `gwapi-apply-FAILED`, `cilium-bootstrap-FAILED` (followed by `;exit 91;}`), `flux-install-FAILED`, `flux-wait-FAILED` and `flux-bootstrap-FAILED`. The block that ran the helper once at the end on Huawei becomes the runcmd item `  - ${fail_mark_cmd}cloud-init-complete||true` for every pack; the plain item `  - touch /var/lib/catalyst/cloud-init-complete` before it stays. So the template has `${fail_mark_cmd}` in exactly 8 lines. The published meaning of `fail_mark_cmd` in `infra/providers/PROVIDER-INTERFACE.md` does not change.
   - The two failure sites of the kubeconfig post-back do not change. They are the runcmd items that end in `exit 98; }` (marker `parent-bootstrap-FAILED`) and `exit 97; }` (marker `handover-peer-FAILED`). They test no provider name. Each reads `sh /var/lib/catalyst/mark $N-FAILED || touch /var/lib/catalyst/$N-FAILED`: it calls the helper where the pack's prelude wrote one and writes a plain marker file where no helper exists. After this change these two lines are the only lines of the template that hold the text `/var/lib/catalyst/mark`.
   - `render_region_kustomization` (bool) gates the two keys `SOVEREIGN_REGION_ID` and `SOVEREIGN_WRITER_REGION_ID` of the variables ConfigMap and the Kustomization `sovereign-region-bootstrap`. It is false only where the user-data limit forbids the block.
   - `gateway_host_network` (bool) gates the `hostNetwork: enabled: true` block of the Cilium gateway values.
   - `provider_overlay_path` (string) is `./clusters/_template/providers/<pack>`. No line of the template reads it in this change; CLD-144 reads it.
3. The values, each a literal in every call of the module:

   | module | `node_ipv4_only` | `fail_mark_cmd` | `render_region_kustomization` | `gateway_host_network` | `provider_overlay_path` |
   |---|---|---|---|---|---|
   | hetzner (both calls) | `false` | `"touch /var/lib/catalyst/"` | `false` | `false` | `"./clusters/_template/providers/hetzner"` |
   | huawei | `true` | `"sh /var/lib/catalyst/mark "` | `true` | `true` | `"./clusters/_template/providers/huawei"` |
   | local | `false` | `"touch /var/lib/catalyst/"` | `true` | `true` | `"./clusters/_template/providers/local"` |

   The render harness `render.tf` and the fixtures of `scripts/lint-cloudinit.sh` and `scripts/cloudinit-size-check.sh` pass the values of the pack of each fixture.
4. `gateway_host_network` equals `spec.network.loadBalancer.mode == "external-hostport"` of the pack's `profile.yaml`. No module reads `profile.yaml`: the provisioner stages only the `*.tf` and `*.tftpl` files of a module. `TestProviderPacks` checks the equality (rule 15 of `scripts/check-provider-contract.sh`), and its template-inputs sub-test runs (rule 14): the line `t.Skip("until CLD-132")` is deleted.
5. The helper `/var/lib/catalyst/mark` is written by a new runcmd item at the end of `local.provider_prelude_huawei` in `infra/providers/huawei/main.tf`, with mode 0700. Its text is what the template wrote before: `touch "/var/lib/catalyst/$1"`, `echo "CLOUDINIT-SENTINEL: $1"`, and, only when the deployment id, the bearer token and the API address are all set, a pause of one second and the `curl -4` push of `/var/log/cloud-init-output.log` with `?node=$(hostname)`. The template's write_files entry of the helper is deleted.
6. The arguments `pdns_api_host`, `node_external_ip_value` and `clustermesh_proxy_port` leave every call of the shared template: the three modules, `render.tf` and the two shell fixtures. The Huawei substitutes file still reads them; its own `templatefile()` call passes them.
7. The user-data limit of a cloud stands only in its pack's `profile.yaml` (`spec.bootstrap.userDataLimitBytes`). `scripts/cloudinit-size-check.py` reads it and calls `worst_case(c, limit)`. `infra/providers/huawei/user_data_worst_case.py` loses `LIMIT = 32768` and measures its four surfaces against `limit`. The Hetzner file keeps its three module limits (32,576, 32,256 and 30,720); they are preconditions of its `main.tf`, not the cloud limit. Rule 3 of `check_profiles` fails a worst-case file that has an upper-case integer constant equal to the profile's limit. The loop over the packs, the per-provider fixtures and the `hetzner|huawei|both` dispatch of the two shell scripts stay.
8. The render changes once. Both golden render hashes change. The Hetzner fixture changes only at the seven failure sites and by the new final line (89 bytes more). The Huawei fixture loses only the helper's write_files entry, because the harness passes an empty prelude. Every file hash of the golden file stays, except that `/var/lib/catalyst/mark` leaves the Huawei map. The local render gains the `hostNetwork` block.
9. The kubeconfig-capture check `scripts/check-cloudinit-primary-kubeconfig-capture.sh` looks for the per-node push of the helper in the Huawei module, where it now is, and no longer reads the template.
10. No other behaviour changes: no exit code, no package and no other file a node writes. One file changes its content: on Hetzner and local the marker `/var/lib/catalyst/cilium-bootstrap-FAILED` becomes an empty file. It held the text `no-cni`, which nothing reads. On Hetzner and local the new final item touches `/var/lib/catalyst/cloud-init-complete` a second time, which changes nothing.
11. The comments follow the code. The header comment of the template lists the inputs of CLD-131 and of this ticket and no longer speaks of blocks gated by the provider. The comment of the final mark says what it does for every pack. In each call a comment says what the new inputs mean. The comments of the three placeholders leave the Hetzner calls and the two shell fixtures together with the placeholders. In the Huawei call, three comment lines above the substitutes call say what `clustermesh_proxy_port` and `pdns_api_host` are for. A comment above `provider_prelude_huawei` describes the helper. The script of step 3 writes all of them; you write no comment yourself.

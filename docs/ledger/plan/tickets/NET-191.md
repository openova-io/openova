# NET-191 — Organization listeners admit only their Organization

## In plain words

**The problem today.** Each Organization gets its own pair of listeners on the console Gateway of a Sovereign, for the host names under its own domain. Both listeners accept web routes from every namespace of the cluster, so a route written in another Organization's namespace can attach to this Organization's host names and take its traffic. Two components write the pair, and both write the open admission.

**What changes.** Both listeners accept routes only from the Organization's own namespace and from the platform namespace that holds its console route. Both writers take that rule from one shared place, and a pair already on a running Sovereign is corrected in place.

**Done means:**

- No listener of an Organization's pair on the console Gateway admits routes from all namespaces.
- A route in another Organization's namespace attaches to no listener of the pair.
- The Organization's own routes and its console route still attach to the pair.
- A pair written before this change is corrected in place on the next reconcile, and a corrected pair is not written again.
- Both components that write the pair write the same admission.
- The network guard holds no counted entry for the two files that admitted all namespaces.

The rest of this ticket is the exact instruction for the model that does the work.

## 2. End goal
Every Organization has a listener pair on the console Gateway `kube-system/cilium-gateway-console`: `console-https-<slug>` and `console-http-<slug>` for `*.<slug>.<parent>`. Two components write it: the organization controller (`ensureConsoleOrgListener` in `core/controllers/organization/internal/controller/tenant_console_tls.go`) and the catalyst-api (`ensureOrgConsoleListener` in `products/catalyst/bootstrap/api/internal/handler/org_console_tls.go`). After this ticket both write, on both listeners, an `allowedRoutes` that admits HTTPRoutes only from two namespaces, selected by the label `kubernetes.io/metadata.name`: the Organization's namespace (its slug) and the namespace of its console route (`catalyst-system` by default). Both take that value from one new package, `core/controllers/pkg/orglistener`, so they never rewrite each other's listener. A live pair that still admits every namespace is drift: the controller's existing comparison reports it changed and rewrites it in place. Network guard G4 then counts no code site, and its two baseline lines are removed.

## 3. The model (the law)
1. Both listeners of an Organization's pair carry exactly this block, with these two values in this order:
   ```yaml
   allowedRoutes:
     namespaces:
       from: Selector
       selector:
         matchExpressions:
           - key: kubernetes.io/metadata.name
             operator: In
             values: [<slug>, <console route namespace>]
   ```
   Kubernetes sets the label `kubernetes.io/metadata.name` on every namespace to its name.
2. The first value is `names.Slug`, the label of the pair. Every path that creates an Organization leaves `tenantPublic.subdomain` unset or sets it to `spec.slug`, so it is the Organization's namespace. The Organization's Applications place their routes there (the per-Org HelmReleases install into `targetNamespace: <slug>`; a route synced out of its vCluster lands in the host namespace `<slug>`).
3. The second value is the namespace of the route of `console.<slug>.<parent>`: `r.consoleRouteNamespace()` in the controller, `catalystConsoleNamespace` (`catalyst-system`) in the catalyst-api.
4. `orglistener.AllowedRoutes(orgNamespace, consoleRouteNamespace)` returns this block as a fresh `map[string]any` on every call. It is the only place that writes it; the four sites call it.
5. The order of the values is fixed: the controller compares a live listener with the desired one by value, so a pair already in this form is not written again.
6. Deleted: the four literals `{"from": "All"}` of the two files, and the two G4 lines of `scripts/network-guards-baseline.tsv` that allowed them.

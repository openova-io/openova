# FND-046 — A chart version the release writer publishes is packaged from the chart main holds at that version

## In plain words

**The problem today.** A release job publishes a chart from the commit it checked out. When another change reaches main during the job, the job's retry writes the same version number onto the newer main, even when that main changed the chart. Main then names a version whose published files it does not hold, and an install of that version gets other files than main shows.

**What changes.** On such a retry the release packages the newer main and compares it with what it published. The same files: it writes the version as before. Other files: it writes nothing and starts a release of main, which takes the next version the registry does not already hold.

**Done means:**

- A release whose retry finds that main changed a template of the chart, or a library the chart packs, after its checkout leaves main's version unchanged and starts exactly one release of main for that chart.
- A release whose retry finds that main changed only a file the package leaves out writes the version as before.
- The version that the release writer writes skips every version the registry already holds.
- The commit step of the release pushes no chart to the registry.
- The guard's own tests put each old behaviour back and each gets a finding, so the check can fail.

The rest of this ticket is the exact instruction for the model that does the work.

## 2. End goal
A chart version that `main` names is the content the registry serves under it. The job of `.github/workflows/blueprint-release.yaml` still publishes its chart from the commit it checked out. When the first push of its lockstep commit is refused because `main` moved, the retry looks at what moved: when a file that the chart's package holds changed on the fresh `main` outside the release-owned lines, the step packages that `main` under the job's version and compares it with the package the job published. The same files: it writes every site, as today. Other files: it writes no site, says so in the log, as a warning and in the job summary, and the next step dispatches one release of `main` for the chart; that release's version skips every version the registry already holds. A person sees it in the output of the check `lockstep` of `tools/guards/cmd/release-own-tree`, which runs the real steps of the workflow on fixtures.

## 3. The model (the law)
1. **Where the mismatch arises.** The first attempt of the step "Commit + push bootstrap-kit pin bump + blueprint.yaml lockstep" (id `lockstep_push`) commits on the job's checkout, and its push is fast-forward only: when it lands, `main` holds the checkout. Only a retry, after `git reset --hard origin/main`, writes the version onto a commit the job did not package. The first attempt is unchanged.
2. **What the retry compares.** The step records the checkout (`checkout="$(git rev-parse HEAD)"`). `packaged_paths <rev>` names the chart folder `<CHART_PATH>/chart` and the folder of each `file://` dependency its `Chart.yaml` names at `<rev>`. `owned_out <rev> <file>` prints the file without the release-owned lines R1 to R3 of `scripts/check-release-owned-lines.py`: this chart's top-level `version:`, the `appVersion:` of `products/catalyst/chart/Chart.yaml`, and the first `  version:` of a `products/<x>/chart/blueprint.yaml`. `compare_main` runs on every retry that has staged sites, before the commit: when no file of the packaged paths (of the checkout and of `origin/main`) differs outside those lines, it does nothing more. Otherwise it adds a temporary worktree of `origin/main`, writes `CHART_VERSION` into its `Chart.yaml`, runs `add_dep_repos` of `scripts/lib/helm-dep-repos.sh`, `helm dependency build` and `helm package`, and compares that package with the one the job published (`${CHARTS_DIR:-/tmp/charts}/<name>-<version>.tgz`) by `scripts/chart-package-diff.py`, as the release writer compares.
3. **What the retry writes.** The comparison exits 0: the step prints `main packages to the files of the published <name> <version>: its sites are written` and writes every site as before. It exits 1: the step commits nothing, writes `redispatch=true` to its outputs, a warning `Lockstep not written: <name> <version>` and a summary section that names the checkout, and exits 0. Any other exit fails the step with the reason in `LOST_WHY`; the existing trap names the chart and the release to start.
4. **The step never pushes a chart.** The commit step holds no `helm push`; a version the job published stays in the registry when main does not name it.
5. **The release of main.** The new step "Release writer: release main again when main changed the chart" (id `dispatch_release`) follows the commit step, runs only when `steps.lockstep_push.outputs.redispatch == 'true'` (and the chart is not skipped), and runs once `gh workflow run blueprint-release.yaml --repo <repo> --ref main -f blueprint=<name> -f tree=<tree>`, with `<tree>/<name>` the chart path. The workflow's `actions: write` permission already exists (FND-027); its comment names the new step.
6. **The bump skips held versions.** In the step "Release writer: bump the chart version", after `next` is computed and before it is written, `held_version <name> <version> <dir>` pulls `oci://ghcr.io/openova-io/<name>` at that version: pulled means held and `next` moves one patch up; an answer with `not found` means free; any other answer prints the log, an error that names the chart and version, and ends the step (nothing is published). So the release of main does not meet the no-republish floor on the version the job left in the registry.
7. **The bound.** There is no fixed run count. A dispatched release dispatches again only when its own retry finds that `main` changed the chart's packaged files to other content during that run, so each re-dispatch needs a new change to the chart during a run; and the job's concurrency group (`blueprint-release-<event>-<path>`, `cancel-in-progress: false`) keeps one pending run per group, so dispatches made while a run is pending merge into one. The releases end with the first run during which `main` does not change the chart's packaged files.
8. **The guard.** `tools/guards/cmd/release-own-tree` gains the check `lockstep` (in its default list, so the existing step of `tree-guards.yaml` runs it): the release writer on a registry stand-in that holds `bp-fx` 1.0.0 with other files writes 1.0.1, and with 1.0.1 held too writes 1.0.2; the commit step after `main` moved writes no site, keeps 1.0.0 on main and the next step calls `gh` exactly once with the dispatch above when main changed a template or the `file://` library; it writes 1.0.1 on the moved main when main changed only a file the package leaves out (`.helmignore`). The check `workflow` counts the `helm dependency build` of the commit step as one of the builds that must follow `add_dep_repos`. Three tests put each old behaviour back and assert the finding.
9. **No version line, no new Python.** No `Chart.yaml` version line changes. The step calls the existing `scripts/chart-package-diff.py`; no Python line is added.

# NET-280 Lab test: the overlay profile (result)

Date: 2026-11-19, one session, on origin/main 9ef70b131a. Type: lab test on the `local` provider pack through CI, two regions with two nodes each. Outcome: **NODE-OVERLAY**.

- Under the profile's network rule (the node addresses of the two regions reach each other on one UDP port, 51871, and on nothing else), only a node overlay forms the mesh. Cilium tunnel mode with WireGuard, and the platform's own data path (native routing with Cilium WireGuard), never connect it: 0 of 1 remote clusters ready after 600 s, in every run. The mesh needs TCP 12379 to the remote node address before WireGuard has a peer in the other region.
- The node overlay is a host WireGuard device `wg0` on UDP 51871 on every node. The other region's pod and node ranges are routed into it, and Cilium runs native routing with its own encryption off, pod MTU 1400 and `wg0` named as a device. In that form the connectivity test gave exactly the baseline's result (the same 20 failed actions, all harness classes). The three cases of NET-120 matched the baseline in the form with overlay addresses; in the final form a harness defect stopped them after the pause of case A.
- With TCP 12379 added to the rule, tunnel mode also matches the baseline. The platform's own data path does not: case A of NET-120 failed in 3 of 3 runs, and host to remote pod fails.
- The pass rule as written cannot be met on this harness by any data path, the baseline included. Section 4 lists the classes that fail everywhere.
- During a 5-minute partition, the remote backend stays in a global Service on every data path. 38 to 61 % of the dials failed.

## Question

Two clusters whose nodes reach each other only on one UDP port. Can they form a Cilium ClusterMesh that carries pod traffic and global Services, and which data path does it?

- Test (a): Cilium tunnel mode with WireGuard and an MTU that Cilium computes.
- Test (b): a node overlay with Cilium native routing, and Cilium encryption off between the clusters.

Pass rule: the Cilium connectivity test and the three cases of NET-120. Outcomes: `TUNNEL`, `NODE-OVERLAY` (that data path becomes the `overlay` profile) or `NONE` (a multi-region Sovereign needs a provider with a private link).

### The profile rule

The lab script applies it after `local-pack.sh up`:

1. Each machine's `eth0` gets its region's /24 instead of the bridge's /16, with the default route via the bridge gateway (`onlink`). The two regions become two routed subnets, with the runner as the router between them. ICMP redirects are off on both sides. `br_netfilter` is on, so bridged frames pass the same filter.
2. Cilium's direct routes into the other region are deleted (8 routes in every run).
3. The runner's `DOCKER-USER` chain drops everything between `172.30.1.0/24, 10.42.0.0/16` and `172.30.2.0/24, 10.43.0.0/16`, except UDP to port 51871 between the two node ranges.
4. Variant "+TCP": stateless ACCEPT rules for TCP to and from port 12379 between the node ranges, above the DROP.

### 7. Facts found on the way

- With `encryption.enabled: false` and a restart of the agents, Cilium 1.19.3 removed its own `cilium_wg0` on every node (4 of 4 nodes, in 5 runs), so the overlay could bind UDP 51871.
- Cilium takes `wg0` as a device by itself only when `wg0` has an address. Named in `devices`, it is taken without one.
- The pack's `local-pack.sh up` connects the mesh without `kvstoremesh`; `mesh-test.sh` turns it on.

## Answer

- `TUNNEL` cannot meet the profile's network rule. The mesh is a TCP connection from each cluster to the other's endpoint, and Cilium learns the WireGuard peers of the other cluster from the mesh. With one UDP port the mesh never forms. The same holds for the platform's own data path.
- With one more rule, TCP 12379 between the node ranges, tunnel mode forms the mesh and matches the baseline on the connectivity test and on the cases. The platform's own data path does not.
- `NODE-OVERLAY` meets the rule. In form b3 it matches the baseline on the connectivity test exactly. On the cases of NET-120 it matched the baseline in forms b1 and b2, and in b3 up to the harness defect after the pause of case A.
- The outcome word is **NODE-OVERLAY**. The `overlay` profile is the node overlay of form b3.

## What follows for the plan

The build package of the `overlay` profile (none exists in the plan yet):

1. On every node, a host WireGuard device on the profile's one UDP port, with no address of its own. Its peers are all nodes of the other regions; a peer's allowed IPs are its node address /32 and its `podCIDR`.

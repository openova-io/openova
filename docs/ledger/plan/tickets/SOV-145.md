# SOV-145 — Two node files that nothing reads leave first boot

## In plain words

**The problem today.** The first-boot user data of a Sovereign control plane is close to the 32 KiB that the clouds accept. It still writes two files on the node that no program reads: a summary of the installation and a second copy of the hand-over public key, whose real copy reaches the platform API as a Kubernetes Secret. Together they cost about 1,300 bytes of the limit.

**What changes.** First boot no longer writes the two files. The Secret with the hand-over key stays as it is, and the stored render values and the render self-test follow the change.

**Done means:**

- The shared first-boot template writes neither /var/lib/catalyst/sovereign.json nor /var/lib/catalyst/handover-jwt-public.jwk.
- The Secret catalyst-handover-jwt-public is still written and applied at first boot, so the platform API on a new Sovereign still verifies hand-over tokens.
- The stored golden render values match the changed render, and the golden self-test still proves that a wrong stored file hash fails the run.
- Every worst-case control-plane surface is 1,313 bytes smaller on Huawei and 1,318 bytes smaller on Hetzner than before the change.
- No file outside docs names sovereign.json.

The rest of this ticket is the exact instruction for the model that does the work.

## 2. End goal
The shared first-boot template of every Sovereign control plane, `infra/providers/_shared/cloudinit-control-plane.tftpl`, no longer writes the two node files `/var/lib/catalyst/sovereign.json` and `/var/lib/catalyst/handover-jwt-public.jwk`. No program reads either file. The hand-over public key keeps reaching the platform API through the Secret `catalyst-system/catalyst-handover-jwt-public`, which first boot still writes and applies. The stored golden values of the render test match the changed render, and the self-test of `scripts/update-cloudinit-golden.sh` uses a file that still exists for its "wrong stored file hash" case. The worst-case control-plane user data, as the check `cloud-init-size` measures it, is 1,313 bytes smaller on each Huawei control-plane surface and 1,318 bytes smaller on each Hetzner one. Nothing is packed and no limit moves.

## 3. The model (the law)
1. First boot writes only what a node needs before Flux and OpenBao exist. The two files are written and never read, so they go. This ticket adds no byte to the user data.
2. The `write_files` entry of `/var/lib/catalyst/sovereign.json` is deleted whole: its four lines and its ten content lines, and the empty line after it.
3. The `write_files` entry of `/var/lib/catalyst/handover-jwt-public.jwk` is deleted whole: its four lines and the empty line after it. Its comment line is reworded to describe the Secret entry that follows it.
4. The Secret entry `/var/lib/catalyst/handover-jwt-public-secret.yaml` stays byte for byte, with its line `public.jwk: ${base64encode(handover_jwt_public_key)}`, and the `runcmd` item that applies it with `-f handover-jwt-public-secret.yaml` stays byte for byte.
5. One comment in the template, one comment in `scripts/cloudinit-size-check.py` and one self-test case in `scripts/update-cloudinit-golden.sh` name `sovereign.json`. The comments are reworded. The self-test case uses `/etc/rancher/k3s/registries.yaml` instead, a file that every fixture writes and that first boot keeps. After the change no file outside `docs/` names `sovereign.json`.
6. `infra/providers/_shared/tests/golden.auto.tfvars.json` becomes the exact file embedded in this ticket: the two render hashes of the changed render, and the file hashes of each fixture without the two deleted files (14 for the Hetzner fixture, 16 for the Huawei fixture).
7. No entry is packed (`encoding: gz+b64`) and no limit is raised.
8. The template variables `org_name`, `org_email`, `k3s_version`, `gitops_repo_url`, `gitops_branch`, `deployment_id` and `handover_jwt_public_key` stay: other lines of the template still read each of them. The provider modules pass them on unchanged.

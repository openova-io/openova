# SEC-040 — Bootstrap secret hygiene on the node and reflector scope

## In plain words

**The problem today.** When a new Sovereign boots, its first control-plane node keeps every bootstrap secret in plain files on disk after they have been loaded into the cluster, and its administrator kubeconfig is readable by every local user. The Harbor robot token is copied into every namespace of the cluster, although only the platform API needs it. A check that proves the opposite exists, but it is only expected to fail.

**What changes.** The boot script deletes the secret files with shred once they are loaded, writes the administrator kubeconfig and the Flux bootstrap file readable by root only, copies the robot token into the platform API's namespace only, and leaves the OpenBao recovery seed to the OpenBao chart. The render test fails when any of this is undone, and the node-hygiene gate check becomes required.

**Done means:**

- The k3s server line of the shared boot template writes the administrator kubeconfig with mode 0600, and the Flux bootstrap file is written with mode 0600.
- After the bootstrap Secrets have been applied without error, the boot script removes their seven files with shred, and after the Flux bootstrap file has been applied it removes that file the same way.
- The Harbor robot token Secret is reflected into the namespace catalyst-system and into no other namespace.
- The boot script no longer creates the Secret openbao-recovery-seed; the OpenBao chart creates it.
- The render test of the boot template fails for either cloud when any of these four changes is undone, and the stored golden render values match the changed template.
- Gate check SEC-G02, which reads the token, the kubeconfig mode and the bootstrap files on every control-plane node, is required.

The rest of this ticket is the exact instruction for the model that does the work.

## 2. End goal
A new Sovereign leaves no bootstrap secret in a file on its control-plane nodes and copies the Harbor robot token only where it is used. The shared boot template `infra/providers/_shared/cloudinit-control-plane.tftpl` starts the k3s server with `--write-kubeconfig-mode=0600`, so `/etc/rancher/k3s/k3s.yaml` is readable by root only. It writes `/var/lib/catalyst/flux-bootstrap.yaml` with mode `0600`. When the one `kubectl apply` of the seven bootstrap Secret files succeeds, the same line removes the seven files with `shred -u`; when the apply of `flux-bootstrap.yaml` succeeds, the next line removes that file with `shred -u`. The Secret `flux-system/harbor-robot-token` is reflected into `catalyst-system`, where the platform API reads it, and into no other namespace. The runcmd item that created the Secret `openbao-recovery-seed` is deleted: the bp-openbao chart creates that Secret itself when it is absent. The render test of the template fails for the hetzner and the huawei fixture when any of this is undone, and the stored golden render values match the changed template. Gate check SEC-G02 (on every control-plane node the k3s token is not of the derived form, the kubeconfig has mode 600, and no bootstrap file remains) moves from `expected-fail` to `required`. `docs/SECURITY.md` and `infra/providers/hetzner/README.md` say what is now true.

# CLD-116 — The wipe removes first what its own destroy cannot remove on the reference cloud, and says so

## In plain words

**The problem today.** The wipe of an environment runs the OpenTofu destroy first, and on the reference cloud that destroy never finishes: the object store refuses the destroy's batch delete of the bucket's objects, the load balancers refuse the deletion of their listeners, and a NAT gateway keeps a rule that was made outside the destroy's state. The purge that follows removes everything, so nothing is left behind, but every wipe report says that the destroy did not finish.

**What changes.** Before the destroy, the wipe removes those three kinds of object itself, one at a time, with the calls the purge already uses on that cloud, and the wipe report names what each step removed. The destroy then finds them gone and removes the rest.

**Done means:**

- When the destroy starts, the deployment's bucket, every listener of its load balancers and every rule of its NAT gateways are gone, and the wipe report names each under its step.
- Every wipe report names the three steps, with an empty list for a step that removed nothing.
- A listener is deleted after its default pool is unset, and it reads as gone before the next listener is touched.
- A step never touches the bucket, load balancer, gateway or rule of another deployment, and a failed read of the cloud is never taken for gone.
- A step that cannot finish is named in the report's errors, and the destroy and the purge after it still run.

The rest of this ticket is the exact instruction for the model that does the work.

## 2. End goal
The Huawei adapter's `Wipe` runs three named steps before `tofu destroy`. `before_destroy_buckets` empties and removes the deployment's bucket with the purge's `emptyAndRemoveOBSBucket`; `before_destroy_listeners` removes every listener of the Sovereign's load balancers one at a time, its default pool unset first, as the purge's `cascadeDeleteELB` does, each read back as gone before the next; `before_destroy_nat_rules` removes every SNAT and DNAT rule of the Sovereign's NAT gateways on the nested path of the purge's `cascadeDeleteNAT`, until the gateway lists none. The cloud then answers not-found for them, the destroy's refresh drops them from the state, and the destroy removes the rest, so the wipe report can say `tofuDestroyed=true`. The report's `providerPurge` carries the three keys on every wipe. The purge after the destroy, the module's `force_destroy` and the wipe response's shape do not change.

## 3. The model (the law)
1. `Wipe` (`internal/providers/huawei/provider.go`) calls `removeBeforeDestroy` after it has read the credentials and before the destroy. The destroy is called through the package variable `tofuDestroy` (`provisioner.New().Destroy`); only a test reassigns it.
2. The steps run in this order: `before_destroy_buckets`, `before_destroy_listeners`, `before_destroy_nat_rules`. Each sets its key in `WipeResult.ProviderPurge` to what it removed and read back as gone, an empty list when nothing. A step that stops appends `<key>: <reason>` to `WipeResult.Errors`; the next step, the destroy and the purge run all the same.
3. The bucket step touches only `BucketNameForSovereign(fqdn, deploymentID)`, through the object-storage seam `obsEndpointFor` and the transport of `httpClientFor`. It reports the bucket only when the bucket was there and reads as gone after `emptyAndRemoveOBSBucket`; it tries at most three times within five minutes (a writer of the still running cluster may add an object between the emptying and the removal).
4. The listener step reads the Sovereign's load balancers with `listELBsByName` and each one's listeners from its own record. For each listener in turn it reads the listener; while the listener is there it unsets the default pool when one is set (`{"listener":{"default_pool_id":null}}`) and deletes it; only a not-found read ends it, within at most 60 seconds per listener. A listener is reported as `<load balancer name>/<listener id>`.
5. The rule step reads the Sovereign's gateways with `listNATsByName` and lists `snat_rules` and `dnat_rules` with `?nat_gateway_id=<gateway>`. A rule is listed only when its `nat_gateway_id` is that gateway. It deletes each listed rule on `/v2/<project>/nat_gateways/<gateway>/<kind>/<rule>` and lists again until the gateway lists none, within at most 120 seconds per gateway. A rule is reported as `<gateway name>/<kind>/<rule id>` once a later read omits it.
6. Only a not-found answer means gone. A read that fails in any other way is retried until the step's bound and then named in the errors; it is never reported as removed. A rule listing answered not-found is an empty listing, as `listELBsByName` and `listNATsByName` already treat a not-found listing.
7. The purge after the destroy reaches the object store through `obsEndpointFor(region)` (the same host as before: `obs.<region>.kom4dc.nationalcloud.om`).
8. Unchanged: `purgeHuaweiResources`, `cascadeDeleteELB`, `cascadeDeleteNAT`, `emptyAndRemoveOBSBucket`, the verify-and-re-purge passes, the address cooldown, the volume backstop, the module's `force_destroy = true`, and the handler's projection of the report.
9. All four paths change only through the patch `CLD-116.patch` of this ticket.

# AIP-103 — Real streaming and real usage

## In plain words

**The problem today.** A streamed answer from Axon arrives all at once, after the model has finished, so a long answer looks stalled and a caller cannot follow tool-call arguments as they form. A caller that goes away is not noticed, so its model run goes on for nobody.

**What changes.** Each part of the answer reaches the caller as the model produces it, a failed stream says so instead of looking finished, and the run stops when the caller leaves.

**Done means:**

- A streamed text answer arrives as a role chunk and one content chunk per model delta, then a finish chunk, the usage chunk when asked for, and the end marker.
- A streamed tool call arrives as one start delta with its index, identifier and name, then one argument delta per piece the model produced.
- The usage chunk carries the real token counts of the model message, never zeros.
- The first chunk reaches the caller while the model is still generating, and the stream path uses no timer.
- An error before the first chunk is answered with its own status; an error after it ends the stream with an error event and without a finish chunk or the end marker.
- A caller that disconnects in the middle of an answer closes its model run.
- Unstreamed answers behave as before, and Axon's unit tests pass.

The rest of this ticket is the exact instruction for the model that does the work.

## 2. End goal
`POST /v1/chat/completions` with `"stream": true` on `products/axon` writes one chunk per upstream event at the moment the event arrives: the role chunk, a content delta per text delta, a tool-call start delta (`index`, `id`, `type`, `function.name`, empty `function.arguments`) per tool-use block and an arguments delta per input JSON delta; then the chunk with `finish_reason`, the usage chunk with empty `choices` when `stream_options.include_usage` is set, and `data: [DONE]`. No answer is buffered before the first chunk and no timer runs in the stream path. A caller that disconnects closes its chain and the run behind it. `cd products/axon && npm ci && npm run build && npm test` passes 55 tests, ten of them in the new `test/stream.test.ts`.

## 3. The model (the law)
1. `src/turns.ts` exports `StepSink` (`role()`, `text(delta)`, `toolStart(index, id, name)`, `toolArgs(index, json)`), `Disconnected` and `emulatedOf(req)`. `TurnManager.step(req, organization, sink?, signal?)`: the sink and the signal are optional, and without them a step is exactly the step of AIP-102.
2. The step calls the sink as each upstream event arrives: a non-empty text delta gives `text`, a tool start gives `toolStart`, an input JSON delta gives `toolArgs`. `role()` is called once, before the first of these, or before the step returns when the answer had no delta. Nothing reaches the sink before the first such event, so an upstream error that comes first is still answered with its own status, `Retry-After` and body, mapped as AIP-102 maps it.
3. With `parallel_tool_calls: false` only the deltas of tool index 0 reach the sink, because only the first tool call is returned.
4. The route writes, per sink call, one `chat.completion.chunk` whose only choice has `finish_reason: null` and the delta: `{"role":"assistant","content":""}`; `{"content": <text>}`; `{"tool_calls":[{"index","id","type":"function","function":{"name","arguments":""}}]}`; `{"tool_calls":[{"index","function":{"arguments": <json>}}]}`. After the step it writes the chunk with `delta: {}` and the `finish_reason` of the result, then, when `stream_options.include_usage` is true, the chunk with `choices: []` and the usage of the result (the raw-event usage of AIP-102), then `data: [DONE]`. Every chunk of one answer has the same `id`, `created` and `model`.
5. The response head is written with the first chunk: status 200, `content-type: text/event-stream`, `cache-control: no-cache`, and `x-openova-emulated` when `emulatedOf(req)` is not empty (the same function the step uses).
6. A text answer's finish chunk is written only after the run's result message: a run that fails after its last model message is not reported as finished. An error after the first chunk ends the stream with one `data: {"error": {"message","type","code"}}` event (the error body of the contract; any error that is not an `HttpError` is `502 backend_error`), with no finish chunk, no usage chunk and no `data: [DONE]`. A stream without `data: [DONE]` is an aborted stream to the meter (package AIP-112).
7. No sleep, no timer and no re-chunking in the stream path.
8. A caller disconnect is the close of the response before it finished. It aborts the step's signal: the chain is closed (its run interrupted) and the step throws `Disconnected`; the route writes nothing more. This holds for unstreamed requests too.
9. Unstreamed requests are answered exactly as in AIP-102.

# SEC-205 — Stores in Organization namespaces

## In plain words

**The problem today.** A platform namespace can get its own External Secrets reader from the library chart, but an Organization namespace has none. An Organization's values can only be read through the one cluster-wide store, which reads for every namespace.

**What changes.** The organization controller writes the namespace's own reader and its one store into the part of the Organization's tree that is applied on the host, in every region. The store reads only keys below that namespace's own path.

**Done means:**

- Every Organization's host-applied tree holds the service account eso-reader, which mounts no token, and the store openbao, which logs in as eso-reader with role eso-ns.
- The same file is in the region-baseline copy that the other regions apply, and both host-apps indexes list it.
- The file is never in the tree that is applied inside the Organization's virtual cluster.
- No object of an Organization names the cluster-wide store, carries the legacy-store label, or is a store for mount mounted/.
- An Organization whose index was written before this change gains the entry on its next reconcile and keeps the entries the provisioning service added.

The rest of this ticket is the exact instruction for the model that does the work.

## 2. End goal
The organization controller renders, for every Organization `<slug>` and every plan, the file `eso-stores.yaml` into the host-applied tree `vcluster/host-apps/` and into its region-baseline copy `vcluster/region-baseline/host-apps/`, and lists it in both trees' `kustomization.yaml`. The file holds ServiceAccount `<slug>/eso-reader` (`automountServiceAccountToken: false`) and SecretStore `<slug>/openbao` (vault provider, `path: secret`, `version: v2`, kubernetes auth mount `kubernetes`, role `eso-ns`, service account `eso-reader`): the same two objects that `platform/secrets-lib` renders for a platform namespace (SEC-200). A unit test decodes both objects strictly and compares them whole, for every plan, and fails when the file leaves the host-apps trees, when an index misses it, or when any rendered object names the cluster-wide store, carries the label `secrets.openova.io/legacy-store` or is a store for `mounted/`.

## 3. The model (the law)
1. One store, not two. SEC-200 renders no store for mount `mounted/` (`platform/secrets-lib/chart/templates/_secret-stores.tpl` lines 11 to 13), because External Secrets cannot write a tier B value with create-only rights (`docs/ledger/plan/spikes/SEC-140.md`, step 2) and a tier B value is written only by the birth Job. This package follows that decision: there is no SecretStore `openbao-mounted`.
2. `eso-stores.yaml` holds exactly two documents, in this order: ServiceAccount `eso-reader` and SecretStore `openbao`, both in namespace `<slug>`, both labelled `openova.io/organization: <slug>` and `openova.io/managed-by: catalyst`; the ServiceAccount also `app.kubernetes.io/component: eso-reader`. The store's server is `http://openbao.openbao.svc.cluster.local:8200`, the default of `platform/secrets-lib`. OpenBao role `eso-ns` already binds `eso-reader` in every namespace (`platform/openbao/chart/templates/_config.tpl` line 341); its policy admits only keys under `openova/apps/<namespace>/`.
3. The file is written in the host-applied tree only: both objects belong in the host namespace `<slug>`, where External Secrets runs. It is never written into `vcluster/apps/` (applied inside the virtual cluster) or listed in the boundary index `vcluster/kustomization.yaml`.
4. The region-baseline copy is produced by the existing copy of the host-apps tree (`addRegionBaselineTrees`, `core/controllers/organization/internal/gitops/region_local.go` line 187); the copy is byte for byte the shared file.
5. An Organization namespace never gets the cluster-wide store `vault-region1` or a `ClusterSecretStore`; no rendered object carries `secrets.openova.io/legacy-store`.
6. The reconcile of a new Organization creates 30 files in Git, two more than before (`eso-stores.yaml` and its region-baseline copy).
7. Nothing else changes: no other template, no Go behaviour outside `Render`, no chart, no version, no pin.

# AIP-153 — The token route admits the workspace of each Organization for its own Organization

## In plain words

**The problem today.** The agent workspace of an Organization will renew its tool identity by asking catalyst-api for a short-lived agent token with the token of its own account. Today catalyst-api gives such a token only to a workload listed by its exact name, and the shipped list names only the conformance probe, so every workspace would be refused. Listing each Organization by hand would need a configuration change for every new Organization.

**What changes.** The shipped list gains one entry that admits the workspace account of every Organization, for its own Organization only, with no change per Organization. The account in any other place, every other account, and a request for another Organization stay refused.

**Done means:**

- The workspace account in the namespace of an Organization gets an agent token for that Organization.
- The same account asking for another Organization is refused.
- The account of that name in a namespace that belongs to no Organization, and every other account of an Organization's namespace, are refused.
- No agent token of the workspace carries a tier above developer.
- The two copies of the shipped list are equal, keep the conformance entry and admit no Organization by wildcard.

The rest of this ticket is the exact instruction for the model that does the work.

## 2. End goal
catalyst-api issues agent tokens at `POST /api/v1/internal/agent-tokens` (package `products/catalyst/bootstrap/api/internal/agenttoken`, contract `docs/contracts/model-contract.md` section 2). Today a caller is admitted only when an entry of `CATALYST_AGENT_TOKEN_CALLERS` names its TokenReview user name exactly, and the shipped default names only the conformance probe. After this ticket an entry may also have the own-Organization form: caller `system:serviceaccount:{organization}:<name>` with organizations `["{organization}"]`. Such an entry admits the ServiceAccount `<name>` of every namespace of an Organization, that is a Namespace whose label `openova.io/organization` holds a slug, and only for that Organization. The shipped default gains the entry `{"caller": "system:serviceaccount:{organization}:agenity", "organizations": ["{organization}"], "maxTier": "developer", "agents": ["agenity"]}` beside the conformance entry, in `values.yaml` and in the literal of `api-deployment-kustomize.yaml`. So the agent workspace (`bp-agenity`), which runs on the host cluster in its Organization's namespace and will run as the ServiceAccount `agenity` (AIP-155 renders it), may ask for tokens of its own Organization with no commit of values per Organization. This ticket fixes the account name `agenity` and the agent name `agenity`.

## 3. The model (the law)
1. An entry that names its caller exactly works as on `main` and is matched first.
2. An entry of the own-Organization form has the caller `system:serviceaccount:{organization}:<name>`, where `<name>` is a DNS label, and the organizations exactly `["{organization}"]`. `{organization}` anywhere else, or with other organizations, makes the value unparsable: the route answers 503 `agent-tokens-misconfigured` and never falls back to allowing.
3. Such an entry admits the TokenReview user `system:serviceaccount:<namespace>:<name>` only when catalyst-api reads the Namespace `<namespace>` and its label `openova.io/organization` holds a slug. That slug is the caller's Organization. Several namespaces may carry the label of one Organization.
4. The caller gets a token for its own Organization only. Any other Organization is 403 `caller-not-allowed`. Its agents and its `maxTier` limit it as for every entry, and no entry has a `maxTier` above developer.
5. The account of that name in a namespace without the label, in a namespace that does not exist or whose label is no slug, every other account of an Organization's namespace, and a user that is not a ServiceAccount get 403 `unauthorized-sa`. No refusal holds a token or writes an audit event.
6. The shipped default of `agentTokens.callers` and its literal in `api-deployment-kustomize.yaml` are equal: the conformance entry, unchanged, then the workspace entry of the End goal. Neither holds `"*"`.
7. The claims, the audit event and the other routes do not change. The token's `caller` claim is the TokenReview user name, as before.

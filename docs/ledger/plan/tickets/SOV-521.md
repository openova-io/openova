# SOV-521 — The release route promotes one region per request and rolls a region back to its recorded main

## In plain words

**The problem today.** A release delivery to a Sovereign moves every region in one request, so a region cannot be updated, watched and compared before the next one moves. When a region misbehaves after its update, nothing puts it back to what it ran before: only a hand change of its Git branch can.

**What changes.** A delivery request may name one region, and only that region moves. A second kind of request puts a named region back to the files it ran before that delivery, as one new commit on top, never by rewriting history. A request that names no region works exactly as before.

**Done means:**

- A request that names one region moves only that region's branch; every other region's branch stays the commit it was.
- A rollback request puts the region back to the files it had before the delivery, as one new commit on top of the delivered one, and no push is ever forced.
- A rollback is refused, with nothing pushed, when the region changed after the delivery or when this release never delivered to it.
- A request that names a region the Sovereign does not have, or a rollback with a dry run or a pull credential, is refused.
- Across the requests of one release the state keeps what each region's delivery recorded, and reading the state shows it.
- A request that names no region delivers to every region exactly as before.

The rest of this ticket is the exact instruction for the model that does the work.

## 2. End goal
A sovereign-admin, or a workflow acting for one, can deliver a release candidate to a cut-over Sovereign one region at a time and put a region back. `PUT /api/v1/sovereign/release` with `"region": "<name>"` stages and prewarms the candidate in every region exactly as a whole delivery does, and its promote checks and pushes that region only; the other regions' `main` stay the commits they were. `PUT` with `"rollback": true` and a region puts that region's `main` back to the tree it had before this candidate's promote, as one commit on top of the promoted one, a fast-forward the Git server checks. `GET` answers, per region, what its promote and rollback recorded. A request without these fields does what it does today. The package that updates the standing environment through the route (FND-076) depends on this.

## 3. The model (the law)
1. A request names at most one region: `primary`, or a follower's name, which is a key `<name>.yaml` of the Secret `cutover-secondary-kubeconfigs` without `.yaml`, as the state ConfigMap `sovereign-release` names regions. Any other name is answered `400 bad-region`, and nothing is created.
2. A region request stages and prewarms like a whole request, in every region, so a conflict in any region moves nothing. Only the promote reads the region: it checks and pushes that region alone. A request without a region promotes every region, the followers first, as before; no container of it carries `RELEASE_REGION`.
3. A region request is promoted by the candidate's own `release-run.sh` (the delivery runs the candidate's mechanism, #7938). The bootstrap's stage reads that script for the phase `rollback` as it reads the phase `verify` (`grep '^  rollback)'`); a candidate without it promotes every region, so the stage refuses the request with phase `refused`, nothing moved, and deletes the pull credential.
4. A rollback names a region and carries neither `dryRun` nor `pullSecret` (`400 rollback-without-region`, `rollback-dry-run`, `rollback-pull-secret`). It runs no stage and no prewarm: the bootstrap Job is the one container `release-run.sh rollback` of the installed route's scripts. With no stage there is no rendered candidate, and a route that accepts the field `rollback` carries this change, so its scripts carry the phase.
5. The route sends a rollback only when the state records, for this candidate, the region's `<region>.promotedFrom` and `<region>.promotedTo` as commit ids; otherwise `409 not-promoted`, nothing created. Only a `release-run.sh` with the phase `rollback` records them, so a candidate without it cannot be rolled back.
6. `release-region.sh rollback` is refused, phase `moved`, nothing pushed, unless the region's `main` is still the promoted commit. It pushes one commit whose tree is the recorded main's tree and whose parent is the promoted commit, with a plain push, which the server refuses unless it is a fast-forward. It never forces a push. The promoted commit stays in the history and Flux applies the earlier tree. A second rollback of the same promote finds that commit and pushes nothing.
7. Every promote records `<region>.promotedFrom` (the main of the stage), `<region>.promotedTo` (the commit pushed) and `<region>.phase` (`promoted`; a rollback sets `rolled-back`). The route keeps these keys across the requests of one candidate and drops them for another. `GET` answers them in `status` and as `promoted.<region>`.
8. `files/release/contract` stays `1`: an installed bootstrap accepts contract 1 only. The API's and the chart's copies of both scripts stay byte-identical.
9. `release-run.sh` gains no call site of the cluster client: every call site is replayed and checked against the runner's RBAC by `TestReleaseScriptCallsAreGrantedToTheirAccount`, which this package does not change. No RBAC rule changes.
10. The installed route of an earlier release answers `400` to a body with a field it does not know, so the first delivery that carries this change to a Sovereign is a whole delivery.

# SOV-130 — Substrate window, part 1: modules and cloud-init take the variables document

## In plain words

**The problem today.** A new Sovereign's boot script types the values of its bootstrap manifests into four Flux objects, each with a list of its own. Several values are repeated in two lists, one name carries two different values, and the DNS API key sits in plain view in one object's specification. Later work has no single object to read these values from or to replace them in.

**What changes.** The boot script writes one ConfigMap that holds every value, and every Flux object it creates reads that ConfigMap. The DNS API key moves to a Secret of its own. What Flux renders on a new Sovereign does not change.

**Done means:**

- A new Sovereign's boot script creates the ConfigMap flux-system/sovereign-variables, and no Flux object that it creates keeps a list of values of its own.
- The keys of that ConfigMap are exactly the bootstrap-kit keys listed in the variables contract.
- The DNS API key appears in the boot script only in the Secret flux-system/sovereign-tls-secrets.
- Every manifest that Flux renders from the bootstrap tree on a new Sovereign is the same as before.
- The render test of the boot template fails when the ConfigMap, its readers or the Secret are missing, and the stored golden render values match the changed template.

The rest of this ticket is the exact instruction for the model that does the work.

## 2. End goal
On a new Sovereign, cloud-init writes one ConfigMap, `flux-system/sovereign-variables`, in the file `/var/lib/catalyst/flux-bootstrap.yaml`, directly after the Kustomization `bootstrap-kit` and before the other Flux Kustomizations of that file. It holds every value that the four inline `postBuild.substitute` maps of the shared boot template `infra/providers/_shared/cloudinit-control-plane.tftpl` hold today, except the DNS-01 API key. Every inline Flux Kustomization of the template (`bootstrap-kit`, `sovereign-tls`, `bootstrap-kit-crs`, `sovereign-region-bootstrap`, `infrastructure-providers`) reads that ConfigMap through `postBuild.substituteFrom`, and none keeps an inline `substitute` map. The API key `POWERDNS_API_KEY` is the one key of the Secret `flux-system/sovereign-tls-secrets`, which cloud-init applies with the other bootstrap Secrets and which `sovereign-tls` reads through `substituteFrom`. Every manifest that Flux builds and substitutes from these Kustomizations is the same, character for character, as before. The render test of the template proves the new shape for both cloud branches, and the stored golden render values match the changed template.

## 3. The model (the law)
1. One ConfigMap, `sovereign-variables` in namespace `flux-system`, is a document of `/var/lib/catalyst/flux-bootstrap.yaml`, directly after the Kustomization `bootstrap-kit` and before `sovereign-tls`. The same `kubectl apply` creates both a moment apart. Flux substitutes only after the GitRepository `openova` has fetched an artifact, which takes minutes on a new cluster, so the ConfigMap exists before any Kustomization reads it; a reconcile that still found it missing would be retried by Flux. Its `data` is the union of the four former inline maps, with each value written as the map wrote it, and with the same `%{ if ... }` template conditions around the keys that had one.
2. The former map of `bootstrap-kit` becomes the body of that `data` in place (the Kustomization keeps its lines above it, and its `postBuild` ends before the ConfigMap begins): its key lines, comment lines and template directives are not changed, except that the value of `SOVEREIGN_CONSOLE_LB_IP` is put in double quotes (rule 6). Three keys that only the smaller maps carried are added after it: `WILDCARD_CERT_ISSUER` (from `sovereign-tls`), and `SOVEREIGN_REGION_ID` and `SOVEREIGN_WRITER_REGION_ID` (from `sovereign-region-bootstrap`, inside `%{ if provider != "hetzner" ~}` as that Kustomization is). No other key is added.
3. Every inline Flux Kustomization of the template has `postBuild.substituteFrom` with the entry `kind: ConfigMap`, `name: sovereign-variables`, and no `postBuild.substitute`. `sovereign-tls` lists three sources in this order: the ConfigMap `sovereign-tls-vars` (`optional: false`, as today), the ConfigMap `sovereign-variables`, and the Secret `sovereign-tls-secrets`. No key is in two of these sources: `sovereign-tls-vars` holds only `PARENT_DOMAINS_LISTENERS_YAML` and `CONSOLE_LISTENERS_YAML` (`platform/sovereign-tls-vars/chart/templates/configmap.yaml` lines 269 and 277). `infrastructure-providers` had no `postBuild` and gets the same `substituteFrom`; its tree names no variable, so nothing in it changes.
4. The key `SOVEREIGN_REGION_KEY` had two values: `${sovereign_region_key}` in the `bootstrap-kit` map and `${primary_region_canonical_label}` in the `sovereign-tls` map. The ConfigMap keeps the `bootstrap-kit` value. The only manifests under the `sovereign-tls` paths that read the key are the two Hetzner load-balancer name annotations of `clusters/_template/sovereign-tls-hetzner/kustomization.yaml`. They read `${SOVEREIGN_PRIMARY_REGION:=primary}` instead, which the ConfigMap holds with the value `${primary_region_canonical_label}`: the same value as before, so the load-balancer names do not change.
5. `POWERDNS_API_KEY` is never a key of the ConfigMap and never in a Kustomization's spec. It is the one key of the Secret `sovereign-tls-secrets` (namespace `flux-system`, type `Opaque`), in `stringData`, with the value `"${base64encode(powerdns_api_key)}"`: the base64 text that the inline map held. The Secret is the new file `/var/lib/catalyst/sovereign-tls-secrets.yaml` (mode `0600`) of `write_files`, applied by the existing `kubectl apply` line of the bootstrap Secrets, which gains ` -f sovereign-tls-secrets.yaml` at its end. That line runs before `flux-bootstrap.yaml` is applied.
6. A ConfigMap value must be a string. The only value of the map that is written without quotes and can be empty is `SOVEREIGN_CONSOLE_LB_IP` (empty when the Sovereign has no console load balancer). It is written as `"${console_load_balancer_ipv4}"`. Every manifest that reads it uses `${SOVEREIGN_CONSOLE_LB_IP:-...}`, which gives the same text for an absent key and for an empty value.
7. The render test `infra/providers/_shared/tests/cloudinit_render.tftest.hcl` gains five asserts in the run `hetzner_render_is_valid` and the same five in the run `huawei_render_is_valid`: the ConfigMap header is rendered; the number of `substituteFrom` entries that name `sovereign-variables` is 4 for the hetzner fixture and 5 for the huawei fixture (the hetzner render has no `sovereign-region-bootstrap`); no line `          substitute:` is rendered; `POWERDNS_API_KEY:` is rendered once, as the key of the Secret; the Secret file is applied with the other bootstrap Secrets.
8. `infra/providers/_shared/tests/golden.auto.tfvars.json` holds the SHA-256 of the changed render of each fixture: `golden_hetzner` is `92075106d95422e456d377e33f7b47e79a0f099b19d0fc8e06911184d8d57d50` and `golden_huawei` is `8e77ae30a9ca35ca83226b764aafd36288a4ac6798e73b3cc4f603d8947cfbbd`. These are the values that `scripts/update-cloudinit-golden.sh` writes for the changed template (field 4).
9. The keys of the ConfigMap are exactly the keys of `docs/contracts/c5-kit-keys.txt`, the bootstrap-kit keys of the variables contract. That file was generated from the four maps with `POWERDNS_API_KEY` left out; after this change the same extraction finds exactly its lines without any exclusion.
10. Nothing else a node boots with changes: no k3s flag, no registry file, no module input, no other file of `write_files`. Objects that cloud-init created on Sovereigns that already run are not touched; the change reaches only Sovereigns provisioned after the merge.

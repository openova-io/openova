# SOV-148 — Lab test: first-boot steps from a fetched, checksum-pinned bundle

## In plain words

**The problem today.** Most of the first-boot user data of a control plane is the same shell logic for every installation of a cloud, and the user data is close to the size limit of the clouds. Whether that logic can be fetched from the registry at boot and checked against a pinned checksum was not measured, so the tasks that shrink the user data could not be planned.

**What changes.** The result record of the lab test is in the repository: what stays inline, what the parent sees when the fetch fails, how long each boot step takes, whether the image pre-pull helps, and the follow-up tasks in order. The package is marked done.

- A control-plane machine of the `local` pack booted from one fetched, checksum-pinned bundle that holds its whole `runcmd`, in both regions, with the upstream hosts of the fetch blocked. The kit core came up Ready and the console answered.

### 6. The two ServiceAccount items as one function

- Bytes, reference cloud: today 1,086 (primary), and 1,086 + 1,080 = 2,166 (secondary). As a function `sa <name> <exit code>`: 1,102 (primary, +16), and 1,102 + a call of 24 = 1,126 (secondary, -1,040).
- Behaviour: both forms ran against a fake `kubectl` in three cases: all succeed, the handover-peer apply fails, the parent-bootstrap apply fails. They gave the same files, the same tokens and the same exit codes (0, 0, 98).
- **Defect, on main today.** The variable `T` is not reset between the two items, which run in one shell. When the handover-peer item never gets its token in its 60 tries, `[ "$T" ]` still holds the parent-bootstrap token. The item then writes `handover-peer.kubeconfig` with the parent-bootstrap token and exits 0. In the fake run, `handover-peer.kubeconfig` was byte for byte `parent-bootstrap.kubeconfig`.
- The function form fixes the defect with `T=` at its start (3 bytes).

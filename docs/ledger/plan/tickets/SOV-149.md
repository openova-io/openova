# SOV-149 — The image pre-pull leaves first boot

## In plain words

**The problem today.** Every new control-plane node starts two background image pulls during first boot. One copies the platform's Git repository, renders the platform chart and pulls its images with the registry password written in plain text into the node's start-up data; the other pulls the Flux and database images on IPv4-only clouds. A lab test measured that neither makes an installation faster, yet together they take about 2,000 to 2,600 bytes of start-up data that is capped at 32 KiB.

**What changes.** Both pulls are gone. The cluster pulls each image when a workload first needs it, through the node's registry mirror, as it already did for every image the pre-pull missed, and the registry password appears only inside the encoded pull secret.

**Done means:**

- The start-up data of a new control-plane node starts no image pull and holds no registry password in plain text.
- On the reference cloud every control-plane start-up data surface is at least 2,500 bytes smaller in the worst case, and on the second provider at least 1,900 bytes smaller; the worker surfaces are unchanged.
- Every file that first boot writes to the node is byte for byte what it was before.
- The render test of the shared template fails if an image pull or a plain registry password comes back.
- The tests of the shared template and of the three provider modules pass.

The rest of this ticket is the exact instruction for the model that does the work.

## 2. End goal
The shared first-boot template `infra/providers/_shared/cloudinit-control-plane.tftpl` holds no image pre-pull. The two background `runcmd` items are deleted: the pull of the platform images (it cloned the GitOps repository, rendered `products/catalyst/chart` twice and ran `crictl pull --creds "${ghcr_pull_username}:${ghcr_pull_token}"`, so the registry token stood in plain text inside `runcmd`), and, in the IPv4-only branch, the pull of the six Flux controller images and the database image. The result of the lab test SOV-148 (`docs/ledger/plan/spikes/SOV-148.md`, section 5) is that neither shortens an installation by a measurable amount, so nothing replaces them: no kit object pulls images ahead of time. The render test asserts the absence in both fixtures, and the golden render hashes follow the smaller render.

## 3. The model (the law)
1. First boot pulls no image ahead of time. The template holds no `crictl` call, no image list and no clone of the GitOps repository for a chart render. Each image is pulled by the kubelet when a pod needs it, through `/etc/rancher/k3s/registries.yaml`, which is unchanged.
2. The registry token stands in the rendered start-up data only inside the base64-encoded `.dockerconfigjson` of Secret `flux-system/ghcr-pull` (the line `password = ghcr_pull_token` of its `jsonencode`). It never stands in `runcmd`.
3. Delete, with no kit object in their place: the plan entry says a kit object takes the pull over only if SOV-148 measured a gain, and SOV-148 measured none.
4. No byte is added to the start-up data. Nothing is packed (`gz+b64`) and no limit is raised.
5. The template's inputs stay as they are. `node_ipv4_only`, `ghcr_pull_username`, `ghcr_pull_token`, `gitops_repo_url` and `gitops_branch` are still read elsewhere in the template, so no call of the template changes and no module changes.
6. Every file that cloud-init writes keeps its golden hash: only the two render hashes `golden_hetzner` and `golden_huawei` change.
7. A comment line of the template is stripped before the start-up data is sent (`^[ ]*#( |$)`), so the comment that replaces the two items costs no byte.

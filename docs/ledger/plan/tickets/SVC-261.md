# SVC-261 — A request with two reuse bindings of one capability on one instance is refused before any write

## In plain words

**The problem today.** The install route writes each backing service of a request as soon as it has checked it. When a later one is refused, the earlier ones stay written: with two reuse bindings of one capability on one instance, the first Context is written and committed, the second answers a conflict, the consumer is never created and the backing instance keeps a Context nobody uses.

**What changes.** The install route checks the whole list of backing services first and writes only when every one of them is accepted. A refused request leaves the cluster as it was.

**Done means:**

- An install request with two reuse bindings of one capability on one instance is refused with 409 context-exists, and the cluster receives no write.
- An install request whose later backing element is refused after a valid create or reuse answers that refusal, and no provider Application, no consumer and no Context entry is left behind.
- An install request whose backing elements are all valid writes the same objects, in the same order, as before, and each written Application is still committed to its Organization's repository.
- No error code is added, no Python line is added and no gate check changes its state.

The rest of this ticket is the exact instruction for the model that does the work.

## 2. End goal
`POST /catalyst/v1/apps/instances` judges every element of `backing[]` before it writes anything. `wireBackingServices` (`products/catalyst/bootstrap/api/internal/handler/endpoint_handler.go`) no longer creates a provider Application or updates a reused instance inside its loop: it plans each write in a `binding.Plan` (`products/catalyst/bootstrap/api/internal/capability/binding/binding.go`) and makes the planned writes, in the order of the list, only after the loop has accepted every element. A request with two reuse bindings of one capability on one instance answers 409 `context-exists`; a request whose later element is refused after a valid create or reuse answers that element's refusal; in both cases the cluster receives no create, update, patch or delete. A request whose elements are all valid writes the same objects in the same order as on `main`.

## 3. The model (the law)
1. The loop of `wireBackingServices` writes nothing to the cluster and commits nothing to Git. A create-mode element plans the create of its provider Application (`Plan.Create`); a reuse-mode element plans the update of the named instance with the consumer's Context entry appended to `spec.parameters[<valuesKey>]` (`Plan.Reuse`).
2. After the loop, and only when no element was refused, the planned writes are made in the order of `backing[]`: a create keeps an Application that already exists (as on `main`), an update is a plain `Update`, and each written Application is committed to its per-Organization `iac` repository with the same Organization as on `main` (`body.Org` for a created provider, the instance's namespace for a reused one). A cluster error answers 500 `backing-create-failed` (create) or `context-write-failed` (update), as on `main`.
3. `Plan.Reuse` refuses, with 409 `context-exists`, an instance that already declares a Context of the consumer's name (the check `main` makes) and an instance that an earlier element of the same request already reuses: the two entries would carry one name. A refused `Reuse` leaves its target object unchanged and plans no write. No error code is added: the refusal is the conflict the route already returns for a Context that exists.
4. The consumer Application is written after `wireBackingServices` returns, as on `main`; a refused element returns before it, so a refused request creates no consumer.
5. Nothing else changes: `binding.Resolve`, the shape checks of `internal/instances/create.go`, the canonical Context entry, `spec.parameters.bindings` and the Blueprint path are untouched. The handler package shrinks by 13 lines, and the structure ratchet `scripts/baselines/api-structure.json` is lowered to it by its own tool. No Python file is added or edited. No chart version line changes. No gate check moves.

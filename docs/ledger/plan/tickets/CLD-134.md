# CLD-134 — The reference cloud's profile declares its user-data limit; the guard checks it

## In plain words

**The problem today.** The Huawei cloud refuses user data over 32,768 bytes, but its cloud profile says that it has no limit. The size guard takes its limits from a second file of the pack and never looks at the profile, so nothing notices that the two disagree. The build workflow also tells the reader that the limit is a 32,256-byte cap of the other provider.

**What changes.** The Huawei profile states the limit of 32,768 bytes. The size guard compares the limit of every pack's profile with the limits it measures against and fails when they disagree; the wrong sentence in the build workflow is corrected.

**Done means:**

- The Huawei cloud profile states a user-data limit of 32,768 bytes, and the generated providers document shows it.
- The size guard fails when a pack measures its user data against limits and its profile states no limit, a lower limit, or a different number than the limit the pack names.
- The size guard fails when a pack states a limit that nothing measures.
- The guard has a self-test with one failing case for each of its rules.
- The build workflow no longer calls the limit a 32,256-byte cap of one provider.

The rest of this ticket is the exact instruction for the model that does the work.

## 2. End goal
Every provider pack states the user-data limit of its cloud in one field of its cloud profile, `spec.bootstrap.userDataLimitBytes` of `infra/providers/<pack>/profile.yaml` (0 means no limit). The Huawei pack states 32768 there; today it states 0. The size guard `scripts/cloudinit-size-check.py` gains the mode `--check-profiles`, which compares the profile of every pack with the limits of its worst-case file `infra/providers/<pack>/user_data_worst_case.py` and fails when they disagree, and the mode `--self-test`, which proves that each rule of that comparison can fail. The render of a provider (the mode `<provider>`, which the workflow `cloud-init-size` runs) makes the same comparison for that provider before it renders. The generated document `docs/generated/providers.md` shows 32768 for the Huawei pack, the Go test of the profile loader expects 32768, and the build workflow `.github/workflows/catalyst-build.yaml` no longer calls the limit "the 32256-byte Hetzner cap". A person can observe it on the pull request: the self-test passes with nine cases, `--check-profiles` passes on the tree, and it fails on the tree of `main` before this change.

## 3. The model (the law)
1. The profile field `spec.bootstrap.userDataLimitBytes` is the user-data limit of the cloud: the most bytes of raw user data the cloud accepts. 0 means no limit.
2. A pack's worst-case file holds each surface (control plane and worker of each region) to a limit. A module may hold a surface lower than the cloud's limit by a precondition of its own; it never holds one higher.
3. The comparison has four rules, and `--check-profiles` prints one line for every place a rule is broken and exits 1:
   - Rule 1: a pack with a worst-case file does not state 0 in its profile.
   - Rule 2: no surface of the worst-case file is held to more than the profile's limit.
   - Rule 3: a worst-case file that names the cloud's limit as the module constant `LIMIT` names the same number as the profile.
   - Rule 4: a pack without a worst-case file states 0: a limit that nothing measures is a limit that nothing holds.
4. A pack is every folder directly under `infra/providers` whose name starts with neither `_` nor `.`. A tree with no pack fails.
5. The profile is read without a YAML library, because the workflow `cloud-init-size` runs the program with the system `python3` and installs no package. The field must occur exactly once outside comment lines; a comment line is not read.
6. The limits of a worst-case file are read without a render: the program calls the file's `worst_case()` and its surface function with a stand-in for the rendered text. So `--check-profiles` and `--self-test` need `python3` only, and no OpenTofu.
7. The render of a provider runs the comparison for that provider first and exits 1, before any render, when a rule is broken.

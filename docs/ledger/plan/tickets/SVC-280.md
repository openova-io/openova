# SVC-280 — The dialog offers the implementation; capabilities routes

## In plain words

**The problem today.** A Blueprint can declare that it needs a capability, such as object storage, but the console's create dialog ignores that declaration and offers only the backing services named in the Blueprint's hard dependencies. Nothing in the API tells the console which Blueprints implement a capability on this Sovereign, which of them are offered, or which one is the default.

**What changes.** catalyst-api lists every capability with its current contract, its default and the Blueprints that provide it. The create dialog shows one block per capability the Blueprint needs, lets the person pick an implementation when there is a choice, then create a new one or reuse an existing one of that implementation, and sends that choice with the create request.

**Done means:**

- The list route and the route of one capability answer the agreed JSON for a test catalogue, and an unknown capability answers 404 capability-not-found.
- A person who is not a sovereign-admin sees only the implementations this Sovereign offers.
- Off a Sovereign the routes answer 404 not-a-sovereign, and before the Blueprint cache has finished its first list they answer 503, never a partial list.
- For a Blueprint that needs object storage with two offered implementations, the dialog shows both, and the create request carries the chosen implementation and the reused Application.
- The implementation picker is hidden when one implementation is offered or the Sovereign fixes the choice.
- A Blueprint without requirements renders and posts as before, and the existing dialog tests pass unchanged.

The rest of this ticket is the exact instruction for the model that does the work.

## 2. End goal
A signed-in User of a Sovereign who opens the create dialog of a Blueprint that declares `spec.requires` (for example `bp-capability-probe`, which requires `object-storage` under the alias `objects`) sees one block per requirement: the capability's title, the alias, a picker of the implementations this Sovereign offers (hidden when only one is offered or the choice is fixed), then the existing Create new / Reuse existing selector, whose reuse list holds only Applications of the chosen implementation. The create request carries one `backing[]` element per requirement, `{capability, alias, implementation, mode, instance}`, the shape the install API reads since SVC-260. The dialog learns the implementations from two new read routes of catalyst-api, `GET /api/v1/catalog/capabilities` and `GET /api/v1/catalog/capabilities/{name}`, which compute the registry from the embedded capability index and the Blueprint objects of the informer cache. A Blueprint without `requires` renders and posts exactly as before.

## 3. The model (the law)
1. The two routes are session routes registered in `products/catalyst/bootstrap/api/cmd/api/routes_catalog.go` (`registerSessionCatalog`), next to `GET /api/v1/catalog/{name}`. The rule of `buildRouter` (`cmd/api/routes.go` lines 38 to 44) places a route in `routes_<concern>.go` by the first path segment after `/api/v1/`, so `/api/v1/catalog/...` belongs to `routes_catalog.go`; `routes_catalyst.go`, the file that registers `POST /catalyst/v1/apps/instances`, holds the `/catalyst/v1/` routes only. The router matches the static segment `capabilities` before the parameter `{name}`.
2. The handlers live in a new package, `products/catalyst/bootstrap/api/internal/capabilityapi`. No file of `internal/handler` changes: `scripts/check-api-structure.py` refuses a new file and any growth of that package.
3. One item: `name`, `title`, `contract` (the newest version with status `current`), `default`, `organizationChoice`, and `implementations[]`, each `{blueprint, title, implementation, lifecycle, offered, available, unavailableReason}`. The capabilities and contracts come from the embedded index `internal/catalog/capabilities.json`; the providers from the Blueprint objects of the informer cache, through `capability.NewRegistry(index, blueprints, nil, capability.NoCloudProfile{})`: no catalogue policy (that block arrives with SVC-300), and no cloud-native implementation is available until the cloud profile says so (SVC-290). An `in-cluster` implementation is always available.
4. A caller for whom `lifecycle.SovereignAdmin` is false sees only the implementations with `offered: true`; a sovereign-admin sees every implementation.
5. Refusals, in the envelope `{"error": {"code", "message"}}`: 404 `not-a-sovereign` when the environment of catalyst-api has no `SOVEREIGN_FQDN` (as `internal/topologyread` does: a mothership process holds the clusters of many Sovereigns); 404 `capability-not-found` for a name the index lacks; 503 `cache-unavailable` when the informer cache is not set up, holds no cluster or cannot list; 503 `cache-not-synced` while the Blueprint informer of the home cluster has not finished its first list (a partial list is never served); 500 `capability-index-invalid` when the index cannot be read or a capability has no current contract.
6. The home cluster is the only cluster of the cache, else the first whose id starts with `sovereign-`, else the first in sorted order (the rule of `internal/topologyread`).
7. The dialog (`products/catalyst/bootstrap/ui/src/pages/sovereign/AppDetail/InstancesSection.tsx`, the sovereign-admin console tree) reads `spec.requires` from the Blueprint it already loads, fetches each capability once (`getCapability` in `src/lib/catalog.api.ts`) and renders block `backing-capability-<alias>`: the picker `backing-implementation-<alias>` when more than one implementation is offered and `organizationChoice` is not `fixed`; then `BackingServiceSelector` for the chosen implementation with test ids `backing-selector-<alias>`, `backing-create-<alias>`, `backing-reuse-<alias>`, `backing-instance-<alias>`. The chosen implementation is the person's pick when it is offered, else the default when it is offered. A required entry with nothing offered keeps Create disabled and says why; an optional entry with nothing offered sends no element.
8. The `depends[]` branch of the dialog stays: its elements are posted first, unchanged. The TypeScript `BackingSelection` gains the optional `capability`, `alias` and `implementation` and makes `blueprint` optional, as the Go type `instances.BackingSelection` has them.
9. The text the change adds to the console holds no banned term of `docs/GLOSSARY.md`. No Python, no chart version line, no live system.

+// registry builds the registry from the Blueprint objects of the home
+// cluster, or writes the refusal.
+func (rt *Routes) registry(w http.ResponseWriter, idx capability.Index) (capability.Registry, bool) {
+	c := rt.cache()
+	if c == nil {
+		refuse(w, http.StatusServiceUnavailable, "cache-unavailable", "the informer cache is not set up")
+		return nil, false
+	}
+	cluster, ok := homeCluster(c.Clusters())
+	if !ok {
+		refuse(w, http.StatusServiceUnavailable, "cache-unavailable", "the informer cache holds no cluster")
+		return nil, false
+	}

+		refuse(w, http.StatusServiceUnavailable, "cache-not-synced",
+			"the Blueprint informer of cluster "+cluster+" has not finished its first list")
+		return nil, false
+	}
+	bps, _, err := c.List(cluster, BlueprintKind, labels.Everything())
+	if err != nil {
+		refuse(w, http.StatusServiceUnavailable, "cache-unavailable", err.Error())
+		return nil, false

+// item is the answer for one capability. Without admin, only the offered
+// implementations are listed.
+func (rt *Routes) item(idx capability.Index, reg capability.Registry, name string, admin bool) (Item, error) {
+	current, ok := idx.Current(name)
+	if !ok {
+		return Item{}, fmt.Errorf("capability %s has no contract with status current", name)
+	}
+	offer := reg.Offer(name)
+	offered := map[string]bool{}
+	for _, im := range offer.Offered {
+		offered[im.Blueprint] = true
+	}
+	it := Item{Name: name, Title: idx.Title(name), Contract: current.Version, Default: offer.Default,
+		OrganizationChoice: offer.OrganizationChoice, Implementations: []Implementation{}}
+	for _, im := range reg.Implementations(name) {
+		if !admin && !offered[im.Blueprint] {
+			continue
+		}
+		available, reason := rt.available(name, im)
+		it.Implementations = append(it.Implementations, Implementation{
+			Blueprint: im.Blueprint, Title: im.Title, Implementation: im.Implementation, Lifecycle: im.Lifecycle,
+			Offered: offered[im.Blueprint], Available: available, UnavailableReason: reason,
+		})
+	}
+	return it, nil
+}

+// available follows the registry's rule: an in-cluster implementation can
+// always be used, a cloud-native one when the Availability says so.
+func (rt *Routes) available(name string, im capability.Implementation) (bool, string) {
+	switch im.Implementation {
+	case "in-cluster":
+		return true, ""
+	case "cloud-native":
+		return rt.avail.Available(name)
+	}
+	return false, fmt.Sprintf("unknown implementation kind %q", im.Implementation)
+}

+// homeCluster picks the cluster this catalyst-api runs in, by the rule of the
+// package comment. ok is false when the cache holds no cluster.
+func homeCluster(clusters []string) (string, bool) {
+	if len(clusters) == 0 {
+		return "", false
+	}
+	sorted := append([]string(nil), clusters...)
+	sort.Strings(sorted)
+	for _, c := range sorted {
+		if strings.HasPrefix(c, "sovereign-") {
+			return c, true
+		}
+	}
+	return sorted[0], true
+}

+// refuse writes {"error": {"code": code, "message": message}}.
+func refuse(w http.ResponseWriter, status int, code, message string) {
+	write(w, status, map[string]map[string]string{"error": {"code": code, "message": message}})

+	w.Header().Set("Content-Type", "application/json")

+	_ = json.NewEncoder(w).Encode(v)

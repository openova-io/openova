# AIP-031 — Spike: one sandbox substrate shared by Organizations, with grants scoped to each Organization

## In plain words

**The problem today.** Every Organization's agent-runtime controller is today a global owner of the one sandbox substrate that a cluster shares, so it could read and change the agents of every other Organization. Nobody had measured whether the substrate can confine each controller to its own space, so the agent runtime with the sandbox was planned for the Sovereign's own Organization only.

**What changes.** The measured result is in the repository: the substrate's API confines each controller through per-space grants that the platform writes, and its actor router does so only with one added rule. The package is marked done.

# Lab test AIP-031: one sandbox substrate shared by Organizations, with grants scoped to each Organization

Outcome: **pass**, with one addition that the upstream chart does not offer (a rule in the actor router). Date of the runs: 2026-11-19. Upstream versions as in lab AIP-030: kagent 1.0.1, Agent Substrate charts 1.0.0, router dataplane agentgateway v1.7.0.

## Question

Lab AIP-030 ran one kagent install per Organization on one shared Agent Substrate (T3). The upstream installer makes every Organization's controller a bootstrap owner of the Substrate API, and a bootstrap owner is a global owner. Can each controller instead be limited to its own atespace, so that it can neither read nor change another Organization's actors, while its own agents keep working? The question has two layers, and each was measured:

- the control plane: the Substrate API (`ate-api-server`), which authorizes every call against its OpenFGA model;
- the data plane: the actor router (`atenet-router`), through which a controller sends each turn to an actor, naming it in the header `ate-target-actor: <atespace>/<actor>`.

## What was run

- **Where.** GitHub Actions in openova-io/openova, on branch `spike/AIP-031` (head `4431ba73e323c0867bb5d6334fe58f0412b5d042`), deleted after the runs and never merged. Workflow `.github/workflows/spike-aip-031.yaml`, which ran only on a push to that branch. Scripts in `tests/spikes/AIP-031/`: `run.sh`, `routerpatch.py` (adds the router rule of S4), and `stub.py`, `a2a.py`, `mint.py` taken from the AIP-030 lab.
- **Runner.** `ubuntu-24.04`, one k3s node. No cloud account, no secret and no cluster outside the job. The NodePort guard of AIP-030 ran the whole job and reported "nodeport guard: no NodePort or LoadBalancer Service seen".
- **Cluster and installs, as AIP-030.** k3s v1.35.10+k3s1 with the platform's server flags, the three Pod Certificate feature gates and the `certificates.k8s.io/v1beta1` runtime-config; Cilium 1.19.3 with the platform's values; `kagent install --provider Ollama -n org-a` (exit 0 in 95 s and 99 s); install A scoped with `global.watchNamespaces=[org-a]`; installs B (`org-b`) and later C (`org-c`) by plain Helm with the same release name, their own PostgreSQL and `global.watchNamespaces` set to their namespace. ### S4, the data plane: fails as shipped; passes with a router rule

- Under the scoped API grants of S2, the identity of `org-a` still reached `org-b`'s actor through the router: `ACTOR_STATE_SUSPENDED` before, `ACTOR_STATE_RUNNING` after, HTTP 200 with the actor's A2A answer. The control (`org-b`'s own identity) gave the same.
- This is the upstream design of v1.0.0: the router's only check is the caller's SPIFFE ID against `ingressAllowedSPIFFEIDs` (chart template `atenet-router.yaml` line 48), "Any ID on the allowlist may use the ingress router to contact any actor" (`cmd/atenet/internal/router/README.md` line 216), and the dataplane calls `ResumeActor` with its own identity and a request that names only the actor (agentgateway v1.7.0 `crates/agentgateway/src/http/substrate/ingress.rs` lines 329 to 345), under its system role `ingress_router`, which holds `can_resume` in every atespace (`cmd/ateapi/internal/authz/model.fga` line 174). Upstream's threat model claims the opposite ("Ingress checks the caller's permission on the target actor", `docs/security/threat-model.md` T-04); the measurement agrees with the README and the source.

The router's ConfigMap `atenet-router-agentgateway-config` got one more `directResponse` condition in the policy block shared by its actor routes (HTTP and gRPC): when `ate-target-actor`, in the request headers or the CONNECT headers, does not start with the atespace paired with the caller's `source.spiffeId`, the router answers 403 before any resume. ## Answer

- **Control plane: yes, as upstream ships it, by configuration.** With the platform's own principal as the only bootstrap owner and one access policy per atespace granting `editor` to that Organization's controller, a controller can read and change only its own atespace. Every call on another Organization, on the global scope and on its own grants was refused, and the runtime kept working (turns, a new Agent, a new Organization). `editor` is enough; `owner` is not needed and would let a controller change its own grants.
- **The platform creates each atespace.** Creating an atespace needs a global owner, so a controller without global ownership cannot start in a new Organization until the platform principal has created the atespace (named as the Organization's host namespace) and its access policy. Then it recovers by itself within seconds.
- **Data plane: no, as upstream ships it; yes with one router rule.** Scoped API grants do not reach the router: any identity on its allow-list can resume and talk to any actor of any Organization. A per-caller rule in the router's configuration, pairing each controller's SPIFFE ID with its atespace, closes it, measured over HTTP and gRPC, while every Organization still reaches its own actors.

## What follows for the plan

1. The restriction set after AIP-030 ("the agent runtime with the sandbox for the Sovereign's own Organization only, until AIP-031 passes") can be lifted when the install of the runtime carries both measures below. Until then it stays.
2. **Bootstrap owner.** The Substrate API's `bootstrapOwners` lists one principal: a platform component's own pod-certificate identity. Never an Organization's controller, never `ate-client`.
3. **Atespace and grant per Organization.** That platform principal creates the atespace named as the Organization's host namespace and writes its access policy, `editor` for `spiffe://cluster.local/ns/<organization>/sa/kagent-controller`, when the Organization's runtime is installed. It deletes them when the Organization is removed, and never reuses an atespace name (upstream's known limitation: grants are keyed by name, `docs/guides/authorization.md`, "Known limitations").
4. **Router rule.** `ingressAllowedSPIFFEIDs` alone is not isolation. The router's ConfigMap carries the per-caller atespace rule measured in S4, regenerated with `ingressAllowedSPIFFEIDs` whenever an Organization is added or removed, by a post-render step because the chart has no value for it. The router was restarted after the change; whether it reloads the file by itself was not measured.
5. A view that lists workers across the cluster belongs to the platform, not to an Organization: kagent's Substrate summary calls the global `ListWorkers` (kagent v1.0.1 `go/core/internal/service/system/substrate.go` line 210), which S2 refused for the controller. The summary view itself was not exercised.

# FND-075 — The gate record carries the pre-flight numbers: quota headroom and the leftover count

## In plain words

**The problem today.** Before a fresh installation is fired, the flight checklist counts what the cloud account holds, what it may hold and what the wiped deployment left. None of these numbers reaches the gate record, so nobody can read later how much room the account had. The clean-wipe check judges one total of leftovers and nothing about the headroom, although its entry in the gate manifest asserts both, and it names kinds of resources that nobody shows were counted.

**What changes.** The gate workflow takes the pre-flight numbers as one input and the suite writes them into the record. The clean-wipe check gets a second step: it passes only when every kind it names was counted with nothing left, the headroom of networks and volumes was measured, and the numbers were read before the environment was created.

**Done means:**

- A gate run that is given the pre-flight numbers writes them into its record, per kind of resource, with the time they were read.
- A number that was not measured is left out of the record; it is never written as 0.
- The record checker accepts such a record and refuses one whose pre-flight numbers are empty, negative, or list a kind twice.
- The clean-wipe check fails when the run was not given the numbers, when a kind it names has no count of leftovers, or when any kind has leftovers.
- The clean-wipe check fails when the used and the allowed count of networks or of volumes is missing, or when the numbers were read after the environment was created.
- A value in another form stops the suite before it starts, with exit code 3.
- The suite README says what the value looks like and which tool each number comes from.

The rest of this ticket is the exact instruction for the model that does the work.

## 2. End goal
A person who starts the gate workflow after a wipe and a fire gives one more input, `preflight`. It holds what the flight checklist counted before the fire: for each kind of resource how many the account held, how many it may hold, and how many the wiped deployment left, with the time the numbers were read. The workflow hands the value to the suite as `ACCEPT_PREFLIGHT`. The suite writes it into the record as `provision.preflight`. `python3 scripts/acceptance-gate.py validate-record` accepts the record. Check FND-G13 records a second step, `FND-G13.2`. The step passes only when every kind the manifest entry names was counted with nothing left, the used and the allowed count of networks and of volumes are there, and the numbers were read before the environment was created. A number that was not measured is never taken as 0.

## 3. The model (the law)
1. **The value.** `--preflight` (variable `ACCEPT_PREFLIGHT`, workflow input `preflight`) is one line: `<UTC time>;<kind>=<used>/<allowed>/<left>,<kind>=<used>/<allowed>/<left>,...`. The time has the form `2026-11-20T05:55:00Z` and no other. A kind matches `^[a-z][a-z0-9_]*$` and is given once. Each of the three numbers is a whole number of 0 or more, written without sign and without a leading zero, or `-` for "not measured". Spaces around the time and around an item are ignored.
2. **An empty value** means the run did not say. The record then has no `preflight`, and step `FND-G13.2` fails.
3. **A value in another form stops the run** before anything runs: `Execute` returns an error that starts with `--preflight: `, and the program exits with code 3. This is what `--nodes-requested` and the two wipe flags do.
4. **The record.** `provision.preflight` is `{"measured_at": <time>, "kinds": [{"kind": <name>, "used": <n>, "allowed": <n>, "leftovers": <n>}]}`. `kind` is always there. `used`, `allowed` and `leftovers` are there only when they were measured; a measured 0 is written. The kinds keep the order of the value. The object is written whenever the flag is given, in the cloud or not, with or without the wipe flags.
5. **The record checker.** `scripts/acceptance-gate.py` knows the object in its table `RECORD`: `measured_at` and `kinds` are required, the three numbers are optional whole numbers, any other field is refused. It also refuses an empty list `kinds`, a kind with an empty name, a kind listed twice and a negative number. It does not judge the numbers; the check does.
6. **Step `FND-G13.2`.** It fails with one reason per broken rule, joined by `; `, in this order: a kind with leftovers above 0 (`<kind>: the wipe left <n>`) or with more used than allowed (`<kind>: <used> used of <allowed> allowed`), in the order of the value; each kind of the list `servers`, `volumes`, `addresses`, `load_balancers`, `networks`, `security_groups`, `buckets`, `dns_records` that has no count of leftovers (`<kind>: the leftovers were not counted`); `networks` and `volumes` when one lacks its used or its allowed count (`<kind>: the used and the allowed count were not both measured`); the creation time of the environment when it cannot be read; the time rule. A kind outside the list may be given; its leftovers count too.
7. **The time rule.** The environment was created at the earliest creation of the namespace `kube-system` in the regions, read with the function `kubeSystemCreated` that step `D0.11` uses. `measured_at` must be earlier than that time. An equal time fails. A region whose time cannot be read fails the step.
8. **The eight kinds** are the kinds that the manifest entry of FND-G13 names. The first seven are kinds of the leftover lister (`providers.LeftoverKind`). `dns_records` are the DNS records of the wiped deployment in its parent zone. No tool counts them yet, so the honest value is `dns_records=-/-/-` and the step fails on it. This is intended: the check never assumes 0.
9. **The two headroom kinds**, `networks` and `volumes`, are the two quotas that the pre-flight gate `scripts/prov-preflight.sh` always measures and refuses a fire on (its checks 3c and 3d). Their allowed count is the limit that gate printed. The check does not judge how much headroom is enough; the pre-flight gate does that before the fire.
10. **Step `FND-G13.1` is unchanged**: the previous deployment is named, is not the deployment under test, and left 0 orphans. The check passes only when both steps pass.
11. **The evidence of step `FND-G13.2`**: `measured_at`, `environment_created_at`, `leftovers` (kind to count), `leftover_count` (their sum) and `free` (kind to allowed minus used, for each kind that has both).
12. **The workflow** `.github/workflows/foundation-gate.yaml` gets the input `preflight` under `workflow_dispatch` and under `workflow_call` (a string, default empty), and the step with the id `run` passes it as `ACCEPT_PREFLIGHT`. Nothing else in the workflow changes. The capability `previous-wipe` is still declared from `previous_deployment_id` alone.
13. This ticket deletes no file and no behaviour.

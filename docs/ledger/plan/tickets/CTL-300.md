# CTL-300 — The running stream is the declared one

## In plain words

**The problem today.** The platform's event stream is not declared anywhere. The first service that starts creates it from code, and the NATS chart carries three other streams that are switched off because they would clash with it, plus a key-value bucket that nothing uses. What runs and what is declared differ, and a second creator could appear without anyone noticing.

**What changes.** The NATS chart declares the one stream, and its controller creates it. The services no longer create it: they bind to it and stop with an error while it is missing. The three switched-off streams, their switch and the unused bucket are removed.

**Done means:**

- The default render of the NATS chart holds exactly one stream object, CATALYST_ORG on the subjects catalyst.>, kept 336 hours, one replica, file storage.
- The render holds no key-value bucket named idempotency, and the chart has no value streamsEnabled.
- A service that starts while the stream is missing stops with an error that names the stream, and creates nothing.
- A chart test fails when the chart, the event contract or the Go code disagree on the stream name or its subjects.
- The event-subject check counts one stream-creation call in Go, the deprecated usage stream, instead of two.

The rest of this ticket is the exact instruction for the model that does the work.

## 2. End goal
The JetStream stream `CATALYST_ORG` is declared in one place: `platform/nats-jetstream/chart/templates/streams.yaml`, as the only `Stream` object of the chart `bp-nats-jetstream`, with the configuration the Go code used to create it with (subjects `catalyst.>`, file storage, limits retention, `maxAge` 336 hours, one replica, discard old). The JetStream controller of the chart's `nack` subchart creates it. The Go function `ensureOrgStream` in `core/services/shared/events/bridge_subscriber.go` no longer creates a stream: it looks the declared stream up, checks that it carries the requested subjects, and returns an error while it is absent. The three disabled `Stream` templates, the value `catalystStreams.streamsEnabled` with its comment, the values that only those templates read, and the `KeyValue` bucket `idempotency` are deleted. A new chart test, `platform/nats-jetstream/chart/tests/catalyst-org-stream.sh`, renders the chart and fails unless exactly one `Stream` renders with that exact spec, no bucket `idempotency` renders, the event contract `docs/contracts/C3-event-subjects.yaml` names the same stream, and the Go constants and default subject lists name the same stream and subjects. The guard `scripts/check-event-subjects.py` then counts one stream-creation call in Go (the deprecated `EnsureUsageStream` in `core/services/shared/events/nats.go`), and its baseline says so. ## 3. The model (the law)
1. **One declared stream.** The default render of `platform/nats-jetstream/chart` holds exactly one object of kind `Stream`: `apiVersion: jetstream.nats.io/v1beta2`, `metadata.name: catalyst-org`, and `spec` exactly `{name: CATALYST_ORG, subjects: ["catalyst.>"], storage: file, retention: limits, maxAge: "336h", replicas: 1, discard: old}`. The spec has no `servers` key: the JetStream controller then uses its own connection, `nack.jetstream.nats.url` (`nats://nats-jetstream:4222`, the Service of the nats subchart). The object renders when `catalystStreams.enabled` is true (the default), the same switch as the `KeyValue` buckets. Its values are fixed in the template, not read from values: the code binds to them, so they are not a per-Sovereign knob.
2. **The values are the ones that ran.** `ensureOrgStream` created the stream with `Subjects` `catalyst.>`, `Retention` limits, `Storage` file, `MaxAge` `14 * 24 * time.Hour` (336 hours) and `Replicas` 1, and no `Discard` (the server default, old). The declared stream has the same values, so on a Sovereign where the code already created the stream, the controller finds it with the same configuration.
3. **No Go code creates the stream.** `ensureOrgStream(ctx, name, subjects)` keeps its signature and its defaults (`name` `CATALYST_ORG`, `subjects` `["catalyst.>"]`). It calls `c.js.Stream(ctx, name)`. When that returns an error (for an absent stream, `jetstream.ErrStreamNotFound`), it returns an error that wraps it and names the stream and the chart. When the stream's cached configuration lacks one of the requested subjects, it returns an error that names the subject. It never calls a create or update method. Its two callers keep their behaviour: `NewMultiSubscriber` returns the error, and `EnsureCatalystOrgStream` (called by the billing service at start) returns it; every service that calls them (billing, domain, notification, provisioning, tenant) already exits with code 1 on that error, so its pod restarts until the stream exists.
4. **Deleted.** From `templates/streams.yaml`: the three `Stream` objects `catalyst-audit`, `catalyst-events` and `catalyst-billing` and their gate on `streamsEnabled`. From `templates/kv-buckets.yaml`: the `KeyValue` object `catalyst-idempotency` (bucket `idempotency`) and its line in the comment. From `values.yaml`: `catalystStreams.streamsEnabled` with its comment, and `catalystStreams.audit`, `.events`, `.billing` and `.idempotency`, which only the deleted objects read. From `tests/kyverno-probes-present.sh`: the render case `streams-enabled`, which sets the deleted value. No Go code uses the bucket `idempotency` (pre-flight P4).
5. **Kept.** The `KeyValue` buckets `dr-leases` and `policy-rollup`, the values `catalystStreams.enabled`, `.replicas`, `.servers`, `.drLeases` and `.policyRollup`, and the helper `catalyst-nats.servers`. The new chart test asserts nothing about these two buckets: other packages decide them (field 11).
6. **The chart test.** `tests/catalyst-org-stream.sh` is created by the patch of field 20 (step 4). CI runs it as `bash <script> <chart dir>`. It renders the chart with `helm template nats-jetstream . --namespace nats-system` and checks, with Python and PyYAML: (a) exactly one `Stream`, with the `apiVersion`, name and spec of item 1; (b) no `KeyValue` with `spec.bucket: idempotency`; (c) the key `stream` of `docs/contracts/C3-event-subjects.yaml` equals the spec's `name`; (d) the line `const StreamCatalystOrg = "<name>"` in `core/services/shared/events/bridge_subscriber.go` and in `core/controllers/pkg/natsbus/subscriber.go` names the spec's `name`; (e) `core/services/shared/events/bridge_subscriber.go` and `core/services/shared/events/nats.go` each hold at least one Go list `[]string{"catalyst..."}`, and every such list is exactly the spec's `subjects`. It prints one `FAIL:` line per failure and exits 1, or prints one summary line and exits 0.
7. **The guard's baseline.** `scripts/check-event-subjects.py` (unchanged) counts the lines of non-test Go that call `AddStream`, `CreateStream`, `CreateOrUpdateStream` or `UpdateStream`, per file, and fails when a count differs from `scripts/baselines/streams.json` in either direction. After the change `bridge_subscriber.go` has none, so its entry under `stream_create_calls` is removed; the entry of `nats.go` (1, `EnsureUsageStream`) stays. The call `c.js.Stream(` is a lookup and is not counted.
8. **The Go test.** `TestEnsureOrgStreamBindsToTheDeclaredStream` in `core/services/shared/events/bridge_subscriber_test.go` gives `NATSConn` a stand-in JetStream whose only method is the stream lookup; any other method panics. It proves: a declared stream with `catalyst.>` binds and is looked up by the name `CATALYST_ORG`; an absent stream gives an error that wraps `jetstream.ErrStreamNotFound`; a stream without `catalyst.>` is refused; `NewMultiSubscriber` with the stream absent returns an error that wraps `jetstream.ErrStreamNotFound`. On the code before this change it panics, because the old code calls `CreateOrUpdateStream`.
9. **Comments follow the code.** The doc comments of `StreamCatalystOrg`, `ensureOrgStream`, `MultiSubscriber`, `MultiSubscriberConfig.StreamSubjects` and `NewMultiSubscriber` in `bridge_subscriber.go`, and of `EnsureCatalystOrgStream` and `SubscribeUsageRecordedOnOrg` in `nats.go`, say that the chart declares the stream and the code binds to it. The header comment of the `catalystStreams` block in `values.yaml` and of `templates/streams.yaml` say the same. These are all the comments this ticket changes. Older comments that still speak of code creating a stream stay as they are: field 11 lists them, with the reason for each.

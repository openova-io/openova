# SEC-152 — Shared template writes the seal key files and the seal profile; seal volume on the reference pack

## In plain words

**The problem today.** Every provider pack already makes one OpenBao seal key per region, but nothing puts that key on a control-plane node. The first-boot template neither writes the key nor prepares the separate disk the reference cloud is meant to keep it on, and OpenBao has no way to learn which key file to use.

**What changes.** First boot now writes the key of its region into memory, prepares and mounts the seal disk where the cloud has one, moves the key onto it before Kubernetes starts, and publishes a small, key-free description of the seal for OpenBao. On the reference cloud every control-plane server gets that small disk, which is removed with the server.

**Done means:**

- A new control-plane node of any pack finds its region's seal key at /var/lib/catalyst/seal, readable only by the OpenBao user, before k3s starts, and the key never lands on the system disk.
- On the reference cloud the key rests on its own 10 GB data disk; if that disk is missing, first boot stops with exit code 96 and k3s never starts.
- The cluster holds ConfigMap flux-system/sovereign-seal-profile with the seal kind and the seal stanza, and no key bytes.
- Re-applying an existing installation plans no replacement of a control-plane server, and wiping an installation deletes its seal disks.
- Every control-plane user-data surface stays within its limit in the worst case, and nothing is packed to make room.
- The tests of the shared template and of the three provider modules assert the four actions and pass.

The rest of this ticket is the exact instruction for the model that does the work.

## 2. End goal
Contract C8 (`docs/contracts/c8-seal-provider.md`, part 1) is carried out on the node. The shared first-boot template `infra/providers/_shared/cloudinit-control-plane.tftpl` writes each node file of the pack's seal hook to `/run/catalyst-seal-stage` (memory), prepares the seal volume when the hook names one (exit code 96 when the device is missing), installs the key at `/var/lib/catalyst/seal/openbao-seal-<key id>.key` (mode 0400, owner 100:1000, directory 0700) before the k3s install, removes the stage, and applies ConfigMap `flux-system/sovereign-seal-profile` (data `kind` and `stanza`) with the bootstrap Secrets. The four call sites of the template in the three provider modules pass the hook's outputs for their region, the control-plane instances of the reference pack carry the seal data disk the hook names (`/dev/vdb`), and every test and script that renders the template with its own inputs passes them too.

## 3. The model (the law)
1. The template names no provider. It reads only the four inputs `seal_kind`, `seal_stanza` (the region's `stanza_by_region` entry), `seal_node_files` (the region's `node_files_by_region` entry) and `seal_volume_device` of contract C8.
2. Action 1: each node file is a `write_files` entry `path: /run/catalyst-seal-stage/<base name of path>`, `permissions: '0400'`, `encoding: b64`, `content:` the hook's `content_b64`. Never packed (`gz+b64`).
3. Actions 2 and 3 are one `runcmd` item placed right before the k3s install item. When `seal_volume_device` is not empty its first lines are, in order: `[ -b <device> ] || exit 96`; `blkid <device> >/dev/null 2>&1 || mkfs.ext4 -q -L catalyst-seal <device>`; `grep -q catalyst-seal /etc/fstab || echo 'LABEL=catalyst-seal /var/lib/catalyst/seal ext4 defaults,nodev,nosuid,noexec 0 2' >>/etc/fstab`; `mkdir -p /var/lib/catalyst/seal && mount /var/lib/catalyst/seal`. Then always: `install -d -m 0700 -o 100 -g 1000 /var/lib/catalyst/seal`; per node file `install -m <permissions> -o <owner user> -g <owner group> /run/catalyst-seal-stage/<base name> <path>`; `rm -rf /run/catalyst-seal-stage`. Exit code 96 is used on that one line only (`scripts/check-cloudinit-exit-codes.py`).
4. Action 4: a plain `write_files` entry `/var/lib/catalyst/sovereign-seal-profile.yaml` (mode default 0644) holds the ConfigMap of the contract; the existing server-side apply of the bootstrap Secrets applies it first (`kubectl apply --server-side -f sovereign-seal-profile.yaml -f ghcr-pull-secret.yaml ...`). It holds no key bytes and is not shredded; the Secret files keep their shred list unchanged.
5. Every byte added must be in the user data: the key opens OpenBao, so it must be on the node before OpenBao starts and before any secret store exists; the volume and install steps must run before k3s; the stanza names the per-installation key id, which exists only in the infrastructure state and cannot come from Git. Nothing is packed and no limit is raised.
6. Each of the four `templatefile()` calls of the shared template (`infra/providers/huawei/main.tf` one, `infra/providers/hetzner/main.tf` two, `infra/providers/local/main.tf` one) passes the four inputs as literal keys from `module.seal`, indexed by the call's own region key.
7. The reference pack (`infra/providers/huawei/main.tf`, `huaweicloud_compute_instance.control_plane`) carries `dynamic "data_disks"` with one disk `type = "SSD"`, `size = 10` when `module.seal.volume_device` is not empty, and `delete_disks_on_termination = true`. `data_disks` is a replace-on-change field of the huaweicloud provider, so `data_disks` and `delete_disks_on_termination` join `lifecycle.ignore_changes`: a re-apply of an existing installation plans no replacement and no update. Workers carry no disk.
8. The device name stays `/dev/vdb`, as the hook of SEC-150 names it; this package changes neither the hook nor the contract.
9. No new Python. The worst-case render (`scripts/cloudinit-size-check.py`) must stand in for `module.seal` to render `main.tf`, which grows that file by 10 lines; its module docstring is rewrapped to the file's code width, without dropping a sentence, so the Python line total of `scripts/baselines/python.json` stays at 51,325.

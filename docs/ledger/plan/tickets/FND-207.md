# FND-207 — A check stays green on the newest valid pair until a newer record says otherwise

## In plain words

**The problem today.** The gate verdict pairs the two newest records. After the first gate run of a newly delivered candidate, and until its second run is recorded, those two records name different candidates, so every check that runs in the cloud is reported as not green. Every story that depends on a gate check is then refused for that whole window, although nothing failed.

**What changes.** The verdict takes the newest two records that form a valid pair. A check stays green on that pair until a newer record fails it; a newer record in which the check passes changes nothing until its own candidate has a pair.

**Done means:**

- Between the first and the second gate run of a new candidate, a check that was green stays green when the new run passes it.
- A check that a newer run fails is not green, and the verdict names that run.
- When no two records form a valid pair, a check is not green and the verdict says why, as before.
- A pair whose newer record is older than the age limit gives not green, also when a recent record of another candidate exists.
- On the records of the repository today the verdict prints the same lines as before.

The rest of this ticket is the exact instruction for the model that does the work.

## 2. End goal
After this ticket, `python3 scripts/acceptance-gate.py verdict` judges a check that runs in the cloud on the newest valid pair of counting records, not on the two newest records. When a newly delivered candidate has recorded its first gate run and not yet its second, the checks that the earlier candidate's pair proved stay green, unless that first run fails them; a run that fails a check is named in the verdict line. Rule 4 of `python3 scripts/plan.py check-pr` reads this verdict, so a story that depends on a gate check is no longer refused in that window. A person sees it in the verdict lines and in the self-test, which gains 8 cases.

## 3. The model (the law)
1. Every change of this ticket comes from the embedded block `FND-207.patch` at the end of field 20. You type no line of either file.
2. The pool of each kind of proof does not change: for a `running` check every counting record, for a `fresh` check the counting records of fresh installations (`proof_pool`).
3. When two records are a valid pair does not change: one candidate, the older finished before the newer started, the artefact lists agree, and for a `fresh` check two different deployments. These tests move unchanged, with their reasons, from `find_pair` into `pair_problem`.
4. The pair is the valid pair whose newer record is the newest, with the newest older record that makes it valid. When no two records of the pool form a valid pair, the reason is that of the two newest, as before.
5. A check is green when, as before, its state is not not-built, the pair's newer record is at most `max_age_days` old, the check applied in a record of the pair and passed in each record of the pair in which it applied; and, new, no record of the same pool that is newer than the pair, in which the check applied, has a status other than PASS. Such a record is named in the reason: `<status> in <file>, a record newer than the pair`.
6. The age rule is read on the pair's newer record, as before; a recent record of another candidate does not make an old pair young.
7. Pass rules 1, 4 and 5, the record schema, `validate`, `validate-record`, `merge-check` and `export` do not change. `scripts/plan.py` is not changed: its rule 4 of `check-pr` reads the verdict.
8. The self-test gains 8 cases. No file is added or deleted.

# CTL-172 — Platform charts take placement from values

## In plain words

**The problem today.** Eleven platform charts create their own Application object and keep its placement and regions by reading the live object back at every upgrade. The placement of these platform Applications can only be changed by writing the live object, never through the values of the chart, so it cannot be kept in Git.

**What changes.** Each of the eleven charts gets the value bootstrapOwned.intent with two optional fields, placement and regions. A field set there is rendered instead of the live value and the seed; while the value is unset every chart renders exactly what it renders today.

**Done means:**

- Setting the placement or the regions in bootstrapOwned.intent of any of the eleven charts changes that field of the rendered Application, also when a live Application exists.
- Each field is taken on its own: setting only one of them leaves the other to the live value or the seed.
- With the value unset, the Application that each chart renders is byte for byte what it rendered before.
- Each of the eleven charts has a chart test that proves this order against a stand-in live object, and each test fails on the templates of before.
- No chart version, no bootstrap-kit file and no other template changes.

The rest of this ticket is the exact instruction for the model that does the work.

## 2. End goal
Each of the eleven charts whose template `templates/application-cr.yaml` seeds a platform Application (label `apps.openova.io/bootstrap-owned: "true"`) has the value `bootstrapOwned.intent`. A field set there, `placement` or `regions`, is what the chart renders into `spec.placement` or `spec.regions` of that Application, ahead of the live value that the template reads back with `lookup` and ahead of the seed. Nothing sets the value yet: CTL-174 passes the placement committed to Git into each slot through `valuesFrom`, and CTL-176 then removes `lookup`. Until then every chart renders exactly what it renders today. A chart test in each of the eleven charts proves the order against a stand-in live Application.

## 3. The model (the law)
1. **The value.** Each of the eleven values files declares `bootstrapOwned.intent: {}`. Its optional keys are `placement`, in the shape of `spec.placement` (the object `{mode, ...}` that the Application CRD stores, or the bare mode string that it still admits), and `regions`, a list of strings. `platform/cnpg-pair/chart` gates its Application on `cnpgPair.application.enabled` and had no `bootstrapOwned` block: it gets a new top-level `bootstrapOwned` block that holds only `intent`, so the value has the same path in every slot and CTL-174 writes one shape, `bootstrapOwned: {intent: {placement: ..., regions: ...}}`, for each of them.
2. **The order, per field.** For `spec.regions` and for `spec.placement` separately, the template renders the first of: `bootstrapOwned.intent.<field>` when it is set and not empty; the field of the live Application from `lookup` when the object exists and has it; the seed of today. An empty string or an empty list counts as unset (the CRD requires at least one region).
3. **The rendering.** An intent field is rendered with `toJson`, exactly as the live branch renders the live value, so an object and a string both come out as valid YAML.
4. **Unset changes nothing.** With `bootstrapOwned.intent` unset, every render of every one of the eleven charts is byte for byte what it is on `main`.
5. **`lookup` stays.** CTL-176 removes it. Its precondition and acceptance count the files under `platform` and `products` that contain the literal call, so the new tests do not contain that literal (they match it with the escaped pattern `lookup "apps\.openova\.io/v1" "Application"`), and the count stays 11.
6. **Nothing else changes.** No chart version (the release writer sets versions, FND-011), no bootstrap-kit slot (CTL-174), no other template, no existing test.
7. **The tests.** Each chart gets `tests/bootstrap-owned-intent-render.sh`. It renders only the Application, with `--api-versions apps.openova.io/v1` and the values that make the chart render it. Because `helm template` has no cluster and `lookup` finds nothing there, the cases marked live render a copy of the chart in which the `lookup` call is replaced by a fixed live Application (placement `{mode: live-mode}`, regions `[live-region]`). Six cases print `ok: <case>`: intent unset without and with a live object (today's results), both fields set with a live object (intent wins, and nothing else in the render differs), placement alone as a string with a live object, regions alone without a live object, and both set but empty (counted as unset). The test reads the two lines with `grep` and uses no `yq`. When the chart's subcharts are not built it runs `helm dependency build`, as other chart tests do.

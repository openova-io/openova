# SEC-200 — Library chart and namespaced stores for platform namespaces

## In plain words

**The problem today.** A platform chart has no common way to declare the secrets it owns: each hand-writes its own objects, and a value that must reach a pod only as a file has no writer at all. External Secrets cannot create such a value without the right to read it back, and nothing writes a value shared by several regions into each region's store.

**What changes.** One library chart declares a chart's store, its generated values and the shim for images that read only variables. A small job born from the library writes each file-only value once, with create-only rights, into this region's store and, for a shared value, into every other region's store.

**Done means:**

- A chart that lists the library renders its namespace's reader and store, and a refused input fails the render with a message that names it.
- A file-only value renders no Secret, no ExternalSecret and no PushSecret; one job writes it.
- After one run of that job a shared value is present, the same, in every region; a second run writes nothing and fails on no region.
- The job's identity can create values below its own namespace and read nothing: in another region it may only create, and only below its own namespace.
- A region that cannot be reached, or that no longer holds a value this region holds, fails the job and the log names that region.
- The OpenBao chart gives each listed namespace one create-only role per peer region and admits the job on the OpenBao port from every cluster of the mesh.

The rest of this ticket is the exact instruction for the model that does the work.

## 2. End goal
A platform chart lists `platform/secrets-lib/chart` as a file dependency and gets, from three templates, its namespace's External Secrets reader, every value it owns and the entrypoint shim. A tier A value is a Password generator, a PushSecret and an ExternalSecret. A tier B value (`delivery: mounted`) never becomes a Kubernetes object: the birth Job of the chart writes it into OpenBao mount `mounted/` with create-only rights, and for a value shared across regions the primary region's Job writes it into every region's OpenBao itself, the peer regions through bp-openbao's peer trust. The proof runs the rendered Job script against two real OpenBao servers that bp-openbao's own reconciler configured: after one run the shared value is present in both, and a second run changes nothing and fails on no region.

## 3. The model (the law)
1. `platform/secrets-lib/chart/Chart.yaml` is `type: library`, `name: secrets-lib`, `version: 0.1.0`. A consumer lists it with `repository: "file://../../secrets-lib/chart"`; it is never published on its own. `chart/.helmignore` keeps `tests/` out of a consumer's package.
2. `openova.secretStores` (input: the root context) renders exactly ServiceAccount `eso-reader` (`automountServiceAccountToken: false`) and SecretStore `openbao` (vault provider, `path: secret`, `version: v2`, kubernetes auth mount `kubernetes`, role `eso-ns`, service account `eso-reader`). It renders no store for `mounted/`: External Secrets never writes or reads a tier B value.
3. `openova.generatedSecrets` (input: `ctx`, `secrets`, `peers`, `primary`, `self`) for `delivery: mounted` renders no Secret, ExternalSecret, PushSecret or Password. The value's path is `<ns>/sa/<serviceAccount>/<name>/e<epoch>` (`scope: sa`, the default) or `<ns>/shared/<name>/e<epoch>`. Every mounted value of the region is one line of the plan `<path> <length> <symbols> <source> <reach>`; with at least one line the library renders ServiceAccount `secrets-birth` (no token mount), ConfigMap and Job `secrets-birth-<10 hex of the SHA-256 of plan, script, image, peers and address>` (so raising an epoch runs a new Job). The Job runs the image `harbor.openova.io/proxy-dockerhub/curlimages/curl:8.10.1` as user 100, read-only root, all capabilities dropped, with a projected token of audience `openbao`, `backoffLimit: 6` and a pod failure rule that ends the Job on exit code 3.
4. Regions: a value with `sharedAcrossRegions` true (the default) is written by the primary into every region (reach `all`); a region that is not the primary renders nothing for it. A value with `sharedAcrossRegions: false` is written by each region for itself (reach `self`). With no peers every value is reach `self`.
5. The birth script, in order: log in here (role `secrets-birth`); when a line has reach `all`, mint the identity token of role `openbao-peer-birth-<ns>` here and log in at each peer's `auth/jwt-peer-<self>` as role `secrets-birth-<ns>`; check through `sys/capabilities-self` that every region grants `create` on every path. Any failure up to here writes nothing and exits 1 (the Job retries). Then per value: here first, then each peer. Here, metadata version 1 or more is present and is not written. At a peer nothing is readable: a refused write while the token holds `create` is the update of an existing value and counts as present. A peer that accepts a write while the value was already present here was missing it: the run ends with exit 3 and names that region. A failure after something was written exits 3. Every message of a failure names the region.
6. `delivery: synced` renders Password `<name>-e<epoch>` and PushSecret `<name>-e<epoch>` (`updatePolicy: IfNotExists`) into SecretStore `openbao` at `openova/apps/<ns>/<name>/e<epoch>`, plus ClusterSecretStore `vault-<peer>` per peer in the primary, and ExternalSecret `<name>` with annotation `secrets.openova.io/register-id`. A region that is not the primary renders only the ExternalSecret of a shared value. Each `mountedCopies` entry is one plan line of reach `self` whose source is the Secret `<name>` mounted read-only into the Job: no PushSecret writes `mounted/`.
7. `openova.envFromFiles` (input: `map`, `exec`) renders exactly the shim of field 18's test R8: the variable map in a here-document, exit code 78 for a missing file, and the original command shell-quoted after `exec`.
8. The render fails on: a missing or unknown `delivery`; `delivery: synced` without `registerId`; `registerId` on a mounted value; `scope: sa` without `serviceAccount`; `mountedCopies` on a mounted value; a missing epoch or one below 1; a name outside `[a-z0-9-]+`; an unknown scope; `symbols` above `length`; peers without a boolean `primary`; a shared value for peers without `self`; an empty `map` or `exec` of the shim.
9. bp-openbao's desired state gains policy `secrets-birth` (create on `mounted/data/<caller's ns>/*`, read on `mounted/metadata/<caller's ns>/*`, and with peers read on `identity/oidc/token/openbao-peer-birth-<caller's ns>`) and role `secrets-birth` (service account `secrets-birth`, any namespace, audience `openbao`, 15m, at most 1h). With peers, per namespace of `peerTrust.birthNamespaces`: identity role `openbao-peer-birth-<ns>` (key `openbao-peer-push`, client id `openbao-peer-birth-<ns>`, template `{"openova_namespace":"<ns>","openova_region":"<self>"}`, 15m), that client id in the key's `allowed_client_ids`, policy `secrets-birth-peer-<ns>` (only `create` on `mounted/data/<ns>/*`: no read, update or list), and per peer the role `secrets-birth-<ns>` on `jwt-peer-<peer>` (audience `openbao-peer-birth-<ns>`, bound claims `openova_region=<peer>` and `openova_namespace=<ns>`), each policy written before its role. A name that is not a DNS label fails the render.
10. bp-openbao's ingress policy `openbao-allow-peer-region-ingress` admits pods labelled `app.kubernetes.io/name: secrets-birth` of any namespace from any ClusterMesh cluster on 8200. No other policy object changes and the library renders none.
11. No platform chart moves to the namespaced store in this package: no ExternalSecret of a platform chart names a remote key under `openova/apps/<its namespace>/` (field 4), so `legacyKeyMap` and the guard baseline `scripts/secret-guard-baselines/check-reflector-scope.txt` stay as they are.

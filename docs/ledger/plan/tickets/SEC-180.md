# SEC-180 — OpenBao snapshot backup to object storage

## In plain words

**The problem today.** OpenBao keeps every secret of the platform, and nothing copies its store anywhere. If a region loses its OpenBao volumes, every value in it is gone, and the earlier replication job was removed without a replacement.

**What changes.** A scheduled job reads one snapshot of the OpenBao store every six hours and puts it into the Sovereign's bucket under the region's own folder, with an identity that may only read snapshots. It keeps 30 days of snapshots, and the runbook says how to restore one.

**Done means:**

- With the backup switched on, a run puts one snapshot into the bucket under the region's folder, named by its UTC time, byte for byte as OpenBao gave it.
- The job's OpenBao identity may read the snapshot endpoint and nothing else, and its token is revoked at the end of the run.
- A run deletes this region's snapshots older than 30 days and no other object, and only after the new snapshot reads back at its full size.
- A refused login, a bucket key the bucket does not accept, or a missing bucket name fails the run and deletes nothing.
- Nothing of the backup renders while it is switched off, which is the default.
- The runbook gives the five steps of a restore and where the seal key comes from.

The rest of this ticket is the exact instruction for the model that does the work.

## 2. End goal
The chart `platform/openbao/chart` (bp-openbao) renders, when the new value `backup.enabled` is true (default false) and `kubernetesAuth.enabled`, the ServiceAccount `openbao-backup`, the ConfigMap `openbao-backup-script` and the CronJob `openbao-backup` in the release namespace (new template `templates/backup-snapshot.yaml`). Every `backup.schedule` (default `17 */6 * * *`, UTC) a run logs in on the Kubernetes auth mount as role `openbao-snapshot` with a projected service-account token for audience `openbao`, reads one raft snapshot from `sys/storage/raft/snapshot`, puts it at `s3://<backup.bucket>/<backup.prefix><peerTrust.selfRegion>/<UTC time>.snap` (prefix default `openbao/`, time `YYYYMMDDTHHMMSSZ`, the layout of ADR-0036 B1 and B2), reads its size back, deletes this region's snapshots older than `backup.retentionDays` (30) and revokes its token. The configuration's desired state (`templates/_config.tpl`) writes the policy `openbao-snapshot` (read on `sys/storage/raft/snapshot` only) and binds the role `openbao-snapshot` to `openbao/openbao-backup` with the backup. A new chart test `tests/backup-render.sh` runs the rendered script for real against a fake OpenBao and a fake bucket that verifies every request's AWS signature version 4. `docs/RUNBOOKS.md` section 2.18 "Restore OpenBao" gives the restore. The kit switches the backup on in SEC-181, which also adds the restore drill.

## 3. The model (the law)
1. **Values** (`platform/openbao/chart/values.yaml`, block `backup`): `enabled` false, `schedule` `"17 */6 * * *"`, `bucket` `""`, `bucketSecretName` `object-storage`, `prefix` `openbao/`, `retentionDays` 30, `image` `harbor.openova.io/proxy-dockerhub/curlimages/curl:8.10.1` (the image the harbor, gitea and kyverno charts already use). No chart version change.
2. **Off by default.** With `backup.enabled` false, or with `kubernetesAuth.enabled` false, nothing of the backup renders: no ServiceAccount, ConfigMap or CronJob `openbao-backup*`, and the desired state has neither policy nor role `openbao-snapshot`. The configuration's render test (`tests/config-desired-render.sh` C1) refuses the policy and the role in the default render; this ticket does not change that test.
3. **Identity.** ServiceAccount `openbao-backup`, `automountServiceAccountToken: false`, on the ServiceAccount and on the pod. The pod's only OpenBao credential is a projected service-account token, audience `openbao`, 600 seconds, at `/var/run/secrets/openbao/jwt`. With the backup on, the desired state writes `sys/policies/acl/openbao-snapshot` with the text of the existing definition `openbao.policy.openbao-snapshot` (exactly one path, `sys/storage/raft/snapshot`, capability `read`), after the earlier policies, and `auth/<kubernetesAuth.mountPath>/role/openbao-snapshot` with `bound_service_account_names` `["openbao-backup"]`, `bound_service_account_namespaces` `[<release namespace>]`, `policies` `["openbao-snapshot"]`, `ttl` and `max_ttl` `15m`, `audience` `openbao`, after every policy.
4. **The bucket key.** Secret `backup.bucketSecretName` in the release namespace is mounted read-only at `/etc/openbao-backup/bucket` with exactly the keys of the object-storage Secret: `s3-endpoint` (a URL), `s3-region`, `s3-access-key`, `s3-secret-key`. No env entry reads a Secret, and no env name contains PASSWORD, TOKEN, KEY or SECRET (Kyverno policy `secret-not-in-env`). The key pair and the OpenBao token reach curl on its standard input (`curl -K -`), never as an argument.
5. **A run** (`backup.sh` of the ConfigMap, POSIX shell, run by the image's `/bin/sh`). It ends non-zero with a line `openbao-backup: FATAL: ...` on the first failure: an empty `BUCKET` or `REGION` or a `RETENTION_DAYS` that is not a whole number (before any request), a missing key file, a refused login, a failed or empty snapshot read, a failed put, a size read back that differs from the size put, a failed listing, a failed delete. Order: login, snapshot read into `/work`, put (`curl -T`, signed with `--aws-sigv4 "aws:amz:<s3-region>:s3"`, path-style `<s3-endpoint>/<bucket>/<key>`), HEAD of the new object, listing (`list-type=2`, `prefix=<prefix><region>/` URL-encoded), deletes. The token is revoked (`auth/token/revoke-self`) when a run that logged in ends, also on failure.
6. **Retention.** Only a key `<prefix><region>/<8 digits>T<6 digits>Z.snap` whose time is older than now minus `retentionDays` days is deleted. Another region's snapshot, a key of another shape and a key outside the prefix are never deleted, and nothing is deleted before the new snapshot read back at its full size.
7. **CronJob.** `timeZone: Etc/UTC`, the Job label `app.kubernetes.io/managed-by: flux` (the Job is not an object of the release, and Kyverno policy `flux-managed` admits it by this label), `concurrencyPolicy: Forbid`, `startingDeadlineSeconds: 3600`, three successful and three failed Jobs kept, `backoffLimit: 2`, `activeDeadlineSeconds: 1800`, `restartPolicy: Never`, non-root user 100 group 1000, read-only root filesystem, no capabilities, RuntimeDefault seccomp, requests 10m and 32Mi, limits 500m and 128Mi, `/work` an emptyDir of at most 2Gi.
8. **The test** `tests/backup-render.sh` prints `  PASS  B1 ` to `  PASS  B5 ` (law 2; laws 3, 4 and 7; law 3's desired state; one real run of the rendered script; the three failures of law 5) and needs curl, go, yq and helm. Its fake is a Go program written by the test into its temporary directory and built with `go build`: under `/v1/` it answers as OpenBao (login, snapshot, revoke-self); elsewhere it is an S3 bucket on a local directory that verifies the AWS signature version 4 of each request with the key pair of the test's bucket Secret and refuses a request it cannot verify. The test runs the script with the host's curl behind a shim that records curl's arguments. No Python.
9. **Runbook.** `docs/RUNBOOKS.md` section `### 2.18 Restore OpenBao`, after section 2.17: the backup, where the seal key comes from (contract C8: the node file, recovered from the encrypted infrastructure state), and five steps: choose the snapshot, place the seal key, install with `selfInit.enabled: false` and initialise once, `bao operator raft snapshot restore -force`, verify a known key and set `selfInit.enabled` back. No provider name.

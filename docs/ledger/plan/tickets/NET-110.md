# NET-110 — Cilium base values to target

## In plain words

**The problem today.** The shared Cilium chart carries the control-plane address of one cloud and a routing range that is right only for one or two regions. A Sovereign with three or more regions would send part of its pod traffic through address translation. The chart also ships three mesh files that Cilium never reads, and its notes name an upstream release it does not bundle.

**What changes.** The chart has no address and no range of its own. Each Sovereign gets both from its variables: the address the node detects at first boot, and the pod supernet that the provider module computes. A release that names an API host and no range is refused with a clear message. Four Hubble metrics are on, and the stale mesh files and version notes are gone.

**Done means:**

- The Cilium chart folder holds neither the fixed control-plane address nor the fixed two-region range outside its history notes.
- A new Sovereign with one or two regions routes 10.42.0.0/15 natively, and one with three to six regions 10.40.0.0/13, both in the Cilium that first boot installs and in the Cilium that Flux installs.
- A Cilium release that names an API host and no routing range does not render, and the error names the missing key.
- The chart still renders with its own values, so the release workflow and the chart lint keep working.
- Every agent serves the Hubble metrics dns, drop, flow and policy, and no ServiceMonitor is rendered for them.
- The three mesh files that Cilium never read are deleted and listed as deleted, and the test and the two documents that pointed at them are corrected.

The rest of this ticket is the exact instruction for the model that does the work.

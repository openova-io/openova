# SEC-020 — Random k3s server token and separate agent token

## In plain words

**The problem today.** Every new Sovereign's cluster join secret is computed from two identifiers, the cloud project and the domain name. Anyone who knows both can compute it and join a machine to the cluster as a control node. Workers receive the same secret as the control nodes, and the cluster also uses this secret to protect its database encryption key, so that protection is worth nothing while the secret can be computed.

**What changes.** Each region of a new Sovereign gets two random secrets, kept in the provisioning state: one for the control nodes and one that workers join with. The first-boot file starts the control node with both, and workers only ever receive the second.

**Done means:**

- No file under the infrastructure folder computes a join secret from the project or the domain name.
- Both cloud modules create a random 64-character server secret and a random 64-character agent secret for every region.
- The rendered first-boot file of a control node holds the server secret and passes the agent secret with the agent-token flag.
- The rendered first-boot file of a worker holds the agent secret and not the server secret, which the module tests of both clouds assert.
- The stored fingerprints of the rendered first-boot file are updated, and the check named golden is green on the pull request.
- The module tests, the size check and the shell lint of the first-boot file pass on the pull request.

The rest of this ticket is the exact instruction for the model that does the work.

## 2. End goal
A Sovereign provisioned after this change has, in every region, two random tokens of 64 letters and digits: a server token and an agent token. They are `random_password` resources of the provider module, so they are stored in the OpenTofu state and stay the same on a re-apply. The control-plane node starts k3s with `K3S_TOKEN` set to the server token and with the flag `--agent-token` set to the agent token. Workers join with the agent token, and their boot data never holds the server token. No token is computed from the project identifier or the domain name any more. A person sees the result on the pull request: the module tests of both clouds pass with a new run that asserts which token each node receives, and the check `golden` is green with new stored fingerprints of the rendered cloud-init.

## 3. The model (the law)
1. Each provider module declares two resources, `random_password.k3s_server_token` and `random_password.k3s_agent_token`. Each has `for_each` over the module's region keys, `length = 64` and `special = false`, so the value has letters and digits only. The region keys are `toset(local.all_region_keys)` in `infra/providers/hetzner/main.tf` (the key `primary` and every secondary key) and `toset(local.region_keys)` in `infra/providers/huawei/main.tf` (the region codes).
2. The shared template `infra/providers/_shared/cloudinit-control-plane.tftpl` starts the k3s server with `K3S_TOKEN=${k3s_server_token}`, and its server flags hold ` --agent-token=${k3s_agent_token}` directly before `${k3s_extra_args}`. The template no longer reads `k3s_token`.
3. Every call that renders the shared template passes `k3s_server_token` and `k3s_agent_token` of its own region: in the Hetzner module the key `primary` for the primary control plane and the key `k` for each secondary; in the Huawei module the key `r.code`. Every call that renders a worker template passes the agent token of its own region under the existing name `k3s_token`. The two worker templates do not change.
4. The derived value `sha256("<project id>/<domain name>/k3s-bootstrap")` is deleted: the local value `k3s_token` of the Hetzner module with its two comment lines, and the two expressions in the Huawei module.
5. Both modules require the provider `hashicorp/random` with the constraint `~> 3.6`. Both lock files carry its entry for version `3.9.1`.
6. Every fixture that renders the shared template passes the two new inputs: `infra/providers/_shared/tests/render.tf`, `scripts/cloudinit-size-check.sh` and `scripts/lint-cloudinit.sh`. Without them the render fails, because the template reads a name that the fixture does not set. The stored fingerprints in `infra/providers/_shared/tests/golden.auto.tfvars.json` are the values that `scripts/update-cloudinit-golden.sh` writes for the changed render.
7. The module tests of both clouds give the two resources fixed values with `override_resource`. Without that, the plan does not know the random values, the rendered cloud-init is unknown, and every assertion on it cannot be evaluated. Each module test gains the run `k3s_server_and_agent_tokens`, which asserts which token the control plane and the workers receive.
8. `infra/providers/PROVIDER-INTERFACE.md` section 5 gains the rule "Random cluster tokens".
9. Not in this change: the flag `--write-kubeconfig-mode=0644` (package SEC-040), the encryption flags of etcd (package SEC-030), the k3s version, the worker templates, and Sovereigns that already run (package SEC-170).

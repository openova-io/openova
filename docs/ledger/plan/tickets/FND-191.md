# FND-191 — Remove the second matcher's job handling from the API

## In plain words

**The problem today.** The platform keeps one vulnerability matcher, Trivy. The API still carries special handling for the job of a second matcher, Syft with Grype: it folds that CronJob's runs onto a made-up row, hides the CronJob's own row, and re-runs the made-up row through that CronJob when a person clicks Re-run. That code serves a matcher the platform removes, and it is a reader that must go before the matcher's chart can be deleted.

**What changes.** The API treats the second matcher's CronJob like every other CronJob: its runs appear under its own schedule row. Only Trivy's scan runs still fold onto one row, and the code, constants and tests that named the second matcher are gone.

**Done means:**

- The API's job listing, retry, schedule and bridge code and their tests name neither Syft nor Grype.
- The Trivy scan runs still fold onto one row, and a Re-run of that row still answers that it cannot be re-run directly.
- Runs of any other CronJob fold onto that CronJob's own row.
- The test file that existed only for the second matcher's retry is deleted and listed in the deleted paths.
- The API builds, and its vet, format and tests of the three changed packages pass.

The rest of this ticket is the exact instruction for the model that does the work.

## 3. The model (the law)

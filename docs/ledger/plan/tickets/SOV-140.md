# SOV-140 — Substrate window, part 2: revocable bootstrap access, peer tokens, node artifacts from the registry

## In plain words

**The problem today.** When a new Sovereign boots, its first control plane sends the node's own administrator kubeconfig to the parent that provisioned it. That credential is a client certificate signed by the cluster's own authority. It cannot be revoked, so the parent keeps full access to the Sovereign for as long as the certificate is valid, also after the hand-over.

**What changes.** The boot script creates a service account with cluster-admin rights and a token, and sends the parent a kubeconfig that carries that token instead of the administrator file. Deleting the service account ends the parent's access. The node's administrator file never leaves the node.

**Done means:**

- On a new Sovereign the boot script creates the ServiceAccount kube-system/parent-bootstrap, its cluster-admin binding and its token Secret before it posts the kubeconfig back.
- Every kubeconfig post-back of the Hetzner and the Huawei module sends the kubeconfig of that account, never /etc/rancher/k3s/k3s.yaml.
- The kubeconfig file the boot script writes for the post-back, and every copy of it under /tmp, is deleted right after the post-back.
- If the token does not appear, the boot script stops with exit code 96 and leaves the sentinel parent-bootstrap-FAILED.
- The render tests of the boot template and of the Huawei module fail when any of this is missing, and the stored golden render values match the changed template.

The rest of this ticket is the exact instruction for the model that does the work.

## 2. End goal
A new Sovereign gives its parent a credential that can be taken back. Right after the API server is healthy and before the kubeconfig post-back, cloud-init applies three objects with the node's administrator kubeconfig: the ServiceAccount `kube-system/parent-bootstrap`, the ClusterRoleBinding `parent-bootstrap` that binds it to the ClusterRole `cluster-admin`, and the Secret `kube-system/parent-bootstrap-token` of type `kubernetes.io/service-account-token`. It waits until Kubernetes has written the token into that Secret, and writes `/var/lib/catalyst/parent-bootstrap.kubeconfig`: the node's `/etc/rancher/k3s/k3s.yaml` without its client-certificate lines, with that token as the credential of its one user. Every kubeconfig post-back of the Hetzner module and of the Huawei module, primary and secondary region alike, sends that file and never `/etc/rancher/k3s/k3s.yaml`. The item right after the post-back deletes the file. Deleting the ServiceAccount later revokes the parent's access, which the administrator certificate never allowed. This ticket is the first part of the package: the peer token for the hand-over and the node artifacts from the registry are later parts (field 11).

## 3. The model (the law)
1. The new runcmd item stands in the shared template `infra/providers/_shared/cloudinit-control-plane.tftpl`, inside the block `%{ if deployment_id != "" && kubeconfig_bearer_token != "" && catalyst_api_url != "" ~}` that holds the post-back, directly before the line `  ${indent(2, kubeconfig_put_block)}`. It runs after the API server answered `/healthz` and before gateway-api, Cilium and Flux, like the post-back itself. A render without a post-back (no deployment identifier, bearer token or API address) has no such item.
2. The item applies one stream of three objects with `kubectl apply`: ServiceAccount `parent-bootstrap` in `kube-system`; ClusterRoleBinding `parent-bootstrap` with `roleRef` ClusterRole `cluster-admin` and one subject, that ServiceAccount; Secret `parent-bootstrap-token` in `kube-system`, type `kubernetes.io/service-account-token`, annotation `kubernetes.io/service-account.name: parent-bootstrap`. Kubernetes writes the token of such a Secret itself, and that token has no expiry. The item tries at most 60 times, 2 seconds apart, until the Secret holds a token.
3. Each document of the stream starts with the key line `apiVersion:`, never with `{`: `kubectl` reads a document that starts with `{` as JSON, and the flow mappings of the stream are not JSON.
4. The kubeconfig is `/etc/rancher/k3s/k3s.yaml` with every line that contains `client-` removed (that is `client-certificate-data` and `client-key-data`), written with umask `077` (mode `0600`), and then `kubectl config set-credentials default --token=<token>` on that file. Its cluster, its certificate authority, its context and its `server: https://127.0.0.1:6443` line stay as in `k3s.yaml`, so the server rewrite of each post-back block works unchanged.
5. If no token appears after the 60 tries, or the file cannot be written, the item runs `sh /var/lib/catalyst/mark parent-bootstrap-FAILED`, or `touch /var/lib/catalyst/parent-bootstrap-FAILED` where the mark helper is absent, and exits with code 96. Code 96 is used nowhere else in the template or the two modules (pre-flight P4). The item names no provider: the shared template's provider-leak count must not rise.
6. The runcmd item right after `  ${indent(2, kubeconfig_put_block)}` is `  - rm -f /var/lib/catalyst/parent-bootstrap.kubeconfig`.
7. Hetzner, both post-back blocks of `infra/providers/hetzner/main.tf` (the local `kubeconfig_put_block_hetzner_primary` and the secondary region's inline block): the public address replaces `127.0.0.1` in `/var/lib/catalyst/parent-bootstrap.kubeconfig` in place (`sed -i`), and `curl --data-binary` sends that file. The three items that made and removed `/etc/rancher/k3s/k3s.yaml.public` are deleted. Route, method, headers and retry flags are unchanged.
8. Huawei, both branches of the post-back block of `infra/providers/huawei/main.tf`: the `sed` that rewrites the server address reads `/var/lib/catalyst/parent-bootstrap.kubeconfig` instead of `/etc/rancher/k3s/k3s.yaml`. The primary branch deletes `/tmp/kubeconfig-rewritten.yaml` after its attempts; the secondary branch deletes `/tmp/kubeconfig-secondary.yaml` together with the body file it deletes today. Route, method, headers, retries, fail-loud lines and payload keys are unchanged.
9. The render test `infra/providers/_shared/tests/cloudinit_render.tftest.hcl` gains two asserts in each of the runs `hetzner_render_is_valid` and `huawei_render_is_valid`: the three objects are rendered; the kubeconfig is written before the post-back and deleted directly after it.

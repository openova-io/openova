# NET-098 — The Hetzner storage node plugin is allowed to read instance metadata

## In plain words

**The problem today.** The platform is about to deny every pod the instance metadata address of its node. The storage driver of the second cloud reads its server identity and zone from that address when it starts, and exits without them, so the deny would stop storage on that cloud. The exception that the secret guard demands cannot be written into the shared register, because that file may not name a cloud provider.

**What changes.** The node pods of that storage driver carry the one exception label of the deny, and the exception is recorded in a file beside the chart. The secret guard accepts such a record in the chart's own folder, and still refuses the label when there is no record.

**Done means:**

- The storage chart of the second cloud renders its node pods with the exception label, and its controller pods without it.
- The chart's folder holds one exception record that names the node workload, its reason and its review date.
- The shared register has no entry for this chart, so it still names no cloud provider.
- The secret guard passes on the repository, and fails when the label is there and the record is not.
- The guard refuses a record that is malformed, that names another chart, or that repeats an entry of the register, and its self-test proves each of these.
- Nothing changes on a running Sovereign yet: the deny is switched on by a separate task after this chart is published.

The rest of this ticket is the exact instruction for the model that does the work.

## 2. End goal
The node plugin of `bp-hcloud-csi` (the DaemonSet `hcloud-csi-node` of the upstream subchart, kit slot 55a, on the pod network) carries the pod label `network.openova.io/metadata-access: "true"`, the one exception of the object `baseline-deny-metadata` of `bp-network-policies`. Once package NET-096 switches that deny on, the node plugin still reads its server ID and zone from `169.254.169.254` and keeps running. The exception is recorded in a new file of the chart's own folder, `platform/hcloud-csi/chart/metadata-access.yaml`, and not in the shared register `scripts/secret-guard-baselines/secret-object-register.yaml`: a register entry for this chart names the provider in its `chart` line, and the provider-leak guard refuses that in a shared file. Rule e of guard G10 (`scripts/secret-object-register.py`) therefore accepts the exception of a chart in either place, refuses a chart that has it in both, refuses a malformed record, and still refuses the label when neither place has it.

## 3. The model (the law)
1. The label is set once, in `platform/hcloud-csi/chart/values.yaml`, as `hcloud-csi.node.podLabels` with the one key `network.openova.io/metadata-access` and the string value `"true"`. The upstream subchart writes `node.podLabels` into the pod template of the DaemonSet `hcloud-csi-node` and not into its selector. The controller Deployment `hcloud-csi-controller` gets no label.
2. The record `platform/hcloud-csi/chart/metadata-access.yaml` holds exactly one field, `metadataAccess`: a list with one entry of the register's form, the five fields `chart: platform/hcloud-csi/chart`, `workload: hcloud-csi-node`, `reason` (a text that says why), `removal: none` and `reviewBy: "2027-11-01"`. The node plugin cannot run without the address in upstream release 2.13.0, so there is no removal package.
3. Rule e of guard G10, as changed: a chart whose templates or `values.yaml` carry the label in the counted form has its exception in one place, not two: an entry of `metadataAccess` in the register, or the record `metadata-access.yaml` in the chart's own folder. The record is read only for an own chart and only when it is a tracked file. Rule e fails when the record is not YAML; when it does not hold exactly the field `metadataAccess` with a list of at least one entry; when an entry lacks a field, has a field too many, has an empty text, a `removal` that is neither `none` nor a package identifier, or a `reviewBy` that is not a date; when an entry's `chart` is not the record's own chart folder; and when the register also has an entry for that chart. A record with any of these faults does not count as an exception, so the label of that chart fails as well.
4. The form check of one `metadataAccess` entry moves into a function of its own, `access_problems`, used by rule a for the register and by rule e for a record. Rule a judges the register exactly as before: same fields, same messages, and its own check that the `chart` of a register entry is an own chart.
5. The lines that guard G10 prints when it passes do not change, and the register file does not change: its `metadataAccess` stays `[]`.
6. The guard's self-test gains nine cases, one per new rule: the label with a valid record passes; seven faulty records fail (another chart, a missing field, an unknown field, a removal that is not a package, an empty list, a second top-level field, text that is not YAML); a chart with an entry in the register and a record fails. Every case the self-test had before stays and passes.
7. No version line changes: not `version:` in `platform/hcloud-csi/chart/Chart.yaml`, not `spec.version` in `platform/hcloud-csi/blueprint.yaml`, not the pin `version: 1.2.2` of kit slot 55a.

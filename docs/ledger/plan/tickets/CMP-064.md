# CMP-064 — Validate policies to ValidatingPolicy, batch 3 (7 policies)

## In plain words

**The problem today.** Seven policies of the policy chart, two of them with cluster lookups, are still written in the engine's legacy policy kind, which the engine line after the current one no longer serves. No test proves what any of them admits or refuses. The test that proves the engine may read what a lookup needs understands only the legacy lookups, through a Python helper.

**What changes.** The seven policies are written in the new kind, in the same files and under the same names, each with a test suite that was green on the legacy policy and is green on the new one with the same resources. The lookup test reads the lookups of the new kinds, runs without Python, and fails when a legacy lookup is left.

**Done means:**

- The policy chart renders nineteen ValidatingPolicy objects; the seven new ones are pdb-permits-eviction, pvc-volume-expansion, cilium-l7-mtls, prometheus-scrape, networkpolicy-present, otel-injected and backup-configured.

- No Python file is left among the policy chart's tests.
- The legacy policy guard counts 26 objects, and seven more checks leave the list of checks without a suite.

## 3. The model (the law)
1. **In place.** Each of the seven templates keeps its path, its `metadata.name`, its labels and annotations (the read model reads title, severity and description from them), its values keys under `compliancePolicies.<key>`, its `enabled` switch and every exclusion. Nothing a policy checks changes; no two policies merge.
2. **Shape.** The shape of CMP-062 and CMP-063: `apiVersion: policies.kyverno.io/v1`, `kind: ValidatingPolicy`; `spec.validationActions` from the helper `bp-kyverno-policies.actions` for all seven (each legacy policy took its action from the helper `bp-kyverno-policies.action`, so each follows the bootstrap window as before); `spec.evaluation.background.enabled: true`; `spec.matchConstraints.resourceRules` with operations `CREATE` and `UPDATE` on the kinds the legacy rule matched (PodDisruptionBudgets; PersistentVolumeClaims; Deployments, StatefulSets and DaemonSets; Namespaces); namespace exclusions as a match condition from the helper `bp-kyverno-policies.excludeNamespacesExpr`; the checks as CEL `validations`. No automatic generation of controller rules: none of the seven matches Pods.
3. **Cluster lookups.** `pvc-volume-expansion` reads the claim's StorageClass with `resource.Get("storage.k8s.io/v1", "storageclasses", "", object.spec.storageClassName)`; `networkpolicy-present` lists the NetworkPolicies and the CiliumNetworkPolicies of the namespace with `resource.List`. These replace the legacy `context.apiCall` entries with the same URL paths. A claim that names a StorageClass that does not exist gets the result `error`, the same as the legacy rule, whose failed GET gave `error` (case 4 of the suite `pvc-volume-expansion`). The reads come from the existing ClusterRoles of `templates/rbac-storageclass-read.yaml` and `templates/rbac-cilium-read.yaml` and from the role `view` that the engine binds; no rendered rule of a ClusterRole changes (only the template comments).
4. **Same verdicts.** Each suite was written and run on the legacy render first (tool v1.19.2) and was green there; the two lookup suites read the tool's fake cluster on both kinds. Then only `policy.yaml` (the new render) and one key of each result (`rule: <name>` became `isValidatingPolicy: true`) changed; the resources and the expected results are the same, and the suite is green. Flipping any single expected result of the seven suites (52 results) turns its suite red. No resource of `tests/fixtures/` is edited.
5. **The lookup test.** `tests/apicall-rbac-correspondence.sh` renders the chart and fails when C1 a lookup does not name its apiVersion and resource as two string literals, or is a function other than `Get` and `List`; C2 the render holds no lookup; C3 a controller that evaluates the policy's kind cannot read the looked-up resource with the verb of the call (`get` for `resource.Get`, `list` for `resource.List`) through its upstream roles or a ClusterRole of the render aggregated to it by the label `rbac.kyverno.io/aggregate-to-<controller>: "true"`, or the kind has no controllers in the test; C4 the render holds a legacy `apiCall` (`urlPath`). Its self-test proves each check can fail (10 cases). It uses helm, yq and the shell; the Python helper `_apicall_groups.py` is deleted, and no Python line is added anywhere.
6. **Current copies.** `tests/suites-current.sh` lists the seven suites in `SUITES` and prints `ALL PASS: 19 suites current`; its self-test still passes 10 cases.
7. **Baselines.** `scripts/baselines/kyverno-legacy.json` loses the seven template entries (33 to 26 objects); `scripts/baselines/policy-suites.json` loses the seven checks that now have a suite.
8. **Network guard exceptions.** The two files of the suite `networkpolicy-present` that hold NetworkPolicy and CiliumNetworkPolicy objects (`cluster-resources.yaml`, and the kind definition `ciliumnetworkpolicy-crd.yaml`) are read only by the tool and never applied. Guard G2 of `scripts/check-network-guards.py` allows a policy object outside the policy chart only in a file named in `scripts/network-guards-exceptions.tsv`, so the two files get a line each with owner CMP-064 and their reason.
9. **One difference, by convention.** The legacy rules named no operation; the new policies match `CREATE` and `UPDATE` only, so a `DELETE` request is no longer judged, as in CMP-062 and CMP-063.

# FND-156 — The conformance account exists on every Sovereign

## In plain words

**The problem today.** A gate check asks each Sovereign for a token of the conformance account, and catalyst-api trusts that account by default, but nothing creates the account. The check is therefore red on every Sovereign, and the conformance Job that will run the suite inside a Sovereign has no account to run under.

**What changes.** The platform chart that every Sovereign installs creates the conformance account with the smallest set of cluster rights the suite needs to judge itself and write its report. A chart test holds those rights to exactly that set.

**Done means:**

- A fresh render of the platform chart in catalyst-system holds the ServiceAccount catalyst-conformance in catalyst-system, a ClusterRole catalyst-conformance and a ClusterRoleBinding that binds the one to the other.
- The ClusterRole holds six rules and no more: reads of Helm releases, Pods, Services, Nodes and Namespaces, a read of the one Kyverno definition and of the one NodePort policy by name, and the write of policy reports.
- The account can read no Secret and cannot exec into a Pod, and no rule holds a wildcard.
- The chart test fails when a rule is added or loses its name, when the binding names another subject, when another binding gives the account a right, when catalyst-api no longer names the account as a caller, or when the gate check asks for another account.
- Every other chart test of the platform chart still passes.

The rest of this ticket is the exact instruction for the model that does the work.

## 3. The model (the law)
1. **One account, in the release namespace.** The ServiceAccount `catalyst-conformance` has `namespace: {{ .Release.Namespace }}`; slot 13 installs the chart with `targetNamespace: catalyst-system`. The file is Helm only, like `templates/clusterrolebinding-cutover-driver.yaml`; `templates/kustomization.yaml` does not list it, so the raw Kustomize build of the mothership is unchanged.
2. **Exactly six rules, the ones the local pack gives the account (FND-155).** In `.github/workflows/conformance-local.yaml` the run in self gives `catalyst-system/catalyst-conformance` these rules, and the ClusterRole holds them, no more and no fewer:
   1. `helm.toolkit.fluxcd.io` `helmreleases`: `get`, `list`, `watch`;
   2. core `pods`, `services`, `nodes`: `get`, `list`, `watch`;
   3. core `namespaces`: `get`, `list`;
   4. `apiextensions.k8s.io` `customresourcedefinitions`, only `clusterpolicies.kyverno.io`: `get`;
   5. `kyverno.io` `clusterpolicies`, only `forbid-nodeport-service`: `get`;
   6. `wgpolicyk8s.io` `clusterpolicyreports`: `get`, `create`, `update`, `patch`. `create` cannot be limited by name, because a create has no name to match yet.
3. **A ClusterRole, not a Role.** Nodes, namespaces, a definition, a cluster policy and a cluster report are all cluster-scoped.
4. **Least privilege.** No Secret, no `pods/exec`, no wildcard in any field, no aggregation. One binding of the ClusterRole, the ClusterRoleBinding `catalyst-conformance`, with the one subject `ServiceAccount catalyst-system/catalyst-conformance`; no other binding of the chart names the account.
5. **No new slot, no Job, no change to the caller entry.** The default `agentTokens.callers` entry of `values.yaml` and the literal of `templates/api-deployment-kustomize.yaml` stay as they are; they already name the account.
6. **The test proves each rule can fail.** The chart test checks the render against laws 1 to 4, that the rendered `CATALYST_AGENT_TOKEN_CALLERS` of catalyst-api names the account, and that check AIP-G07 (`aipG07NS`, `aipG07SA`) asks for this account; for each rule it changes a copy of the render and shows that the test then fails with that rule's message.

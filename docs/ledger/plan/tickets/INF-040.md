# INF-040 — Chart bp-kured with the node patch configuration

## In plain words

**The problem today.** The platform's nodes install operating-system updates, but nothing reboots them in a controlled way, and nothing owns the setting that decides whether a node may reboot itself. A node can therefore stay on an old kernel for ever, or reboot on its own at any hour.

**What changes.** A new chart installs kured, which reboots one node at a time inside a reboot span and never a node on which a Kubernetes upgrade runs, and a small DaemonSet that writes the same unattended-upgrade settings on every node: install security updates, never reboot by yourself.

**Done means:**

- The repository has a chart bp-kured that wraps the upstream kured chart 6.1.0 and sets one node at a time, the span 00:30 to 22:00 UTC, a 15-minute drain limit and the narrow blocking selector as its defaults.
- The chart writes the two unattended-upgrade files on every node, rewrites a file only when it differs, and the second file says Automatic-Reboot false.
- The chart's own test checks the file bodies byte for byte, every kured argument, the write loop and the function test, and passes on the pull request.
- The chart carries a function test that a person can run with helm test on a cluster.
- The generated catalogue lists bp-kured as unlisted, and the catalogue, seed-coverage and service-model checks stay green.

The rest of this ticket is the exact instruction for the model that does the work.

## 2. End goal
The repository holds a new Blueprint folder `platform/kured` with the chart `bp-kured` 0.1.0. The chart wraps the upstream chart `kured` 6.1.0 (kured 1.23.0) of `https://kubereboot.github.io/charts`. ## 3. The model (the law)
1. **The chart.** `platform/kured/chart/Chart.yaml`: name `bp-kured`, version `0.1.0`, `appVersion: "1.23.0"`, `type: application`, one dependency `kured` version `6.1.0` from `https://kubereboot.github.io/charts`. The version 6.1.0 is the release measured beside the system-upgrade-controller in `docs/ledger/plan/spikes/INF-030.md`.
2. **The kured values**, under the key `kured:` of `values.yaml`: `fullnameOverride: kured` (the DaemonSet and its lock annotation `weave.works/kured-node-lock` are named `kured` whatever the release is called); `rebootSentinel /var/run/reboot-required`; `period 15m`; `concurrency 1`; `startTime "00:30"`; `endTime "22:00"`; `timeZone UTC`; `rebootDays` all seven days; `drainTimeout 15m`; `lockTtl 1h`; `lockReleaseDelay 5m`; `annotateNodes true`; `blockingPodSelector` the one item `upgrade.cattle.io/controller=system-upgrade-controller,upgrade.cattle.io/plan`; `tolerations` the one item `operator: Exists`. The reboot command stays the upstream default `/bin/systemctl reboot`. The selector has two keys because the system-upgrade-controller's own Pod carries the first label too; with one key, kured never reboots the node of that Pod (`docs/ledger/plan/spikes/INF-030.md`, section "Findings beyond the six questions").
3. **node-patch-config.** `templates/node-patch-config.yaml` renders a ConfigMap and a DaemonSet, both named `node-patch-config`, in the release namespace. The ConfigMap holds the two files of rule 4 byte for byte. The DaemonSet tolerates every taint, runs on every Linux node, mounts no API token, and has one container whose image is `nodePatchConfig.image`. Its only host mount is `/etc/apt/apt.conf.d`, writable, at `/host`; the ConfigMap is mounted read-only at `/config`. The container runs as root (root owns the directory) with no capability, no privilege escalation and a read-only root file system. Its loop compares each file with `cmp`, writes a differing file through a temporary name ending in `.dpkg-tmp` (apt ignores that name) and an atomic `mv`, and then sleeps one hour.
4. **The two files.**
```text
/etc/apt/apt.conf.d/20auto-upgrades
APT::Periodic::Update-Package-Lists "1";
APT::Periodic::Unattended-Upgrade "1";
APT::Periodic::AutocleanInterval "7";

/etc/apt/apt.conf.d/52unattended-upgrades-catalyst
Unattended-Upgrade::Allowed-Origins { "${distro_id}:${distro_codename}-security"; "${distro_id}ESMApps:${distro_codename}-apps-security"; "${distro_id}ESM:${distro_codename}-infra-security"; };
Unattended-Upgrade::Automatic-Reboot "false";
Unattended-Upgrade::Remove-Unused-Kernel-Packages "true";
Unattended-Upgrade::Remove-Unused-Dependencies "true";
```
5. **The image.** `nodePatchConfig.image` defaults to `""`. The chart writes no registry host name: the kit slot (INF-050) sets the image with the Sovereign's registry prefix. With the value empty the chart still renders, so that the release workflow's default-values smoke render passes and the chart can be published; the install of such a release fails, because the DaemonSet has a container without an image. The render test proves that the default render leaves the image empty.
6. **The function test.** `templates/tests/function-test.yaml` follows `docs/RUNBOOKS.md` section 4.5 (`scripts/check-function-test.py` passes on it). It renders a ServiceAccount, a Role that may only `get` the DaemonSet `kured`, a RoleBinding and the Pod `<release>-function-test`, image `nodePatchConfig.image`, non-root. The Pod passes when the DaemonSet `kured` has as many ready Pods as it has nodes to run on, and at least one, and when its own node has both files under `/etc/apt/apt.conf.d` (read through a read-only host mount) equal byte for byte to the ConfigMap. The file uses no ClusterRole: rule FT4 of `scripts/check-function-test.py` allows only ServiceAccount, Role, RoleBinding and network policies besides the Pod, so the test compares with the DaemonSet's own count of nodes to run on, which is every Linux node because kured tolerates every taint.
7. **The render test.** `chart/tests/render.sh` renders the chart with no cluster and asserts rules 2 to 6; it runs the write loop and the function test's script against a stub `sleep` and a stub `kubectl`. CI runs it as `bash <script> <chart dir>`.
8. **The Blueprint.** `platform/kured/blueprint.yaml`: `apiVersion: catalyst.openova.io/v1`, name `bp-kured`, `spec.version: 0.1.0`, `visibility: unlisted`, a `topology` block that `platform/_schemas/blueprint-topology.json` accepts (the shape of `platform/storage-ready/blueprint.yaml`), no category, family, tier or section field or label. # bp-kured

Coordinated node reboots: kured reboots a node that needs it, one node at a
time and only inside the reboot span. The DaemonSet `node-patch-config` makes

## Role in Catalyst

Control-plane plumbing on every cluster of every region, never a catalog item

Reboots and upgrades take turns by time: kured reboots only inside its span,

## What it ships and how to configure it

- The upstream chart `kubereboot/kured` 6.1.0 (kured 1.23.0) under the key
  `kured:` of `values.yaml`. Its DaemonSet is named `kured` and holds the
  reboot lock in the annotation `weave.works/kured-node-lock`. Defaults: one
  node at a time, from 00:30 to 22:00 UTC on every day, a check every 15
  minutes, a 15-minute drain limit (a node that cannot drain is not
  rebooted), a lock time-to-live of 1 hour and a 5-minute pause before the
  next node. kured does not reboot a node while an upgrade Job Pod of the
  system-upgrade-controller runs on it; the selector's second key,
  `upgrade.cattle.io/plan`, leaves out the controller's own Pod. The
  measurements are in
  [`docs/ledger/plan/spikes/INF-030.md`](../../docs/ledger/plan/spikes/INF-030.md).
- The DaemonSet and ConfigMap `node-patch-config`. On every node, whatever its
  taints, it writes `/etc/apt/apt.conf.d/20auto-upgrades` and
  `/etc/apt/apt.conf.d/52unattended-upgrades-catalyst` when they differ from
  the ConfigMap, and checks again every hour. The second file sets
  `Unattended-Upgrade::Automatic-Reboot "false"`. Its only host mount is that
  directory.
- `nodePatchConfig.image` has no default; the kit slot sets it with the
  registry prefix of the Sovereign. The image needs a shell with `cmp`, and
  `kubectl` for the function test. Left empty, the install fails.

## Operational notes

- No data, no backup. Each cluster runs its own kured and its own lock.
- `helm test <release>` passes when `kured` has as many ready Pods as nodes to
  run on and the test Pod's node has both files as the ConfigMap holds them.
- `bash platform/kured/chart/tests/render.sh` checks the chart with no cluster.

  name: node-patch-config
  namespace: {{ .Release.Namespace }}
  labels:
    {{- toYaml $labels | nindent 4 }}

    matchLabels:
      {{- toYaml $labels | nindent 6 }}

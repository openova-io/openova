# SEC-219 — A synced value of the secrets library takes a template and copies

## In plain words

**The problem today.** The secrets library gives a chart each synced value as a plain Secret with the one key password, under the value's own name. A database operator needs its role Secrets typed basic-auth, labelled for reload and carrying a user name, other charts need two values in one Secret under the keys their upstream reads, and some need the same value in a second Secret. None of this can be declared, and an External Secrets object written by hand is not allowed.

**What changes.** A synced value can state the type, labels, annotations and keys of its Secret, join other values into it, and add copies in its own namespace. A copy in another namespace fails the render with a message that names the package that delivers it, and a chart that uses none of these inputs renders exactly what it rendered before.

**Done means:**

- The role Secret of a database operator in namespace postgres renders typed kubernetes.io/basic-auth, labelled cnpg.io/reload, and with exactly the keys username and password.
- One Secret carries two of the library's values, each under its own key; the joined value is still born in every region and gets no Secret of its own.
- A copy renders one more Secret of the same value, register id and store path in the value's namespace, with its own keys or the plain key password.
- A copy that names another namespace fails the render, and the message says that such a value is written through by its producer, in SEC-225.
- The console chart, the one chart that uses the library today, renders byte for byte what it rendered before, and so does every fixture of the library's earlier tests.
- Each new input and each refusal has a test, and each of these tests fails against the library before this change.

The rest of this ticket is the exact instruction for the model that does the work.

## 2. End goal
A chart that declares a synced value in `generatedSecrets` can shape the Secret it gets: its `type`, labels, annotations and keys (`template`), other synced values of the same chart in the same Secret under their own keys (`join`), and further Secrets of the same value in the same namespace (`copies`). The first user is SEC-231: thirteen role Secrets in namespace `postgres`, each of type `kubernetes.io/basic-auth`, labelled `cnpg.io/reload: "true"`, with the keys `username` and `password`. A copy in another namespace is refused at render, because the store of that namespace reads only its own prefix; SEC-225 delivers that case. A chart that uses none of the three inputs renders exactly what it rendered before.

## 3. The model (the law)
1. `template` is a map of at most `type` (a Secret type), `labels`, `annotations` and `data` (maps whose values are strings; a data key matches `[-._a-zA-Z0-9]+`). It renders as the ExternalSecret's `spec.target.template` with `engineVersion: v2`: `type`, then `metadata.labels` and `metadata.annotations`, then `data`. Each data entry is an External Secrets template over the value, `{{ .password }}`, and over each joined value, `{{ index . "<name>" }}`.
2. `join` is a list of names of other synced values of the same chart. Every ExternalSecret of the value (its own and each copy) carries in `spec.data`, after the entry `password`, one entry per joined value: `secretKey` the joined value's name, remote key `openova/apps/<ns>/<joined>/e<epoch>`, property `password`. A joined value is born as before (its Password generator and PushSecret) and renders no ExternalSecret of its own, so it takes no `registerId`, `template`, `copies`, `join` or `mountedCopies`. A value does not join itself, `password`, a mounted or an unknown value, or one value twice.
3. `copies` is a list of entries with `name` (a Secret name), an optional `namespace` and an optional `template`. Each entry renders one more ExternalSecret named as the copy, in the value's namespace, with the same register id and remote keys as the value's own, through SecretStore `openbao`, with its own template or none. A copy's name is not the name of a value of the chart nor of an earlier copy.
4. A copy whose `namespace` is not the value's namespace fails the render with: `namespace "<given>" is not the value's namespace "<ns>". A copy stays in its value's namespace; a value read in another namespace is written through by its producer (SEC-225)`.
5. `template`, `copies` and `join` on a mounted value fail the render. A value with `mountedCopies` and a template whose `data` is given keeps `password: "{{ .password }}"`, because the birth Job copies key `password` of the value's Secret.
6. Without `template`, `copies` and `join` every object is the one the library rendered before, byte for byte. No chart version line changes: the library stays at version 0.1.0, and `blueprint-release.yaml` skips a chart of `type: library`.

# SOV-341 — The kubeconfig route serves the primary region's file that the parent holds after hand-over

## In plain words

**The problem today.** After a Sovereign is handed over, the parent still holds the kubeconfig file of its primary region, yet the route that serves kubeconfigs answers 409 for that region while it answers 200 for the follower region. The record of a handed-over deployment no longer names the primary's file, and the route looks for that file only through the record.

**What changes.** The route finds the primary region's file by its fixed name when the deployment record carries none, as it already finds a follower's file by name, and serves it. Every other answer of the route stays as it is.

**Done means:**

- A deployment record without a kubeconfig path, whose primary file is in the kubeconfigs directory, gets 200 with that file from the route, with no region and with the primary's cloud region as region.
- A follower region's file is served as before.
- Without a file for the region asked the route answers as before: 409 not-implemented with no region, 409 kubeconfig-file-missing with a region.
- The route writes no file, and the handler package of the catalyst-api has no more lines and no more methods than before.

The rest of this ticket is the exact instruction for the model that does the work.

## 2. End goal
After the hand-over of a Sovereign, a caller of the parent's route `GET /api/v1/deployments/{id}/kubeconfig` gets the primary region's kubeconfig with HTTP 200, with no `region` query and with `?region=<the primary's cloud region>`, for as long as the parent holds the file `<kubeconfigs dir>/<id>.yaml`. The route finds that file by its fixed name when the deployment record carries no kubeconfig path, as it already finds a follower's file by its name `<id>-<region>.yaml`. Every other answer of the route is unchanged, and when the parent's copies are deleted is not decided here.

## 3. The model (the law)
1. The primary region's file is the path on the record (`Result.KubeconfigPath`) when the record carries one; otherwise `<kubeconfigsDir>/<id>.yaml` while that file exists (`os.Stat` succeeds); otherwise none.
2. With no `region` query the route serves the primary region's file. With `?region=<Request.Region>` (the primary's cloud region, which `Request.Validate` mirrors from `Regions[0].CloudRegion`) it serves the primary region's file when neither `<id>-<region>.yaml` nor a slot-suffixed `<id>-<region>-<n>.yaml` exists: the rule of issue 1882, unchanged except that it now finds the file of rule 1.
3. Every other answer stays: a record path whose file is gone gives 409 `kubeconfig-file-missing`; no record path and no `<id>.yaml` gives 409 `not-implemented`; a region with no file gives 409 `kubeconfig-file-missing`; a follower's exact or slot-suffixed file is served; a region query without a kubeconfigs directory gives 503; 404 and the ownership check come first.
4. The route writes nothing. It does not call `resolvePrimaryKubeconfigPath` (`internal/handler/clustermesh.go`): that helper builds a kubeconfig from the ServiceAccount on the Sovereign itself and maps a lost record path to "no file", which would change two other answers.
5. The handler package does not grow (`scripts/check-api-structure.py`): its line count and its count of methods on `*Handler` stay as they are. The two locked reads of the record path become one, and the comments that described the record path as the only source are rewritten in as many lines.
6. Nothing else changes: no route, no chart, no RBAC rule, no node port, no deletion of any file.

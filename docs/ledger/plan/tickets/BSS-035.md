# BSS-035 — The storefront says when prices are unavailable

## In plain words

**The problem today.** When the storefront cannot read the price list of its Sovereign, the plan step quietly shows the older plan deck with prices of its own. A customer can then pick a plan at a price that the price list does not show, and nothing on the page says that the price list was not read.

**What changes.** The storefront tells apart two cases. When nothing is published yet, the plan step shows the plan deck as before. When the price list cannot be read, the plan step says that prices are unavailable, shows no plans, and does not let the customer go on.

**Done means:**

- When the price list cannot be read (the request fails, or it answers an error other than 404), the plan step shows the text "Prices are unavailable. Please try again shortly.", shows no plan cards, and its continue button is disabled.
- When nothing is published (no price list address, an answer 404, or a list with no package), the plan step shows the plan deck exactly as before.
- When the price list is read, the plan step shows the packages exactly as before.
- The add-ons, topology and review steps behave as before in every case.
- Unit tests cover a list with packages, a list without packages, an answer 404, an answer 500 and a network error; browser tests in CI cover the message and the deck.

The rest of this ticket is the exact instruction for the model that does the work.

## 2. End goal
The storefront (`core/marketplace`) reads the price list of its Sovereign with `loadPublicPackages` in `core/marketplace/src/lib/packages.ts`. That function no longer answers "a document or null". It answers one of three results: `ok` with the document, `none` when nothing is published, and `unavailable` when the price list could not be read. On `unavailable` the plan step (`/plans`, component `PackageTable.svelte`) shows the heading of the step, the text "Prices are unavailable. Please try again shortly.", no plan card, and a continue button that is disabled. On `none` it shows the plan deck exactly as today. On `ok` it shows the packages exactly as today. The three later steps that read the price list (add-ons, topology, review) behave exactly as today in all three cases. A browser shows this in the Playwright specs that CI runs against the production build.

## 3. The model (the law)
1. `core/marketplace/src/lib/packages.ts` exports the type `PackagesResult`, which is exactly `{ state: 'ok'; packages: PublicPackages } | { state: 'none' } | { state: 'unavailable' }`. `loadPublicPackages(baseURL, deps)` returns `Promise<PackagesResult>` and never throws.
2. The result is `none` in three cases: there is no chargeback base address; the answer has status 404; the body is the contract (an object with a `packages` list) and `parsePublicPackages` finds no valid package in it. A 404 is "nothing published": the engine answers 404 until its plans book exists, which is the state of every fresh Sovereign.
3. The result is `unavailable` in four cases: there is no `fetch` function; the request fails or times out (6 seconds, as today); the status is not 2xx and not 404; the body is not JSON, not an object, or has no `packages` list.
4. Otherwise the result is `{ state: 'ok', packages: <the parsed document> }`.
5. The one warning per page stays: the first result of a page that is not `ok` logs one warning, and a later one on the same page logs nothing. The warning is `[packages] Could not load packages — <reason>.` There are seven reasons. Two carry no address: `no chargeback host for this storefront` (result `none`) and `fetch unavailable` (result `unavailable`). Five start with the address that was asked: `<address> answered 404` (`none`), `<address> published no packages` (`none`), `<address> answered <status>` (`unavailable`), `<address> answered a body that is not the packages document` (`unavailable`) and `<address> unreachable (<error>)` (`unavailable`). Nothing is cached: every call fetches again.
6. `PACKAGE_STRINGS.pricesUnavailable` is exactly `Prices are unavailable. Please try again shortly.`
7. `packages.ts` exports `documentOf(result)`: the document for `ok`, `null` for `none` and for `unavailable`. `AddonsStep.svelte`, `BCPStep.svelte` and `ReviewStep.svelte` call `loadPublicPackages(chargebackBaseURL()).then(documentOf)`. For them `none` and `unavailable` are both "no document", which is what `null` meant before, so they behave exactly as today. Only the plan step changes.
8. `PackageTable.svelte` keeps `let status = $state<'deck' | 'table' | 'ladder'>('deck')` unchanged, because `core/marketplace/src/lib/packagesLadder.test.ts` line 602 pins that line, and adds `let unavailable = $state(false)`. On `none` it returns and the server-rendered deck stays. On `unavailable` it sets `unavailable = true`. The first branch of its markup is `{#if unavailable}`. That branch holds two elements, one after the other. The first is `<div class="pk-page" data-testid="packages-unavailable">`: it holds the step heading (`PACKAGE_STRINGS.title`) and the text (`PACKAGE_STRINGS.pricesUnavailable`, in a `<p role="status">`). The second is `<div class="float-nav">`: it holds one `<button>` with `data-testid="packages-unavailable-continue"` that is `disabled`. The button is outside the element with `data-testid="packages-unavailable"`. That branch holds no `PlanStep`, no table, no ladder and no link. The initial value of `unavailable` is false, so the deck stays the server render and its stylesheet stays in the production bundle.
9. The unit tests in `packages.test.ts` cover the five inputs (200 with packages, 200 without packages, 404, 500, network error), a body that is not the contract, no base address, `documentOf`, the text, and the markup of the plan step and of the three later steps.
10. Two Playwright tests in `core/marketplace/playwright/package-table.spec.ts` asserted the deck where the result is now `unavailable` (an answer 503 and a request aborted at the network layer). They now answer 404, the state "nothing published", and keep their assertions. Two new tests assert the message, no `.pcard`, no table, no ladder and a disabled continue button for an answer 503 and for an aborted request.

# INF-132 — Chart templates for the operations controller

## In plain words

**The problem today.** The machine plane can schedule scans of the nodes and run them, but nothing runs the program that does it. The chart of the Blueprint runs only the inventory, so no scan is ever made and no hardening report or bill of materials is ever written. Its documentation still says the scans come later.

**What changes.** When the chart is switched on, it also runs the operations controller with access rules limited to what it needs, and it renders a nightly scan of every node. The chart refuses to render without the runner image and the address of the evidence store. At its defaults it still renders nothing.

**Done means:**

- Switched on with all its required values, the chart renders two Deployments: the inventory controller and the operations controller.
- The operations controller can start and read runner Jobs and their Pods only in its own namespace, and no access rule of the chart grants anything on Secrets.
- The runner Jobs have a service account that carries no token and is bound to no role.
- The chart renders a nightly scan of every node with the profiles inventory and hardening, and a value switches it off.
- Switched on without the runner image, the evidence endpoint or the evidence region, the chart refuses to render and names the missing value.
- A test of the chart checks all of this, and its self-test proves that each of its rules can fail.

The rest of this ticket is the exact instruction for the model that does the work.

## 2. End goal
The Blueprint `bp-machine-operations` can run its operations controller. When the chart's value `enabled` is true and its values `image`, `runner.image`, `evidence.endpoint` and `evidence.region` are set, the chart renders, beside the inventory controller of before: the Deployment `machine-controller-operations`, which runs `/usr/local/bin/machine-controller --controllers=operations` with the flags the program needs and mounts the evidence binding read-only; its service account; a ClusterRole for the machine kinds and the hardening reports; a Role in the release namespace for the runner Jobs, their Pods and the leader-election Lease; the service account `mr-node` of the runner Jobs, with no token and no role; and the default scan of the nodes, the `HardeningBaseline` and the `ScanPolicy` `nodes` in namespace `catalyst-infra`. No rule grants anything on Secrets. At its defaults the chart renders nothing, as before. The test `platform/machine-operations/chart/tests/render.sh` checks all of this on every pull request that changes the chart. No kit slot installs the chart yet, and no gate check changes.

## 3. The model (the law)
1. **The switch stays.** The chart renders nothing until `enabled` is true (default `false`). Every new template is behind `enabled`. `Chart.yaml` keeps `catalyst.openova.io/smoke-render-mode: default-off`, which allows the empty default render; `Chart.yaml` is not changed.
2. **Required values.** `runner.image`, `evidence.endpoint` and `evidence.region` (each default `""`) are required once the chart is switched on: the render fails with a message that names `.Values.runner.image`, `.Values.evidence.endpoint` or `.Values.evidence.region`. The program refuses to start without them (`checkSettings` in `products/catalyst/bootstrap/api/cmd/machine-controller/main.go`), so a render without them would give a pod that only restarts. `evidence.bucket` (default `machine-evidence`) and `runs.retention` (default `720h`) have defaults.
3. **The Deployment `machine-controller-operations`.** In the release namespace: one replica; strategy `Recreate`; service account `machine-controller-operations`; one container `machine-controller` with the image `image` and exactly the command `/usr/local/bin/machine-controller`, `--controllers=operations`, `--job-namespace=<release namespace>`, `--runner-image=<runner.image>`, `--evidence-endpoint=<evidence.endpoint>`, `--evidence-region=<evidence.region>`, `--evidence-bucket=<evidence.bucket>`, `--runs-retention=<runs.retention>`; probes, resources and security settings as the inventory Deployment. It mounts the CSI volume `evidence-store` (driver `secrets-store.csi.k8s.io`, attribute `secretProviderClass: evidence-store`, read-only) read-only at `/var/run/secrets/evidence-store`: the program reads the key of the evidence bucket there (`operations.EvidenceMountPath`), exactly as the runner Jobs do. The SecretProviderClass itself is not in this ticket.
4. **The ClusterRole `machine-controller-operations`** grants exactly: `get`, `list`, `watch` on `machines`; `patch` on `machines/status`; `get`, `list`, `watch`, `create`, `update`, `patch`, `delete` on `machineruns`; `get`, `update`, `patch` on `machineruns/status`; `get`, `list`, `watch` on `scanpolicies` and `hardeningbaselines`; `update`, `patch` on `scanpolicies/status` (a HardeningBaseline has no status subresource); `get`, `list`, `watch`, `create`, `update`, `patch`, `delete` on `policyreports` of group `wgpolicyk8s.io`. No rule names `secrets`, and no rule uses the wildcard `*`.
5. **The Role `machine-controller-operations`** in the release namespace grants exactly: `create`, `get`, `list`, `watch`, `delete` on `jobs` of group `batch`; `get`, `list`, `watch` on `pods`; `create` on `leases`; `get` and `update` on the Lease `machine-controller-operations` only; `create` and `patch` on `events`. The Job and Pod verbs are in this Role and in no ClusterRole. A ClusterRoleBinding and a RoleBinding bind the two roles to the service account `machine-controller-operations` of the release namespace.
6. **The service account `mr-node`** in the release namespace: `automountServiceAccountToken: false`, and no binding names it. The runner Jobs use it (`operations.NodeServiceAccount`); a Job writes no object.
7. **The default scan.** When `enabled` and `defaults.nodeScan.enabled` (default `true`) are both true, the chart renders in `catalyst-infra` the `HardeningBaseline` `nodes` (content `complianceascode` release `0.1.82`; profile `xccdf_org.ssgproject.content_profile_cis_level1_server` for `ubuntu` `22.04` and `24.04`) and the `ScanPolicy` `nodes` (selector `machines.openova.io/class: node`, profiles `inventory` and `hardening`, baseline `nodes`, schedule `0 2 * * *`, jitter `2h`). The profile `vulnerability` is not in the list: the definition does not allow it yet (package INF-140 adds it). The release `0.1.82` is the one `products/machine-runner/tools.lock.yaml` carries.
8. **The test.** `tests/render.sh` keeps rules R1 to R8 and the 15 self-test cases of before unchanged and adds R9 to R14 (written at its head), with 15 more self-test cases. Switched on, the render holds 16 objects.
9. **The NodePort guard sees every template.** `chart/ci/nodeport-render-values.yaml` also sets `runner.image`, `evidence.endpoint` and `evidence.region`. Without them the guard's second render fails at the new required values and the guard drops it without a word.
10. **The README says what ships**: how the chart runs the operations controller, its access, the evidence mount, the service account of the runner Jobs, the default scan, the six new values, and that the SecretProviderClass `evidence-store` must exist before the chart is switched on.

# bp-machine-operations

Machine operations on the machines a Sovereign runs on, starting with an
inventory of the cluster's own Nodes and with scheduled scans of them.

## Role in Catalyst

Control-plane plumbing, not an Application a User installs. The kinds of the
API group `machines.openova.io` belong to this Blueprint: they arrive with its
chart and are absent where it is not installed. They are not platform
entities. See [`docs/ARCHITECTURE.md`](../../docs/ARCHITECTURE.md) for the
place of a Blueprint in the model.

## What this version ships

The chart holds five custom resource definitions, in `chart/crds/`, and the
templates of the inventory and the operations controller:

| Kind | Written by | Meaning |
|---|---|---|
| `MachineSource` | chart values or Git | One place machines are read from. Type `nodes` lists the Kubernetes Nodes of the cluster. |
| `Machine` | the inventory controller only | One machine a source saw. An observation, never committed to Git. The operations controller adds `status.sbom`. |
| `ScanPolicy` | chart values or Git | Which machines are scanned, with which profiles (`inventory`, `hardening`) and on which cron schedule. |
| `HardeningBaseline` | chart values or Git | The hardening content and, per operating-system release, the profile a machine is evaluated against. |
| `MachineRun` | the operations controller only | The record of one scan: its targets, the outcome of each and the files it stored. Never committed to Git. |

The inventory controller is the binary `machine-controller` of the
catalyst-api module (`products/catalyst/bootstrap/api/cmd/machine-controller`),
built into the catalyst-api image as `/usr/local/bin/machine-controller`. Its
code is in `products/catalyst/bootstrap/api/internal/machines/`. The chart runs
it as the Deployment `machine-controller-inventory` in the release namespace:
one replica, the command
`/usr/local/bin/machine-controller --controllers=inventory`, and the service
account of the same name. Its ClusterRole reads Nodes and MachineSources,
writes Machines and the status of MachineSources, and grants no verb on
Secrets. A Role in the release namespace covers its leader-election Lease. The
chart also renders the built-in source `nodes` (type `nodes`) in namespace
`catalyst-infra`.

The operations controller runs from the same image as the Deployment
`machine-controller-operations` in the release namespace: one replica, the
command `/usr/local/bin/machine-controller --controllers=operations` with the
flags of the runner image, the evidence bucket and the retention, and the
service account of the same name. Its ClusterRole reads Machines, ScanPolicies
and HardeningBaselines, writes MachineRuns, the status of Machines, of
MachineRuns and of ScanPolicies, and the `PolicyReport` objects of the group
`wgpolicyk8s.io`. Jobs and Pods it reaches only in the release namespace,
through the Role `machine-controller-operations`, which also covers its
leader-election Lease. No role grants a verb on Secrets. The Deployment mounts
the CSI volume of the SecretProviderClass `evidence-store` read-only at
`/var/run/secrets/evidence-store`, where it reads the key of the evidence
bucket. The runner Jobs run as the service account `mr-node`, which mounts no
token and is bound to no role. The chart also renders the default scan of the
nodes in namespace `catalyst-infra`: the HardeningBaseline `nodes` (content
`complianceascode` release `0.1.82`, the profile
`xccdf_org.ssgproject.content_profile_cis_level1_server` for Ubuntu 22.04 and
24.04) and the ScanPolicy `nodes` (every Machine of class `node`, profiles
`inventory` and `hardening`, each night at 02:00 UTC with a jitter of `2h`).

## How the inventory works

- A Machine is identified by its namespace, its source and the source's own
  identifier. A Machine of class `node` is named after its Node.
- An enumeration that fails, or that cannot read every scope, marks nothing.
- After a complete enumeration, an `Active` Machine that the source did not
  list becomes `Stale`. The time since it was last seen is never the test.
- If that would mark more than `spec.stale.holdPercent` (default 20) of the
  source's active Machines, and at least `spec.stale.holdMinimum` (default 10),
  nothing is marked: `status.held` and the condition `StaleHold` are set. Set
  `spec.stale.releaseHoldFor` to `status.held.enumerationId` to apply the sweep.
- A Machine that a source lists again becomes `Active` and keeps `firstSeen`.
- A Machine that is stale for `spec.stale.retireAfter` (default `720h`)
  becomes `Retired`; after a further `spec.stale.purgeAfter` (default `2160h`)
  it is deleted.
- Each Machine carries exactly five labels, written by the controller:
  `machines.openova.io/class`, `ownership`, `os-family`, `phase` and `source`.

## How a scan runs

The operations controller is the same binary with `--controllers=operations`
(code: `products/catalyst/bootstrap/api/internal/machines/operations/`), run by
the Deployment `machine-controller-operations`.

- At each time of a ScanPolicy's `spec.schedule` (five-field cron, UTC) the
  controller creates one MachineRun. It waits for that exact time; there is no
  loop with a fixed period.
- The targets are the selected Machines of class `node` that are `Active` and
  not quarantined. A target of a scheduled run starts at its own stable offset
  inside `spec.jitter`, at most `spec.maxParallel` at a time.
- One Job of the image `machine-runner` (`products/machine-runner/`) scans a
  target on its Node, one container per profile. The Job writes no object. A
  Job without a parsable result document is `Failed` with `no-result`; a
  document that does not say `completed` is `Incomplete`, and nothing is written.
- `inventory` sets `Machine.status.sbom`. `hardening` writes the `PolicyReport`
  `machine-<machine>-hardening`: one result per rule, the worst 200 first. A
  release without a profile in the baseline is `skip`, never `pass`. A finished
  MachineRun is deleted after `--runs-retention`, which the chart sets from
  `runs.retention` (default `720h`).

## Configuration

| Value | Default | Meaning |
|---|---|---|
| `enabled` | `false` | Switches the chart on. At `false` it renders nothing; only the definitions are installed. |
| `image` | `""` | The catalyst-api image, as a full reference. Required when `enabled` is true: the render fails while it is empty. |
| `sources.nodes.enabled` | `true` | Renders the built-in source `nodes` in `catalyst-infra`. |
| `runner.image` | `""` | The machine-runner image, by digest, that the runner Jobs use. Required when `enabled` is true: the render fails while it is empty. |
| `evidence.endpoint` | `""` | The S3 endpoint of the evidence bucket, `https://host[:port]`. Required when `enabled` is true: the render fails while it is empty. |
| `evidence.region` | `""` | The region of the evidence endpoint. Required when `enabled` is true: the render fails while it is empty. |
| `evidence.bucket` | `machine-evidence` | The bucket that holds every file a run stores. |
| `runs.retention` | `720h` | How long a finished MachineRun is kept before the controller deletes it. |
| `defaults.nodeScan.enabled` | `true` | Renders the default scan of the nodes: the ScanPolicy and the HardeningBaseline `nodes` in `catalyst-infra`. |

`chart/tests/render.sh` checks what the chart renders. Run it with

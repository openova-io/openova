# FND-036 — Sign-in as a gate check

## In plain words

**The problem today.** The check that signing in works across the platform's own applications is listed in the gate but not built. The sign-in probe exists, but it runs only by hand or on a nightly schedule that needs secrets nobody set, with a sign-in key from outside the Sovereign, and its result never reaches the gate record.

**What changes.** Every live gate run makes a user of its own in the Sovereign's identity provider, signs it in with the Sovereign's own session signer, runs the probe as that user and deletes the user again. The probe's result becomes the sign-in check of the gate record. The scheduled run and its secrets are removed.

**Done means:**

- A live gate run adds check FND-G07 to its record, PASS or FAIL, with one step per application the probe visited.
- When the user, the session, Node or the browser cannot be set up, the record still gets FND-G07, as FAIL with the reason; it is never left out or counted as a pass.
- The user of the run is deleted in a step that runs even when an earlier step failed, and a user left by an earlier run is deleted before a new one is made.
- The gate manifest lists FND-G07 as expected-fail, implemented by the sign-in probe.
- The sign-in workflow has no schedule and no secrets any more; its static guard still runs on pull requests.

The rest of this ticket is the exact instruction for the model that does the work.

## 2. End goal
A live run of `.github/workflows/foundation-gate.yaml` (job `live`) proves sign-in as gate check `FND-G07`. After the suite, the job creates the user `gate-<run id>@<env>.omani.works` in the realm `sovereign` of region A, in the groups `/sovereign-admins` and `/sovereign-viewers`, through `kcadm.sh` inside the identity provider's Pod. It mints that user's console session with the Sovereign's own signer, the same way `scripts/acceptance-sovereign.sh` mints the owner's. It runs `scripts/sso-zero-click-probe.mjs` with that session, deletes the user in a step that always runs, and adds the probe's result to the record with the new command `python3 scripts/acceptance-gate.py merge-check`. A person sees this in the record of the run (`docs/ledger/acceptance/<env>-<run_id>.json`): an entry `FND-G07` in `checks` and one step per probed application in `steps`. `docs/ledger/gates.yaml` lists `FND-G07` as `expected-fail` with the probe as its implementation. `.github/workflows/sso-probe.yaml` keeps only its static guard.

## 3. The model (the law)
1. The probe gets two flags. `--session-file <path>`: the raw value of the console cookie `catalyst_session`; the probe sets it on the domain `.<fqdn>` (the domain the console itself gives that cookie) and opens `https://console.<fqdn>/dashboard` for the row `console`. `--result-file <path>`: the probe writes `{"id":"FND-G07","status":"PASS"|"FAIL","steps":[...]}`. Each step has the fields of a step of the record: `journey` `FND-G07`, `id` the row name, `name`, `status` `PASS` or `FAIL`, `started_at`, `finished_at`, `duration_ms`, `evidence` (`url`, `finalURL`) and, for a failed row, `error`. `status` is `PASS` only when every probed row is green.
2. A harness error of the probe (no `--fqdn`, no session input, an unreadable or empty session file, a browser that does not start) writes `FAIL` with one step `id` `-`, `name` `the probe could run`, and the error. The probe imports `playwright` only after its arguments are read, so these errors are written even where `playwright` is not installed.
3. The probe's rows and their assertions do not change. The handover URL and `--jwt-key` inputs stay. The `--json` output keeps its form.
4. `acceptance-gate.py merge-check <record> <result file> --check <id>` adds the check to `checks` with `state_at_run` from the manifest of its own checkout, and appends the result's steps to `steps`. A result file that is missing, not JSON, or not of the form of point 1 (wrong id, status not PASS or FAIL, no steps, a step not of the record's form, a step of another journey, PASS with a step that did not pass) adds the check as `FAIL` with the reason and one step `the check wrote a valid result`. A missing input is never a pass. A check whose `needs` the record does not declare is added as `SKIP`. A required check that does not pass sets `result` to `FAIL` (pass rule 5). It refuses, with exit 1 and no change to the record, a check that is not in the manifest, is `not-built`, does not list the record's `run_in`, or is in the record already. Exit 0 added, 1 refused, 2 cannot run. Its self-test has one case per rule.
5. In the job `live`, after the step "Run the suite" and before the step "Validate the record", four steps run in this order: Node 22 (`continue-on-error`); the sign-in step; the delete step (`if: always() && steps.sso.outcome != 'skipped'`); the merge step. The sign-in step and the delete step never fail the job, so the record is still validated and committed. The merge step fails the job only when `merge-check` refuses or cannot run.
6. The sign-in step: (a) deletes every user of the realm `sovereign` whose user name is `gate-<digits>@<env>.omani.works`; (b) creates `gate-<github.run_id>@<env>.omani.works` (user name and email, enabled, email verified) and adds it to `/sovereign-admins` and `/sovereign-viewers`, then reads its groups back; (c) mints its session with `sovereign-acceptance mint-session --email <user> --ttl 1h`, the signer piped from region A's `catalyst-api` exactly as `scripts/acceptance-sovereign.sh` does, into a file made with `umask 077`; (d) installs `playwright@1.46.0` and Chromium in `$RUNNER_TEMP/sso` and runs a copy of the probe there with `--session-file` and `--result-file`. When a part fails it writes the reason into the job summary and an error annotation and stops without a result file.
7. All identity-provider calls are `kubectl exec keycloak-0 -c keycloak` in namespace `keycloak` of region A, running `/opt/bitnami/keycloak/bin/kcadm.sh` with `--config /tmp/kcadm-gate.config`, server `http://localhost:8080`, realm `master`, user `admin`, and the password read inside the Pod from `/opt/bitnami/keycloak/secrets/admin-password` (the Pod's mount of Secret `keycloak/keycloak-admin`, key `admin-password`). No new secret, no new network path, and the password never reaches the runner.
8. The delete step deletes the user of the run and removes the session file. A user it cannot delete is deleted by the next run's step (a).
9. `docs/ledger/gates.yaml`: entry `FND-G07` gets `state: expected-fail` and `implementation: scripts/sso-zero-click-probe.mjs`. Nothing else of the entry changes.
10. `.github/workflows/sso-probe.yaml`: the triggers `workflow_dispatch` (with its three inputs) and `schedule`, the job `probe` with its three secrets, and the header lines that describe them are deleted. The trigger `pull_request` with its paths and the job `dead-grant-guard` stay unchanged.

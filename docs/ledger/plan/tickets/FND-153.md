# FND-153 — The suite image and its signed build

## In plain words

**The problem today.** The acceptance suite can run inside a Sovereign as a Job, but nothing builds an image of it. Without a signed image of the suite, no Job can run it, and a Sovereign cannot verify what it would run.

**What changes.** A container file of the suite and a build workflow are added. Every run builds the image and starts it; a run on main also pushes it to the registry and signs it with the keyless signature and the release key.

**Done means:**

- A pull request that changes the suite, its container file, the NodePort script, the gate tool, the gate manifest or the build workflow builds the image of the suite and starts it once.
- The image runs as user 65534 and holds the suite program, kubectl v1.31.8, bash, python3, the live NodePort script and the gate manifest as JSON, together with the commit it was built from in SUITE_GIT_SHA.
- A run on main pushes the image as ghcr.io/openova-io/openova/conformance with the short commit as its tag, signs it through the shared signing action with the release key, and writes its digest to the summary of the run.
- The signing guard and the pin guard pass with the new workflow, and every action and base image in the two new files is pinned.

The rest of this ticket is the exact instruction for the model that does the work.

## 3. The model (the law)
1. **The image.** Two stages, both `FROM docker.io/library/alpine:3.20@sha256:d9e853e87e55526f6b2917df91a2115c36dd7c696a35be12163d44e6e2a4b6bc` (alpine 3.20.10, the base that `platform/keycloak/extensions/fapi-consent/Containerfile` already uses). The fetch stage downloads `https://dl.k8s.io/release/v1.31.8/bin/linux/amd64/kubectl` and stops unless its SHA-256 is `be0aa44a50a9aada4e9402e361ffb0d5bb1fd4f6950751399fcaf3b8b936a746`. The runtime stage adds `bash` and `python3` from the Alpine archive, kubectl from the fetch stage, and the three files of the build context.
2. **Where things are in the image.** `/usr/local/bin/sovereign-acceptance` is the entry point. `/opt/conformance` is the working folder and the value for `--repo-root` (check FND-G05 runs `scripts/check-live-nodeports.sh` below it). `/opt/conformance/gates.json` is the value for `--manifest`. `/usr/local/bin/kubectl` is v1.31.8, the minor of the default `k3s_version` `v1.31.8+k3s1` of `infra/providers/local/variables.tf`. The default user is `65534:65534`.
3. **The commit.** The build argument `SUITE_GIT_SHA` is the commit the workflow checked out, 40 lower-case hexadecimal characters; the build stops otherwise. The image sets the environment variable `SUITE_GIT_SHA` to it, and the suite writes it into its record as `suite_git_sha` (after FND-151).
4. **The build context is not the repository.** The workflow fills `$RUNNER_TEMP/conformance` with exactly three files, all from the commit it checked out: `sovereign-acceptance` (built with `CGO_ENABLED=0 GOOS=linux GOARCH=amd64`), `scripts/check-live-nodeports.sh` (a copy) and `gates.json` (the output of `python3 scripts/acceptance-gate.py export`).
5. **Every run starts the image.** With no network, the image must run as `65534:65534` in `/opt/conformance`; bash, python3 and kubectl v1.31.8 must start; `bash scripts/check-live-nodeports.sh --self-test` must pass; the three files must have the SHA-256 they had in the build context; `SUITE_GIT_SHA` must equal the commit; and `sovereign-acceptance run --env smoke --run-in self` must exit 3 with the text `--suite-image-digest must be sha256` (after FND-151).
6. **Only main publishes.** The login, the push, the signature and the summary line run only when `github.ref == 'refs/heads/main' && github.event_name != 'pull_request'`. The signing step uses the shared action with `ref`, `digest` from the push step, `release-key: ${{ secrets.RELEASE_COSIGN_KEY }}` and `release-key-password: ${{ secrets.RELEASE_COSIGN_PASSWORD }}`, so `scripts/check-builds-sign.py` holds. No step runs `cosign` itself.
7. **Everything is pinned.** Every `uses:` line of the workflow names a 40-character commit, and every `FROM` line names a digest, so `scripts/check-pins.py --base origin/main` holds for the two new files.
8. **No Kubernetes client library.** The suite reads the cluster and writes its report only through kubectl; this ticket adds no Go dependency and changes no Go file.

# FND-155 — The `self` selection run by a Job on the local provider pack

## In plain words

**The problem today.** The gate suite can run inside a Sovereign as a Job, and its image can be built, but nothing has ever run it that way. Nobody has seen whether a Job with read rights only can run the suite, write its report and leave a record that names it.

**What changes.** Every full run of the local conformance job builds the suite image from its own commit, loads it into the primary region of the local pack and runs it there as a Job with narrow rights. The report and the record of that run are kept as an artifact, and the job fails when they do not show a run by that Job.

**Done means:**

- Every full run of the local conformance job builds the suite image from the commit under test and runs it as a Job in the primary region of the pack, by its digest, without pulling it.
- The Job runs under a service account of its own that can read releases, pods, services, nodes and namespaces, read the one Kyverno policy that the NodePort check reads, and write the conformance report, and nothing else; the job asks the cluster so after the run.
- The run writes the conformance report into the pack and prints its record into the log of the Job.
- The job fails unless the record is valid, names that Job, the image it ran and the commit under test, matches the report, and passes.
- The report, the record, the Job, its pod and its log are kept as an artifact of the run.
- A release whose spec names no single chart version, such as the range that the cluster writes for a chart from a Git repository, no longer holds a run in self at its first step.

The rest of this ticket is the exact instruction for the model that does the work.

## 2. End goal
After this ticket the job `conformance-local` of `.github/workflows/conformance-local.yaml` runs the gate suite twice on the local provider pack: from the runner with `--run-in local`, as today, and then, once that run has passed, inside the pack as a Job with `--run-in self`. The job builds the suite image of FND-153 from the commit it checked out, loads it into every machine of the primary region, and starts the Job `catalyst-system/catalyst-conformance` with the image named by its digest, under the ServiceAccount `catalyst-system/catalyst-conformance`. The suite writes the ClusterPolicyReport `conformance` into the region and prints its record into the log of the Job. The step "Run in self (a Job in the primary region runs the suite image)" fails unless the Job completed and the record, the pod and the report agree that this Job ran that image on this commit, and the record passes. A person sees the result in the check `conformance-local` of a pull request: the summary of the run has the table "Run in self on the local pack", the log of that step ends with the line `record local-pack-<run id>.json: run in self by Job catalyst-system/catalyst-conformance (uid <uid>), image sha256:<digest>, ...`, and the artifact `conformance-self` holds the report, the record, the Job, its pod and its log.

## 3. The model (the law)
1. **The image.** The job builds it with `docker build` from the commit it checked out, with the three-file build context of `.github/workflows/build-conformance.yaml` (the suite program built with `CGO_ENABLED=0`, `scripts/check-live-nodeports.sh`, the output of `python3 scripts/acceptance-gate.py export`) and `tests/acceptance/sovereign/Containerfile`, `SUITE_GIT_SHA` set to `git rev-parse HEAD`, without provenance or SBOM attestations. Its tag is `ghcr.io/openova-io/openova/conformance:local`, held in the job variable `SELF_IMAGE`. It is never pushed: the job adds no login, no push and no action.
2. **Loading.** The image goes into every node of the primary region (`REGION_A` of the env file of `scripts/local-pack.sh up`): `docker save` into `k3s ctr -n k8s.io images import --all-platforms --base-name ghcr.io/openova-io/openova/conformance -` inside the machine whose container name ends with `-<node name>`. On each machine the digest of `SELF_IMAGE` is read with `k3s ctr images ls`; it must be one `sha256:<64 hex>` and the same on every machine. Then `k3s ctr -n k8s.io images tag --force` gives the image the reference `ghcr.io/openova-io/openova/conformance@<digest>`, and that reference must be listed exactly once by `k3s ctr images ls -q`; the Job names the image by it.
3. **Rights.** The ServiceAccount `catalyst-system/catalyst-conformance` is bound by the ClusterRoleBinding `catalyst-conformance` to the ClusterRole `catalyst-conformance`, which holds exactly six rules: `get`, `list`, `watch` on `helmreleases` of `helm.toolkit.fluxcd.io`; `get`, `list`, `watch` on `pods`, `services` and `nodes`; `get`, `list` on `namespaces`; `get` on `customresourcedefinitions` of `apiextensions.k8s.io` with `resourceNames: [clusterpolicies.kyverno.io]`; `get` on `clusterpolicies` of `kyverno.io` with `resourceNames: [forbid-nodeport-service]`; `get`, `create`, `update`, `patch` on `clusterpolicyreports` of `wgpolicyk8s.io`. No `pods/exec`, no Secrets. The two named reads are what `scripts/check-live-nodeports.sh` of check FND-G05 reads besides the Services: first the definition of the kind, then the policy (P12). Without the first, the script reports the kind as absent, skips the policy, and still ends with its line that the policy is Enforce; without the second, it fails the region. They are added as the namespace read was, because a check of the first `self` selection needs them there. After the Job, the step asks `kubectl auth can-i --as system:serviceaccount:catalyst-system:catalyst-conformance` eight questions and fails on any other answer: yes to `get` of the definition and of the policy, `list namespaces` and `patch clusterpolicyreports`; no to `get` of another definition, `list clusterpolicies`, `get secrets` in any namespace and `create pods --subresource=exec` in any namespace. It asks after the Job and not right after the apply, so that the binding is in the authorizer's cache.
4. **The Job.** `catalyst-system/catalyst-conformance`, `backoffLimit: 0`, `activeDeadlineSeconds: 1200`. One container, image `ghcr.io/openova-io/openova/conformance@<digest>`, `imagePullPolicy: Never`, user and group 65534, a read-only root file system with an empty directory at `/tmp`, `HOME=/tmp`. It runs `sovereign-acceptance run --run-in self --env local-pack --region-a local-<REGION_A>-rtz-prod --suite-image-digest <digest> --report-name conformance --manifest /opt/conformance/gates.json --repo-root /opt/conformance --wait-for-release 10 --record --record-dir /tmp/record`, then prints each record file between the lines `--- record <file>` and `--- end of record`, and exits with the suite's exit code. `ACCEPT_JOB_NAMESPACE`, `ACCEPT_JOB_NAME` and `ACCEPT_JOB_UID` come from the downward API: the pod's namespace and its labels `batch.kubernetes.io/job-name` and `batch.kubernetes.io/controller-uid`.
5. **The judgement.** The step fails unless all of these hold: the Job has `succeeded: 1`; the log of the Job holds exactly one record; `python3 scripts/acceptance-gate.py validate-record` exits 0 on it; its `run_in` is `self`; its `producer` is `{"kind": "job", "job": {"namespace", "name", "uid"}}` of the Job as the API server returns it; its `suite_image_digest` is the digest of law 2; its `suite_git_sha` is `git rev-parse HEAD`; the `imageID` of every container of the Job's pod ends with `@<digest>`; the report has the label `catalyst.openova.io/run-id` equal to the record's `run_id` and `app.kubernetes.io/managed-by: catalyst-conformance`; the `policy` values of its results are the `id` values of the record's checks; and the record's `result` is `PASS`. Each failure is one line that starts with `::error::run in self:`.
6. **Order and conditions.** The two new steps "Suite image for the run in self" and "Run in self (a Job in the primary region runs the suite image)" come after "Upload the record" and before "Collect evidence", and each has `if: steps.suite.outcome == 'success'`: they run only when the run in local ran and passed, so a run that skips the pack skips them too. The new step "Upload the evidence of the run in self" has `if: always() && steps.self.outcome != 'skipped'` and uploads `$RUNNER_TEMP/conformance-self` as the artifact `conformance-self`. Every other line of the workflow stays as it is: the change only adds lines.
7. **No port.** Nothing publishes a port, and nothing uses a node port. The Job reaches only the API server of its own region.
8. **Step D0.12.** The step compares the deployed chart version of a HelmRelease with the version its spec names only when that spec names one version: major, minor and patch with an optional pre-release and build (the expression `exactChartVersion` of `tests/acceptance/sovereign/internal/suite/report.go`). A suspended release, a spec with no version and a spec that names a range (`*`, `>=1.0.0`, `1.x`) are not compared. A pinned release that runs another version still holds the step until the wait of `--wait-for-release` ends.

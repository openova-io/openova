# NET-080 — Pin the Organization virtual cluster chart

## In plain words

**The problem today.** The organization controller asks for the vcluster chart of every Organization by a version range, so each Sovereign takes whatever patch the chart source offers at the moment it resolves the range. Two Sovereigns, or two Organizations created at different times, can run different vcluster patches, and the cutover can mirror a different patch from the one the controller asks for later. Nothing in the platform chart even passes the version to the controller.

**What changes.** The controller's default, a new platform chart value and the cutover's mirror version name one exact version, 0.33.4, the highest stable 0.33 release today. The platform chart passes that value to the controller.

**Done means:**

- The organization controller, the platform chart and the cutover chart name no vcluster version range.
- When nothing overrides it, the organization controller asks for vcluster chart 0.33.4.
- The platform chart starts the organization controller with vcluster chart version 0.33.4, taken from its own values.
- The cutover pulls vcluster chart 0.33.4 and mirrors it into the Sovereign's own registry.
- The organization controller's tests still pass.

The rest of this ticket is the exact instruction for the model that does the work.

## 2. End goal
Every per-Org vCluster HelmRelease that the organization controller renders asks for the vcluster chart at one exact version, `0.33.4`, instead of the range `0.33.*`. The same value stands in three places that must agree: the controller's built-in default (env `CATALYST_VCLUSTER_CHART_VERSION`), a new value `controllers.organization.vclusterChartVersion` of the platform chart that the chart passes to the controller as that env, and `helmRepositories.vclusterLoftPivot.chartVersion` of the cutover chart, the version the cutover pulls from the upstream chart source and pushes into the Sovereign-local Harbor. A person who renders the platform chart sees the env with `0.33.4`; a person who renders the cutover chart sees `VCL_LOFT_VERSION` with `0.33.4`.

## 3. The model (the law)
1. The vcluster chart version is exact: three numbers, no `*`, no `x`, no range. The pin is `0.33.4`.
2. Three sites carry it, and they are equal:
   - the default of `CATALYST_VCLUSTER_CHART_VERSION` in `core/controllers/organization/cmd/main.go`;
   - the new value `controllers.organization.vclusterChartVersion` in `products/catalyst/chart/values.yaml`, which the template `products/catalyst/chart/templates/controllers/organization-controller-deployment.yaml` passes to the controller as the env `CATALYST_VCLUSTER_CHART_VERSION`, with no fallback in the template;
   - `helmRepositories.vclusterLoftPivot.chartVersion` in `platform/self-sovereign-cutover/chart/values.yaml`, which the cutover Job reads as `VCL_LOFT_VERSION`.
3. Comments that describe the version as the range `0.33.*` are corrected in the two cutover files, so that no comment in these files states the range. They name `<chartVersion>` instead of repeating the number.
4. The minor version stays 0.33. The renderer of the per-Org HelmRelease (`core/controllers/organization/internal/gitops/manifests.go`) and the vCluster values it renders do not change.
5. No chart `version:`, `appVersion:`, slot pin, catalogue pin or image tag changes. The values this ticket writes are the version of an upstream chart that the platform installs, not a release-owned value.
6. Nothing is deleted.

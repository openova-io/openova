# SOV-133 — The boot template and the provider contract take the variables document

## In plain words

**The problem today.** The provider modules receive the variables document of a Sovereign region, but they hand the boot template only one value of it, under the old name of the hand-over switch. The test renders of the boot template, its size check and its lint carry no document at all. The provider contract still describes the old switch and does not know the document.

**What changes.** The boot template receives the whole document and reads the hand-over switch from it. The modules, the render test and the two render scripts pass the document, and the provider contract, its two examples and its table require it.

**Done means:**

- The boot template has no input of its own for the hand-over switch; it reads the switch from the variables document.
- Both provider modules pass the variables document to the boot template, and their tests still pass.
- The render test, the size check and the lint of the boot template render it with a complete variables document, and the render test fails when the switch is not taken from the document.
- The provider contract lists the required input variables and no longer fire_cutover_on_handover, and its two examples carry a complete document.
- A new Sovereign boots with the same text as before.

The rest of this ticket is the exact instruction for the model that does the work.

## 2. End goal
The shared boot template `infra/providers/_shared/cloudinit-control-plane.tftpl` takes the variables document of the region (contract C5, `docs/contracts/c5-upstream-variables.schema.json`) as one template input, `variables`, a map of strings. Its template input `fire_cutover_on_handover` is gone: the kit key `FIRE_CUTOVER_ON_HANDOVER` of the ConfigMap `flux-system/sovereign-variables` takes the value of the key `HANDOVER_AUTO` of that map. The three `templatefile()` calls of the provider modules pass `variables = var.variables`. The render harness `infra/providers/_shared/tests/render.tf`, the size check `scripts/cloudinit-size-check.sh` and the lint `scripts/lint-cloudinit.sh` render the template with a complete document of the 39 contract keys. The render test asserts that the kit key follows `HANDOVER_AUTO`, and the golden values match the new render. The provider contract `infra/providers/_contract/contract.json` lists the required input `variables` in place of `fire_cutover_on_handover`; its two fixtures carry a complete document, its shared test body passes it, and the table of `infra/providers/PROVIDER-INTERFACE.md` says the same. The text that a new Sovereign boots with does not change. This ticket is complete in itself. Writing the contract keys into the ConfigMap is the later package SOV-134 (field 11).

## 3. The model (the law)
1. **The template input.** The template reads the input `variables` on exactly one line, `            FIRE_CUTOVER_ON_HANDOVER: "${variables["HANDOVER_AUTO"]}"`, which replaces the line `            FIRE_CUTOVER_ON_HANDOVER: "${fire_cutover_on_handover}"`. Three comment lines above it are rewritten. The template names `fire_cutover_on_handover` nowhere after the change. No other line of the template changes.
2. **The modules.** In each of the three `templatefile()` calls (`infra/providers/hetzner/main.tf`, primary and secondary regions; `infra/providers/huawei/main.tf`) the line `fire_cutover_on_handover = var.variables["HANDOVER_AUTO"]` and its comment are replaced by the line `variables = var.variables` and a two-line comment. The modules already passed `HANDOVER_AUTO` as the value, so the rendered user-data of every region is byte for byte what it was.
3. **The render harness.** `render.tf` gains the local `fixture_variables`, a document with exactly the 39 contract keys: the example values of the module tests, with `LOCAL_REGISTRY_HOST` `registry.render-test.example.test`, `K3S_VERSION` `v1.31.4+k3s1` (the fixture's own `k3s_version`) and `HANDOVER_AUTO` `"false"`.

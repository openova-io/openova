# SVC-250 result: composite resources in a release; bucket provisioning for an Organization

Date: 2026-11-19, one session, on origin/main faf778eb22. Type: spike, measured in CI on a throw-away kind cluster, three runs. Outcome:

- (a) Works, with two corrections to the design. A chart that renders one namespaced composite resource per Context installs, grows and shrinks under Flux. A new Context had its Workspace and its resource 7 seconds after the upgrade. A removed Context lost its resource when its management policies held `Delete`, and kept it when they did not. The release does not wait: it was Ready 4 seconds after the install, 162 seconds before its last composite resource. The namespaced Workspace has no `deletionPolicy`; the choice is `managementPolicies`.
- (b) Outcome 2, not possible. A Job in the Organization namespace that holds only an identity scoped to its bucket prefix, behind the chart's NetworkPolicy, creates buckets under that prefix and nothing more. Every call that makes a key for another user is refused with 403. On the kit as installed, every key-making call is refused, the caller's own key included. Only the administrator key made a key scoped to one bucket.
- On the kit as installed, a pod in any namespace needs no credential: SeaweedFS has no NetworkPolicy, and one `weed shell s3.configure` from the Organization namespace made an `Admin` identity whose key worked at once. The chart's own NetworkPolicy closes that path.
- The kit's SeaweedFS layout holds data in at most 5 buckets. Each new bucket takes 7 volume slots at its first write and the kit has 30. The sixth bucket was created, and its first write failed.

## Question

(a) A chart renders one namespaced composite resource per Context and Flux installs it. Does the release wait for readiness? Does adding a Context add a Workspace? Does removing one remove the cloud resource only when the deletion setting says so?

(b) Can a Job in an Organization's provider Application create a bucket and a key scoped to that bucket on the Sovereign's SeaweedFS, without holding a SeaweedFS administrator credential in that namespace, with only a NetworkPolicy path and a scoped identity?

## Answer

(a) Yes for adding and removing, no for waiting. A release that renders composite resources is Ready before they are. The keep-or-delete choice of a namespaced managed resource is its `managementPolicies`.

(b) Outcome 2. With only a NetworkPolicy path and a scoped identity, the Organization's Job can create buckets under its prefix. It cannot make a key scoped to one bucket. On the kit as installed it cannot make any key. Every way to make a narrower key needs an administrator-equivalent credential.

## What later stories must take into account

1. SVC-290: the release does not signal readiness of its composite resources. The managed chart's function test is the readiness signal. It must wait for `Ready` of each composite resource of the release.
2. SVC-290 and SVC-330: a Context that keeps its cloud resource on removal sets `managementPolicies` without `Delete`. The namespaced managed kinds refuse `deletionPolicy`, so a Context field of that name is mapped to `managementPolicies` by the Composition.
3. SVC-290 and the cloud area's provider configuration: a namespaced Workspace resolves `providerConfigRef` to `ClusterProviderConfig/default` of group `opentofu.m.upbound.io`. The kit has only the legacy group's ProviderConfig (`clusters/_template/infrastructure/base/provider-config-opentofu.yaml`). A namespaced Workspace can read a Secret only in its own namespace: its `env[].secretKeyRef` has no namespace field. The ClusterProviderConfig's `credentials[].secretRef` has one. Cloud credentials therefore go into the ClusterProviderConfig and never into the Organization namespace. The kit's cloud-adoption Composition reads `flux-system/cloud-credentials` through Workspace `env`, which the namespaced kind cannot express.
4. SVC-290: provider-opentofu applies one Workspace at a time. One slow Context of one Organization delays every other Workspace of the Sovereign. The DeploymentRuntimeConfig `provider-opentofu` sets no `--max-reconcile-rate` today.
5. SVC-270 takes its outcome-2 form. The Job that makes buckets and one-bucket keys runs in a platform namespace that holds the administrator key, and Organizations reuse that instance (SVC-275). The gateway must run with `-iam.readOnly=false`, which kit slot 18 does not set. A new key works only on the gateway that made it until both gateways restart: 4 of 12 calls, then 12 of 12. The Job must make keys in a way every gateway sees, or restart the gateways after a change.
6. A package must switch on the chart's NetworkPolicy in kit slot 18 before any Organization workload runs. No package of the plan does so today. Until then, any pod of any namespace can make an `Admin` identity without a credential and can read every key stored in the filer. ACC-030 recorded a filer bypass of the S3 API for object lock.
7. SVC-270 and SVC-275: one bucket per Context does not fit the kit's SeaweedFS layout. After 5 buckets with data, the next first write fails, and so does a write to the default collection. Platform buckets use the same slots. The volume layout must change before buckets are made per Context: the volume growth count, `-max`, or one collection for many buckets. No measurement here chooses among them.
8. INF-210 builds on (a): composite resources of an Organization's release add and remove one Context without touching the others.
9. SVC-330: the measured form is one composite resource per Context. An in-place change of a list inside one resource was not measured, so SVC-330 uses one resource per database.

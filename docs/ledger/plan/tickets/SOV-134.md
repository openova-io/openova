# SOV-134 — The contract keys of the variables document land in the sovereign-variables ConfigMap

## In plain words

**The problem today.** A new Sovereign receives the variables document of the upstream contract at first boot, but none of its keys reaches the cluster: the ConfigMap that the Flux Kustomizations and the controllers read holds only the kit keys. The later work that reads the registry, release and hand-over keys from that ConfigMap cannot start. Written as plain lines, the keys would push the Hetzner boot text over its size limit.

**What changes.** The boot template writes the variables document as one packed file, and the first boot creates the ConfigMap from it just before the Flux bootstrap adds the kit keys. The render test checks the file and that order, and the Hetzner size test uses the room that was kept for this change.

**Done means:**

- The ConfigMap flux-system/sovereign-variables of a newly booted control plane holds every key of the variables document, among them HANDOVER_AUTO, LOCAL_REGISTRY_HOST and SOVEREIGN_CONSUME, besides the kit keys.
- The DNS-01 API key is still only in its Secret and never in that ConfigMap.
- If the ConfigMap cannot be created, the first boot stops with the same loud failure as a failed Flux bootstrap.
- The render test fails when the packed file or the creation step is missing, and the stored golden hashes match the new render.
- The Hetzner renders with the kubeconfig post-back stay under their size guards, and no guard is raised.

The rest of this ticket is the exact instruction for the model that does the work.

## 2. End goal
A new control plane boots with the ConfigMap `flux-system/sovereign-variables` holding the 39 keys of contract C5 (`docs/contracts/c5-upstream-variables.schema.json`), the variables document that the provider module passes to the shared template as its input `variables`, besides the kit keys that `flux-bootstrap.yaml` already writes there. The template writes the document as one packed file, `/var/lib/catalyst/variables.env` (one `KEY=value` line per key, gzipped and base64-encoded with `encoding: gz+b64`, the form the template already uses for seven files), and the boot step that applies `flux-bootstrap.yaml` first creates the ConfigMap from that file with `kubectl create`. Every Flux Kustomization that reads the ConfigMap through `postBuild.substituteFrom` can then substitute the contract keys. The Hetzner renders grow by 1158 bytes and stay under their guards: 30633 bytes for the primary region (guard 32576) and 31814 for a secondary region (guard 32256).

## 3. The model (the law)
1. The shared template `infra/providers/_shared/cloudinit-control-plane.tftpl` gets one new `write_files` entry, right before the entry `/var/lib/catalyst/flux-bootstrap.yaml`: path `/var/lib/catalyst/variables.env`, permissions `'0600'`, `encoding: gz+b64`, content `${base64gzip(join("", [for k, v in variables : "${k}=${v}\n"]))}`. The file on the node is the template input `variables`, one line `KEY=value` per key, in key order (OpenTofu iterates a map in key order), each line ending in one newline. A comment block above the entry says what it is and why it is packed. Comment lines are removed from the render, so the comment costs no byte.
2. In the `runcmd` item that hands the cluster to Flux, the line that applies `flux-bootstrap.yaml` becomes `kubectl -n flux-system create cm sovereign-variables --from-env-file=/var/lib/catalyst/variables.env && kubectl apply -f /var/lib/catalyst/flux-bootstrap.yaml || { ...; exit 92; }`. The failure branch is unchanged: when either command fails, the marker `flux-bootstrap-FAILED` is written and the item exits 92. Three comment lines above the item say so. The namespace `flux-system` exists at that point. The Flux install item, the third `runcmd` item before this one, installs Flux, which creates the namespace, and then waits for the Deployments in it; when it cannot, it stops the boot with exit 93 or 94. The two items between them apply the bootstrap Secrets and the OpenBao seed.
3. Why `create` and not `apply`. `kubectl create` stores no last-applied annotation. The `kubectl apply` of the ConfigMap in `flux-bootstrap.yaml` that follows then has no previous configuration to compare with, so its patch adds the kit keys and deletes no key. Had the contract keys been written with `kubectl apply`, the next apply of the kit keys would delete them. The contract keys and the kit keys (`docs/contracts/c5-kit-keys.txt`) share no name, so no key overwrites another.
4. `POWERDNS_API_KEY` is not a key of the ConfigMap; it stays the one key of the Secret `flux-system/sovereign-tls-secrets`. The provider modules accept for `variables` exactly the contract keys (their input validation), and no contract key holds a secret. The kit key `FIRE_CUTOVER_ON_HANDOVER` stays, with the value of `HANDOVER_AUTO`.
5. The render harness `infra/providers/_shared/tests/render.tf` gains three locals and two outputs: `variables_env` (the expected file text, built from `fixture_variables` with an explicit `sort(keys(...))`), `variables_env_entry` (the exact `write_files` entry that must carry it packed) and `variables_env_written` (the render contains that entry). The render test `cloudinit_render.tftest.hcl` gains three asserts in each of the runs `hetzner_render_is_valid` and `huawei_render_is_valid`: the entry is written; the file holds 39 keys, among them `HANDOVER_AUTO=false`, `LOCAL_REGISTRY_HOST=registry.render-test.example.test` and `SOVEREIGN_CONSUME=origin`, and no `POWERDNS_API_KEY`; the creation of the ConfigMap comes right before the one apply of `flux-bootstrap.yaml`, inside the same failure branch.
6. The golden values in `infra/providers/_shared/tests/golden.auto.tfvars.json` are the hashes of the new render of the two fixtures.
7. The Hetzner module test run `post_back_render_fits_the_size_guards_with_room` kept 1200 bytes of room under each guard for this change. Its two size asserts move to the guards themselves: `length(local.control_plane_cloud_init) <= 32576` and `length(local.secondary_region_cloud_init["nbg1-1"]) <= 32256`. Its comment and the two error messages say so. Its other three asserts and the guards in `infra/providers/hetzner/main.tf` do not change.
8. No other `write_files` entry, `runcmd` item or top-level key of the render changes. No module, no caller and no input of the template changes. Nothing is deleted.

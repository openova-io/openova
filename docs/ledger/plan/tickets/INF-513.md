# INF-513 — Runner test task: the ZAP baseline scan and its SARIF report (profile web-passive)

## In plain words

**The problem today.** The runner can run the passive network test of a declared machine, but the passive web test is refused and the image holds no web scanner. A test scope that asks for the web profile cannot run.

**What changes.** The runner runs the ZAP baseline scan, with passive rules only, against the declared machine on each port of its scope and stores the findings as SARIF beside those of the network profile. A target that the target check refuses is never scanned.

**Done means:**

- A web test runs the baseline scan once per port of the scope with one fixed argument list: the spider for one minute, passive rules only, no update check and no download.
- Port 443 is scanned as https and port 80 as http; any other port is scanned as https only when a TLS handshake with it completes.
- An address or a port that the target check refuses is refused before any tool starts, for the web profile as for the network profile.
- Each scan report becomes one SARIF run of the one findings file of the run, with the risk of each alert mapped to a SARIF level, and the result document counts the findings.
- A failed scan or an unreadable report ends the run failed, says why, and stores nothing.
- The image holds ZAP, its baseline script and its Python client at exact versions whose checksums the build checks, and no active-scan, fuzzing, brute-force or out-of-band add-on of ZAP.

The rest of this ticket is the exact instruction for the model that does the work.

## 2. End goal
`machine-runner --task=test --mode=ssh --address=<ip> --ports=<p>,... --test-profile=web-passive` (alone or with `network-passive`) runs the ZAP baseline scan of one declared machine, once per port of the scope, in the Job shape of SSH mode that INF-512 built (no SSH session; the egress policy of the run allows only the target address on the scope's ports). Each run reads one line of the target list that INF-512's check wrote, read back and checked, and nothing else. The scan is the passive baseline: the spider for at most one minute and the passive scan rules, no active scan, no fuzzing, no attack, nothing downloaded at run time. Each JSON report is converted into one SARIF run, stored in the one `test.sarif.json` of the run (evidence kind `test-sarif`) beside the runs of Nuclei, and counted in the result member `test`. The image gains ZAP 2.17.0 with only the ten add-ons the baseline needs, the baseline script and its library of the same release, the Python client `zaproxy` 0.6.0, and the Java runtime from the Debian archive of the base image.

## 3. The model (the law)
1. **The target check is INF-512's, unchanged.** `Targets` and `CheckTargets` are not edited. The task writes the list, reads the file back and checks it before any tool starts; a refusal gives `Refused` with `target-refused: ...` and starts no tool, for either profile. Profile `web-passive` reads only the lines of that checked list: the URL of each ZAP run is `<scheme>://<line>/` and its port is the port of the line. So no ZAP run can reach a target the check refuses.
2. **The scheme.** Port 443 is `https` and port 80 is `http`, with no probe. On any other port the runner tries a TLS handshake with the line's target, for at most 5 seconds, whatever the certificate (the Go client's minimum, TLS 1.2): `https` if it completes, else `http`. The probe sends no request and closes the connection.
3. **The arguments.** Each run is exactly `/zap/zap-baseline.py -t <url> -J zap-<port>.json -m 1 -z "-silent -dir <work>/zap-<port>"` with the environment `IS_CONTAINERIZED=true` and `HOME=<work>/zap-<port>`, where `<work>` is the work folder; the folder `zap-<port>` is created first and a stale `zap-<port>.json` removed. With these options the script runs ZAP's automation framework: passive-scan configuration, the spider capped at one minute, the wait for the passive scan, the summary and the JSON report into `/zap/wrk`. No active scan, no AJAX spider, no hook, no context, no configuration file. `-silent` makes ZAP send no unsolicited request and makes the script skip its add-on update run; `-dir` gives each run its own ZAP home. `--requests-per-second` is not passed to ZAP: it is the rate of Nuclei.
4. **Exit codes.** 0 (only passes), 1 (an alert at FAIL level) and 2 (an alert at WARN level) are results. Any other exit gives `Failed` with `zap-baseline.py exited <n>: <end of its standard error>; <end of its standard output>`, because the script prints the reason (for example `Job spider failed to access URL ...`) on its standard output. A port of the scope where nothing listens therefore fails the run. A missing report or a report that is not ZAP's gives `Failed` with `zap-<port>.json cannot be read: ...`. A failed run stores nothing.
5. **The SARIF conversion** (`ZAPRun` in `runner/sarif.go`). One SARIF 2.1.0 run per report: driver `ZAP`, its version from the report, `informationUri` `https://www.zaproxy.org/`; run property `target` is the URL. The rule of an alert is its `alertRef`, or its `pluginid` when that is empty; each rule is listed once, with properties `pluginId` and `cweId`. Each instance of an alert is one result at the instance's URI, with properties `confidence`, `method`, `param` and `evidence`; an alert without an instance is one result without a location. Levels follow ZAP's own SARIF report: risk code 3 (High) `error`, 2 (Medium) `warning`, 1 (Low) `note`, 0 (Informational) `none`. A report that is not ZAP's (`@programName`), has no site list, or holds an alert without plugin, without name or with another risk code is refused.
6. **The result.** `test.sarif.json` is one log with the runs in the order of the profiles in `--test-profile`: the runs of Nuclei's file unchanged, then one run per ZAP run in the order of the ports. `test.findings` counts all results. Before any tool starts, a missing template folder gives `Failed` with `nuclei-templates-not-in-image: ...` when `network-passive` is asked, and a missing baseline script `Failed` with `zap-not-in-image: ...` when `web-passive` is asked. A profile other than the two gives `Refused` with `not-supported: test-profile <profile>`.
7. **The image.** `tools.lock.yaml` gains `zap` 2.17.0 (the Linux release archive), `zap-baseline` and `zap-common` 2.17.0 (the two files `docker/zap-baseline.py` and `docker/zap_common.py` at the release tag) and `zaproxy` 0.6.0 (the wheel of the module `zapv2`), all Apache-2.0 and separate processes. The build copies ZAP's program, jar and folders `db`, `lang`, `lib`, `license` and `xml` to `/zap`, and of its 48 add-ons only `automation`, `callhome`, `commonlib`, `database`, `network`, `pscan`, `pscanrules`, `reports`, `retire` and `spider`, and checks that there are ten. This keeps ZAP's active-scan rules, fuzzer, brute-force and out-of-band add-ons out of the image, as INF-512 keeps only four folders of the Nuclei templates. It writes `/zap/zap-x.sh`, which runs `/zap/zap.sh` (there is no display), and links `/zap/wrk` to the work folder. The runtime stage installs `openjdk-21-jre-headless`, `python3-six`, `python3-requests` and `python-is-python3` from the archive of the base image (the first line of the script names `python`); pip installs the wheel with the two ansible wheels. The build line prints `python3 -c 'import zapv2, six, yaml'` and the ZAP version. `LICENSES.md` and the README name all of it.
8. No NodePort: nothing here creates a Service. No forbidden tool name enters `products/machine-runner`.

+// reads. Its fields match the keys of the report without regard to case (pluginid,
+// alertRef, riskcode, cweid, uri), as encoding/json matches them.
+type zapReport struct {
+	Program string `json:"@programName"`
+	Version string `json:"@version"`
+	Site    *[]struct {
+		Alerts []struct {
+			PluginID, AlertRef, Name, RiskCode, Confidence, CWEID string
+			Instances                                             []zapInstance
+		}
+	}
+}

+// ZAPRun converts the JSON report of one ZAP baseline scan of url into one SARIF 2.1.0 run
+// and returns it with its number of results. Each instance of an alert is one result at
+// the instance's URI; an alert without an instance is one result without a location. The
+// rule of a result is the alert's reference (its plugin when it has none). A report that
+// is not ZAP's, has no site list, or holds an alert without plugin, name or a known risk
+// code is refused.
+func ZAPRun(data []byte, url string) (json.RawMessage, int, error) {
+	var r zapReport
+	if err := json.Unmarshal(data, &r); err != nil {
+		return nil, 0, err
+	}
+	if r.Program != "ZAP" || r.Site == nil {
+		return nil, 0, errors.New("not a ZAP report with a site list")
+	}
+	rules, results, seen := []any{}, []any{}, map[string]bool{}
+	for _, site := range *r.Site {
+		for _, a := range site.Alerts {
+			level, ok := ZAPLevels[a.RiskCode]
+			if a.PluginID == "" || a.Name == "" || !ok {
+				return nil, 0, fmt.Errorf("an alert without plugin, name or a known risk code: %q", a.Name)
+			}
+			id := a.AlertRef
+			if id == "" {
+				id = a.PluginID
+			}

+				seen[id] = true
+				rules = append(rules, map[string]any{"id": id, "name": a.Name, "shortDescription": text(a.Name),
+					"properties": map[string]string{"pluginId": a.PluginID, "cweId": a.CWEID}})
+			}
+			instances := a.Instances
+			if len(instances) == 0 {
+				instances = []zapInstance{{}}

+func TLSHandshake(ctx context.Context, target string) bool {

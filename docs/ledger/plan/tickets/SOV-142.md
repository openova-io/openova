# SOV-142 — New nodes fetch k3s, Flux and Gateway API install files from the registry, with fallback

## In plain words

**The problem today.** A new control plane downloads the k3s installer, the Gateway API install manifest and the Flux install manifest from public upstream hosts at first boot. A Sovereign that must not depend on those hosts cannot boot without them, and the downloads are not checked against a known digest. The Hetzner boot text has almost no room left for a change of this size.

**What changes.** The boot template carries a small packed helper that fetches each of the three files from the origin registry named by the variables document, checks it against its digest, and only falls back to today's upstream address while a fallback switch is on, which is its default. Two small plain boot files travel packed to make room, and the render test checks the helper, its three uses and the default of the switch.

**Done means:**

- A new control plane takes the k3s installer, the Gateway API install manifest and the Flux install manifest from the origin registry when the registry serves them, and writes a file only when its SHA-256 matches the digest of the registry's manifest.
- When the origin registry does not serve a file, the node downloads it from the same upstream address as before and logs that it did, as long as the fallback switch is on; with the switch off the step fails.
- The render test fails when the helper, one of its three uses, or the default of the fallback switch is missing, and the stored golden hashes match the new render.
- The SSH hardening file and the unattended-upgrades file on a node keep their exact bytes, and the Hetzner renders with the kubeconfig post-back stay under their size guards, with no guard raised.
- The count of upstream address literals in the provider tree does not rise, and the Flux version pin test still finds the Flux release in the template.

The rest of this ticket is the exact instruction for the model that does the work.

## 2. End goal
A new control plane fetches the three files that it downloads from public hosts today, the k3s installer (`https://get.k3s.io`), the Gateway API install manifest and the Flux install manifest, from the origin registry named by its variables document (contract C5, `docs/contracts/c5-upstream-variables.schema.json`): repository `<REGISTRY_PATH_NODE_ARTIFACTS>/<name>` on `<ORIGIN_REGISTRY_SCHEME>://<ORIGIN_REGISTRY_HOST>`. A packed helper, `/var/lib/catalyst/oci_fetch`, does the fetch: manifest request, pull token from the realm the registry names when it answers 401, first-layer download, SHA-256 check against the layer digest. When the origin does not serve the file it downloads it from the upstream address the node used before, but only while `NODE_ARTIFACT_FALLBACK=true`, its default in the template; SOV-510 changes the default to `false`. The render test asserts the helper, its three uses and the default.

## 3. The model (the law)
1. The template `infra/providers/_shared/cloudinit-control-plane.tftpl` gets one new `write_files` entry, right after the entry `/var/lib/catalyst/variables.env` (the file the helper reads): path `/var/lib/catalyst/oci_fetch`, permissions `'0700'`, `encoding: gz+b64`, content `${base64gzip(<<-EOT ... EOT)}`, the convention the template already uses for packed files. The helper's text is fixed by the patch of this ticket; its 24 lines carry no comment, because a packed file loses no comment line. A comment block above the entry says what it does.
2. The helper's call is `sh /var/lib/catalyst/oci_fetch <repository> <tag> <output> <upstream address>`. It reads `ORIGIN_REGISTRY_HOST`, `ORIGIN_REGISTRY_SCHEME` and `REGISTRY_PATH_NODE_ARTIFACTS` from `/var/lib/catalyst/variables.env`. It requests `<scheme>://<host>/v2/<REGISTRY_PATH_NODE_ARTIFACTS>/<repository>/manifests/<tag>` with `Accept: application/vnd.oci.image.manifest.v1+json`. On 401 it reads `realm` and `service` from the `WWW-Authenticate: Bearer` header, asks `<realm>?service=<service>&scope=repository:<path>:pull` for a token (field `token` of the answer) and requests the manifest again with it. On 200 it downloads the blob of `.layers[0].digest` (following redirects, the token sent only to the registry host) and moves it to `<output>` only when `sha256:<SHA-256 of the blob>` equals that digest; otherwise it prints `oci_fetch: <repository>:<tag>: bad layer <digest>` to stderr and exits non-zero, with no fallback. In every other case (an empty host, no answer, a refused token, 404, any status but 200) the origin does not serve the file: it prints `oci_fetch: <repository>:<tag> not at the origin (<status>), fallback <true|false>: <upstream address>` to stderr and, only when `NODE_ARTIFACT_FALLBACK` is `true`, downloads `<output>` from the upstream address with `curl -fsSL --max-time 60`, as the node does today; when it is not `true` it exits non-zero. The script uses no numeric `exit`: its status is that of its last command. It removes its temporary files `<output>.oci` and `<output>.oci.h` when it ends.
3. The three artifacts, their repositories and tags, and the files the steps then use:
   - `k3s-install`, tag `${replace(k3s_version, "+", "-")}` (for `v1.31.4+k3s1` the tag is `v1.31.4-k3s1`; an OCI tag cannot hold `+`), output `/var/lib/catalyst/k3s-install.sh`, upstream `https://get.k3s.io`.
   - `gateway-api-experimental-install`, tag `v1.1.0`, output `/var/lib/catalyst/gwapi.yaml`, upstream `https://github.com/kubernetes-sigs/gateway-api/releases/download/v1.1.0/experimental-install.yaml`; the step then applies the file.
   - `flux-install`, tag `v2.4.0`, output `/var/lib/catalyst/flux.yaml`, upstream `https://github.com/fluxcd/flux2/releases/download/v2.4.0/install.yaml`; the step then applies the file.
   Each artifact is one OCI manifest whose first layer is the file itself. This ticket defines these names; the package that publishes node artifacts to the registry uses them.
4. The three `runcmd` steps keep their retry loops, their failure markers and their exit codes (88, 95, 93). Only the download inside each changes: the k3s step runs the helper instead of `curl ... https://get.k3s.io -o /var/lib/catalyst/k3s-install.sh`; the Gateway API step runs the helper and then `kubectl apply -f /var/lib/catalyst/gwapi.yaml` instead of `kubectl apply -f <the upstream address>`; the Flux step runs the helper and then `kubectl apply -f /var/lib/catalyst/flux.yaml` instead of `curl ... | kubectl apply -f -`. The upstream address of each stays on its line, so the Flux version pin test (`platform/flux/chart/tests/version-pin-replay.sh`) still reads `v2.4.0` there.
5. Room in the Hetzner render. Two plain `write_files` entries become packed with the same convention: `/etc/ssh/sshd_config.d/99-catalyst-hardening.conf` and `/etc/apt/apt.conf.d/52unattended-upgrades-catalyst`. Their paths, permissions and the bytes on the node do not change; the one comment line of the SSH file, which the modules' comment strip already removed from every render, is no longer written. This saves 245 bytes of the Hetzner render.
6. The render test `infra/providers/_shared/tests/cloudinit_render.tftest.hcl` gains four asserts in each of the runs `hetzner_render_is_valid` and `huawei_render_is_valid`: the entry is written once, before `runcmd`; each of the three steps calls the helper once with its tag, output and an upstream address, and the helper is called three times in all; no direct download of the three files is left; the template sets `NODE_ARTIFACT_FALLBACK=true` once. The golden values in `infra/providers/_shared/tests/golden.auto.tfvars.json` are the hashes of the new render.
7. No module, no module input, no size guard, no other `write_files` entry and no other `runcmd` step changes. The worker templates do not change (field 11). Nothing is deleted.

# SOV-142 — New nodes fetch k3s, Flux and Gateway API install files from the registry, with fallback

## In plain words

**The problem today.** A new control plane downloads the k3s installer, the Gateway API install manifest and the Flux install manifest from public upstream hosts at first boot. A Sovereign that must not depend on those hosts cannot boot without them, and nothing checks what it downloaded.

**What changes.** First boot carries a small helper that fetches each of the three files from the origin registry named by the Sovereign's variables, checks it against its digest, and falls back to today's upstream address only while a fallback switch is on, which is its default. The render test checks the helper, its three uses and the default of the switch.

**Done means:**

- A new control plane takes the k3s installer, the Gateway API install manifest and the Flux install manifest from the origin registry when the registry serves them, and writes a file only when its SHA-256 matches the digest in the registry's manifest.
- When the origin registry does not serve a file, the node downloads it from the same upstream address as before and logs that it did, while the fallback switch is on; with the switch off the step fails.
- The render test fails when the helper, one of its three uses, or the default of the fallback switch is missing, and the stored golden values match the new render.
- Every file a node wrote before keeps its bytes; the only new file is the helper.
- Every worst-case control-plane surface stays under its limit, no limit is raised and no entry is packed to make room.
- The guard that refuses a client-side apply of a Secret, or of a file it cannot read, still passes, and it names the two fetched install manifests as what they are.

The rest of this ticket is the exact instruction for the model that does the work.

## 3. The model (the law)
1. Why these bytes are in the first-boot user data. The helper runs before k3s exists (the k3s installer) and before Flux exists (the Gateway API and Flux install manifests), so neither Flux nor OpenBao can deliver it. It is the only thing this ticket adds to the user data.
2. The template `infra/providers/_shared/cloudinit-control-plane.tftpl` gets one new `write_files` entry, right after the entry `/var/lib/catalyst/variables.env` (the file the helper reads) and before the entry `/var/lib/catalyst/flux-bootstrap.yaml`: path `/var/lib/catalyst/oci_fetch`, permissions `'0700'`, `encoding: gz+b64`, content `${base64gzip(<<-EOT ... EOT)}`. That is the form of its packed neighbours (the bootstrap Secret entries); the entry is not packed to make room, and SOV-153 writes it plain with the other packed entries. A comment block above the entry says what the helper does. The helper itself carries no comment line.
3. The helper's call is `sh /var/lib/catalyst/oci_fetch <repository> <tag> <output> <upstream address>`. It reads `ORIGIN_REGISTRY_HOST`, `ORIGIN_REGISTRY_SCHEME` and `REGISTRY_PATH_NODE_ARTIFACTS` from `/var/lib/catalyst/variables.env`. It requests `<scheme>://<host>/v2/<REGISTRY_PATH_NODE_ARTIFACTS>/<repository>/manifests/<tag>` with `Accept: application/vnd.oci.image.manifest.v1+json`. On 401 it reads `realm` and `service` from the `WWW-Authenticate: Bearer` header, asks `<realm>?service=<service>&scope=repository:<path>:pull` for a token (field `token` of the answer) and requests the manifest again with it. On 200 it downloads the blob of `.layers[0].digest` (following redirects; curl sends the token to the registry host only) and moves it to `<output>` only when `sha256:<SHA-256 of the blob>` equals that digest; otherwise it prints `oci_fetch: <repository>:<tag>: bad layer <digest>` to stderr and exits non-zero, with no fallback. In every other case (an empty host, no answer, a refused token, 404, any status but 200) the origin does not serve the file: it prints `oci_fetch: <repository>:<tag> not at the origin (<status>), fallback <true|false>: <upstream address>` to stderr and, only when `NODE_ARTIFACT_FALLBACK` is `true`, downloads `<output>` from the upstream address with `curl -fsSL --max-time 60`, as the node does today; when it is not `true` it exits non-zero. The helper uses no numeric `exit`: its status is that of its last command. It removes its temporary files `<output>.oci` and `<output>.oci.h` when it ends. The file the node gets is exactly these 24 lines (1,125 bytes, SHA-256 `edbe98eeb3d54922bc764b93299c830f6d963474f80abfa8df9730191bc995dd`). This block is for reading only; work step 3 writes it.
```text
#!/bin/sh
NODE_ARTIFACT_FALLBACK=true
v() { sed -n "s/^$1=//p" /var/lib/catalyst/variables.env; }
h=$(v ORIGIN_REGISTRY_HOST) r=$(v REGISTRY_PATH_NODE_ARTIFACTS)/$1 o=$3.oci s= t=
u=$(v ORIGIN_REGISTRY_SCHEME)://$h/v2/$r
trap 'rm -f $o $o.h' 0
c="curl -sS --connect-timeout 10 -m 300"
m="Accept: application/vnd.oci.image.manifest.v1+json"
if [ -n "$h" ]; then
  s=$($c -o $o -D $o.h -w '%{http_code}' -H "$m" $u/manifests/$2)
  if [ "$s" = 401 ]; then
    t=$($c -f "$(tr -d '\r' < $o.h | sed -n 's/.*realm="\([^"]*\)",service="\([^"]*\)".*/\1?service=\2/p')&scope=repository:$r:pull" | jq -r .token)
    s=$($c -o $o -w '%{http_code}' -H "$m" -H "Authorization: Bearer $t" $u/manifests/$2)
  fi
fi
if [ "$s" = 200 ]; then
  d=$(jq -r '.layers[0].digest' $o)
  $c -fL -o $o ${t:+-H "Authorization: Bearer $t"} $u/blobs/$d && [ "sha256:$(sha256sum $o | cut -d' ' -f1)" = "$d" ] && mv $o $3 && exit
  echo "oci_fetch: $1:$2: bad layer $d" >&2
  false
else
  echo "oci_fetch: $1:$2 not at the origin ($s), fallback $NODE_ARTIFACT_FALLBACK: $4" >&2
  [ "$NODE_ARTIFACT_FALLBACK" = true ] && curl -fsSL --max-time 60 $4 -o $3
fi
```

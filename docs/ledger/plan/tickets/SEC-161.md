# SEC-161 — Reconciler: secrets mounts and accessor substitution

## In plain words

**The problem today.** The OpenBao configuration reconciler can enable auth mounts but no secrets engine, so every engine still depends on the one-shot setup job. A policy cannot yet name the namespace or the service account of a pod, because that needs the accessor of the auth mount, and the accessor differs on every installation. The reconciler is also forbidden to change its own policy, so only that setup job can ever widen it.

**What changes.** The reconciler can enable secrets mounts, and it fills in the accessor of its login mount in every payload before it sends it. Its own policy becomes the first item it writes, and the kv mount becomes part of its desired state.

**Done means:**

- The desired state of the chart starts with the policy of the reconciler itself, followed by the kv mount secret/.
- A second pass of the reconciler enables no mount again and changes nothing.
- A policy whose text names the accessor placeholder is stored in OpenBao with the real accessor of the login mount in its place.
- When the listing of auth mounts holds no accessor for the login mount, the pass ends with a warning and that policy is not written.
- The reconciler may enable the kv mount secret/ and no other secrets mount, and it still may not change its own role.
- The chart tests and the test against real OpenBao servers pass on the pull request.

The rest of this ticket is the exact instruction for the model that does the work.

## 2. End goal
The OpenBao configuration reconciler of the chart `platform/openbao/chart` (the Deployment `openbao-config`, which runs `files/openbao-config-reconcile.sh` against the ConfigMap `openbao-config-desired`) has three new abilities, on the OpenBao version the chart runs today. It enables a secrets mount when the listing of secrets mounts does not hold it (a new operation kind, `secrets-mount`). Before it sends any payload, it replaces every occurrence of the text `AUTH_ACCESSOR_KUBERNETES` by the accessor of its own login mount, so that a policy can name the namespace and the service account of a pod. And it may write its own policy: that write is the first operation of the desired state, so a later chart version can change the policy without the setup job. The kv mount `secret/` is the second operation. Later packages add their mounts and policies on top of these three abilities.

## 3. The model (the law)
1. The desired state keeps its format. ConfigMap `openbao-config-desired` holds a file `manifest` with one operation per line, `<kind> <path> [<probe URL>]`, and one payload file per operation, named after the path with every `/` replaced by `.`, plus `.json`. Empty lines and lines starting with `#` are skipped. Operations run top to bottom.
2. The kinds after this ticket:
   - `write <any API path>`: POST the payload. A failed write to a path that starts with `sys/policies/` ends the pass (unchanged).
   - `mount sys/auth/<name>`: POST the payload unless the listing of `sys/auth` contains `"<name>/"` (unchanged).
   - `secrets-mount sys/mounts/<name>` (new): POST the payload unless the listing of `sys/mounts` contains `"<name>/"`. On success it logs `enabled secrets mount <name>/`; on failure it logs `WARN: enable secrets mount <name>/ failed` and marks the pass pending, like `mount`.
   - A probe URL that does not answer skips the operation for this pass (unchanged).
3. Each pass reads the listing of `sys/mounts` once, right after the existing read of `sys/auth`. If that read fails, the pass logs `WARN: cannot list secrets mounts`, forgets the login token and ends with a non-zero result, exactly as the existing read of `sys/auth` does.
4. Accessor substitution. Each pass reads the accessor of the auth mount named by the environment variable `BAO_K8S_AUTH_PATH` once, from the `sys/auth` listing it already holds, with this exact line:
   ```sh
   acc="$(printf '%s' "${mounts}" | tr -d '\n' | sed -n "s/.*\"${BAO_K8S_AUTH_PATH}\/\":{\"accessor\":\"\([^\"]*\)\".*/\1/p")"
   ```
   Before an operation sends its payload: if the payload file contains the text `AUTH_ACCESSOR_KUBERNETES`, every occurrence is replaced by the accessor, the result is written to the file named by `PAYLOAD_FILE` (default `/tmp/openbao-config-payload.json`; `/tmp` is the writable `emptyDir` of the Deployment), and that file is sent. If the accessor is empty and a payload contains the text, the script logs `WARN: no accessor for <value of BAO_K8S_AUTH_PATH>` and ends the pass with a non-zero result; that payload is not sent. A payload without the text is sent from its own file, byte for byte as before.
5. Policy `openbao-config-admin` (the define `openbao.configAdminPolicy` in `platform/openbao/chart/templates/_config.tpl`): the two lines that make the reconciler's own policy read-only are removed (`path "sys/policies/acl/openbao-config-admin" { capabilities = ["read"] }` and `path "sys/policy/openbao-config-admin" { capabilities = ["read"] }`). One line is added after `path "sys/mounts" { capabilities = ["read"] }`: `path "sys/mounts/<kv mount>" { capabilities = ["create", "update"] }`, where `<kv mount>` is the value `autoUnseal.kubernetesAuth.kvMountPath` (default and only value today: `secret`). The line `path "auth/+/role/openbao-config-admin" { capabilities = ["read"] }` stays: the reconciler may not change its own role.
6. The ordered operations (the define `openbao.configOps`) start with two new operations, before every other one: first `write sys/policies/acl/openbao-config-admin` with the payload `{"policy": <the text of openbao.configAdminPolicy>}`, then `secrets-mount sys/mounts/<kv mount>` with the payload `{"options":{"version":"2"},"type":"kv"}`. The order of every other operation is unchanged. The rule "every policy write comes before every other operation" now leaves out `secrets-mount` operations.
7. The setup hook `templates/auth-bootstrap-job.yaml` is not changed. It still mounts the kv engine and still writes policy `openbao-config-admin` on every install and upgrade, from the same define, so it writes the new text.
8. The reconciler gets no access to the Kubernetes API and reads no other ConfigMap. `templates/config-reconciler.yaml` is not changed: it renders every operation kind the same way.
9. No version line changes. The release writer bumps the chart version after the merge.
10. The three test files assert the new behaviour: `config-desired-render.sh` (scope of the policy, first two operations), `config-reconcile-idempotence.sh` (against a fake OpenBao: the kv mount is enabled once, the accessor is substituted, a missing accessor ends the pass) and `tests/e2e/bp-openbao-config-live.sh` (against real OpenBao servers).
11. `platform/openbao/README.md` item 3a no longer says that the reconciler cannot rewrite its own grant.

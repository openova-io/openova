# NET-210 — Availability zone per region and a separation output

## In plain words

**The problem today.** A Sovereign with two regions may or may not survive the loss of one failure domain, and the cloud modules do not say which in a value of their own. The record of the network carries the answer, but no test shows that two regions given two zones really land in two zones, load balancers included, or that the default request stays in one zone.

**What changes.** Both cloud modules give the region separation as an output of its own, the same value as in the network record. The test of the reference module plans two regions in two zones and checks every subnet, node and load balancer, and checks that the default request and a single region give none.

**Done means:**

- Both cloud modules have the output region_separation, and its value is the region separation of the network record.
- A plan with two regions in two zones of one cloud region puts each region's subnet and nodes in its own zone and both load balancers in the primary region's zone, and gives zone.
- A plan of the default two-region request, which names no zone, keeps every subnet, node and load balancer in the module's one default zone and gives none.
- Two regions that name the same zone give none, and so does a single region.
- No resource of either module changes: only an output and module test runs are added.

The rest of this ticket is the exact instruction for the model that does the work.

## 2. End goal
The OpenTofu modules `infra/providers/huawei` and `infra/providers/hetzner` each have the output `region_separation`. Its value is `none`, `zone` or `site`, and it is always the same as the field `regionSeparation` of the output `network_registry`, because both read one local, `local.network_registry_separation`. The module test of the reference module (`infra/providers/huawei/tests/multi_region.tftest.hcl`) has four new runs. With two regions of one cloud region in two zones, every subnet and node is planned in its own region's zone, both load balancers in the primary region's zone, and the output is `zone`. The default two-region request, which names no zone, plans everything in `var.huawei_az` and gives `none`. Two regions that name the same zone give `none`, and so does one region. No resource of either module changes.

## 3. The model (the law)
1. **One value, one source.** The output `region_separation` of each module is `local.network_registry_separation`, the local that already fills `regionSeparation` of `network_registry`. No second computation of the separation is written.
2. **The rule.** `site` when every region has its own cloud region; `zone` when the cloud regions repeat but every region has its own pair of cloud region and zone; `none` otherwise, and always for one region. The reference module refuses two different cloud regions, so it gives `zone` or `none`. The Hetzner module has no zones: it gives `site` when every region has its own location, else `none`. Both rules are already in the two `main.tf` files; this ticket does not change them.
3. **The zone of a region.** In the reference module a region's zone is its `availability_zone`, or `var.huawei_az` when that is empty (`local.region_az`). Subnet, control-plane nodes and workers use their own region's zone. The two load balancers (`primary` and `console`) stand in the primary region, so they use the primary region's zone.
4. **No change for a running Sovereign.** A request without zones plans every resource exactly where it was planned before: in `var.huawei_az`. This ticket changes no resource, no variable and no local: it appends one output block to each `outputs.tf` and four runs to the end of the reference module test.
5. **Not in the contract.** `region_separation` stays a module output. The contract (`infra/providers/_contract/contract.json`) lists an output only when shared code reads it, and this ticket adds no such reader. The reserved row of `region_separation` in `infra/providers/PROVIDER-INTERFACE.md` is not changed.
6. **No second provider configuration.** The reference module keeps one provider configuration and the one-zone default of `var.huawei_az`. The lab result `docs/ledger/plan/spikes/NET-300.md` measured one zone on the reference cloud: every real multi-region Sovereign there gives `none`.

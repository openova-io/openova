# SEC-217 — secrets-lib writes a generated secret into a named namespace

## In plain words

**The problem today.** The secrets library writes every generated value, and runs the Job that creates it, in the namespace of the release that includes it. OpenBao lets that Job create a value only below its own namespace. A chart released in one namespace whose reader runs in another, such as the console chart and the auth service, therefore cannot give its reader a generated secret at all.

**What changes.** A chart can name the namespace of its generated values. The values, their birth Job and everything the Job needs are then rendered in that namespace, and a chart that names none renders exactly what it rendered before.

**Done means:**

- A chart that names no namespace, or names it as null, renders exactly what it rendered before, the name of the birth Job included.
- A chart released in one namespace that names another renders every value, the birth Job, its account, its plan, its OpenBao paths and its peer roles in the named namespace, and nothing in its own.
- Against a real OpenBao, a birth Job of the release namespace given the plan of the named namespace is refused and writes nothing, and the Job of the named namespace writes the value.
- An empty or malformed namespace fails the render with a message that names it.
- The library README documents the input, and its table of templates lists all three templates.

The rest of this ticket is the exact instruction for the model that does the work.

## 2. End goal
A platform chart that includes `openova.generatedSecrets` can pass `"namespace" <name>` and have its generated values written for a reader that runs in that namespace, not in the release namespace: the Password, PushSecret and ExternalSecret of a synced value, the birth Job of the mounted values with its ServiceAccount `secrets-birth` and plan ConfigMap, the plan paths `<ns>/sa/...` and `<ns>/shared/...`, the remote keys `openova/apps/<ns>/...` and the peer roles `secrets-birth-<ns>` and `openbao-peer-birth-<ns>` all name the given namespace. `openova.secretStores` takes the same input, so a synced value reads through the store of its own namespace. A chart that passes no namespace is unchanged. The first consumer is SEC-212 (the console chart, released in catalyst-system, gives the auth service in org-services its signing secret).

## 3. The model (the law)
1. `openova.generatedSecrets` takes an optional input `namespace`. Absent or null: the release namespace, as before. Given: a namespace name (a DNS label: `^[a-z0-9]([-a-z0-9]*[a-z0-9])?$`, at most 63 characters); anything else, the empty string included, fails the render with `openova.secrets: namespace "<value>" is not a namespace name (a DNS label)`.
2. The namespace is carried to every object and path the template renders for its values: the `metadata.namespace` of the Password, PushSecret, ExternalSecret, Job, ServiceAccount `secrets-birth` and ConfigMap; every path of the birth plan; the remote key of the PushSecret and the ExternalSecret; and the Job's `PEER_ROLE` and `PEER_TOKEN_ROLE`. No object of a value stays in the release namespace.
3. `openova.secretStores` takes the root context (the release namespace, as before) or `dict "ctx" . "namespace" <name>`, and renders ServiceAccount `eso-reader` and SecretStore `openbao` in that namespace. One helper, `openova.secretsNamespace` in `_generated-secrets.tpl`, decides the namespace for both templates.
4. A birth Job writes only below its own namespace. The OpenBao policy `secrets-birth` grants create on `mounted/data/<its namespace>/*` only (`platform/openbao/chart/templates/_config.tpl` lines 178 to 190) and role `secrets-birth` binds the account `secrets-birth` in every namespace (line 402). So the Job runs in the named namespace, and a Job of the release namespace given the plan of another namespace is refused (L9). No policy or role of bp-openbao changes.
5. A chart that does not name the namespace renders byte for byte what it rendered before, the Job name included (the plan, script, image, peers and address it hashes are unchanged).
6. One namespace per include. The library renders no Namespace: the named namespace must exist, and the release must be allowed to write there. A shared value in a named namespace needs that namespace in bp-openbao `peerTrust.birthNamespaces` of every region, as any shared value does.
7. No chart consumes the library at this commit; this package adds no consumer. No new Python, no yq in the tests, no change to a live system, and the version line of `platform/secrets-lib/chart/Chart.yaml` is not touched.

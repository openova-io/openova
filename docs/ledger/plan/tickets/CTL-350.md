# CTL-350 — Applications views from the informer cache

## In plain words

**The problem today.** Every time the Applications page of a Sovereign asks for its list, the API reads three whole kinds of objects from the cluster again, although it already keeps a live copy of the same objects in memory. The page asks every few seconds, so the cluster answers the same three questions over and over. The API also still serves two status streams that work by asking the cluster on a timer, and no screen opens either of them.

**What changes.** The list of the Applications page is built from the copy the API already keeps, and the cluster is asked directly only while that copy is not ready. The two unused status streams and the two unused address helpers of the console are gone.

**Done means:**

- On a Sovereign whose copy of the cluster state is ready, a request for the Applications list makes no list call to the cluster.
- The answer of the Applications list is the same, byte for byte, as before for the same cluster state.
- While the copy of one kind of object is not ready, that kind alone is read from the cluster, once per request, and the API logs it.
- On the mothership the Applications list still reads its own cluster directly and never reads another Sovereign's copy.
- The Application status stream and the Continuum status stream are gone from the router and from the route list.
- The size guard of the API handler package and the polling guard record the deleted code.

The rest of this ticket is the exact instruction for the model that does the work.

## 2. End goal
`GET /api/v1/sovereign/apps` (`HandleSovereignApps`) of catalyst-api builds its answer from the informer cache that the API already keeps for the cluster it runs in. On a Sovereign whose cache is synced, one request makes no LIST call to the API server for HelmReleases, HTTPRoutes or Applications. While the informer of one of these kinds has not synced, the handler lists that one kind live, once, and logs it. On the mothership, whose own cluster is not in the cache, the handler reads live as before. The answer is the same, byte for byte, for the same objects. The two status streams that poll the cluster on a timer and that no front end opens, `GET /api/v1/sovereigns/{id}/applications/{name}/stream` and `GET /api/v1/sovereigns/{id}/continuum/{name}/stream`, are deleted with their handlers, their helpers, and their lines of the route list. The two unused address helpers of the console, `applicationStreamURL` and `continuumAuditStreamURL`, are deleted.

## 3. The model (the law)
1. **One read path.** `HandleSovereignApps` gets HelmReleases, HTTPRoutes and Applications only through the new method `sovereignAppsList` of `products/catalyst/bootstrap/api/internal/handler/sovereign.go`. Nothing else in the handler changes: the same joins, the same rows, the same order.
2. **When the cache answers.** `sovereignAppsList(ctx, deps, kind, gvr)` reads the cache when all of these hold: the handler has a cache (`h.k8sCache != nil`); `h.resolveChrootClusterID("")` returns a cluster id that is not empty; `h.k8sCache.Synced()[id][kind]` is true; and `h.k8sCache.List(id, kind, labels.Everything())` returns no error. The kinds are `helmrelease`, `httproute` and `application`.
3. **What the cache path returns.** A deep copy of every object, sorted by the text `<namespace>/<name>`. That is the order in which the API server lists a namespaced kind across all namespaces, and the handler's result depends on it (the order of the cards, and which of two objects with one name wins).
4. **Otherwise one live LIST.** In every other case the method writes one log line at level Info (`sovereign apps: informer cache not synced for this kind, one live LIST`, with the key `kind`) and makes one LIST of the kind across all namespaces with the client of `deps`. It returns the items, or the error unchanged. The handler's rule that a failed Application LIST means "could not ask", not "none", stays.
5. **The mothership.** With `SOVEREIGN_FQDN` unset, `resolveChrootClusterID("")` returns the empty text, so the handler never reads the cache there. The cache of the mothership holds the clusters of other Sovereigns, never its own.
6. **No informer is added.** The three kinds are registered in `products/catalyst/bootstrap/api/internal/k8scache/kinds.go` with the same group, version and resource the handler lists. `internal/k8scache` is not changed.
7. **Deleted from the API.** The methods `HandleApplicationStream` and `HandleContinuumStream`; their two routes in `cmd/api/routes_sovereigns.go`; their two lines in `cmd/api/testdata/routes.golden`; the constants `applicationStreamPingInterval` and `applicationStreamPollInterval` and the variable `timeNewTicker` of `applications.go`; the functions `writeSSEFrame` and `continuumStreamUnavailableFrame` of `continuum_extras.go`; the imports that only this code used (`encoding/json` and `time` in `applications.go`, `encoding/json` in `continuum_extras.go`); and the comment lines that name the two routes or `timeNewTicker`.
8. **Deleted from the console.** The functions `applicationStreamURL` of `products/catalyst/bootstrap/ui/src/lib/catalog.api.ts` and `continuumAuditStreamURL` of `products/catalyst/bootstrap/ui/src/lib/continuum.api.ts`, and the comment line of `catalog.api.ts` that names the stream route.
9. **Baselines.** `scripts/baselines/api-structure.json` and `scripts/baselines/polling.json` are written by their own guards (`--write-baseline`). Neither is edited by hand.

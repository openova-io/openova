# BSS-071 — Deleting an Organization from the storefront removes it and its namespaces in every region

## In plain words

**The problem today.** When an Organization that a customer bought through the storefront is deleted, the storefront answers that it is deleted, but the Organization and its namespaces stay in both regions. The platform's own delete answers not found, because it looks only among the Organizations made through the console, so the teardown of the Organization never starts.

**What changes.** The platform's delete also finds an Organization the storefront made, by its tenant id or by its name, and deletes it. That starts the same teardown that already removes every other Organization from every region.

**Done means:**

- The platform's delete of an Organization the storefront made answers 204 and removes that Organization's object, whether it is addressed by its tenant id or by its name.
- That delete touches no other Organization, and an id that names no Organization still answers 404.
- A delete that the cluster refuses answers 502 with the cluster's own reason, for an Organization of either origin.
- An Organization made through the console is deleted exactly as before.
- In the next gate run on the two-region Sovereign, check BSS-G01 finds no Organization and no namespace of its journey left in either region after its delete.

The rest of this ticket is the exact instruction for the model that does the work.

## 2. End goal
`DELETE /api/v1/organizations/{id}` of catalyst-api deletes an Organization that the storefront created. Such an Organization has no record in the console's provisioning store, only its Organization object (`orgs.openova.io/v1` `organizations`, cluster-scoped), named after the slug and labelled `openova.io/tenant-id` with the storefront's tenant id, and the console lists it under that tenant id. For an id without a record the route now finds the objects that the id names (by that label or by the name) and deletes each through the existing object delete of the recorded path. The Organization controller's finalizers then remove the per-region Flux files and, through them, the Organization's namespace and vCluster in every region, as they already do for an Organization made through the console. Gate check BSS-G01 step 9 then sees no Organization object and no namespace of its journey left in either region.

## 3. The model (the law)
1. An id with a record in the provisioning store takes the recorded path unchanged: overlay reap, object delete, registry, DNS and event, in that order.
2. An id without a record is answered by the new package `products/catalyst/bootstrap/api/internal/orgdelete` (function `Unrecorded`): no in-cluster client gives 404 `org-tenant-not-found` (as the GET of the same path); a refused list of Organization objects gives 502 `organization-cr-read-failed` (a list that could not be read is never answered as an Organization that does not exist); no object named by the id gives 404 `org-tenant-not-found`; otherwise each named object is deleted and the answer is 204.
3. An object is named by the id when its label `openova.io/tenant-id` equals the id, or when its name equals the id in lower case (`orgdelete.Names`). No other object is deleted.
4. The object is deleted only through `Handler.deleteOrgOrganizationCR` (`products/catalyst/bootstrap/api/internal/handler/org_tenant_org_cr.go`), so the change adds no cluster write of its own and needs no new grant. A refused delete answers 502 with the body `orgdelete.Refused`: `error` `organization-cr-delete-failed`, `detail` the apiserver's text cut at 512 bytes, and the same `hint` as before; the recorded path uses the same body.
5. No provision record is written for an id without one, and no overlay reap runs for it.
6. Nothing is deleted from the tree; no chart, no go.mod, no ClusterRole and no version line changes. The code lives in its own package because the handler package's line count is held by the api-structure ratchet.

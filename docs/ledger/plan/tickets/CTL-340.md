# CTL-340 — Jobs store subscribe; flow stream event-driven; jobs stream route

## In plain words

**The problem today.** The Jobs page and the flow canvas learn about changes only by asking again: the canvas stream rebuilds its picture every three seconds, and nothing tells a reader that a job changed. A run whose Kubernetes Job finished and was then deleted, by its time to live or by a Helm hook policy, reads Running forever, because only a later listing of the cluster could close it and the deleted Job is no longer listed.

**What changes.** The jobs store tells its subscribers about each write, a new stream route passes these hints to the browser, and the canvas stream sends a new picture only after something changed. The watch of Jobs in the shared informer cache closes a run with the outcome the Job itself recorded, and finds the run by the unique id of the Job.

**Done means:**

- A reader of the jobs stream of a deployment receives a frame shortly after one of its jobs changes.
- The flow canvas stream sends a new snapshot after a change, not on a three-second timer, and it keeps its heartbeat.
- A run whose Job finished and was then deleted shows the outcome the Job recorded instead of Running.
- A run whose Job disappeared without a recorded outcome is not marked Succeeded or Failed.
- Two Jobs with the same name, in two namespaces or one after the other, are two different runs.
- The polling guard counts one ticker less, and the size guard of the API handler package records no growth.

The rest of this ticket is the exact instruction for the model that does the work.

## 2. End goal
`jobs.Store` of catalyst-api (`products/catalyst/bootstrap/api/internal/jobs`) has `Subscribe`: every successful write (`UpsertJob`, `StartExecution` and `StartJobRun`, `FinishExecution`, `AppendLogLines`, `CloseJobRun`) publishes one `Change` to the subscribers of its deployment. The new route `GET /api/v1/deployments/{depId}/jobs/stream` sends one `event: jobs` frame per change and a `: ping` comment every 20 seconds. The local flow stream (`flowStreamLocal`) sends a `snapshot` frame after a change, at most one per 250 milliseconds, instead of every 3 seconds; its 15-second heartbeat stays. Every run the seed records for a Kubernetes Job (a CronJob run, a standalone task run, a scanner run, an install-hook run) carries the Job's `metadata.uid`, and the new package `internal/jobwatch` subscribes to the `job` kind of the informer cache and closes such a run when the Job object shows a terminal condition, in an added, modified or deleted event. A run whose Job disappears without a terminal condition is left as it is. The polling guard counts one ticker less in `flow_snapshot_local.go`, and the size guard of the handler package records one line less and the same number of methods.

## 3. The model (the law)
1. **Changes.** `jobs.Change` has the fields `DeploymentID`, `JobID` (empty for `log-appended` and `resync`), `ExecutionID` (empty for `job-upserted` and `resync`), `Kind`, `Seq` and `At`. `Kind` is a `jobs.ChangeKind`: `job-upserted`, `execution-started`, `execution-finished`, `log-appended` or `resync`. `Seq` increases by one per published change of one store instance; `At` is the time of publishing, in UTC. A change is a hint: the reader refetches. `resync` means "refetch everything for this deployment".
2. **Subscribe.** `func (s *Store) Subscribe(deploymentID string) (ch <-chan Change, cancel func())` delivers every later change of one deployment; `""` means every deployment. The channel holds `jobs.SubscribeBuffer` (256) changes. When a publish finds it full, the changes it holds are dropped and one `resync` change is put in their place, so the next change the reader receives is the `resync`. `cancel` closes the channel and may be called more than once. A publish never waits for a reader, and it uses its own lock, never the lock of the writes.
3. **Publishing.** A write publishes after it has written the index, and only then. `UpsertJob` publishes `job-upserted`; `StartExecution` and `StartJobRun` publish `execution-started`; `FinishExecution` and `CloseJobRun` publish `execution-finished`; `AppendLogLines` publishes `log-appended`. `UpsertJob` whose merged row equals the stored row writes nothing and publishes nothing, so a re-seed of an unchanged tree sends no change.
4. **The stream.** `jobs.StreamHandler(access jobs.StreamAccess) http.HandlerFunc` serves `GET /api/v1/deployments/{depId}/jobs/stream`. `StreamAccess` is `func(w http.ResponseWriter, r *http.Request, deploymentID string) (*jobs.Store, bool)`: the caller injects it, so package `jobs` does not import package `handler`. The handler answers 400 `{"error":"missing-depId"}` for an empty id, leaves the answer to the access check when it returns false, subscribes before it writes the header, and then writes `text/event-stream` with one frame per change:
   ```
   event: jobs
   data: {"deploymentId":"…","jobId":"…","executionId":"…","kind":"job-upserted","seq":41}
   ```
   and the comment line `: ping` every 20 seconds. Empty ids are sent as `""`. There is no replay. The route sits in the session group, so a request without a session gets 401 there.
5. **The access check** is the new method `func (h *Handler) JobsReadAccess(w, r, depID) (*jobs.Store, bool)` in `internal/handler/jobs.go`: 503 `{"error":"jobs-store-unavailable"}` without a jobs store; the deployment is looked up as `ListJobs` looks it up (`chrootEnsureDeployment`, then the in-memory map); 404 `{"error":"deployment-not-found"}` when it is unknown; then `checkOwnership`, which answers 404 for the deployment of another owner.
6. **The flow stream.** `flowStreamLocal` subscribes to its deployment before it writes the first snapshot, turns the change channel into a signal with `jobs.Coalesce(ctx, changes, 250ms)`, and writes a `snapshot` frame on each signal. `Coalesce` fires once at the end of a 250-millisecond window that the first change after a quiet spell opens, however many changes come in it; it uses a `time.Timer`, not a ticker. The ticker of 3 seconds is deleted; the heartbeat ticker of 15 seconds stays.
7. **Runs carry the UID of their Job.** `helmwatch.ReconcilerExecution` gains `UID` and `helmwatch.ReconcilerObservation` gains `JobUID`, both set from the Job's `metadata.uid` where `ListReconcilerObservations` reads a Job (a CronJob run, a task run, a scanner run, an install hook). The jobs mirror types gain the same fields, `reconcilerObsToBridge` copies them, and `jobs.Execution` gains `JobUID` (JSON `jobUid`, omitted when empty). The seed writes it through the new `StartJobRun(deploymentID, jobName, jobUID, startedAt)`; `StartExecution` is `StartJobRun` with an empty UID. Runs recorded before this change carry no UID.
8. **Closing a run.** `func (s *Store) CloseJobRun(deploymentID, jobUID, status string, finishedAt time.Time) (bool, error)` sets the open Execution that carries `jobUID` to `status` (succeeded or failed) with `FinishedAt`. It returns false and changes nothing when the id or the UID is empty, when the deployment has no index (it never creates a directory), or when no open Execution carries the UID. A non-terminal status is an error. When the parent leaf is of kind cron or task, the leaf takes the headline of all its stored runs by the three rules of `resolveRunHeadline`, which now live in one function, `foldRunHeadline`, used by the seed and by `CloseJobRun`; when the closed run is the leaf's latest, the leaf gets its `FinishedAt` and duration. A leaf of any other kind (an install leaf with a hook run) keeps its status.
9. **The Job watch.** `jobwatch.Run(ctx, src, st, log)` subscribes to the kind `job` of the informer cache and calls `jobwatch.Handle` for each event. `Handle` acts only on kind `job` with an object and a non-empty `metadata.uid`. The outcome is read only from the Job's own conditions, through `helmwatch.JobRunStatus` (exported from `jobRunStatus`): `Complete` or `SuccessCriteriaMet` with status `True` is succeeded, `Failed` with status `True` is failed, at the condition's `lastTransitionTime` (the event time when the condition has none). Anything else gives no verdict and no write. The cluster id of the event is the deployment id of the store. `Handler.SetK8sCache` starts `jobwatch.Run` once when both the factory and the jobs store exist.
10. **Never.** No outcome is taken from log text, from a Helm hook-delete policy, from an absent Event or from the passing of time. A leaf headline follows the three rules it followed before: a run still in flight never clears a recorded failure. No second way of reading cluster state is added: the watch uses the informer cache that already watches the kind `job`.
11. **The handler package does not grow.** `chrootSeedReconcilerObservations` (a method) and the second copy of its body in `motherSeedInClusterReconcilers` become one function, `seedReconcilerObservations(ctx, log, dyn, bridge, depID, seed)`, that both seeds call. With the new method `JobsReadAccess` the handler package keeps its 637 methods and has one line less. The log lines of the two seeds keep their prefixes `chroot seed:` and `mother seed:`; the mother line `in-cluster reconciler activities projected` becomes `reconciler activities projected`.
12. **Baselines.** `scripts/baselines/polling.json` loses the `go_ticker` count of `internal/handler/flow_snapshot_local.go` (its heartbeat stays in `allow`) and gains an `allow` entry for the 20-second ping of `internal/jobs/stream.go` with the reason `connection heartbeat, not a poll of remote state` and owner `CTL`. `scripts/baselines/api-structure.json` is written by the guard itself (`--write-baseline`), which lowers `handler_lines` by one.
13. The per-read seed of `ListJobs` and `GetJob` (`kickJobsSeedAsync`) stays as it is in this ticket. See field 11.

+// sseLines streams the lines of a GET to url.
+func sseLines(t *testing.T, url string) (int, <-chan string) {
+	t.Helper()
+	req, err := http.NewRequest(http.MethodGet, url, nil)
+	if err != nil {
+		t.Fatal(err)
+	}
+	resp, err := http.DefaultClient.Do(req)
+	if err != nil {
+		t.Fatal(err)
+	}
+	t.Cleanup(func() { _ = resp.Body.Close() })
+	lines := make(chan string, 256)
+	go func() {
+		defer close(lines)
+		sc := bufio.NewScanner(resp.Body)
+		sc.Buffer(make([]byte, 1<<20), 1<<24)
+		for sc.Scan() {
+			lines <- sc.Text()
+		}
+	}()
+	return resp.StatusCode, lines
+}

+// Package jobwatch closes the runs of the Jobs page from the Job watch of
+// the shared informer cache (internal/k8scache).
+//
+// A run of a Kubernetes Job is recorded by the seed as an Execution that
+// carries the Job's metadata.uid. When the watch reports that Job with a
+// terminal condition (Complete, SuccessCriteriaMet or Failed set to True),
+// in an added, modified or deleted event, the run is closed with that
+// outcome. The deleted event carries the last object the watch held, so a
+// Job that finished and was then deleted (by its TTL or by a Helm hook
+// policy) still closes its run.
+//
+// The rules:
+//
+//  1. The key is the Job's metadata.uid. Two Jobs with the same name in two
+//     namespaces, or a Job deleted and created again under one name, are
+//     different runs.
+//  2. The outcome is the Job's own terminal condition, nothing else. A Job
+//     that disappears without a terminal condition gives no verdict: its run
+//     stays as it is.
+//  3. The cluster id of the event is the deployment id of the jobs store.
+//     An event of a cluster with no store index changes nothing.
+package jobwatch
+
+import (
+	"context"
+	"log/slog"
+	"time"
+
+	"github.com/openova-io/openova/products/catalyst/bootstrap/api/internal/helmwatch"
+	"github.com/openova-io/openova/products/catalyst/bootstrap/api/internal/jobs"
+	"github.com/openova-io/openova/products/catalyst/bootstrap/api/internal/k8scache"
+)
+
+// kindJob is the k8scache kind name of batch/v1 Jobs.
+const kindJob = "job"
+
+// Source is the part of k8scache.Factory the watch uses.
+type Source interface {
+	Subscribe(user string, kinds map[string]struct{}) (<-chan k8scache.Event, func())
+}
+
+// Closer is the part of jobs.Store the watch uses.
+type Closer interface {
+	CloseJobRun(deploymentID, jobUID, status string, finishedAt time.Time) (bool, error)
+}
+
+// Run subscribes to the Job events of src and closes runs in st until ctx
+// ends or the subscription channel closes.
+func Run(ctx context.Context, src Source, st Closer, log *slog.Logger) {
+	ch, cancel := src.Subscribe("jobwatch", map[string]struct{}{kindJob: {}})
+	defer cancel()
+	for {
+		select {
+		case <-ctx.Done():
+			return
+		case ev, ok := <-ch:
+			if !ok {
+				return
+			}
+			Handle(ev, st, log)
+		}
+	}
+}
+
+// Handle applies one event. It reports whether a run was closed.
+func Handle(ev k8scache.Event, st Closer, log *slog.Logger) bool {
+	if ev.Kind != kindJob || ev.Object == nil {
+		return false
+	}
+	uid := string(ev.Object.GetUID())
+	if uid == "" {
+		return false
+	}
+	status, at, ok := Outcome(ev)
+	if !ok {
+		return false
+	}
+	closed, err := st.CloseJobRun(ev.Cluster, uid, status, at)
+	if err != nil {
+		if log != nil {
+			log.Warn("jobwatch: close run failed",
+				"cluster", ev.Cluster, "namespace", ev.Object.GetNamespace(), "job", ev.Object.GetName(), "err", err)
+		}
+		return false
+	}
+	if closed && log != nil {
+		log.Info("jobwatch: run closed from the Job watch",
+			"cluster", ev.Cluster, "namespace", ev.Object.GetNamespace(), "job", ev.Object.GetName(),
+			"status", status, "event", string(ev.Type))
+	}
+	return closed
+}
+
+// Outcome is the terminal outcome the event's Job object records: the jobs
+// status (jobs.StatusSucceeded or jobs.StatusFailed) and the time of the
+// terminal condition, or of the event when the condition has no time.
+// ok is false when the Job has no terminal condition.
+func Outcome(ev k8scache.Event) (status string, at time.Time, ok bool) {
+	st, _, finished := helmwatch.JobRunStatus(ev.Object)
+	switch st {
+	case helmwatch.ObsStatusSucceeded:
+		status = jobs.StatusSucceeded
+	case helmwatch.ObsStatusFailed:
+		status = jobs.StatusFailed
+	default:
+		return "", time.Time{}, false
+	}
+	if finished.IsZero() {
+		finished = ev.At
+	}
+	return status, finished.UTC(), true
+}
